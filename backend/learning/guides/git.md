# Git — справочник модели

Этот справочник собирает модель Git целиком: снимки, объекты, указатели, обмен копиями. Команды здесь — иллюстрации к модели, не шпаргалка «выучите 40 строк».

## Зачем контроль версий

Файловая система помнит только текущие байты пути. Копии папок (`финал2`) не дают честной цепочки «какое состояние следовало за каким» и плохо масштабируются на совместную работу. Система контроля версий хранит историю состояний и умеет сравнивать их.

Git хранит историю локально в базе `.git`. Сайт вроде GitHub — хостинг другой копии той же модели плюс интерфейс процессов (PR, права). Git ≠ GitHub.

Без истории ломаются три вещи: возврат к рабочему состоянию стенда, слияние чужих правок без перезаписи, безопасный эксперимент на отдельной линии. Снимки закрывают все три, если ими пользоваться осознанно.

## Снимок, не список патчей как единственная правда

Коммит логически — снимок дерева файлов. Diff пользователь видит потому, что Git умеет сравнить два снимка. Внутри неизменённые файлы часто разделяют одни и те же объекты содержимого (одинаковый хеш), поэтому «полный снимок» не означает наивную полную копию всех байтов каждый раз.

Когда говорят «Git запомнил правку», точнее сказать: Git запомнил новое состояние путей и связал его с предыдущим через родителя. Патч — удобное представление для глаз и для применения изменений, но источник правды для истории — граф снимков.

## Три области работы

1. **Рабочее дерево** — файлы на диске, которые открывает редактор.
2. **Индекс (staging)** — подготовленное содержимое следующего снимка: пути и хеши blob.
3. **База объектов** — blob, tree, commit (и tag) в `.git/objects`, плюс ссылки в `refs`.

Редактор пишет в (1). `git add` обновляет (2) и при необходимости создаёт blob в (3). `git commit` оформляет tree из индекса, пишет commit, двигает указатель ветки.

Пока правка только на диске, `git log` её не знает. Пока правка в индексе, но не в коммите, она войдёт в следующий снимок, но ещё не является историей ветки. Это разделение — главный антихаос против «закоммитил случайно всё подряд» и против «думал, что уже сохранил в историю».

## Объекты

- **blob** — байты файла без имени пути.
- **tree** — список записей «имя → тип + хеш» (файлы и поддеревья).
- **commit** — указатель на корневое tree, список родителей, автор, время, сообщение.
- **tag** (аннотированный) — объект с указанием на commit и метаданными; лёгкий тег — просто ref.

Адрес объекта — хеш от содержимого (с заголовком типа/размера). Изменили байты — другой адрес. Поэтому «подправить коммит» после публикации меняет историю для всех, у кого был старый хеш.

Имена путей живут в tree, не в blob. Один и тот же blob может фигурировать под разными именами в разных деревьях, если содержимое совпало. Это нормально и полезно для дедупликации.

## Указатели

- **Ветка** (`refs/heads/name`) — подвижное имя на commit. Создать ветку дёшево: новый файл-ссылка.
- **HEAD** — обычно указывает на имя текущей ветки (`ref: refs/heads/main`). Новый коммит двигает эту ветку. Detached HEAD смотрит прямо на хеш — коммиты не двигают ветку.
- **Тег** — обычно не двигают при обычной работе; закладка на релизный снимок.
- **Remote-tracking** (`refs/remotes/origin/main`) — локальная память о том, где была ветка на remote после fetch.

Ветка — не копия папки. Расхождение веток — разные commit на концах указателей. Переключение ветки перестраивает рабочее дерево под выбранный снимок (с оговорками про локальные незафиксированные правки).

## История как граф

Коммиты образуют DAG: у обычного коммита один родитель, у merge — два и более. `git log` обходит родителей от выбранной точки. Merge-коммит честно фиксирует интеграцию двух линий. Fast-forward — случай, когда достаточно передвинуть указатель без нового merge-узла: конец одной ветки — предок конца другой.

Читать историю полезно от вопроса: где появилась регрессия, какой снимок был на стенде, кто менял контракт. Сообщения коммитов — часть интерфейса для людей; «правки» и «wip» без контекста обесценивают граф.

## Слияние (merge)

Слияние подтягивает одну линию в другую. Если возможен fast-forward — указатель просто перематывается. Если линии разошлись — создаётся commit с двумя родителями и новым tree, собранным из обеих сторон относительно общего предка.

Направление важно: вы стоите на принимающей ветке и вливаете другую. После слияния проверяйте получившееся дерево и смысл, а не только «команда прошла».

## Rebase

Rebase повторяет смысловые шаги коммитов на новой базе, создавая **новые** commit-объекты с новыми хешами. Линия выглядит линейнее; цена — переписывание идентификаторов. Для уже опубликованной общей ветки это опасно без договорённости. Локальная ветка до push — типичное место применения.

Конфликты на rebase возможны на каждом переносимом шаге: каждый шаг заново прикладывается к новому основанию. Это не «баг rebase», а следствие новой базы.

## Удалённые копии

Remote — имя → URL другой базы объектов. `fetch` докачивает недостающие объекты и обновляет remote-tracking refs, не меняя ваши `heads` и рабочее дерево само по себе. `pull` — fetch плюс интеграция (merge или rebase) в текущую ветку. `push` отправляет объекты и просит remote сдвинуть ref; non-fast-forward отвергается, чтобы не потерять чужие снимки из указателя.

`origin` — лишь обычное имя первого remote после clone, не закон природы. Можно иметь несколько remote: `origin`, `upstream`, запасной сервер.

Сравнивайте `main` и `origin/main` как два указателя на графе. «Ahead/behind» — про коммиты, которых нет у другой стороны, а не про «файлы не долетели».

## Clone

Clone создаёт локальную базу, забирает объекты, настраивает `origin`, checkout ветки. Это не ZIP без истории: у вас появляется граф коммитов (в полном клоне). После clone `git log` работает офлайн — история уже локальна.

ZIP с сайта удобен для разового взгляда на файлы, но без графа нельзя честно ветвиться, сливать и отвечать «что было на стенде в коммите X».

## Конфликты

Конфликт — автомат не собрал tree из двух изменений относительно общего предка. В файле маркеры границ. Нужно собрать осмысленное содержимое, убрать маркеры, `git add`, завершить merge/rebase. Конфликт — сигнал человеку, не «поломка Git».

Иногда правильный итог — одна сторона целиком, иногда — смысловой гибрид (не слепая склейка строк). После разрешения думайте о тестах и инвариантах проекта.

## Ignore

`.gitignore` отсекает неотслеживаемые пути от случайного добавления. Уже tracked файл сам по себе не исчезнет из истории из-за ignore. Секрет, попавший в commit, остаётся в объектах старых снимков — профилактика важнее «потом удалим».

Типичный игнор для Python-проектов: виртуальные окружения, кэш байткода, локальные `.env`, артефакты сборки. В снимок кладут то, что нужно воспроизвести проект, а не случайный мусор машины.

## Reset и revert

**Reset** двигает указатель текущей ветки на другой commit; режимы soft/mixed/hard решают, синхронизировать ли индекс и рабочее дерево. Hard опасен для незакоммиченного. На опубликованной истории reset+force ломает коллег.

**Revert** добавляет новый commit, отменяющий эффект выбранного, без переписывания хешей общей линии. Для уже запушенного — предпочтительный способ «отменить смысл».

Путать reset и revert — частая ошибка. Reset переписывает, где стоит ветка; revert наращивает историю «противоядием».

## Stash

Stash временно сохраняет незафиксированные правки и чистит витрину под HEAD. Это карман, не замена ветке и коммиту. Долгоживущий stash легко забыть. Для работы дольше часа обычно лучше осмысленный коммит на ветке задачи.

## Теги

Тег помечает конкретный commit для воспроизводимости выпуска. Ветка `main` уйдёт вперёд; `v1.2.0` останется на старом снимке. Двигать опубликованный тег — путать всех, кто уже собрал релиз по старому хешу.

## GitHub и PR

Хостинг хранит remote и даёт UI. Pull Request — процесс обсуждения и проверки перед слиянием веток на сервере; под капотом всё тот же граф. Хороший PR мал и осмыслен; CI проверяет снимок.

«Залить на GitHub» = локальные коммиты + remote + push. Кнопка на сайте не создаёт осмысленную историю за вас. Issues и wiki — рядом с кодом, но это не объекты Git.

## Рабочий цикл (скелет)

Обновить знание о main → ветка задачи → маленькие коммиты → push → PR → review → merge → обновить локальный main. Договорённости команды (rebase-only / merge-only / squash) важнее споров «как правильно в интернете».

Короткий цикл уменьшает размер диффов и боль конфликтов. Неделя работы без push — риск потерять связь с чужими снимками и накопить неразбираемый ком.

## Частые ментальные ошибки

- «Сохранил в редакторе = закоммитил».
- Путать `main` и `origin/main`.
- Думать, что fetch меняет файлы в редакторе.
- Force push в общий main.
- Коммитить `.env` и бинарный мусор.
- Rebase уже общей ветки без договора.
- Оставлять маркеры конфликта в файлах.

## Мини-схема

```text
рабочее дерево ─add─► индекс ─commit─► commit-объект
                                         ▲
ветка ────────────────────────────────────┘
HEAD → ветка
fetch обновляет origin/*
merge/rebase двигает вашу ветку к интеграции
push двигает ref на remote
```

Расхождение после совместной работы:

```text
main:          C1—C2—C3
feature:       C1—C2—C4—C5
origin/main:   C1—C2—C3     (после вашего fetch)
```

После merge feature в main появится узел с родителями C3 и C5 (если не fast-forward). После rebase feature на main появятся C4' и C5' поверх C3.

Идите по `06-git` по порядку: зачем → проблема → репозиторий → дерево → индекс → коммит → история → ветки → merge/rebase → remote/origin → clone/fetch/pull/push → конфликты → ignore/tags → reset/revert/stash → GitHub/PR → цикл. Этот справочник — карта; уроки дают задания и типичные ловушки.

## Практика закрепления

Нарисуйте на бумаге три коммита, две ветки, remote-tracking после fetch, и покажите стрелками, что двигает commit, merge, rebase, reset, revert. Если стрелки путаются — перечитайте разделы про объекты и refs, не список флагов команд.

Сделайте учебный репозиторий: два расходящихся коммита, merge с конфликтом в одной строке, разрешение, тег на результат, ветка эксперимента со stash. Перескажите вслух, какие объекты появились и какие указатели сдвинулись. Когда пересказ стабилен, команды перестают быть магией.

## Объекты: что именно лежит в `.git/objects`

Blob хранит содержимое файла без имени. Два файла с одинаковыми байтами — один blob. Имя файла живёт в tree. Tree — список записей «режим, имя, хэш». Коммит — снимок tree плюс родитель, автор, сообщение. Тег-объект (аннотированный) указывает на коммит и хранит подпись и текст.

Хэш — идентификатор содержимого. Поменять байт файла — новый blob, новый tree, новый коммит. Старые объекты остаются, пока на них есть ссылка из коммита, ветки, тега или reflog. Поэтому «удалить коммит» командой reset обычно прячет его, а не стирает сразу.

## Refs и reflog

Ветка — файл или запись в `packed-refs` с хэшем коммита. `HEAD` — либо символическая ссылка на ветку, либо «отделённый» HEAD прямо на коммит. `origin/main` — локальная копия чужой ветки, обновляется fetch, не вашим commit.

Reflog помнит, куда смотрели HEAD и ветки. После ошибочного reset по reflog часто можно найти потерянный коммит. Это журнал указателей, не замена истории для команды: у коллег вашего reflog нет.

## Конфликт: что сравнивается

При merge Git находит общего предка и смотрит, как каждая сторона изменила одни и те же строки. Если правили разные места, слияние часто проходит само. Если правили одну строку — конфликтные маркеры в рабочем дереве. Разрешение — новый blob, который вы сами собрали, и коммит с двумя родителями.

Rebase переписывает ваши коммиты поверх новой базы. Хэши меняются. Уже отправленную и разобранную коллегами ветку rebase-ить без договорённости опасно: их работа ссылается на старые хэши.

## Команды как движение указателей

| Действие | Что двигается | История |
| --- | --- | --- |
| commit | текущая ветка и HEAD | новый коммит |
| fetch | origin/* | локальные ветки не трогает |
| merge | текущая ветка | новый коммит или fast-forward |
| rebase | текущая ветка | новые коммиты, старые остаются в reflog |
| reset --soft | ветка | индекс и файлы на месте |
| reset --mixed | ветка и индекс | файлы на месте |
| reset --hard | ветка, индекс, файлы | незакоммиченное пропадает |
| revert | ветка | новый коммит, отменяющий изменения |
| stash | отдельный стек | рабочее дерево очищается |

`pull` — это fetch и затем merge или rebase. Путаница «pull не забрал» обычно значит: fetch прошёл, а интеграция остановилась на конфликте, либо смотрели не ту ветку.

## `.gitignore` и то, что уже в истории

Игнор не даёт новым неотслеживаемым файлам попасть в индекс. Файл, который уже коммитили, игнор не выкинет. Секреты в истории нужно убирать отдельной переписью истории и ротацией ключа: удаление файла в новом коммите оставляет blob в старых.

## Мини-разбор конфликта

Было `timeout = 5`. Вы написали `timeout = 8`. Коллега написал `timeout = 12` и добавил комментарий. Общий предок — строка с 5. Обе стороны изменили её. Git не знает, что «правильно» 12 с комментарием или 8. Вы выбираете смысл: например `timeout = 12` и комментарий коллеги, затем `git add` и завершение merge. Это не магия маркеров, а ручная сборка нового blob.

## Разбор типичных сценариев

### «Нужно срочно поправить main, а я на feature с грязным деревом»

Сначала решите судьбу правок: stash, или коммит на feature, или отмена. Чистое дерево упрощает переход. Затем `fetch`, обновление main по правилам команды, hotfix-ветка от актуального main, маленький коммит, push, PR. Грязный эксперимент на feature не должен смешиваться с hotfix в одном снимке без нужды.

### «Push отвергнут»

На remote есть коммиты, которых нет в вашей истории этой ветки. Сделайте fetch, посмотрите `origin/ветка`, выберите merge или rebase по договору, разрешите конфликты, затем push снова. Force имеет смысл только если вы сознательно переписываете свою не общую ветку и команда это допускает.

### «Случайно закоммитил секрет»

Ignore после факта не вычищает историю. Нужно убрать секрет из текущего снимка, сменить сам секрет (он уже мог утечь), и отдельно решать, переписывать ли историю (дорого в общей ветке) или жить с тем, что старые объекты ещё содержат значение, пока репозиторий не очищен специальными средствами. Профилактика через ignore и ревью — дешевле лечения.

### «Два человека правили один файл»

Общий предок + две линии → merge или rebase. Конфликт в одних строках — человеческое решение. Разные строки часто сливаются автоматически, но логический конфликт («оба поменяли смысл протокола») автоматом не ловится: нужны тесты и чтение диффа.

## Словарь указателей ещё раз

| Имя | Что это | Движется ли само |
|-----|---------|------------------|
| `main` | ветка = ref на commit | да, при коммите на неё |
| `HEAD` | «где я» | следует за веткой или detached |
| `origin/main` | память о remote | при fetch/pull |
| `v1.0.0` | тег | обычно нет |
| индекс | черновик tree | при add/reset |

## Что не входит в этот справочник намеренно

Тонкие флаги каждой команды, редкие porcelain-опции, серверные хуки CI в деталях, LFS как отдельная подсистема. Их осмысленно смотреть после устойчивой модели снимков. Без модели флаги превращаются в суеверия.

## Контрольные вопросы

1. Чем commit отличается от «файла в облаке»?
2. Что именно двигает `git commit` — рабочее дерево, индекс или указатель ветки?
3. Почему `origin/main` нельзя «просто коммитить как ветку»?
4. Чем merge-коммит отличается от fast-forward?
5. Почему rebase меняет хеши?
6. Когда предпочтительнее revert, а не reset?
7. Что делает fetch с рабочим деревом в типичном случае?

Ответы должны ссылаться на объекты и refs. Если ответ — только имя команды, модель ещё не села.

## Итог

Git — база объектов-снимков и указателей на них, плюс три зоны (дерево, индекс, история) и обмен копиями. Выучите стрелки. Команды станут короткими ярлыками к уже понятным движениям.

Держите рядом схему «blob ← tree ← commit ← ветка ← HEAD» и отдельно схему «fetch обновляет origin/*, push двигает remote ref». Если обе схемы рисуются без подсказки, модуль Git можно считать усвоенным на базовом уровне, достаточном для командной работы над учебным и стендовым кодом.
