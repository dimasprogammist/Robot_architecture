# Справочник · Терминал и командная строка

Краткий опорный текст к модулю terminal. Здесь собраны механизмы, а не список флагов «на все случаи».

## 1. Слои: терминал, TTY, shell, программа

Эмулятор терминала рисует текст и принимает клавиши. Псевдотерминал (PTY) связывает окно с процессами. Драйвер линии обрабатывает канонический ввод и спецклавиши (Ctrl+C → SIGINT). Shell читает строки команд, разбирает их и запускает программы. Утилита делает работу через системные вызовы.

Путаница слоёв приводит к ложным диагнозам: цвет «не работает» часто из-за не-TTY; Tab — настройка shell; зависание — процесс утилиты.

Команда `tty` показывает slave PTY текущей сессии. Разные вкладки — разные `/dev/pts/N`.

## 2. Shell как процесс

Shell — пользовательская программа. Builtin (`cd`, `export`) меняют его состояние. Внешние команды ищутся в PATH и запускаются как отдельные процессы. PATH — упорядоченный список каталогов.

Интерактивный режим даёт prompt. Неинтерактивный читает скрипт или `-c`. Состояние (переменные, функции) живёт, пока жив процесс shell, если не сохранено в профиле.

`type`/`command -v`/`Get-Command` помогают понять, builtin это или внешний файл.

## 3. Разбор командной строки и argv

Программа получает массив argv, не «сырую строку пользователя». Границы токенов задаёт shell: пробелы, кавычки, экранирование. Glob раскрывается до запуска, если есть совпадения.

В bash одинарные кавычки почти буквальны; двойные допускают `$var` и подстановки. `"$var"` защищает пробелы. Незакавыченный `$var` подвержен word splitting.

Маркер `--` у многих утилит означает конец опций: дальше имена файлов, даже с ведущим дефисом.

Отладка: печать `sys.argv` / `printf '%q\n' "$@"`.

## 4. Стандартные потоки

Дескрипторы: 0 stdin, 1 stdout, 2 stderr. На экране они часто сливаются, но перенаправляются раздельно. Данные для следующего этапа — в stdout; диагностика — в stderr.

Фильтры читают stdin и пишут stdout. EOF с клавиатуры — Ctrl+D в типичном UNIX-терминале.

isatty влияет на цвет, pager и буферизацию. В pipe stdout часто блочно буферизуется.

## 5. Конвейер

`|` создаёт pipe в ядре: stdout слева на write-конец, stdin справа на read-конец. Процессы работают параллельно; заполненный буфер тормозит писателя (backpressure). stderr по умолчанию не в pipe.

Статус конвейера без `pipefail` — обычно статус последней стадии. В скриптах включайте `set -o pipefail`.

`tee` копирует поток в файл и дальше по трубе — удобно для отладки середины цепочки.

## 6. Перенаправление

`>` обрезает/создаёт файл для stdout; `>>` дописывает; `<` подаёт файл на stdin; `2>` — stderr. Объединение: `>file 2>&1` (порядок важен!). Обратный `2>&1 >file` ведёт себя иначе.

Не направляйте вывод команды в тот же файл, который она читает, без промежуточного буфера: shell обрежет файл до запуска.

Права на каталог проверяются при open. Ошибка перенаправления может случиться до полезной работы команды.

## 7. Пути

POSIX: `/` корень, разделитель `/`. Windows: диски и `\`, хотя многие API принимают `/`. cwd — свойство процесса; относительные пути от него.

`.` текущий каталог, `..` родитель. Symlink добавляет косвенность; `pwd -L`/`-P` различают логику и физику.

Абсолютный путь независим от cwd. Относительный удобен в репозитории. В скриптах часто вычисляют базу от расположения файла (`BASH_SOURCE`). cron/systemd предпочитают абсолютные пути.

Регистр имён на Linux обычно важен. Склейка путей — через библиотеки (`pathlib`), не конкатенацией вслепую.

## 8. Окружение

Окружение — набор `ИМЯ=значение` у процесса, копируется детям при exec. `export` в bash помечает переменную для наследования. `VAR=value cmd` задаёт на один запуск.

Типичные: PATH, HOME, LANG, USER. Интерактивный профиль ≠ окружение systemd/cron. Секреты в окружении видны в `/proc` и наследуются — ограничьте срок жизни.

Подстановка `$VAR` делает shell до запуска; программа может читать getenv сама.

## 9. Код возврата

Ноль — успех по соглашению. Ненуль — класс ошибки (см. документацию утилиты). `$?` в bash хранит статус до следующей команды.

`&&` / `||` ветвят по статусу. `if cmd` тоже смотрит статус, не текст. Сигналы дают характерные коды (часто 128+n).

`set -e` прерывает скрипт при ошибках простых команд (с оговорками). Не глушите ошибки массовым `|| true` без причины.

## 10. Скрипты

Shebang `#!/usr/bin/env bash` выбирает интерпретатор. Нужен execute bit для `./script`. Аргументы: `$1`…`$@`, всегда кавычки.

Строгий режим: `set -euo pipefail`. Явный PATH. Не полагайтесь на cwd. Shell — клей; сложную логику выносите в язык приложения.

Отладка: `bash -x`. Ловушки `trap` для очистки.

## 11. Bash — опорные конструкции

Переменные-строки, `[[ ]]` условия, циклы `for`/`while`, функции с `local`, подстановки `$()` и `${var%pattern}`. Alias в скриптах не надёжны.

На минимальных образах может не быть bash — только `sh`. Не смешивайте диалекты.

## 12. PowerShell — контраст

Конвейер объектов, cmdlet Verb-Noun, именованные параметры. `$env:NAME`, `$LASTEXITCODE` для native-программ. Execution policy может блокировать `.ps1`.

Не переносите bash-quoting буквально. Форматированный текст на экране ≠ объект в pipeline.

## 13. Базовые утилиты через механизм

`ls` читает каталог/stat. `cat` — read/write. `cp` копирует данные. `mv` часто rename в одной ФС, иначе copy+delete. `rm` убирает имя; блоки живут, пока открыты fd и ненулевой nlink. `find` обходит дерево. `grep` фильтрует поток. `ps` читает `/proc`.

GNU и BSD флаги различаются. Для скриптов — стабильный вывод.

## 14. Job control и сигналы (кратко)

Foreground получает сигналы TTY. Ctrl+Z останавливает; `bg`/`fg` управляют. Фоновые задачи с `&` не должны считаться заменой супервизору на проде.

SIGTERM — вежливая остановка; SIGKILL — без очистки. Сначала TERM.

## 15. Профили и точки входа

Login/non-login, interactive/non-interactive читают разные файлы (`/etc/profile`, `~/.profile`, `~/.bashrc`…). Документируйте, какой путь нужен вашему сценарию. В CI задавайте окружение явно.

## 16. Практический чеклист отладки команды

1) Команда найдена? (`type`, PATH). 2) argv правильный? (кавычки). 3) cwd тот? 4) Права на файлы? 5) stdout/stderr куда? 6) Код возврата? 7) TTY или pipe? 8) То же окружение, что в проде?

## 17. Мини-шпаргалка синтаксиса bash

```bash
cmd >out 2>err
cmd >both 2>&1
cmd1 | cmd2
export VAR=1
VAR=1 cmd
echo "$VAR"
./script.sh arg1
echo $?
```

## 18. Чего справочник намеренно не делает

Не заменяет `man`. Не перечисляет все флаги `tar`/`find`. Даёт модель, чтобы man читался осмысленно.

## 19. Связь с Linux-модулем

Когда команды касаются прав, процессов и служб, смотрите справочник Linux: там FHS, systemd и journal. Терминал объясняет, как вы запускаете; Linux — где это живёт на хосте.

## 20. Типовые сценарии

Пакетная обработка логов: `grep | sort | uniq -c`. Копия артефакта: `cp`/`rsync` с явными путями. Одноразовая диагностика: цепочка `ps`/`ss`/`journalctl` в shell. Обёртка деплоя: строгий bash-скрипт + код возврата в CI.

## 21. Безопасность командной строки

Не вставляйте недоверенный текст в `eval`. Осторожнее с `curl | sh`. Не кладите секреты в историю shell и world-readable скрипты. Ограничивайте PATH. На общих машинах не оставляйте agent с ключами без политики.

## 22. Кодировки и перевод строк

UTF-8 — практический стандарт. CRLF с Windows ломает shebang и скрипты. `file`/`dos2unix` помогают. Локаль влияет на сортировку и десятичную точку — в CI часто `LANG=C.UTF-8`.

## 23. История и удобства

История shell — ускоритель и источник утечек (пароли в командах). Отключайте запись чувствительных команд. Completion экономит время, но учите и полные имена опций для скриптов.

## 24. Когда переходить с shell на другой язык

Появились структуры данных, сложная обработка ошибок, параллелизм с состоянием, HTTP с ретраями — пишите на Python/Go/… Shell оставьте для склейки и запуска.

## 25. Итог модели

Вы всегда имеете дело с процессом, его дескрипторами, argv, окружением и кодом возврата. Терминал показывает байты; shell интерпретирует язык запуска; ядро исполняет. Держите эту тройку в голове — и любая новая утилита встраивается в уже понятную схему.

## Дополнение: практика и нюансы

Этот раздел расширяет справочник практическими проверками. Выполняйте их на учебной машине и сохраняйте выводы.

Привязывайте каждый симптом к механизму из основного текста. Если не можете назвать слой или компонент — возвращайтесь к соответствующему уроку курса.

Проверочный лист терминала: type/command -v; echo "$?"; tty; printf тест кавычек; одна команда с > и 2>; один pipe с pipefail; printenv PATH; bash -n script.sh.

Типовые ловушки: CRLF в скриптах; alias в non-interactive; PATH cron; glob без совпадений; перенаправление в тот же файл; секрет в history.

Связка с Linux: права execute на скрипт; shebang интерпретатор установлен пакетом; логи обёртки уходят в journal при запуске из unit.

Связка с сетями: curl/wget как клиенты; ss через shell; SSH как защищённый канал до того же shell на сервере.

Рекомендуемый порядок обучения: shell → streams → paths → pipe/redirect → env/exit → scripts → bash/PowerShell → базовые утилиты.

Мини-лаборатория: создайте каталог lab_term, скрипт count_lines.sh, который считает строки всех *.log через pipe и возвращает ненуль, если логов нет. Прогоните успех и ошибку.

Критерий зрелости: вы объясняете коллеге разницу builtin/внешняя команда и почему cd нельзя заменить обычным бинарником без смены модели.

Дополнительно про профили: login shell читает другие файлы, чем интерактивный non-login. Проверьте на своей системе man bash раздел INVOCATION и составьте таблицу «режим → файлы».

Дополнительно про кодировки: `locale`, `file`, `iconv`. В логах фиксируйте UTF-8. Для бинарных протоколов не используйте текстовые редиректы вслепую.

Дополнительно про безопасность: sudo права на конкретные скрипты лучше, чем полный root; проверяйте, что скрипт нельзя перезаписать недоверенным пользователем.

Дополнительно про отладку: `PS4='+${BASH_SOURCE}:${LINENO}: '` вместе с `set -x` показывает место в скрипте. Убирайте -x после разбора, чтобы не светить секреты в логах.

Дополнительно про переносимость: пишите POSIX-подмножество, если цель — ash/dash в контейнере; или фиксируйте `bash` в shebang и образе.

Дополнительно про Windows: Git Bash, WSL и PowerShell — три разных мира. Для серверного Linux-таргета проверяйте скрипты в Linux/WSL, не только в Git Bash.

Дополнительно про документацию команд: в runbook храните точные команды с ожидаемым выводом-образцом (санитизированным). Это ускоряет ночные инциденты.

Закрепление: раз в неделю разбирайте одну «сломанную» однострочник-команду из истории и переписывайте её в читаемый фрагмент скрипта со строгим режимом.


Проверьте согласованность настроек после перезагрузки: разовые правки ip/sysctl часто исчезают без конфига.

Сверьте документацию сервиса с фактическим unit или командой запуска: расхождения дают сюрпризы.

Зафиксируйте ожидаемый код возврата успешного сценария в runbook рядом с командой проверки.

Сравните поведение на TTY и в pipe: буферизация и цвет меняют вывод без смены логики программы.

Убедитесь, что время хоста синхронизировано: ложные ошибки TLS и путаница в логах часто из-за часов.
