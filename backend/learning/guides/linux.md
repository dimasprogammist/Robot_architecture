# Справочник · Linux

Опора к модулю linux: устройство хоста глазами администратора и разработчика сервисов.

## 1. Ядро и user space

Linux-ядро управляет CPU, памятью, процессами, сетью и драйверами. Приложения в user space делают системные вызовы. Дистрибутив = ядро + user space (утилиты, init, пакеты, политики).

Контейнеры используют namespaces и cgroups того же ядра. Это изоляция процессов, не отдельное ядро на контейнер (в обычной схеме).

Модули ядра подгружают драйверы. Версия `uname -r` важна для совместимости.

## 2. Устройства и виртуальные ФС

`/dev` — узлы устройств (блочные и символьные). Запись «не туда» губит данные. `/proc` и `/sys` — интерфейсы состояния ядра и устройств, не обычные дисковые файлы.

udev создаёт узлы и правила имён/прав при появлении железа. Для USB-устройств роботов права группы и правил udev критичны.

## 3. FHS — карта каталогов

`/bin`, `/usr/bin`, `/sbin` — программы. `/etc` — конфигурация. `/var` — переменные данные и логи. `/home` — дома пользователей; `/root` — дома root. `/opt`, `/srv` — опциональное ПО и данные сервисов. `/tmp`, `/var/tmp` — временное с разной политикой. `/boot` — ядро и загрузчик. `/mnt`, `/media` — монтирования.

Свои данные службы: `/var/lib/имя`. Свой конфиг: `/etc/имя`. Не складывайте state в `/usr`.

## 4. Пользователи и группы

UID/GID — то, что проверяет ядро. Имена — удобство. root = 0. Сервисные учётки ограничивают ущерб. Группы дают общий доступ (к устройствам, docker-сокету).

`id`, `getent passwd`, `getent group` — диагностика идентичности. sudo — делегирование с аудитом лучше постоянного root-login.

Файлы passwd/group/shadow: парольные хэши защищены правами shadow.

## 5. Права файлов

Режим: rwx для owner/group/others. У каталога x — проход; w — создание/удаление имён. Sticky на `/tmp` мешает удалять чужое. setuid опасен.

`chmod`, `chown`, `umask`. Секреты — `600` и правильный владелец. `777` — запах неисправной модели прав.

ACL расширяют модель; базу rwx знать обязательно. Цепочка каталогов тоже требует x.

## 6. Процессы

PID, PPID, состояния, зомби до wait. Сигналы: TERM, INT, HUP, KILL. Сначала вежливые сигналы. nice — приоритет CPU, не «ускорение диска».

`/proc/<pid>/` — cmdline, environ, fd, status. `ps`, `top`/`htop` читают эти данные. Лимиты fd/памяти — ulimit и cgroups.

## 7. Службы и супервизор

Долгий процесс на проде держит супервизор (systemd): автозапуск, restart policy, зависимости, логи. Не заменяйте это tmux.

Служба бежит от сервисного пользователя с явным WorkingDirectory и Environment. Foreground-процесс под супервизором предпочтительнее самодемонизации.

## 8. systemd

Юниты: `.service`, `.timer`, `.socket`, `.target`. Секции `[Unit]`, `[Service]`, `[Install]`. `enable` ≠ `start`. После правок файлов — `daemon-reload`.

Кастом — в `/etc/systemd/system/` или drop-in `*.service.d/`. `systemctl status/cat/restart`. Логи: `journalctl -u имя`.

Type=simple — главный процесс ExecStart. Неверные User/пути — тихие fail-loop.

## 9. Сеть на хосте

`ip link`, `ip addr`, `ip route`, `ss -lntp`. Интерфейсы, адреса, default route, слушатели — четыре разных вопроса.

DNS на хосте — resolv/systemd-resolved. Firewall отдельно от «порт слушает». Persist настроек — через конфиг NetworkManager/networkd/distro, не только разовый `ip`.

## 10. Пакеты

Пакет = файлы + зависимости + скрипты + учёт. Репозитории с подписями. apt/dnf/pacman… — по семейству. Спрашивайте «какой пакет владеет файлом».

Не смешивайте ручные копии в `/usr` с пакетами. Языковые экосистемы (pip/npm) — отдельный слой; системные демоны лучше штатно или в контейнере с политикой.

## 11. Логи

journald + `journalctl` (unit, priority, since, boot). `/var/log` + logrotate. `dmesg` — ядро. Не логируйте секреты. Полный диск — частая авария.

Метод: status → journal unit → app log → kernel. Сужайте время. Ищите первопричину, не последний ERROR.

## 12. Конфигурация слоями

sysctl/cmdline; `/etc`; unit Environment; процесс environ; user profile. SSH-сессия ≠ окружение службы. Отладка: `/proc/pid/environ`, `systemctl show`.

Drop-in сохраняет обновляемость пакетов. Секреты — узкие права, не git.

## 13. SSH

sshd слушает (часто 22). Ключи лучше паролей. Публичный в `authorized_keys`, приватный секретен. `known_hosts` защищает от смены host key. Права на `~/.ssh` строгие.

`~/.ssh/config` — алиасы и ключи. На сервере ограничьте root/password login. Обновляйте sshd.

## 14. Повседневный runbook хоста

hostname/date/uptime → df/free → systemctl --failed → journalctl -p err → ip route → ss -lntp → логи приложения. Меняйте мало, с копией конфига и проверкой статуса. Документируйте исключения.

## 15. Диски и место (кратко)

`df -h` — ФС. `du -sh` — деревья. Запас inode важен. Логи и контейнерные слои заполняют диск незаметно. Мониторьте до 100%.

## 16. Время и синхронизация

Неверные часы ломают TLS и логи. `timedatectl`, chrony/ntp. В распределённых системах время — часть контракта.

## 17. Безопасность базового хоста

Минимум открытых портов, обновления, отдельный пользователь для приложения, sudo по необходимости, SSH-ключи, firewall, бэкапы с проверкой restore. SELinux/AppArmor — по политике дистрибутива, не отключайте «чтобы заработало» без понимания.

## 18. Отладка «в терминале работает, в службе нет»

Сверьте User, PATH, cwd, переменные, права на файлы, SELinux context, наличие TTY, зависимость от сети after=. Читайте journal той же unit.

## 19. Таймеры и cron

systemd-timer или cron запускают задачи по расписанию. Окружение бедное — задавайте явно. Логируйте вывод. Не запускайте интерактивное без TTY.

## 20. Сеть namespace и контейнеры (обзор)

У контейнера свой сетевой namespace и интерфейсы. `ss` на хосте ≠ `ss` в контейнере. Проброс портов — отдельная карта. Для отладки заходите в нужный namespace.

## 21. Полезные команды-опоры

```bash
uname -a
id
df -h
ip addr
ip route
ss -lntp
systemctl --failed
journalctl -u SERVICE -n 50 --no-pager
ps aux --sort=-%mem | head
```

Интерпретируйте результат по разделам этого справочника, не как магический тотем.

## 22. Файлы конфигурации: практика правок

Копия до правки. Комментарий «почему». Reload/restart по документации. Проверка статуса и healthcheck. Запись в журнал изменений хоста/репозиторий конфигурации.

## 23. Производительность: с чего начать

Load average и CPU; память и swap; диск iowait; сеть errors/drops; рестарты unit. Одна метрика редко врёт, набор — чаще. `vmstat`/`iostat`/`sar` — углубление.

## 24. Резервное копирование

Что: данные `/var/lib`, конфиги `/etc`, секреты (отдельно и шифрованно). Как часто. Куда. Проверка восстановления. Снимки дисков ≠ приложение-consistent без подготовки.

## 25. Итог модели Linux-хоста

Идентичность (who) → права (на что) → процессы (что бежит) → супервизор (кто следит) → пакеты (откуда софт) → логи (что случилось) → сеть (как достучались). Терминал — способ спросить; Linux — предмет ответа.

## Дополнение: практика и нюансы

Этот раздел расширяет справочник практическими проверками. Выполняйте их на учебной машине и сохраняйте выводы.

Привязывайте каждый симптом к механизму из основного текста. Если не можете назвать слой или компонент — возвращайтесь к соответствующему уроку курса.

Проверочный лист хоста: uname -r; id; df -h; ip route; ss -lntp; systemctl --failed; journalctl -p err -n 20; ls /etc и /var/log.

Типовые ловушки: служба без User; секрет 644; диск 100%; DNS vs route; SSH host key changed; drop-in забыли daemon-reload.

Связка с терминалом: все осмотры делаются через shell; скрипты runbook — строгий bash; коды возврата для автоматизации осмотра.

Связка с сетями: ip/ss на хосте — край модели LAN; дальше протоколы из модуля networks объясняют DNS/TCP/HTTP.

Лаборатория: unit-файл простого python -m http.server от user nobody/другой сервисный (в VM), логи в journal, автозапуск выключен до проверки.

Критерий зрелости: вы находите причину «в SSH работает, в systemd нет» сравнением environ и WorkingDirectory без угадывания.

Дополнительно про диски: UUID в fstab надёжнее букв устройств. После клонирования дисков проверяйте mount.

Дополнительно про пользователей: expire и lock учёток (`chage`, `usermod -L`) — часть offboarding.

Дополнительно про journal: `journalctl --disk-usage` и vacuum-size предотвращают сюрпризы на маленьких дисках.

Дополнительно про пакеты: после ручного «лечебного» удаления файла верните его пакетом (`apt-get install --reinstall`).

Дополнительно про SSH: отдельные ключи на роли (deploy vs admin), а не один ключ на всё.

Дополнительно про время: TLS и логи лгут при неверных часах — включите chrony/ntp в базовый образ.

Дополнительно про hardening: минимальный набор пакетов, автоматические security updates по политике, отдельный admin-user.

Дополнительно про контейнеры на Linux: понимайте, что root в контейнере может быть root на хосте без user namespace — изучайте runtime.

Закрепление: составьте одностраничный паспорт стенда (версии, IP, unit'ы, диски) и обновляйте после каждого изменения.


Разделите метрики ошибок транспорта и прикладных 4xx/5xx — это разные классы проблем.

Проверьте политику ретраев на идемпотентность метода, чтобы не создать дубликаты.

Сверьте версии TLS на клиенте и сервере при загадочных handshake failure.

Посмотрите journal за окно инцидента целиком, не только последнюю строку ERROR.

Проверьте, что пакетный менеджер владеет ключевыми бинарниками, а не конфликтует с ручной копией.

Убедитесь, что firewall и security group оба пропускают нужный порт.

Проверьте sticky-сессии для WebSocket за балансировщиком при «прыгающем» канале.

Сверьте Content-Type и схему тела ответа API с тем, что парсит клиент.

Проверьте аренду DHCP и резервации до смены коммутатора или точки доступа.

Убедитесь, что ARP или ND к шлюзу снова REACHABLE после краткого обрыва.

Посмотрите, не перехватывает ли корпоративный прокси HTTPS своим CA.

Проверьте, что cron или таймер запускает тот же интерпретатор и PATH, что ручной прогон.

Сверьте порядок зависимостей After и Wants при гонках старта сети и приложения.
