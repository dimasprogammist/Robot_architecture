# Операционная система — справочник

Справочник по ОС для проекта Robot Architecture. Дополняет модуль курса `os-*` и пересекается с `guide-computer`, но фокус здесь — договор между программами и ядром: ресурсы, изоляция, ФС, права, службы, сигналы, запуск.

## 1. Зачем ОС существует

Проблемы без посредника на машине общего назначения:

- конфликт за CPU, память, устройства;
- необходимость писать драйверы в каждом приложении;
- отсутствие единой политики безопасности;
- невозможная переносимость ПО между партиями железа.

ОС даёт абстракции (процесс, файл, сокет), мультиплексирует ресурсы и остаётся арбитром в привилегированном режиме.

### Что ОС не обязана давать

- Гарантии жёсткого realtime (нужны RTOS/патчи/вынос контура).
- Защиту от логических ошибок вашего алгоритма.
- Бэкапы данных — это политика выше.

## 2. Архитектура: ядро и userland

```
[ приложения, демоны, оболочки ]
        ↓ API/libc/syscalls
[ ядро: планировщик, MM, VFS, сеть, драйверы ]
        ↓
[ железо ]
```

- **Ядро** — привилегированный код.
- **Userland** — всё остальное: утилиты, GUI, ваши сервисы, пакетный менеджер.
- **Дистрибутив** — согласованная сборка ядра + userland + политики.

Монолитное vs микроядро: где живут драйверы и сервисы. Linux — преимущественно монолит с модулями; идея границы режимов CPU сохраняется везде.

## 3. Системные вызовы

Единственный легальный «официальный» вход приложения к услугам ядра (плюс faults/IRQ). Примеры классов:

- процессы: clone/fork, execve, exit, wait;
- файлы: open, read, write, close, fsync;
- память: mmap, brk, mprotect;
- сеть: socket, connect, sendto, epoll;
- синхронизация и сигналы: futex, kill, sigaction.

Библиотека C и runtime языков оборачивают syscall. Ошибка возвращается как код / errno / исключение языка.

### API vs ABI

- API — имена и семантика для программиста.
- ABI — двоичная совместимость (структуры, соглашения вызовов, номера syscall).

Смена major glibc или архитектуры CPU ломает ABI даже при похожем API.

## 4. Процессы

### Сущность

Процесс = учётная запись в ядре + адресное пространство + ресурсы (fd, сигналы, креды). PID идентифицирует. PPID — родитель.

### Состояния (упрощённо)

running, runnable, sleeping/blocked, stopped, zombie.

Zombie = завершился, но статус не собран родителем через wait. Лечится корректным wait/SIGCHLD-обработкой или переходом под init.

### Изоляция

Запись по указателю в процессе A не попадает в память B (без явного IPC). Это база безопасности и устойчивости.

### IPC (кратко)

pipe, unix socket, TCP/UDP, shared memory, message queues, файлы, сигналы (бедные по данным). Выбор — по надёжности, копиям данных, задержке.

## 5. Память процесса

Виртуальные области (VMA): код, данные, heap, stacks, mmap file-backed и anonymous.

Трансляция через page tables. COW на fork. RSS vs VSZ. Page cache принадлежит ОС, не «памяти Chrome» в бытовом счёте, но конкурирует за RAM.

OOM: ядро выбирает жертву или отказывает в аллокации — зависит от настроек overcommit и cgroup limits (контейнеры!).

### Практические лимиты

ulimit, cgroups v2 memory.max, commit charge на Windows. Робот в контейнере с 256 МиБ умрёт иначе, чем на хосте с 8 ГиБ.

## 6. Потоки с точки зрения ОС

Планируемая сущность часто = поток ядра (task в Linux). Процесс — группа потоков с общим mm. Синхронизация — ответственность программы (мьютексы, атомики). Сигналы + threads = осторожный дизайн.

## 7. Файловая система глазами ядра

VFS унифицирует ext4/nfs/tmpfs/proc. Объекты: inode, dentry, file, superblock.

Дескриптор в процессе → file object → inode → страницы/данные.

Нюансы:

- unlink открытого файла — данные живут до последнего close;
- writeback асинхронный; fsync для барьера;
- directory permissions: x для traverse;
- спецФС: proc/sysfs как интерфейсы ядра;
- mount namespaces в контейнерах меняют видимое дерево.

### Надёжная запись конфига

Паттерн: писать во временный файл на том же ФС → fsync → rename поверх цели. Rename в пределах одной ФС обычно атомарно для имени.

## 8. Права доступа

Субъект: UID, GID, groups, capabilities. Объект: файл/директория/устройство + mode/ACL + иногда MAC (SELinux).

Классика rwx для u/g/o. Каталожный x обязателен для пути. setuid опасен. 777 — запах проблемы.

Устройства: группы `dialout`, `video`, `gpio` и udev-правила решают доступ без root.

Windows: ACL и SID; UAC отделяет повышение привилегий.

## 9. Пользователи и аутентификация

/etc/passwd + shadow (или каталог LDAP). Root = UID 0. Системные пользователи для демонов без login shell.

sudo лучше постоянной работы под root. PAM стыкует методы входа. В контейнерах UID mapping может обмануть интуицию владельца файлов на томах.

## 10. Службы и init

systemd unit: ExecStart, User, Restart, After/Requires, Environment, Limits.

Политика stop: SIGTERM → таймаут → SIGKILL. Пишите graceful shutdown.

Альтернативы: SysV, OpenRC, Windows Services, supervisord, docker restart policies — одна идея desired state.

Антипаттерн продакшена: вечный `screen` без мониторинга.

## 11. Окружение и PATH

Env — массив строк процесса, наследуется детьми. Не секрет-хранилище. PATH задаёт поиск команд.

Разные миры env: интерактивный bash, cron, systemd, CI. Фиксируйте абсолютные пути в unit или явный EnvironmentFile.

LD_LIBRARY_PATH / PYTHONPATH — мощно и ломко; предпочитайте штатную установку и venv.

## 12. Сигналы

Асинхронные уведомления. SIGTERM — штатная остановка; SIGKILL — нет handler. SIGINT — Ctrl+C. SIGHUP — часто reload у демонов (по соглашению).

Ограничения: коалесцирование, мало данных, async-signal-safety. Предпочтительны флаги + signalfd/self-pipe в сложных программах.

Для роботов: обработчик TERM должен обесточить актуаторы по политике безопасности.

## 13. Запуск программ

Цепочка: поиск пути → проверка прав → fork/spawn → execve → динамический линкер → точка входа → main/runtime.

Диагностика по этапу: not found / permission denied / wrong ELF class / missing .so / runtime exception / логический exit code.

Shebang запускает интерпретатор. setuid меняет cred при exec с оговорками безопасности env.

cwd наследуется —相对тельные пути ломаются в службах.

## 14. Как приложения «говорят» с ОС

Язык → stdlib/runtime → libc (часто) → syscall → ядро.

Дополнительно: ioctl, netlink, /proc, /sys. Песочницы (seccomp, caps drop) режут таблицу допустимых syscall.

POSIX задаёт переносимый слой API; расширения Linux/BSD/Windows живут рядом.

## 15. Планировщик и время

CFS и аналоги делят CPU между runnable потоками. Приоритеты nice/realtime политик. Вытеснение мешает монополии одного цикла.

Для soft realtime: приоритеты, изоляция CPU, PREEMPT_RT, вынос цикла. Измеряйте джиттер, не верьте лозунгам.

Часы: CLOCK_MONOTONIC для интервалов; realtime clock может прыгать при NTP.

## 16. Сеть на уровне ОС (кратко)

Стек в ядре: NIC → драйвер → IP → TCP/UDP → сокет процесса. Буферы сокетов, listen backlog, epoll/kqueue/IOCP для масштаба. Firewall — тоже политика ядра/netfilter.

Ошибка «address already in use» — занят локальный порт другим процессом (или TIME_WAIT в нюансах).

## 17. Контейнеры и виртуализация (место в карте)

- VM: своё ядро гостя (гипервизор).
- Контейнер: общее ядро, namespaces + cgroups изолируют вид и ресурсы.

Контейнер не заменяет понимания UID, ФС, сигналов и лимитов памяти — он их использует.

## 18. Логи и наблюдаемость

journald, syslog, Event Log. stdout службы. dmesg для ядра. Метрики: CPU steal, pressure stall (PSI), page faults, context switches.

Правило: сначала статус службы и последние логи, потом гипотезы о «баге языка».

## 19. FAQ

**ОС = рабочий стол?**  
Нет. GUI — userland. Есть headless-серверы без монитора.

**Root равен ядру?**  
Нет. Root — могучий userland-субъект; ядро всё равно проверяет и выполняет syscalls (но root может загрузить модуль и т.п.).

**Почему в Docker «не находится команда», а в SSH есть?**  
Другой PATH/env и другой набор пакетов образа.

**Чем kill -9 плох?**  
Нет graceful cleanup: блокировки, моторы, временные файлы, flush.

**Зачем fsync, если есть журналируемая ФС?**  
Журнал защищает структуру ФС; ваши данные приложения всё равно нужно барьерить по требованиям durability.

**Можно ли обойтись без libc?**  
Да (Go, некоторые static designs), но syscall остаются.

**Почему permission denied на файл 644?**  
Нет x на одном из каталогов пути, или MAC-политика, или capabilities/устройство.

**Что такое zombie и вреден ли?**  
Слот PID и запись process table; при массовом появлении — баг родителя.

**Зачем отдельные пользователи служб?**  
Минимизация ущерба при компрометации и ошибках записи файлов.

**systemd обязателен?**  
Нет, но на многих Linux-дистрибутивах он де-факто стандарт управления службами.

## 20. Типичные поломки и куда смотреть

| Симптом | Куда смотреть |
|--------|----------------|
| Не стартует после reboot | enable unit, зависимости, env |
| Работает в терминале, не в service | PATH, cwd, User, tty |
| Permission denied на /dev/ttyUSB0 | группы, udev, ACL |
| Растёт память демона | утечка, кэш, лимит cgroup |
| Порт занят | ss/netstat, чей PID |
| «Теряются» логи после rotate | reopen дескрипторов |
| Медленно при свободном CPU | диск, lock, сеть, DNS |

## 21. Чеклист деплоя робота на Linux

1. Отдельный пользователь и каталоги данных с правильными владельцами.
2. Unit с абсолютными путями и Restart=on-failure + RestartSec.
3. Обработка SIGTERM в приложении (безопасная остановка).
4. Логи в journal или ротируемые файлы с reopen.
5. Доступ к устройствам через группы, не через вечный root.
6. Лимиты памяти/CPU при необходимости.
7. Синхронизация времени (для логов и TLS).
8. Мониторинг места на диске.
9. Образ/пакет с зафиксированными версиями runtime.
10. Проверка автозапуска холодным reboot-тестом.

## 22. Глоссарий

- **Init** — первый процесс userland / менеджер служб.
- **Namespace** — изоляция видимости ресурсов.
- **Cgroup** — учёт и лимиты.
- **Capability** — дробная привилегия вместо монолитного root.
- **Seccomp** — фильтр syscall.
- **VFS** — слой виртуальной ФС.
- **Page cache** — кэш файловых страниц в RAM.
- **Overcommit** — выделение виртуальной памяти сверх физической с риском OOM позже.
- **ABI** — двоичный контракт.
- **Graceful shutdown** — управляемое завершение по TERM.
