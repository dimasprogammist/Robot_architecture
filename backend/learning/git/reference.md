# Справочник: как устроен репозиторий Git

Этот текст не заменяет последовательный курс. Он нужен, когда вопрос уже конкретный: что лежит в `.git`, чем `commit` отличается от сохранения файла, почему `pull` иногда останавливается.

## Три дерева

У Git три места, где одновременно может существовать разное содержимое одних и тех же файлов.

**Рабочая директория** — то, что видно в редакторе и проводнике. Сохранение в редакторе пишет байты на диск сюда. История об этом ещё не знает.

**Индекс (staging area)** — список того, что войдёт в следующий коммит. Файл можно изменить на диске и не класть в индекс. Тогда коммит его не увидит. Команда `git add путь` копирует текущее содержимое файла в индекс. Если после `add` файл снова изменить, в индексе останется прежняя копия, пока вы не добавите файл ещё раз.

**История (коммиты)** — снимки, которые уже записаны. Их не правят обычным сохранением. Новый снимок появляется только коммитом.

`git status` показывает расхождение этих трёх мест: что изменено на диске, но не в индексе, и что уже в индексе, но ещё не в коммите.

## Что такое коммит

Коммит хранит:

- ссылку на дерево файлов (снимок);
- ссылку на один или несколько родительских коммитов (у первого коммита родителей нет, у слияния их два);
- имя и почту автора, время;
- сообщение.

Имя коммита — хеш содержимого, обычно показывают первые символы. Хеш меняется, если меняется содержимое. Поэтому нельзя «тихо поправить старый коммит» так, чтобы имя осталось прежним: это уже другой объект.

Сообщение пишут о причине, не о списке файлов. Список Git и так умеет показать. «Поправить» через месяц ничего не объясняет. «Не стирать карту при ошибке чтения» объясняет.

## Объекты внутри .git

Папка `.git` — база репозитория. Основные виды объектов:

- **blob** — содержимое одного файла, без имени. Имя файла живёт в дереве.
- **tree** — каталог: имена файлов и ссылки на blob или на вложенные tree.
- **commit** — снимок, который указывает на один tree верхнего уровня и на родителей.
- **tag** — необязательная подпись, которая указывает на коммит и даёт ему человеческое имя вроде `v1.2`.

Одинаковые содержимое файла хранится один раз: если два коммита содержат один и тот же blob, второй раз байты не копируются. Поэтому «снимок целиком» не означает, что каждый коммит заново кладёт на диск весь проект.

Ветки и HEAD — не отдельные копии файлов. **Ветка** — файл с хешем коммита, на который она указывает. **HEAD** — указатель, какая ветка сейчас выбрана. Когда вы делаете коммит, новый объект указывает на прежний конец ветки, а ветка начинает указывать на новый коммит.

## Команды как действия над этой моделью

Не список для заучивания, а соответствие модели.

```bash
git init
```

Создаёт `.git` в текущей папке. Файлы проекта не коммитятся сами.

```bash
git status
```

Сравнивает рабочую директорию, индекс и HEAD.

```bash
git add file.txt
```

Кладёт текущие байты `file.txt` в индекс.

```bash
git commit -m "Зачем этот снимок"
```

Записывает коммит из индекса и сдвигает текущую ветку.

```bash
git log --oneline
```

Печатает цепочку коммитов от HEAD назад, по родителям.

```bash
git switch -c experiment
```

Создаёт ветку `experiment` на текущем коммите и переключает HEAD на неё. Старая ветка остаётся на прежнем коммите.

```bash
git merge experiment
```

Находясь на другой ветке, вливает коммиты `experiment`. Если одни и те же строки менялись в обеих линиях, Git останавливается: это конфликт, его решают в файле, затем снова `git add` и `git commit`.

```bash
git clone адрес
```

Копирует историю и файлы, запоминает удалённую копию под именем `origin`.

```bash
git push
```

Отправляет коммиты текущей ветки в `origin`, если история там не разошлась.

```bash
git pull
```

Забирает коммиты с `origin` и сливает их с вашей веткой. Это `fetch` плюс `merge`. Если вы тоже успели сделать коммиты, может понадобиться слияние.

## Удалённый репозиторий и GitHub

**Remote** — другое хранилище тех же объектов. У него есть адрес и короткое имя, почти всегда `origin`.

GitHub, GitLab и похожие сайты дают такой remote и веб-страницу. Учётная запись на сайте не устанавливает Git. Команды `push` и `pull` говорят с remote по сети. Без сети коммиты по-прежнему делаются локально, просто их никто другой ещё не видит.

`clone` нужен один раз, когда папки ещё нет. Дальше в этой папке работают `pull` и `push`. Повторный `clone` в ту же папку не обновляет проект.

## Типичные ошибки

- Коммит без `git add`: в снимок попало не то, что сейчас на экране, а то, что последний раз клали в индекс.
- `git add .` в корне, где лежат пароли, базы и огромные файлы. После коммита они остаются в истории, даже если файл удалить следующим коммитом. Секрет надо убирать отдельной переписью истории, это уже не обычный цикл.
- Сообщение `fix` и десять несвязанных правок в одном снимке. Откатить одну из них трудно.
- `pull` при местных незакоммиченных правках в тех же строках. Сначала коммит или осознанное откладывание, потом забор чужой истории.
- Путать ветку и папку. Ветка не создаёт второй каталог на диске. Переключение ветки меняет файлы в той же рабочей директории.

## Ограничения

Git не блокирует файл, пока вы его редактируете. Два человека могут править одно и то же. Конфликт обнаружится при слиянии, а не в момент открытия файла.

Он не проверяет, что программа собирается. Коммит может содержать код, который не запускается. Проверка сборкой — отдельный шаг, не часть модели снимков.

История публичного репозитория после `push` уже могла быть скачана другими. Переписывать опубликованные коммиты можно, но чужие копии тогда разойдутся с вашей. Для учебного репозитория, где вы один, это менее больно. Для общей ветки `main` новые коммиты безопаснее переписывания старых.

## Частые вопросы

**Сохранение в редакторе уже сделало коммит?** Нет. Коммит — отдельное действие.

**Нужен ли GitHub, чтобы пользоваться Git?** Нет. `git init` достаточен для истории на одном компьютере.

**Можно ли вернуть файл из вчерашнего снимка, не откатывая весь проект?** Да. История хранит blob этого файла. Конкретная команда зависит от того, хотите вы только посмотреть файл или записать его обратно в рабочую директорию. Сначала смотрят `git log`, чтобы найти нужный снимок, и не начинают с команд, которые стирают незакоммиченную работу.

**Чем ветка отличается от копии папки?** Копия папки дублирует байты и не знает про другую копию. Ветка — второе имя на цепочку коммитов в том же репозитории. Общие неизменённые файлы не хранятся второй раз.
