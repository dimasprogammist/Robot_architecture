# Зачем вообще помнить версии

Пока вы правите один файл в одиночку и никогда не возвращаетесь назад, история не нужна. Достаточно кнопки «Сохранить». Трудность начинается в тот момент, когда сегодняшняя версия сломала то, что вчера работало, или когда два человека поменяли один и тот же абзац.

**Система контроля версий** — программа, которая хранит не только текущие файлы, а последовательность их состояний. Можно спросить: что изменилось, когда, и по чьему решению. Git — одна из таких систем. Это не сайт и не «облачный диск». Это инструмент, который ставится на компьютер и работает с папкой проекта.

## Какую боль он закрывает

Без системы версий люди делают копии папок: `проект`, `проект_финал`, `проект_финал2`. Через неделю уже не вспомнить, чем вторая копия отличается от третьей. Если внутри поменялись десять файлов, сравнивать их глазами долго. Если нужно вернуть один удалённый абзац, приходится искать ту копию, где он ещё был.

Вторая боль — параллельная работа. Вы правите описание мотора, коллега в том же файле правит описание камеры. Если просто переслать файл, чья-то правка пропадёт. Система версий умеет показать оба изменения и помочь собрать из них один файл.

Третья боль — эксперимент. Хочется попробовать другой способ чтения датчика, но страшно испортить рабочий код. Копия папки снова приводит к «финал2». В Git для этого есть ветка: отдельная линия истории, которую можно выбросить или влить обратно.

## Что Git не делает

Git не заменяет резервное копирование питания и не понимает смысл программы. Он не знает, что ваша функция считает скорость. Он знает байты файлов и то, как они менялись.

Он плохо подходит как единственное хранилище гигабайтных видео и сканов: история раздувается. Для текста, кода и небольших настроек он как раз уместен.

Git также не равен GitHub. GitHub — сайт, где можно положить копию репозитория, чтобы её видел другой компьютер. Сам Git работает и без интернета, в одной папке.

## Слова, которые понадобятся дальше

Их рано заучивать как команды. Пока это карта.

- **Репозиторий** — проект вместе с его историей.
- **Рабочая директория** — обычные файлы, которые вы редактируете.
- **Индекс (staging)** — список изменений, которые вы сознательно отложили в следующий снимок.
- **Коммит** — один сохранённый снимок с короткой запиской, зачем он сделан.
- **Ветка** — имя, которое указывает на конец одной линии коммитов.
- **Слияние** — перенос изменений из одной линии в другую.
- **Удалённый репозиторий** — другая копия той же истории, часто на сервере.

Команды вроде `git add` и `git commit` имеют смысл только после этих слов. Следующие уроки разбирают их по одной, от устройства папки до ежедневного цикла.

## Как люди жили до таких систем

Сначала историю вели вручную. Инженер копировал каталог и подписывал дату в имени. В архиве завода это та же идея, что папка `чертёж_12марта`. Минус очевиден: копия хранит всё целиком, даже то, что не менялось, и не отвечает на вопрос «какие строки стали другими».

Потом появились централизованные системы вроде CVS и Subversion. История лежала на одном сервере. Чтобы зафиксировать изменение, нужно было связаться с сервером. Работать в поезде без сети было неудобно, а сервер был единой точкой, без которой история недоступна.

Git появился в 2005 году для разработки ядра Linux: тысячи правок, много людей, нельзя останавливать работу из-за одного сервера. Поэтому Git хранит полную историю у каждого, кто скопировал репозиторий. Сервер нужен, чтобы обмениваться, а не чтобы «разрешить» сделать снимок.

## Снимок, а не список поправок

Есть два способа помнить изменения. Первый — хранить только разницу: «в строке 10 было А, стало Б». Второй — хранить снимок файлов целиком и уметь сравнить два снимка, когда разницу просят показать.

Git устроен вторым способом. Коммит — это снимок дерева файлов. Когда вы смотрите `git diff`, программа сама вычисляет разницу между двумя снимками. Для вас это выглядит как список строк, но внутри записаны не «патчи как единственная правда», а состояния.

Это важно, когда вы думаете «Git запомнил, что я дописал функцию». Точнее: Git запомнил, как файл выглядел после этого, и может показать отличие от предыдущего вида.

## Где это применяется

Любой текст, который живёт дольше одного вечера: программа, конфигурация станка, описание протокола, учебные заметки. Робототехнический проект обычно состоит из прошивки, скриптов на компьютере и файлов настроек. Без истории нельзя честно ответить, какая настройка камеры стояла в тот день, когда стенд ещё проходил испытание.

Дальше мы откроем, из каких трёх областей состоит работа в Git: файлы на диске, индекс и история. Команд по-прежнему не будет списком «выучите пятнадцать штук». Будет одна область — и зачем она отделена от остальных.
