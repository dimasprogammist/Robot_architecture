# Архитектура ПО

## Назначение справочника

Сжатые определения, сравнения стилей и чеклисты по архитектуре приложений. Для поиска «что это значит» и «чем отличается», не как замена последовательным урокам модуля architecture.

## Карта темы

- Что считают архитектурой
- Модуль, компонент, граница
- Связность и связанность
- Слои: api / service / repository
- DTO, зависимости, DI
- SOLID и SoC в практике
- Монолит, модульный монолит, микросервисы
- События, outbox, саги
- Когда не дробить
- Типичные ошибки

## 1. Архитектура — определение

**Архитектура ПО** — набор устойчивых решений о границах частей, их ответственности, способах связи и местах, где живут правила и данные. Менять архитектуру дороже, чем локальный алгоритм.

Не архитектура сама по себе: выбор цвета кнопки, имя временной переменной, разовый скрипт миграции без контракта.

## 2. Архитектурное решение (ADR-мысль)

Фиксируйте: контекст → решение → последствия. Пример: «заказы и платежи в одной БД, пока команда < 5 и нет PCI-контура».

## 3. Модуль vs компонент

| Термин | Смысл |
|--------|--------|
| **Модуль** | единица организации кода/домена с явной границей (пакет `orders`) |
| **Компонент** | заменяемая часть с интерфейсом (может совпадать с модулем) |
| **Сервис (процесс)** | единица деплоя/рантайма |

Путаница: называть «микросервисом» любой Python-пакет.

## 4. Граница

**Граница** — линия, через которую общение идёт по правилам (функция-порт, HTTP, сообщение), а не через чужие внутренности.

Признак дырявой границы: импорт чужого `repository` и прямые UPDATE чужих таблиц.

## 5. Связанность (coupling) и связность (cohesion)

- **Высокая связность** внутри модуля — хорошо: код про одно.
- **Сильная связанность** между модулями — плохо: сложно менять по отдельности.

Цель: высокая cohesion, низкий coupling.

## 6. Separation of Concerns (SoC)

Разделение интересов: UI ≠ HTTP-валидация ≠ доменные правила ≠ SQL. Один файл/слой — один класс причин изменения.

## 7. Слои бэкенда (шпаргалка)

```text
HTTP handlers  →  application/services  →  repositories  →  DB
     ↑ DTO/схемы         ↑ домен/usecase        ↑ SQL/ORM
```

| Слой | Делает | Не делает |
|------|--------|-----------|
| API | протокол, коды, auth deps | бизнес-инварианты «вразнобой» |
| Service | правила, оркестрация | сырой SQL по проекту |
| Repository | доступ к данным | решать политику скидок |

## 8. DTO

**DTO** — объект передачи данных через границу (запрос/ответ API, сообщение). Не обязательно = ORM-модель.

Ошибка: отдать SQLAlchemy-модель в JSON с lazy-load и циклическими связями.

## 9. Зависимости и направление

Правило: внутренние политики не зависят от деталей фреймворка/БД. Детали зависят от абстракций (портов).

```python
class OrderRepo(Protocol):
    def insert(self, order: Order) -> Order: ...
```

Service зависит от `OrderRepo`, а не от «конкретного PostgresRepo» в сигнатурах домена — по возможности.

## 10. DI (внедрение зависимостей)

Вместо `repo = OrderRepo()` внутри service — передача снаружи (конструктор / FastAPI `Depends`). Упрощает тесты и замену реализации.

## 11. SOLID — одна строка каждое

- **S** — один повод менять класс/модуль.
- **O** — расширение без ломания существующего (осторожно с фанатизмом).
- **L** — подтипы не ломают контракт базы.
- **I** — узкие интерфейсы вместо «бога-порта».
- **D** — зависимость от абстракций.

SOLID — эвристики, не закон космоса.

## 12. Домен и приложение

**Домен** — правила бизнеса (заказ нельзя отгрузить без оплаты — если так решили).  
**Приложение** — use-case: «оформить заказ» склеивает домен + инфраструктуру.  
**Инфраструктура** — БД, HTTP, брокер, почта.

## 13. Монолит

Один деплойный юнит, обычно один основной процесс приложения и одна БД как истина.

Плюсы: простые транзакции, проще отладка, меньше ops.  
Минусы: общий риск выката, масштабирование целиком, риск «комка» без модулей.

## 14. Модульный монолит

Один деплой, жёсткие доменные модули (`catalog` / `orders` / `billing`), общение через публичные порты, владение таблицами.

Это часто **оптимум** до реальной нужды в отдельных процессах.

## 15. Микросервисы

Независимые процессы (часто со своими данными) + сеть.

Покупаете: независимый деплой/масштаб/изоляцию.  
Платите: частичные отказы, latency, контракты, распределённые данные, ops.

**Shared DB между «сервисами»** — антипаттерн (распределённый монолит).

## 16. Сравнение трёх стилей

| | Монолит | Модульный монолит | Микросервисы |
|--|---------|-------------------|--------------|
| Процессы | 1 | 1 | много |
| Транзакция checkout | легко | легко | саги/компенсации |
| Цена сети | нет | нет | да |
| Независимый деплой модуля | нет | нет | да |
| Требование к ops | низкое | низкое/среднее | высокое |

## 17. Событийная архитектура (EDA)

Интеграция через **факты** (`order_placed`), подписчики реагируют сами.

Плюсы: слабая связанность, буфер нагрузки, фан-out.  
Минусы: eventual consistency, сложнее отладка, нужны идемпотентность и DLQ.

## 18. Команда vs событие

| | Команда | Событие |
|--|---------|---------|
| Время | сделай | уже случилось |
| Имя | `ChargePayment` | `PaymentCaptured` |
| Адресат | известен | подписчики |

## 19. Outbox

Писать бизнес-данные и запись «отправить событие» в **одной** транзакции БД; отдельный publisher шлёт в брокер. Защита от «commit есть — publish нет».

## 20. Идемпотентность

Повтор сообщения не должендважды списывать деньги. Ключ: `event_id` / `Idempotency-Key` + уникальность в БД.

## 21. Сага

Длинный бизнес-процесс без распределённой ACID: шаги + компенсации при отказе. Пример: charge → reserve → при ошибке reserve сделать refund.

## 22. Синхронный RPC vs асинхронные сообщения

| | HTTP/gRPC sync | Message async |
|--|----------------|---------------|
| Ответ сразу | да | нет (или отдельный reply) |
| Связность по времени | оба up | буфер |
| UX | проще happy-path | нужны статусы |

## 23. API как продукт границы

Версионирование, обратная совместимость, явные ошибки, идемпотентность POST, пагинация списков, контрактные тесты. Ломать JSON поля без версии — ломать клиентов.

## 24. Согласованность

- **Strong** (в одной БД-транзакции) — для инвариантов заказа в монолите.
- **Eventual** — после событий/кэша; UI показывает «обрабатывается».

Выбор согласованности — архитектурное решение, не деталь реализации.

## 25. Когда НЕ дробить систему

1. Маленькая команда, один релизный ритм.  
2. Неясные границы домена.  
3. Нет платформы (логи, трейсы, CI, on-call).  
4. Нет измеримой боли масштаба/изоляции.  
5. Критична простая атомарность checkout.  
6. «Хотим как Netflix» без нагрузки Netflix.

Сначала модули и порты. Потом процессы.

## 26. Чеклист перед выносом сервиса

- [ ] Чистый публичный порт  
- [ ] Свои данные / план миграции  
- [ ] Контракт и версия  
- [ ] Таймауты, ретраи, идемпотентность  
- [ ] Компенсации  
- [ ] Наблюдаемость end-to-end  
- [ ] Владелец и SLO  

## 27. Типичные запахи

- Циклические импорты модулей  
- God service на 3k строк  
- SQL в роутах и в React-мечтах  
- Распределённая транзакция «на скорую»  
- События-команды в одном топике без дисциплины  
- Копипаст доменных правил на фронте как единственная защита  

## 28. Мини-примеры границ (магазин)

Хорошо: `orders` вызывает `catalog.public.get_price()`.  
Плохо: `orders` делает `UPDATE products SET ...`.  
Хорошо: `order_placed` → billing consumer.  
Плохо: billing ходит SELECT по всем таблицам orders без контракта.

## 29. Слои и микросервисы — ортогональны

Микросервис внутри всё равно имеет слои. Монолит без слоёв остаётся хаосом. Нарезка процессов **не заменяет** SoC.

## 30. Read models / CQRS (кратко)

Иногда отделяют модель записи и модель чтения (проекция из событий). Имеет смысл при сложной нагрузке чтения; иначе — YAGNI.

## 31. Антикоррупционный слой (ACL)

При интеграции с легаси/внешней системой — переводчик моделей на границе, чтобы чужой язык не протекал во весь домен.

## 32. Наблюдаемость как часть архитектуры

Correlation id через HTTP и сообщения; структурированные логи; метрики латентности и ошибок по границам. Без этого распределённый стиль необслуживаем.

## 33. Безопасность границ

Authn/authz на каждом входе (HTTP, WS, consumer не «доверяй всем»). Zero-trust внутри сети: сервис-к-сервису тоже с идентичностью.

## 34. Эволюция

Предпочтительный путь роста:

```text
модульный монолит → вынос стабильного модуля → события для фан-out
```

Скачок «с нуля 20 репозиториев» редко окупается.

## 35. Глоссарий

- **Порт/адаптер** — вход/выход приложения (гексагональная идея).  
- **Bounded context** — граница языка домена (DDD).  
- **SLO/SLA** — цели надёжности/договор.  
- **Fan-out** — один факт → много обработчиков.  
- **DLQ** — очередь «ядовитых» сообщений.  
- **BFF** — backend for frontend, узкий API под UI.  

## 36. Сравнение: слой service vs «микросервис»

Service (слой) — класс/модуль в процессе.  
Микросервис — процесс/деплой.  
Имя «OrderService» не делает его микросервисом.

## 37. Быстрый выбор стиля (дерево)

1. Одна команда, домен живой → модульный монолит.  
2. Нужен фон и фан-out → события/очередь **внутри** того же продукта.  
3. Независимый масштаб/комплаенс/команда доказаны → вынос процесса.  
4. Нетops-зрелости → не делать шаг 3.

## 38. Типичные ошибки (сборник)

1. Микросервисы + одна БД на всех.  
2. Дробить до стабилизации модулей.  
3. Транзакции через HTTP без саги.  
4. Игнор идемпотентности consumers.  
5. Архитектура «по папкам слоёв» без доменных границ (или наоборот — только папки доменов без дисциплины).  
6. Скрытые связи через глобальный singleton state.  
7. Путать deployment unit и source module.  
8. Event storming без внедрения в код (ритуал без эффекта).  

## 39. Чеклист ревью архитектуры PR

- Меняется ли граница модуля/контракт?  
- Появилась ли зависимость на чужой repository?  
- Есть ли новая сеть/таймаут?  
- Где истина данных после изменения?  
- Как отладить отказ?  

## 40. Связь с остальным курсом

Frontend и HTTP — край. FastAPI — адаптер входа. Service/repository — структура монолита. SQL — истина. Kafka/workers — асинхронные границы. Docker/Linux/Git — поставка архитектурных единиц. Архитектура — как эти части **разрешено** соединять.

## 41. Что помнить всегда

Границы и данные важнее модных слов. Монолит с модулями бьёт распределённый хаос. События требуют идемпотентности. Дробить систему нужно по боли, не по тренду.

## 42. Пример: владение данными в магазине

| Данные | Владелец | Кто читает иначе |
|--------|----------|------------------|
| `products` | catalog | orders через порт/API снимка цены |
| `orders` | orders | billing получает `order_id`+сумму, не JOIN вслепую |
| `payments` | billing | orders слушает `payment_captured` |
| `stock_levels` | stock | orders резервирует командой/событием |

Владение снимает вопрос «кто имеет право миграции колонки».

## 43. Контракты: потребитель и поставщик

**Consumer-driven contracts** — тесты на стороне клиента, что поставщик всё ещё отвечает ожидаемой формой. Полезно между микросервисами и даже между фронтом и API при частых ломающих правках.

Минимум без фреймворков: зафиксировать JSON Schema / OpenAPI и проверять в CI.

## 44. Версионирование API

Стратегии:

- URL: `/v1/orders`, `/v2/orders`;
- заголовок `Accept-Version`;
- эволюция без версии: только аддитивные поля.

Ломать обязательное поле без версии — ломать клиентов мобилки и партнёров.

## 45. Паттерн Strangler

Замена легаси по частям: новый модуль/сервис перехватывает часть трафика, старое остаётся, пока не сузится. Для магазина: новый billing рядом, прокси решает, куда слать charge. Не требует big-bang rewrite.

## 46. Multi-tenant кратко

Несколько магазинов в одной системе: tenant_id в каждой строке, жёсткие фильтры в repository, отдельные схемы или даже БД для крупных клиентов. Архитектурный риск — «забытый WHERE tenant_id» = утечка данных.

## 47. Идемпотентность HTTP

`POST /orders` с заголовком `Idempotency-Key: uuid`. Сервер хранит ключ → ответ. Повтор клика возвращает тот же заказ, а не второй. Особенно важно при мобильных сетях и ретраях gateway.

## 48. Таймауты и деградация

На каждой исходящей границе: connect timeout, read timeout, политика retry только для идемпотентных запросов. При падении catalog — fail checkout или режим «цена из кэша с пометкой»? Решение продуктовое, но должно быть явным.

## 49. Тестирование архитектурных границ

| Уровень | Что ловит |
|---------|-----------|
| Unit service | правила без HTTP/БД |
| Repository integration | SQL против реальной Postgres |
| Contract | форма API/события |
| E2E | клик → строка (мало, дымовые) |

Архитектура без тестов границ быстро «протекает» обратно в ком.

## 50. Документы, которые реально помогают

- диаграмма контекстов (кто с кем говорит);
- список модулей и таблиц-владельцев;
- каталог событий и совместимость;
- runbook отказа брокера/БД;
- ADR по ключевым решениям.

Вики на 40 страниц «будущих микросервисов» без кода — не помогает.

## 51. Антипаттерн: распределённый монолит

Признаки: много процессов, одна БД, синхронные цепочки на каждый клик, общий релиз всё равно одновременный, отладка хуже, чем в монолите. Лечение: либо вернуть модульный монолит, либо довести владение данными и async-границы до конца.

## 52. Стоимость изменения (эвристика)

Оцените изменение «добавить поле промокода в заказ»:

- монолит модульный: миграция + service + API + UI;
- микросервисы: то же × число затронутых репо + совместимость событий + выкат порядка.

Если такие изменения частые — держите заказ в одной поставке.

## 53. Frontend и архитектура

UI — отдельный деплой, но не отдельный домен правды. BFF может собрать read-model под экран оператора. Не тащите JOIN из трёх микросервисов в браузер пятью запросами без нужды — лучше один серверный агрегирующий край.

## 54. Безопасный дефолт для курса/стартапа

```text
Модульный монолит + PostgreSQL + очередь для писем
+ чёткие порты модулей + хорошие логи
```

Этого достаточно, чтобы вырастить продукт. Остальное добавляйте по метрикам и оргструктуре.

## 55. Финальный чеклист «готово ли дробить»

- [ ] Модуль живёт без чужих таблиц ≥ 1–2 месяца  
- [ ] Есть второй потребитель или отдельный SLO  
- [ ] Команда может деплоить независимо  
- [ ] Есть план данных и отказов  
- [ ] On-call понимает распределённый путь  

Нет двух галочек — рано.
