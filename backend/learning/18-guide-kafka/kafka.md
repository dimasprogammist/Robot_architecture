# Справочник: Kafka и очереди

Поиск по понятиям, сравнениям и типовым сбоям. Не конспект уроков и не копия вендорной документации.

---

## 1. Быстрые определения

**Брокер сообщений** — инфраструктура, которая принимает сообщения от отправителей, хранит их по своим правилам и отдаёт получателям.

**Очередь (work queue)** — модель, где сообщение обычно является задачей: воркер забирает, обрабатывает, подтверждает; после успешного ack задача исчезает из очереди для конкурирующих воркеров.

**Лог / поток (Kafka topic log)** — упорядоченная append-only последовательность записей. Чтение двигает курсор; удаление для всех читателей определяется retention, а не вашим commit.

**Producer** — клиент записи.

**Consumer** — клиент чтения и обработки.

**Consumer group** — набор консьюмеров с одним `group.id`, делящих партиции топика; у группы общий курсор offset.

**Topic** — именованный поток записей в Kafka.

**Partition** — упорядоченный сегмент топика; единица параллелизма и локального порядка.

**Offset** — индекс записи внутри партиции. Адрес: `(topic, partition, offset)`.

**Key** — ключ записи; влияет на выбор партиции и группировку порядка.

**Value** — тело записи (байты после сериализации).

**Headers** — метаданные записи (trace id, тип события, версия схемы).

**Leader** — реплика партиции, обслуживающая клиентские операции записи/чтения в классической модели.

**Replica / follower** — копия лога партиции на другом брокере.

**Commit offset** — сохранить прогресс consumer group по партиции.

**Lag** — насколько позиция группы отстаёт от конца лога партиции/топика.

**Retention** — политика хранения записей (время, размер, compaction).

**Ack (producer)** — подтверждение брокера, что запись принята с выбранной строгостью.

**Ack (queue consumer)** — подтверждение воркера, что задачу можно считать завершённой и удалить/не ределиверить.

**DLQ / DLT (dead letter)** — карантин для сообщений, исчерпавших ретраи или признанных ядовитыми.

**Idempotence** — повторная обработка не меняет итоговый эффект.

**At-most-once** — ≤1 доставка эффекта; возможны потери.

**At-least-once** — ≥1; возможны дубли.

**Exactly-once** — =1 в явно заданных границах системы (не «магия на весь мир»).

## 2. Kafka vs обычная очередь (шпаргалка)

| Критерий | Классическая очередь | Kafka (лог) |
|---|---|---|
| Метафора | Ящик задач | Журнал событий |
| После успешной обработки | Обычно исчезает для воркеров очереди | Курсор группы двигается; данные живут по retention |
| Несколько независимых читателей | Отдельные очереди/подписки/копии | Разные `group.id` на один топик |
| Параллелизм | Часто по сообщениям между воркерами | По партициям внутри группы |
| Порядок | Зависит от продукта; конкурирующие воркеры легко перемешивают эффекты | Гарантия внутри партиции |
| Replay истории | Обычно ограничен/не штатный | Штатный в окне retention |
| Пустая система «в норме» | Короткая/пустая очередь | Лог может быть большим специально |
| Приоритеты / delay | Часто из коробки | Обычно через отдельные топики и соглашения |
| Типичная роль | Work queue | Event stream / bus; иногда и команды |

**Когда очередь уместнее:** один пул воркеров, job’ы, приоритеты, delayed retry, малый поток, проще эксплуатация.

**Когда лог уместнее:** fan-out многим сервисам, высокий TPS, replay проекций, порядок по ключу сущности, единый журнал фактов.

**Оба нужны в компании:** нормальная гибридная схема, не противоречие.

## 3. Модель данных записи

Минимальный состав записи Kafka:

1. **topic** — логический поток.
2. **partition** — номер лога.
3. **offset** — позиция в логе.
4. **timestamp** — время (создания/брокера — зависит от настроек).
5. **key** — опционально, но важен для порядка.
6. **value** — полезная нагрузка.
7. **headers** — опциональные пары ключ/значение.

Рекомендуемый бизнес-конверт value (JSON-пример):

```text
{
  "event_id": "uuid",
  "type": "OrderCreated",
  "version": 1,
  "occurred_at": "2026-09-25T08:00:00Z",
  "payload": { "...": "..." }
}
```

Правила:

- `event_id` стабилен при ретраях продюсера (генерируйте до send).
- `type` явный — консьюмеры ветвятся без угадывания.
- `version` схемы — эволюция без сюрпризов.
- Не кладите мегабайты бинарей: ссылка на object storage + метаданные.

## 4. Схема ключей (практика)

| Цель | Ключ | Следствие |
|---|---|---|
| Порядок по заказу | `order_id` | Все события заказа в одной партиции |
| Порядок по счёту | `account_id` | Сериализация операций счёта |
| Равномерный кликстрим без порядка сущности | `null` или случайный | Больше перемешивания, выше параллелизм без локального порядка |
| Письма одному пользователю по порядку | `user_id` / email | Локальный порядок коммуникаций |
| Избежать hot key одного tenant | составной `tenant_id:entity_id` или иной шард | Снижение перекоса (иногда ценой порядка по tenant целиком) |

**Опасность:** новый UUID в ключе на каждое сообщение связанного потока — порядок сущности уничтожен.

**Опасность:** смена `num.partitions` — `hash(key) % N` меняется для новых записей; история ключа может «переехать».

**Hot key:** один ключ даёт непропорциональную долю трафика → одна партиция перегружена. Лечение: пересмотр ключа, бизнес-ограничение, выделенный путь обработки.

---

## 5. Партиции и группы — формулы мышления

- Полезный параллелизм **внутри одной group** ≈ число партиций топика.
- Лишний консьюмер в группе сверх N партиций → idle.
- Две group на один топик → каждое сообщение обработается **в каждой** группе (при нормальной работе) — это fan-out, не дубль бага.
- Один `group.id` на два разных сервиса по ошибке → они делят партиции и каждый видит **часть** потока — авария контракта.

Rebalance: при изменении членства группы партиции переназначаются; частые rebalance → просадки. Причины: долгий poll, частые рестарты, сетевые обрывы heartbeat.

---

## 6. Commit offset — шпаргалка семантики

| Момент commit | Риск при падении | Класс |
|---|---|---|
| До обработки | Потеря эффекта | at-most-once |
| После обработки | Повтор эффекта | at-least-once |
| В одной транзакции с записью в свою БД (идея) | Ближе к ровному эффекту на границе БД | практический exactly-once на эффекте БД |
| Транзакционный read-process-write в топики Kafka | Ровные границы внутри Kafka | не покрывает внешний SMTP/HTTP сами по себе |

Рабочий стандарт большинства доменов:

1. Транспорт: at-least-once.
2. Эффект: идемпотентность / уникальный `event_id`.
3. Commit после успешного локального эффекта.

---

## 7. Семантики доставки (кратко и жёстко)

**At-most-once** — мониторинг, приблизительные счётчики, где дырка дешевле дубля.

**At-least-once** — заказы, почта, склад, почти всё бизнес-критичное + дедуп.

**Exactly-once** — уточняйте границы: «ровно одна запись в выходном топике на входную» ≠ «ровно одно письмо у пользователя навсегда без вашей таблицы дедупа».

Идемпотентный продюсер снижает дубли на участке ретраев send. Он не отменяет дедуп на консьюмере для всех жизненных ситуаций.

---

## 8. Ретраи и dead letter

Классификация ошибок:

- **Temporary** — timeout, 503, deadlock → backoff + jitter, лимит попыток.
- **Permanent** — битая схема, нарушенный инвариант → сразу DLT.

Head-of-line blocking: стоять вечно на ядовитой записи = остановить хвост партиции для группы.

Минимум полей в DLT-конверте:

```text
source.topic, source.partition, source.offset
group_id, failed_at, attempt, error
original key/value (или ссылка)
```

DLT без алерта на глубину/скорость роста — могильник, не процесс.

После успешной публикации в DLT — commit исходного offset, иначе яд останется в голове.

## 9. Мини-примеры

### 9.1 Продюсер события

```python
def publish_order_created(producer, order: dict) -> None:
    event = {
        "event_id": order["event_id"],
        "type": "OrderCreated",
        "version": 1,
        "order_id": order["id"],
        "user_id": order["user_id"],
        "total_cents": order["total_cents"],
    }
    producer.send(
        topic="orders.events",
        key=order["id"].encode(),
        value=encode_json(event),
        headers={"event_type": "OrderCreated"},
        acks="all",
        retries=10,
    )
```

### 9.2 Консьюмер с дедупом

```python
def handle(record, db, broker) -> None:
    event = decode(record.value)
    with db.transaction():
        if not db.try_insert_event(event["event_id"]):
            broker.commit_record(record)
            return
        db.apply(event)
    broker.commit_record(record)
```

### 9.3 Две группы — fan-out

```text
topic: orders.events
group mail-service       -> письма
group warehouse-service  -> резерв склада
```

Одинаковый топик, разные курсоры, независимые деплои и лаги.

### 9.4 Очередь задач (контраст)

```python
queue.enqueue("render-pdf", {"report_id": "r1"})
# воркеры конкурируют; после ack задача уходит
# второй сервис сам по себе этот поток не читает
```

### 9.5 Outbox (согласование БД и брокера)

```text
Транзакция БД:
  INSERT order
  INSERT outbox(event)
Потом процесс publisher читает outbox и делает producer.send
Помечает outbox sent
```

Снижает «commit в БД есть, в брокер не ушло» и обратную гонку при наивном порядке операций.

## 10. Типичные сбои и что смотреть

| Симптом | Частые причины | Куда смотреть |
|---|---|---|
| Растёт lag одной группы | Медленный handler, мало консьюмеров, hot partition, внешний API | lag по партициям, CPU/время handle, назначение партиций |
| Lag только на части партиций | Hot key / перекос | распределение ключей, размер партиций |
| Дубли писем/проводок | at-least-once без идемпотентности; ретраи продюсера | уникальные ключи, логи event_id |
| «Потеряли событие» | commit до эффекта; at-most-once; retention вычистил пока лагали | момент commit, retention vs lag, DLQ |
| Частые rebalance | Долгий poll, OOM, убийство подов, сеть | max.poll.interval, длительность batch, деплои |
| Не пишется в топик | Нет лидера, диск полный, ACL, quota | health брокеров, under-replicated, auth |
| Консьюмер «не видит старое» | Старт с latest; новый group id; retention | политика auto.offset.reset, возраст данных |
| После увеличения партиций «порядок сломался» | ключ уехал на другой номер | план миграции, N с запасом заранее |
| Пустой DLT растёт | Яд схемы / перманентные ошибки | алерты, фикс продюсера, replay процесс |
| Два сервиса видят половину потока | Случайно один group.id | инвентаризация group id |

## 11. Эксплуатационные якоря

**Имена топиков:** стабильные, доменные (`orders.events`, не `test_final_v3`).

**Владелец топика:** команда-продюсер отвечает за схему и совместимость.

**ACL:** не всем write на всё.

**Мониторинг минимум:**

- under-replicated partitions / недоступные партиции;
- диск и retention;
- produce/consume latency и ошибки клиентов;
- lag по каждой критичной group;
- глубина DLT.

**Схемы:** версионируйте; договаривайтесь о совместимости (добавление поля vs переименование).

**Число партиций:** планируйте от целевого параллелизма и TPS; не меняйте каждую неделю.

**Replication factor:** в проде обычно ≥3 для критичных топиков (зависит от размера кластера и SLA).

## 12. Паттерны применения

**Domain events** — факт произошёл; много подписчиков.

**Commands topic** — просьба выполнить работу; часто одна исполняющая group.

**Changelog / compacted topic** — важно последнее состояние по ключу (кэш, словарь).

**CQRS projection** — события → read-модель; replay при пересборке.

**Integration buffer** — сгладить пики вебхуков до внутренней скорости.

**Anti-corruption adapter** — внешний формат → внутренний топик канонических событий.

Не паттерн: использовать Kafka как синхронный RPC между двумя сервисами «потому что можно» — обычно хуже прямого вызова или очереди request/reply с ясной необходимостью.

---

## 13. Что не обещает Kafka сама по себе

- Глобальный порядок по всему топику при N>1.
- Exactly-once эффект во внешней системе без вашей идемпотентности.
- Бесконечное хранение без политики и диска.
- Замену OLTP/OLAP базе для произвольных запросов.
- Автоматическое исправление плохой схемы сообщений.
- Нулевую задержку для пользователя на всех побочных эффектах.

## 14. Чеклист выбора инструмента

1. Сколько независимых потребителей у факта?
2. Нужен ли replay?
3. Какой пиковый TPS?
4. Нужен ли порядок по сущности?
5. Нужны ли приоритеты/delay из коробки?
6. Какая допустимая задержка эффекта?
7. Кто эксплуатирует брокер?
8. Это событие или команда-задача?

Грубые стрелки:

- много потребителей + replay + поток → **Kafka/лог**;
- один пул job’ов + приоритеты → **очередь**;
- редкий sync с ответом в том же запросе → **прямой вызов**;
- согласование БД и публикации → **outbox** (поверх любого транспорта).

---

## 15. Глоссарий коротких формул

- **Append-only** — пишем только в конец лога партиции; «правка факта» = новое сообщение.
- **Fan-out** — один publish, много независимых обработок.
- **Backpressure** — потребитель не успевает; растёт lag/очередь; нужны scale или политика нагрузки.
- **Poison message** — стабильно ломает handler.
- **Replay** — перечитать прошлый участок лога (осторожно с дублями эффектов).
- **Outbox** — событие сначала в БД продюсера, потом в брокер.
- **Inbox / processed store** — таблица уже применённых event_id у консьюмера.
- **ISR (идея)** — набор реплик, достаточно догнавших лидера для durability-политик.
- **Sticky / round-robin без ключа** — распределение без стабильной привязки сущности.

## 16. Мини-сценарии для отладки в уме

**Сценарий A.** Продюсер получил ошибку сети после записи. При ретрае без идемпотентности в логе два value с одним смыслом. Консьюмер без `event_id` дедупа сделает эффект дважды.

**Сценарий B.** Консьюмер обработал, упал до commit. После рестарта снова видит ту же запись. Идемпотентность спасает; её отсутствие — дубль.

**Сценарий C.** Консьюмер закоммитил, потом упал до HTTP на почту. Письмо не ушло, offset уже сдвинут. Это потеря эффекта — commit был слишком рано.

**Сценарий D.** Битый JSON на offset 100, handler ретраит вечно. Offset 101+ не двигаются в этой партиции для группы. Нужен DLT + commit.

**Сценарий E.** Добавили консьюмеры 10 штук при 3 партициях. Семь idle. Ускорения нет. Увеличивать партиции — отдельное решение с последствиями для ключей.

## 17. Совместимость команд и событий

| | Событие | Команда |
|---|---|---|
| Время глагола | Прошедшее (`Created`) | Повелительное (`Send`, `Reserve`) |
| Смысл | Факт уже есть | Просьба сделать |
| Подписчики | Часто много | Часто один исполнитель |
| Идемпотентность | По event_id / натуральному ключу | По command_id |
| Типичный транспорт | Лог/bus | Очередь или command-топик |

Путаница команды и события в одном контракте — источник вечных споров «кто кому должен».

## 19. Антирекомендации (краткий чёрный список)

- Один топик на всю компанию со смешанными схемами.
- Один group.id на разные продукты.
- Commit в `finally` без понимания успеха эффекта.
- Бесконечный ретрай без DLT.
- Ключ = random на каждое сообщение «для равномерности» при нужном порядке.
- Kafka как единственная БД правды без clear retention/compaction стратегии.
- Обещание exactly-once заказчику без границ и без уникальных ключей.
- Увеличение партиций ночью без коммуникаций с владельцами консьюмеров.
