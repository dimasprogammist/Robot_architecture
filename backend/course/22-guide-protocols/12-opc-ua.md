# OPC UA

## Цель

До этого мы изучали протоколы, которые передают данные между устройствами. Теперь рассмотрим OPC UA — технологию, которая позволяет не просто передавать набор байтов, а представлять данные устройств в структурированном виде.

После урока вы должны понимать:

* что такое OPC UA;
* кто такие OPC UA Client и Server;
* что такое Node;
* зачем нужны Namespace и NodeId;
* что такое чтение и запись значений;
* как работают subscriptions;
* почему OPC UA отличается от обычного TCP-протокола;
* где OPC UA может использоваться в автоматизации, робототехнике и системах мониторинга.

---

# 1. Зачем нужен более высокий уровень

Представим устройство, которое передаёт данные через TCP.

Мы можем получить:

```text
24.7
```

Но что означает это число?

Возможно:

```text
температура = 24.7 °C
```

А может:

```text
скорость = 24.7 м/с
```

Или:

```text
уровень = 24.7 %
```

Сам TCP этого не знает.

Он отвечает только за транспорт байтов.

Поэтому приложение должно определить структуру данных самостоятельно.

OPC UA решает эту задачу на более высоком уровне.

Он позволяет описывать данные как объекты с именами, типами, связями и дополнительной информацией.

---

# 2. Что такое OPC UA

OPC UA — это технология обмена структурированными данными между приложениями и устройствами.

Типичная схема:

```text
┌─────────────────┐
│ OPC UA Client   │
│                 │
│ SCADA            │
│ программа        │
│ аналитика        │
└────────┬────────┘
         │
         │ OPC UA
         │
┌────────▼────────┐
│ OPC UA Server   │
│                 │
│ данные устройства│
│ датчики          │
│ переменные       │
└─────────────────┘
```

Сервер предоставляет данные.

Клиент получает к ним доступ.

Например, сервер может предоставлять:

```text
Temperature
Pressure
MotorSpeed
RobotPosition
```

---

# 3. OPC UA Server

OPC UA Server — программа, которая предоставляет клиентам определённый набор данных и функций.

Например:

```text
OPC UA Server
│
├── Temperature
├── Pressure
├── MotorSpeed
├── Conveyor
│   ├── Speed
│   ├── State
│   └── Error
└── Robot
    ├── Position
    └── Status
```

Это уже значительно удобнее, чем просто поток байтов.

Клиент может обращаться к конкретному элементу.

---

# 4. Node

Основным элементом модели OPC UA является **Node** — узел.

Узел может представлять:

* переменную;
* объект;
* метод;
* тип;
* ссылку на другой элемент;
* другую информацию модели.

Например:

```text
Robot
│
├── Position
│
├── Speed
│
└── Status
```

Можно представить, что сервер предоставляет не просто список переменных, а дерево объектов.

---

# 5. NodeId

Каждый узел должен иметь идентификатор.

Например:

```text
ns=2;s=Robot.Speed
```

Здесь:

```text
ns=2
```

— namespace index,

а:

```text
s=Robot.Speed
```

— идентификатор узла.

Другой пример:

```text
ns=1;s=Temperature
```

Клиент использует NodeId, чтобы обратиться к конкретному узлу.

---

# 6. Namespace

Namespace помогает разделять идентификаторы различных моделей и источников данных.

Например:

```text
Namespace 1
    Temperature
    Pressure

Namespace 2
    Robot.Speed
    Robot.Position
```

Поэтому два разных пространства имён могут иметь одинаковые имена узлов без обязательного конфликта.

Упрощённо:

```text
ns=1;s=Temperature
```

и:

```text
ns=2;s=Temperature
```

могут быть разными узлами.

---

# 7. Значение переменной

У Node, представляющего переменную, есть значение.

Например:

```text
Node:
Temperature

Value:
24.7

Type:
Double
```

Но OPC UA может хранить не только само значение.

У него есть также информация о качестве и времени.

Упрощённо:

```text
Value
24.7

Status
Good

Timestamp
2026-10-01 12:00:00
```

Поэтому клиент может понять не только:

> Значение равно 24.7.

но и:

> Значение 24.7 получено в определённый момент и сервер считает его корректным.

---

# 8. StatusCode

Качество значения имеет большое значение.

Например:

```text
Good
```

означает, что значение считается корректным.

Но могут быть состояния:

```text
Bad
Uncertain
```

Например, датчик отключился.

Тогда вместо:

```text
Temperature = 24.7
```

клиент может получить:

```text
Temperature = 24.7
Status = Bad
```

Последнее измеренное число ещё не обязательно означает, что датчик сейчас работает.

Это важная особенность систем мониторинга.

---

# 9. Чтение значения

Клиент может запросить значение узла.

Например:

```text
Client
   │
   │ Read Temperature
   ▼
Server
   │
   │ 24.7 °C
   ▼
Client
```

Если клиенту нужно много переменных:

```text
Temperature
Pressure
Speed
Position
Status
```

он может читать несколько узлов.

---

# 10. Запись значения

OPC UA также может использоваться для записи.

Например:

```text
Client
   │
   │ Write MotorSpeed = 1000
   ▼
Server
```

Сервер может принять или отклонить запись в зависимости от прав доступа и логики приложения.

Это значит, что OPC UA может использоваться не только для мониторинга.

Однако запись в реальные устройства должна проектироваться осторожно.

Например, команда:

```text
StartMotor = true
```

может привести к физическому движению оборудования.

---

# 11. Подписки

Постоянно читать переменную каждую секунду не всегда удобно.

Представим:

```text
Client → Read
Client → Read
Client → Read
Client → Read
...
```

Если значение изменяется редко, большая часть запросов оказывается ненужной.

OPC UA предоставляет механизм **Subscription**.

Клиент говорит серверу:

> Следи за этими переменными и сообщай мне об изменениях.

Например:

```text
Client
  │
  │ Subscribe:
  │ Temperature
  │ Pressure
  │ Speed
  ▼
Server
```

Когда значение изменилось:

```text
Server
  │
  │ Temperature = 25.1
  ▼
Client
```

---

# 12. Monitored Items

Внутри подписки клиент может указать конкретные элементы, за которыми нужно наблюдать.

Например:

```text
Subscription
│
├── Temperature
├── Pressure
└── MotorSpeed
```

Эти элементы называются **Monitored Items**.

Таким образом:

```text
Subscription
    ↓
набор наблюдаемых Node
```

---

# 13. Почему subscriptions полезны

Представим систему с 10 000 переменных.

Если постоянно опрашивать каждую:

```text
10 000 запросов
10 000 ответов
10 000 запросов
...
```

это может создать большую нагрузку.

С подписками сервер может отправлять изменения только тогда, когда это необходимо.

Например:

```text
Temperature: 24.1 → 24.2
```

Только это изменение и отправляется клиенту.

---

# 14. OPC UA и TCP

OPC UA — не замена TCP в том смысле, что это протокол совершенно другого уровня.

Упрощённо можно представить:

```text
OPC UA
   ↓
TCP
   ↓
IP
   ↓
Ethernet
```

То есть TCP может обеспечивать транспорт, а OPC UA определяет, что именно означают передаваемые данные и операции.

---

# 15. Клиентская программа

Например, Python-приложение может подключиться к OPC UA Server:

```python
from asyncua import Client

async def main():
    client = Client(
        "opc.tcp://192.168.1.100:4840"
    )

    await client.connect()

    node = client.get_node("ns=2;s=Temperature")

    value = await node.read_value()

    print(value)

    await client.disconnect()
```

Конкретный адрес, namespace и NodeId зависят от сервера.

# 16. OPC UA в робототехнике

Представим роботизированную систему:

```text
Robot Controller
       │
       │
       ▼
 OPC UA Server
       │
       ├── Position
       ├── Speed
       ├── State
       ├── Battery
       └── Error
             │
             ▼
        OPC UA Client
             │
             ▼
       Monitoring PC
```

Теперь клиенту не нужно самостоятельно придумывать, как разобрать бинарный пакет.

Он обращается к определённым узлам.

Например:

```text
Robot.Position.X
Robot.Position.Y
Robot.Position.Z
Robot.Speed
Robot.State
```

# 17. Безопасность

OPC UA предусматривает механизмы безопасности.

В зависимости от конфигурации могут использоваться:

* шифрование;
* подпись сообщений;
* сертификаты;
* аутентификация;
* права доступа.

Это особенно важно, когда данные передаются не в изолированной локальной сети.

Однако наличие OPC UA само по себе не означает, что система автоматически безопасна.

Безопасность зависит от конкретной конфигурации:

```text
какие endpoints включены
какие политики разрешены
как выполняется аутентификация
какие права имеют пользователи
```

---

# 18. OPC UA и обычный собственный протокол

Представим два подхода.

### Собственный TCP-протокол

```text
TCP
 ↓
[CMD][LENGTH][DATA][CRC]
```

Нам самостоятельно нужно определить:

* формат пакета;
* команды;
* типы данных;
* обработку ошибок;
* версию протокола;
* структуру объектов.

### OPC UA

Многие общие механизмы уже определены:

```text
Nodes
Types
Values
Status
Timestamps
Subscriptions
Security
```

Поэтому OPC UA особенно полезен, когда много разных программ должны понимать одну модель данных.

---

# 19. Главное различие

Очень важно не путать:

```text
TCP
```

и:

```text
OPC UA
```

TCP отвечает в основном за транспорт потока.

OPC UA предоставляет более высокий уровень взаимодействия.

Можно провести аналогию:

```text
TCP
=
как доставить байты

OPC UA
=
что эти байты означают
и как клиент должен работать
с моделью данных
```

## Итог

OPC UA позволяет перейти от простого обмена байтами к обмену структурированными данными.

Упрощённая модель:

```text
OPC UA Client
      │
      │
      ▼
OPC UA Server
      │
      ├── Objects
      ├── Variables
      ├── Methods
      ├── Types
      └── Metadata
```

А сами данные могут передаваться поверх сетевых технологий:

```text
OPC UA
   ↓
TCP/IP
   ↓
Ethernet
```

В следующем уроке рассмотрим другой подход к обмену данными — MQTT, где устройства не подключаются напрямую друг к другу, а используют промежуточный брокер.
