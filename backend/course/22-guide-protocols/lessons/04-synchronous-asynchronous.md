# Синхронный и асинхронный обмен

## Цель

После этого урока вы должны понимать:

* что такое синхронная и асинхронная передача;
* зачем устройствам нужна синхронизация;
* как работает тактовый сигнал;
* что такое baud rate;
* как работает UART на базовом уровне;
* зачем нужны start bit и stop bit;
* почему в сетевом обмене важны таймауты.

---

## Устройства должны понимать время

Представим два устройства:

```text
A ───────────────→ B
```

A передаёт последовательность:

```text
10110100
```

Возникает вопрос:

> С какой скоростью нужно читать эти биты?

Если A отправляет:

```text
1 0 1 1 0 1 0 0
```

слишком быстро, B может не успеть их прочитать.

Если слишком медленно, B будет ожидать данные дольше.

Поэтому устройства должны иметь способ договориться о **времени передачи**.

Одним из вариантов является общий тактовый сигнал.

Другим — заранее известная скорость передачи.

Отсюда появляются понятия **синхронного** и **асинхронного** обмена.

---

## Синхронная передача

При синхронной передаче устройства используют общий механизм синхронизации, часто — тактовый сигнал.

Условно:

```text
CLOCK:  ─┐_┐_┐_┐_┐_┐_┐_┐_

DATA:   ──1──0──1──1──0──0─
```

Тактовый сигнал сообщает:

> Сейчас нужно считать очередной бит.

Условно:

```text
CLOCK → когда читать
DATA  → что читать
```

Один из распространённых примеров — SPI.

Там присутствует тактовая линия:

```text
SCLK
```

и линии данных.

Упрощённо:

```text
Controller
    │
    ├── SCLK ─────→ Device
    ├── MOSI ─────→ Device
    └── MISO ←───── Device
```

Контроллер генерирует тактовый сигнал, а устройство использует его для синхронизации.

---

## Почему это удобно

При наличии общего clock не обязательно заранее очень точно согласовывать внутренние часы устройств.

Вместо этого:

```text
clock
  ↓
синхронизация
  ↓
чтение данных
```

Каждый такт определяет момент передачи очередного бита.

Это особенно удобно для быстрых локальных соединений.

---

## Асинхронная передача

При асинхронной передаче отдельная тактовая линия между устройствами не используется.

Вместо этого стороны заранее договариваются о параметрах передачи.

Например:

```text
9600 baud
8 data bits
no parity
1 stop bit
```

Один из классических примеров — UART.

---

## Как получатель понимает, когда читать бит

Если нет отдельной линии clock, получатель должен самостоятельно определить границы передачи.

Для этого используются специальные биты.

Упрощённая структура UART-кадра:

```text
START | DATA | STOP
```

Например:

```text
0 | 01000001 | 1
```

Start bit сообщает:

> Начинается передача.

После этого приёмник отсчитывает интервалы времени и считывает биты данных.

Stop bit сообщает:

> Передача этого символа закончена.

---

## UART

UART расшифровывается как:

**Universal Asynchronous Receiver-Transmitter**

Это устройство/механизм, который преобразует байты в последовательный поток и обратно.

Программа может сказать:

```text
отправить байт 0x41
```

UART преобразует его в последовательность электрических состояний.

Условно:

```text
байт
  ↓
UART
  ↓
последовательный сигнал
  ↓
кабель
  ↓
UART
  ↓
байт
```

---

## Baud rate

В последовательной связи часто используется параметр:

**baud rate**

Например:

```text
9600
19200
115200
```

В типичном простом UART-контексте baud rate часто совпадает с количеством передаваемых символов в секунду, но строго говоря baud и bit/s — не всегда одно и то же понятие.

Для распространённого UART с двоичным сигналом можно грубо считать:

```text
115200 baud ≈ 115200 бит/с
```

Но это не означает:

```text
115200 байт/с
```

Один байт обычно требует больше времени из-за служебных битов.

---

## Почему 115200 baud не означает 115200 байт/с

Рассмотрим распространённый формат:

```text
1 start bit
8 data bits
1 stop bit
```

Итого:

```text
10 бит на один передаваемый байт
```

При:

```text
115200 бит/с
```

теоретическая скорость передачи байтов будет примерно:

```text
115200 / 10 = 11520 байт/с
```

Это упрощённая оценка без учёта дополнительных особенностей конкретной реализации.

---

## Start bit

Передатчик должен сообщить приёмнику:

> Сейчас начинается новый символ.

Для этого используется start bit.

Упрощённо:

```text
IDLE
  │
  ↓
START
  │
  ↓
DATA
  │
  ↓
STOP
  │
  ↓
IDLE
```

Приёмник обнаруживает начало передачи и начинает отсчитывать временные интервалы.

---

## Stop bit

После данных передатчик отправляет stop bit.

Он нужен для завершения кадра и помогает приёмнику определить, что передача текущего символа закончилась.

Упрощённо:

```text
START | 8 DATA BITS | STOP
```

После этого линия возвращается в состояние ожидания.

---

## Parity

Дополнительно можно использовать бит чётности — **parity bit**.

Например:

```text
START | DATA | PARITY | STOP
```

Parity позволяет обнаруживать некоторые простые ошибки.

Существуют варианты:

```text
Even parity
Odd parity
No parity
```

Например, при чётной parity количество единиц в соответствующей группе битов должно иметь заданную чётность.

Parity не является полноценной защитой от ошибок, но позволяет обнаружить часть проблем.

---

## Почему настройки UART должны совпадать

Представим:

```text
Устройство A:
115200, 8N1
```

а:

```text
Устройство B:
9600, 8N1
```

Они используют разную скорость.

Получатель будет неправильно определять границы битов.

Результат:

```text
данные → мусор
```

Поэтому параметры должны быть согласованы.

Например:

```text
115200
8 data bits
No parity
1 stop bit
```

Сокращённо:

```text
115200 8N1
```

---

## Что такое 8N1

Очень распространённая запись:

```text
8N1
```

означает:

```text
8 → 8 бит данных
N → No parity
1 → 1 stop bit
```

Например:

```text
115200 8N1
```

означает:

```text
115200 baud
8 data bits
no parity
1 stop bit
```

---

## Синхронный и асинхронный обмен — не «лучше» и «хуже»

У каждого подхода свои особенности.

Синхронная передача:

```text
данные + clock
```

может быть очень удобной для локального обмена между микросхемами.

Асинхронная:

```text
данные + заранее известная скорость
```

позволяет передавать данные без отдельной тактовой линии.

Поэтому выбор зависит от задачи.

---

## Синхронный обмен на примере SPI

Рассмотрим упрощённо SPI.

Есть:

```text
SCLK
MOSI
MISO
CS
```

Например:

```text
Controller
   │
   ├── SCLK ─────→ Sensor
   ├── MOSI ─────→ Sensor
   ├── MISO ←───── Sensor
   └── CS ───────→ Sensor
```

Контроллер генерирует clock.

На определённых переходах clock устройство считывает данные.

Условно:

```text
SCLK: _|‾|_|‾|_|‾|_|‾|_

DATA:  1   0   1   1
```

Clock определяет, когда считывать данные.

---

## Асинхронный обмен на примере UART

UART выглядит иначе:

```text
TX ─────────────→ RX
```

Отдельной линии clock нет.

Обе стороны заранее знают:

```text
115200 8N1
```

Передатчик отправляет:

```text
START
DATA
STOP
```

Приёмник использует известную скорость, чтобы определить моменты чтения.

---

## Таймауты

Синхронизация важна не только для отдельных битов.

Она важна и для обмена сообщениями.

Представим:

```text
Компьютер → запрос → устройство
```

Компьютер ожидает ответ:

```text
устройство → ответ
```

Но ответ может не прийти.

Например:

```text
устройство выключено
кабель повреждён
сеть недоступна
программа зависла
сообщение потерялось
```

Если компьютер будет ждать бесконечно, программа зависнет.

Поэтому используется **таймаут**.

Например:

```text
отправить запрос
↓
ждать 1000 мс
↓
ответа нет
↓
ошибка timeout
```

---

## Таймаут и повторная передача

Протокол может определить:

```text
TIMEOUT = 1 секунда
RETRIES = 3
```

Тогда:

```text
Запрос
  ↓
ждать 1 с
  ↓
нет ответа
  ↓
повторить
  ↓
ждать 1 с
  ↓
нет ответа
  ↓
повторить
  ↓
ждать 1 с
  ↓
нет ответа
  ↓
ошибка
```

Это уже часть поведения протокола.

---

## Синхронное и асинхронное выполнение программы

Здесь есть важная ловушка.

Слова **«синхронный»** и **«асинхронный»** используются и в программировании.

Например:

```python
result = read_sensor()
```

и:

```python
result = await read_sensor()
```

могут описывать синхронное и асинхронное выполнение программы.

Но это не то же самое, что синхронная и асинхронная **передача данных**.

Например, можно использовать асинхронную программу для работы с асинхронным UART.

Поэтому всегда нужно смотреть на контекст.

---

## Синхронизация бывает на разных уровнях

Это особенно важно понимать.

Мы можем говорить о синхронизации:

### Битов

Когда приёмник должен понять, когда считывать очередной бит.

### Байтов

Когда нужно определить границы символов.

### Сообщений

Когда нужно определить начало и конец сообщения.

### Обмена

Когда нужно определить:

```text
кто отправляет;
кто отвечает;
сколько ждать;
когда повторять.
```

Все эти механизмы могут существовать одновременно.

---

## Пример полного обмена

Представим:

```text
Компьютер ↔ Микроконтроллер
```

Используется UART:

```text
115200 8N1
```

Протокол сообщений:

```text
[START][CMD][LEN][DATA][CRC]
```

Обмен:

```text
Компьютер → запрос температуры
Микроконтроллер → температура
```

Если ответа нет:

```text
1 секунда
↓
повтор
↓
1 секунда
↓
повтор
↓
ошибка
```

Здесь одновременно работают несколько механизмов:

```text
UART
  ↓
синхронизация битов

формат сообщения
  ↓
синхронизация структуры

таймаут
  ↓
контроль обмена
```

---

## Главное

Синхронная передача обычно использует общий механизм тактирования:

```text
CLOCK + DATA
```

Асинхронная передача не использует отдельный clock между устройствами:

```text
DATA
```

но требует заранее согласованных параметров.

UART — классический пример асинхронной последовательной передачи.

SPI — классический пример синхронного обмена.

А таймауты нужны уже на уровне обмена сообщениями, чтобы система не ждала ответ бесконечно.
