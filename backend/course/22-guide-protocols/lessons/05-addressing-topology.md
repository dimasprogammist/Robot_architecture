# Адресация и способы взаимодействия устройств

## Цель

После этого урока вы должны понимать:

* зачем устройствам нужны адреса;
* что такое point-to-point;
* что такое общая шина;
* чем отличаются client/server и peer-to-peer;
* что такое broadcast и multicast;
* почему топология и способ взаимодействия — разные понятия;
* как выбрать простой способ организации обмена.

---

## Когда устройств становится несколько

С двумя устройствами всё относительно просто:

```text
A ───────── B
```

A знает, что B находится на другом конце соединения.

Но представим сеть:

```text
A ──┐
B ──┼──── сеть
C ──┤
D ──┘
```

Теперь возникает вопрос:

> Если A отправляет данные, кому они предназначены?

Для этого используются **адреса** и правила доставки.

---

## Что такое адрес

Адрес — это идентификатор, позволяющий определить участника обмена.

Например:

```text
Device 1
Device 2
Device 3
```

или:

```text
10.0.0.10
10.0.0.11
10.0.0.12
```

или другой идентификатор, в зависимости от системы.

Главная идея:

```text
отправитель
    ↓
адрес получателя
    ↓
сообщение
```

---

## Адрес не обязательно означает IP

Это очень важно.

Адресом может быть:

* номер устройства;
* MAC-адрес;
* IP-адрес;
* номер узла;
* идентификатор сообщения;
* логическое имя.

Например, в простой системе можно использовать:

```text
01
02
03
```

А в IP-сети:

```text
192.168.1.10
192.168.1.20
```

Это разные механизмы адресации, хотя общая идея похожа.

---

## Point-to-point

Самая простая схема — **point-to-point**, то есть соединение «точка-точка».

```text
A ───────── B
```

Есть два участника.

A знает:

> Моё соединение ведёт к B.

B знает:

> Моё соединение ведёт к A.

Отдельный адрес получателя может вообще не понадобиться.

Например, простой последовательный канал между компьютером и микроконтроллером:

```text
Компьютер
    │
    │ UART
    │
Микроконтроллер
```

Если к линии подключено только два устройства, адресация может быть ненужной.

---

## Общая шина

Теперь представим несколько устройств на одном канале:

```text
A ─┬────────────┬─ B
   │            │
   C            D
```

Все устройства используют общую среду передачи.

Теперь сообщение должно содержать информацию о том, кому оно предназначено.

Например:

```text
[ADDRESS][DATA]
```

Сообщение:

```text
03 55
```

может означать:

> отправить данные `55` устройству №3.

Устройство №3 принимает сообщение.

Другие устройства могут его проигнорировать.

---

## Почему все устройства видят сообщение

В общей среде передачи сигнал физически может быть доступен нескольким участникам.

Например:

```text
        сообщение
            ↓
      ─────────────
       │    │    │
       ↓    ↓    ↓
      A     B    C
```

Поэтому участники должны уметь определить:

> Это сообщение предназначено мне?

Если адрес:

```text
02
```

то устройство №2 обрабатывает сообщение, а остальные игнорируют его.

---

## Звезда

Другой распространённый вариант — топология «звезда».

```text
       A
       │
       │
B ─── Switch ─── C
       │
       │
       D
```

Все устройства подключаются к центральному узлу.

В Ethernet-сетях таким центральным устройством часто является switch.

В этой схеме физически устройство A не подключено напрямую к C.

Обмен проходит через центральный узел.

---

## Топология и протокол — разные вещи

Важно не путать эти понятия.

**Топология** отвечает на вопрос:

> Как физически или логически соединены устройства?

Например:

```text
point-to-point
bus
star
```

**Протокол** отвечает на вопрос:

> По каким правилам устройства обмениваются данными?

Например:

```text
TCP
HTTP
Modbus
MQTT
```

Одна и та же топология может использовать разные протоколы.

---

## Client и Server

Теперь перейдём от физической структуры к логике взаимодействия.

Один из распространённых вариантов — **client/server**.

```text
Client ─────→ Server
       ←─────
```

Клиент отправляет запрос.

Сервер принимает запрос и отвечает.

Например:

```text
Клиент → GET /temperature
Сервер → 24.5
```

Клиент обычно инициирует обмен.

---

## Пример с веб-сайтом

Когда браузер открывает страницу:

```text
Браузер → Сервер
```

браузер выступает в роли клиента.

Сервер принимает запрос:

```text
GET /index.html
```

и возвращает ответ.

```text
Сервер → HTML
```

Получается:

```text
Client
  │
  │ request
  ↓
Server
  │
  │ response
  ↓
Client
```

---

## Сервер не обязательно означает мощный компьютер

Это распространённое заблуждение.

Слово **server** в данном контексте описывает роль в обмене.

Например, микроконтроллер может быть сервером:

```text
Компьютер → запрос → Микроконтроллер
Компьютер ← ответ  ← Микроконтроллер
```

Несмотря на то что микроконтроллер намного слабее компьютера.

То же устройство в другой системе может выступать клиентом.

---

## Peer-to-peer

В модели **peer-to-peer** участники могут взаимодействовать напрямую, без постоянного выделенного сервера.

Условно:

```text
A ↔ B
```

или:

```text
A ↔ B
↕   ↕
C ↔ D
```

Устройства могут выполнять одинаковые или похожие роли.

Например, два компьютера могут напрямую обмениваться файлами.

---

## Client/server и point-to-point — не одно и то же

Эти понятия относятся к разным уровням.

Например:

```text
Point-to-point
```

говорит:

> Есть два соединённых участника.

А:

```text
Client/server
```

говорит:

> Один участник отправляет запрос, другой предоставляет сервис.

Поэтому вполне возможна система:

```text
Client
  ↕
Server
```

при физическом соединении:

```text
point-to-point
```

---

## Broadcast

Иногда сообщение должно попасть не одному устройству, а всем.

Например:

```text
A → всем
```

Это называется **broadcast**.

Условно:

```text
         ┌── B
         │
A ───────┼── C
         │
         └── D
```

A отправляет сообщение:

```text
BROADCAST: STOP
```

и все устройства получают его.

Например, команда может означать:

> Остановить все двигатели.

Broadcast полезен, когда сообщение действительно предназначено всей группе.

---

## Multicast

Иногда сообщение должно получить только определённая группа устройств.

Например:

```text
A → B
A → C
```

но:

```text
A ↛ D
```

Это можно реализовать через **multicast**.

Устройства объединяются в логическую группу:

```text
Группа "robots"

B ─┐
C ─┼── multicast group
E ─┘
```

Сообщение группе получают только участники этой группы.

---

## Unicast

Противоположная идея — отправка одному конкретному получателю.

```text
A → B
```

Это называется **unicast**.

Получатель один.

Можно представить три базовых варианта:

```text
Unicast:
A → B

Broadcast:
A → всем

Multicast:
A → группе
```

---

## Зачем вообще нужны разные способы доставки

Представим систему из 100 устройств.

Нужно передать:

> Температура устройства №25 равна 24 °C.

Логично отправить:

```text
A → Device 25
```

То есть unicast.

Теперь другое сообщение:

> Всем устройствам перейти в безопасное состояние.

Здесь удобно:

```text
A → всем
```

То есть broadcast.

А если нужно отправить команду только роботам:

```text
A → группа роботов
```

можно использовать multicast.

Выбор способа доставки зависит от задачи.

---

## Адресация в реальной системе

Рассмотрим сеть:

```text
PC
 │
 ├──── Robot 1
 ├──── Robot 2
 ├──── Robot 3
 └──── Sensor
```

Можно назначить:

```text
Robot 1 → 192.168.1.10
Robot 2 → 192.168.1.11
Robot 3 → 192.168.1.12
Sensor  → 192.168.1.20
```

Теперь компьютер может отправить:

```text
192.168.1.11
```

и сеть сможет определить, что это Robot 2.

---

## Несколько адресов у одного устройства

У одного устройства может быть несколько видов адресов.

Например:

```text
Компьютер
 ├── MAC
 ├── IP
 └── порт
```

Каждый используется на своём уровне.

Например:

```text
IP
```

помогает определить устройство в IP-сети.

А:

```text
порт
```

помогает определить конкретное сетевое приложение или сервис на этом устройстве.

Например:

```text
192.168.1.20:8080
```

можно условно читать как:

```text
устройство: 192.168.1.20
приложение/сервис: порт 8080
```

---

## Адрес и порт

Представим сервер:

```text
192.168.1.100
```

На нём работают:

```text
веб-сервер → 80
другое приложение → 5000
другая служба → 8080
```

Тогда:

```text
192.168.1.100:80
```

и:

```text
192.168.1.100:5000
```

обращаются к одному компьютеру, но к разным сетевым службам.

Это важная идея, которая понадобится при изучении TCP/IP.

---

## Как выбрать схему

При проектировании системы сначала полезно ответить на несколько вопросов.

### Сколько участников?

```text
2
```

или:

```text
10
```

или:

```text
1000
```

### Кто инициирует обмен?

```text
клиент
```

или:

```text
любой участник
```

### Нужно ли отправлять сообщение одному устройству?

```text
unicast
```

или группе:

```text
multicast
```

или всем:

```text
broadcast
```

### Как соединены устройства?

```text
point-to-point
bus
star
```

Ответы на эти вопросы влияют на выбор архитектуры.

---

## Пример системы роботов

Представим:

```text
          Компьютер
              │
           Ethernet
              │
            Switch
       ┌──────┼──────┐
       │      │      │
    Robot1 Robot2 Robot3
```

Физически это похоже на звезду.

Логически компьютер может работать как сервер:

```text
Robot → запрос состояния → Computer
Computer → команда → Robot
```

Адресация:

```text
Robot1 → 192.168.1.10
Robot2 → 192.168.1.11
Robot3 → 192.168.1.12
```

Обычная команда одному роботу:

```text
Computer → Robot2
```

может быть unicast.

А команда:

```text
STOP ALL
```

может быть организована как broadcast или другим механизмом групповой доставки.

---

## Главное

Несколько понятий нужно держать отдельно:

```text
ТОПОЛОГИЯ
Как соединены устройства?

        ↓

АДРЕСАЦИЯ
Как определить конкретное устройство?

        ↓

МОДЕЛЬ ВЗАИМОДЕЙСТВИЯ
Кто с кем и как общается?

        ↓

СПОСОБ ДОСТАВКИ
Одному, группе или всем?

        ↓

ПРОТОКОЛ
Какие правила обмена используются?
```

Основные модели доставки:

```text
Unicast
A → B

Broadcast
A → всем

Multicast
A → группе
```

Основные модели взаимодействия:

```text
Client / Server
Peer-to-peer
```

Основные варианты топологии:

```text
Point-to-point
Bus
Star
```

Это не взаимоисключающие понятия. Они описывают разные стороны одной системы.
