# Как устроено сообщение

## Цель

После этого урока вы должны понимать:

* что такое сообщение и пакет;
* из каких частей может состоять сообщение;
* зачем нужны заголовок, адрес, команда и данные;
* что такое длина сообщения;
* как определить конец сообщения;
* зачем нужна контрольная сумма;
* почему бинарные протоколы часто используют фиксированную структуру.

---

## Откуда берётся сообщение

В предыдущих уроках мы говорили, что устройства обмениваются данными по определённым правилам.

Теперь посмотрим внутрь самого обмена.

Представим:

```text
Компьютер → Микроконтроллер
```

Компьютер хочет отправить команду:

> Установить скорость двигателя 1500.

Нельзя просто передать компьютеру строку:

```text
1500
```

Получатель должен понимать:

* что это команда;
* для какого устройства она предназначена;
* какое значение передано;
* где сообщение начинается;
* где оно заканчивается;
* не повреждены ли данные.

Поэтому сообщение обычно имеет определённую структуру.

---

## Самая простая структура

Например, можно придумать такой формат:

```text
[КОМАНДА][ДАННЫЕ]
```

Для команды установки скорости:

```text
05 96
```

где:

```text
05 → установить скорость
96 → значение
```

Но такой формат быстро становится недостаточным.

Что делать, если в сети несколько устройств?

Тогда нужен адрес:

```text
[АДРЕС][КОМАНДА][ДАННЫЕ]
```

Например:

```text
02 05 96
```

где:

```text
02 → устройство №2
05 → команда
96 → значение
```

---

## Типичная структура сообщения

Более полноценное сообщение может выглядеть так:

```text
┌────────┬────────┬────────┬────────┬────────┐
│ START  │ ADDR   │ CMD    │ DATA   │ CRC    │
└────────┴────────┴────────┴────────┴────────┘
```

Здесь:

**START** — начало сообщения.

**ADDR** — адрес получателя.

**CMD** — команда.

**DATA** — данные.

**CRC** — проверка целостности.

Это только пример. Реальные протоколы могут использовать совершенно другую структуру.

---

## Начало сообщения

Получателю нужно понять:

> Где начинается сообщение?

Например, можно использовать специальный байт:

```text
AA
```

Тогда сообщение:

```text
AA 02 05 96 7F
```

можно интерпретировать как:

```text
AA → начало
02 → адрес
05 → команда
96 → данные
7F → контроль
```

Если поток данных начинается с:

```text
10 43 72 AA 02 05 96 7F
```

получатель может искать:

```text
AA
```

и после него начинать разбор сообщения.

---

## Адрес

Если устройств несколько:

```text
          ┌── Device 1
          │
шина ─────┼── Device 2
          │
          └── Device 3
```

нужно понимать, кому предназначено сообщение.

Например:

```text
01 → устройство 1
02 → устройство 2
03 → устройство 3
```

Тогда:

```text
02 05 96
```

может означать:

> устройству №2 выполнить команду №5 со значением 150.

Адрес не всегда присутствует в сообщении.

Если соединение point-to-point:

```text
A ───────── B
```

то стороны уже знают, с кем они соединены.

В таком случае отдельный адрес может быть не нужен.

---

## Команда

Команда определяет, **что должен сделать получатель**.

Например:

```text
01 → прочитать температуру
02 → прочитать влажность
03 → включить двигатель
04 → выключить двигатель
05 → установить скорость
```

Тогда:

```text
03
```

означает:

> включить двигатель.

А:

```text
05 96
```

может означать:

> установить скорость 150.

---

## Данные

Команда часто сопровождается дополнительными данными.

Например:

```text
05 96
```

может означать:

```text
05 → установить скорость
96 → скорость
```

Но данные могут занимать несколько байтов:

```text
05 00 96
```

Например:

```text
05 → команда
00 96 → значение 150
```

Можно передавать числа, текст, координаты, измерения и другие данные.

---

## Размер данных

Возникает новая проблема.

Допустим, сообщение выглядит так:

```text
02 05 00 96
```

Получатель знает, где адрес и команда, но как он понимает, сколько байтов относится к данным?

Можно заранее определить фиксированный размер.

Например:

```text
ADDR = 1 байт
CMD  = 1 байт
DATA = 2 байта
```

Тогда получатель всегда знает структуру:

```text
[1][1][2]
```

Другой вариант — добавить длину:

```text
[ADDR][CMD][LEN][DATA]
```

Например:

```text
02 05 03 10 20 30
```

Здесь:

```text
02 → адрес
05 → команда
03 → длина данных
10 20 30 → три байта данных
```

---

## Зачем нужна длина

Поле длины особенно удобно, когда данные имеют переменный размер.

Например:

```text
[ADDR][CMD][LEN][DATA]
```

Сообщение:

```text
01 20 05 48 65 6C 6C 6F
```

можно разобрать:

```text
01 → адрес
20 → команда
05 → длина
48 65 6C 6C 6F → 5 байтов данных
```

Данные здесь являются ASCII-строкой:

```text
Hello
```

Получатель видит `05` и понимает, что после поля длины нужно прочитать ещё пять байтов.

---

## Конец сообщения

Не всегда используется поле длины.

Иногда протокол определяет специальный символ конца.

Например:

```text
START = <
END   = >
```

Сообщение:

```text
<SET SPEED 1500>
```

Получатель знает:

```text
< → начало
> → конец
```

Это простой текстовый протокол.

---

## Фиксированный размер

Другой вариант — сообщение всегда имеет одинаковый размер.

Например:

```text
[ADDR][CMD][VALUE][CRC]
```

где:

```text
ADDR  = 1 байт
CMD   = 1 байт
VALUE = 2 байта
CRC   = 2 байта
```

Итого:

```text
6 байт
```

Получателю не нужно искать конец сообщения.

Он знает:

> Каждое сообщение занимает ровно 6 байтов.

Такой подход часто удобен для устройств с ограниченными ресурсами.

---

## Контрольная сумма

Теперь представим, что сообщение должно пройти через кабель:

```text
Устройство A
     ↓
   кабель
     ↓
Устройство B
```

Из-за помех один бит может измениться.

Например, было:

```text
01001010
```

а стало:

```text
01000010
```

Получатель получил другие данные.

Проблема:

> Как понять, что сообщение повреждено?

Для этого применяют механизмы контроля целостности.

Один из простых вариантов — контрольная сумма.

---

## Простейшая checksum

Допустим, данные:

```text
10 20 30
```

Можно вычислить сумму:

```text
10 + 20 + 30 = 60
```

и добавить её к сообщению:

```text
10 20 30 60
```

Получатель снова вычисляет сумму.

Если результат отличается:

```text
получено: 61
ожидалось: 60
```

значит данные, скорее всего, повреждены.

Это очень упрощённый пример.

Реальные алгоритмы могут быть намного сложнее.

---

## CRC

Один из распространённых способов контроля целостности — **CRC**, или Cyclic Redundancy Check.

CRC используется во множестве протоколов.

Упрощённая идея:

```text
данные
  ↓
алгоритм CRC
  ↓
контрольное значение
```

Отправитель вычисляет CRC:

```text
DATA → CRC
```

и отправляет:

```text
DATA + CRC
```

Получатель получает сообщение:

```text
DATA + CRC
```

и самостоятельно вычисляет CRC от данных.

Если значения совпадают:

```text
CRC_received == CRC_calculated
```

данные прошли проверку.

Если нет:

```text
CRC_received != CRC_calculated
```

сообщение считается повреждённым.

---

## Важно: CRC не исправляет данные

CRC позволяет обнаружить множество ошибок, но сама по себе не означает:

> «Исправь повреждённый байт».

Обычно система делает другое:

```text
сообщение повреждено
       ↓
сообщение отклоняется
       ↓
при необходимости запрос повторяется
```

Поэтому контроль целостности часто работает вместе с механизмом повторной передачи.

---

## Подтверждение

Представим:

```text
A → команда → B
```

Как A узнает, что B получил команду?

B может отправить подтверждение:

```text
B → OK → A
```

Получается:

```text
A → COMMAND
B → OK
```

Если ответа нет:

```text
A → COMMAND
      ...
      ...
```

после таймаута A может повторить команду.

Например:

```text
A → COMMAND
B → OK
```

или:

```text
A → COMMAND
       X
       ↓
     потеря
       
A → COMMAND
B → OK
```

Так протокол становится устойчивее к проблемам передачи.

---

## Пример собственного протокола

Давайте спроектируем небольшой протокол для робота.

Пусть сообщение имеет формат:

```text
[START][ADDR][CMD][LEN][DATA][CRC]
```

Например:

```text
AA 02 10 02 00 64 7F
```

Можно определить:

```text
AA → начало сообщения
02 → адрес робота
10 → команда движения
02 → длина данных
00 64 → скорость
7F → CRC
```

Получатель делает:

```text
1. Находит AA.
2. Читает адрес.
3. Читает команду.
4. Читает длину.
5. Читает указанное количество байтов.
6. Проверяет CRC.
7. Выполняет команду.
8. Отправляет ответ.
```

Это уже вполне настоящий протокол, пусть и очень простой.

---

## Текстовые и бинарные сообщения

Сообщения можно передавать в текстовом или бинарном виде.

### Текстовый вариант

Например:

```text
SET_SPEED 1500
```

Преимущества:

* легко читать человеку;
* удобно отлаживать через терминал;
* просто тестировать.

Недостатки:

* сообщения могут занимать больше места;
* требуется разбор текста;
* возможны неоднозначности формата.

### Бинарный вариант

Например:

```text
02 05 05 DC
```

Преимущества:

* компактность;
* быстрый разбор;
* удобно для небольших устройств.

Недостатки:

* человеку сложно читать;
* отладка требует специальных инструментов;
* формат нужно строго документировать.

---

## Почему формат сообщения нужно документировать

Если вы создаёте собственный протокол, недостаточно написать программу.

Нужно описать формат.

Например:

```text
Byte 0 — START
Byte 1 — ADDRESS
Byte 2 — COMMAND
Byte 3 — LENGTH
Byte 4..N — DATA
Последние 2 байта — CRC
```

И отдельно описать команды:

```text
0x01 — READ_TEMPERATURE
0x02 — READ_SPEED
0x03 — SET_SPEED
0x04 — STOP
```

Тогда другой разработчик сможет написать совместимую программу.

---

## Главное

Большинство сообщений можно мысленно представить как:

```text
┌───────────┐
│ начало    │
├───────────┤
│ адрес     │
├───────────┤
│ команда   │
├───────────┤
│ длина     │
├───────────┤
│ данные    │
├───────────┤
│ проверка  │
└───────────┘
```

Конкретный протокол может не содержать некоторые из этих полей или использовать совершенно другую структуру.

Но идея остаётся одинаковой:

> получатель должен иметь достаточно информации, чтобы однозначно разобрать сообщение и понять, что с ним делать.

## Практика

### Задание 1

Придумайте сообщение для команды:

> Установить скорость двигателя 1200 об/мин.

Используйте структуру:

```text
[START][ADDR][CMD][LEN][DATA][CRC]
```

Определите назначение каждого поля.

### Задание 2

Придумайте три команды для робота:

```text
MOVE
STOP
GET_STATUS
```

Назначьте каждой команде числовой код.

### Задание 3

Объясните, зачем нужны:

* адрес;
* команда;
* длина;
* CRC;
* подтверждение.

```text
SET_SPEED 1500
```

и:

```text
AA 02 03 02 05 DC CRC
```

Какие преимущества и недостатки есть у каждого формата?

```text

```

* читать влажность;
* включать устройство;

Опишите структуру сообщения и список команд.
