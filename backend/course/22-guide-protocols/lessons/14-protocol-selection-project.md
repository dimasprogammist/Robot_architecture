# Как выбрать протокол и построить систему обмена

## Цель

За предыдущие уроки мы рассмотрели много разных технологий:

```text
UART
RS-232
RS-485
Modbus
CAN
Ethernet
TCP/IP
OPC UA
MQTT
```

Теперь важно научиться не просто помнить их названия, а понимать, **какую задачу решает каждый протокол и как выбрать подходящий вариант**.

После урока вы должны уметь:

* определить требования к обмену данными;
* разделять физический интерфейс, транспорт и протокол приложения;
* выбирать подходящий способ связи;
* проектировать простую систему обмена;
* понимать, когда нужен TCP, UDP, MQTT или OPC UA;
* строить архитектуру из нескольких уровней.

---

# 1. Не существует одного лучшего протокола

Очень легко попасть в ловушку:

> Какой протокол лучше?

На практике такой вопрос почти всегда неполный.

Нужно спрашивать:

> Какой протокол лучше подходит для конкретной задачи?

Например, у нас есть:

```text
датчик температуры
```

и:

```text
робот с несколькими контроллерами
```

и:

```text
сервер с десятками приложений
```

Для этих задач могут использоваться совершенно разные технологии.

---

# 2. Сначала определяем задачу

Перед выбором протокола нужно ответить на несколько вопросов.

### Сколько устройств?

```text
2
10
100
1000
```

### Какое расстояние?

```text
10 см
2 м
100 м
1 км
```

### Какая скорость нужна?

```text
несколько байт в секунду
тысячи сообщений в секунду
поток данных
```

### Нужна ли гарантированная доставка?

Иногда потеря одного сообщения критична.

Иногда нет.

### Нужна ли связь в реальном времени?

Например:

```text
управление движением
```

требует других свойств, чем:

```text
передача температуры раз в минуту
```

### Кто должен знать о данных?

```text
один получатель
несколько получателей
динамически подключающиеся клиенты
```

---

# 3. Первый уровень — физическая связь

Сначала нужно определить, как устройства физически соединяются.

Например:

```text
UART
Ethernet
CAN
RS-485
Wi-Fi
```

Это ещё не обязательно полный протокол обмена.

Например:

```text
RS-485
```

описывает физический способ передачи сигнала, но не определяет полностью, что означает сообщение.

Поэтому поверх RS-485 может работать:

```text
Modbus RTU
```

Получается:

```text
Modbus RTU
    ↓
RS-485
```

---

# 4. Второй уровень — транспорт

В сетях Ethernet часто используются:

```text
TCP
UDP
```

Например:

```text
Application
    ↓
TCP
    ↓
IP
    ↓
Ethernet
```

или:

```text
Application
    ↓
UDP
    ↓
IP
    ↓
Ethernet
```

TCP и UDP определяют особенности доставки данных.

Но сами по себе они ещё не говорят, что означает сообщение.

---

# 5. Третий уровень — протокол приложения

На верхнем уровне появляется смысл данных.

Например:

```text
Modbus
OPC UA
MQTT
HTTP
собственный протокол
```

Теперь можно построить полноценную цепочку:

```text
OPC UA
  ↓
TCP
  ↓
IP
  ↓
Ethernet
```

или:

```text
MQTT
  ↓
TCP
  ↓
IP
  ↓
Wi-Fi
```

или:

```text
Modbus RTU
  ↓
RS-485
```

---

# 6. Пример: два микроконтроллера

Представим:

```text
MCU A ───────── MCU B
```

Расстояние:

```text
1 метр
```

Передавать нужно:

```text
команды
состояние
несколько чисел
```

Нет необходимости использовать сложную сетевую инфраструктуру.

Можно использовать:

```text
UART
```

и определить простой протокол:

```text
[COMMAND][LENGTH][DATA][CRC]
```

Например:

```text
[01][02][64][00][CRC]
```

где:

```text
01 = команда
02 = длина
64 00 = данные
```

Для маленькой системы собственный простой протокол может быть вполне достаточным.

---

# 7. Пример: несколько устройств на общей линии

Теперь устройств больше:

```text
MCU 1
MCU 2
MCU 3
MCU 4
```

Они подключены к общей линии.

Для такой задачи может подойти:

```text
CAN
```

CAN специально рассчитан на обмен между множеством узлов в общей шине.

У каждого сообщения есть идентификатор.

Устройства могут определять, какие сообщения им интересны.

---

# 8. Пример: устройства на большом расстоянии

Представим:

```text
Device A ───────────── Device B
```

и между ними десятки метров.

Для проводного соединения может использоваться:

```text
RS-485
```

А поверх него:

```text
Modbus RTU
```

Получается:

```text
Application
    ↓
Modbus RTU
    ↓
RS-485
    ↓
Cable
```

Это уже полноценная система обмена.

---

# 9. Пример: устройство подключено к локальной сети

Представим:

```text
                 Ethernet
                    │
             ┌──────┴──────┐
             │   Switch    │
             └─┬────┬────┬─┘
               │    │    │
              PC   MCU   Server
```

Теперь можно использовать IP.

Например:

```text
MCU:
192.168.1.20
```

Сервер:

```text
192.168.1.100
```

Для обмена можно использовать TCP.

Например:

```text
MCU → TCP → Server
```

И определить собственный протокол:

```text
GET_STATUS
GET_POSITION
SET_SPEED
```

---

# 10. Когда появляется OPC UA

Теперь представим, что данные должны использовать несколько разных программ:

```text
Устройство
    │
    ▼
OPC UA Server
    │
    ├────► SCADA
    ├────► Dashboard
    ├────► Analytics
    └────► Другой клиент
```

Нам важно не просто передавать байты.

Нужно представить данные как понятную модель:

```text
Robot
├── Position
├── Speed
├── State
└── Battery
```

В такой ситуации OPC UA может быть удобным решением.

---

# 11. Когда появляется MQTT

Другой сценарий:

```text
100 устройств
     │
     ▼
   Broker
     │
 ┌───┼─────┐
 ▼   ▼     ▼
DB  Web   Analytics
```

Каждое устройство публикует данные.

Например:

```text
robot/17/temperature
robot/17/battery
robot/17/state
```

А потребители подписываются на нужные Topics.

Здесь MQTT хорошо соответствует модели:

```text
publish
   ↓
broker
   ↓
subscribe
```

# 12. TCP или UDP

Если мы используем IP-сеть, часто возникает вопрос:

```text
TCP или UDP?
```

Нужно определить требования.

### TCP

Подходит, когда важны:

* надёжная доставка;
* порядок данных;
* поток;
* контроль соединения.

Например:

```text
передача конфигурации
файла
команд
важных данных
```

### UDP

Может быть удобен, когда важны:

* низкие задержки;
* простота;
* регулярные обновления;
* допустимость потери отдельных пакетов.

Например:

```text
текущая позиция
телеметрия
поток состояний
```

Но это не означает, что TCP всегда медленный, а UDP всегда быстрый. Реальные характеристики зависят от сети и приложения.

---

# 13. Сравнение технологий

Полезно держать в голове примерно такую картину:

| Технология | Основная идея | Типичные задачи |
|---|---|---|
| UART | Простая последовательная связь | MCU ↔ MCU, отладка |
| RS-232 | Последовательный интерфейс | Точечное соединение |
| RS-485 | Дифференциальная последовательная связь | Несколько устройств, длиннее линии |
| Modbus RTU | Команды и регистры поверх последовательной связи | Простые устройства |
| CAN | Сообщения в общей шине | Автомобили, роботы, контроллеры |
| Ethernet | Локальная сеть | Компьютеры и устройства |
| TCP | Надёжный поток | Клиент-серверные приложения |
| UDP | Датаграммы | Телеметрия, потоковые данные |
| OPC UA | Структурированная модель данных | Интеграция устройств и приложений |
| MQTT | Publish/Subscribe | IoT, телеметрия |

Это не строгая таблица возможностей, а ориентир для первоначального выбора.

# 14. Не нужно выбирать всё сразу

В реальной системе может использоваться несколько протоколов одновременно.

Например:

```text
Датчик
  │
  │ CAN
  ▼
Контроллер
  │
  │ Ethernet
  ▼
Компьютер
  │
  │ OPC UA
  ▼
Приложение
```

Или:

```text
Микроконтроллер
      │
      │ MQTT
      ▼
    Broker
      │
      ├────► Database
      ├────► Dashboard
      └────► Analytics
```

То есть вопрос:

> Какой протокол использовать?

может иметь ответ:

> Несколько протоколов, каждый на своём уровне.

---

# 15. Проектируем систему по шагам

Допустим, нам нужно построить систему мониторинга робота.

Требования:

```text
1 робот
1 контроллер
1 компьютер
данные о состоянии
позиция
температура
ошибки
команды управления
```

Начинаем проектирование.

### Шаг 1. Физическое соединение

Допустим:

```text
Ethernet
```

### Шаг 2. Сетевая адресация

Например:

```text
Robot:
192.168.1.20

Computer:
192.168.1.10
```

### Шаг 3. Транспорт

Допустим:

```text
TCP
```

### Шаг 4. Формат данных

Можно определить собственный протокол:

```text
GET_STATUS
GET_POSITION
SET_SPEED
```

Или использовать существующий протокол, если он подходит.

---

# 16. Более масштабная система

Теперь представим 50 роботов:

```text
Robot 1
Robot 2
...
Robot 50
```

Каждый напрямую подключается к одному серверу.

Можно построить:

```text
Robots
   │
   │ MQTT
   ▼
Broker
   │
   ├────► Database
   ├────► Dashboard
   └────► Analytics
```

Роботы публикуют:

```text
robots/1/state
robots/2/state
...
robots/50/state
```

Добавление нового потребителя не требует изменения всех роботов.

Например, можно добавить:

```text
Alert Service
```

который подпишется на:

```text
robots/+/errors
```

---

# 17. А что если нужна модель данных?

Представим другую задачу.

Нам нужно предоставить приложениям:

```text
Robot
├── Position
│   ├── X
│   ├── Y
│   └── Z
├── Speed
├── Battery
├── State
└── Errors
```

Кроме значений нужны:

* типы;
* состояния;
* временные метки;
* качество;
* подписки;
* описание структуры.

Тогда OPC UA может быть естественным кандидатом.

---

# 18. А что если нужно просто отправить команду?

Иногда задача намного проще.

Например:

```text
компьютер → микроконтроллер
```

Команда:

```text
LED_ON
```

В таком случае полноценная сложная модель может быть избыточной.

Можно использовать:

```text
UART
```

или:

```text
TCP
```

с собственным простым протоколом.

Важно не усложнять систему без необходимости.

---

# 19. Надёжность — это не только протокол

Очень распространённая ошибка — считать, что выбор протокола автоматически решает все проблемы.

Например, TCP обеспечивает надёжную доставку потока, но приложение всё равно должно учитывать:

```text
соединение разорвалось
сервер недоступен
клиент завис
данные устарели
команда выполнена или нет
```

Поэтому хороший протокол приложения может содержать:

```text
команды
ответы
коды ошибок
идентификаторы сообщений
таймауты
heartbeat
версию протокола
```

Например:

```text
Client:
SET_SPEED 100

Server:
OK
```

или:

```text
Server:
ERROR MOTOR_NOT_READY
```

---

# 20. Heartbeat

В распределённых системах часто нужно понимать:

> Устройство всё ещё работает?

Для этого можно использовать heartbeat.

Например:

```text
Device → HEARTBEAT
Server → OK
```

или устройство периодически публикует:

```text
robot/1/heartbeat
```

Если сообщений давно нет:

```text
последний heartbeat:
10:00:00

текущее время:
10:00:30
```

приложение может считать устройство недоступным.

Это уже часть архитектуры системы, а не просто выбор транспорта.

---

# 21. Таймауты

Любая сетевая система должна учитывать возможность отсутствия ответа.

Например:

```text
Client
  │
  │ REQUEST
  ▼
Server
```

Если ответа нет:

```text
timeout
```

После этого приложение может:

```text
повторить запрос
закрыть соединение
показать ошибку
перейти в безопасное состояние
```

Конкретное поведение зависит от задачи.

---

# 22. Версия протокола

Если система развивается годами, формат сообщений может измениться.

Например, версия 1:

```json
{
  "speed": 100
}
```

А версия 2:

```json
{
  "speed": 100,
  "unit": "rpm"
}
```

Если старые и новые программы работают одновременно, нужно понимать, какой формат они поддерживают.

Поэтому в собственных протоколах полезно предусматривать:

```text
version
```

Например:

```text
VERSION=2
```

или:

```json
{
  "version": 2,
  "speed": 100
}
```

# 23. Главный алгоритм выбора

При проектировании можно использовать такую последовательность:

```text
1. Что передаём?
        ↓
2. Между какими устройствами?
        ↓
3. Какое расстояние?
        ↓
4. Какая физическая среда?
        ↓
5. Нужна ли сеть?
        ↓
6. Нужен ли TCP/UDP?
        ↓
7. Один получатель или много?
        ↓
8. Нужна ли модель данных?
        ↓
9. Насколько критична доставка?
        ↓
10. Выбираем протокол
```

Это гораздо полезнее, чем запоминать:

> Modbus для этого, MQTT для того.

# 24. Финальный пример

Рассмотрим небольшую систему:

```text
              ┌───────────────┐
              │   Dashboard   │
              └───────▲───────┘
                      │
                      │ MQTT
                      │
              ┌───────┴───────┐
              │    Broker     │
              └───────▲───────┘
                      │
                   Ethernet
                      │
              ┌───────┴───────┐
              │  Controller   │
              └───────▲───────┘
                      │
                     CAN
                      │
             ┌────────┴────────┐
             │                 │
          Sensor             Motor
```

Здесь одновременно используются разные технологии.

```text
CAN
```

связывает устройства внутри локальной системы.

```text
Ethernet
```

соединяет контроллер с сетевой инфраструктурой.

```text
MQTT
```

передаёт телеметрию через брокер.

Каждый уровень решает свою задачу.

# 25. Что нужно запомнить из всего модуля

Мы начали с самого простого:

```text
Что такое протокол?
```

И постепенно пришли к полноценной системе:

```text
Физический сигнал
       ↓
Интерфейс
       ↓
Кадр
       ↓
Адрес
       ↓
Протокол
       ↓
Транспорт
       ↓
Приложение
```

Теперь можно представить реальные цепочки.

Например:

```text
Modbus RTU
    ↓
RS-485
```

или:

```text
Modbus TCP
    ↓
TCP
    ↓
IP
    ↓
Ethernet
```

или:

```text
OPC UA
    ↓
TCP
    ↓
IP
    ↓
Ethernet
```

или:

```text
MQTT
    ↓
TCP
    ↓
IP
    ↓
Wi-Fi / Ethernet
```

# Практика

Нужно соединить:

```text
MCU A

```

```text
1 метр
```

```text

STOP
STATUS
```

## Задание 2. Общая шина

Есть:

```text

```

Выберите подходящую технологию и объясните свой выбор.

```text

```

```text

ошибки
```

```text
сервер
dashboard
```

Предложите архитектуру.

```text
        ↓
```


# Итог модуля

Теперь у вас есть базовое представление о том, как устройства обмениваются информацией.

Вы знаете:

* что такое протокол;
* чем сигнал отличается от протокола;
* как устроено сообщение;
* зачем нужна адресация;
* как обнаруживаются ошибки;
* как работает последовательная связь;
* что такое RS-232 и RS-485;
* как устроен Modbus;
* как работает CAN;
* что такое Ethernet;
* чем TCP отличается от UDP;
* как работает OPC UA;
* зачем нужен MQTT;
* как выбирать технологию под конкретную задачу.

Самая важная мысль всего модуля:

> **Протокол выбирают не по популярности, а по требованиям системы.**

Хорошая архитектура не обязательно использует самый сложный протокол. Она использует подходящий протокол на каждом уровне.

```text
Задача
  ↓
Требования
  ↓
Архитектура
  ↓
Физическая связь
  ↓
Транспорт
  ↓
Протокол
  ↓
Приложение
```

На этом базовый модуль «Протоколы» завершён. Дальше эти знания можно применять уже внутри более крупных систем: микроконтроллеров, сетевых приложений, робототехники и распределённых систем.
