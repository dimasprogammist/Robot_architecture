# CAN Bus

## Цель

После этого урока вы должны понимать:

* зачем был создан CAN;
* чем CAN отличается от обычной схемы клиент/сервер;
* что такое общая шина;
* что такое идентификатор CAN-сообщения;
* как устройства конкурируют за право передачи;
* что такое arbitration;
* почему меньший идентификатор может иметь больший приоритет;
* где CAN применяется в автомобилях и робототехнике.

---

## Зачем нужен CAN

Представим автомобиль.

В нём есть множество электронных блоков:

```text
Engine ECU
Dashboard
ABS
Airbag
Transmission
Sensors
```

Если соединить каждую пару устройств отдельным кабелем, получится огромное количество проводов.

Можно сделать иначе:

```text
             CAN BUS
────────────────────────────────
   │          │         │       │
  ECU        ABS     Dashboard Sensor
```

Все устройства подключаются к общей шине.

Они могут обмениваться сообщениями через неё.

---

## CAN — это не обычная клиент/серверная сеть

В классической модели:

```text
Client → Server
```

клиент отправляет запрос, сервер отвечает.

В CAN устройство может просто отправить сообщение в общую шину:

```text
Device A → CAN BUS
```

Другие устройства могут получить это сообщение.

Получатели определяют, интересно ли им оно.

Например:

```text
CAN message:
ID = 0x120
DATA = speed
```

Приборная панель может использовать его для отображения скорости.

Другой контроллер может использовать те же данные для своей логики.

---

## Сообщение вместо адресата

В CAN важна концепция:

> Сообщение имеет идентификатор, описывающий его смысл и приоритет.

Например:

```text
ID 0x100 → скорость автомобиля
ID 0x200 → температура двигателя
ID 0x300 → положение педали
```

Это отличается от подхода:

```text
сообщение → конкретному устройству
```

В CAN можно думать:

```text
сообщение → всем
```

а каждое устройство решает:

> Нужно ли мне это сообщение?

---

## CAN-шина

Упрощённо:

```text
──────────────────────── CAN BUS ────────────────────────
       │                 │                │
      ECU               ABS          Dashboard
```

Все узлы подключены к общей среде.

Поэтому возникает проблема:

> Что делать, если два устройства хотят передавать одновременно?

Например:

```text
ECU ── хочет передать
ABS ── хочет передать
```

Нужен механизм выбора.

---

## Arbitration

CAN использует механизм **arbitration**.

Его задача:

> определить, какое сообщение получает право передачи.

Каждому сообщению назначается идентификатор.

Например:

```text
0x100
0x200
0x300
```

В классическом CAN меньший числовой идентификатор соответствует более высокому приоритету.

Поэтому:

```text
0x100
```

имеет более высокий приоритет, чем:

```text
0x300
```

---

## Почему это удобно

Представим:

```text
Device A → ID 0x100
Device B → ID 0x300
```

Оба хотят передавать одновременно.

CAN позволяет определить победителя без обычного централизованного диспетчера.

Условно:

```text
A → 0x100
B → 0x300

результат:
A продолжает передачу
B ждёт
```

Устройство с более низким приоритетом может повторить передачу позже.

---

## Это не просто «кто первый»

Приоритет связан именно с идентификатором сообщения.

Это позволяет проектировать систему так, чтобы важные сообщения имели высокий приоритет.

Например:

```text
Emergency stop → высокий приоритет
Temperature    → средний
Diagnostics    → низкий
```

Конкретное назначение идентификаторов зависит от системы.

---

## Важность приоритета

Представим робота.

Есть сообщения:

```text
MOTOR_COMMAND
SENSOR_DATA
DEBUG_MESSAGE
```

Если одновременно возникает:

```text
аварийная команда
```

и:

```text
диагностическое сообщение
```

желательно, чтобы аварийное сообщение не ждало длинную очередь обычных данных.

CAN позволяет учитывать это через приоритет идентификаторов.

---

## CAN ID — это не обычный адрес устройства

Это очень важный момент.

В CAN ID обычно идентифицирует **сообщение**, а не конкретный физический узел.

Например:

```text
ID 0x120 → скорость двигателя
```

может отправляться одним устройством, а получать её могут несколько других.

То есть:

```text
ID
↓
смысл / идентификатор сообщения
```

а не:

```text
ID
↓
адрес конкретного устройства
```

---

## Кадр CAN

Упрощённо CAN-кадр можно представить так:

```text
┌───────┬──────┬──────────┬───────┐
│ ID    │ Ctrl │ Data     │ CRC   │
└───────┴──────┴──────────┴───────┘
```

В реальном CAN-кадре есть дополнительные поля и служебные биты.

Сейчас важно понимать основные идеи:

```text
идентификатор
↓
служебная информация
↓
данные
↓
контроль
```

---

## Размер данных

Классический CAN имеет небольшой размер полезной нагрузки кадра.

Это одна из причин, почему CAN хорошо подходит для коротких сообщений управления и состояния.

Например:

```text
ID = 0x120
DATA:
01 7A 00 00
```

Здесь может передаваться несколько параметров.

Если нужно передать большие объёмы информации, протоколы верхнего уровня могут разбивать данные на несколько CAN-кадров.

---

## CAN FD

Существует расширение:

**CAN FD**

Оно позволяет передавать больше данных в одном кадре и использовать более высокие скорости для части передачи.

Поэтому сегодня можно встретить:

```text
Classic CAN
CAN FD
```

Для базового понимания достаточно помнить:

> CAN FD расширяет возможности классического CAN.

---

## Ошибки

CAN уделяет большое внимание обнаружению ошибок.

В протоколе предусмотрены механизмы контроля передачи.

Упрощённо:

```text
отправка
  ↓
контроль
  ↓
обнаружение ошибки
```

При обнаружении определённых ошибок CAN может инициировать повторную передачу.

Это помогает сделать сеть устойчивой.

---

## CAN и CRC

CAN использует CRC внутри кадра для обнаружения ошибок.

Но CRC — только один из механизмов контроля.

CAN также имеет другие механизмы обнаружения ошибок.

Поэтому нельзя представлять CAN как:

```text
данные + CRC
```

и считать задачу полностью решённой.

---

## Error handling

CAN-узлы отслеживают ошибки в сети.

Если устройство постоянно обнаруживает проблемы, его состояние может изменяться.

Это позволяет системе не просто обнаруживать отдельную ошибку, но и учитывать состояние самого узла.

В реальных системах это помогает отделять:

```text
единичную ошибку
```

от:

```text
узла, который постоянно нарушает обмен
```

---

## CAN и физический уровень

CAN включает правила, связанные не только с форматом сообщения, но и с физическим обменом.

Типичная CAN-линия использует дифференциальную передачу:

```text
CAN_H
CAN_L
```

Устройства подключаются к общей шине.

Упрощённо:

```text
Node ───────── Node ───────── Node
```

На концах линии обычно используется терминация.

---

## CAN и RS-485

На первый взгляд они похожи:

```text
RS-485 → дифференциальная линия
CAN    → дифференциальная линия
```

Но это не означает, что они одинаковые.

RS-485 в первую очередь определяет физический способ передачи.

CAN включает значительно больше механизмов:

* формат кадров;
* идентификаторы;
* arbitration;
* контроль ошибок;
* правила доступа к шине.

Поэтому:

```text
RS-485 ≠ CAN
```

---

## CAN и Modbus

Эти протоколы тоже решают разные задачи.

Modbus часто использует модель:

```text
Client → Request → Server
Client ← Response ← Server
```

CAN ориентирован на обмен сообщениями в общей шине:

```text
Node → Message → Bus
```

Другие узлы могут принять сообщение.

Поэтому архитектуры отличаются.

---

## Пример в автомобиле

Представим:

```text
Датчик скорости
       │
       ↓
      CAN
       │
 ┌─────┼──────┐
 ↓     ↓      ↓
ABS   ECU   Dashboard
```

Датчик или контроллер публикует данные:

```text
ID = 0x120
Speed = 80
```

Другие блоки могут использовать эту информацию.

Например:

```text
Dashboard → показывает скорость
ECU       → использует скорость в управлении
ABS       → использует скорость колёс
```

Один источник может обслуживать несколько потребителей.

---

## CAN в робототехнике

CAN также удобно использовать в роботах.

Например:

```text
Главный контроллер
       │
      CAN
       │
 ┌─────┼─────┐
 ↓     ↓     ↓
Motor Motor Sensor
Driver Driver Module
```

Каждый модуль может публиковать свои сообщения.

Например:

```text
ID 0x101 → Motor 1 speed
ID 0x102 → Motor 2 speed
ID 0x201 → Motor 1 temperature
ID 0x202 → Motor 2 temperature
```

Контроллеру не обязательно постоянно спрашивать каждый модуль.

Модули могут сами публиковать состояние.

---

## Почему CAN хорошо подходит для распределённых систем

Представим архитектуру:

```text
             CAN
              │
     ┌────────┼────────┐
     ↓        ↓        ↓
 Motor 1    Motor 2   Sensors
```

Каждый модуль отвечает за свою задачу.

Это позволяет строить распределённые системы:

```text
один контроллер
        ↓
много специализированных узлов
```

Но все узлы используют общий канал обмена.

---

## Пример обмена

Пусть:

```text
ID = 0x120
DATA = 00 64
```

Документация системы говорит:

```text
0x120 → скорость двигателя
16-bit unsigned
масштаб 1 rpm
```

Тогда:

```text
0x0064 = 100
```

и сообщение означает:

```text
скорость = 100 rpm
```

Важно:

CAN сам не знает, что `0x120` означает скорость.

Это определено протоколом более высокого уровня или документацией конкретной системы.

---

## CANopen

Поверх CAN существуют протоколы более высокого уровня.

Один из известных вариантов:

**CANopen**

Он определяет дополнительные правила:

* структуру данных;
* идентификаторы;
* управление узлами;
* обмен параметрами;
* диагностику.

Получается:

```text
CANopen
   ↓
CAN
   ↓
физический сигнал
```

Это хороший пример того, что один протокол может работать поверх другого уровня.

---

## Главное

CAN удобно представить как:

```text
общая шина
    ↓
много устройств
    ↓
сообщения с ID
    ↓
arbitration
    ↓
передача
    ↓
контроль ошибок
```

Ключевая идея:

> В CAN важен не адрес получателя, а идентификатор сообщения и его приоритет.

Устройства получают сообщения из общей сети и решают, какие из них им нужны.
