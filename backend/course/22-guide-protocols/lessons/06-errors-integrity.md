# Ошибки передачи данных и контроль целостности

## Цель

После этого урока вы должны понимать:

* почему данные могут повреждаться при передаче;
* чем потеря данных отличается от повреждения данных;
* зачем нужны проверки целостности;
* как работают parity, checksum и CRC на базовом уровне;
* зачем нужны подтверждения и повторная передача;
* что такое таймаут;
* почему надёжность передачи — это не только проверка CRC.

---

## Данные не всегда доходят правильно

Представим простую систему:

```text
Компьютер ─────────────→ Микроконтроллер
```

Компьютер отправляет:

```text
10110100
```

Но между устройствами могут возникать проблемы:

* электрические помехи;
* плохой контакт;
* повреждённый кабель;
* перегрузка устройства;
* ошибка программы;
* потеря сетевого пакета;
* отключение питания.

В результате получатель может получить:

```text
10100100
```

Один бит изменился.

Проблема заключается в том, что получатель может даже не знать, что данные повреждены.

---

## Основные виды проблем

Условно проблемы передачи можно разделить на несколько типов.

### Повреждение

Сообщение дошло, но его содержимое изменилось.

```text
Отправлено:
10 20 30

Получено:
10 21 30
```

### Потеря

Сообщение вообще не дошло.

```text
A → MESSAGE → B

        X
      потеря
```

### Дублирование

Одно сообщение было обработано дважды.

```text
A → COMMAND → B
A → COMMAND → B
```

Например, команда:

```text
INCREASE_SPEED
```

может быть выполнена два раза.

### Изменение порядка

Сообщения могут прийти не в том порядке, в котором были отправлены.

```text
Отправлено:

1 → A
2 → B
3 → C

Получено:

2
1
3
```

Не каждый протокол допускает такую ситуацию, но при проектировании обмена порядок сообщений иногда приходится учитывать.

---

## Проверка целостности

Первый вопрос:

> Как понять, что сообщение изменилось?

Для этого отправитель добавляет дополнительную информацию, вычисленную на основе данных.

Например:

```text
DATA → алгоритм → CHECK
```

И отправляет:

```text
DATA + CHECK
```

Получатель снова вычисляет проверочное значение.

```text
полученные DATA
      ↓
   алгоритм
      ↓
  CHECK_NEW
```

После этого:

```text
CHECK_NEW == CHECK_RECEIVED
```

означает, что проверка пройдена.

Если:

```text
CHECK_NEW != CHECK_RECEIVED
```

данные считаются повреждёнными.

---

## Parity

Один из самых простых механизмов проверки — **бит чётности**, или parity bit.

Пусть данные:

```text
1011001
```

В зависимости от выбранного режима добавляется дополнительный бит.

Например, при чётной parity количество единиц должно быть чётным.

Если в данных уже четыре единицы:

```text
1011001
  ↑ ↑↑
```

то parity может быть:

```text
0
```

Если в данных нечётное количество единиц, parity будет другой.

---

## Что делает parity

Получатель получает:

```text
DATA + PARITY
```

и считает количество единиц.

Если правило нарушено:

```text
ошибка
```

Таким образом parity позволяет обнаруживать некоторые ошибки.

Но это очень простой механизм.

Он не способен надёжно обнаруживать все возможные повреждения.

---

## Пример

Пусть отправлено:

```text
1011001
```

и используется чётная parity.

Допустим, итоговое сообщение:

```text
10110010
```

Если один бит изменится:

```text
10100010
```

количество единиц изменится, и проверка может обнаружить ошибку.

Но если изменятся сразу два бита, parity в некоторых случаях может снова выглядеть корректной.

Поэтому parity не является полноценной защитой от ошибок.

---

## Checksum

Более универсальный подход — контрольная сумма.

Например, есть данные:

```text
10 20 30
```

Можно вычислить:

```text
10 + 20 + 30 = 60
```

и добавить:

```text
10 20 30 60
```

Получатель вычисляет сумму самостоятельно.

Если он получает:

```text
10 21 30 60
```

то:

```text
10 + 21 + 30 = 61
```

а переданная сумма:

```text
60
```

не совпадает.

Получатель обнаруживает проблему.

---

## Реальные checksum сложнее

Простая сумма — только учебный пример.

На практике контрольная сумма может учитывать:

* порядок байтов;
* переносы;
* размер результата;
* различные математические операции.

Например, значение может ограничиваться одним байтом:

```text
checksum = (a + b + c) & 0xFF
```

Тогда результат всегда находится в диапазоне:

```text
0...255
```

---

## CRC

Один из широко используемых методов проверки — **CRC**.

CRC расшифровывается как:

**Cyclic Redundancy Check**

Идея похожа на checksum:

```text
данные
  ↓
алгоритм CRC
  ↓
CRC
```

Отправитель добавляет CRC к сообщению.

Получатель вычисляет CRC заново.

```text
получено:
DATA + CRC

проверка:
CRC(DATA) == полученный CRC
```

Если значения отличаются, сообщение считается повреждённым.

---

## Почему CRC лучше простой суммы

CRC специально разработан для обнаружения большого количества типичных ошибок передачи.

Он хорошо обнаруживает многие виды:

* одиночных ошибок;
* групп изменённых битов;
* последовательных повреждений;
* ошибок в пакетах.

Конкретные свойства зависят от выбранного варианта CRC.

Например, существуют:

```text
CRC-8
CRC-16
CRC-32
```

Это не один единственный алгоритм.

Даже два алгоритма с одинаковым размером результата могут иметь разные параметры.

---

## CRC не шифрует данные

Это очень важное различие.

CRC отвечает на вопрос:

> Похоже ли сообщение на то, которое было отправлено?

CRC не отвечает на вопросы:

> Кто отправил сообщение?

или:

> Может ли посторонний прочитать данные?

Поэтому:

```text
CRC ≠ шифрование
```

и:

```text
CRC ≠ защита от злоумышленника
```

Это механизм обнаружения ошибок, а не механизм безопасности.

---

## Что делать после обнаружения ошибки

Представим:

```text
A → MESSAGE → B
```

B обнаружил:

```text
CRC ERROR
```

Теперь возможны разные варианты.

### Игнорировать сообщение

```text
получили
↓
ошибка
↓
отбросить
```

### Отправить сообщение об ошибке

```text
B → ERROR → A
```

### Попросить повторить

```text
B → RETRY → A
```

### Ничего не отправлять

A через некоторое время обнаружит:

```text
TIMEOUT
```

и сам повторит запрос.

---

## Подтверждение

Представим простой обмен:

```text
A → COMMAND → B
B → OK      → A
```

A получает подтверждение и понимает:

> B получил сообщение и обработал его.

Но это зависит от конкретного протокола.

Сам факт получения `OK` ещё не означает, что физическое действие точно завершилось.

Например:

```text
B → OK
```

может означать:

> Команда принята.

а не:

> Двигатель уже полностью остановился.

Это важное различие.

---

## ACK и NACK

В протоколах часто встречаются понятия:

**ACK** — подтверждение получения.

**NACK** — отрицательное подтверждение.

Например:

```text
A → MESSAGE
B → ACK
```

или:

```text
A → MESSAGE
B → NACK
```

NACK может означать:

> Сообщение получено, но обработать его нельзя.

Например, команда неизвестна или данные некорректны.

---

## Таймаут

А что делать, если B вообще не отвечает?

Например:

```text
A → COMMAND
```

и дальше ничего.

A должен иметь ограничение времени ожидания:

```text
TIMEOUT = 1 секунда
```

Через секунду:

```text
ответ не получен
```

система может решить, что обмен не удался.

---

## Повторная передача

Можно использовать:

```text
MAX_RETRIES = 3
```

Тогда:

```text
A → COMMAND
     ↓
   timeout
     ↓
A → COMMAND
     ↓
   timeout
     ↓
A → COMMAND
     ↓
   timeout
     ↓
ERROR
```

Такой механизм часто делает обмен значительно устойчивее.

---

## Но повтор может быть опасен

Рассмотрим команду:

```text
OPEN_VALVE
```

Компьютер отправляет:

```text
OPEN_VALVE
```

Клапан открывается.

Но подтверждение теряется:

```text
A → OPEN_VALVE → B
B → VALVE OPEN
      X
    потеря
```

A думает:

> ответа нет.

И повторяет:

```text
A → OPEN_VALVE → B
```

Что произойдёт?

Если команда просто устанавливает состояние:

```text
OPEN
```

повтор может быть безопасным.

Но если команда означает:

```text
INCREASE_SPEED
```

повтор может изменить состояние второй раз.

Поэтому протокол должен учитывать **повторную передачу команд**.

---

## Идемпотентность

Команда называется условно безопасной для повторения, если повторное выполнение не меняет результат неожиданным образом.

Например:

```text
SET_SPEED 1000
```

Первый раз:

```text
скорость = 1000
```

Второй раз:

```text
скорость = 1000
```

Результат тот же.

А:

```text
INCREASE_SPEED 100
```

при повторе:

```text
+100
+100
```

может дать неожиданный результат.

Поэтому при проектировании протокола нужно думать не только:

> Что делать при ошибке?

но и:

> Что произойдёт, если сообщение придёт дважды?

---

## Номер сообщения

Один из способов решить проблему повторов — добавить идентификатор сообщения.

Например:

```text
[ID][COMMAND][DATA]
```

Первый запрос:

```text
15 SET_SPEED 1000
```

Устройство выполняет его и запоминает:

```text
ID = 15
```

Если тот же запрос приходит снова:

```text
15 SET_SPEED 1000
```

устройство понимает:

> Это уже обработанный запрос.

И может повторно отправить ответ, но не выполнять действие второй раз.

---

## Надёжность — это несколько механизмов

Надёжный обмен обычно строится не на одном CRC.

Например:

```text
структура сообщения
       ↓
CRC
       ↓
ACK
       ↓
TIMEOUT
       ↓
RETRY
       ↓
ID сообщения
```

Каждый механизм решает свою проблему.

---

## Что делает каждый механизм

| Механизм | Задача |
|---|---|
| Start/Length | Определить границы сообщения |
| Parity | Обнаружить некоторые ошибки |
| Checksum | Проверить данные |
| CRC | Надёжнее обнаруживать повреждения |
| ACK | Подтвердить получение |
| NACK | Сообщить об ошибке |
| Timeout | Не ждать бесконечно |
| Retry | Повторить передачу |
| Message ID | Обрабатывать повторы |

---

## Пример полного обмена

Представим:

```text
Компьютер → Робот
```

Сообщение:

```text
[ID][CMD][DATA][CRC]
```

Обмен:

```text
Компьютер
    │
    │ COMMAND ID=10
    ↓
  Робот
    │
    │ проверка CRC
    │
    │ выполнение
    │
    │ ACK ID=10
    ↓
Компьютер
```

Если сообщение повреждено:

```text
Компьютер
    │
    │ COMMAND
    ↓
  Робот
    │
    │ CRC ERROR
    ↓
Компьютер
```

Если ответ потерялся:

```text
Компьютер → COMMAND ID=10
Робот      → ACK ID=10
                 X
               потеря

Компьютер
    ↓
timeout
    ↓
повтор COMMAND ID=10
```

Робот видит:

```text
ID=10
```

и понимает, что команда уже была обработана.

---

## Что делать, если ошибки слишком частые

Если система постоянно получает:

```text
CRC ERROR
CRC ERROR
CRC ERROR
```

не стоит просто бесконечно повторять сообщения.

Нужно искать причину.

Возможны:

* плохой кабель;
* электрические помехи;
* неправильная скорость;
* неправильные настройки;
* слишком большая длина линии;
* проблемы с питанием;
* ошибка в программном обеспечении.

Протокол может обнаружить проблему, но не всегда способен её исправить.

---

## Главное

Надёжный обмен — это цепочка механизмов:

```text
Передача
   ↓
Проверка целостности
   ↓
Подтверждение
   ↓
Таймаут
   ↓
Повтор
   ↓
Контроль повторов
```

При этом важно различать:

```text
CRC
```

и:

```text
ACK
```

CRC отвечает:

> Данные выглядят неповреждёнными?

ACK отвечает:

> Получатель подтвердил получение/обработку?

Это разные задачи.
