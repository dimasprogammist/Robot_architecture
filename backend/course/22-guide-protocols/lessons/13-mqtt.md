# MQTT и обмен через брокер

## Цель

До этого мы часто использовали модель:

```text
Клиент → Сервер
```

MQTT предлагает другой подход:

```text
Publisher → Broker ← Subscriber
```

После урока вы должны понимать:

* что такое MQTT;
* зачем нужен брокер;
* кто такие Publisher и Subscriber;
* что такое Topic;
* как устройство публикует данные;
* как клиент подписывается на данные;
* что такое QoS;
* зачем нужны retained messages;
* где MQTT полезен в IoT и робототехнике.

---

# 1. Проблема прямых соединений

Представим несколько устройств:

```text
Sensor 1
Sensor 2
Sensor 3
Robot
Server
Dashboard
```

Если каждый участник должен напрямую обмениваться данными с каждым:

```text
Sensor 1 ───── Server
Sensor 1 ───── Dashboard
Sensor 2 ───── Server
Sensor 2 ───── Dashboard
Robot ───────── Server
Robot ───────── Dashboard
...
```

количество соединений начинает расти.

Можно сделать архитектуру проще:

```text
              ┌─────────────┐
Sensor 1 ────►│             │
Sensor 2 ────►│   Broker    │◄──── Dashboard
Robot ───────►│             │◄──── Server
              └─────────────┘
```

Устройства публикуют сообщения в брокер.

Получатели подписываются на интересующие их сообщения.

---

# 2. Что такое MQTT

MQTT — лёгкий протокол обмена сообщениями по модели **publish/subscribe**.

Основные элементы:

```text
Publisher
Subscriber
Broker
Topic
Message
```

Например:

```text
Temperature Sensor
       │
       │ publish
       ▼
    Broker
       │
       │ subscribe
       ▼
 Monitoring App
```

---

# 3. Broker

Broker — центральный узел, который принимает сообщения и распределяет их подписчикам.

Например:

```text
             ┌───────────────┐
             │    Broker     │
             └───────┬───────┘
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
     Sensor        Robot       Server
```

В реальной системе брокер может обслуживать большое количество клиентов.

Важно:

> Publisher и Subscriber не обязаны знать адреса друг друга.

Они знают адрес брокера.

---

# 4. Publisher

Publisher — клиент, который публикует сообщение.

Например, датчик измерил:

```text
24.7 °C
```

и публикует:

```text
Topic:
sensors/temperature

Payload:
24.7
```

Схема:

```text
Sensor
  │
  │ publish
  │
  │ sensors/temperature
  │ 24.7
  ▼
Broker
```

---

# 5. Subscriber

Subscriber подписывается на Topic.

Например:

```text
Monitoring App
       │
       │ subscribe
       ▼
sensors/temperature
```

Когда кто-то публикует:

```text
sensors/temperature = 24.7
```

брокер передаёт сообщение подписчику.

---

# 6. Topic

Topic — это адрес или имя потока сообщений.

Например:

```text
sensors/temperature
```

или:

```text
robot/position
robot/speed
robot/state
```

Можно построить целую структуру:

```text
robot/
├── position
├── speed
├── state
├── battery
└── errors
```

Например:

```text
robot/position
```

может содержать:

```json
{
  "x": 120.5,
  "y": 80.2,
  "z": 35.0
}
```

---

# 7. Publisher и Subscriber не обязаны знать друг друга

Это одна из главных идей MQTT.

Представим:

```text
                    Broker
                  /        \
                 /          \
          Publisher       Subscriber
```

Publisher знает:

```text
broker.example
```

Subscriber тоже знает:

```text
broker.example
```

Но Publisher не обязан знать, кто получает его сообщения.

Это позволяет легко добавлять новых потребителей.

Например:

```text
Sensor
   │
   ▼
Broker
 ┌─┼─────────┐
 ▼ ▼         ▼
PC Web   Database
```

Датчик ничего не знает о компьютере, веб-интерфейсе и базе данных.

---

# 8. Несколько подписчиков

Допустим, устройство публикует:

```text
robot/speed
```

На этот Topic подписались:

```text
Dashboard
Logger
Analytics
```

Тогда брокер отправит сообщение всем подходящим подписчикам.

```text
                 Broker
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
    Dashboard    Logger    Analytics
```

Один источник данных может обслуживать множество приложений.

---

# 9. Payload

MQTT передаёт сообщение, состоящее из Topic и полезной нагрузки.

Например:

```text
Topic:
robot/speed

Payload:
120
```

Payload может быть текстом:

```text
120
```

JSON:

```json
{
  "speed": 120,
  "unit": "rpm"
}
```

или бинарными данными.

MQTT не требует, чтобы payload обязательно был JSON.

Формат данных определяет приложение.

---

# 10. QoS

MQTT имеет несколько уровней качества доставки — QoS.

### QoS 0

Сообщение отправляется без гарантии повторной доставки.

```text
Publisher
   │
   │ message
   ▼
Broker
```

Подходит для данных, которые регулярно обновляются.

Например:

```text
temperature = 24.7
```

Если одно значение потерялось, через секунду придёт новое.

---

### QoS 1

MQTT предусматривает подтверждение доставки и может повторить сообщение.

Это увеличивает надёжность, но сообщение потенциально может быть обработано более одного раза.

Поэтому приложение должно учитывать возможные дубликаты.

---

### QoS 2

Предназначен для наиболее строгой семантики доставки MQTT.

Обмен становится сложнее и требует больше служебных сообщений.

---

# 11. Retained message

Представим, что устройство опубликовало:

```text
robot/state = READY
```

После этого подключился новый клиент.

Без дополнительного механизма новый клиент мог бы не знать текущее состояние, пока робот снова что-нибудь не опубликует.

MQTT поддерживает retained messages.

Брокер может сохранить последнее сообщение Topic.

Тогда новый Subscriber получает последнее сохранённое значение при подписке.

Например:

```text
Broker:

robot/state
    ↓
READY
```

Подключается новый клиент:

```text
Subscriber
    │
    │ subscribe robot/state
    ▼
Broker
    │
    │ READY
    ▼
Subscriber
```

---

# 12. Wildcard Topics

MQTT позволяет подписываться не только на один Topic.

Например:

```text
robot/#
```

может означать все дочерние Topics:

```text
robot/state
robot/speed
robot/battery
robot/position
```

Другой вариант:

```text
robot/+/speed
```

может соответствовать:

```text
robot/1/speed
robot/2/speed
robot/3/speed
```

Это удобно, когда устройств много.

---

# 13. Пример системы

Представим небольшую роботизированную систему:

```text
Robot 1
Robot 2
Robot 3
   │
   │ MQTT
   ▼
┌──────────────┐
│    Broker    │
└──────┬───────┘
       │
   ┌───┼───────────┐
   ▼   ▼           ▼
Dashboard Logger  Analytics
```

Роботы публикуют:

```text
robots/1/state
robots/1/position
robots/1/battery

robots/2/state
robots/2/position
robots/2/battery
```

Приложение мониторинга подписывается:

```text
robots/#
```

и получает информацию обо всех роботах.

---

# 14. MQTT и TCP

MQTT не является альтернативой TCP в том же смысле, что TCP и UDP.

Типичная схема:

```text
MQTT
  ↓
TCP
  ↓
IP
  ↓
Ethernet / Wi-Fi
```

То есть MQTT определяет модель обмена сообщениями, а TCP может обеспечивать транспорт.

---

# 15. MQTT и HTTP

Можно сравнить две модели.

HTTP:

```text
Client
  │
  │ request
  ▼
Server
  │
  │ response
  ▼
Client
```

MQTT:

```text
Publisher
    │
    ▼
 Broker
    │
    ├────► Subscriber 1
    ├────► Subscriber 2
    └────► Subscriber 3
```

HTTP хорошо подходит для:

* запросов;
* веб-приложений;
* REST API;
* загрузки ресурсов.

MQTT особенно удобен для:

* телеметрии;
* IoT;
* событий;
* большого количества устройств;
* передачи небольших сообщений.

---

# 16. MQTT в микроконтроллерах

Представим микроконтроллер с датчиком температуры.

Каждые пять секунд:

```text
прочитать датчик
      ↓
получить 24.7
      ↓
publish
      ↓
sensors/temperature
```

Сервер мониторинга подписан на:

```text
sensors/temperature
```

Получив значение:

```text
24.7
```

он может:

```text
записать его в БД
показать график
проверить аварийное условие
передать в аналитическую систему
```

При этом микроконтроллер не должен знать, что именно делает сервер.

---

# 17. MQTT и команды

MQTT можно использовать не только для телеметрии.

Например:

```text
robot/1/command
```

может принимать:

```json
{
  "command": "move",
  "speed": 100
}
```

А робот публикует состояние:

```text
robot/1/state
```

Например:

```json
{
  "state": "moving",
  "speed": 100
}
```

Получается двусторонний обмен:

```text
              Broker
             /      \
            /        \
      Commands       State
          ↓            ↑
        Robot ─────────┘
```

---

# 18. Где MQTT не всегда подходит

MQTT не является универсальным протоколом.

Если приложению нужно:

```text
запросить конкретный ресурс
получить сложный ответ
```

HTTP может быть естественнее.

Если требуется:

```text
структурированная модель устройств
метаданные
типы
подписки на значения
```

может подойти OPC UA.

Если требуется:

```text
очень простой обмен по локальной линии
```

может быть достаточно UART, CAN или другого протокола.

Выбор определяется задачей.

---

# 19. Пример на Python

Для работы с MQTT в Python существуют различные библиотеки.

Концептуально код выглядит так:

```python
import paho.mqtt.client as mqtt

client = mqtt.Client()

client.connect("localhost", 1883)

client.publish(
    "robot/1/state",
    "READY"
)

client.disconnect()
```

Subscriber может подписаться:

```python
client.subscribe("robot/1/state")
```

и обрабатывать входящие сообщения.

Конкретная библиотека и версия API могут отличаться, но архитектура остаётся той же:

```text
connect
subscribe / publish
receive
disconnect
```

---

# 20. Главное

MQTT строится вокруг идеи:

```text
Publisher
    ↓
  Broker
    ↓
Subscriber
```

А не:

```text
Device A
    ↓
Device B
```

Основные понятия:

```text
Broker
Publisher
Subscriber
Topic
Payload
QoS
Retained message
```

Если понять эти элементы, большая часть базовой архитектуры MQTT становится понятной.

## Итог

MQTT позволяет строить слабосвязанные системы обмена сообщениями.

Главная идея:

```text
Источник данных
      ↓
   Topic
      ↓
   Broker
      ↓
┌─────┼──────┐
▼     ▼      ▼
PC   DB   Dashboard
```

Это особенно полезно для IoT, распределённых устройств и телеметрии.

В последнем уроке модуля соберём всё изученное вместе и разберём, как выбирать протокол под конкретную задачу.
