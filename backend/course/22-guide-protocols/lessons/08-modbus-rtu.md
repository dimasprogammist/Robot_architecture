# Modbus как пример готового протокола

## Цель

После этого урока вы должны понимать:

* зачем существуют готовые протоколы;
* какую задачу решает Modbus;
* как устроена модель клиент/сервер в современном представлении Modbus;
* что такое адрес устройства;
* что такое function code;
* что такое coils и registers;
* как выглядит запрос и ответ;
* чем Modbus RTU отличается от Modbus TCP.

---

## Зачем нужен готовый протокол

Представим, что нужно соединить:

```text
Компьютер
   ↕
Датчик
```

Можно разработать собственный протокол:

```text
01 05 10 20 CRC
```

и написать программу, которая его понимает.

Но если таких устройств много, возникает проблема.

Каждый производитель может придумать свой формат:

```text
Device A → свой протокол
Device B → другой протокол
Device C → ещё один протокол
```

Тогда для каждого устройства потребуется отдельная логика.

Гораздо удобнее иметь общий протокол, который знают разные устройства.

Одним из таких протоколов является **Modbus**.

---

## Что такое Modbus

Modbus — прикладной протокол обмена данными между устройствами.

Он появился давно и получил широкое распространение благодаря простой модели обмена.

Упрощённо:

```text
клиент → запрос → сервер
клиент ← ответ  ← сервер
```

Например:

```text
Компьютер → прочитать температуру
Датчик    → 24.5
```

Modbus сам по себе не определяет физический кабель.

Он может работать, например, поверх:

```text
RS-485
```

или:

```text
TCP/IP
```

---

## Modbus RTU

Один из распространённых вариантов — **Modbus RTU**.

Типичная схема:

```text
Controller
    │
    │ RS-485
    │
    ├── Device 1
    ├── Device 2
    └── Device 3
```

На физическом уровне используется последовательная связь.

На уровне протокола используется Modbus RTU.

Получается:

```text
Modbus RTU
    ↓
RS-485
    ↓
электрический сигнал
```

---

## Модель клиент/сервер

В старой документации Modbus часто встречаются термины:

```text
Master
Slave
```

В современном описании чаще используются:

```text
Client
Server
```

Идея:

```text
Client → Request → Server
Client ← Response ← Server
```

Клиент инициирует запрос.

Сервер отвечает.

Например:

```text
PLC → прочитать значение
Sensor → вернуть значение
```

---

## Адрес устройства

Если несколько устройств подключены к одной линии, им нужны адреса.

Например:

```text
Sensor 1 → address 1
Sensor 2 → address 2
Sensor 3 → address 3
```

Клиент отправляет запрос:

```text
01 ...
```

если обращается к устройству №1.

Или:

```text
03 ...
```

для устройства №3.

---

## Структура Modbus RTU-сообщения

Упрощённо кадр выглядит так:

```text
┌─────────┬──────────────┬──────────────┬─────────┐
│ Address │ Function     │ Data         │ CRC     │
└─────────┴──────────────┴──────────────┴─────────┘
```

То есть:

```text
адрес устройства
      ↓
код функции
      ↓
данные
      ↓
CRC
```

Это хорошо показывает идеи, которые мы изучали раньше.

---

## Function code

Function code сообщает серверу, какую операцию нужно выполнить.

Например:

```text
01
02
03
04
05
06
15
16
```

Каждый код соответствует определённому типу операции.

Например, среди стандартных функций есть чтение:

* coils;
* discrete inputs;
* holding registers;
* input registers.

И операции записи.

---

## Coils

**Coil** — дискретное значение, которое обычно представляется как:

```text
0
```

или:

```text
1
```

Например:

```text
Motor enabled = 1
Valve open = 0
Lamp = 1
```

То есть coil удобно использовать для логических состояний.

---

## Discrete inputs

Это также дискретные значения:

```text
0
1
```

Но они предназначены для чтения входных состояний.

Например:

```text
Limit switch = 1
Door sensor = 0
Emergency input = 1
```

Упрощённо можно думать:

```text
Coil
↓
дискретное значение, с которым можно выполнять предусмотренные протоколом операции записи/чтения

Discrete input
↓
дискретное значение для чтения
```

---

## Registers

Для числовых значений используются регистры.

Например:

```text
Temperature = 245
Speed = 1500
Pressure = 320
```

Один регистр Modbus обычно содержит:

```text
16 бит
```

То есть:

```text
2 байта
```

Но само физическое значение может требовать несколько регистров.

Например, 32-битное число:

```text
Register 100
Register 101
```

---

## Holding registers

Holding registers — один из наиболее часто используемых типов.

Они представляют собой 16-битные регистры, доступные для предусмотренных протоколом операций чтения и записи.

Например:

```text
Register 100 → speed
Register 101 → pressure
Register 102 → temperature
```

Точное назначение зависит от конкретного устройства.

---

## Input registers

Input registers используются для хранения значений, которые предоставляются устройством для чтения.

Например:

```text
Register 300 → temperature
Register 301 → pressure
```

Главное сейчас — понимать концепцию:

```text
coils → логические значения
registers → 16-битные числовые значения
```

---

## Почему Modbus не знает, что такое температура

Это очень важный момент.

Если устройство говорит:

```text
Register 100 = 245
```

Modbus знает только:

> В регистре находится число.

Но Modbus не знает:

> Это температура 24.5 °C.

Эту информацию предоставляет документация конкретного устройства.

Например, производитель может написать:

```text
Register 100
Temperature
Scale: 0.1 °C
```

Тогда программа выполняет:

```text
245 × 0.1 = 24.5 °C
```

---

## Запрос на чтение

Упрощённо клиент говорит:

```text
Устройство №2,
прочитай 3 регистра начиная с 100.
```

В структурированном виде:

```text
Address = 2
Function = READ
Start = 100
Count = 3
```

Сервер отвечает:

```text
Register 100 → 245
Register 101 → 1500
Register 102 → 50
```

---

## Запрос и ответ

Полный обмен можно представить:

```text
Client
  │
  │ READ REGISTERS
  ↓
Server
  │
  │ 245, 1500, 50
  ↓
Client
```

Если используется RTU, в реальном кадре будут дополнительные байты:

```text
Address
Function
Data
CRC
```

---

## CRC в Modbus RTU

Modbus RTU использует CRC для проверки целостности кадра.

Получатель проверяет:

```text
CRC received
```

и сравнивает его с вычисленным значением.

Если проверка не проходит:

```text
кадр ошибочный
```

и он не должен обрабатываться как корректный запрос.

Это пример механизма, который мы разбирали в предыдущем уроке.

---

## Временные интервалы

Modbus RTU работает через последовательную передачу, поэтому важны временные параметры.

Получатель должен понимать:

> Где заканчивается один кадр и начинается другой?

В RTU границы кадров определяются в том числе временными интервалами между передачами.

Это одна из причин, почему нельзя просто передавать Modbus RTU как произвольный поток байтов без соблюдения правил.

---

## Modbus RTU и RS-485

Их часто называют вместе:

```text
Modbus RTU по RS-485
```

Но это не одно и то же.

Правильнее представлять:

```text
Modbus RTU
     ↓
протокол обмена

RS-485
     ↓
физический интерфейс

кабель
     ↓
физическая передача
```

Можно сказать:

> Modbus RTU работает поверх последовательного физического соединения, часто реализованного через RS-485.

---

## Что происходит при ошибке

Допустим:

```text
Client → Request
```

Но запрос повреждён.

Сервер проверяет CRC:

```text
CRC ERROR
```

Кадр не проходит проверку.

Дальнейшее поведение зависит от конкретной ситуации и реализации, но клиент может:

```text
не получить корректный ответ
      ↓
timeout
      ↓
повторить запрос
```

---

## Почему Modbus удобен для обучения

Modbus хорошо показывает архитектуру протоколов.

В нём можно увидеть:

```text
адрес
  ↓
команда
  ↓
данные
  ↓
CRC
```

То есть почти все основные понятия предыдущих уроков:

* адресация;
* запрос/ответ;
* формат сообщения;
* регистры;
* контроль целостности;
* таймауты;
* последовательная передача.

---

## Modbus TCP

Modbus существует не только в RTU-варианте.

Есть также:

**Modbus TCP**

Он работает поверх:

```text
Ethernet
TCP/IP
```

Упрощённая схема:

```text
Modbus
  ↓
TCP
  ↓
IP
  ↓
Ethernet
```

В отличие от RTU, здесь не используется RS-485 как физический канал.

---

## Главное различие

Modbus RTU:

```text
Modbus
  ↓
RTU
  ↓
последовательная связь
  ↓
часто RS-485
```

Modbus TCP:

```text
Modbus
  ↓
TCP
  ↓
IP
  ↓
Ethernet
```

При этом смысл команд Modbus остаётся похожим.

---

## Что такое порт 502

Modbus TCP обычно использует TCP-порт:

```text
502
```

Поэтому соединение может выглядеть:

```text
192.168.1.20:502
```

Здесь:

```text
192.168.1.20
```

— адрес устройства,

```text
502
```

— TCP-порт сервиса Modbus.

---

## Важное замечание о нумерации регистров

В документации устройств можно встретить записи вроде:

```text
40001
40002
40003
```

Это исторически распространённый способ обозначения областей данных Modbus.

Но номер, который указан в документации, и фактическое поле адреса в запросе не всегда совпадают напрямую.

Например, устройство может писать:

```text
40001
```

а библиотека ожидает:

```text
0
```

или:

```text
1
```

в зависимости от используемого API.

Поэтому при работе с Modbus всегда нужно смотреть документацию конкретного устройства и библиотеки.

---

## Modbus — это не база данных

Иногда регистры воспринимают как обычную память:

```text
Register 100
Register 101
Register 102
```

Но это не полноценная база данных.

Это просто адресуемые области данных, определённые конкретным устройством.

Например:

```text
100 → температура
101 → давление
102 → скорость
```

Как именно интерпретировать эти значения, решает производитель устройства.

---

## Практический пример

Представим контроллер:

```text
Controller
    │
    │ RS-485
    │
    ├── Sensor 1
    ├── Sensor 2
    └── Sensor 3
```

Адреса:

```text
Sensor 1 → 1
Sensor 2 → 2
Sensor 3 → 3
```

У каждого:

```text
Register 100 → temperature × 10
```

Контроллер отправляет:

```text
Device = 2
Function = read holding registers
Start = 100
Count = 1
```

Sensor 2 отвечает:

```text
245
```

Контроллер знает из документации:

```text
Temperature = register / 10
```

Получаем:

```text
245 / 10 = 24.5 °C
```

---

## Главное

Modbus — хороший пример готового прикладного протокола.

Его можно представить так:

```text
               Modbus
                  │
          ┌───────┴───────┐
          ↓               ↓
      Modbus RTU      Modbus TCP
          ↓               ↓
     RS-485/Serial       TCP
                          ↓
                         IP
                          ↓
                      Ethernet
```

В Modbus важно понимать:

```text
адрес
↓
function code
↓
данные
↓
CRC для RTU
```

А также различать:

```text
Coils
Discrete Inputs
Holding Registers
Input Registers
```
