# Зачем Docker

## Цель

Понять, какую проблему решают контейнеры: одинаковое окружение на любом хосте, изоляция процессов и предсказуемый запуск приложения без «у меня на машине работает».

## Что уже нужно понимать

- Процесс в ОС — это программа, загруженная в память и выполняющаяся с собственным адресным пространством.
- Файловая система, переменные окружения и сетевые порты принадлежат процессу через ядро ОС.
- Backend, frontend и база данных — разные процессы, которым нужны свои зависимости и настройки.
- Версии библиотек и системных пакетов на разных машинах часто не совпадают.

## Объяснение

Классическая боль разработки: код запускается у автора, но падает на сервере или у коллеги. Причины обычно не в алгоритме, а в окружении: другая версия Python, другой PostgreSQL, другой набор системных библиотек, другой путь к конфигу.

Docker упаковывает приложение вместе с его окружением в единицу доставки — образ. Из образа запускается контейнер: это обычный процесс на хосте, но с изолированным взглядом на файловую систему, сеть и часть ресурсов. Изоляция строится на механизмах ядра Linux: namespaces отделяют «видимость» (PID, сеть, mount), cgroups ограничивают CPU и память.

Важно: контейнер — не виртуальная машина. Внутри нет отдельного ядра ОС. Ядро одно — хостовое. Контейнер получает изолированные пространства имён, но системные вызовы идут в то же ядро. Поэтому контейнеры лёгкие: старт за секунды, десятки контейнеров на одной машине без гипервизора.

Зачем это в практике:

1. **Воспроизводимость.** Один и тот же образ на ноутбуке, CI и продакшене даёт одинаковые файлы и зависимости.
2. **Изоляция.** Зависимости сервиса A не ломают сервис B: у каждого свой корневой каталог и свой набор пакетов.
3. **Упаковка.** «Доставить приложение» = отдать образ или compose-файл, а не инструкцию из двадцати шагов установки.
4. **Масштаб мышления.** Локально поднимаете стек (API + БД + фронт) теми же примитивами, что и в облаке.

Docker не заменяет понимание ОС и сетей. Он снимает рутину «поставить всё вручную» и фиксирует срез окружения. Если в Dockerfile написана устаревшая библиотека — она будет устаревшей везде. Контейнер усиливает дисциплину: окружение становится частью кода (Dockerfile), а не устной традиции команды.

Ещё один смысл Docker — единый контракт запуска. Вместо «установи Node 20, потом Postgres 16, потом скопируй .env» вы говорите: `docker compose up`. Состояние «что должно быть запущено» описано декларативно. Это снижает порог входа для новых людей в проекте и уменьшает расхождение между стендами.

Контейнеры также помогают разделять роли: разработчик пишет код и Dockerfile, инфраструктура крутит одни и те же образы на разных окружениях. Образ — артефакт сборки, как jar или wheel, только с файловой системой целиком.

## Термины

| Термин | Смысл |
|--------|--------|
| Образ (image) | Неизменяемый шаблон файловой системы и метаданных для запуска |
| Контейнер (container) | Запущенный процесс, созданный из образа |
| Namespace | Изоляция видимости ресурсов процесса в ядре Linux |
| Host | Машина (или ВМ), на которой крутится Docker Engine |
| Runtime | Движок, который создаёт контейнеры из образов |
| Dockerfile | Текстовый рецепт сборки образа |
| Реестр (registry) | Хранилище образов (Docker Hub и аналоги) |

## Как это устроено

На хосте работает Docker Engine (демон). Клиент (`docker`) шлёт ему команды: собрать образ, запустить контейнер, создать сеть.

Когда вы запускаете контейнер:

1. Демон берёт слои образа и собирает корневую файловую систему контейнера (union mount).
2. Создаёт namespaces: отдельное дерево процессов, отдельный сетевой стек (часто через bridge), отдельный mount namespace.
3. Применяет лимиты cgroups при необходимости.
4. Стартует процесс с указанной командой (`CMD` / `ENTRYPOINT` / аргумент `docker run`).

С точки зрения хоста это процесс с PID на хосте. С точки зрения внутри контейнера — часто PID 1. Сеть по умолчанию идёт через виртуальный мост: контейнер получает свой IP в внутренней сети Docker.

На Windows и macOS Docker обычно работает через Linux-ВМ: контейнеры всё равно Linux-процессы внутри этой ВМ. Для учебного курса достаточно помнить: изоляция — про Linux namespaces, а не про «ещё одну Windows внутри».

Связка «образ → контейнер» похожа на «класс → объект», но точнее: образ — снимок ФС, контейнер — живой процесс с writable-слоем поверх снимка. Остановка контейнера не уничтожает образ. Удаление контейнера уничтожает его writable-слой, если данные не вынесены в том.

## Пример

Минимальный Dockerfile для статического «hello» на nginx:

```dockerfile
FROM nginx:1.27-alpine
COPY index.html /usr/share/nginx/html/index.html
EXPOSE 80
```

Запуск без compose:

```bash
docker build -t hello-web .
docker run --rm -p 8080:80 hello-web
```

Браузер открывает `http://localhost:8080`. Порт 8080 на хосте проброшен на порт 80 внутри контейнера. Образ `hello-web` можно перенести на другой хост с Docker — страница откроется так же, если `index.html` был в контексте сборки.

## Разбор

- `FROM` задаёт базовый образ: уже есть nginx и минимальная ОС (alpine).
- `COPY` кладёт ваш файл в файловую систему образа — это новый слой.
- `docker build` собирает образ локально; тег `-t` даёт человекочитаемое имя.
- `docker run` создаёт контейнер и стартует процесс nginx.
- `-p 8080:80` — проброс порта: без него сервис слушает только внутри сети Docker.
- `--rm` удаляет контейнер после остановки — удобно для одноразовых прогонов.

Проблема «разные окружения» здесь снята частично: nginx и layout файлов одинаковы везде. Контент страницы — ваш; версия nginx — зафиксирована тегом образа.

## Практическое применение

- Локальная разработка полного стека без установки Postgres/Redis в систему.
- CI: собрать образ, прогнать тесты внутри контейнера с теми же зависимостями, что в проде.
- Выкат: в реестр пушится образ с конкретным digest/тегом; на сервере тянут именно его.
- Демо и онбординг: новый разработчик клонирует репозиторий и поднимает стек одной командой compose.

Типичный путь внедрения: сначала контейнеризуют БД для локалки, потом API, потом фронт; затем собирают compose. Не обязательно начинать с продакшена — ценность появляется уже на ноутбуке.

## Типичные ошибки

- Путать контейнер с ВМ и ждать «полноценную ОС» с systemd и постоянным диском без томов.
- Ставить всё на хост «для скорости» и держать Docker только для прода — расхождение окружений возвращается.
- Тащить в образ секреты и `.env` с продакшен-паролями.
- Считать, что Docker « Magически» чинит баги кода — он фиксирует окружение, не логику.
- Игнорировать версии базовых образов (`latest`) и ловить сюрпризы при пересборке через полгода.

## Что запомнить

- Docker решает проблему воспроизводимого окружения и упаковки зависимостей.
- Контейнер — изолированный процесс на ядре хоста, не отдельная виртуальная машина.
- Образ — шаблон; контейнер — запуск этого шаблона.
- Изоляция опирается на namespaces и cgroups.
- Окружение должно описываться в Dockerfile/compose, а не только в голове команды.
