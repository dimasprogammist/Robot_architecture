# Слои образа

## Цель

Понять, как union filesystem собирает видимую корневую ФС контейнера из read-only слоёв образа и верхнего writable-слоя; научиться контролировать размер и кэш через устройство слоёв.

## Что уже нужно понимать

- Dockerfile порождает слои инструкциями `RUN`, `COPY`, `ADD`.
- Образ неизменяем; контейнер пишет в свой верхний слой.
- Кэш сборки переиспользует неизменённые слои.

## Объяснение

Слой — это набор файловых изменений: добавленные, изменённые или помеченные удалёнными файлы относительно родителя. Образ — стек таких слоёв. Контейнер видит результат объединения (union mount): снизу вверх применяется каждый слой, сверху — writable-слой контейнера.

Технологии на Linux часто называют overlay/overlay2. Идея одна: нижние слои только читаются и могут шариться между образами и контейнерами; уникальная запись контейнера идёт наверх.

Следствия:

1. **Общие базы экономят место.** Десять сервисов на `python:3.12-slim` делят одни и те же нижние слои на диске хоста.
2. **Удаление файла не всегда уменьшает образ.** Если слой N добавил большой файл, а слой N+1 его удалил, байты слоя N всё ещё в образе. Union просто скрывает файл. Чтобы реально убрать вес, удаление должно произойти в том же `RUN`, где файл появился, либо нужна другая стратегия сборки (multi-stage, без попадания файла в финальные слои).
3. **Кэш привязан к цепочке.** Изменили ранний слой — все последующие пересобираются, даже если их текст в Dockerfile тот же.

Практичный пример плохого слоя:

```dockerfile
RUN apt-get update && apt-get install -y huge-tool
RUN apt-get remove -y huge-tool
```

Второй слой «удаляет» пакет из видимости, но первый слой с пакетом остаётся в истории образа. Правильнее:

```dockerfile
RUN apt-get update && apt-get install -y huge-tool \
    && do-something \
    && apt-get purge -y huge-tool \
    && rm -rf /var/lib/apt/lists/*
```

Всё в одном `RUN` — в итоговом слое нет `huge-tool`.

`COPY` большого каталога создаёт слой целиком. Потом `RUN rm -rf` внутри не сэкономит место в сумме слоёв. Multi-stage копирует в финальный образ только нужные пути — лишние инструменты сборки не входят в финальные слои вообще.

Writable-слой контейнера: любые `echo > file`, установка пакетов внутри `docker exec` живут здесь. Они не возвращаются в образ, пока вы явно не сделаете `docker commit` (обычно плохая практика для прод-образов: лучше править Dockerfile и пересобрать).

Инструменты наблюдения:

- `docker history` — команды и размеры слоёв (размер — вклад слоя, не «сумма на диске с учётом шаринга» в бытовом смысле, но полезно искать толстые шаги).
- Dive и аналоги — интерактивный разбор содержимого слоёв.
- `docker system df` — сколько места занято images/containers/volumes.

Слои и pull: registry отдаёт слои по digest. Если на машине уже есть слой с тем же digest, повторно не качается. Отсюда ценность стабильных базовых образов в команде.

Связь с безопасностью: секрет, попавший в любой слой, остаётся в истории, даже если позже «удалён». Считайте слои auditable log файловой системы сборки.

## Термины

| Термин | Смысл |
|--------|--------|
| Layer | Read-only diff файловой системы |
| Union / Overlay FS | Объединение слоёв в одно дерево каталогов |
| Writable layer | Верхний слой записи контейнера |
| Parent image | Образ/слой, на котором строится следующий |
| Squash | Склеивание слоёв (редко нужно; лучше правильная сборка) |
| Cache bust | Событие, инвалидирующее последующие слои |

## Как это устроено

При чтении файла контейнером драйвер overlay ищет файл сверху вниз: есть в writable — берёт его; иначе в верхнем read-only слое; и так до базы. При записи файла, который был только внизу, делается copy-up: файл копируется в writable, затем меняется (copy-on-write).

Удаление файла из видимости помечается whiteout в верхнем слое — нижние копии физически на месте.

Поэтому «очистка» должна проектироваться на этапе Dockerfile, а не надеждой на поздний `rm` в отдельной инструкции, если цель — размер образа.

BuildKit может представлять шаги графом и кэшировать тоньше, но модель «каждый тяжёлый diff остаётся» для `RUN`/`COPY` сохраняется как ментальная модель.

## Пример

```dockerfile
FROM alpine:3.20

# Плохо для размера: большой файл останется в слое 1
# RUN wget -O /tmp/big.bin http://example.com/big && cp /tmp/big.bin /opt/big.bin
# RUN rm /tmp/big.bin

# Хорошо: скачали, использовали, удалили в одном слое
RUN wget -O /tmp/big.bin https://example.com/big.bin \
    && install -D /tmp/big.bin /opt/payload/big.bin \
    && rm /tmp/big.bin

COPY app.sh /usr/local/bin/app.sh
RUN chmod +x /usr/local/bin/app.sh

CMD ["/usr/local/bin/app.sh"]
```

Сравнение истории:

```bash
docker build -t layers-demo:1 .
docker history layers-demo:1
```

Multi-stage вариант, когда нужен компилятор:

```dockerfile
FROM golang:1.22-alpine AS build
WORKDIR /src
COPY .. .
RUN go build -o /out/app .

FROM alpine:3.20
COPY --from=build /out/app /usr/local/bin/app
CMD ["app"]
```

В финальном образе нет toolchain Go — только бинарник.

## Разбор

- Один `RUN` с `wget` + `rm` не оставляет временный файл в отдельном слое.
- `COPY --from=build` переносит артефакт без наследования слоёв стадии build.
- `docker history` на multi-stage финальном теге покажет короткую цепочку относительно builder.
- Writable-слой появится только после `docker run` и записи внутри контейнера — его нет в `history` образа.

Если вы «похудели» образ, удалив файлы отдельным `RUN rm`, сравните `docker history`: сумма размеров слоёв почти не упала — белые дыры whiteout не стирают нижний diff.

## Практическое применение

- Проектировать Dockerfile под кэш CI: редкие изменения выше частых.
- Держать финальные образы тонкими через multi-stage.
- Аудит толстых слоёв перед выкладкой в registry с лимитами размера.
- Не коммитить контейнеры как способ «сохранить правки» — это плодит невоспроизводимые слои.

## Типичные ошибки

- Думать, что `RUN rm` в новом слое уменьшает сумму слоёв образа.
- Копировать секреты «на минуту» и удалять позже — секрет остаётся в истории.
- Ставить `apt-get update` в одном слое, а `install` в другом — update устаревает, кэш врёт.
- Игнорировать shared layers и удивляться, что «10 образов × 200 МБ» на диске заняли меньше арифметики.

## Что запомнить

- Видимая ФС контейнера — union слоёв + writable.
- Слои образа read-only и неизменяемы.
- Удаление в новом слое скрывает, но не стирает байты нижнего слоя.
- Multi-stage и аккуратные `RUN` контролируют реальный размер.
- Секреты в любом слое = секреты навсегда в истории этого образа.

## Задание

Соберите два образа: в первом большой файл создаётся в одном `RUN`, удаляется в следующем; во втором создание и удаление в одном `RUN`. Сравните `docker history` и размер. Затем соберите multi-stage пример (можно с простым `echo` артефактом) и убедитесь, что финальный образ не содержит лишних файлов builder-стадии (`docker run ... ls`).
