# Тома

## Цель

Понять volumes и bind mounts: зачем выносить данные из writable-слоя контейнера, как том переживает удаление контейнера и когда какой тип монтирования уместен.

## Что уже нужно понимать

- Запись внутри контейнера без монтирования попадает в writable-слой и исчезает с `docker rm`.
- Образ и контейнер — разные сущности; данные приложения часто должны жить дольше контейнера.
- Базы данных и загрузки пользователей — классические долгоживущие данные.

## Объяснение

Контейнер по задумке эфемерен: его можно удалить и создать заново из образа. Но PostgreSQL с данными, загруженные фото, сертификаты Let’s Encrypt — не должны исчезать при каждом пересоздании. Решение — смонтировать хранилище снаружи writable-слоя.

Два основных механизма:

1. **Named volume (том Docker)** — объект, которым управляет Docker (`docker volume create`). Демон размещает данные в своей области на диске хоста. Контейнеру путь виден как обычный каталог, например `/var/lib/postgresql/data`.
2. **Bind mount** — прямой маппинг пути хоста (`./data` или `C:\proj\data`) в путь контейнера. Удобно для разработки: правите код на хосте — процесс в контейнере видит изменения.

Есть ещё tmpfs (память) для секретов/временного, но фокус урока — volume и bind.

Почему БД без volume теряет данные:

1. СУБД пишет файлы в каталог данных внутри ФС контейнера.
2. Эти файлы лежат в writable-слое.
3. `docker compose down` с удалением контейнера или `docker rm -v` уничтожает слой.
4. Новый контейнер из того же образа стартует с пустым каталогом данных — «чистая» база.

С томом каталог данных смонтирован: удалили контейнер — том остался. Новый контейнер монтирует тот же том — данные на месте.

Жизненный цикл тома:

- Создаётся явно или автоматически при первом `docker run -v name:/path`.
- Живёт независимо от контейнеров.
- Удаляется `docker volume rm` или `docker compose down -v` (осторожно: `-v` сносит тома compose).

Bind mount не создаёт объект volume: это просто связь с путём хоста. Удалили контейнер — файлы на хосте остаются. Риск: права UID/GID процесса в контейнере могут не совпадать с владельцем файлов на хосте; на Linux это частая боль.

Для продакшена данных БД обычно named volume или внешнее хранилище (облачный диск), а не bind на случайный путь разработчика. Для кода в dev — bind. Для node_modules иногда анонимный volume поверх bind, чтобы Linux-зависимости не смешивались с Windows-хостом — продвинутый приём, знать о проблеме полезно.

Копирование данных при первом старте: если том пустой и в образе в точке монтирования были файлы, Docker может инициализировать том содержимым из образа (для named volumes). Это удобно для образов СУБД с entrypoint-инициализацией.

Бэкапы: бэкапить нужно том или логический дамп БД, а не «образ с данными». Образ не для пользовательских данных.

## Термины

| Термин | Смысл |
|--------|--------|
| Volume | Хранилище под управлением Docker |
| Bind mount | Монтирование пути хоста в контейнер |
| Mount point | Путь внутри контейнера, куда смонтировано |
| Anonymous volume | Том без имени, часто от compose |
| Persist | Данные переживают пересоздание контейнера |
| Volume driver | Плагин размещения томов (локальный, облачный) |

## Как это устроено

При старте контейнера демон настраивает mount namespace: выбранные пути перекрываются томом или bind. Процесс пишет «в `/var/lib/postgresql/data`», фактически — в хранилище тома на хосте. Writable-слой образа для этих путей не используется (или используется только вне mount).

Команды:

```bash
docker volume ls
docker volume inspect mydata
docker run -v mydata:/data alpine write-something
```

В Compose:

```yaml
volumes:
  pgdata:
services:
  db:
    volumes:
      - pgdata:/var/lib/postgresql/data
```

Inspect покажет `Mountpoint` на хосте (путь внутри данных Docker). Править туда руками можно, но надёжнее через контейнер или утилиты бэкапа.

## Пример

```yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    ports:
      - "5432:5432"

  api:
    build: ./api
    volumes:
      - ./api/app:/app/app
    environment:
      DATABASE_URL: postgresql://postgres:secret@db:5432/app
    depends_on:
      - db

volumes:
  pgdata:
```

Для api bind `./api/app` — удобная разработка. Для db — named volume `pgdata`.

## Разбор

- После `docker compose down` (без `-v`) контейнеры удаляются, `pgdata` остаётся.
- `docker compose down -v` удалит `pgdata` — учебный стенд обнулится, прод так не делают случайно.
- Bind кода api не сохраняет «состояние бизнеса»; он лишь отражает файлы хоста.
- Строка `DATABASE_URL` указывает на хост `db` — имя сервиса в сети compose, не на том.

Проверка потери данных: поднимите Postgres без volume, создайте таблицу, удалите контейнер, поднимите снова — таблицы нет. С volume — есть.

## Практическое применение

- Локальная БД с данными, пережившими пересборку api.
- Хранение загрузок (`/var/app/uploads`) в томе или объектном хранилище.
- Dev: bind исходников + команда с hot-reload.
- Прод: тома на надёжном диске + регулярные бэкапы/снимки.

## Типичные ошибки

- Запускать Postgres без volume и удивляться пустой базе после recreate.
- Делать `compose down -v` на среде с нужными данными.
- Bind всего проекта включая `.git` и секреты без необходимости.
- Путать «образ с данными» и том: коммит контейнера БД — антипаттерн.
- На Windows/macOS ждать нативной скорости I/O БД на bind в общую папку — иногда лучше named volume.

## Что запомнить

- Том переживает контейнер; writable-слой — нет.
- БД без volume при удалении контейнера теряет данные.
- Named volume — для данных; bind — часто для кода в dev.
- `down -v` удаляет тома compose — опасный флаг.
- Бэкапы строят вокруг томов/дампов, не вокруг образов.

## Задание

Поднимите Postgres двумя способами: с named volume и без. Создайте таблицу в обоих. Пересоздайте контейнеры. Зафиксируйте результат. Выполните `docker volume ls` и `inspect`. Затем осознанно удалите учебный том.
