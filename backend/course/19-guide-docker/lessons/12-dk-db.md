# База данных в Docker

## Цель

Запускать СУБД в Docker правильно: том для каталога данных, переменные инициализации, сеть для api, осторожность с публикацией портов и понимание, почему без volume данные теряются.

## Что уже нужно понимать

- Контейнер эфемерен; writable-слой удаляется с контейнером.
- Named volume переживает контейнер.
- Compose DNS: api подключается к `db:5432`.

## Объяснение

Официальные образы Postgres, MySQL, Mongo — стандарт для локальной разработки и небольших стендов. Они уже содержат entrypoint-скрипты: при первом запуске с пустым томом создают пользователя, БД, применяют init-скрипты из специальной директории.

Критическое правило: **каталог данных СУБД должен быть на томе**.

Для Postgres это обычно `/var/lib/postgresql/data`. Без тома:

1. Инициализация пишет кластер в writable-слой.
2. Вы удаляете контейнер (`compose down`, recreate).
3. Новый контейнер стартует с пустым каталогом — снова init, пустая БД.
4. Все таблицы и данные учебной недели исчезают.

С томом `pgdata:/var/lib/postgresql/data` пересоздание контейнера (новый образ патча Postgres, смена env кроме критичных) сохраняет файлы кластера. Смена `POSTGRES_PASSWORD` на уже инициализированном томе **не всегда** меняет пароль — init выполняется только на пустом data-каталоге. Это частый сюрприз.

Переменные типичного Postgres-образа:

- `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` — для первой инициализации;
- дальше пароль и роли меняют SQL-ом или своим процессом.

Публикация `5432:5432` удобна для DBeaver с хоста. В проде на открытом сервере это риск: БД видна снаружи. Лучше VPN/SSH-туннель или доступ только из Docker-сети.

Производительность: на Docker Desktop bind-mount каталога данных в Windows-файловую систему может быть медленным; named volume часто быстрее. Для учёбы разница заметна на крупных фикстурах.

Бэкапы:

- логический: `pg_dump` из эфемерного контейнера в той же сети / с монтированием;
- файловый: бэкап тома при остановленной записи — сложнее.
Не делайте `docker commit` контейнера БД «чтобы сохранить данные» — это не стратегия.

Обновление мажорной версии Postgres — не просто смена тега на том же data-каталоге. Нужен dump/restore или официальный путь апгрейда. Минорные патчи обычно проще.

Несколько БД на одном хосте: разные compose-проекты и тома, разные published-порты (`5433:5432`), чтобы не конфликтовать.

Seed-данные: SQL в `/docker-entrypoint-initdb.d` срабатывает только при пустом томе. Для повторного наката используйте миграции приложения или отдельные скрипты.

Healthcheck (`pg_isready`) помогает api не стартовать раньше приёма соединений.

## Термины

| Термин | Смысл |
|--------|--------|
| Data directory | Каталог файлов кластера СУБД |
| Init entrypoint | Скрипты первого запуска официального образа |
| pg_dump | Логический дамп Postgres |
| Named volume | Том Docker для data directory |
| Superuser | Роль с полными правами (создаётся init) |

## Как это устроено

При старте контейнера Postgres:

1. Entrypoint проверяет data directory.
2. Если пусто — initdb, создание роли/БД из env, прогон initdb.d.
3. Если не пусто — пропускает init, просто запускает сервер с существующими файлами.
4. Сервер слушает 5432 внутри netns; в compose доступен как `db:5432`.

Том монтируется до старта процесса — postgres сразу пишет «на том». Удаление контейнера не трогает том, пока не указан `-v` у `down` или явный `volume rm`.

## Пример

```yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./db/init:/docker-entrypoint-initdb.d:ro
    ports:
      - "5432:5432"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      timeout: 3s
      retries: 10

  api:
    build: ./backend
    environment:
      DATABASE_URL: postgresql://app:${POSTGRES_PASSWORD}@db:5432/app
    depends_on:
      db:
        condition: service_healthy

volumes:
  pgdata:
```

Пример потери данных (антипаттерн):

```yaml
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: secret
    # нет volumes — данные в writable-слое
```

## Разбор

- С томом учебные таблицы переживают пересборку api и recreate db-контейнера.
- Init SQL в `init/` выполнится один раз на пустом `pgdata`.
- Смена пароля в `.env` после init не пересоздаст пользователя автоматически.
- `ports` нужны только для инструментов на хосте; api работает и без них.
- Antipattern без volume демонстрирует главный учебный тезис курса про данные.

Проверка: создайте таблицу, `compose down`, `compose up` — данные есть. Затем `compose down -v`, `up` — данных нет.

## Практическое применение

- Локальная БД без установки Postgres в систему.
- Изоляция проектов разными томами.
- CI: Postgres-сервис в compose/github service container для интеграционных тестов (часто без долгого тома).
- Демо: поднять стек с уже проинициализированным томом или seed-скриптом.

## Типичные ошибки

- БД без volume и «куда делись данные».
- `down -v` на нужном томе.
- Ожидание, что смена `POSTGRES_PASSWORD` обновит уже живой кластер.
- Открытый 5432 в интернет без защиты.
- Апгрейд major-версии сменой тега на том же data dir без процедуры.

## Что запомнить

- Без volume данные БД живут в writable-слое и гибнут с контейнером.
- Том монтируют в data directory официального образа.
- Init env и initdb.d — только на пустом томе.
- Api подключается к `db`, не к localhost.
- Бэкапы — dump/том, не docker commit.

## Задание

Поднимите Postgres с томом, создайте таблицу с данными. Пересоздайте контейнер — проверьте сохранность. Повторите без тома. Выполните `pg_dump` через `docker compose exec` или `run`. Измените пароль в env на существующем томе и задокументируйте поведение.
