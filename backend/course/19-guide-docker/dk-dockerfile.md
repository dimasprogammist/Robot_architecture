# Dockerfile

## Цель

Научиться описывать сборку образа через Dockerfile: базовый образ, копирование файлов, установка зависимостей, команда запуска и разумный порядок инструкций для кэша.

## Что уже нужно понимать

- Образ состоит из слоёв; контейнер запускается из образа.
- Контекст сборки — файлы, которые клиент отдаёт демону при `docker build`.
- Разница между зависимостями приложения и исходным кодом.

## Объяснение

Dockerfile — текстовый рецепт. Каждая инструкция добавляет слой (или влияет на метаданные). Демон читает файл сверху вниз. Результат — образ, готовый к `docker run`.

Базовые инструкции:

- `FROM` — обязательная точка старта, базовый образ.
- `WORKDIR` — каталог по умолчанию для последующих команд и для процесса.
- `COPY` / `ADD` — файлы из контекста в образ (`COPY` предпочтительнее в большинстве случаев).
- `RUN` — выполнить команду на этапе сборки (установка пакетов, сборка).
- `ENV` — переменные окружения в образе.
- `EXPOSE` — документирует порт (не публикует его на хост).
- `CMD` — команда по умолчанию при старте контейнера.
- `ENTRYPOINT` — фиксированная точка входа; часто комбинируется с `CMD` как аргументами.
- `USER` — пользователь, от которого идёт процесс (не root — хорошая привычка).
- `ARG` — переменные только на этапе сборки.

Порядок критичен для кэша. Docker кэширует слой, если инструкция и входные данные не изменились. Паттерн для языков с манифестом зависимостей:

1. Скопировать только файл зависимостей.
2. Установить зависимости (`RUN pip install` / `npm ci`).
3. Скопировать исходники.
4. Задать `CMD`.

Тогда правка `main.py` не пересобирает тяжёлый слой с пакетами.

Контекст сборки — обычно каталог с Dockerfile. Всё, что не исключено `.dockerignore`, может уйти на демон. В ignore кладут: `.git`, `venv`, `node_modules`, `__pycache__`, локальные `.env`, тесты с фикстурами огромного размера, если они не нужны в образе.

Multi-stage: несколько `FROM` в одном файле. В первой стадии ставят компилятор и собирают артефакт; во второй — минимальный runtime и `COPY --from=builder`. Финальный образ меньше и без инструментов сборки.

`CMD` vs `ENTRYPOINT`:

- Только `CMD ["app"]` — легко заменить командой в `docker run image othercmd`.
- `ENTRYPOINT ["app"]` + `CMD ["--flag"]` — `app` всегда запускается, аргументы подменяются.
- Shell-форма `CMD app` запускает через `/bin/sh -c` — удобно, но хуже с сигналами.

Не кладите в образ то, что должно приходить извне в рантайме: пароли, ключи API, специфичные для стенда URL. Для этого env и секреты оркестратора. В образе — код, зависимости, разумные значения по умолчанию для разработки.

Версии базы фиксируйте: `python:3.12.7-slim`, не безымянный `python`. Обновление базы — сознательное действие, а не сюрприз при кэш-миссе.

Проверка сборки локально: `docker build -t name:tag .` из каталога с Dockerfile. Для отладки слоёв — `docker history`. Для уменьшения размера — меньше пакетов, очистка кэшей пакетного менеджера в том же `RUN`, alpine/slim базы осторожно (совместимость libc).

## Термины

| Термин | Смысл |
|--------|--------|
| Dockerfile | Рецепт сборки образа |
| Build context | Файлы, доступные для `COPY` |
| .dockerignore | Исключения из контекста |
| Instruction | Строка-директива (`RUN`, `COPY`, …) |
| Multi-stage | Несколько стадий `FROM` в одном файле |
| Build cache | Переиспользование неизменённых слоёв |

## Как это устроено

Клиент упаковывает контекст и отправляет демону. Демон для каждой инструкции:

1. Проверяет кэш.
2. При промахе создаёт временный контейнер от предыдущего слоя, выполняет шаг, коммитит новый слой.
3. Обновляет метаданные образа (Env, Cmd, …).

`COPY` инвалидирует кэш, если изменился хэш копируемых файлов. `RUN` — если изменилась строка команды или предыдущие слои. Поэтому «тяжёлое и редкое» ставят выше «лёгкого и частого» по возможности, с оглядкой на корректность.

На современных BuildKit поведение кэша и параллелизма богаче, но учебная модель «слой на инструкцию» остаётся рабочей для понимания.

## Пример

```dockerfile
FROM python:3.12-slim AS base

WORKDIR /app

RUN apt-get update && apt-get install -y --no-install-recommends \
    curl \
    && rm -rf /var/lib/apt/lists/*

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app ./app

ENV APP_ENV=production \
    PYTHONUNBUFFERED=1

EXPOSE 8000
USER nobody
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

`.dockerignore`:

```text
.git
.venv
__pycache__
*.pyc
.env
.pytest_cache
```

## Разбор

- Один `RUN` для `apt-get` с очисткой lists — не оставляем кэш пакетов отдельным слоем.
- Зависимости ставятся до копирования `app/` — кэш pip живёт дольше.
- `USER nobody` — процесс не от root (для реального проекта создают отдельного пользователя с нужными правами на `/app`).
- `EXPOSE 8000` документирует порт; публикация всё равно через `-p` или compose `ports`.
- `.dockerignore` не даёт утечь `.env` и не раздувает контекст `.venv`.

Если нужен компилятор только для сборки wheel, вынесите его в stage `builder` и копируйте site-packages или бинарник в slim-стадию.

## Практическое применение

- Репозиторий сервиса содержит Dockerfile рядом с кодом — единый способ собрать артефакт.
- CI выполняет `docker build` и пушит в registry.
- Разные Dockerfile для dev (с hot-reload) и prod (минимальный) — осознанно, не смешивая цели.
- Шаблоны для команды: базовые образы и линтеры Dockerfile (hadolint) в пайплайне.

## Типичные ошибки

- `COPY . .` в начале файла — любой чих в репозитории сбрасывает кэш всего.
- Секреты в `ARG`/`ENV`, видимые в `docker history`.
- Забыть удалить кэш `apt` и получить образ на сотни лишних мегабайт.
- Shell-форма `CMD` и проблемы с graceful shutdown.
- Отсутствие `.dockerignore` и копирование `node_modules` с хоста Windows в Linux-образ.

## Что запомнить

- Dockerfile — код сборки окружения.
- Порядок инструкций = скорость за счёт кэша.
- Контекст ограничивают `.dockerignore`.
- `CMD`/`ENTRYPOINT` задают процесс контейнера.
- Секреты и стенд-специфика — не в слоях образа.

## Задание

Напишите Dockerfile для маленького HTTP-сервиса на знакомом языке. Добавьте `.dockerignore`. Соберите образ дважды: до и после правки одного файла кода — сравните время и вывод сборки (какие шаги `CACHED`). Откройте `docker history` и сопоставьте строки с инструкциями.
