# Контейнер

## Цель

Понять контейнер как запущенный процесс, созданный из образа: изоляция через namespaces, жизненный цикл, запись в writable-слой и почему остановка контейнера не равна удалению образа.

## Что уже нужно понимать

- Образ — неизменяемый шаблон файловой системы и метаданных.
- Процесс в ОС имеет PID, открытые файлы, сетевые сокеты.
- Docker Engine принимает команды `run`, `stop`, `rm`.

## Объяснение

Контейнер — это экземпляр запуска образа. Демон создаёт изолированное окружение и стартует процесс (часто один главный — PID 1 внутри контейнера). Пока процесс жив (или пока контейнер в состоянии running), контейнер «работает». Когда главный процесс завершился — контейнер останавливается.

Ключевая формула: **образ = шаблон, контейнер = процесс + writable-слой поверх слоёв образа**.

Изоляция:

- **PID namespace** — внутри контейнера своё дерево процессов; главный процесс видит себя как PID 1.
- **Mount namespace** — своя корневая ФС из слоёв образа + верхний слой записи.
- **Network namespace** — свой сетевой стек: интерфейсы, маршруты, порты (часто veth + bridge на хосте).
- **UTS / IPC** — своё имя хоста и изоляция IPC при необходимости.
- **User namespace** (опционально) — отображение UID внутри и снаружи.

На хосте вы можете увидеть процесс контейнера через `ps` (на Linux): это обычный процесс с другими namespace. Отсюда лёгкость: нет второй ОС, есть границы видимости.

Жизненный цикл типовых состояний:

1. Создан (`created`) — контейнер есть, процесс ещё не стартовал.
2. Запущен (`running`).
3. Остановлен (`exited`) — процесс завершился или его остановили; writable-слой и метаданные пока на диске.
4. Удалён — запись о контейнере и его writable-слой уничтожены (если не было внешних томов).

Команды:

- `docker run` = создать + стартовать (часто в одном шаге).
- `docker start` / `stop` / `restart` — управление уже существующим контейнером.
- `docker rm` — удалить остановленный контейнер.
- `docker exec` — запустить дополнительный процесс в уже работающих namespaces (шелл для отладки).
- `docker logs` — stdout/stderr главного процесса.

Важно про данные: всё, что записано в файловую систему контейнера вне томов, живёт в writable-слое. Удалили контейнер — записи пропали. Образ при этом цел. Поэтому БД и загруженные файлы выносят в volumes.

Интерактивность: `-it` даёт TTY для шелла. В проде API-контейнеры обычно без `-it`, в фоне (`-d`). Имена контейнеров (`--name`) удобны для логов и compose; без имени Docker генерирует случайное.

Порты: процесс внутри слушает, например, `:8000`. Чтобы достучаться с хоста, нужен publish (`-p 8000:8000`) или общая Docker-сеть с другим контейнером. Без проброса порт «существует» только внутри network namespace контейнера (и связанных сетей).

Ресурсы: можно ограничить память и CPU (`--memory`, `--cpus`). Без лимитов один прожорливый контейнер может исчерпать хост — изоляция namespaces не равна жёстким квотам; квоты — зона cgroups.

Сигналы: при `docker stop` демону шлётся SIGTERM главному процессу, потом SIGKILL по таймауту. Поэтому PID 1 должен корректно обрабатывать сигналы. Если `CMD` записан через `sh -c "..."`, сигналы может глотать оболочка — отсюда рекомендация exec-формы JSON.

Контейнер можно «лечить» пересозданием: удалили и создали заново из того же образа — чистое состояние ФС (кроме томов). Это и сила, и ловушка: любое ручное «подкрутить внутри» без фиксации в образе потеряется.

## Термины

| Термин | Смысл |
|--------|--------|
| Container | Процесс + writable-слой на базе образа |
| PID 1 | Главный процесс внутри контейнера |
| Writable layer | Слой записи поверх read-only слоёв образа |
| docker exec | Доп. процесс в namespaces уже запущенного контейнера |
| Publish ports | Проброс порта контейнера на хост |
| Restart policy | Правило автоперезапуска при падении |

## Как это устроено

При `docker run`:

1. Выбирается образ (локально или pull).
2. Создаётся контейнер: конфиг, сеть, mounts.
3. Собирается mount: слои образа + overlay/writable.
4. Настраиваются namespaces и cgroups.
5. Стартует процесс с Env/Cmd из образа, перекрытыми флагами run при необходимости.

Сеть по умолчанию — bridge: контейнер получает IP вида `172.x.x.x`. DNS внутри пользовательских сетей compose резолвит имена сервисов. На default bridge DNS-имена сервисов ограничены — для связки сервисов лучше user-defined network или compose.

Логи контейнера — это поток stdout/stderr, который драйвер логирования Docker сохраняет (часто json-file на диске хоста). Приложение должно писать логи в stdout, а не только в файл внутри контейнера (файл пропадёт вместе с контейнером, если нет тома).

## Пример

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY main.py .
CMD ["python", "main.py"]
```

`main.py`:

```python
import time
print("container started", flush=True)
while True:
    time.sleep(5)
    print("heartbeat", flush=True)
```

Запуск:

```bash
docker build -t heartbeat:1 .
docker run -d --name hb heartbeat:1
docker ps
docker logs -f hb
docker exec hb ps aux
docker stop hb
docker rm hb
```

## Разбор

- Контейнер `hb` — процесс Python в изоляции; образ `heartbeat:1` не меняется от логов.
- `docker logs` читает stdout; `flush=True` важен, иначе буферизация отложит вывод.
- `docker exec ... ps` показывает процессы внутри PID namespace.
- `stop` + `rm` убирают контейнер; `docker images` всё ещё покажет `heartbeat:1`.
- Если бы `main.py` писал в `/tmp/data.txt`, после `rm` файл исчез бы вместе с writable-слоем.

Перезапуск с `--restart unless-stopped` полезен на сервере: демон поднимет контейнер после ребута хоста. Для обучения чаще достаточно ручного `run`.

## Практическое применение

- Одинаковый запуск API на ноутбуке и в CI через один и тот же образ.
- Отладка: `docker exec -it app sh` (или bash), просмотр env и файлов.
- Синие/зелёные выкаты: новый контейнер из нового образа, старый останавливают после проверки.
- Эфемерные job-контейнеры: миграции, одноразовые скрипты с `--rm`.

## Типичные ошибки

- Править код только внутри контейнера и удивляться, что после пересоздания правки исчезли.
- Хранить базу в writable-слое без volume.
- Путать `stop` (процесс остановлен, контейнер есть) и `rm` (контейнера нет).
- Забыть `-p` и считать, что сервис «не работает», хотя внутри он слушает порт.
- Держать много остановленных контейнеров и забивать диск их слоями — помогает `docker container prune`.

## Что запомнить

- Контейнер — запущенный процесс из образа, не сам образ.
- Изоляция — namespaces; лимиты — cgroups.
- Запись без тома живёт только в writable-слое контейнера.
- Удаление контейнера не удаляет образ.
- Главный процесс должен корректно завершаться по сигналам.

## Задание

Запустите контейнер из любого образа (`nginx` или своего). Проверьте `docker ps`, `docker logs`, сделайте `docker exec`. Остановите и удалите контейнер, убедитесь, что образ остался. Создайте файл внутри контейнера, удалите контейнер и объясните, куда делся файл.
