# Переменные окружения

## Цель

Научиться конфигурировать контейнеры через переменные окружения: отличие build-time и runtime, файлы `.env`, секреты и почему один образ обслуживает dev/stage/prod с разными значениями.

## Что уже нужно понимать

- Процесс читает окружение ОС (`environ`): строки `KEY=value`.
- Образ фиксирует файлы; конфигурация стенда часто меняется чаще кода.
- Сеть compose даёт имена хостов; в URL их подставляют в переменные.

## Объяснение

12-factor подход: конфиг — в окружении, не в коде. Docker усиливает это: один и тот же образ `myapi:1.4.0` запускают с разными `DATABASE_URL`, `LOG_LEVEL`, `FEATURE_X`. Пересборка не нужна, если код уже умеет читать env.

Где задают переменные:

1. **Dockerfile `ENV`** — значения по умолчанию, вшитые в образ (видимы в истории). Подходит для безобидного `PYTHONUNBUFFERED=1`, не для паролей.
2. **`docker run -e KEY=val`** или `--env-file`.
3. **Compose `environment` / `env_file`** — удобно для стека.
4. **Оркестратор/CI secrets** — в проде предпочтительно.

Разделение build-time и runtime:

- `ARG` — только во время `docker build`. Можно пробросить в `ENV`, но тогда значение попадёт в образ.
- Runtime `-e` — только у конкретного контейнера, образ не меняется.

Типичные ключи для backend:

- URL БД, Redis, брокера;
- секрет подписи JWT (не коммитить);
- режим приложения (`APP_ENV=development|production`);
- публичный URL фронта для редиректов OAuth.

Фронтенд-нюанс: переменные, попавшие в бандл JavaScript на этапе `npm run build`, — это build-time. `REACT_APP_*` / `VITE_*` часто «запекаются» в статику. Для чисто runtime-конфига фронта нужен другой приём (env.js, подстановка при старте nginx). Не путайте: `-e` на контейнере nginx не изменит уже собранный JS сам по себе.

Файлы `.env` в compose:

- Compose автоматически читает `.env` в каталоге проекта для подстановки `${VAR}` в yaml.
- `env_file: - .env` передаёт переменные в контейнер.
- `.env` не должен попадать в git, если там секреты; в репозитории — `.env.example` без секретов.

Приоритет (упрощённо): флаги/compose environment перекрывают env_file, те перекрывают ENV образа. Точные таблицы зависят от инструмента — проверяйте на практике для своего случая.

Секреты:

- Не `ENV PASSWORD=...` в Dockerfile.
- Не светить секреты в `docker inspect` на общих машинах без нужды (они видны в конфиге контейнера).
- Для обучения хватит env_file вне git; для прода — secret store.

Приложение обязано валидировать обязательные переменные при старте: понятный crash лучше, чем молчаливый localhost.

Смена env = пересоздание контейнера (обычно), не «горячая» подстановка во все фреймворки. Процесс читает окружение при старте.

## Термины

| Термин | Смысл |
|--------|--------|
| ENV | Переменная в образе / процессе |
| ARG | Переменная сборки Dockerfile |
| env_file | Файл со списком KEY=value для контейнера |
| Runtime config | Конфиг, задаваемый при запуске |
| Build-time config | Конфиг, запечённый при сборке |
| Secret | Чувствительное значение, не для образа и git |

## Как это устроено

При старте контейнера демон собирает итоговый массив окружения и передаёт его процессу (execve с envp). Внутри Linux это `/proc/self/environ` у процесса. Приложение использует стандартные API языка (`os.environ`, `process.env`).

Compose подставляет переменные в YAML до создания контейнеров: `${POSTGRES_PASSWORD}` берётся из окружения хоста или файла `.env` проекта. Это отдельный механизм от `env_file` сервиса.

Инспекция:

```bash
docker exec api env
docker inspect api --format '{{json .Config.Env}}'
```

Не оставляйте отладочный вывод всех env в публичных логах.

## Пример

Dockerfile:

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app ./app
ENV APP_ENV=production \
    PYTHONUNBUFFERED=1
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Compose:

```yaml
services:
  api:
    build: ./api
    env_file:
      - ./api/.env
    environment:
      DATABASE_URL: postgresql://postgres:${POSTGRES_PASSWORD}@db:5432/app
      APP_ENV: development
    ports:
      - "8000:8000"
    depends_on:
      - db

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
```

Файл `.env` рядом с compose:

```text
POSTGRES_PASSWORD=dev-only-secret
```

## Разбор

- Образ не знает пароль Postgres — он приходит при запуске.
- `APP_ENV` в compose перекрывает default из Dockerfile для локалки.
- `${POSTGRES_PASSWORD}` подставляется compose при разборе yaml; тот же секрет уходит в db и в URL api.
- Хост БД в URL — `db`, имя сервиса в сети.
- Если забыть пароль в `.env`, подстановка будет пустой — контейнер БД может не стартовать или отвергнуть пароль; лучше явная проверка.

Для продакшена пароль берут из секрет-хранилища CI/CD, не из закоммиченного файла.

## Практическое применение

- Один артефакт образа на все стенды.
- Быстрое переключение feature-flag через env на staging.
- Документирование контракта окружения в `.env.example` и README.
- Разделение публичных и секретных ключей (публичные можно в пример, секреты — нет).

## Типичные ошибки

- Секреты в слоях образа и в git.
- Ожидать, что runtime `-e VITE_API_URL` изменит уже собранный фронтовый бандл.
- `localhost` в `DATABASE_URL` внутри контейнера api.
- Разные имена переменных в документации и в коде (`DB_URL` vs `DATABASE_URL`).
- Логировать полный env при старте в проде.

## Что запомнить

- Env отделяет конфиг стенда от содержимого образа.
- `ARG` — сборка; runtime `-e` / compose — запуск.
- Секреты не в Dockerfile и не в git.
- Фронтовый бандл часто требует build-time переменных.
- Имена хостов сервисов compose задают в URL через env.

## Задание

Сделайте сервис, который печатает `APP_ENV` и наличие `DATABASE_URL` (без печати пароля). Запустите с двумя разными наборами env без пересборки образа. Создайте `.env.example` и реальный `.env` в ignore. Намеренно сломайте URL хостом `localhost` и сравните с хостом `db`.
