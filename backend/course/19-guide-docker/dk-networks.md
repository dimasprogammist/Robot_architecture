# Сети Docker

## Цель

Понять сети Docker: bridge, изоляция network namespace, DNS-имена сервисов в user-defined сетях и Compose, отличие внутренней связности от проброса портов на хост.

## Что уже нужно понимать

- У контейнера свой network namespace: свои интерфейсы и порты.
- Сервисы (api, db, web) обычно общаются по TCP.
- Том решает данные; сеть решает связность процессов.

## Объяснение

Каждый контейнер по умолчанию получает сетевой стек, отделённый namespace. Чтобы пакеты ходили между контейнерами и наружу, Docker создаёт виртуальные сети. Самый частый драйвер — **bridge**: на хосте появляется мост (например `docker0` или `br-xxxx`), контейнеры подключаются через пары veth.

Адрес контейнера — внутренний IP в подсети моста. С хоста до него можно достучаться через этот IP (на Linux) или, удобнее и стабильнее, через published ports (`-p`). Между контейнерами на одной user-defined bridge-сети лучше ходить по **имени контейнера или сервиса**, а не по IP: IP может смениться при recreate.

DNS внутри Docker:

- На сети по умолчанию (`bridge`) встроенный DNS для произвольных имён ограничен.
- На **user-defined network** (compose создаёт такую сам) работает DNS: имя сервиса `db` резолвится в IP контейнера(ов) этого сервиса.

Поэтому в `DATABASE_URL=postgresql://db:5432/app` хост `db` — не магия Postgres, а DNS Docker Compose.

Проброс портов `-p 8080:80`:

- Слушает порт 8080 на хосте (или на выбранном интерфейсе).
- Направляет трафик на порт 80 **внутри** network namespace контейнера.
- Нужен людям и браузерам снаружи Docker-сети.
- Не нужен для связи api↔db внутри одной compose-сети: api стучится на `db:5432` напрямую, без `-p`.

Публиковать порт БД на все интерфейсы хоста в проде часто лишнее и опасно. Для локальной отладки из GUI-клиента — допустимо `5432:5432`.

Типы сетей (учебный минимум):

- **bridge** — стандарт для контейнеров на одном хосте.
- **host** — контейнер делит сеть хоста (без изоляции сети; на Docker Desktop поведение особое).
- **none** — без сети.
- **overlay** — для Swarm/мультихоста (за рамками курса, знать о существовании).

Изоляция: контейнеры в разных user-defined сетях друг друга «не видят», пока не подключены к общей сети. Можно подключить контейнер к нескольким сетям (например, frontend в сети edge, backend в сети app).

Отладка сети:

- `docker network ls` / `inspect`
- `docker exec api ping db` (если есть ping) или `wget`/`curl` до `http://db:5432` не всегда показателен для бинарных протоколов — лучше клиент БД или `nc`.
- Логи приложения с ошибкой connection refused / name resolution — разные диагнозы: DNS vs порт не слушается.

Hostname контейнера по умолчанию — короткий id; в compose часто совпадает с именем сервиса + project. Не завязывайте жёстко логику на случайные имена вне compose.

Firewall хоста и корпоративные VPN иногда ломают ожидания Docker Desktop — имейте в виду при «у коллеги работает».

## Термины

| Термин | Смысл |
|--------|--------|
| Bridge network | Виртуальный мост на одном хосте |
| User-defined network | Явно созданная сеть с DNS имён |
| Service name | Имя сервиса в Compose = DNS-имя |
| Port publishing | Проброс порта на хост |
| veth | Виртуальная пара интерфейсов контейнер↔мост |
| Ingress | Вход трафика снаружи в контейнер |

## Как это устроено

При создании сети bridge демон настраивает bridge-интерфейс и IPAM (выдачу адресов). При подключении контейнера:

1. Создаётся netns контейнера.
2. Один конец veth — в netns, другой — на мосту.
3. Выдаётся IP из подсети сети.
4. Настраивается маршрутизация и, при publish, правила перенаправления портов (proxy/iptables/nftables — детали зависят от платформы).

Compose-проект создаёт сеть вида `project_default` и подключает сервисы. Обновление контейнера сохраняет имя сервиса — клиенты продолжают резолвить `db`.

Внешний доступ: браузер → `localhost:8080` → publish → процесс в контейнере. Внутренний: api → DNS `db` → IP → порт 5432 в netns db.

## Пример

```yaml
services:
  web:
    image: nginx:1.27-alpine
    ports:
      - "8080:80"
    networks:
      - frontend

  api:
    build: ./api
    networks:
      - frontend
      - backend
    environment:
      DATABASE_URL: postgres://postgres:secret@db:5432/app

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: secret
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks:
      - backend

networks:
  frontend:
  backend:

volumes:
  pgdata:
```

Здесь `web` не имеет прямого доступа к `db` — только через `api`, если так задумана сегментация.

## Разбор

- `web` публикует 8080 для человека; `api` и `db` могут обойтись без ports.
- Имя `db` резолвится только у тех, кто в сети `backend` (у `api`).
- Разделение frontend/backend сетей — простой аналог сегментации.
- Том `pgdata` ортогонален сети: данные и связность — разные оси.

Если api пишет URL `localhost:5432`, он ищет Postgres **в своём** netns — там пусто. Нужен хост `db`.

## Практическое применение

- Локальный стек compose без ручной прописки IP.
- Не светить БД наружу без нужды.
- Подключать sidecar (proxy) в те же сети, что и приложение.
- Отладка «connection refused» vs «could not resolve host» как разные классы ошибок.

## Типичные ошибки

- `localhost` внутри контейнера вместо имени сервиса.
- Публикация всех портов «на всякий случай».
- Ожидание DNS-имён на legacy default bridge как в compose.
- Жёсткая привязка к IP контейнера в конфигах.
- Забыть, что два compose-проекта — разные сети по умолчанию (нужен `external` network для связи).

## Что запомнить

- Контейнер в своём network namespace; bridge связывает их на хосте.
- User-defined / compose DNS даёт имена сервисов.
- Publish — для доступа с хоста/интернета; внутри сети достаточно имени и порта.
- `localhost` в контейнере — это сам контейнер.
- Сеть и тома решают разные задачи.

## Задание

Поднимите два контейнера в одной user-defined сети (`docker network create lab`). Запустите nginx и alpine с `wget -qO- http://web:80` (подставьте имя). Затем уберите общую сеть и повторите — зафиксируйте ошибку. В compose добавьте сервис без `ports` и достучитесь до него только из соседнего сервиса.
