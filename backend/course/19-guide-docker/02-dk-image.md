# Образ

## Цель

Понять образ Docker как неизменяемый шаблон файловой системы и метаданных, из которого создаются контейнеры; научиться читать теги, слои и связь с реестром.

## Что уже нужно понимать

- Зачем нужен Docker: воспроизводимое окружение и упаковка зависимостей.
- Процесс ОС читает файлы, библиотеки и интерпретатор с диска.
- Разница между «исходниками» и «артефактом сборки».

## Объяснение

Образ (image) — это снимок корневой файловой системы плюс инструкции запуска: какая команда стартует по умолчанию, какие переменные окружения заданы, какой рабочий каталог, какие порты документированы. Образ не «работает» сам по себе: это шаблон. Работает контейнер, созданный из образа.

Аналогия: образ — как установочный диск с уже разложенными файлами приложения; контейнер — включённый компьютер, загруженный с этого диска, плюс свой тонкий слой изменений. Более точная техническая картина: образ состоит из слоёв (layers). Каждый слой — набор изменений файловой системы относительно предыдущего. Слои только для чтения. При запуске контейнера поверх добавляется тонкий writable-слой.

Почему неизменяемость важна: если образ с тегом `myapi:1.2.0` уже собран, его содержимое не меняется «по ходу жизни». Чтобы изменить код или зависимости, собирают новый образ (часто с новым тегом). Старый образ остаётся; контейнеры, созданные из него, продолжают ссылаться на те же слои. Это даёт откат: вернули предыдущий тег — получили прежнее окружение.

Образы имеют идентификаторы (digest, обычно sha256) и человекочитаемые имена с тегами: `nginx:1.27-alpine`, `postgres:16`. Тег — указатель на конкретный digest. Тег `latest` опасен тем, что сегодня и через месяц может указывать на разное. В учебных примерах `latest` допустим; в проде фиксируют версию или digest.

Откуда берутся образы:

1. Сборка локально через Dockerfile (`docker build`).
2. Скачивание из реестра (`docker pull`).
3. Загрузка в реестр (`docker push`) для команды и серверов.

Базовый образ (`FROM`) — фундамент. Для Python-сервиса часто берут `python:3.12-slim`, для Node — `node:20-alpine`. Чем меньше и понятнее база, тем меньше поверхность атаки и быстрее доставка, но иногда нужен полный образ с компиляторами для сборки нативных расширений.

Метаданные образа включают:

- `Entrypoint` и `Cmd` — что запускать;
- `Env` — переменные по умолчанию;
- `WorkingDir` — каталог процесса;
- `ExposedPorts` — документация портов (сама по себе публикацию не делает);
- метки (labels) — произвольные ключи для автоматизации.

Образ можно инспектировать: `docker image inspect`, `docker history` показывает слои и команды, которыми они появились. История помогает понять, почему образ раздут: лишний `apt-get` без очистки, копирование всей папки `.git`, установка dev-зависимостей в финальный слой.

Кэш сборки опирается на слои: если инструкция Dockerfile и её контекст не изменились, Docker переиспользует слой. Поэтому порядок инструкций влияет на скорость: сначала копируют файлы зависимостей и ставят пакеты, потом копируют исходники — чтобы правка кода не инвалидировала слой с `pip install`.

Образ — единица обмена между людьми и средами. CI собирает образ, тестирует, пушит в registry. Staging и production тянут один и тот же digest. Это сильнее, чем «на сервере сделали git pull»: на сервере может быть другая системная библиотека; в образе системные файлы уже внутри.

## Термины

| Термин | Смысл |
|--------|--------|
| Image | Неизменяемый шаблон ФС + метаданные запуска |
| Tag | Человекочитаемая метка на конкретный образ |
| Digest | Хэш содержимого (точные байты слоёв) |
| Layer | Read-only слой изменений ФС |
| Base image | Образ в инструкции `FROM` |
| Registry | Сервер хранения и раздачи образов |
| Manifest | Описание, какие слои входят в образ |

## Как это устроено

Физически слои хранятся на диске хоста (или ВМ Docker Desktop). Демон знает граф: какие слои к каким образам относятся. Несколько образов могут делить общие базовые слои — экономия места и времени pull.

При `docker pull nginx:1.27-alpine`:

1. Клиент запрашивает манифест у registry.
2. Скачиваются недостающие слои (уже имеющиеся пропускаются).
3. Локально появляется ссылка `nginx:1.27-alpine` на digest.

При `docker build`:

1. Клиент отправляет контекст сборки (файлы каталога, с учётом `.dockerignore`).
2. Демон выполняет инструкции Dockerfile по порядку, кэшируя слои.
3. Результат получает тег, если вы его указали.

Удаление образа (`docker rmi`) возможно, только если нет контейнеров, которые на него ссылаются (или с принудительными флагами). Слои, на которые больше никто не ссылается, становятся кандидатами на очистку (`docker image prune`).

## Пример

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app ./app

ENV PYTHONUNBUFFERED=1
EXPOSE 8000
CMD ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Сборка и просмотр:

```bash
docker build -t myapi:0.1.0 .
docker images
docker history myapi:0.1.0
```

## Разбор

- База `python:3.12-slim` уже содержит интерпретатор — не ставим Python с нуля.
- Сначала `requirements.txt` и `pip install` — слой зависимостей кэшируется, пока файл не изменится.
- Затем копируется код `app/` — частые правки не пересобирают pip-слой.
- `--no-cache-dir` уменьшает мусор pip внутри слоя.
- `CMD` в exec-форме (JSON-массив) — процесс получает сигналы корректно, без лишней оболочки.
- Тег `myapi:0.1.0` фиксирует версию для людей; для продакшена дополнительно смотрят digest.

`docker history` покажет размеры шагов: если `COPY . .` огромный — в контекст попало лишнее (venv, node_modules, данные).

## Практическое применение

- Версионирование релизов: каждый деплой — новый тег образа.
- Multi-stage сборка: в одном Dockerfile собрать бинарник/статику, в финальный образ скопировать только артефакт.
- Политика безопасности: сканировать образы на уязвимости базовых пакетов.
- Экономия: общие базовые образы в организации, чтобы команды не тянули разные «самопальные» базы.

## Типичные ошибки

- Использовать только `latest` и не понимать, что пересборка через месяц даёт другой digest.
- Класть секреты в слои (`ENV PASSWORD=...` или `COPY .env`) — они остаются в истории образа.
- Копировать весь репозиторий без `.dockerignore` — раздутый контекст и утечка лишних файлов.
- Путать имя образа с именем контейнера: контейнер может называться иначе, чем образ.
- Думать, что правка файлов внутри запущенного контейнера меняет образ — меняется только writable-слой этого контейнера.

## Что запомнить

- Образ — шаблон файловой системы, не запущенный процесс.
- Слои read-only; неизменяемость даёт воспроизводимость и откат.
- Тег — указатель; digest — точная идентичность содержимого.
- Порядок инструкций Dockerfile влияет на кэш и скорость сборки.
- Образ — артефакт для передачи между машинами и средами.

## Задание

Соберите образ из примера (можно упростить до `FROM python:3.12-slim` + `CMD ["python", "--version"]`). Выполните `docker images` и `docker history`. Измените только код (или добавьте `RUN echo hi`) и пересоберите — отметьте, какие слои взялись из кэша. Запишите digest через `docker image inspect`.
