# Архитектура программного обеспечения робота

## Цель

Программа робота редко представляет собой один большой файл с функциями управления двигателями.

Даже небольшой робот постепенно получает:

* датчики;
* двигатели;
* контроллер;
* интерфейс связи;
* алгоритмы управления;
* диагностику;
* логику поведения;
* пользовательский интерфейс.

Если всё это смешать в одном месте, программу становится сложно изменять и отлаживать.

Поэтому программное обеспечение робота разделяют на уровни.

В этом уроке разберём:

* из каких частей состоит ПО робота;
* чем firmware отличается от прикладной программы;
* где находятся драйверы;
* где реализуется управление;
* как организовать обмен между компонентами;
* почему важны циклы управления;
* как построить простую архитектуру робота.

---

## Робот как несколько уровней

Упрощённо программную систему можно представить так:

```text
┌────────────────────────────┐
│     Логика поведения       │
├────────────────────────────┤
│       Управление           │
├────────────────────────────┤
│ Датчики / исполнительные   │
│ устройства                 │
├────────────────────────────┤
│      Драйверы              │
├────────────────────────────┤
│       Hardware             │
└────────────────────────────┘
```

Каждый уровень решает свою задачу.

---

## Hardware

Самый нижний уровень:

```text
моторы
энкодеры
датчики
GPIO
ADC
PWM
UART
SPI
I²C
```

Это физическое оборудование и интерфейсы контроллера.

Программа должна взаимодействовать с ним через понятные программные интерфейсы.

---

## Firmware

Firmware — программа, которая работает непосредственно на контроллере или микроконтроллере.

Она может:

* читать GPIO;
* запускать PWM;
* получать данные энкодеров;
* читать ADC;
* обмениваться по UART;
* управлять таймерами;
* контролировать watchdog.

Например:

```text
микроконтроллер
     ↓
firmware
     ↓
GPIO / PWM / ADC / UART
```

Firmware является связующим уровнем между программой и аппаратурой.

---

## Драйвер

Драйвер скрывает аппаратные детали.

Например, без драйвера программа могла бы работать с регистром:

```c
GPIOA->ODR |= (1 << 5);
```

Но прикладному коду не обязательно знать, какой именно регистр нужно изменить.

Можно предоставить интерфейс:

```cpp
led.set(true);
```

Тогда структура получается:

```text
Application
     ↓
LED driver
     ↓
GPIO
     ↓
Hardware
```

Это упрощает разработку.

---

## Слой датчиков

Можно создать отдельные компоненты:

```text
Encoder
TemperatureSensor
DistanceSensor
IMU
Camera
```

Например:

```cpp
double speed = encoder.getSpeed();
```

Вместо того чтобы вся программа знала:

* номер таймера;
* количество импульсов;
* коэффициент пересчёта;
* частоту измерения.

---

## Слой исполнительных устройств

Аналогично можно скрыть детали управления приводами.

Например:

```cpp
motor.setSpeed(0.5);
```

А внутри:

```text
скорость
 ↓
ограничение
 ↓
регулятор
 ↓
PWM
 ↓
драйвер
 ↓
мотор
```

Приложение работает с понятной абстракцией.

---

## Слой управления

Этот уровень отвечает за физический процесс.

Например:

```text
заданная скорость
       ↓
     ошибка
       ↓
     PID
       ↓
    команда
       ↓
    двигатель
```

Здесь находятся:

* PID;
* ограничители;
* регуляторы положения;
* регуляторы скорости;
* алгоритмы стабилизации.

---

## Слой поведения

Выше находится логика:

```text
IDLE
MOVING
GRIPPING
DELIVERING
ERROR
```

Она решает:

> что робот должен делать сейчас?

Но не обязательно знает, каким именно PWM управляется двигатель.

Например:

```cpp
robot.moveTo(1000, 500);
```

А ниже уже работают алгоритмы движения.

---

## Коммуникационный слой

Роботу часто нужно обмениваться данными с другими системами:

```text
PLC
ПК
сервер
другой робот
датчик
панель оператора
```

Для этого используются:

```text
UART
CAN
Ethernet
TCP/IP
UDP
Modbus
MQTT
OPC UA
```

Коммуникационный слой должен скрывать детали конкретного протокола от остальной программы.

Например:

```cpp
robot.receiveCommand();
```

вместо того чтобы логика робота занималась разбором байтов TCP-пакета.

---

## Диагностика

Отдельный слой отвечает за информацию о состоянии системы:

```text
температура
напряжение
ошибки датчиков
состояние связи
ошибки двигателя
watchdog
время цикла
```

Например:

```text
SYSTEM OK

Motor 1: OK
Motor 2: OK
Encoder: OK
Battery: 24.1 V
Communication: OK
Watchdog: OK
```

Диагностика особенно важна, когда робот работает без постоянного присутствия разработчика.

---

## Типичная архитектура

Для небольшого робота можно использовать такую структуру:

```text
                APPLICATION
                     │
                     ↓
              BEHAVIOR / FSM
                     │
                     ↓
                 CONTROL
              ┌──────┴──────┐
              ↓             ↓
           SENSORS       ACTUATORS
              │             │
              └──────┬──────┘
                     ↓
                  DRIVERS
                     │
                     ↓
                  HARDWARE
```

Отдельно:

```text
COMMUNICATION
DIAGNOSTICS
CONFIGURATION
LOGGING
```

---

## Почему нельзя всё смешивать

Представим функцию:

```cpp
void robot()
{
    readEncoder();

    if (sensor)
    {
        pwm = 120;
    }

    sendTcpPacket();

    if (button)
    {
        motor = 0;
    }
}
```

Пока система маленькая, это может работать.

Но затем появляется:

* второй двигатель;
* PID;
* энкодер;
* камера;
* сеть;
* ошибки;
* аварийная остановка.

Функция начинает превращаться в огромный блок.

Изменение одной части может случайно сломать другую.

---

## Разделение ответственности

Хороший принцип:

> каждый компонент должен отвечать за одну понятную область.

Например:

```text
Motor
```

отвечает за двигатель.

```text
Encoder
```

отвечает за измерение скорости и положения.

```text
PIDController
```

отвечает за регулирование.

```text
Navigator
```

отвечает за навигацию.

```text
RobotStateMachine
```

отвечает за состояние робота.

```text
Communication
```

отвечает за обмен.

---

## Цикл управления

Роботу часто нужно выполнять действия периодически.

Например:

```text
каждые 10 мс:
    прочитать энкодеры
    вычислить скорость
    выполнить PID
    обновить PWM
```

Это цикл управления с периодом:

```text
T = 10 мс
```

или частотой:

```text
f = 1 / T = 100 Гц
```

---

## Более медленные задачи

Не все задачи должны выполняться с такой же частотой.

Например:

```text
1 кГц  → быстрый контур управления
100 Гц → состояние датчиков
10 Гц  → навигация
1 Гц   → диагностика
```

Это позволяет не тратить вычислительные ресурсы на задачи, которым высокая частота не нужна.

---

## Пример архитектуры

Допустим, есть мобильный робот.

### Быстрый цикл

```text
энкодеры
   ↓
скорость колёс
   ↓
PID
   ↓
PWM
```

### Средний цикл

```text
датчики
   ↓
оценка движения
   ↓
команда скорости
```

### Медленный цикл

```text
диагностика
   ↓
температура
   ↓
напряжение
   ↓
состояние связи
```

### Логика

```text
FSM
 ↓
команда движения
```

Получается несколько уровней, работающих с разной периодичностью.

---

## Обмен данными

Компоненты должны обмениваться данными.

Например:

```text
Encoder
   ↓
WheelController
   ↓
Motor
```

Можно использовать простые структуры данных.

Например:

```cpp
struct WheelState
{
    double position;
    double speed;
    bool valid;
};
```

Теперь один компонент может передать другому:

```cpp
WheelState state;
```

Вместо десятков отдельных переменных.

---

## Конфигурация

Настройки не стоит зашивать во все части программы.

Например:

```text
max_speed
wheel_diameter
pid_kp
pid_ki
pid_kd
timeout
```

Лучше хранить их централизованно:

```cpp
struct RobotConfig
{
    double max_speed;
    double wheel_diameter;

    double pid_kp;
    double pid_ki;
    double pid_kd;
};
```

Тогда параметры можно менять без переписывания логики.

---

## Ошибки

Ошибки также должны иметь понятную модель.

Например:

```cpp
enum class ErrorCode
{
    None,
    EncoderFailure,
    MotorFailure,
    CommunicationTimeout,
    LowVoltage,
    EmergencyStop
};
```

Теперь система может передавать не просто:

```text
error = true
```

а конкретную причину.

---

## Логирование

Во время разработки полезно записывать:

```text
10:32:01 Robot started
10:32:02 Moving to target
10:32:04 Target reached
10:32:05 Gripper closed
10:32:06 Error: encoder timeout
```

Это помогает восстановить последовательность событий.

Но логирование не должно мешать основному циклу управления.

Особенно важно не выполнять тяжёлые операции записи внутри самого быстрого контура.

---

## Пример структуры проекта

Программный проект робота может выглядеть так:

```text
robot/
├── drivers/
│   ├── motor.cpp
│   ├── encoder.cpp
│   └── sensor.cpp
│
├── control/
│   ├── pid.cpp
│   └── motion.cpp
│
├── behavior/
│   └── state_machine.cpp
│
├── communication/
│   └── protocol.cpp
│
├── diagnostics/
│   └── diagnostics.cpp
│
├── config/
│   └── config.cpp
│
└── main.cpp
```

Это не единственно правильная структура.

Но она показывает принцип разделения.

## Пример прохождения команды

Допустим, оператор отправляет:

```text
MOVE_FORWARD
```

Команда приходит через сеть:

```text
Communication
      ↓
Command parser
      ↓
Behavior
      ↓
Motion controller
      ↓
PID
      ↓
Motor driver
      ↓
PWM
      ↓
Motor
```

Обратный путь:

```text
Encoder
   ↓
Driver
   ↓
Control
   ↓
Robot state
   ↓
Diagnostics
   ↓
Communication
   ↓
Operator
```

---

## Главный принцип архитектуры

Хорошая архитектура позволяет менять одну часть системы с минимальным воздействием на остальные.

Например, сегодня используется:

```text
UART
```

а завтра:

```text
Ethernet
```

Если логика робота напрямую работает с UART, изменение будет сложным.

Если есть абстракция:

```text
Communication
```

то можно заменить реализацию:

```text
UART communication
        ↓
Ethernet communication
```

а остальная программа продолжит использовать тот же интерфейс.

---

## Что важно запомнить

Программное обеспечение робота удобно разделять на уровни:

```text
Hardware
   ↓
Drivers
   ↓
Sensors / Actuators
   ↓
Control
   ↓
Behavior
   ↓
Application
```

Дополнительно существуют:

```text
Communication
Diagnostics
Configuration
Logging
```

Главная идея:

> логика поведения не должна знать лишние аппаратные детали, а аппаратные драйверы не должны решать, куда робот должен ехать.

Так система становится понятнее и масштабируется от простого микроконтроллера до сложного робота.
