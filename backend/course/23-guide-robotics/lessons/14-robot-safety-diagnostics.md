# Безопасность, диагностика и отказоустойчивость

## Цель

Робот работает с физическим миром. Он может двигаться, вращать механизмы, перемещать грузы, нагреваться и создавать значительные усилия.

Поэтому программа робота должна учитывать не только нормальную работу, но и ситуации, когда что-то пошло не так.

В этом уроке разберём:

* что означает безопасное состояние;
* зачем нужна аварийная остановка;
* что делать при потере датчика;
* зачем нужен watchdog;
* как контролировать питание и температуру;
* как обнаруживать потерю связи;
* почему ошибка должна приводить к предсказуемому поведению;
* как строится диагностика робота.

---

## Нормальная работа — не единственный сценарий

Очень простая программа может выглядеть так:

```text
получить команду
     ↓
двигаться
     ↓
достичь цели
     ↓
остановиться
```

Но реальный робот может столкнуться с проблемами:

```text
датчик перестал отвечать
двигатель перегрелся
пропала связь
напряжение стало низким
энкодер перестал изменяться
камера перестала выдавать кадры
оператор нажал аварийную кнопку
```

Робот должен иметь заранее определённое поведение для таких ситуаций.

---

## Что такое безопасное состояние

Безопасное состояние — это состояние, в котором при возникновении определённой неисправности система не продолжает опасное действие.

Например, для небольшого мобильного робота это может означать:

```text
скорость = 0
двигатели отключены
```

Для манипулятора:

```text
движение остановлено
приводы переведены в безопасный режим
```

Конкретное безопасное состояние зависит от устройства.

Главный принцип:

> при опасной или неопределённой ситуации робот должен переходить в заранее определённый режим, а не продолжать работу вслепую.

---

## Аварийная остановка

Аварийная остановка должна быть максимально предсказуемой.

Упрощённая схема:

```text
E-STOP
   ↓
остановка опасного движения
   ↓
фиксация аварийного состояния
   ↓
диагностика
```

Важно отличать:

```text
обычная остановка
```

и:

```text
аварийная остановка
```

Обычная остановка является частью нормального алгоритма.

Аварийная остановка возникает при опасной или критической ситуации.

---

## Почему нельзя полагаться только на программу

Если программа зависла, программная команда:

```text
stop_motor()
```

может вообще не выполниться.

Поэтому критически важные защитные функции часто должны иметь независимый аппаратный или специально выделенный безопасный путь.

Например:

```text
аварийная кнопка
      ↓
цепь безопасности
      ↓
отключение силовой части
```

а не только:

```text
аварийная кнопка
      ↓
if emergency:
    stop_motor()
```

Программная диагностика остаётся полезной, но не должна автоматически считаться единственным средством защиты.

---

## Контроль датчиков

Представим энкодер.

В нормальном режиме:

```text
1000
1010
1020
1030
1040
```

Значение меняется.

Но если двигатель вращается, а энкодер постоянно показывает:

```text
1000
1000
1000
1000
```

это может означать неисправность.

Однако просто отсутствие изменения ещё не всегда является ошибкой.

Если двигатель действительно остановлен, значение и должно оставаться постоянным.

Поэтому проверка должна учитывать контекст:

```text
команда движения есть
+
движения нет
+
в течение заданного времени
=
возможная ошибка
```

## Timeout

Timeout — ограничение времени ожидания.

Например:

```text
отправили команду
       ↓
ждём ответ
       ↓
если ответа нет 1 секунду
       ↓
TIMEOUT
```

Без timeout программа может ждать бесконечно.

Например:

```python
while not response:
    pass
```

Это плохая идея для управляющей системы.

Лучше:

```python
start = time.monotonic()

while not response:
    if time.monotonic() - start > timeout:
        raise TimeoutError()
```

## Watchdog

Watchdog следит за тем, что система продолжает работать.

Представим программу:

```text
работает
работает
работает
зависла
```

Если watchdog регулярно получает сигнал:

```text
tick
tick
tick
```

а затем сигналы прекращаются:

```text
tick
tick
tick
...
```

он может определить зависание.

В зависимости от архитектуры watchdog может:

* перезапустить контроллер;
* перевести систему в безопасное состояние;
* отключить определённую функцию;
* сформировать ошибку.

---

## Программный watchdog

Можно иметь несколько уровней контроля.

Например:

```text
main loop
    ↓
heartbeat
    ↓
watchdog
```

Или отдельные heartbeat:

```text
navigation heartbeat
control heartbeat
communication heartbeat
```

Это помогает определить, какая часть системы перестала работать.

---

## Потеря связи

Робот может получать команды от компьютера.

Например:

```text
PC → робот
```

Что произойдёт, если Ethernet отключится?

Плохой вариант:

```text
последняя команда:
скорость = 50%
```

и робот продолжает двигаться.

Более безопасная логика:

```text
есть связь
    ↓
робот работает

нет связи
    ↓
таймер timeout
    ↓
остановка
    ↓
ERROR / SAFE
```

---

## Проверка питания

Напряжение также является диагностическим параметром.

Например:

```text
24.1 V → нормально
23.5 V → нормально
22.0 V → предупреждение
20.5 V → критическое состояние
```

Конкретные пороги зависят от оборудования.

При низком напряжении могут возникнуть:

* сбои контроллера;
* ошибки приводов;
* неправильная работа датчиков;
* перезапуски;
* потеря связи.

---

## Температура

Аналогично контролируется температура.

Например:

```text
температура двигателя
температура контроллера
температура батареи
```

Можно использовать уровни:

```text
NORMAL
WARNING
CRITICAL
```

Например:

```text
NORMAL
    ↓
температура растёт
    ↓
WARNING
    ↓
температура продолжает расти
    ↓
CRITICAL
```

При критическом значении система должна выполнить заранее определённое действие.

---

## Диагностика должна отвечать на вопрос «что произошло?»

Просто:

```text
ERROR = true
```

мало полезно.

Лучше:

```text
Error:
Motor 2
Encoder timeout
Duration: 850 ms
```

Или:

```text
Code: E102
Subsystem: Communication
Reason: Response timeout
```

Это позволяет быстрее находить неисправности.

---

## Уровни состояния

Можно использовать:

```text
OK
WARNING
ERROR
CRITICAL
```

Например:

```text
Battery: OK
Motor 1: OK
Motor 2: WARNING
Encoder: OK
Communication: OK
```

Если двигатель перегревается:

```text
Motor 2: CRITICAL
```

---

## Журнал событий

Роботу полезно хранить журнал:

```text
12:31:04 SYSTEM START
12:31:05 MOTORS ENABLED
12:31:12 TARGET RECEIVED
12:31:15 MOVEMENT START
12:31:18 TARGET REACHED
12:31:19 COMMUNICATION TIMEOUT
12:31:19 SAFE STOP
```

Такой журнал помогает понять последовательность событий.

Особенно полезно сохранять:

* время;
* код ошибки;
* подсистему;
* состояние робота;
* важные измерения.

---

## Отказоустойчивость

Отказоустойчивость — способность системы корректно переживать неисправности или переходить в безопасное состояние при их возникновении.

Например:

```text
датчик расстояния отказал
        ↓
робот обнаружил неисправность
        ↓
остановился
        ↓
сообщил ошибку
```

Это лучше, чем:

```text
датчик отказал
        ↓
программа получила мусор
        ↓
робот продолжил движение
```

---

## Принцип fail-safe

Один из важных подходов:

> при неопределённости система должна выбирать заранее определённое безопасное поведение.

Например:

```text
нет подтверждения → не запускать
нет данных датчика → остановиться
нет связи → перейти в безопасное состояние
неизвестное состояние → ошибка
```

Это не означает, что абсолютно любая ошибка требует полной остановки.

Действие зависит от системы.

Но решение должно быть заранее предусмотрено.

---

## Диагностика как отдельная система

Можно создать компонент:

```text
Diagnostics
```

который получает информацию от разных подсистем:

```text
Motor
Encoder
Battery
Communication
Sensors
Controller
```

и формирует единое состояние:

```text
Robot Health
```

Например:

```text
Robot Health

System: OK
Motors: OK
Sensors: OK
Battery: WARNING
Communication: OK
```

## Пример проверки

Упрощённый Python-код:

```python
def check_robot():
    errors = []

    if not encoder_ok:
        errors.append("Encoder failure")

    if not communication_ok:
        errors.append("Communication timeout")

    if battery_voltage < 20:
        errors.append("Low voltage")

    if motor_temperature > 80:
        errors.append("Motor overtemperature")

    return errors
```

Затем:

```python
errors = check_robot()

if errors:
    stop_robot()
```

В реальной системе архитектура будет сложнее, но идея остаётся такой же.

## Ошибка не должна исчезать бесследно

Допустим, датчик временно перестал отвечать.

Плохая система:

```text
ошибка
↓
датчик снова заработал
↓
ошибка полностью потеряна
```

Лучше хранить:

```text
current error
```

и:

```text
event history
```

То есть система может показывать:

```text
Сейчас ошибок нет.

Последняя ошибка:
Encoder timeout
12:41:22
```

---

## Восстановление

После ошибки не всегда нужно просто включить всё обратно.

Например:

```text
ERROR
  ↓
проверка причины
  ↓
сброс ошибки
  ↓
инициализация
  ↓
проверка датчиков
  ↓
READY
```

Получается отдельное состояние:

```text
RECOVERY
```

Это гораздо безопаснее, чем:

```text
ERROR → MOVING
```

---

## Пример полного сценария

Мобильный робот движется:

```text
MOVING
```

Связь с компьютером пропала.

```text
MOVING
   ↓
нет сообщений
   ↓
timeout
   ↓
SAFE_STOP
```

После этого:

```text
SAFE_STOP
   ↓
запись ошибки
   ↓
ожидание связи
```

Связь восстановилась:

```text
WAITING
   ↓
проверка системы
   ↓
READY
```

И только после новой команды:

```text
READY
   ↓
MOVING
```

---

## Что важно запомнить

Безопасность робота — это не одна кнопка и не одна проверка.

Это совокупность механизмов:

```text
аварийная остановка
датчики
timeout
watchdog
контроль питания
контроль температуры
контроль связи
диагностика
журналирование
безопасные состояния
восстановление
```

Главный принцип:

> неисправность должна приводить не к неопределённому поведению, а к заранее предусмотренному сценарию.
