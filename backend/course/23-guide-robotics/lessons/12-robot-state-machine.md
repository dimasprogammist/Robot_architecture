# Состояния и логика поведения робота

## Цель

Робот не должен просто выполнять последовательность команд. В реальной системе он постоянно реагирует на события:

* оператор нажал кнопку;
* появилась деталь;
* робот достиг точки;
* закончился заряд;
* пропала связь;
* сработал датчик;
* возникла ошибка;
* операция завершилась.

Для организации такого поведения используется понятие **состояния**.

В этом уроке разберём:

* что такое состояние робота;
* зачем нужна конечная машина состояний;
* как описывать переходы;
* почему один большой набор `if` быстро становится сложным;
* как организовать запуск, движение, остановку и ошибки;
* как состояния помогают сделать программу предсказуемой.

---

## Что такое состояние

Состояние описывает, **что робот делает сейчас и по каким правилам должен себя вести**.

Например:

```text
IDLE
```

означает:

> робот находится в ожидании и ничего не выполняет.

Другие состояния:

```text
STARTING
MOVING
WORKING
STOPPING
ERROR
RECOVERY
```

В каждом состоянии программа выполняет свою логику.

---

## Пример

Рассмотрим мобильного робота.

Он может находиться в состояниях:

```text
IDLE
  ↓
STARTING
  ↓
MOVING
  ↓
WORKING
  ↓
IDLE
```

Но возможны и ошибки:

```text
MOVING
   ↓
ERROR
   ↓
RECOVERY
   ↓
IDLE
```

Таким образом, поведение робота можно представить как граф.

---

## Конечный автомат

Такую систему называют **конечной машиной состояний**, или FSM — Finite State Machine.

Она состоит из:

* набора состояний;
* событий;
* переходов;
* действий.

Например:

```text
             start
 IDLE ─────────────────→ STARTING
  ↑                         │
  │                         │ ready
  │                         ↓
  │                      MOVING
  │                         │
  │                         │ target reached
  │                         ↓
  └────────────────────── WORKING
```

При этом состояние меняется не случайно.

Для каждого перехода существует условие.

---

## Почему нельзя просто написать много if

Для маленькой программы можно сделать:

```python
if start:
    start_motor()

if sensor:
    stop_motor()

if error:
    emergency_stop()
```

Но по мере роста программы количество условий увеличивается:

```text
если старт...
если не старт...
если ошибка...
если датчик...
если двигатель...
если связь...
если оператор...
если заряд...
если цель...
```

Через некоторое время становится трудно понять:

* что робот делает сейчас;
* почему двигатель включился;
* какое условие изменило режим;
* можно ли выполнять конкретную команду.

Состояния позволяют явно описать текущий режим работы.

---

## Простая реализация

Например:

```python
state = "IDLE"

while True:
    if state == "IDLE":
        if start_button:
            state = "STARTING"

    elif state == "STARTING":
        enable_motors()
        state = "MOVING"

    elif state == "MOVING":
        move_robot()

        if target_reached:
            state = "STOPPING"

    elif state == "STOPPING":
        stop_robot()
        state = "IDLE"

    elif state == "ERROR":
        stop_robot()
```

Теперь поведение программы читается гораздо проще.

---

## Событие и состояние — разные вещи

Это важное различие.

**Состояние**:

```text
MOVING
```

**Событие**:

```text
target_reached
```

Событие может вызвать переход:

```text
MOVING
   +
target_reached
   ↓
STOPPING
```

То есть:

```text
состояние = где мы сейчас
событие = что произошло
переход = что делать после события
```

---

## Пример робота-манипулятора

Допустим, робот должен взять деталь.

Последовательность:

```text
IDLE
 ↓
MOVE_TO_PICK
 ↓
GRIP
 ↓
CHECK_GRIP
 ↓
MOVE_TO_PLACE
 ↓
RELEASE
 ↓
IDLE
```

Если деталь не захвачена:

```text
CHECK_GRIP
     ↓
  ошибка
     ↓
   ERROR
```

Если во время движения сработал аварийный сигнал:

```text
любое состояние
       ↓
    EMERGENCY
```

Это уже значительно ближе к реальному поведению робота.

---

## Состояние должно иметь чёткий смысл

Хорошее состояние отвечает на вопрос:

> Что сейчас делает система?

Например:

```text
WAITING_FOR_PART
```

понятно.

А состояние:

```text
STEP_7
```

ничего не говорит человеку, который читает программу.

Лучше использовать названия:

```text
IDLE
STARTING
MOVING_TO_PICK
GRIPPING
MOVING_TO_PLACE
RELEASING
ERROR
```

---

## Вход и выход из состояния

Иногда у состояния есть действия, которые нужно выполнить только один раз.

Например, при входе в:

```text
MOVING
```

нужно запустить движение.

Но если написать:

```python
while state == "MOVING":
    start_motion()
```

команда будет выполняться постоянно.

Можно разделить:

```text
on_enter
on_update
on_exit
```

Например:

```text
ENTER MOVING
    ↓
запустить движение

UPDATE MOVING
    ↓
проверять датчики

EXIT MOVING
    ↓
остановить или передать управление
```

---

## Пример структуры

```python
class RobotController:
    def __init__(self):
        self.state = "IDLE"

    def update(self):
        if self.state == "IDLE":
            self.update_idle()

        elif self.state == "MOVING":
            self.update_moving()

        elif self.state == "ERROR":
            self.update_error()
```

В большом проекте состояния можно сделать отдельными классами.

Но для небольшого контроллера обычного перечисления состояний часто достаточно.

---

## Безопасные переходы

Не каждый переход должен быть разрешён.

Например:

```text
IDLE → MOVING
```

может быть разрешён.

Но:

```text
ERROR → MOVING
```

без процедуры восстановления может быть запрещён.

Получается граф допустимых переходов:

```text
IDLE
 ↓
STARTING
 ↓
MOVING
 ↓
STOPPING
 ↓
IDLE
```

При ошибке:

```text
любое состояние → ERROR
```

А из `ERROR`:

```text
ERROR → RECOVERY
RECOVERY → IDLE
```

Только после проверки системы.

---

## Аварийное состояние

Аварийное состояние должно быть особенным.

Например:

```text
EMERGENCY
```

При его активации:

```text
остановить движение
отключить опасные приводы
зафиксировать ошибку
записать событие
```

После этого робот не должен автоматически продолжать работу только потому, что сигнал ошибки исчез.

Часто требуется явное подтверждение оператора или отдельная процедура восстановления.

---

## Watchdog и состояния

В роботах часто используется watchdog.

Например, контроллер ожидает обновление от другого устройства.

Если обновлений нет:

```text
NORMAL
   ↓
нет связи
   ↓
TIMEOUT
   ↓
ERROR
```

Таким образом, состояние становится частью системы отказоустойчивости.

---

## Пример полного цикла

Рассмотрим робота, который доставляет деталь.

```text
IDLE
```

Ждём команду.

После команды:

```text
STARTING
```

Проверяем:

* питание;
* датчики;
* приводы;
* связь.

Если всё хорошо:

```text
MOVING_TO_PICK
```

После достижения точки:

```text
GRIPPING
```

Проверяем захват:

```text
если деталь захвачена
    → MOVING_TO_PLACE

если нет
    → ERROR
```

После доставки:

```text
RELEASING
```

После освобождения:

```text
RETURNING
```

После возврата:

```text
IDLE
```

---

## Почему FSM полезна в робототехнике

Конечная машина состояний позволяет отделить:

```text
что робот делает
```

от:

```text
при каком условии он должен перейти дальше
```

Это особенно полезно для:

* мобильных роботов;
* манипуляторов;
* станков;
* автоматических тележек;
* дронов;
* небольших автономных устройств;
* автоматизированных установок.

---

## Практический пример

Представим робота:

```text
камера → обнаруживает деталь
энкодеры → определяют движение
датчик захвата → проверяет захват
```

Состояния:

```text
IDLE
SEARCH
APPROACH
GRIP
CHECK
DELIVER
ERROR
```

Логика:

```text
IDLE
 ↓ команда
SEARCH
 ↓ деталь найдена
APPROACH
 ↓ достигнута позиция
GRIP
 ↓
CHECK
 ├── захвачена → DELIVER
 └── не захвачена → ERROR
```

Такой граф гораздо проще проверять, тестировать и отлаживать, чем десятки независимых условий.

---

## Состояния не заменяют управление

Важно не смешивать уровни.

Например:

```text
FSM
```

может решить:

> робот должен двигаться вперёд.

Но сама FSM не обязана рассчитывать ток двигателя.

Это может делать другой уровень:

```text
FSM
 ↓
команда скорости
 ↓
регулятор
 ↓
PWM
 ↓
драйвер
 ↓
двигатель
```

То есть состояния отвечают за **логику поведения**, а контроллеры — за **управление физическим процессом**.

---

## Что важно запомнить

Состояние описывает текущий режим работы робота.

Событие сообщает, что произошло.

Переход определяет, какое состояние должно быть следующим.

В простейшем виде:

```text
STATE
  +
EVENT
  ↓
TRANSITION
  ↓
NEW STATE
```

Конечная машина состояний помогает сделать поведение робота:

* понятным;
* предсказуемым;
* тестируемым;
* расширяемым;
* безопасным.
