# JavaScript в браузере

## Цель

Понять, зачем в странице запускается JavaScript и чем браузерный JS отличается от скрипта на сервере. После урока вы подключите скрипт к панели заказов, объявите функции и измените текст на странице по действию пользователя — без перезагрузки.

## Что уже нужно понимать

HTML даёт структуру, CSS — вид. JavaScript вы уже встречали как язык: переменные, функции, массивы, объекты, условия. Здесь тот же язык, но среда другая: вместо файла на диске и терминала у вас есть **окно браузера**, документ страницы и события пользователя. Серверный Python/FastAPI по-прежнему отвечает за данные и правила; браузерный JS — за реакцию интерфейса.

## Объяснение

Без JS страница либо статична, либо каждый клик уходит полной перезагрузкой через форму. Для панели заказов это неудобно: оператор хочет отметить «упаковывается», увидеть новый статус сразу и не потерять прокрутку списка. JavaScript как раз умеет: найти элемент, поменять его содержимое или класс, послать запрос на сервер в фоне, обработать ответ.

Скрипт подключают тегом `<script src="app.js"></script>`. Положение важно: если скрипт в `head` без `defer`/`async`, он может выполниться до того, как `body` построен, и поиск элементов вернёт `null`. Практичный путь для учебных страниц — ставить `<script src="..." defer></script>` в `head` или подключать скрипт в конце `body`.

В браузере есть глобальные объекты: `window` (окно), `document` (текущий HTML как объектная модель), `console` (отладочный вывод). Ваш код делит страницу с расширениями и другими скриптами, поэтому засорять глобальную область десятками переменных — плохая привычка. Оборачивайте логику в функции и модули (о модулях позже на уровне bundler/React; пока достаточно функций и одного объекта-приложения).

JS в браузере однопоточен в основном смысле: долгий цикл `while (true)` заморозит и клики, и отрисовку. Поэтому тяжёлую работу не пихают в обработчик клика «в лоб», а сетевые операции делают асинхронно (`fetch` + `await` — в уроках про HTTP).

## Термины

- **Среда выполнения** — здесь движок JS внутри браузера + Web API.
- **Web API** — объекты вроде `document`, `fetch`, `localStorage`, которых нет в «голом» языке.
- **defer** — отложить выполнение внешнего скрипта до разбора HTML, сохранив порядок.
- **Консоль** — панель разработчика для логов и ошибок.

## Как это устроено

Движок читает ваш JS, компилирует/интерпретирует и выполняет. Когда скрипт обращается к `document.getElementById('orders')`, он идёт не в файл `.html` на диске, а в **уже построенное** дерево документа в памяти. Поэтому порядок «сначала HTML, потом поиск узлов» критичен.

Типичный учебный цикл панели: 1) найти контейнер списка; 2) описать функцию отрисовки массива заказов в HTML; 3) повесить обработчик на кнопку; 4) обновить массив и перерисовать. Пока данные могут жить в обычном массиве объектов в памяти вкладки — это ещё не «настоящий state-менеджмент», но уже модель интерфейса.

Отладка начинается с `console.log` и панели Sources/Console. Ошибка `Cannot read properties of null` почти всегда значит: элемент не найден — неверный id или скрипт сработал слишком рано. Привыкайте читать стек ошибки: файл, строка, что вызывалось.

## Пример

```html
<!DOCTYPE html>
<html lang="ru">
<head>
  <meta charset="UTF-8" />
  <title>Orders Desk</title>
  <script src="app.js" defer></script>
</head>
<body>
  <h1>Заказы</h1>
  <ul id="orders"></ul>
  <button id="add-demo" type="button">Добавить демо-заказ</button>
</body>
</html>
```

```javascript
// app.js
const orders = [
  { id: 101, title: "Упаковка", status: "new" },
  { id: 102, title: "Доставка", status: "packing" },
];

function renderOrders() {
  const root = document.getElementById("orders");
  root.innerHTML = "";
  for (const order of orders) {
    const li = document.createElement("li");
    li.textContent = `#${order.id} — ${order.title} — ${order.status}`;
    root.appendChild(li);
  }
}

function addDemoOrder() {
  const nextId = orders.length ? orders[orders.length - 1].id + 1 : 1;
  orders.push({ id: nextId, title: "Демо", status: "new" });
  renderOrders();
}

document.getElementById("add-demo").addEventListener("click", addDemoOrder);
renderOrders();
```

## Разбор примера

`defer` гарантирует: к моменту выполнения `app.js` элементы `orders` и `add-demo` уже в дереве. Массив `orders` — источник правды для списка в этой вкладке; HTML списка не хранит отдельную «истину», а строится функцией `renderOrders`.

Мы не конкатенируем гигантскую строку HTML вручную в цикле с риском XSS из пользовательского ввода: здесь данные учебные и мы ставим `textContent`, что безопасно экранирует текст. Кнопка имеет `type="button"`, чтобы случайно не вести себя как submit формы.

Обработчик клика меняет данные и вызывает отрисовку снова. Это зачаток идеи, которая в React станет декларативным рендером: UI — функция от состояния.

## Типичные ошибки

- Подключить скрипт в `head` без `defer` и удивляться `null`.
- Путать серверный JS (Node) с браузерным: `fs` в браузере нет, `document` на сервере нет.
- Блокировать вкладку тяжёлым синхронным кодом.
- Писать бизнес-правила только на клиенте («скидку посчитал в JS») и верить этому на сервере.
- Оставлять пароли и секреты в фронтенд-коде — его видит кто угодно.

## Что запомнить

Браузерный JavaScript оживляет страницу через Web API. Скрипт работает с документом в памяти. Данные интерфейса удобно держать в структурах JS и отрисовывать в DOM. Порядок загрузки скрипта важен. Клиент дополняет сервер, а не заменяет проверку правил.

## Задание

Сделайте страницу телеметрии: массив из 3 измерений, функция отрисовки в `<ul>`, кнопка «Случайное значение» добавляет новый пункт. Выведите в консоль длину массива после каждого добавления. Подключите скрипт через `defer`.
