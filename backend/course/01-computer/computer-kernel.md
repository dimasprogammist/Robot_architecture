# Пользовательское пространство и ядро

## Цель

Разделить user space и kernel space: зачем процессор имеет режимы привилегий, что можно делать приложению, что только ядру, и как системный вызов пересекает эту границу безопасно.

## Что уже нужно понимать

ОС стоит между программой и железом. Процессы изолированы. Запрос услуг идёт через системные вызовы.

## Объяснение

Современные CPU умеют работать в разных **уровнях привилегий**. Упрощённо для курса: **пользовательский режим** и **режим ядра**. В пользовательском режиме запрещены опасные инструкции: произвольный доступ к страницам чужой памяти, управление некоторыми регистрами системной конфигурации, прямой in/out к портам (где это применимо). В режиме ядра код ОС может настраивать таблицы страниц, общаться с устройствами, останавливать прерывания на короткое время.

**Пользовательское пространство (user space)** — память и код процессов приложений. **Пространство ядра (kernel space)** — код ядра, драйверов, структур учёта. Приложение не должно произвольно читать/писать память ядра: это дыра безопасности и стабильности.

Переход user→kernel происходит контролируемо: системный вызов, исключение (fault), прерывание. Аппаратура сохраняет состояние, повышает привилегии, передаёт управление обработчику ядра. После работы ядро возвращает результат и понижает привилегии обратно.

Почему не держать всё в одном режиме? Исторические системы так жили и были хрупкими. Разделение даёт шанс пережить падение приложения. Падение ядра обычно роняет всю машину (panic/BSOD) — поэтому драйверы особенно критичны.

Микроядра выносят часть сервисов в user space; монолитные ядра (как Linux) держат много подсистем в kernel space ради производительности. Идея границы режимов остаётся.

## Термины

- **User space** — пространство пользовательских процессов.
- **Kernel space** — пространство ядра.
- **Системный вызов** — согласованный вход в ядро.
- **Trap / exception** — внутреннее событие CPU (деление на ноль, page fault).
- **Interrupt** — внешнее прерывание устройства.
- **Page fault** — обращение к странице, требующее реакции ядра (подгрузка, отказ).
- **Ring / privilege level** — уровень привилегий архитектуры.

## Как это устроено

Таблица системных вызовов — каталог услуг. Библиотека C (`read`, `write`, `mmap`…) готовит номера и аргументы и выполняет инструкцию перехода. Ядро валидирует указатели: нельзя передать адрес ядра как буфер пользователя без проверок copy_to_user/copy_from_user.

Виртуальная память усиливает стену: у процесса своя карта; страницы ядра обычно недоступны из user mode. При page fault ядро решает: выделить физическую страницу, подгрузить с диска, послать сигнал (SIGSEGV) процессу.

Драйвер в ядре работает с высокими привилегиями. Ошибка в драйвере опаснее ошибки в приложении. Отсюда движение к user-space драйверам где возможно, песочницам, подписи модулей.

Отладка: «segfault в моём коде» — user space. «kernel oops» — уже ядро. Путать уровни бесполезно для лечения.

## Пример

Программа делает `ptr = NULL; *ptr = 1;`. CPU генерирует page fault. Ядро видит, что это не легитимная потребность в новой странице, а ошибка доступа. Процессу доставляется сигнал segmentation fault; процесс падает. Ядро живо, другие процессы продолжают работать — именно благодаря границе.

Другой пример: `open("/etc/shadow")` от обычного пользователя. Syscall входит в ядро; проверка прав отказывает; errno = EACCES; программа получает ошибку, а не содержимое файла. Стена привилегий сработала на политике ОС.

## Типичные ошибки

- Считать, что root в user space «равен ядру». Root — мощный пользователь, но всё ещё через syscalls (хотя может грузить модули и т.д.).
- Писать в учебном коде «ядро Linux = весь дистрибутив». Дистрибутив = ядро + user space.
- Ловить все сбои как «Windows/Linux виноват», когда падает ваше приложение.
- Передавать в syscall указатели без проверки длины буфера — классика уязвимостей на границе.
- Грузить сомнительные модули ядра «чтобы заработало устройство».

## Что запомнить

User space ограничен; kernel space привилегирован. Переходы только через контролируемые события. Стабильность системы строится на этой стене. Падение процесса ≠ падение ядра. Понимание границы нужно для безопасности, отладки и разговора с драйверами.

## Задание

Приведите два своих примера событий: одно обрабатывается целиком в user space (чистое вычисление), одно требует входа в ядро. Для второго назовите вероятный класс syscall (файлы, сеть, память, процессы).

## Практика и нюансы

Разберите последний свой segfault или access violation: это был user space. Сравните мысленно с ситуацией kernel panic — система бы не предложила просто «перезапустить одно приложение».

Почитайте (обзорно) список syscalls вашей ОС или документацию по `/proc`. Вы увидите каталог услуг, которые ядро считает своими: не «все функции Python», а именно привилегированные операции.

При работе с устройствами через `/dev` помните: файл в user space — лишь дверь; за ней драйвер в ядре. Права на дверь и баги за дверью — разные риски.

Не запускайте отладку драйверов на единственной рабочей машине без serial-консоли и плана отката. Цена ошибки на границе привилегий высока.

## Углубление (дополнение)

Page fault — нормальный механизм ленивого выделения и mmap, не всегда ошибка. SIGSEGV — уже сигнал о нарушении. Учитесь различать в профилировщиках.

Копирование user↔kernel (copy_to_user) защищает от подмены указателей. Высокоскоростные пути иногда используют zero-copy; это сложнее и требует доверия к буферам.

Не отлаживайте модуль ядра на единственном борту без консоли и образа отката.
