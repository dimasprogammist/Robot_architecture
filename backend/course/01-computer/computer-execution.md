# Как программа выполняется

## Цель

Пройти путь от команды запуска до исполнения инструкций процессором: роль загрузчика ОС, появление процесса, системные вызовы, ожидание I/O и завершение. Связать абстракцию «программа работает» с конкретными механизмами.

## Что уже нужно понимать

Что такое программа как файл и как набор инструкций. Роль CPU и RAM. Файловая система хранит образ. Есть ОС, которая управляет ресурсами (детали ОС углубим в следующем модуле).

## Объяснение

Выполнение начинается не с «процессора сам нашёл файл», а с **запроса к ОС**. Оболочка, графический ярлык, systemd, другой процесс вызывают API запуска (в Unix-семействе концептуально `fork`/`exec` или аналоги, в Windows — CreateProcess). Ядро проверяет права, готовит адресное пространство, загружает образ, настраивает стек, передаёт аргументы и окружение, ставит процесс в очередь планировщика.

Когда процессу дают квант времени на ядре CPU, счётчик команд указывает на инструкции. CPU крутит цикл исполнения. Как только программе нужно что-то за пределами своего адресного пространства — прочитать файл, принять сокет, выделить ещё память через brk/mmap, вывести на терминал — она делает **системный вызов**. Управление переходит в ядро; ядро выполняет работу от имени процесса (с проверками) и возвращает результат.

Если данные с диска ещё не готовы, процесс часто **блокируется** в ожидании. Планировщик переключает CPU на другой процесс. Это кажется параллелизмом даже на одном ядре: быстрое переключение создаёт иллюзию одновременности. На нескольких ядрах часть процессов реально идёт параллельно.

Интерпретируемые языки добавляют слой: CPU исполняет интерпретатор, а тот исполняет ваш байткод. Отладка, исключения, сборка мусора — события этого слоя, но внизу всё равно системные вызовы и инструкции.

Завершение: программа вызывает exit или получает сигнал/авария. Ядро освобождает ресурсы, закрывает дескрипторы (если не унаследованы иначе), сообщает код выхода родителю. Файл программы на диске не исчезает.

## Термины

- **Загрузка (load)** — размещение образа программы в адресном пространстве.
- **Точка входа** — адрес первой исполняемой инструкции пользовательского кода (упрощённо).
- **Системный вызов (syscall)** — контролируемый вход в ядро за услугой.
- **Планировщик** — часть ОС, решающая, кому дать CPU.
- **Блокировка I/O** — ожидание завершения ввода-вывода.
- **Код выхода** — целочисленный статус завершения процесса.
- **Контекст** — состояние регистров и учёта, сохраняемое при переключении.

## Как это устроено

Упрощённая последовательность для нативной программы:

1. Пользовательская команда → библиотека запуска → syscall создания процесса.
2. Ядро создаёт структуры учёта процесса, таблицы страниц.
3. Загрузчик отображает сегменты ELF/PE, решает динамические библиотеки.
4. Управление передаётся в пользовательский код.
5. Цикл: инструкции CPU ↔ изредка syscalls ↔ возможные прерывания и перепланирование.
6. Exit → очистка → статус родителю.

Для скрипта шаг 3 включает запуск интерпретатора и передачу пути скрипта аргументом.

Производительность часто упирается не в «сложение чисел», а в число и стоимость syscall и ожиданий. Пакетное чтение, буферы, асинхронность — способы уменьшить простои.

Ошибки выполнения: segmentation fault — выход за свою память; permission denied — отказ ядра; «command not found» — оболочка не нашла файл до запуска. Важно локализовать этап: до старта, во время загрузки, во время работы.

## Пример

Команда `python app.py` в терминале:

1. Shell ищет `python` через PATH.
2. ОС запускает бинарник интерпретатора с аргументом `app.py`.
3. Интерпретатор открывает файл скрипта (syscall read).
4. Исполняет код; `print` в итоге пишет в stdout (часто тоже через буферы и write).
5. Скрипт заканчивается — интерпретатор завершается, shell показывает приглашение снова.

Если `app.py` зависает на сетевом запросе, процесс в состоянии sleeping/waiting, CPU может быть почти свободен — «не работает» ≠ «грузит процессор».

## Типичные ошибки

- Думать, что программа исполняется «мимо ОС» на обычном ПК.
- Путать высокую загрузку CPU с единственной причиной медленной работы.
- Не различать ошибку оболочки (не найден файл) и ошибку внутри уже запущенной программы.
- Игнорировать код выхода в скриптах автоматизации.
- Считать интерпретатор «не настоящим выполнением» — для железа он настоящий.

## Что запомнить

Запуск — услуга ОС. Исполнение — инструкции CPU в рамках процесса. Внешние действия — через syscalls. Ожидание I/O отдаёт процессор другим. Завершение возвращает статус и освобождает ресурсы. Слои языка сидят поверх этой модели, не вместо неё.

## Задание

Запустите короткую программу, которая спит одну секунду и печатает сообщение. Наблюдайте (хотя бы мысленно по состоянию): когда идёт CPU, когда ожидание. Добавьте чтение несуществующего файла и разберите, на каком этапе появляется ошибка — до полезной работы или во время syscall.

## Практика и нюансы

Намеренно запустите программу с неверным аргументом, с отсутствующим файлом и с бесконечным циклом (осторожно, с возможностью прервать). Три разных класса проблем: логика, syscall/ошибка I/O, занятость CPU. Научитесь не лечить их одним и тем же способом.

В трассировке (strace/аналог) даже простой `ls` показывает пачку open/read/getdents — выполнение «простой» команды богато на разговоры с ядром. Это нормально; оптимизация начинается с понимания, какие вызовы частые и дорогие.

Интерпретируемый цикл «медленно» часто упирается не в математику байткода, а в частые мелкие I/O или аллокации. Профилируйте до переписывания на C.

Код выхода в автоматизации — контракт. Ноль — успех по соглашению; ненуль — сигнал пайплайну. Игнорирование статусов порождает «зелёные» CI с пустыми артефактами.

## Углубление (дополнение)

Научитесь читать состояния процесса: running vs sleeping. Высокий load average при низком %user часто значит ожидание диска. Высокий %user — реально считает. Высокий %iowait — узкое место носитель.

Трассировка syscalls на коротком интервале показывает «о чём программа разговаривает с ядром». Это быстрее гадания по симптомам UI.

Код выхода и stderr — контракт автоматизации. Молчаливый exit 0 после частичного провала — враг пайплайнов.


## Закрепление

Классифицируйте инциденты: CPU spin, I/O wait, блокировка замка, ожидание сети. Лечение разное.
