# Память

Когда программа работает, ей постоянно нужно где-то хранить инструкции, переменные, буферы и промежуточные результаты.

Но у компьютера нет одной универсальной «памяти», одинаково быстрой, большой и сохраняющей данные после выключения.

Вместо этого используется **иерархия памяти**:

```text
                 быстрее
                    ▲
                    │
                Регистры
                    │
                  L1/L2
                    │
                   L3
                    │
                   RAM
                    │
                 SSD/HDD
                    │
          внешнее / сетевое хранилище
                    │
                    ▼
                 больше
```

Верхние уровни маленькие и быстрые.

Нижние — значительно вместительнее, но медленнее.

Эта иерархия является одной из причин, почему две программы с похожим количеством вычислений могут работать совершенно по-разному.

---

## Почему нельзя сделать всю память быстрой

Система постоянно балансирует между тремя характеристиками:

```text
скорость
объём
стоимость
```

Очень быстрая память дорогая и физически ограничена.

Поэтому процессор получает небольшое количество наиболее быстрой памяти рядом с вычислительными блоками, а большие объёмы данных хранятся дальше.

Например:

```text
Регистры
   │
   │ очень быстро
   ▼
L1
   │
   ▼
L2
   │
   ▼
L3
   │
   ▼
RAM
   │
   ▼
SSD
   │
   │ медленнее, но намного больше
   ▼
архив / внешнее хранилище
```

Программа не обязана знать обо всех этих уровнях напрямую.

Но инженер должен понимать, что они существуют, потому что они влияют на реальное время выполнения.

---

## Летучая и энергонезависимая память

Есть ещё одно фундаментальное различие.

### Энергозависимая память

Типичный пример:

```text
RAM
регистры
кэш
```

При отключении питания содержимое обычно теряется.

### Энергонезависимое хранение

Например:

```text
SSD
HDD
Flash
eMMC
```

Данные сохраняются без постоянного питания.

Отсюда появляется важное правило:

> Если состояние должно пережить перезагрузку, его нужно сохранить в энергонезависимое хранилище.

Например:

```text
текущий угол мотора
       ↓
RAM

сохранённая калибровка
       ↓
Flash / SSD
```

После перезагрузки первое значение исчезнет, если его не сохранить.

---

## RAM — рабочая память программы

Оперативная память, RAM (Random Access Memory), — основное рабочее пространство запущенных программ.

Когда приложение запускается, ОС создаёт для него адресное пространство и организует размещение:

```text
┌-----------------------┐
│ код программы         │
├-----------------------┤
│ глобальные данные     │
├-----------------------┤
│ heap                  │
│ динамические объекты  │
├-----------------------┤
│ memory-mapped области │
├-----------------------┤
│ stack потока          │
└-----------------------┘
```

Это упрощённая модель.

Реальное адресное пространство процесса сложнее и зависит от ОС и архитектуры.

Главная идея:

**работающая программа имеет состояние, которое должно где-то храниться, и значительная его часть находится в RAM.**

---

## Что происходит при запуске программы

Пусть на SSD находится:

```text
robot.py
```

или исполняемый файл программы.

Сам файл находится на накопителе.

При запуске:

```text
SSD
 │
 │ загрузка
 ▼
ОС
 │
 ▼
адресное пространство процесса
 │
 ▼
RAM
 │
 ▼
CPU
```

Процессор не выполняет программу непосредственно «с диска» в обычном смысле.

Нужные инструкции и данные должны быть доступны вычислительной подсистеме памяти.

---

## Адреса памяти

Память можно представить как огромный массив адресуемых ячеек:

```text
Адрес       Данные

0x1000      25
0x1001      17
0x1002      ...
0x1003      ...
```

Программа работает с объектами и переменными, а на более низком уровне эти данные находятся в определённых областях адресного пространства.

Например:

```python
value = 42
```

можно концептуально представить как:

```text
переменная value
       │
       ▼
область памяти
       │
       ▼
байты, представляющие 42
```

Точный механизм зависит от языка, компилятора и runtime, поэтому нельзя сводить каждую переменную высокого уровня к одной физической ячейке RAM.

---

## Виртуальная память

Современные ОС обычно не дают процессам напрямую работать с физическими адресами RAM.

Каждый процесс получает собственное виртуальное адресное пространство.

Например:

```text
Процесс A:

виртуальный адрес 0x1000
        │
        ▼
физическая страница X


Процесс B:

виртуальный адрес 0x1000
        │
        ▼
физическая страница Y
```

Оба процесса могут использовать одинаковый виртуальный адрес, но получать разные физические области.

Это обеспечивает изоляцию:

```text
Процесс A --┐
            ├--► ОС / MMU ──► физическая RAM
Процесс B --┘
```

Поэтому ошибка одной программы не должна автоматически означать, что она может записать произвольные данные в память другой программы.

---

## Стек и куча

В адресном пространстве программы есть разные области с разными задачами.

### Стек

Стек используется для кадров вызовов функций и локального состояния.

Например:

```python
def calculate(a, b):
    result = a + b
    return result
```

Во время вызова функции системе нужно где-то хранить состояние её выполнения и локальные данные.

### Куча

Куча используется для динамически создаваемых объектов.

Например, программа может постепенно создавать:

```text
список
объекты
буферы
строки
структуры
```

Если таких объектов становится слишком много, потребление RAM растёт.

---

## Почему файл 200 МБ может занять намного больше RAM

Рассмотрим Python:

```python
with open("log.txt") as f:
    lines = f.readlines()
```

Сам файл может занимать на диске:

```text
200 MB
```

Но после загрузки каждая строка становится объектом Python.

У объектов есть дополнительные накладные расходы.

Поэтому:

```text
200 MB файл
      ↓
объекты Python
      ↓
может потребоваться значительно больше
      ↓
RAM
```

Поэтому нельзя автоматически считать:

> Размер файла = объём необходимой оперативной памяти.

Иногда гораздо лучше обрабатывать данные постепенно:

```text
with open("log.txt") as f:
    for line in f:
        process(line)
```

Теперь программе не нужно держать весь файл в RAM одновременно.

---

## Нехватка RAM

Представим:

```text
RAM компьютера: 8 GB

Процесс A → 3 GB
Процесс B → 2 GB
Процесс C → 2 GB
ОС         → 1 GB
```

Практически вся память занята.

Если программы продолжают запрашивать память, ОС должна что-то делать.

На системах с виртуальной памятью часть редко используемых страниц может быть перемещена в swap/page file.

Упрощённо:

```text
RAM
 │
 ├-- активные страницы
 │
 └-- редко используемые
          │
          ▼
        SSD
```

Проблема в том, что SSD значительно медленнее RAM.

Система может начать постоянно перемещать страницы:

```text
RAM → SSD → RAM → SSD → RAM ...
```

И работа резко замедлится.

На системах без swap может произойти отказ выделения памяти или сработать механизм завершения процессов из-за нехватки памяти.

---

## Swap не превращает SSD в RAM

Это важное различие.

Если на компьютере:

```text
8 GB RAM
100 GB свободного SSD
```

это не означает:

> «У меня фактически 108 GB оперативной памяти».

Swap используется как дополнительный уровень хранения страниц, но его задержки намного выше.

Для обычных приложений он может помочь системе пережить кратковременный дефицит RAM.

Для задач с жёсткими временными требованиями, например управляющего контура робота, непредсказуемый доступ к диску может быть недопустим.

---

## Утечка памяти и большое потребление — не одно и то же

Представим сервис, который работает несколько суток.

Потребление памяти:

```text
1 час   → 300 MB
2 часа  → 350 MB
3 часа  → 400 MB
4 часа  → 450 MB
...
```

Если рост продолжается при одинаковой нагрузке, это может быть признаком утечки.

Другой вариант:

```text
1 час   → 1.5 GB
2 часа  → 1.5 GB
3 часа  → 1.5 GB
4 часа  → 1.5 GB
```

Большое потребление само по себе ещё не означает утечку.

Программа может сознательно держать большой кэш.

Поэтому важно смотреть не только на одно измерение, но и на изменение потребления во времени.

---

## Пример с камерой робота

Пусть камера создаёт кадры размером несколько мегабайт.

Программа делает:

```text
камера
  │
  ▼
кадр
  │
  ├-- очередь A
  ├-- очередь B
  └-- очередь C
```

Если очереди не ограничены:

```text
кадр → очередь → очередь → очередь → ...
```

RAM постепенно заполняется.

CPU при этом может быть загружен совсем не сильно.

Симптом:

```text
RAM растёт
   ↓
swap / нехватка памяти
   ↓
задержки
   ↓
процесс завершается или система начинает тормозить
```

Правильнее проектировать ограниченные очереди и явно определять, что делать, если обработка не успевает за поступлением данных.

Например:

```text
очередь заполнена
      │
      ├-- удалить старый кадр
      ├-- отбросить новый
      └-- замедлить источник
```

Выбор зависит от задачи.

Для видеопотока иногда лучше потерять старый кадр, чем накапливать очередь из устаревших данных.

---

## Локальность данных

Память влияет не только на объём, но и на скорость.

Рассмотрим массив:

```text
[10][20][30][40][50][60][70][80]
```

Последовательный доступ:

```text
10 → 20 → 30 → 40 → 50
```

хорошо соответствует работе кэша и подсистемы памяти.

Случайный:

```text
10 → 700000 → 25 → 900000 → 400
```

может приводить к большому количеству cache miss и ожиданий памяти.

Поэтому иногда более простой алгоритм с хорошей организацией данных работает быстрее более «умного» алгоритма, который постоянно прыгает по памяти.

---

## Page cache ОС и кэш CPU — не одно и то же

Это часто путают.

### Кэш CPU

Используется процессором для ускорения доступа к данным и инструкциям:

```text
CPU
 ↓
L1/L2/L3
 ↓
RAM
```

### Page cache ОС

Используется операционной системой для хранения содержимого файлов в RAM:

```text
SSD
 ↓
page cache
 ↓
RAM
```

Это разные механизмы.

Если файл прочитали один раз:

```text
SSD → RAM
```

а потом повторно прочитали, ОС может вернуть данные из RAM без обращения к SSD.

Поэтому второе чтение иногда оказывается намного быстрее первого.

---

## Memory-mapped файлы

ОС может отображать файл в адресное пространство процесса.

Концептуально:

```text
Файл на SSD
     │
     ▼
memory mapping
     │
     ▼
адресное пространство процесса
```

Для программы часть файла может выглядеть как область памяти.

ОС загружает необходимые страницы по мере обращения к ним.

Это мощный механизм, но он не отменяет ограничений памяти и не делает SSD таким же быстрым, как RAM.

---

## Память в микроконтроллере

На микроконтроллере модель обычно жёстче.

Например:

```text
Flash
 └-- прошивка

SRAM
 ├-- переменные
 ├-- стек
 └-- буферы
```

Если SRAM закончилась:

```text
SRAM → недостаточно
```

нет возможности просто включить swap, как на обычном ПК.

Поэтому размер буферов и структур нужно заранее контролировать.

Для систем реального времени особенно важно понимать:

```text
сколько памяти нужно
когда она выделяется
кто ей владеет
когда освобождается
что произойдёт при нехватке
```

---

## Память в роботе: что должно пережить перезагрузку

Рассмотрим коэффициенты PID:

```text
Kp = 1.2
Ki = 0.05
Kd = 0.01
```

Во время работы они находятся в RAM.

После калибровки их нужно сохранить:

```text
RAM
 │
 │ сохранение
 ▼
Flash / SSD
```

После перезагрузки:

```text
Flash / SSD
      │
      ▼
     RAM
      │
      ▼
контроллер
```

Если сохранить значения забыли, после перезагрузки система может вернуться к старым параметрам.

Это типичный пример того, почему инженер должен различать **рабочее состояние** и **сохранённую конфигурацию**.

---

## Как выбирать уровень хранения

Для каждого важного состояния полезно задать четыре вопроса:

```text
1. Как часто оно меняется?
2. Как быстро к нему нужно обращаться?
3. Должно ли оно пережить reboot?
4. Какой объём требуется?
```

Например:

| Данные                 | Где обычно находятся | Переживают reboot  |
| ---------------------- | -------------------- | ------------------ |
| текущая переменная     | RAM                  | нет                |
| стек функции           | RAM                  | нет                |
| кэш CPU                | cache                | нет                |
| программа              | SSD/Flash → RAM      | исходник/файл — да |
| конфигурация           | SSD/Flash            | да                 |
| лог                    | SSD                  | да                 |
| текущий кадр камеры    | RAM                  | нет                |
| сохранённая калибровка | Flash/SSD            | да                 |

Эта таблица полезнее, чем просто запоминание терминов, потому что заставляет связывать свойства памяти с реальной задачей.

## Практика

### 1. Найдите потребление RAM

Откройте любой знакомый процесс:

* браузер;
* IDE;
* Python-программа;
* собственное приложение.

Посмотрите:

```text
потребление памяти
изменение со временем
что происходит после открытия большого файла
```

Сделайте предположение, какие данные находятся в RAM.

### 2. Найдите границу рабочего набора

Постепенно увеличивайте объём данных, который обрабатывает программа.

Например:

```text
100 MB
200 MB
500 MB
1 GB
2 GB
...
```

Следите за тем, когда система начинает заметно замедляться.

Попробуйте определить, связано ли это с нехваткой RAM и обращениями к диску.

### 3. Разберите собственный проект

Составьте список:

```text
Что должно пережить reboot?
Что существует только во время работы?
Что хранится в RAM?
Что хранится на Flash/SSD?
Какие данные постоянно изменяются?
```

Особенно полезно сделать это для робота:

```text
конфигурация
калибровки
текущие координаты
буферы датчиков
логи
модели
```

### 4. Найдите потенциальную утечку

Запустите собственное приложение и оставьте его работать при примерно одинаковой нагрузке.

Записывайте потребление RAM:

```text
10 мин → ?
30 мин → ?
1 час  → ?
2 часа → ?
```

Если оно постоянно растёт, выясняйте, какие объекты или буферы не освобождаются.

## Что нужно запомнить

* Память компьютера образует иерархию: **регистры → кэш → RAM → накопитель**.
* Чем быстрее память, тем меньше её обычно можно использовать и тем дороже она обходится.
* RAM — рабочая память запущенных программ.
* SSD/HDD/Flash предназначены для долговременного хранения.
* RAM обычно теряет содержимое при отключении питания.
* Программы работают с виртуальными адресными пространствами, которые ОС отображает на физическую память.
* Стек и куча выполняют разные задачи внутри адресного пространства процесса.
* Нехватка RAM может привести к swap, сильным задержкам или отказу выделения памяти.
* Swap не превращает SSD в полноценную замену RAM.
* Размер файла на диске не равен объёму RAM, необходимому для его обработки.
* Кэш CPU и page cache ОС — разные механизмы.
* Локальность данных сильно влияет на эффективность использования памяти.
* В микроконтроллерах память обычно гораздо более ограничена, поэтому буферы и рабочие области приходится проектировать заранее.
* Для каждого состояния системы нужно понимать, **где оно хранится и должно ли оно пережить перезагрузку**.
