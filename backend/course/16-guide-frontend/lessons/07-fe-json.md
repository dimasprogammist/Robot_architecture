# JSON как контракт с сервером

## Цель

Научиться читать и формировать JSON так, чтобы фронтенд и бэкенд говорили об одних и тех же полях заказа. После урока вы разберёте типичный ответ API, преобразуете его в объекты JS и обратно, и поймаете ловушки с датами и необязательными полями.

## Что уже нужно понимать

Вы вызываете `fetch` и ждёте `response.json()`. JSON — текстовый формат обмена: не «база данных» и не «класс», а соглашение о том, как записать структуру в строку. В Python на сервере это часто `dict`/`list` через Pydantic; в браузере — обычные объекты и массивы.

## Объяснение

Контракт важнее красивого UI. Если сервер отдаёт `status: "new"`, а клиент ждёт `state: "NEW"`, интерфейс будет пустым или врёт. JSON фиксирует имена, вложенность и допустимые значения на границе систем. Менять контракт нужно версионированием или явной миграцией обоих концов — не «тихо переименовать на фронте».

Типы JSON ограничены: объект, массив, строка, число, `true`/`false`, `null`. Нет дат как отдельного типа — обычно ISO-строка `"2026-09-25T08:00:00Z"`. Нет `undefined` — отсутствующее поле либо не включают, либо ставят `null` (семантика разная: «не прислали» vs «значение пустое»).

`JSON.parse` и `JSON.stringify` — мост строка ↔ значение. `fetch` + `res.json()` делает parse за вас. При отправке `stringify` пропускает функции и `undefined` в значениях объектов — внезапно пропавшее поле на сервере часто отсюда.

Для панели заказов полезно явно описать форму:

```text
Order = { id: number, customer: string, city: string, status: string, created_at: string }
```

Даже без TypeScript такой комментарий/схема спасает. Позже TypeScript закрепит это типами.

## Термины

- **Контракт API** — согласованная форма запросов и ответов.
- **Сериализация** — значение → строка JSON.
- **Десериализация** — строка → значение.
- **Schema validation** — проверка на сервере (Pydantic) и иногда на клиенте.

## Как это устроено

Поток: сервер сериализует модель → байты по HTTP → браузер парсит → ваш код читает `order.status`. Обратно: форма → объект JS → stringify → тело POST → Pydantic валидирует → модель домена.

Ошибки валидации FastAPI часто приходят как JSON с `detail` (массив или строка). Клиент должен уметь показать это человеку, а не только в консоль. Пустой список `[]` — валидный JSON и нормальный ответ «заказов нет»; не путайте с ошибкой сети.

Большие ответы: не тащите на клиент лишние поля «на всякий случай». Для списка достаточно краткой проекции; детали — отдельным `GET /orders/{id}`. Это и трафик, и ясность контракта.

## Пример

```javascript
// Пример тела ответа GET /api/orders
const raw = `[
  {
    "id": 101,
    "customer": "ООО Ромашка",
    "city": "Казань",
    "status": "new",
    "created_at": "2026-09-25T06:15:00Z"
  }
]`;

const orders = JSON.parse(raw);

function formatOrder(order) {
  const created = new Date(order.created_at);
  if (Number.isNaN(created.getTime())) {
    throw new Error(`Битая дата у заказа ${order.id}`);
  }
  return {
    id: order.id,
    title: `${order.customer} (${order.city})`,
    status: order.status,
    createdLabel: created.toLocaleString("ru-RU"),
  };
}

const viewModels = orders.map(formatOrder);

const payload = {
  customer: "Иван",
  city: "Уфа",
  // status сервер выставит сам — не шлём лишнего
};

const body = JSON.stringify(payload);
console.log(body); // {"customer":"Иван","city":"Уфа"}
```

## Разбор примера

`JSON.parse` превращает текст в массив объектов. Мы не рисуем сырой `created_at` в UI: парсим в `Date` и проверяем на Invalid Date — иначе «Invalid Date» утечёт на экран.

`formatOrder` отделяет **транспортную** форму от **представления**: в списке удобнее одно поле `title`. Это ещё не полноценный слой view-model фреймворка, но уже дисциплина: не размазывать `toLocaleString` по десяти кнопкам.

При создании заказа клиент шлёт только то, что должен решать пользователь. Статус и id назначает сервер — иначе легко подделать «сразу delivered».

## Типичные ошибки

- Сравнивать статусы без учёта регистра и словаря (`New` vs `new`).
- Слать циклические объекты в `stringify` (будет исключение).
- Путать число и строку: `"101"` и `101` в id.
- Считать, что JSON «сохраняет» `Date` как дату — это строка или число.
- Молча игнорировать неизвестные поля ответа — лучше логировать рассинхрон контракта в разработке.

## Что запомнить

JSON — язык границы фронт/бэк. Типы беднее, чем в JS. Даты — строки. Явный контракт полей заказа снижает баги. Парсите, проверяйте, преобразуйте в удобную для UI форму, обратно шлите только нужное.
