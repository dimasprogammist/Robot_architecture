# TypeScript для фронтенда

## Цель

Научиться описывать данные UI и props компонентов типами TypeScript, чтобы ловить рассинхрон с API на этапе компиляции. После урока вы типизируете заказ, статус и простой React-компонент.

## Что уже нужно понимать

JavaScript из предыдущих уроков модуля: объекты заказов, массивы, функции, React-компоненты. TypeScript — надстройка: тот же JS + типы, которые стираются при сборке. В браузер уходит обычный JavaScript. Вы не «переписываете язык», вы добавляете контракты.

## Объяснение

Опечатка `order.statuts` в JS всплывёт в рантайме (или тихо даст `undefined`). TypeScript скажет об этом в редакторе. Для панели заказов это критично: статусы, поля формы, ответ `fetch` — места, где фронт и бэк легко разъехаться.

Базовые типы: `string`, `number`, `boolean`, массивы `Order[]`, объекты через `type` или `interface`, объединения `"new" | "packing" | "done"`. Для JSON с сервера часто сначала описывают тип, потом утверждают/валидируют: компилятор не проверяет реальный ответ сети сам по себе — он проверяет, как вы с этим значением обращаетесь в коде.

В React типы props: `function OrderItem(props: { order: Order; onPack: (id: number) => void })` или вынесенный `type OrderItemProps = ...`. Хуки тоже типизированы: `useState<Order[]>([])`.

Строгий режим (`strict`) полезен с первого дня обучения: меньше «магического any». `any` отключает пользу TypeScript — используйте редко и осознанно.

## Термины

- **Статическая типизация** — проверка до запуска.
- **type / interface** — описание формы значения.
- **Union** — значение из набора вариантов.
- **Generics** — тип-параметр (`Promise<Order[]>`).
- **Стирание типов** — в рантайме типов уже нет.

## Как это устроено

Цепочка: вы пишете `.tsx` → TypeScript проверяет → сборщик (Vite) транспилирует в JS → браузер исполняет. Ошибки типов — ошибки сборки/редактора, не «красный экран» сами по себе. Ошибки сервера по-прежнему возможны: тип на клиенте может врать, если вы солгали при `as Order`. Поэтому для критичных мест иногда добавляют runtime-проверку (zod и т.п.) — за рамками минимума, но идея важна.

Согласование с бэкендом: идеально те же имена полей, что в Pydantic-схеме. Документируйте статусный словарь один раз. Если API вернул новое поле — старый клиент его игнорирует; если удалили поле, на которое вы опираетесь — тип и падение в UI напомнят обновить контракт.

## Пример

```tsx
type OrderStatus = "new" | "packing" | "shipped" | "cancelled";

type Order = {
  id: number;
  customer: string;
  city: string;
  status: OrderStatus;
  created_at: string;
};

type OrderItemProps = {
  order: Order;
  onPack: (id: number) => void;
};

function OrderItem({ order, onPack }: OrderItemProps) {
  return (
    <li>
      #{order.id} {order.customer}{" "}
      <em>{order.status}</em>
      <button
        type="button"
        onClick={() => onPack(order.id)}
        disabled={order.status !== "new"}
      >
        В упаковку
      </button>
    </li>
  );
}

async function fetchOrders(): Promise<Order[]> {
  const res = await fetch("/api/orders");
  if (!res.ok) {
    throw new Error(`HTTP ${res.status}`);
  }
  const data: unknown = await res.json();
  if (!Array.isArray(data)) {
    throw new Error("Ожидали массив заказов");
  }
  // Учебная проверка: в проде — схема/валидатор
  return data as Order[];
}
```

## Разбор примера

`OrderStatus` ограничивает строки: присвоить `"packaging"` компилятор не даст — поймаете опечатку словаря. `OrderItemProps` фиксирует колбэк: нельзя передать `onPack` без аргумента id и не заметить.

`fetchOrders` возвращает `Promise<Order[]>`. Ответ сначала `unknown` — честнее, чем сразу `as Order[]` без проверки. Мы хотя бы убеждаемся, что это массив. Полная валидация каждого поля — следующий шаг зрелости; здесь показан правильный скепсис к сети.

`disabled={order.status !== "new"}` опирается на union: сравнение осмысленно и автодополняется в IDE.

## Типичные ошибки

- Везде писать `any`, чтобы «не мешало».
- Слепо делать `as Order` без проверки формы ответа.
- Дублировать один и тот же тип в пяти файлах с расхождениями (вынесите в `types.ts`).
- Типизировать CSS-классы вместо данных домена.
- Путать типы TypeScript с проверками на сервере — безопасность API только на бэкенде.

## Что запомнить

TypeScript добавляет контракты к уже знакомому JS/React. Описывайте домен заказа и props. Сеть возвращает `unknown` по смыслу — проверяйте. Типы стираются, но ловят ошибки раньше. Строгость окупается на границе фронт/API.

## Задание

Опишите `type TelemetryPoint` и компонент `TelemetryRow(props)`. Добавьте функцию `statusColor(status: OrderStatus): string` с `switch` и `default` через `never`, чтобы новый статус в union заставлял дописать ветку.
