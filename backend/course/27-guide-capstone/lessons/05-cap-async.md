# Фон и очереди

## Цель

Понять, когда HTTP-запрос **не ждёт** тяжёлую работу: публикация в Kafka, воркеры, статусы «принято» vs «готово». После урока вы сможете разделить синхронный путь заказа и асинхронные побочные эффекты.

## Что уже нужно понимать

Путь HTTP-запроса. События. Где живут данные. Базовый Docker (отдельный процесс worker).

## Объяснение

### Проблема синхронного ожидания

Плохой дизайн checkout:

```text
POST /orders
  → INSERT order
  → вызвать банк (2–5 с)
  → сгенерировать PDF
  → отправить email
  → ответить клиенту
```

Пока банк и SMTP думают, воркер uvicorn занят, пользователь смотрит спиннер, таймаут прокси может оборвать запрос. Один медленный SMTP роняет UX всех.

### Правильный раздел

Синхронно (в запросе):

- валидация;
- запись заказа в PostgreSQL;
- (опционально) резерв в той же транзакции, если монолит и быстро;
- публикация задания/события (или запись outbox);
- ответ `201` с `status: accepted` / `new`.

Асинхронно (воркер):

- оплата у внешнего провайдера;
- письма;
- тяжёлые отчёты;
- фан-out на склад/аналитику.

### Роль Kafka в учебной карте

Kafka (или совместимый брокер) — буфер между API и воркерами:

```text
API --produce--> topic orders.events --consume--> worker-billing
                                         \------> worker-mail
```

API не вызывает SMTP. Он пишет событие и освобождает HTTP-воркер.

### Фрагмент: публикация после commit

```python
def create(db, user_id, data):
    order = orders_repo.insert(...)
    db.commit()
    producer.send(
        "orders.events",
        key=str(order.id),
        value={
            "type": "order_placed",
            "event_id": new_event_id(),
            "payload": {"order_id": order.id, "total": str(order.total)},
        },
    )
    return order
```

Ещё надёжнее — outbox в той же транзакции, что INSERT (см. урок по событиям). Иначе редкий сбой: заказ есть, события нет.

### Фрагмент: воркер

```python
def handle(message):
    event = parse(message)
    if event["type"] != "order_placed":
        return
    if already_processed(event["event_id"]):
        return
    charge_provider(event["payload"]["order_id"])
    orders_repo.set_status(event["payload"]["order_id"], "paid")
    mark_processed(event["event_id"])
    notify_realtime(event["payload"]["order_id"])
```

Воркер — отдельный процесс в Compose: `command: python -m app.workers.billing`. Рестарт API его не останавливает (и наоборот — почти).

### Что видит фронт

1. Сразу после POST: статус `new` / `accepted`.
2. Позже по WebSocket или GET: `paid` / `failed`.

UI обязан уметь промежуточные состояния. Не обещайте «оплачено», пока воркер не подтвердил.

### Когда HTTP всё же ждёт

Иногда бизнес требует синхронности:

- жёсткая проверка антифрода < 200 мс локально;
- идемпотентный reserve на складе в той же БД монолита;
- критичный ответ платёжного шлюза в редиректе (часто всё равно async + webhook).

Правило: **ждите в HTTP только то, без чего нельзя честно ответить пользователю**. Письмо чека — не из этого списка.

### Очереди задач vs событийный журнал

| | Очередь задач (RQ/Celery) | Kafka-события |
|--|---------------------------|---------------|
| Модель | «сделай работу X» | «случился факт Y» |
| Подписчики | обычно один тип воркера | много независимых |
| Типичный старт | проще | больше инфраструктуры |

Для одного email после заказа хватит очереди задач. Для склада + биллинга + аналитики от одного факта — события удобнее.

### Отказы и повторы

Воркер упал посередине — брокер отдаст сообщение снова. Отсюда:

- идемпотентность по `event_id`;
- ограниченный retry;
- dead letter topic для яда;
- алерт, если лаг консьюмера растёт.

Без этого фон превращается в тихий генератор двойных платежей.

### Наблюдаемость фона

В логах должны быть:

- `order_id`, `event_id`, `consumer`;
- успех/ошибка;
- время обработки.

Иначе симптом «заказ завис в new» не расследуется. HTTP access-лог тут бесполезен — запрос давно завершился 201.

### Типичные ошибки

- пихать sleep и SMTP в FastAPI-handler;
- отвечать 201 до commit, а событие слать «когда-нибудь»;
- один огромный воркер со всей логикой мира без модулей;
- отсутствие DLQ и бесконечный ретрай;
- фронт, который считает 201 = «уже оплачено».

### Практика разделения для магазина

Разберите каждый побочный эффект checkout:

| Эффект | Sync в HTTP? | Почему |
|--------|--------------|--------|
| INSERT order | да | без этого нет смысла ответа |
| Проверка схемы | да | иначе 422 |
| Charge банк | нет* | долго, внешний |
| Email | нет | не блокирует UX |
| Analytics | нет | eventual ок |
| Reserve stock (монолит, локально) | часто да | инвариант |

\*если провайдер и продукт требуют синхронного 3-D Secure — отдельный UX-поток, не «повисший POST».

## Коротко

HTTP фиксирует факт заказа и быстро отвечает; Kafka/воркеры делают оплату, почту и фан-out. Фронт показывает промежуточные статусы и узнаёт финал через GET/WS. Идемпотентность и outbox обязательны, иначе фон врёт деньгам.
