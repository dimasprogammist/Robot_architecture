# MAC-адрес и кадры канала

## Цель

Понять роль MAC-адреса в Ethernet-подобных сетях: как кадр доставляется внутри локального сегмента и чем MAC отличается от IP.

## Исходные знания

LAN как локальный сегмент. Общее представление о сетевом интерфейсе.

## Объяснение

На канальном уровне (типично Ethernet) данные упакованы в кадр. В заголовке кадра есть адрес отправителя и получателя — MAC. Это идентификатор сетевого интерфейса в пределах локальной среды, обычно 48 бит, записывается шестнадцатерично.

Коммутатор изучает, на каком порту какой MAC виден, и пересылает кадры целенаправленно. Если адрес неизвестен, кадр может быть залит на порты сегмента. Широковещательный MAC доставляет кадр всем в домене.

MAC не маршрутизируется через интернет. За пределами локального сегмента доставку делает IP, а на каждом участке снова используются локальные канальные адреса следующего прыжка.

Адрес можно сменить программно (spoofing), поэтому MAC сам по себе не сильная аутентификация. Фильтрация по MAC — слабый барьер, удобный только против случайностей.

Беспроводные сети тоже используют адресацию станций, хотя детали среды другие. Идея «локальный идентификатор интерфейса для кадра» сохраняется.

Увидеть MAC на Linux можно через `ip link`. Это свойство интерфейса, не пользователя.

## Термины

**MAC** — Media Access Control address, адрес интерфейса на канале.

**Кадр (frame)** — единица данных канального уровня.

**Коммутатор (switch)** — устройство пересылки кадров по MAC.

**Broadcast** — доставка всем в сегменте.

**OUI** — часть MAC, связанная с производителем (часто).

## Как это работает

Драйвер формирует кадр с MAC назначения. На Ethernet среда/коммутатор доставляет его на порт, где этот MAC изучен. Получатель снимает канальный заголовок и отдаёт полезную нагрузку верхнему уровню (часто IP-пакет).

Если IP указывает на хост вне сегмента, MAC назначения будет адресом шлюза, а не конечного сервера. Конечный IP при этом остаётся в заголовке пакета.

## Пример

```bash
ip link show
# в выводе ищите link/ether xx:xx:xx:xx:xx:xx

# логика кадра (схема)
# | MAC dst | MAC src | тип | полезная нагрузка | FCS |
```

## Разбор

`ip link` показывает MAC каждого интерфейса. `lo` не имеет Ethernet MAC в том же смысле.

Схема кадра подчёркивает: без правильного MAC dst кадр не попадёт на нужный порт локально, даже если IP внутри верный — на этом участке канальный заголовок обязателен.

## Ошибки

- Считать MAC «глобальным адресом в интернете».
- Путать MAC компьютера с IP сайта.
- Строить безопасность только на MAC-фильтре.
- Ждать, что MAC сервера за океаном виден локально.

## Что запомнить

- MAC адресует кадры в локальном сегменте.
- Коммутаторы пересылают по таблицам MAC.
- Через маршрутизатор меняется канальный заголовок.
- IP и MAC решают разные задачи.

## Дополнение: практика и нюансы

`ip link set dev eth0 address` меняет MAC — используйте только понимая последствия DHCP/reservations.

VLAN тегирует кадры; один физический линк — несколько L2-сегментов. ARP остаётся внутри VLAN.

Wi‑Fi ретраи на L2 маскируют потери от UDP-приложений иначе, чем Ethernet.

Таблица MAC коммутатора конечна: аномальный флуд адресов — отдельный класс атак/багов.


Проверьте согласованность настроек после перезагрузки: разовые правки ip/sysctl часто исчезают без конфига.

Сверьте документацию сервиса с фактическим unit/командой запуска: расхождения — частый источник сюрпризов.

Зафиксируйте ожидаемый код возврата успешного сценария в runbook рядом с командой проверки.

Сравните поведение на TTY и в pipe: буферизация и цвет меняют наблюдаемый вывод без смены логики программы.

Убедитесь, что время хоста синхронизировано: ложные ошибки TLS и путаница в логах часто из-за часов.

Проверьте лимиты файловых дескрипторов у процесса, если странно падают долгие сервисы под нагрузкой.
