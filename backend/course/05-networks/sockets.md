# Сокеты — API обмена

## Цель

Связать протоколы с программированием: что такое сокет, какие бывают типы, как выглядят bind/listen/accept и connect/send/recv.

## Исходные знания

TCP, UDP, порты. Базовый Python или любой язык с сетевым API.

## Объяснение

Сокет — абстракция ОС для сетевого (и не только) обмена. Приложение создаёт сокет, настраивает его и вызывает операции. Ядро связывает эти вызовы с протокольным стеком.

Для TCP сервер: `socket` → `bind` → `listen` → цикл `accept` → чтение/запись → закрытие. Клиент: `socket` → `connect` → чтение/запись → закрытие. Для UDP чаще `bind` + `recvfrom`/`sendto` без accept.

Домен адреса: IPv4, IPv6, Unix-domain (локальные файлы-сокеты). Тип: stream (TCP), dgram (UDP). Ошибки приходят как коды/исключения языка: отказ соединения, таймаут, reset.

Блокирующие сокеты останавливают поток до события. Неблокирующие и multiplexing (select/poll/epoll/io_uring) нужны серверам с многими клиентами. Для старта достаточно блокирующей модели.

Буферы ОС отделяют приложение от сети: `send` скопировал в буфер — ещё не значит, что байты дошли до пира. Протоколы приложения делают framing сообщений поверх байтового TCP-потока.

Закрытие: `close` освобождает дескриптор. Полуоткрытые состояния и TIME_WAIT — нормальные артефакты TCP; ими забивают порт при слишком агрессивных тестах.

## Термины

**Сокет** — конечная точка обмена в API ОС.

**listen/accept** — очередь и приём TCP-соединений.

**connect** — установление TCP к удалённой стороне.

**Unix-socket** — локальный IPC через файловый путь.

**Framing** — границы сообщений в потоке байтов.

## Как это работает

Файловый дескриптор сокета попадает в таблицу процесса. read/write или send/recv копируют данные между user space и буферами ядра. Ядро занимается сегментами, таймерами и маршрутами.

Библиотеки высокого уровня (HTTP-клиенты) прячут сокеты, но ошибки сети всё равно всплывают из этого слоя.

## Пример

```python
import socket
# TCP клиент к локальному эхо/закрытому порту — учебный каркас
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.settimeout(2)
try:
    s.connect(('127.0.0.1', 22))
    print('connected', s.getpeername())
except OSError as e:
    print('connect failed:', e)
finally:
    s.close()
```

```text
сервер: bind → listen → accept → recv/send
клиент: connect → send/recv → close
```

## Разбор

Клиентский пример показывает connect и обязательный close. Успех к порту 22 зависит от наличия sshd.

Схема сервера напоминает, что accept возвращает новый сокет на конкретное соединение, а слушающий остаётся ждать следующих.

## Ошибки

- Путать UDP sendto с TCP stream без границ сообщений.
- Забывать close и течь дескрипторами.
- Слушать только IPv4, когда клиент приходит по IPv6 (или наоборот).
- Считать, что один recv вернёт ровно одно прикладное сообщение.

## Что запомнить

- Сокет — API к стеку ОС.
- TCP и UDP используют разные шаблоны вызовов.
- send ≠ доставка до приложения пира.
- Framing поверх TCP — обязанность протокола приложения.

## Дополнение: практика и нюансы

SO_REUSEADDR и TIME_WAIT влияют на быстрый ребинд в тестах. Понимайте, прежде чем копировать сниппеты.

Таймауты: socket timeout ≠ HTTP client timeout ≠ LB idle timeout. Согласуйте цепочку.

Unix-сокеты быстрее localhost TCP для локальных демонов и проще ограничить правами файла.

Всегда закрывайте сокеты в finally/context manager — утечки fd валят сервисы через дни.

Итог раздела: закрепляйте механизм на практике, а не только синтаксис команд.
