# Шлюз по умолчанию

## Цель

Понять роль default gateway: куда отправлять пакеты, для которых нет более точного маршрута, и как это связано с MAC шлюза.

## Исходные знания

Подсети и таблица маршрутов. ARP на уровне идеи «нужен MAC соседа».

## Объяснение

Шлюз по умолчанию — маршрутизатор (или L3-устройство), которому хост отдаёт пакеты «в остальной мир». В таблице это маршрут `default` / `0.0.0.0/0` (и аналог в IPv6 `::/0`) через адрес шлюза на локальной подсети.

Без default route хост общается только с on-link сетями. Отсюда симптом: ping соседу по LAN работает, сайт в интернете — нет (если дело в маршруте, а не в DNS).

Шлюз должен быть в той же L3-подсети, что и интерфейс хоста (обычно). Иначе хост не сможет сделать ARP/ND до шлюза. Ошибка «gateway not on-link» — классика кривой ручной настройки.

На границе дома шлюз делает NAT и firewall. В корпоративной сети шлюз может вести в сложную фабрику маршрутов. Для хоста это всё равно next hop.

Несколько default route с разными метриками появляются при двух интерфейсах (Ethernet+Wi‑Fi, VPN). Метрика решает предпочтение. VPN часто добавляет маршруты специфичнее default или меняет default — отсюда «пропал интернет» при кривом VPN-профиле.

Проверка шлюза: есть ли он в `ip route`, пингуется ли (если ICMP разрешён), известен ли его MAC в кэше соседей.

## Термины

**Default route** — маршрут для всех назначений без лучшего совпадения.

**Next hop** — следующий IP, которому отдают пакет.

**Метрика** — стоимость/приоритет маршрута.

**On-link** — достижимость без промежуточного роутера.

**Edge router** — маршрутизатор на границе сети.

## Как это работает

Алгоритм: longest prefix match по таблице. Если ничего точнее не совпало — берётся default. Пакет с конечным dst IP инкапсулируется в кадр с MAC шлюза. Шлюз принимает, смотрит свою таблицу и двигает дальше.

Если шлюз мёртв, локальная сеть может жить, а выход наружу — нет. Резервирование шлюзов (VRRP и аналоги) решает это на уровне сети.

## Пример

```bash
ip route | grep -E 'default|0\.0\.0\.0/0' || ip route
ip -6 route | grep -E '^default|^::/0' || true

# логика
# dst=8.8.8.8 не в LAN → next hop = gateway → MAC(gateway)
```

## Разбор

Команда показывает, какой next hop выбран для «всего остального».

Логика подчёркивает: конечный IP остаётся 8.8.8.8, меняется канальный адрес на первом прыжке.

## Ошибки

- Указать шлюз из чужой подсети.
- Иметь два default без понимания метрик.
- Винить DNS, когда нет default route.
- Путать адрес шлюза с адресом DNS-сервера (часто совпадают дома, но роли разные).

## Что запомнить

- Default gateway — выход для неизвестных префиксов.
- Шлюз обычно on-link в вашей подсети.
- Метрики важны при нескольких выходах.
- Кадр на первом hop адресован шлюзу, не конечному серверу.

## Задание

Найдите default gateway. Проверьте, что он в вашей подсети. Посмотрите соседский кэш (`ip neigh`) на наличие его MAC.

## Дополнение: практика и нюансы

Два default route без політики — путь в неопределённость. Оставьте один или настройте метрики/правила.

Проверка шлюза: ARP/ND запись должна быть REACHABLE после ping.

Виртуальный IP VRRP/HSRP меняет активный шлюз без смены адреса — кэш соседей всё ещё важен.

В контейнерах default via часто bridge — путаница с хостовым шлюзом нормальна, рисуйте схему.


Проверьте согласованность настроек после перезагрузки: разовые правки ip/sysctl часто исчезают без конфига.

Сверьте документацию сервиса с фактическим unit/командой запуска: расхождения — частый источник сюрпризов.

Зафиксируйте ожидаемый код возврата успешного сценария в runbook рядом с командой проверки.

Сравните поведение на TTY и в pipe: буферизация и цвет меняют наблюдаемый вывод без смены логики программы.

Убедитесь, что время хоста синхронизировано: ложные ошибки TLS и путаница в логах часто из-за часов.

Проверьте лимиты файловых дескрипторов у процесса, если странно падают долгие сервисы под нагрузкой.
