# TCP — надёжный поток байтов

## Цель

Понять проблему надёжной доставки поверх IP, зачем нужен TCP, ход установления соединения, поля сегмента своими словами и типичные ошибки.

## Исходные знания

IP best effort, порты как идея, клиент-сервер. ARP/маршруты уже известны.

## Объяснение

### Проблема

IP может терять, дублировать и переупорядочивать пакеты. Многим приложениям нужен надёжный упорядоченный поток байтов между процессами, как «труба».

### Зачем протокол

TCP добавляет соединения, порты, номера последовательности, подтверждения, повтор передачи, контроль потока и (частично) перегрузки. Приложение пишет байты в сокет и читает байты; сегментацию делает стек.

### Принцип

Стороны устанавливают соединение (handshake), обмениваются сегментами с seq/ack, закрывают связь. Потерянный сегмент пересылают. Окно ограничивает, сколько данных можно отправить без новых ack.

### Структура сообщения своими словами

TCP-сегмент: порт источника и назначения, sequence number, acknowledgment number, флаги (SYN, ACK, FIN, RST…), размер окна, контрольная сумма, указатель срочности, опции, затем данные. Вместе с IP-заголовком это то, что бежит по сети. Порты мультиплексируют процессы на хосте.

### Ход обмена

1) Клиент → SYN. 2) Сервер → SYN+ACK. 3) Клиент → ACK. Соединение established. Далее данные с ACK. Закрытие через FIN/ACK (или RST при аварийном сбросе). Потеря — повтор по таймеру/быстрый повтор.

### Ошибки

Таймаут handshake (фильтр, нет маршрута, сервис down). RST — порт закрыт или сброс. Застревание из-за чёрной дыры MTU. Перегрузка и длинный RTT снижают скорость. Half-open соединения при обрыве сети.

## Термины

**Сегмент** — единица TCP.

**Handshake** — согласование соединения.

**Seq/Ack** — нумерация байтов и подтверждения.

**Окно** — лимит неподтверждённых данных.

**RST** — немедленный сброс соединения.

## Как это работает

ОС держит машину состояний TCP. Приложение видит сокет API. Надёжность не абсолютна: если соединение не удаётся — ошибка верхнему слою. TCP не шифрует; этим занимается TLS поверх.

Повторные передачи — признак потерь, не обязательно «медленный сервер». Смотрите RTT и retransmits в диагностике.

## Пример

```text
Клиент                Сервер
 SYN   ------------->
       <------------- SYN+ACK
 ACK   ------------->
 данные <-----------> данные
 FIN/ACK закрытие
```

```bash
ss -ltn | head
python -c "import socket; s=socket.create_connection(('127.0.0.1', 9), 1)" 2>/dev/null || echo "ожидаемо: порт 9 может быть закрыт"
```

## Разбор

Диаграмма — классический three-way handshake и фаза данных.

`ss -ltn` показывает слушающие TCP-порты. Попытка к закрытому порту часто даёт отказ соединения — иллюстрация RST/ошибки API.

## Ошибки новичков

- Думать, что TCP гарантирует доставку «навсегда» даже при мёртвой сети.
- Путать HTTP-ошибку 500 с обрывом TCP.
- Открывать новый TCP на каждый крошечный запрос без нужды (хотя HTTP/1.1 keep-alive/HTTP/2 решают иначе).
- Игнорировать таймауты приложения.

## Что запомнить

- TCP = соединение + надёжный поток поверх IP.
- Seq/ack/окно/флаги — каркас сегмента.
- Handshake обязателен до данных.
- Диагностируйте: слушает ли порт, доходит ли handshake, есть ли retransmit.

## Дополнение: практика и нюансы

Таймауты приложения должны быть больше RTT и учитывать handshake+TLS. Слишком короткие дают ложные ошибки.

Nagle и delayed ACK иногда взаимодействуют плохо с маленькими сообщениями — профилируйте, не гадайте.

`ss -ti` показывает детали состояния TCP на linux — полезно при медленных каналах.

Повторы на приложении идут поверх TCP retries; проектируйте идемпотентность.
