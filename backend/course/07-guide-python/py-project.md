Осталось сложить практики в устойчивое дерево каталогов.

## Объяснение с нуля

Хаотичные скрипты плохо масштабируются. Каркас: пакет кода, tests/, requirements.txt или pyproject.toml, README, venv рядом (не в git).

Точка входа тонкая: __main__.py или python -m pkg; логика — в импортируемых модулях. Конфиг отдельно; секреты не коммитить. Цель — чтобы за минуты было ясно, где код, тесты и как поднять среду.

## Термины

- **Пакет приложения**.

- **Точка входа**.

- **tests/**.

- **pyproject.toml / requirements.txt**.

- **README / .gitignore**.

- **Изоляция venv**.

- **Воспроизводимость**.

## Внутреннее устройство

Структура держит sys.path и имена импорта предсказуемыми. editable install добавляет проект в site-packages.

python -m pkg сохраняет пакетный контекст. Модель объектов та же: модули — namespaces, один раз за процесс.

## Пример

```text

myapp/

  .venv/

  README.md

  requirements.txt

  myapp/

    __init__.py

    __main__.py

    logic.py

  tests/

    test_logic.py

```

```python

# myapp/logic.py

def clamp(x, lo, hi):

    return max(lo, min(hi, x))



# myapp/__main__.py

from myapp.logic import clamp

print(clamp(15, 0, 10))

```

```text

python -m venv .venv

python -m pip install -r requirements.txt

python -m myapp

pytest -q

```

## Разбор

Пакет отделён от тестов; __main__ даёт python -m myapp.

logic импортируют CLI и тесты. venv+requirements воспроизводят среду — итог модуля.

## Ошибки

- Всё в одном main.py на тысячи строк.

- Коммитить .venv и секреты.

- Ломать импорты запуском внутренних модулей как скриптов.

- Дублировать код между скриптами.

- Не фиксировать зависимости.

## Что запомнить

Пакет + тесты + зависимости + тонкий вход.

Запускайте через python -m.

Структура служит читаемости и воспроизводимости.

## Задание

Мини-проект: пакет с функцией, __main__.py, один тест, requirements.txt.

venv → install → python -m → pytest; команды в README.
