# Виртуальные окружения

## Цель

Понять venv как изолированный набор пакетов поверх интерпретатора.

Создавать и активировать окружение, проверяя sys.executable.

## Что уже пройдено

Вы раскладываете код по пакетам.

Сторонние зависимости нельзя сваливать в один глобальный Python.

## Объяснение с нуля

venv — каталог со своим python и site-packages. Активация подменяет PATH так, что python/pip относятся к окружению.

Зачем: проект A хочет lib v1, проект B — v2. Создание: `python -m venv .venv`. Проверка — снова sys.executable.

Окружение обычно не коммитят; коммитят список зависимостей и воспроизводят.

## Внутреннее устройство

venv настраивает бинарник и site так, что sys.path указывает на локальные site-packages.

Без активации можно звать .venv/Scripts/python напрямую. IDE выбирает интерпретатор явно.

## Пример

```text

python -m venv .venv

# Windows PowerShell:

\.\.venv\Scripts\Activate.ps1

python -c "import sys; print(sys.executable)"

```

## Разбор

После активации путь должен указывать внутрь .venv.

Дальнейший pip install пойдёт в это окружение.

## Ошибки

- Ставить проектные пакеты в системный Python.

- Коммитить огромный .venv.

- Активировать одно, а в IDE выбрать другое.

- Удалить базовый Python и ждать магии.

- Путать conda и stdlib venv без нужды.

## Что запомнить

venv изолирует site-packages.

Проверяйте sys.executable.

Окружение воспроизводят по списку пакетов.
