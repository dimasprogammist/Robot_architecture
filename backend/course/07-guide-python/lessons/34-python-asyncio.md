# Асинхронное программирование и asyncio

Обычный `requests.get` **держит поток**, пока сеть отвечает: вы не выполняете другой Python-код в этом потоке. Если нужно ждать много сокетов сразу (чат, тысяча соединений, WebSocket), модель «один поток = одно ожидание» дорогая.

**asyncio** — кооперативная многозадачность в одном потоке: задача дошла до `await` «подожди I/O» — цикл событий может крутить другую задачу.

```python
import asyncio


async def fetch_name():
    await asyncio.sleep(0.1)
    return "ok"


async def main():
    a, b = await asyncio.gather(fetch_name(), fetch_name())
    print(a, b)


asyncio.run(main())
```

`async def` — корутина. Вызов `fetch_name()` не выполняет тело: возвращает объект, который надо `await` или запланировать. Забыть `await` — «как будто ничего не сделали», частый баг.

`asyncio.sleep` — не `time.sleep`. Обычный sleep заморозит **весь** цикл событий. В async-коде ждать нужно async-примитивами и async-библиотеками (`httpx.AsyncClient`, async-драйверы). Синхронный `requests` внутри `async def` без обходных путей снова блокирует всех.

Это не ускоряет тяжёлую арифметику на всех ядрах. CPU- Bound лучше процессы или иной инструмент. Async про **ожидание**.

Отладка сложнее: трассировки, «кто кого ждёт». Не тащите asyncio в скрипт из двадцати строк с одним запросом — обычный вызов яснее. Там, где фреймворк уже async (FastAPI, многие веб-сокеты), имеет смысл жить в этой модели.
