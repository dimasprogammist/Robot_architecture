# Потоки, процессы и параллельное выполнение

Один поток выполняет байт-код Python под **GIL** (глобальная блокировка интерпретатора в CPython): чистый Python-счёт на всех ядрах сразу из двух потоков не поедет как «×2». Потоки всё же полезны: ждать диск, часть библиотек, отпускающих GIL, не блокировать UI.

```python
from threading import Thread


def work():
    print("фон")


t = Thread(target=work)
t.start()
t.join()
```

Общая память: списки и словари с двух потоков без блокировки — гонки. `queue.Queue` — очереди сообщений — спокойнее, чем общий список `append` с двух сторон.

**Процесс** — отдельная память, отдельный интерпретатор. Модуль `multiprocessing` или `concurrent.futures.ProcessPoolExecutor` для CPU-задач: посчитать много независимых кусков. Цена: сериализация аргументов, нет общих списков просто так, старт тяжелее.

```python
from concurrent.futures import ProcessPoolExecutor


def sq(x):
    return x * x


if __name__ == "__main__":
    with ProcessPoolExecutor() as pool:
        print(list(pool.map(sq, [1, 2, 3])))
```

`if __name__ == "__main__"` на Windows обязателен для честного старта процессов — иначе рекурсия запуска.

Выбор грубо: ждать сеть в одном приложении — потоки или asyncio. Считать тяжёлое — процессы. Робот с жёстким циклом 50 мс — сначала измерьте, не плодите пулы «на будущее».

Взаимная блокировка двух lock — классика. Меньше разделяемого состояния — меньше боли.
