# Логирование программ

`print` для учёбы хорош. В долгой программе нужна **лента событий** с уровнем важности, временем, именем модуля: что случилось, когда, насколько это страшно. Модуль `logging`.

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s: %(message)s",
)
log = logging.getLogger(__name__)

log.debug("сырой пакет %s", packet)
log.info("робот стартовал")
log.warning("батарея %s %%", percent)
log.error("датчик не ответил")
```

Уровни снизу вверх: DEBUG, INFO, WARNING, ERROR, CRITICAL. Порог `level` отсекает мелочь. На стенде DEBUG, в «спокойной» эксплуатации INFO или WARNING.

Форматирование через `%s` и аргументы, не через f-строку в вызове лога: тогда отсечённый DEBUG не собирает тяжёлую строку зря (привычка; для коротких сообщений не догма).

`getLogger(__name__)` — логгер с именем модуля. Потом можно крутить подробность отдельно для `sensors` и для библиотеки HTTP.

Не логируйте пароли, токены, персональные данные «на всякий случай». Лог часто уезжает в файл и в чужие руки.

Ротация файлов, JSON-логи, связь с systemd — позже. Сначала: один `basicConfig` в точке входа (`main`), в библиотечных модулях только `getLogger`, **не** второй `basicConfig`.

`print` и `logging` вместе без договорённости — каша в терминале. Выберите лог как канал «состояния системы».
