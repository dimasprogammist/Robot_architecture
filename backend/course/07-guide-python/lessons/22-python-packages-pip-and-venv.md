# Пакеты Python, pip и виртуальные окружения

Стандартной библиотеки мало: HTTP-клиент поудобнее, драйвер, численные штуки. **Пакет с индекса** (PyPI) ставят инструментом **pip**. Это не «пакет» в смысле каталога вашего проекта — то же слово, другой слой: *зависимость*.

Ставить всё в системный Python — путь к «у проекта A версия 1, у B версия 2, сломалось оба». **Виртуальное окружение** — отдельный каталог с интерпретатором и своими установленными зависимостями.

```text
python -m venv .venv
```

На Windows активация обычно `.venv\Scripts\activate`, на Unix — `source .venv/bin/activate`. После активации `python` и `pip` смотрят внутрь `.venv`. Каталог `.venv` не коммитят: его собирают заново.

```text
python -m pip install requests
```

`python -m pip` надёжнее, чем голый `pip`: ясно, *чей* pip. Зависимости проекта перечисляют в `requirements.txt`:

```text
requests==2.32.3
```

Или в `pyproject.toml` — как принято в конкретном репозитории. Фиксировать версии — чтобы чужая машина и ваш ноут не «почти те же пакеты».

Ставить с недоверенных источников, смешивать conda и pip без понимания, править файлы внутри site-packages руками — боль. Обновлять всё подряд на проде без теста — тоже.

`pip freeze` вывалит весь граф, включая транзитивное. Для учебного проекта часто пишут прямые зависимости руками, не слепой freeze из случайной машины.

Пакет вашего приложения (`sensors/`) и пакет с PyPI (`requests`) встречаются в импортах одинаково `import ...`. Разница: одни ваши файлы, другие появились после install.
