# Индексы и поиск в NoSQL

Мы рассмотрели все четыре модели NoSQL. Теперь перейдём к теме, которая касается почти любой из них одинаково: как база данных вообще находит нужные записи, и почему это далеко не всегда происходит мгновенно без специальной подготовки.

## Поиск без индекса

Представим документную коллекцию с миллионом заказов, и нужно найти все заказы конкретного пользователя. Без дополнительной подготовки база данных вынуждена последовательно просмотреть каждый документ в коллекции, проверяя у каждого поле `user_id`, — это называют **полным сканированием коллекции**. Для миллиона документов это уже заметно медленно, а для сотен миллионов — зачастую практически неприемлемо для системы, которая должна отвечать на запрос за доли секунды.

```text
   запрос: user_id = "u1042"
         ↓
   без индекса: проверить все N документов по очереди
         ↓
   время растёт линейно с ростом числа документов
```

## Поиск с индексом

**Индекс** — это дополнительная структура данных, которую база хранит отдельно от самих документов специально для того, чтобы быстро находить их по определённому полю, не перебирая всю коллекцию. Концептуально индекс можно представить как алфавитный указатель в конце книги: вместо того чтобы листать книгу целиком в поисках нужного слова, можно сразу заглянуть в указатель и узнать точный номер страницы.

```text
   индекс по полю user_id:

   "u1040" → документы на позициях [12, 445, 991]
   "u1042" → документы на позициях [7, 302]
   "u1043" → документы на позициях [88]
```

С индексом по `user_id` поиск заказов конкретного пользователя превращается из полного перебора в быстрое обращение к заранее построенной структуре — порядок роста времени поиска становится не линейным, а значительно более медленным (логарифмическим или ещё более быстрым, в зависимости от конкретной структуры индекса), что для больших коллекций — принципиальная разница.

## Стоимость индекса

Индекс не появляется бесплатно, и это главная мысль урока: **индекс ускоряет определённые запросы, но требует дополнительной памяти и усложняет операции записи**. Разберём обе стороны этого компромисса подробнее.

**Память.** Индекс — это отдельная структура данных, которая занимает место на диске и в оперативной памяти вдобавок к самим данным. Чем больше в коллекции индексов и чем они сложнее, тем больше дополнительного места они требуют — для больших коллекций это может быть совсем не мелочью.

**Запись.** Каждый раз, когда документ создаётся, изменяется или удаляется, базе данных нужно не только обновить сам документ, но и актуализировать каждый индекс, который ссылается на изменившиеся поля. Чем больше индексов построено на коллекции, тем дороже становится каждая операция записи — это прямой компромисс: индексы ускоряют чтение ценой замедления записи.

```text
   запись документа
         ↓
   обновление самого документа
         ↓
   обновление индекса 1
         ↓
   обновление индекса 2
         ↓
   ...
```

Именно поэтому бездумное «создать индекс на каждое поле, на всякий случай» — плохая практика: для коллекции с интенсивной записью (например, потока телеметрии) лишние индексы способны заметно замедлить именно ту операцию, которая и так происходит чаще всего.

## Составные индексы

**Составной индекс** строится сразу по нескольким полям вместе, а не по одному. Если приложение часто ищет заказы одновременно по `user_id` и `status` («все доставленные заказы этого пользователя»), составной индекс по обоим полям сразу может оказаться эффективнее, чем два отдельных индекса по каждому полю по отдельности. У составных индексов есть важная особенность: порядок полей в индексе обычно имеет значение — индекс, построенный как «сначала `user_id`, потом `status`», эффективно ускоряет и поиск только по `user_id`, и поиск по обоим полям сразу, но плохо или вовсе не ускоряет поиск только по `status` в отрыве от `user_id`.

## Индексы по вложенным полям

Документная модель позволяет строить индексы не только по полям верхнего уровня документа, но и по значениям внутри вложенных объектов и массивов — например, индекс по полю `items.product` внутри массива позиций заказа из прошлого урока позволил бы быстро находить все заказы, где фигурирует конкретный товар, не разбирая структуру документа вручную при каждом запросе. Это одна из практических причин, почему embedding связанных данных внутрь документа (о котором шла речь в уроке 4) не обязательно означает потерю возможности эффективно искать по этим вложенным данным.

## Почему нельзя просто проиндексировать всё

Возвращаясь к главной мысли урока: каждое новое поле, добавленное в индекс, увеличивает расход памяти и замедляет каждую операцию записи во всей коллекции, даже если это поле редко используется в запросах. Разумная практика — строить индексы осознанно, опираясь на реальные, часто повторяющиеся запросы приложения (то есть снова на access patterns, о которых шла речь в уроке про документную модель), а не на теоретическую возможность когда-нибудь искать по любому полю.

## Типичные ошибки

Частая ошибка — строить индекс по полю, которое на практике почти никогда не используется для поиска, просто «на всякий случай» — это чистая потеря ресурсов без практической пользы. Вторая — строить составной индекс в порядке, который не соответствует реальным запросам приложения, из-за чего индекс почти не приносит пользы, хотя формально существует. Третья — забывать, что обилие индексов особенно вредно именно для систем с высокой интенсивностью записи — там, где важнее всего быстрая запись (например, поток телеметрии), избыточные индексы способны создать заметное узкое место производительности.

## Что нужно запомнить

Без индекса поиск по произвольному полю требует полного просмотра всей коллекции, что становится неприемлемо медленным при росте объёма данных. Индекс — отдельная структура, которая резко ускоряет поиск по конкретному полю или набору полей ценой дополнительной памяти и замедления каждой операции записи. Составные индексы ускоряют запросы по нескольким полям сразу, но чувствительны к порядку полей, а индексы по вложенным полям документа позволяют эффективно искать даже внутри встроенных структур.

## Практика

1. Объясните, почему полное сканирование коллекции становится всё менее приемлемым по мере роста числа документов.
2. Коллекция заказов часто ищется по `user_id` и редко — по `status` в отрыве от пользователя. Предложите, какой индекс стоит построить и почему.
3. Объясните, почему составной индекс «user_id + status» в этом порядке плохо ускоряет запрос, который ищет только по `status`.
4. Система телеметрии пишет 10 000 записей в секунду и почти не делает сложных поисковых запросов по произвольным полям. Обоснуйте, стоит ли здесь строить много индексов.
5. Приведите пример запроса, для которого полезен индекс по вложенному полю документа, и объясните, какую структуру данных он должен был бы искать.
6. Опишите своими словами компромисс «индекс ускоряет чтение, но замедляет запись» на конкретном числовом примере (например, коллекция с 5 индексами против коллекции без индексов при частой записи).
7. Объясните, почему бездумное создание индекса «на каждое поле документа» является плохой практикой, даже если место на диске не ограничено.
