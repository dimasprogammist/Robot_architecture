# Key-value, wide-column и graph

В прошлом уроке мы подробно разобрали документную модель. Теперь вернёмся к трём оставшимся моделям из обзорного урока 3 и рассмотрим каждую из них уже предметно — на том уровне детализации, который позволит уверенно понимать, когда к ней стоит обращаться.

## Key-value: максимальная простота ради максимальной скорости

Мы уже знаем общую идею: ключ и непрозрачное значение. Разберём, почему именно эта предельная простота оказывается настолько практически полезной.

Поскольку база данных не пытается анализировать содержимое значения, а просто сохраняет и отдаёт его по ключу, операции чтения и записи можно сделать исключительно быстрыми — зачастую такие хранилища держат основной объём данных прямо в оперативной памяти, а не только на диске, что на порядки снижает задержку по сравнению с чтением с накопителя (вспомним урок про разницу скорости RAM и SSD из раздела «Основы компьютера»).

Частый спутник key-value модели — **TTL** (time to live, «время жизни») — возможность пометить запись так, чтобы она автоматически удалилась сама по прошествии заданного времени. Это делает модель особенно удобной для данных, которые по своей природе временные: сессия пользователя должна автоматически завершиться через определённое время бездействия, временный код подтверждения должен перестать быть действительным через несколько минут.

```text
   SET session:a93f  "user_id=1042"  EX 1800   (TTL — 1800 секунд)
          ↓
   через 30 минут запись исчезает сама, без явного удаления
```

Типичные применения: **кэш** часто запрашиваемых, но дорого вычисляемых данных (результат сложного запроса к основной базе данных сохраняется на некоторое время, чтобы не пересчитывать его при каждом обращении); **хранение сессий** пользователей; **счётчики** (например, число просмотров страницы, которое нужно очень часто и очень быстро увеличивать на единицу). Классический пример такой системы — Redis.

## Wide-column: партиции ради распределённой записи

Мы уже видели, что wide-column модель физически организует данные вокруг **ключа партиции** (partition key). Разберём, почему это настолько важно для производительности.

В распределённой wide-column системе данные физически разложены по множеству серверов, и то, на каком именно сервере окажется конкретная запись, определяется её ключом партиции. Запрос, который явно указывает ключ партиции, система направляет сразу к нужному серверу и получает ответ очень быстро — вне зависимости от того, сколько всего партиций хранится во всей системе. А вот запрос, который не опирается на ключ партиции (например, «найди все записи, где значение температуры выше 100, вне зависимости от устройства»), вынужден был бы опросить каждый сервер по очереди, что для системы с тысячами партиций становится крайне неэффективным — поэтому wide-column системы сознательно ограничивают гибкость запросов ради предсказуемой производительности записи и чтения по партиции.

```text
   partition key = sensor_id

   sensor_42  →  сервер A  →  все измерения датчика 42 физически рядом
   sensor_43  →  сервер B  →  все измерения датчика 43 физически рядом
```

Эта модель особенно хорошо подходит там, где поток новых записей огромен и предсказуемо структурирован вокруг понятного ключа — классический пример — временные ряды измерений с множества датчиков, где ключом партиции естественно становится идентификатор конкретного датчика. Классический пример такой системы — Cassandra.

## Graph: связи как главный гражданин модели

Мы уже знаем, что графовая модель хранит **вершины** и **рёбра** со свойствами у каждой. Разберём, почему обход связей здесь принципиально быстрее, чем в реляционной модели с `JOIN`.

В реляционной базе данных связь между двумя записями восстанавливается заново при каждом запросе — через сопоставление внешнего ключа одной таблицы с первичным ключом другой, и чем длиннее цепочка связей (друг друга друга), тем больше последовательных `JOIN` требуется, и тем медленнее в общем случае становится запрос. В графовой базе данных физическая связь между двумя узлами хранится как готовая, уже существующая ссылка — обход от узла к соседнему узлу не требует поиска по индексу и сопоставления ключей, а представляет собой, по сути, прямой переход по уже существующей ссылке, что делает его дешёвым даже при большой глубине обхода.

```text
   (Контроллер A) --[управляет]--> (Мотор 1)
   (Контроллер A) --[подключён к]--> (Датчик температуры)
   (Датчик температуры) --[установлен на]--> (Узел B)

   Запрос: "что связано с контроллером A на расстоянии до 2 связей?"
   → прямой обход рёбер, а не серия JOIN
```

Графовая модель особенно естественна там, где сами связи между объектами так же важны, как и сами объекты, а часто — даже важнее: социальные связи (друзья, подписки), зависимости (какие модули программы зависят от каких, какие задачи блокируют какие), маршруты и навигация (прямое продолжение темы графов из математического модуля курса), топология промышленного оборудования (какой контроллер к какому датчику и мотору подключён, через какую сеть). Классический пример такой системы — Neo4j.

## Сводный взгляд на три модели

| | Key-value | Wide-column | Graph |
|---|---|---|---|
| Главная идея | непрозрачное значение по ключу | строки, распределённые по ключу партиции | узлы и явные связи между ними |
| Сильная сторона | предельная скорость доступа по ключу | огромный поток записи, предсказуемое распределение нагрузки | быстрый обход связей любой глубины |
| Пример продукта | Redis | Cassandra | Neo4j |
| Типичная задача | кэш, сессии, счётчики | телеметрия, временные ряды | социальные связи, зависимости, топология |

## Типичные ошибки

Частая ошибка — пытаться получить от key-value хранилища поиск по содержимому значения: эта модель структурно для этого не предназначена, и правильное решение — либо хранить дополнительные индексы вручную на уровне приложения, либо выбрать другую модель. Вторая — делать запросы к wide-column системе без опоры на ключ партиции «иногда, для удобства», не осознавая, что это превращает быструю, предсказуемую операцию в дорогой опрос всех узлов системы. Третья — считать Redis «просто быстрым SQL»: Redis не реализует реляционную модель и не предоставляет `JOIN`, транзакционные гарантии и язык запросов, сопоставимые с SQL, — это другая модель с другими целями, пусть и действительно очень быстрая для своих операций.

## Что нужно запомнить

Key-value хранилища жертвуют возможностью заглянуть внутрь значения ради максимальной скорости доступа по точному ключу и часто используют TTL для автоматически истекающих данных. Wide-column системы физически организуют огромные объёмы данных вокруг ключа партиции, обеспечивая предсказуемую скорость записи и чтения ценой ограниченной гибкости запросов без указания этого ключа. Графовые базы данных делают связи между объектами такой же полноценной частью хранимых данных, как и сами объекты, что превращает обход даже длинных цепочек связей в дешёвую операцию.

## Практика

1. Объясните, почему TTL особенно уместен для данных сессии пользователя, но неуместен для данных заказа интернет-магазина.
2. Система должна хранить показания тысячи датчиков, каждый пишет раз в секунду. Предложите подходящий ключ партиции для wide-column хранилища и обоснуйте выбор.
3. Объясните, почему запрос «найди все измерения выше заданного порога независимо от датчика» плохо ложится на партиционированную по датчику wide-column модель.
4. Опишите структуру графа (вершины, рёбра, свойства) для системы, моделирующей зависимости между сервисами в распределённом приложении.
5. Сравните, как реляционная база данных и графовая база данных будут искать «всех людей на расстоянии двух рукопожатий от пользователя» — в чём принципиальная разница в подходе?
6. Приведите пример данных, для которых key-value модель окажется неудобной, и объясните, какая из оставшихся моделей подошла бы лучше.
7. Объясните своими словами, почему утверждение «Redis — это просто быстрый SQL» некорректно.
