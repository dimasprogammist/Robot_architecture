# Основные модели NoSQL

Мы уже выяснили, что NoSQL — это не одна структура, а несколько разных. Настало время познакомиться с четырьмя моделями, которые встречаются чаще всего. Это один из центральных уроков всего модуля — к нему мы будем регулярно возвращаться, а в следующих двух уроках подробно разберём каждую модель по отдельности.

## Key-value: данные как огромный словарь

**Key-value** (ключ-значение) — самая простая из всех моделей. Данные хранятся в виде пар: уникальный **ключ**, по которому происходит обращение, и связанное с ним **значение**, которое база данных не пытается анализировать или разбирать на части — для неё это просто набор байтов.

```text
   "user:1042:session"  →  "a93f...token data..."
   "cart:7731"           →  "[{item: 42, qty: 2}, ...]"
   "counter:page_views"  →  "184293"
```

Поиск происходит почти исключительно по точному ключу — это делает key-value хранилища чрезвычайно быстрыми для своей главной операции («дай мне значение по этому ключу», «запиши это значение под этим ключом»), но принципиально неудобными для запросов вида «найди все значения, где внутри встречается такое-то поле» — модель просто не умеет заглядывать внутрь значения. Классический пример этой модели — Redis, который мы подробнее разберём в уроке 5.

## Document: данные как самодостаточные записи

**Документная модель** хранит данные в виде структурированных, обычно JSON-подобных документов, которые могут содержать вложенные объекты и массивы — в отличие от key-value, база данных «видит» и понимает внутреннюю структуру документа, а не просто хранит его как непрозрачный набор байтов.

```text
   {
     "_id": "u1042",
     "name": "Анна",
     "addresses": [
       {"city": "Москва", "type": "home"},
       {"city": "Казань", "type": "work"}
     ]
   }
```

Это позволяет искать не только по идентификатору документа, но и по значениям внутри него, а также естественно хранить вложенные, иерархические данные без разбиения на отдельные таблицы, как пришлось бы сделать в реляционной модели. Классический пример — MongoDB; подробно документную модель и то, как под неё проектировать данные, разберём в уроке 4.

## Wide-column: данные как таблица с гибкими, очень широкими строками

**Wide-column** (широкие колонки) модель внешне немного напоминает таблицу — у неё есть строки и столбцы, — но устроена принципиально иначе: разные строки могут иметь совершенно разный набор столбцов, а сами данные физически организуются вокруг так называемого **ключа партиции** (partition key), определяющего, на каком узле распределённой системы данные будут физически храниться.

```text
   Партиция "sensor:42"
       timestamp=10:00:01, temp=21.3
       timestamp=10:00:02, temp=21.4
       timestamp=10:00:03, temp=21.5, humidity=55
```

Эта модель спроектирована прежде всего под огромные объёмы данных с очень высокой скоростью записи, распределённых между множеством серверов, — типичный сценарий: поток измерений с тысяч датчиков. Классический пример — Cassandra; подробнее разберём эту модель в уроке 5.

## Graph: данные как сеть связей

**Графовая модель** делает связи между объектами не побочным свойством, а главным объектом хранения. Данные — это **вершины** (узлы, представляющие сущности — людей, устройства, места) и **рёбра** (связи между ними, например «дружит с», «подключён к», «находится в»), причём и у вершин, и у рёбер могут быть собственные свойства.

```text
   (Пользователь: Анна) --[дружит с]--> (Пользователь: Борис)
   (Контроллер: A1) --[подключён к]--> (Датчик: температура-7)
```

Там, где в реляционной модели поиск «друзей друзей» или «всех устройств, связанных через цепочку подключений» требует нескольких последовательных `JOIN`, которые становятся всё медленнее с ростом глубины связи, графовая модель устроена так, что обход связей — её родная, оптимизированная операция. Классический пример — Neo4j; подробнее разберём в уроке 5.

## Сравнение четырёх моделей

| Модель | Данные | Типичный поиск | Особенно хороша для | Главное ограничение |
|---|---|---|---|---|
| Key-value | непрозрачное значение по ключу | только по точному ключу | кэш, сессии, счётчики | нельзя искать «внутри» значения |
| Document | структурированный документ | по ключу и по полям внутри | гибкие, вложенные данные, карточки объектов | связи между документами проектируются вручную |
| Wide-column | строки с гибким набором столбцов, партиционированные | по ключу партиции, иногда с диапазоном | огромный поток записи, временные ряды | запросы без указания ключа партиции неэффективны |
| Graph | узлы и связи между ними | обход связей от узла к узлу | социальные связи, зависимости, маршруты | не рассчитан на огромные аналитические агрегации по всем данным |

## Это не взаимоисключающий выбор

Важно сразу увидеть: эти четыре модели не конкурируют за звание «лучшей» NoSQL-базы — они решают структурно разные задачи, и крупная система нередко использует одновременно несколько из них для разных частей своих данных (мы разберём конкретный такой пример в последнем уроке модуля, применительно к робототехнической системе). Выбор модели определяется не модой, а тем, какие у конкретных данных естественные связи и какой характер у запросов к ним — вопрос, к которому мы ещё вернёмся предметно в уроке про выбор NoSQL.

## Типичные ошибки

Частая ошибка — считать MongoDB синонимом всего NoSQL: MongoDB — это один конкретный продукт, реализующий ровно одну из четырёх моделей (документную), а не всю NoSQL-экосистему целиком. Вторая — пытаться использовать key-value хранилище там, где реально нужен поиск по содержимому значений, а не только по ключу — модель для этого структурно не предназначена. Третья — выбирать графовую модель «потому что она выглядит гибкой», не имея задачи, где обход связей — это действительно центральная, часто повторяющаяся операция.

## Что нужно запомнить

Четыре основные модели NoSQL — key-value, document, wide-column и graph — устроены принципиально по-разному и решают структурно разные задачи. Key-value — максимально простой и быстрый доступ по точному ключу. Document — структурированные, вложенные записи с возможностью поиска по полям. Wide-column — огромные объёмы данных с высокой скоростью записи, распределённые по партициям. Graph — данные, где сами связи между объектами являются главным предметом запросов. Выбор между ними зависит от характера данных и запросов, а не от того, какая модель «современнее».

## Практика

1. Для каждой из четырёх моделей приведите свой пример данных (не из урока), которые ей естественно подходят.
2. Объясните, почему key-value хранилище плохо подходит для поиска «всех пользователей старше 30 лет».
3. Система хранит данные датчиков: временная метка, идентификатор устройства, значение. Поток записи — тысячи измерений в секунду. Какая модель кажется наиболее подходящей и почему?
4. Система должна искать «всех людей, с которыми пользователь связан через цепочку до трёх рукопожатий». Какая модель для этого лучше всего приспособлена?
5. Объясните разницу между тем, как key-value и document модели хранят значение — почему документная модель «видит» структуру, а key-value — нет.
6. Приведите пример системы, где было бы разумно использовать сразу две разные модели NoSQL для разных частей данных, и обоснуйте выбор каждой.
7. Объясните, почему утверждение «MongoDB — это и есть NoSQL» некорректно, опираясь на материал этого урока.
