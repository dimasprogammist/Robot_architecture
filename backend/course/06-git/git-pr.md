# Запрос на слияние (PR)

## Цель

Понять PR как обсуждение и проверку перед merge двух веток на хостинге.

## Что уже пройдено

Ветки и push знакомы. PR — социальный слой над слиянием.

## Объяснение с нуля

**Pull Request** (или Merge Request) — предложение: влить коммиты ветки A в ветку B на remote, с обсуждением, проверками и явным approve. Технически под капотом всё тот же merge/rebase графа. Ценность — процесс: дифф виден, CI прогнался, история решения сохранена в веб-интерфейсе.

Локально вы пушите ветку; на сайте открываете PR; после принятия указатель целевой ветки на remote двигается (появится merge-коммит или FF/squash — политика репозитория).

## Термины

- **PR/MR** — запрос на интеграцию ветки.
- **Review** — проверка людьми.
- **CI check** — автоматические проверки на снимке PR.
- **Squash** — схлонуть коммиты при влитии (политика).

## Внутреннее устройство

```text
feature → push → PR в main → review → merge на GitHub → fetch у остальных
```

## Пример

```text
# локально перед PR
git switch -c feature/timeout
# коммиты...
git push -u origin feature/timeout
# далее кнопка PR на хостинге
```

## Разбор

Хороший PR — маленький дифф и понятное намерение. Гигантский PR непросматриваем, как гигантский коммит.

## Ошибки

- PR из грязной истории с секретами.
- Игнорировать падающий CI.
- Вливать не глядя в конфликты на целевой ветке.

## Что запомнить

PR = процесс вокруг слияния снимков. Git под ним тот же.

## Задание

Опишите для учебного изменения: имя ветки, целевая ветка, что должно быть в описании PR.

## Связь со следующим уроком

Последний урок модуля — скелет ежедневного рабочего цикла.

## Ещё раз тем же смыслом

Git не угадывает намерение: он двигает указатели и создаёт объекты по правилам. Рисуйте стрелки «ветка → commit → tree → blob». Контрпример («а если push после rebase?») проявляет цену переписывания хешей. Перескажите урок за две минуты без списка флагов — только снимки и refs. Свой учебный репозиторий ценнее чужого длинного учебника. Сначала модель, потом команда.
