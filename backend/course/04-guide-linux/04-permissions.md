# Права доступа к файлам

## Цель

Научиться читать и менять режим файла: права владельца, группы и остальных, биты каталогов и типичные ошибки с `chmod`/`chown`.

## Исходные знания

Пользователи, группы, UID/GID из предыдущего урока. Общая модель прав доступа из раздела об операционных системах — здесь она конкретизируется до синтаксиса и команд именно Linux.

## Объяснение

У каждого файла есть владелец-пользователь, владелец-группа и режим доступа. Режим задаёт три тройки прав: read, write, execute для owner, group, others. Для обычного файла execute означает «можно запустить как программу». Для каталога execute означает «можно входить в каталог и обходить его имя» — без этого нельзя обратиться к содержимому даже при read.

Read на каталоге позволяет читать список имён. Write на каталоге позволяет создавать и удалять имена внутри (с оговорками про sticky bit в `/tmp`). Поэтому права каталога часто важнее прав файла при создании новых объектов.

Числовая запись `chmod 644` кодирует биты. Символьная `chmod u+x` удобнее точечных правок. `chown` меняет владельца; на многих системах обычный пользователь ограничен в смене владельца.

Специальные биты: setuid/setgid и sticky. setuid на исполняемом файле запускает процесс с UID владельца файла — мощно и опасно. sticky на каталоге (типично `/tmp`) мешает удалять чужие файлы даже при записи в каталог.

ACL расширяют классическую модель, но базовые rwx нужно знать всегда: ими пользуются скрипты, unit-файлы и большинство инструкций.

Проверка прав выполняется ядром при системном вызове. Программа не может «убедить» ядро текстом ошибки — она лишь сообщает EACCES.

Умный минимум для секретов: файл конфигурации с ключом — `600` и владелец службы. Для публичных скриптов — `755`. Для данных группы разработчиков — общая группа и `770`/`760` по политике.

## Термины

**Режим (mode)** — биты rwx и спецбиты файла.

**chmod** — смена режима.

**chown** — смена владельца и/или группы.

**Sticky bit** — ограничение удаления в общих каталогах.

**umask** — маска прав по умолчанию при создании файлов.

## Как это работает

При open ядро выбирает категорию: владелец, группа или others (и учитывает ACL, если есть). Сопоставляет запрошенную операцию с битами. Отказ — ошибка без чтения содержимого.

umask процесса вычитает биты из режима по умолчанию. Поэтому два пользователя могут создавать файлы с разными правами при одинаковых программах.

Для каталогов цепочка пути тоже проверяется: на каждом компоненте нужен execute.

## Пример

```bash
umask
touch /tmp/demo_perm.txt
ls -l /tmp/demo_perm.txt
chmod 600 /tmp/demo_perm.txt
ls -l /tmp/demo_perm.txt
chmod u+x /tmp/demo_perm.txt || true
mkdir /tmp/demo_dir && chmod 750 /tmp/demo_dir
ls -ld /tmp/demo_dir
```

## Разбор

`umask` показывает, какие биты снимаются у новых файлов.

`chmod 600` оставляет чтение/запись только владельцу — типичный шаблон для секретов.

На каталоге `750` даёт владельцу полный доступ, группе — чтение и вход, остальным — ничего.

`ls -l` и `ls -ld` отображают режим и владельцев в привычном виде `rwxr-x---`.

## Ошибки

- Выставлять `777` «чтобы заработало».
- Путать смысл execute у файла и у каталога.
- Открывать секретные ключи правами `644`.
- Забывать, что write на каталоге позволяет удалять имена файлов.

## Что запомнить

- Права — три тройки плюс спецбиты; ядро проверяет их на syscall.
- Для каталогов x — проход, w — создание/удаление имён.
- Секреты — узкие права и правильный владелец.
- umask влияет на права новых файлов.

## Практика

Создайте файл и каталог в `/tmp`. Сделайте файл доступным только вам, каталог — вам и вашей группе без доступа others. Проверьте отображение `ls -l`.

Каталог без x для пользователя делает дочерние файлы недоступными, даже если файл `777` — проверяйте путь целиком.

umask 022 даёт типичные `755/644`; для секретных каталогов ужесточайте.

Смена владельца рекурсивно (`chown -R`) опасна на больших деревьях и symlink — смотрите опции.

В контейнерах UID внутри и снаружи могут расходиться при bind-mount — планируйте numeric UID.
