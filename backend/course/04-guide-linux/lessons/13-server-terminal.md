# Сервер через терминал — повседневная работа

Монитора нет. Нужен устойчивый **маршрут осмотра**, не энциклопедия флагов.

1. Кто я, какой hostname, какое время (`whoami`, `hostnamectl`, `date`).
2. Ресурсы: CPU, память, диск (`df` ≠ `du`; inode тоже кончаются).
3. Службы приложения: status, не «процесс в ps похож».
4. Логи вокруг окна инцидента.
5. Сеть, если симптом снаружи.

Правка маленькая и обратимая: копия конфига, reload/restart, status, healthcheck. Конфиг в файле и в git/ansible, не только в открытом nano. Слепой `upgrade` ядра без окна — риск; читайте, что уедет.

Уникальности хоста запишите: зачем этот drop-in, какой таймер критичен. У робота те же шаги плюс `/dev` и udev. Сначала руками, потом скрипт мониторинга.

```text
доступ → идентичность → ресурсы → службы → логи → сеть
изменение → копия → reload → проверка
```

Rollback: вернуть файл, restart, снова healthcheck. Не чинить пять вещей сразу.

## Практика

### Задание 1. Чеклист входа

Восемь команд первого осмотра вашего стенда. Что смотрите до любой правки `/etc`?

### Задание 2. df vs du

`df` 100%, `du` по `/var` не сходится. Какие две гипотезы (удалённый открытый файл, другой mount)?

### Задание 3. Малое изменение

Нужно сменить порт службы. Порядок: копия, правка, reload vs restart, проверка `ss`, откат. Где ошибка, если пропустить копию?

### Задание 4. Окно логов

Инцидент «около 14:10». Как сузить journalctl и почему «весь журнал с grep error» хуже?

Раздел Linux на этом складывается: хост, права, нянька процессов, пакеты, журнал, вход. Сети как протоколы — отдельный курс.
