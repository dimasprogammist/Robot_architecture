# Пользователи и группы

Процесс в Linux бежит не «от имени человека в чате», а от **чисел**: UID и GID. Имя `alice` — подпись в системных базах. Ядро в проверках прав смотрит на числа. `/etc/passwd` и `/etc/group` (плюс shadow для паролей) описывают локальных пользователей; LDAP/SSSD подставляют те же поля из сети. `getent` читает через этот слой, не только плоский файл.

Обычный пользователь ограничен. `root` — UID 0, обходит большинство проверок. Жить в login как root «чтобы не мешало» — плохая привычка: любая опечатка пишет куда угодно. `sudo` поднимает права на команду с аудитом.

Группы делят доступ между людьми и службами без «всем можно». У процесса основная группа и дополнительные. Файл несёт владельца-пользователя и владельца-группу; биты rwx разбирает следующий урок. Доступ к `/dev/ttyUSB*` или сокету docker часто решается членством в группе, не chmod 777.

Сервисные учётки (`www-data`, пользователи systemd, `nobody`) нужны, чтобы демон не был root. Компрометация службы тогда ограничена её UID. Два разных демона на одном системном пользователе делят весь ущерб. Интерактивный вход сервису не нужен: `/usr/sbin/nologin` вместо login-shell.

Дочерние процессы наследуют UID/GID, пока не сработает легальный переход: sudo, setuid, capabilities, `User=` в юните systemd.

На NFS один и тот же UID 1000 на двух машинах может быть разными людьми — права «как у себя» врут.

```bash
whoami
id
getent passwd "$USER"
getent group "$(id -gn)"
ls -l /etc/passwd
```

`/etc/passwd` часто читается всеми; хэши — в shadow с жёсткими правами. Править passwd руками, не зная блокировок и shadow, — способ сломать вход. `useradd` и `adduser` на разных дистрибутивах не синонимы: смотрите man этой системы, не первую статью из поиска.
