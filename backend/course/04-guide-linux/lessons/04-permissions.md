# Права доступа к файлам

У файла есть владелец (UID), группа (GID) и **режим**: три тройки rwx для owner, group, others. Ядро сверяет их на системном вызове. Программа не уговаривает диск текстом ошибки — она получает EACCES.

Смысл битов зависит от типа. Файл: x — запуск. **Каталог**: x — войти и пройти имя в пути; без x к файлу внутри не обратиться, даже если у файла r. r на каталоге — читать список имён. w на каталоге — создавать и удалять **имена** (не «содержимое файла»). Поэтому права каталога часто важнее прав файла, который вы только что создали.

Число `chmod 644`, символы `chmod u+x`. `chown` меняет владельца; обычному пользователю чужой UID не отдать. umask процесса **снимает** биты у новых файлов — два человека с разным umask получают разный `ls -l` от одной программы.

Спецбиты. setuid на исполняемом: процесс стартует с UID владельца файла — мощно и опасно (passwd). Sticky на `/tmp`: писать в каталог можно, чужое имя не удалить. ACL расширяют модель; инструкции и unit-файлы всё равно говорят языком rwx.

Секрет службы: `600`, владелец сервиса. Скрипт в PATH: `755`. Совместная работа группы: общая группа и `770`/`760` по политике, не `777`.

Цепочка пути: на **каждом** компоненте нужен execute. Нет x на `/home/alice` — не поможет rwx на файле глубже.

```bash
umask
touch /tmp/demo_perm.txt
ls -l /tmp/demo_perm.txt
chmod 600 /tmp/demo_perm.txt
mkdir /tmp/demo_dir && chmod 750 /tmp/demo_dir
ls -ld /tmp/demo_dir
```

`chmod 777`, «чтобы заработало» — дыра, не диагностика. Сначала: какой UID у процесса, какая тройка сработала, есть ли x на каталогах пути.
