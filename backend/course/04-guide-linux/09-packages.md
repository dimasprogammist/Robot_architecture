# Пакетные менеджеры

## Цель

Понять роль пакетного менеджера: зависимость, репозиторий, установка, обновление и почему «разбросать бинарники вручную» ломает сопровождение.

## Исходные знания

FHS и службы. Умение пользоваться терминалом.

## Объяснение

Пакет — архив файлов плюс метаданные: имя, версия, зависимости, скрипты установки. Пакетный менеджер (apt, dnf, zypper, pacman…) скачивает пакеты из репозиториев, разрешает зависимости и раскладывает файлы по FHS, запоминая учёт.

Репозиторий — подписанный источник пакетов дистрибутива. Без подписей и закреплённых источников легко получить подменённый софт. Обновления безопасности приходят тем же каналом.

Установка «вручную в /usr/local» возможна, но тогда вы сами отвечаете за обновления и откат. Смешивание ручных файлов с файлами пакетов приводит к конфликтам: менеджер не знает о ваших правках.

Зависимости бывают обязательные и рекомендуемые. Удаление «лишней» библиотеки может утянуть половину рабочего стола — читайте план действий перед confirm.

Есть слои поверх: snap, flatpak, pip, npm. Они решают другие задачи (изоляция, языковые экосистемы). На системном уровне для демонов дистрибутива предпочтителен нативный пакет или свой пакет/контейнер с понятной политикой.

Версии: «поставить последнюю с GitHub» на проде без фиксации версии — путь к невоспроизводимости. Фиксируйте версии и читайте changelog.

## Термины

**Пакет** — единица поставки ПО с метаданными.

**Репозиторий** — хранилище пакетов дистрибутива.

**Зависимость** — другой пакет, нужный для работы.

**apt/dnf/…** — конкретные менеджеры семейств дистрибутивов.

**Pinning / freeze** — практики удержания версий.

## Как это работает

Клиент обновляет индекс метаданных, считает транзакцию, скачивает архивы, проверяет подписи, распаковывает, запускает maintainer scripts, обновляет базу установленных пакетов.

Откат не всегда тривиален, но база установленных файлов позволяет спросить «какой пакет владеет этим файлом?» — критично при отладке.

Для своих программ собирают пакет или используют контейнер. Оба пути лучше бесконтрольного копирования в `/usr/bin`.

## Пример

```bash
# Debian/Ubuntu-семейство (если доступно)
apt --version 2>/dev/null | head -n 1 || true
# Red Hat-семейство
dnf --version 2>/dev/null | head -n 1 || true

command -v curl
# узнать владельца файла пакетом (пример для dpkg)
dpkg -S "$(command -v bash)" 2>/dev/null || rpm -qf "$(command -v bash)" 2>/dev/null || true
```

## Разбор

Проверка версии менеджера показывает экосистему хоста.

`command -v` находит путь бинарника. Запрос владельца связывает файл с пакетом — ключ к сопровождению.

На разных дистрибутивах команды различаются, принцип учёта один.

## Ошибки

- Ставить всё через `curl | sh` без понимания.
- Мешать ручные файлы с пакетными путями.
- Глушить зависимость «насильно» и ломать систему.
- Не обновлять безопасность месяцами.

## Что запомнить

- Пакетный менеджер знает зависимости и файлы.
- Репозитории и подписи — часть доверия.
- Системные демоны удобнее ставить штатно.
- Воспроизводимость требует версий.

## Практика

Определите, какой пакетный менеджер есть на машине. Найдите, какому пакету принадлежит `bash` или `sh`. Обновите индекс пакетов (без массового upgrade, если не уверены) и посмотрите, что команда предлагает.

Фиксируйте версии в продуктовых образах. `apt-get update && apt-get install -y pkg=ver`.

Удаление пакета не всегда удаляет conf (`purge` vs `remove`). Знайте разницу.

Сторонние репозитории повышают риск. Добавляйте минимально и с подписью.

Инвентаризация: регулярно сохраняйте список установленных пакетов для воспроизводимости хоста.
