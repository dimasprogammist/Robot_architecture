# Проверка наличия и правильности компонентов

## Цель

Понять, как машинное зрение проверяет комплектность изделий и правильность установки отдельных компонентов.

После урока вы должны понимать:

* что такое контроль наличия;
* чем наличие отличается от правильного положения;
* как проверять количество компонентов;
* как проверять ориентацию;
* как строятся контрольные зоны;
* когда достаточно классического алгоритма;
* когда имеет смысл использовать классификацию или детекцию.

## Что такое контроль наличия

Очень распространённая задача:

> Находится ли нужный компонент там, где он должен быть?

Например, изделие должно содержать:

```text
винт
разъём
наклейку
крышку
уплотнение
шайбу
```

Камера проверяет их наличие.

Простейший результат:

```text
ComponentPresent = TRUE
```

или:

```text
ComponentPresent = FALSE
```

## Но наличие — не всё

Компонент может:

* отсутствовать;
* присутствовать;
* быть установлен неправильно;
* быть повернутым;
* быть смещённым;
* иметь неправильный размер;
* иметь неправильный цвет.

Например:

```text
правильно:

┌──────────────┐
│      ●       │
└──────────────┘
```

и:

```text
неправильно:

┌──────────────┐
│          ●   │
└──────────────┘
```

Компонент присутствует в обоих случаях.

Но во втором он установлен неправильно.

## Контрольная зона

Для простого компонента можно определить ROI:

```text
┌──────────────────────┐
│                      │
│      ┌───────┐       │
│      │   ●   │       │
│      └───────┘       │
│                      │
└──────────────────────┘
```

Внутри этой области ожидается определённый объект.

Если он найден:

```text
OK
```

если нет:

```text
NOK
```

## Контроль по яркости

Если компонент сильно отличается от фона, можно использовать порог.

Например:

```python
roi = image[y1:y2, x1:x2]

gray = cv2.cvtColor(
    roi,
    cv2.COLOR_BGR2GRAY
)

_, binary = cv2.threshold(
    gray,
    120,
    255,
    cv2.THRESH_BINARY
)
```

Затем можно определить количество белых пикселей:

```python
count = cv2.countNonZero(binary)
```

Если:

```text
count > threshold
```

компонент, вероятно, присутствует.

## Почему нельзя просто смотреть на среднюю яркость

Допустим, компонент занимает только небольшую часть зоны.

Среднее значение может почти не измениться.

Поэтому полезнее анализировать:

* площадь;
* форму;
* положение;
* контраст;
* контур.

## Проверка площади

Например:

```text
ожидаемая площадь:
1000 ... 1500 px
```

Если найдено:

```text
1250 px
```

то:

```text
OK
```

Если:

```text
400 px
```

возможно:

```text
компонент отсутствует
```

или:

```text
компонент установлен частично
```

## Проверка количества

Предположим, изделие должно содержать четыре винта:

```text
●       ●

●       ●
```

Система ищет четыре объекта.

Результат:

```text
count = 4
```

Если:

```text
count = 3
```

получаем:

```text
NOK
```

## Контроль положения

Количество может быть правильным:

```text
●       ●

●       ●
```

но один винт может находиться не на своём месте:

```text
●       ●

    ●   ●
```

Поэтому после поиска объектов можно проверить координаты.

Например:

```text
винт 1 → X=100 Y=100
винт 2 → X=300 Y=100
винт 3 → X=100 Y=300
винт 4 → X=300 Y=300
```

Для каждой позиции задаётся допуск.

## Контроль ориентации

Некоторые компоненты должны иметь определённую ориентацию.

Например:

```text
правильно:

┌──────────┐
│   →      │
└──────────┘
```

а:

```text
неправильно:

┌──────────┐
│      ←   │
└──────────┘
```

Камера может определить угол:

```text
Angle = 2°
```

и:

```text
Angle = 178°
```

и различить правильную и неправильную установку.

## Полярность

Некоторые компоненты имеют определённую ориентацию:

* разъёмы;
* диоды;
* электронные модули;
* маркировки;
* штекеры.

Например:

```text
правильно:
[ + → ]

неправильно:
[ ← + ]
```

Визуальный контроль может определить ориентацию по форме или маркировке.

## Цветовая проверка

Если компонент должен иметь определённый цвет, можно использовать цветовое пространство HSV.

Например:

```python
hsv = cv2.cvtColor(
    image,
    cv2.COLOR_BGR2HSV
)
```

После этого выделить диапазон цвета.

Это удобно для:

* цветных меток;
* проводов;
* крышек;
* маркировок;
* индикаторов.

## Проверка маркировки

На детали может быть:

```text
MODEL-A
```

а требуется:

```text
MODEL-B
```

В этом случае одной геометрии недостаточно.

Можно использовать:

* OCR;
* сравнение шаблонов;
* классификацию;
* поиск характерных признаков.

Например:

```text
camera
  ↓
text region
  ↓
OCR
  ↓
"MODEL-B"
  ↓
compare
  ↓
OK
```

## Проверка правильного компонента

Допустим, на рабочем месте могут находиться две похожие детали:

```text
Component A
Component B
```

Нужно проверить, что установлен именно A.

Можно использовать:

* форму;
* размеры;
* цвет;
* маркировку;
* характерные признаки;
* классификацию изображения.

## Классический алгоритм

Если компоненты всегда находятся в фиксированных местах:

```text
позиция 1 → винт
позиция 2 → разъём
позиция 3 → наклейка
```

то можно создать три независимые зоны:

```text
ROI 1
ROI 2
ROI 3
```

и проверять каждую отдельно.

Преимущество:

* просто;
* быстро;
* предсказуемо;
* легко диагностировать.

## Детекция объектов

Если компоненты могут находиться в разных местах:

```text
●         ●

      ●

  ●
```

фиксированные ROI становятся неудобными.

Тогда можно использовать детекцию объектов:

```text
изображение
    ↓
детектор
    ↓
объект 1
объект 2
объект 3
объект 4
```

Для каждого объекта можно получить:

```text
class
confidence
bounding box
```

## Проверка по количеству и классу

Например, система ожидает:

```text
2 × Screw
1 × Connector
1 × Label
```

Детектор вернул:

```text
Screw      → 2
Connector  → 1
Label      → 1
```

Результат:

```text
OK
```

Если:

```text
Screw      → 1
Connector  → 1
Label      → 1
```

то:

```text
NOK
```

## Проверка последовательности сборки

Машинное зрение может использоваться не только для финального контроля.

Например, после каждой операции:

```text
операция 1
   ↓
камера
   ↓
винт установлен?
   ↓
операция 2
   ↓
камера
   ↓
разъём установлен?
```

Так камера становится частью процесса сборки.

## Ошибка оператора

Если человек собирает изделие вручную, система может контролировать результат.

Например:

```text
оператор
   ↓
устанавливает компонент
   ↓
камера
   ↓
проверка
   ↓
OK → продолжить
NOK → показать ошибку
```

Это позволяет обнаружить ошибку до передачи изделия на следующий этап.

## Визуальная подсказка

Система может не только сказать:

```text
NOK
```

но и показать место ошибки:

```text
┌─────────────────────┐
│                     │
│       █████         │
│       █████  ← NOK  │
│                     │
└─────────────────────┘
```

Так оператору проще исправить проблему.

## Контроль правильной установки

Предположим, компонент должен находиться внутри допустимой области:

```text
┌──────────────────┐
│   ┌──────────┐   │
│   │ компонент│   │
│   └──────────┘   │
└──────────────────┘
```

Система может проверить:

```text
X
Y
Angle
```

и сравнить с допустимыми диапазонами.

Например:

```text
X = 250 ± 2 мм
Y = 120 ± 2 мм
Angle = 0 ± 3°
```

## Проверка нескольких условий

Для одного компонента можно сделать:

```text
Present
AND
Position_OK
AND
Angle_OK
AND
Size_OK
```

Только если все условия истинны:

```text
Component_OK = TRUE
```

Например:

```text
Present      = TRUE
Position_OK  = TRUE
Angle_OK     = TRUE
Size_OK      = FALSE

Component_OK = FALSE
```

## Архитектура проверки

Общий процесс:

```text
trigger
  ↓
camera
  ↓
image
  ↓
ROI / detection
  ↓
component localization
  ↓
geometry / color / OCR
  ↓
validation
  ↓
OK / NOK
```

## Передача результата

Промышленная система может передать в ПЛК:

```text
InspectionDone = TRUE
InspectionOK = TRUE
```

или:

```text
InspectionDone = TRUE
InspectionOK = FALSE
```

Дополнительно:

```text
ErrorCode = 3
```

Например:

```text
1 = component missing
2 = wrong position
3 = wrong orientation
4 = wrong component
```

Так ПЛК может выполнить соответствующее действие.

## Почему лучше разделять ошибки

Если система выдаёт только:

```text
NOK
```

оператор не знает причины.

Гораздо полезнее:

```text
NOK
Reason = COMPONENT_MISSING
```

или:

```text
NOK
Reason = WRONG_ORIENTATION
```

Это упрощает диагностику производства.

## Главное

Контроль компонентов можно строить от простого к сложному:

```text
фиксированная ROI
    ↓
порог / цвет / контур
    ↓
положение
    ↓
ориентация
    ↓
геометрия
    ↓
OCR / шаблон
    ↓
детекция / классификация
```

Нужно выбирать самый простой метод, который надёжно решает задачу.

Основная идея:

> Машинное зрение может контролировать не только наличие компонента, но и его идентичность, положение, ориентацию, размеры и правильность установки.

Так vision-система становится инструментом контроля всего процесса сборки.
