# Перенос линии (rebase)

## Цель

Понять rebase как создание новых коммитов поверх другой базы.

## Что уже пройдено

Merge сохраняет развилку. Rebase переписывает линию.

## Объяснение с нуля

**Rebase** повторяет смысловые шаги коммитов поверх другого основания. На деле создаются **новые** commit-объекты с новыми хешами. Старые объекты могут остаться достижимы через reflog, но ветка указывает на новые.

Типичный сюжет: `feat` росла от старого `main`, `main` ушёл вперёд — переносим шаги `feat` после нового конца `main`. Это переписывание графа. Уже опубликованные коммиты так двигать опасно для коллег.

## Термины

- **Rebase** — перенос последовательности на новую базу.
- **Новый хеш** — неизбежен (другой родитель).
- **Upstream** — база, на которую переносят.

## Внутреннее устройство

```text
до:  main A—B—C ; feat A—B—D—E
после: feat A—B—C—D'—E'
```

D' и E' — другие объекты, даже если содержимое похоже.

## Пример

```bash
git switch feat
git rebase main
```

## Разбор

Merge добавляет узел с двумя родителями. Rebase строит новую линию. Выбор — договорённость команды, не «физика правильнее».

## Ошибки

- Rebase общей ветки, которую уже тянут другие.
- Путать с merge.
- Считать, что старые коммиты мгновенно стёрты с диска.

## Что запомнить

Rebase создаёт новые коммиты на новой базе. Для локальных веток удобно; для общих — осторожно.

## Задание

На учебной ветке сделайте rebase на обновлённый main. Сравните хеши до/после.

## Ещё раз тем же смыслом

Git не угадывает намерение: он двигает указатели и создаёт объекты по правилам. Рисуйте стрелки «ветка → commit → tree → blob». Контрпример («а если push после rebase?») проявляет цену переписывания хешей. Перескажите урок за две минуты без списка флагов — только снимки и refs. Свой учебный репозиторий ценнее чужого длинного учебника. Сначала модель, потом команда.
