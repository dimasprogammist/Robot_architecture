# Fetch: забрать объекты

## Цель

Понять fetch как докачку объектов и обновление remote-tracking refs.

## Что уже пройдено

Локальный клон есть. Remote мог уйти вперёд.

## Объяснение с нуля

**Fetch** спрашивает remote: какие новые объекты и куда сдвинулись refs. Скачивает недостающие blob/tree/commit и обновляет `refs/remotes/…`. Ваша текущая ветка и рабочее дерево **сами не меняются**.

Это безопасно для осмотра: можно смотреть `origin/main`, сравнивать, решать merge/rebase. Fetch отделяет «узнать новости» от «влить в мою линию».

## Термины

- **Fetch** — получить объекты + обновить tracking-refs.
- **Prune** — убрать устаревшие tracking-refs (опционально).
- **Не трогает** рабочее дерево и `refs/heads/*` (обычный fetch).

## Внутреннее устройство

```text
до:  origin/main → C3 ; main → C3
на сервере main → C5
после fetch: origin/main → C5 ; main всё ещё C3
```

## Пример

```bash
git fetch origin
git log main..origin/main --oneline
```

## Разбор

Разница `main..origin/main` — коммиты, которые есть на tracking-ref, но не в вашем main. Это кандидаты к вливанию.

## Ошибки

- Ждать, что fetch обновит файлы в редакторе.
- Путать fetch и pull.
- Игнорировать, что объекты уже локальны после fetch — сеть для этого шага больше не нужна.

## Что запомнить

Fetch обновляет знание о remote. Витрина и ваши ветки остаются на месте, пока вы сами не сольёте.

## Задание

Сделайте fetch и сравните `main` с `origin/main` через log. Опишите словами, кто впереди.

## Связь со следующим уроком

Дальше — pull: fetch плюс интеграция в текущую ветку.

## Ещё раз тем же смыслом

Git не угадывает намерение: он двигает указатели и создаёт объекты по правилам. Рисуйте стрелки «ветка → commit → tree → blob». Контрпример («а если push после rebase?») проявляет цену переписывания хешей. Перескажите урок за две минуты без списка флагов — только снимки и refs. Свой учебный репозиторий ценнее чужого длинного учебника. Сначала модель, потом команда.
