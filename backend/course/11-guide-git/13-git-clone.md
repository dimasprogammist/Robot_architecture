# Клонирование

## Цель

Понять clone как копирование объектов и установку remote + tracking.

## Что уже пройдено

Имя origin и remote-модель знакомы.

## Объяснение с нуля

**Clone** создаёт новый локальный репозиторий, забирает доступные объекты с URL, настраивает `origin`, обычно checkout главной ветки. Это не «скачать ZIP без истории»: у вас появляется полноценная база `.git` с графом коммитов (в типичном полном клоне).

После clone рабочее дерево соответствует снимку выбранной ветки. История уже локальна — `git log` работает офлайн.

## Термины

- **Clone** — создать репозиторий из удалённой копии.
- **Shallow clone** — урезанная история (особый режим; знать, что он существует).
- **Checkout после clone** — витрина под tip ветки.

## Внутреннее устройство

```text
сервер: objects + main→C10
после clone у вас: objects (нужные) + main→C10 + origin→url + origin/main→C10
```

## Пример

```bash
git clone <url> myproj
cd myproj
git log --oneline -5
```

## Разбор

ZIP с сайта даёт файлы без графа. Clone даёт модель снимков. Для учёбы и работы почти всегда нужен именно граф.

## Ошибки

- Редактировать в клоне и ждать, что сервер сам узнает без push.
- Клонировать вложенно внутрь другого репозитория без нужды.
- Путать «скачал код» и «настроил remote».

## Что запомнить

Clone = локальная база объектов + origin + checkout. История копируется, не только текущие файлы.

## Задание

Клонируйте любой учебный публичный репозиторий и убедитесь, что `git log` показывает коммиты без сети.

## Связь со следующим уроком

Дальше — fetch: обновить знание о remote без слияния в вашу ветку.

## Ещё раз тем же смыслом

Git не угадывает намерение: он двигает указатели и создаёт объекты по правилам. Рисуйте стрелки «ветка → commit → tree → blob». Контрпример («а если push после rebase?») проявляет цену переписывания хешей. Перескажите урок за две минуты без списка флагов — только снимки и refs. Свой учебный репозиторий ценнее чужого длинного учебника. Сначала модель, потом команда.
