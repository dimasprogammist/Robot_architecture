# Коммит — снимок

## Цель

Понять commit: tree, родители, сообщение; как ветка сдвигается.

## Что уже пройдено

Индекс готов. Пора записать снимок в историю.

## Объяснение с нуля

**Коммит** фиксирует: корневое tree, родительский коммит (или несколько), автор/время, сообщение. Это не «патч»; патч вычисляют сравнением деревьев.

При создании: из индекса собирается tree → пишется commit с родителем = текущий HEAD → указатель ветки переписывается на новый хеш. Если HEAD смотрит на ветку, он «едет» вместе с ней.

Неизменившиеся файлы часто указывают на те же blob — снимок логически полный, физически с переиспользованием объектов.

## Термины

- **Commit** — объект снимка с метаданными.
- **Родитель** — предыдущий коммит.
- **Сообщение** — зачем снимок, не дамп diff.
- **Хеш** — адрес объекта; изменилось содержимое — другой адрес.

## Внутреннее устройство

```text
refs/heads/main ──► C3
C3 → T3, parent C2
C2 → T2, parent C1
C1 → T1
```

## Пример

```bash
git add note.txt
git commit -m "Добавить заметку со скоростью"
git log --oneline
```

## Разбор

Сообщение «правки» бесполезно. Сообщение «фиксируем чтение энкодера после калибровки» связывает снимок с намерением.

## Ошибки

- Гигантский коммит раз в неделю.
- «Подправить» уже опубликованный коммит без понимания смены хеша.
- Забыть, что коммит локален, пока не отправлен.

## Что запомнить

Коммит = tree + родители + метаданные. Ветка двигается на новый commit. Diff — производное.

## Задание

Сделайте два коммита с осмысленными сообщениями. Нарисуйте C1→C2 и куда указывает ветка.

## Ещё раз тем же смыслом

Git не угадывает намерение: он двигает указатели и создаёт объекты по правилам. Рисуйте стрелки «ветка → commit → tree → blob». Контрпример («а если push после rebase?») проявляет цену переписывания хешей. Перескажите урок за две минуты без списка флагов — только снимки и refs. Свой учебный репозиторий ценнее чужого длинного учебника. Сначала модель, потом команда.
