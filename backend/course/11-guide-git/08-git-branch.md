# Ветки как указатели

## Цель

Увидеть ветку как подвижное имя на commit, а не копию папки.

## Что уже пройдено

Цепочка коммитов есть. Ветка держит «конец» линии.

## Объяснение с нуля

**Ветка** — ref на коммит. Создать ветку — новое имя на тот же (или выбранный) коммит. Это дёшево: файлы проекта не копируются.

Пока указатели совпадают, отличаются только имена. Новый коммит двигает ту ветку, на которую смотрит HEAD. Другая остаётся — линии расходятся.

Обычно HEAD содержит `ref: refs/heads/main`, а не голый хеш. Detached HEAD (прямой хеш) не двигает ветку — легко «потерять» коммиты из виду.

## Термины

- **Ветка** — ref → commit.
- **Текущая ветка** — цель HEAD.
- **Расхождение** — разные концы.
- **Переключение** — сменить HEAD и обновить рабочее дерево.

## Внутреннее устройство

```text
main ──► C2
feat ──► C2
# commit на feat:
feat ──► C3
main ──► C2
```

Файлы в `refs/heads/` хранят хеши (иногда в packed-refs — модель та же).

## Пример

```bash
git branch feat
git switch feat
# правка, add, commit
git switch main
```

## Разбор

«Я на ветке» = HEAD → имя → commit → tree → файлы. Не «скрытая полная копия проекта».

## Ошибки

- Путать ветку с `origin/main`.
- Коммитить в detached HEAD.
- Имена вроде `new`, `fix2`.

## Что запомнить

Ветка = указатель. Расхождение = разные коммиты. Переключение меняет витрину.

## Задание

Создайте ветку, сделайте коммит, вернитесь. Нарисуйте два указателя на разные хеши.

## Связь со следующим уроком

Дальше — слияние: соединить линии (FF или merge-коммит).

## Ещё раз тем же смыслом

Git не угадывает намерение: он двигает указатели и создаёт объекты по правилам. Рисуйте стрелки «ветка → commit → tree → blob». Контрпример («а если push после rebase?») проявляет цену переписывания хешей. Перескажите урок за две минуты без списка флагов — только снимки и refs. Свой учебный репозиторий ценнее чужого длинного учебника. Сначала модель, потом команда.
