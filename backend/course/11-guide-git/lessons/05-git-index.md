# Индекс (staging)

Коммит не обязан забирать «всё, что красное в редакторе». **Индекс** — заготовка следующего снимка: какие пути и какие хеши содержимого войдут в коммит, если его сделать сейчас. Это файл(ы) в `.git`, не облако и не вторая копия проекта.

`git add путь` читает байты с диска, при необходимости кладёт blob, обновляет индекс. Можно добавить два файла из пяти. Можно добавить кусок файла (`git add -p`) — тот же слой, тоньше.

Три возраста одного пути:

```text
диск:   a.py версия 3, b.py версия 2
индекс: a.py v3,       b.py v1
HEAD:   a.py v2,       b.py v1
следующий commit возьмёт индекс: a=v3, b=v1
```

На диске `b` уже новее, но в снимок пойдёт то, что в индексе. Это не баг, а смысл staging: вы собираете кадр.

```bash
echo one > a.txt
echo two > b.txt
git add a.txt
# b.txt ещё не в индексе — в коммит не войдёт
```

`git restore --staged` снимает с индекса, файлы на диске оставляет. Путать со `restore` рабочего дерева — затереть черновик.

Коммит строит tree **из индекса**, не «из всего, что видит ls». Забыли add — в истории старое.

## Практика

### Задание 1. Два файла

Измените два файла, добавьте один. Что попадёт в коммит? Как это увидеть до commit?

### Задание 2. Снова правите

После add снова меняете тот же файл на диске. Сколько «версий» пути теперь? Что возьмёт commit без повторного add?

### Задание 3. Зачем слой

Зачем не коммитить сразу с диска, минуя индекс? Приведите ситуацию «в коммите только часть правок».
