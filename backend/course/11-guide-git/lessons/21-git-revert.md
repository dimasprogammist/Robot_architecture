# Revert: новый коммит-отмена

**Revert** не двигает ветку в прошлое. Он берёт изменения выбранного коммита и применяет **обратные**, новым снимком. История публичная остаётся честной: «вот мы отменили то».

Типично для `main`, который уже у всех. Reset там — война force-push. Revert — ещё один коммит, pull проходит.

Revert merge-коммита требует указать родителя (`-m`): какую сторону считать «основной». Без этого Git не знает, что считать обратным.

Конфликт при revert — норма, если после отменяемого коммита файл ещё меняли. Разрешаете как обычно.

Не путать revert с «вырезать коммит из середины интерактивом»: это снова новые хеши хвоста.

### Задание 1. Зачем новый снимок

Почему для общей ветки revert безопаснее reset? Что видит коллега после pull?

### Задание 2. Не последний

Нужно отменить коммит из середины, не трогая более новые нужные. Почему revert подходит, а `reset` к нему — нет?

### Задание 3. Merge

Revert merge без `-m`. Что Git не понимает?

### Задание 4. Дважды

Revert уже revert'нутого. Какой смысл у второго обратного (вернуть фичу)?
