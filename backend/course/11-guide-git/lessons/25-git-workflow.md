# Рабочий процесс

Команды из уроков складываются в ритуал, а не в религию. Типичный поток для учебной команды робота:

1. `switch main`, fetch, подтянуть (merge или pull).
2. Ветка задачи `feat/lidar-filter` от свежего main.
3. Мелкие коммиты с понятными сообщениями, push, PR.
4. Ревью, CI, squash или merge в main.
5. Локально подтянуть main, удалить ветку.

Альтернативы: trunk-based (короткие ветки), git-flow (release/hotfix) — тяжелее, чем нужно стенду из трёх человек. Выбирают по частоте релизов и числу рук, не по красивой схеме из блога.

Боль: долгоживущая ветка без rebase/merge main — конфликты в конце. Коммиты «fix» без сюжета — bisect слепой. Force на shared ветке — чужие клоны в аду.

Локально вы боги истории своей ветки до первого общего push. После — договорённость важнее удобства rebase.

Курс Git здесь заканчивается моделью: снимки, указатели, три дерева, сеть как обмен объектами, хостинг как люди поверх. Дальше — привычка смотреть `status` и `log --graph` до «магии».

## Практика

### Задание 1. Свой ритуал

Опишите восемь команд от «задача в трекере» до «в main на origin» для вашего репозитория. Где fetch, где не force?

### Задание 2. Долгая ветка

Две недели feat без подтягивания main. Что сломается на PR и как дешевле было не копить?

### Задание 3. Сообщения

Два сюжета: поиск бага через bisect и чтение PR. Какие сообщения помогают в каждом и какие бесполезны?

### Задание 4. Три дерева

Перед push `status` чистый, но вы «вроде правили конфиг». Какие три места проверить, чтобы не пушить воздух и не оставить правки только в редакторе?
