# Pull: забрать и влить

## Цель

Понять pull как fetch + merge (или rebase) в текущую ветку.

## Что уже пройдено

Fetch отделяет получение от интеграции. Pull совмещает.

## Объяснение с нуля

**Pull** по умолчанию делает fetch, затем вливает remote-tracking ветку в текущую (часто merge). Можно настроить pull через rebase — тогда после fetch выполняется rebase. В любом случае меняются и объекты/tracking-refs, и (обычно) ваша ветка и рабочее дерево.

Новичку полезно сначала fetch+посмотреть, потом merge. Pull удобен, когда доверяете автоматической интеграции.

## Термины

- **Pull** — fetch + интеграция.
- **Pull with rebase** — fetch + rebase вместо merge.
- **Conflict on pull** — интеграция не собрала tree автоматически.

## Внутреннее устройство

```text
fetch: origin/main → C5
merge main ← origin/main: main → M (или FF на C5)
```

## Пример

```bash
git pull origin main
# эквивалент по смыслу: fetch, затем merge origin/main
```

## Разбор

Если есть локальные коммиты и удалённые — возможен merge-коммит или rebase, в зависимости от настроек. Конфликты те же, что при обычном merge/rebase.

## Ошибки

- Тянуть вслепую на грязном дереве без понимания статуса.
- Путать «pull скачал ZIP» с обновлением графа.
- Думать, что pull всегда fast-forward.

## Что запомнить

Pull = узнать новости + влить в текущую линию. Для обучения полезно разделять шаги.

## Задание

Один раз сделайте вручную `git fetch` и `git merge origin/main`, затем сравните ощущение с `git pull`.

## Связь со следующим уроком

Дальше — push: отправить ваши коммиты и сдвинуть указатель на remote.

## Ещё раз тем же смыслом

Git не угадывает намерение: он двигает указатели и создаёт объекты по правилам. Рисуйте стрелки «ветка → commit → tree → blob». Контрпример («а если push после rebase?») проявляет цену переписывания хешей. Перескажите урок за две минуты без списка флагов — только снимки и refs. Свой учебный репозиторий ценнее чужого длинного учебника. Сначала модель, потом команда.
