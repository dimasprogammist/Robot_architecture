# Нормализация

Если в каждой задаче лежит `user_name`, смена Ann → Anna — обновление тысяч строк, и часть обязательно забудете. Это **аномалия обновления**. **Нормализация** выносит сущность в свою таблицу и оставляет ключ.

Грубо, без зубрёжки номеров форм:

- значения атомарные, не список в ячейке;
- неключевые признаки зависят от ключа строки, не от соседнего неключевого («город клиента» не должен жить в каждой строке товара заказа).

На практике: одна сущность — одна таблица. Имя человека — в `users`. Задача знает `user_id`. Имя в отчёте появляется JOIN-ом в момент чтения.

```sql
SELECT t.title, u.name
FROM tasks t
JOIN users u ON u.id = t.user_id
WHERE u.id = 5;
```

Плохо: `tasks(id, title, user_name)`. Хорошо: ключ + справочник. Ann→Anna трогает одну строку `users`.

Таблица `orders(order_id, customer_name, customer_city, product)` врёт сразу несколько раз: город копируется, товар не позиция с количеством, клиент не сущность. Режут на `customers`, `orders`, `order_items` (и `products`, если товар повторяется).

Цена нормализации — JOIN при чтении. Иногда **денормализуют** сознательно: кэш «число открытых задач» на пользователе, чтобы не считать COUNT каждый раз. Риск — кэш разойдётся с истиной. Без измерения нагрузки нормализовать «до боли» и денормализовать «на глаз» одинаково вредно.
