# Ограничения

Форма браузера не пускает пустой заголовок. Второй клиент — скрипт без формы. Если правило живёт только в UI, в таблицу всё равно въедет мусор. **Ограничение** — правило, которое СУБД проверяет при записи. PK и FK уже такие. Рядом стоят NOT NULL, UNIQUE, CHECK.

`NOT NULL` — значение должно быть. `UNIQUE` — не повторяться (NULL в уникальном столбце разные СУБД трактуют по-разному; не стройте на этом тонкую логику). `CHECK` — предикат: приоритет от 1 до 5, статус из короткого списка.

```sql
CREATE TABLE tasks (
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('todo', 'doing', 'done')),
  priority INTEGER NOT NULL CHECK (priority BETWEEN 1 AND 5)
);
INSERT INTO tasks (id, title, status, priority)
VALUES (1, 'A', 'todo', 3);
-- priority 9 → отказ CHECK
-- title NULL → отказ NOT NULL
-- status 'donee' → отказ CHECK
```

Отклонённая вставка строки не создаёт. В транзакции дальше — откат оператора или всей транзакции, как настроено. Читать таблицу ограничения «не лечат»: старый мусор останется, пока не проверите отдельно.

UNIQUE на email уместен, если один ящик — один пользователь. Общий отдел `info@` на двоих — тогда уникальность врёт предмету.

Лучше поймать на INSERT, чем чистить годы прода. Валидация в приложении всё равно нужна (понятные сообщения), но она не замена ограничению: обойти код легче, чем движок.
