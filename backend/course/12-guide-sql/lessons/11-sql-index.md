# Индексы

Сто тысяч задач, запрос «все задачи пользователя 5». Без помощи движок читает таблицу с начала. **Индекс** — отдельная структура (часто дерево), которая по значению столбца сразу ведёт к нужным строкам. Первичный ключ уже проиндексирован. Внешний ключ почти всегда стоит индексировать: и поиск детей, и проверка FK при DELETE родителя.

Цена: место и более тяжёлые INSERT/UPDATE/DELETE — надо обновить дерево. Десять индексов «на всякий случай» на таблице из тысячи строк часто медленнее, чем seq scan: писать дорого, читать выигрыша нет.

Селективность: индекс полезен, когда условие отсекает большую часть строк. Флаг `done` 50/50 — прыжок по индексу может не окупиться, планировщик возьмёт полное сканирование. Это не «индекс сломался».

```sql
CREATE INDEX idx_tasks_user ON tasks(user_id);
CREATE INDEX idx_tasks_user_created ON tasks(user_id, created_at);

EXPLAIN QUERY PLAN
SELECT id, title FROM tasks WHERE user_id = 5;

EXPLAIN QUERY PLAN
SELECT id, title FROM tasks
WHERE user_id = 5
ORDER BY created_at DESC
LIMIT 20;
```

Список «задачи пользователя по времени» любит составной индекс `(user_id, created_at)`: и фильтр, и порядок. Один только `created_at` найдёт время по всей таблице, потом придётся отфильтровать чужих пользователей.

`SELECT *` мешает покрывающему индексу: даже найдя id, движок идёт в таблицу за остальными столбцами. Если API нужны два поля — просите два.

Планировщик выбирает seq scan или index scan. Неверный индекс — мёртвый груз. EXPLAIN подробнее будет отдельным уроком; сейчас достаточно создать индекс и сравнить план до и после на учебной базе.

## Практика

### Задание 1. Boolean

Нужен ли индекс только по `done` при ~50/50? Когда `done = 0` вдруг станет селективным?

### Задание 2. Список

Почему для ленты задач пользователя одного индекса по `created_at` мало? Предложите составной.

### Задание 3. INSERT

Что индекс делает лишнего на каждой вставке? Когда на маленькой таблице десять индексов хуже полного скана?

### Задание 4. FK

Зачем индекс по `tasks.user_id`, если FK уже «есть»? Что станет дорогим при удалении пользователя без этого индекса?

Дальше несколько изменений как одна работа: транзакции.
