# Реляционная модель

JSON любит вкладывать: у пользователя внутри массив задач, у задачи — массив комментариев. Пока документ один и маленький, это читается. Как только нужно «все открытые задачи всех людей» или «Ann сменила имя» — вы либо обходите всех, либо копируете имя в каждую задачу и забываете обновить три копии.

Реляционная модель режет мир иначе. **Таблица** — набор однотипных фактов. Строка — один факт. Столбец — одно свойство с типом. Связь «у пользователя много задач» — не массив внутри пользователя, а столбец `user_id` в таблице задач: число, которое указывает на строку в `users`.

```sql
CREATE TABLE users (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL
);
CREATE TABLE tasks (
  id INTEGER PRIMARY KEY,
  user_id INTEGER NOT NULL,
  title TEXT NOT NULL
);
```

Строка `tasks (10, 5, 'Отчёт')` значит: есть задача 10, она принадлежит пользователю 5, заголовок такой-то. Если пользователя 5 нет, внешний ключ (следующий урок подробно) может запретить вставку — факт без хозяина в эту модель не лезет.

Порядок строк в таблице сам по себе не «история мира». Кто последний — спрашивают `ORDER BY`, не «как физически легли на диск». Операции думают множествами: отфильтровать, взять столбцы, соединить таблицы. JOIN потом склеит имя Ann с её задачами в момент чтения, не храня имя десять раз.

Одна таблица «на всё» (`id, user_name, task_title, comment_text, product_json`) снова смешивает сущности. Тогда правка комментария рискует задеть задачу, а индекс по «всему подряд» теряет смысл.

Заказ в магазине тем же приёмом: не массив товаров в ячейке заказа, а `orders` + `order_items` со ссылкой на заказ и на товар. Количество и цена позиции живут в строке позиции — это отдельный факт.

## Практика

### Задание 1. Заказ

Разложите заказ с несколькими товарами на таблицы без массива в одной строке. Какие факты в какой таблице? Где количество?

### Задание 2. Согласованные id

Три пользователя, шесть задач, у каждой `user_id` с существующим человеком. Какая седьмая строка задач стала бы ложью, если включить внешний ключ?

### Задание 3. Смена имени

Ann стала Anna. Сколько строк трогаете, если `name` копировали в каждую задачу? Сколько — если имя только в `users`?

### Задание 4. «Последние»

Почему «последние задачи» нельзя надёжно взять как «хвост файла вставки»? Какой столбец и какой `ORDER BY` вы добавите?
