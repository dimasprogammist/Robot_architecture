# SELECT

SELECT — основной способ читать таблицы: какие **столбцы**, какие **строки**, в каком порядке и сколько штук. Без LIMIT на огромной таблице легко убить API. Нужны ACID на уровне идей и таблица `tasks`.

Учебный набор:

```text
id  user_id  title           done  priority
1   5        Купить молоко   0     1
2   5        Отчёт           1     2
3   7        Звонок          0     3
4   5        Почта           0     1
5   7        Ревью           1     2
```

Проекция — список столбцов. Фильтр — `WHERE`. Порядок — `ORDER BY`. Обрезка — `LIMIT` / `OFFSET`. Каждый кусок меняет результат независимо: сначала представьте множество строк, потом столбцы.

```sql
SELECT id, title
FROM tasks
WHERE done = 0;
```

Результат: строки 1, 3, 4. Строка 2 и 5 отфильтрованы. Столбец `priority` в выдачу не попал — проекция его отбросила.

```sql
SELECT id, title
FROM tasks
WHERE done = 0
ORDER BY id
LIMIT 2;
```

После фильтра те же три строки, по `id` это 1, 3, 4. `LIMIT 2` оставляет 1 и 3. Строка 4 не «пропала из таблицы» — её обрезала выдача.

```sql
SELECT id, title
FROM tasks
WHERE done = 0
ORDER BY id
LIMIT 2 OFFSET 2;
```

`OFFSET 2` пропускает 1 и 3, остаётся 4. Пустая страница — нормальный ответ, не ошибка схемы.

```sql
SELECT id, title
FROM tasks
WHERE user_id = 5 AND done = 0
ORDER BY priority DESC, id;
```

Два условия в `WHERE` сужают до задач пользователя 5, которые не закрыты: 1 и 4. Оба `priority = 1`, поэтому второй ключ `id` решает порядок: сначала 1, потом 4.

```sql
SELECT COUNT(*) AS open_cnt
FROM tasks
WHERE done = 0;
```

Агрегат без `GROUP BY` — одна строка: `3`. Это тоже SELECT, только схлопывает множество.

Планировщик может взять индекс по `WHERE` / `ORDER BY`. `SELECT *` в горячем API тащит лишние столбцы и мешает покрывающим индексам.

## Типичные ошибки

- `SELECT *` в горячем API.
- `ORDER BY` без индекса на больших данных без нужды.
- Путать `OFFSET` для пагинации с «страница всегда одной длины» при удалении строк между запросами.

## Что запомнить
