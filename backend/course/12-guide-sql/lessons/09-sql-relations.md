# Типы связей

Внешний ключ уже умеет «указать на родителя». Осталось выбрать форму.

**Один ко многим (1:N)** — обычный случай. У пользователя много задач: `tasks.user_id` → `users.id`. Сторона «много» держит FK.

**Один к одному (1:1)** — редкий профиль, который жалко тащить в широкую `users`: таблица `user_profiles` с `user_id` одновременно PK или UNIQUE. Не плодите 1:1 без причины: лишний JOIN на каждый экран.

**Многие ко многим (N:M)** — у задачи несколько тегов, у тега несколько задач. Один FK не справится. Нужна **таблица связи**: две ссылки и обычно первичный ключ из пары.

```text
tags:        1 sql    2 python
task_tags:   задача 10 — тег 1
             задача 10 — тег 2
             задача 11 — тег 1
```

Задача 10 с двумя тегами, тег sql на двух задачах.

```sql
SELECT tags.name
FROM task_tags
JOIN tags ON tags.id = task_tags.tag_id
WHERE task_tags.task_id = 10;
```

```sql
SELECT t.title, tags.name
FROM tasks t
JOIN task_tags tt ON tt.task_id = t.id
JOIN tags ON tags.id = tt.tag_id
WHERE t.id IN (10, 11);
```

Первый запрос — имена тегов одной задачи. Второй — пары задача/тег.

Ошибка новичка: `'1,2,3'` в TEXT. Тогда нельзя нормально JOIN, уникальность тега, индекс по «есть ли тег sql». Связь — столбец FK или таблица пар, не список в строке.

Студенты и курсы — тот же N:M: `students`, `courses`, `enrollments(student_id, course_id)`.

JOIN потом собирает картину обратно. Нормализация специально размазала факты, чтобы не врать при обновлении.
