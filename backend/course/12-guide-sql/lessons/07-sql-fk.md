# Внешний ключ

Задача принадлежит пользователю. В строке задач лежит `user_id`. Откуда уверенность, что такой пользователь есть? Если только из Python — любой скрипт вставит `9` и получит сироту.

**Внешний ключ** — правило СУБД: значение столбца (или нескольких) должно существовать в первичном или уникальном ключе другой таблицы. `tasks.user_id` ссылается на `users.id`. Родитель — `users`, дочерняя — `tasks`.

```sql
CREATE TABLE tasks (
  id INTEGER PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id),
  title TEXT NOT NULL
);
INSERT INTO tasks (id, user_id, title) VALUES (10, 1, 'A');
-- INSERT INTO tasks (id, user_id, title) VALUES (12, 9, 'X');
-- отказ: нет users.id = 9
```

Это ошибка **ограничения**, не «Python упал». Её ловят в приложении как отказ записи и отдают клиенту 400/409, а не как SyntaxError.

При `DELETE` родителя политика разная:

- запрет (RESTRICT / без CASCADE) — «сначала убери задачи»;
- CASCADE — удалить потомков вместе с родителем;
- SET NULL — обнулить ссылку, если столбцу можно быть NULL.

Комментарии к задаче чаще CASCADE: умерла задача — ничьи реплики не нужны. Счета к клиенту чаще запрет: нельзя стереть клиента с живой бухгалтерией «заодно». Каскад везде — способ снести полбазы одним DELETE.

Без FK «для скорости» за год копится мусор: задачи на удалённых людей, отчёты в никуда. Целостность потом не восстановить скриптом с первого раза.

Проверка на INSERT/UPDATE дочерней строки: есть ли родитель. На DELETE родителя — выбранная политика.
