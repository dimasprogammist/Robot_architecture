# Что такое база данных

Трекер задач на одном ноутбуке часто начинают с файла: `tasks.json`, перезаписали целиком после каждого клика. Пока вы один — это работает. Откройте тот же файл из двух процессов сразу: один прочитал старую версию, второй уже записал новую, первый сохранил поверх — задача пропала. Поиск «все незакрытые» на десяти тысячах записей каждый раз читает файл с начала. Часть записи оборвалась при выключении — JSON битый, приложение не стартует.

База данных под управлением **СУБД** — это не «файл покрасивее». Это процесс (или библиотека в вашем процессе), который принимает **запросы**, сам решает, как положить байты на накопитель, проверяет правила и координирует тех, кто пишет одновременно.

Приложение говорит: «верни id и заголовок, где дело ещё не сделано». Оно не двигает страницы файла руками. СУБД разбирает запрос, проверяет типы и ограничения, читает нужные куски, отдаёт **строки**. Если два клиента меняют разные задачи — оба доходят. Если один и тот же ряд — либо очередь, либо отказ по правилам транзакции, а не тихая порча файла.

## Что видно снаружи

Учебная таблица `tasks`:

| id | title | done |
| --- | --- | --- |
| 1 | Купить молоко | 0 |
| 2 | Отчёт | 1 |
| 3 | Звонок | 0 |

Запрос незавершённых не «открывает базу как документ». Он отфильтровывает строку 2 и возвращает две пары значений. Приложение получает набор кортежей. Весь файл целиком ему не нужен.

```python
import sqlite3

conn = sqlite3.connect("app.db")
cur = conn.cursor()
cur.execute("SELECT id, title FROM tasks WHERE done = 0")
print(cur.fetchall())  # [(1, 'Купить молоко'), (3, 'Звонок')]
conn.close()
```

`connect` — **соединение**, сеанс с СУБД. `execute` — текст запроса. `fetchall` — результат. `close` отдаёт ресурсы. Между ними могла жить **транзакция**: пачка изменений, которая либо вся видна, либо ни одна.

**Схема** — описание таблиц и ограничений: какие столбцы, какие типы, что нельзя вставить. Данные живут отдельно от кода Python, но код зависит от схемы: переименовали столбец — сломался запрос.

## Два способа «быть СУБД»

**SQLite** встраивается в ваш процесс: файл на диске, нет отдельного сервера. Удобно для локального инструмента, тестов, телефона. Несколько писателей на один файл ограничены жёстче, чем в серверной СУБД.

**PostgreSQL** (и похожие) — отдельный сервер. Клиенты ходят по сети или сокету. Пул соединений, роли, репликация — уже про сервис, который живёт дольше одного скрипта.

Путь мысли один и тот же: открыть соединение → выполнить SQL → прочитать строки → зафиксировать или откатить. Меняется только то, где крутится движок.

Внутри, очень грубо: клиент → драйвер → разбор SQL → план («идти по индексу или сканировать таблицу») → чтение страниц → результат. План вы ещё не обязаны читать; важно, что «написать SELECT» и «как СУБД это сделает» — разные слои. К ним вернёмся в EXPLAIN.

Каталог с копиями JSON — запасной архив, не база: нет схемы как контракта, нет одновременного доступа, нет языка запросов. Бэкап СУБД — отдельная дисциплина, её не заменяет «скопировал папку проекта».
