# Сервисный слой

## Цель

Понять роль прикладного сервиса заказов: оркестрация сценария, транзакции, вызов репозитория и портов — без превращения сервиса в свалку и без дублирования инвариантов. После урока вы напишете метод `create`/`cancel` с чёткими границами.

## Что уже нужно понимать

Слои transport → application → domain → infrastructure. Сервисный слой ≈ application: «что система делает для пользователя/клиента API».

## Объяснение

Сервис отвечает на команды и запросы прикладного уровня: создать заказ, начать упаковку, отменить, получить список с фильтром. Он:

- принимает уже простые данные (или DTO);
- загружает сущности;
- вызывает доменные методы / политики;
- сохраняет;
- дергает порты (уведомления, события);
- возвращает результат.

Он не:

- парсит HTTP-заголовки (это API);
- знает диалект SQL (это repo);
- содержит CSS и React.

Когда сервис толстеет ветвлениями статусов — часть логики просится в домен (`order.cancel()`), а не новые `if` в сервисе. Когда сервис только проксирует `repo.add` без правила — возможно, сценарий слишком тонкий; это нормально для чистого CRUD, не усложняйте.

Один сервис на агрегат `Order` удобен. Раздувание `GodService` на заказы+оплаты+склад — сигнал резать по сценариям/модулям.

## Термины

- **Команда** — изменить состояние (`ship`).
- **Запрос** — прочитать (`list`, `get`) без побочных эффектов.
- **Оркестрация** — порядок шагов сценария.
- **Анемичная модель** — вся логика в сервисе, объекты без поведения.

## Как это устроено

Чтение и запись можно разделить стилем: `OrderService` для команд, отдельные query-функции для списков с JOIN. На старте один класс допустим, пока читаемые методы не начнут тянуть тяжёлые отчёты в тот же файл.

Идемпотентность и повторные запросы — забота сервиса/контракта API: повторный `ship` уже shipped заказа может вернуть тот же результат или 409 — решите явно и задокументируйте.

Транзакция: сервис (или UoW вокруг него) определяет границы. Не коммитьте в репозитории молча на каждый `save`, если сценарий из трёх save — иначе частичный успех.

## Пример

```python
class OrderService:
    def __init__(self, repo: OrderRepository, notifier: Notifier, uow: UnitOfWork):
        self._repo = repo
        self._notifier = notifier
        self._uow = uow

    def create(self, customer: str, city: str) -> Order:
        with self._uow:
            order = Order.create(customer=customer, city=city)
            return self._repo.add(order)

    def cancel(self, order_id: int, reason: str) -> Order:
        with self._uow:
            order = self._repo.get(order_id)
            order.cancel(reason=reason)  # инвариант внутри
            saved = self._repo.save(order)
            self._notifier.order_cancelled(saved)
            return saved

    def list(self, status: str | None = None) -> list[Order]:
        return self._repo.list(status=status)
```

```python
# domain fragment
def cancel(self, reason: str) -> None:
    if self.status == "shipped":
        raise Conflict("cannot cancel shipped")
    if self.status == "cancelled":
        return  # идемпотентность на уровне домена
    self.status = "cancelled"
    self.cancel_reason = reason
```

## Разбор примера

`create` тонкий: фабрика `Order.create` гарантирует начальный статус `new`. `cancel` оркестрирует загрузку, домен, сохранение, уведомление. Повторная отмена не падает — доменная идемпотентность.

`list` без UoW на запись — чтение. Фильтр уходит в repo; сервис не фильтрует огромный список в Python без нужды, если БД справится лучше.

Notifier внутри транзакции спорный: если письмо медленное, лучше outbox. Для учебного курса допустим вызов после save в той же UoW или сразу после commit — главное осознанно.

## Типичные ошибки

- Сервис = все `if` мира, домен пустой.
- Сервис знает Request/Response FastAPI.
- Коммит в трёх местах репозитория в одном сценарии.
- Смешивать отчётный SQL на 200 строк с `cancel` в одном классе без меры.

## Что запомнить

Сервисный слой оркестрирует сценарии заказов. Инварианты — в домене. SQL — в репозитории. HTTP — в API. Транзакция вокруг сценария. Толстый сервис — сигнал переноса правил или разрезания.
