# Модульный монолит

## Цель

Научиться держать границы доменов `catalog`, `orders`, `billing` внутри одного деплоя так, чтобы завтра можно было вынести модуль, а сегодня — не платить ценой сети. После урока вы сможете описать правила импортов и владения данными модульного монолита магазина.

## Что уже нужно понимать

Монолит как один процесс и одна БД. Слои api/service/repository. Идея связности и связности по данным: кто владеет таблицей, тот меняет её правила.

## Объяснение

### Идея

Модульный монолит — это **один деплой**, внутри которого код и данные разрезаны по **явным модульным границам**. Процесс один, сеть между модулями обычно нет (вызовы — функции и интерфейсы), но дисциплина как у сервисов: модуль не лезет в чужие таблицы «через заднюю дверь».

Для интернет-магазина:

| Модуль | Ответственность | Владеет данными |
|--------|-----------------|-----------------|
| `catalog` | товары, цены витрины, категории | `products`, `categories` |
| `orders` | корзина, оформление, статусы заказа | `orders`, `order_items`, `carts` |
| `billing` | платежи, возвраты, чеки | `payments`, `refunds` |

Деплой один: контейнер `shop-api`. БД одна, но **схемы/префиксы/пакеты** разделены по владельцу.

### Как выглядит граница на коде

Структура:

```text
app/
  catalog/
    api.py
    service.py
    repository.py
    models.py
  orders/
    api.py
    service.py
    repository.py
    models.py
  billing/
    api.py
    service.py
    repository.py
    models.py
  shared/          # редко: auth context, errors, db session
```

Правило импортов:

- `orders` может вызывать **публичный** API модуля `catalog` (функцию/порт), но не импортировать `catalog.repository` и не писать `UPDATE products`.
- `billing` не читает корзину напрямую — получает сумму и `order_id` от `orders`.
- `catalog` не знает про платежи.

Публичный порт каталога:

```python
# catalog/public.py
def get_product_for_order(db, product_id: int) -> ProductSnapshot:
    """Снимок для заказа: id, price, title. Не ORM-сущность наружу."""
    ...
```

Использование в заказах:

```python
# orders/service.py
from app.catalog.public import get_product_for_order

def place_order(db, user_id, items):
    lines = []
    for item in items:
        snap = get_product_for_order(db, item.product_id)
        lines.append(OrderLine(product_id=snap.id, price=snap.price, qty=item.qty))
    ...
```

Так вы сохраняете монолитный деплой, но уже тренируете контракт между частями.

### Одна БД — разные владельцы

В модульном монолите таблицы часто лежат в одной PostgreSQL, но:

- миграции модуля трогают только «свои» таблицы;
- запрещены FK «наобум» из чужого модуля, если это ломает независимость (иногда FK оставляют осознанно — это компромисс);
- чтение чужих данных — через порт (функцию), не через join «потому что удобно» в чужом репозитории.

Пример плохо:

```python
# billing/repository.py — антипаттерн
db.execute("SELECT * FROM orders WHERE ...")  # billing лезет в таблицу orders
```

Пример лучше:

```python
# orders/public.py
def get_order_total(db, order_id: int) -> Money: ...

# billing/service.py
total = get_order_total(db, order_id)
charge(db, order_id, total)
```

### Транзакции остаются простыми

Поскольку процесс один и БД одна, оформление заказа всё ещё может быть одной транзакцией:

```python
def checkout(db, user_id, cart_id):
    with db.begin():
        order = orders.place_from_cart(db, user_id, cart_id)
        billing.create_payment(db, order.id, order.total)
        # склад может быть отдельным модулем stock с портом reserve()
        stock.reserve(db, order.lines)
    return order.id
```

Вы получаете **модульность кода** без саг и без двухфазного коммита между сервисами.

### Зачем это нужно до микросервисов

Модульный монолит — мост:

1. учит команды жить с границами;
2. показывает реальные зависимости данных;
3. позволяет позже вынести `billing` в отдельный процесс, заменив вызов функции на HTTP/очередь, *если* граница уже чистая;
4. не заставляет платить сетью сегодня.

Если сразу резать на микросервисы без модульных границ, вы перенесёте хаос в сеть.

### Правила команды

Зафиксируйте в README/CONTRIBUTING:

- список модулей и владельцев таблиц;
- запрет импорта `*.repository` чужого модуля;
- публичные символы только из `public.py` / `api` модуля;
- review: «этот PR лезет в чужую таблицу?»

Без социальных правил модульный монолит на бумаге сдувается за спринт.

### Когда модульный монолит достаточен надолго

Для многих интернет-магазинов — на годы:

- нагрузка умеренная;
- одна команда или несколько фиче-команд в одном репо;
- нужна быстрая итерация по заказу;
- консистентность важнее независимого деплоя биллинга.

Вынос сервиса оправдан, когда:

- биллинг должен обновляться по другому циклу/комплаенсу;
- каталог читают в 50 раз чаще, чем пишут заказы, и нужно иное масштабирование;
- падение каталога не должно валить приём платежей (жёсткая изоляция).

Пока этих причин нет — **не дробите**. Усильте модули.

### Типичные ошибки

- Модули по слоям (`models/`, `services/`) вместо доменов — границы размыты.
- Общий `utils` на 2000 строк, куда утекает домен.
- «Публичный» API, который возвращает ORM-модели с lazy-load — утечка инфраструктуры.
- Циклические импорты `orders` ↔ `billing` без событий/портов — сигнал, что граница кривая.
- Общая таблица `stuff` для всего — убийца модульности.

### Связь с фронтом

Фронт не обязан знать про модули. Он видит HTTP API магазина. Модульность — внутренняя: роуты могут жить в пакетах модулей, но снаружи один origin API.

```text
React → POST /api/orders → orders.api → orders.service
                              ↓ порты
                         catalog.public / billing.public
```

### Практика

Возьмите существующий монолит магазина и:

1. назовите три модуля;
2. перечислите таблицы каждого;
3. найдите три прямых обращения к чужим таблицам;
4. замените одно обращение на порт.

Это дешевле любого «переезда на микросервисы».

## Коротко

Модульный монолит — один процесс и один деплой, но жёсткие границы `catalog` / `orders` / `billing`: свои пакеты, свои таблицы, общение через публичные порты. Транзакции остаются локальными. Дробить на процессы имеет смысл только после того, как границы уже работают без сети.
