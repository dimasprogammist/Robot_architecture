# Микросервисы

## Цель

Понять микросервисы как отдельные процессы с собственной жизненной поставкой и **ценой сети**, на примере разрезанного интернет-магазина. После урока вы сможете назвать, что вы покупаете и чем платите, когда выносите `orders`, `billing` и `catalog` в разные сервисы.

## Что уже нужно понимать

Монолит и модульный монолит. HTTP, таймауты, идемпотентность. Базы и транзакции. Очереди на уровне идеи.

## Объяснение

### Определение без маркетинга

Микросервисная система — набор **независимо развёртываемых процессов**, обычно со **своими данными**, общающихся по сети (HTTP, gRPC, сообщения).

Для магазина заказов возможная нарезка:

| Сервис | Процесс | БД | Пример API |
|--------|---------|----|------------|
| `catalog-service` | отдельный | `catalog_db` | `GET /products/{id}` |
| `orders-service` | отдельный | `orders_db` | `POST /orders` |
| `billing-service` | отдельный | `billing_db` | `POST /charges` |
| `stock-service` | отдельный | `stock_db` | `POST /reservations` |

Фронт или API-gateway ходит в несколько бэкендов (или в gateway, который проксирует).

### Сценарий оформления заказа — уже не одна транзакция

`POST /orders` в `orders-service`:

1. orders спрашивает catalog по HTTP: актуальная цена;
2. orders пишет заказ в `orders_db` со статусом `pending`;
3. orders вызывает billing: `POST /charges`;
4. orders вызывает stock: `POST /reservations`;
5. если шаг 4 упал, заказ уже есть, платёж мог пройти — нужна **компенсация**.

Пример вызова:

```python
# orders-service
async def place_order(user_id, items):
    priced = await catalog_client.price_items(items)      # сеть
    order = await orders_repo.insert(user_id, priced, status="pending")
    try:
        payment = await billing_client.charge(order.id, order.total)  # сеть
        await stock_client.reserve(order.id, priced)                  # сеть
    except RemoteError:
        await billing_client.refund(order.id)  # компенсация
        await orders_repo.mark_failed(order.id)
        raise
    return order
```

Каждый `await ..._client` — это DNS, TCP, сериализация JSON, таймаут, ретраи, частичный отказ.

### Цена сети — конкретно

Что вы платите:

1. **Задержка.** Три последовательных HTTP по 20–50 мс — уже заметно на UX оформления.
2. **Частичные отказы.** Billing ответил 200, stock — 503. Состояние системы рассинхронизировано, пока не отработает сага/воркер.
3. **Наблюдаемость.** Нужен correlation id через все сервисы, иначе «заказ завис» не отладить.
4. **Контракты.** Версионирование API, обратная совместимость, контрактные тесты.
5. **Данные.** Нет JOIN между `orders` и `products` в одной БД — нужны копии, события или синхронные запросы.
6. **Операционка.** Отдельные образы, деплои, лимиты CPU, секреты, миграции на сервис.

Микросервисы — не «бесплатная масштабируемость», а **обмен простоты на независимость**.

### Что вы покупаете

- независимый деплой биллинга без выката каталога;
- изоляцию сбоя: падение витрины не обязательно роняет приём webhook банка (если границы верные);
- масштабирование чтения каталога отдельно от записи заказов;
- разные стеки/команды (иногда — дорогая роскошь).

Покупать это имеет смысл, когда выгода **измерима**, а команда готова платить операционную цену.

### Shared database — ловушка

Антипаттерн: три «микросервиса», одна PostgreSQL, все пишут во все таблицы. Вы получили:

- сетевую задержку и деплойный хаос;
- без преимущества владения данными;
- ещё более хрупкие миграции.

Если БД общая на запись — это распределённый монолит. Лучше вернуться к модульному монолиту.

### Синхронные цепочки vs хореография

Синхронно (как выше): просто понять happy-path, плохо при отказах.

Через события (следующий урок): `order_placed` публикуется, billing и stock подписываются. HTTP заказа отвечает быстрее, консистентность — eventual.

Выбор зависит от SLA: должен ли пользователь сразу увидеть «оплачено и зарезервировано» или достаточно «заказ принят, обработка идёт».

### Когда НЕ дробить на микросервисы

Не дробите интернет-магазин, если:

1. команда маленькая и деплоит всё вместе;
2. домен заказа ещё плавает (часто меняются сущности);
3. нет сильной платформенной практики (CI, логи, трейсы, on-call);
4. узкое место не доказано профилем — «на будущее»;
5. вы хотите микросервисы «для резюме», а не для нагрузки/изоляции;
6. критичные инварианты требуют жёсткой атомарности без готовой саги.

Сначала модульный монолит с портами. Вынос — когда модуль уже стабилен и боль независима.

### Минимальный чеклист перед разрезанием

- [ ] граница модуля чистая (нет чужих таблиц);
- [ ] есть владелец сервиса и SLO;
- [ ] определён контракт и идемпотентность;
- [ ] есть план отказов и компенсаций;
- [ ] логи/метрики/трейсы сквозные;
- [ ] данные мигрируют без даунтайма или с понятным окном.

Если чеклист пустой — рано.

### Пример деплоя магазина

```yaml
# упрощённо
services:
  catalog:
    image: shop/catalog:1.4
  orders:
    image: shop/orders:2.1
  billing:
    image: shop/billing:1.9
  stock:
    image: shop/stock:1.2
  postgres-catalog: ...
  postgres-orders: ...
```

Каждый сервис — свой релиз. Цена: согласование версий клиентов и схемы событий.

### Типичные ошибки

- слишком мелкие сервисы («микро» до абсурда: сервис на одну таблицу без смысла);
- чаттистые синхронные вызовы в цикле (N+1 по сети);
- отсутствие таймаутов и circuit breaker;
- разный `user_id` и семантика статусов в каждом сервисе без общего языка;
- распределённые транзакции «как в одной БД» через XA — редко нужно, сложно.

### Наблюдаемость — не опция

В монолите достаточно логов процесса. В микросервисах заказа без сквозного `trace_id` / `order_id` в каждом сервисе вы получите четыре несвязанных лога и тикет «оплата зависла». Договоритесь о корреляции **до** разрезания, не после первого инцидента.

Метрики минимума: latency и error rate на каждом исходящем клиенте, лаг консьюмеров, доля компенсаций.

### Контракт клиента catalog

Даже простой `GET /products/{id}` нуждается в политике:

- таймаут 200–500 мс;
- что делать при 404 (товар снят) и при 503 (деградация: отменить checkout или взять кэш цены?);
- кэш на стороне orders — риск устаревшей цены.

Эти решения и есть архитектура микросервисов на практике, а не только стрелки на схеме.

## Коротко

Микросервисы магазина — отдельные процессы и обычно отдельные БД: заказ ходит в catalog/billing/stock по сети и теряет простую транзакцию. Выигрыш — независимость деплоя и масштаба; цена — отказы, задержки, контракты и операции. Не дробите, пока модульный монолит не упёрся в реальную боль.
