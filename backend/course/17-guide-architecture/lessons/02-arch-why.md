# Зачем нужна архитектура

## Цель

Связать архитектурные решения с конкретными болями растущего сервиса заказов: дублирование правил, хрупкие правки, невозможность тестировать, страх деплоя. После урока вы сможете объяснить «зачем слои» бизнесово-инженерным языком, без абстрактной морали.

## Что уже нужно понимать

Идея архитектуры как границ и ответственности. Опыт: правка «мелочи» внезапно ломает другое место. Это сигнал, что связи в системе запутанные — даже если пользователей мало.

## Объяснение

Архитектура нужна не для резюме и не для соответствия чеклисту. Она нужна, когда:

1. **Правило домена живёт в трёх местах.** Скидку посчитали в роуте, в скрипте отчёта и во фронте — итоги разошлись. Выделение доменного сервиса/модуля уменьшает число истин.

2. **Тестировать можно только через HTTP+БД.** Чтобы проверить «нельзя отгрузить cancelled», поднимают весь стек. Вынесенная функция/сервис тестируется за миллисекунды.

3. **Смена хранения рвёт всё.** Переезд с SQLite на Postgres затрагивает 40 файлов, потому что SQL расползся. Репозиторий локализует удар.

4. **Новый вход в систему.** Добавили consumer Kafka «создай заказ из файла партнёра» — и пришлось тащить FastAPI Request в воркер. Значит, правило создания не там.

5. **Онбординг.** Новый человек не находит, где менять статус. Папки и имена ролей — карта.

Цена архитектуры — чуть больше файлов и дисциплины импортов. На нулевом прототипе из одного экрана можно жить без церемоний. Как только появляются статусы, оплаты, уведомления и второй клиент API — цена «без структуры» растёт быстрее.

## Термины

- **Стоимость изменения** — сколько мест и рисков затронет правка.
- **Регрессия** — старое поведение сломалось новой правкой.
- **Точка расширения** — место, куда логично добавить новый вариант поведения.

## Как это устроено

История Orders API в миниатюре:

- Неделя 1: `POST /orders`, таблица, всё в одном файле — ок.
- Неделя 3: статусы, фильтры, мягкое удаление — файл пухнет.
- Неделя 5: письмо клиенту из того же обработчика — тесты HTTP медленные, письмо уходит из юнит-тестов «случайно».
- Неделя 7: нужно создать заказ из batch-файла — копипаста правила.

Ветка с модулями на неделе 3: письмо — порт `Notifier`, batch вызывает тот же `OrderService.create`. Архитектура окупилась конкретной экономией, не лозунгом.

Важно: не проектируйте микросервисы на неделе 1 «на вырост». Выращивайте границы внутри процесса. Разрез на сервисы — отдельное дорогое решение (сеть, данные, версии).

## Пример

```python
# Боль: правило размазано
@app.post("/orders/{order_id}/ship")
def ship(order_id: int, db: Session = Depends(get_db)):
    order = db.get(OrderRow, order_id)
    if order.status == "cancelled":
        raise HTTPException(409, "cancelled")
    if order.status != "packing":
        raise HTTPException(409, "need packing")
    order.status = "shipped"
    db.commit()
    send_email(order.customer_email, "shipped")  # побочный эффект врос в HTTP
    return order


# Тот же сценарий с выделенным применением правила
class OrderService:
    def __init__(self, repo: OrderRepository, notifier: Notifier):
        self._repo = repo
        self._notifier = notifier

    def ship(self, order_id: int) -> Order:
        order = self._repo.get(order_id)
        if order.status == "cancelled":
            raise Conflict("cancelled")
        if order.status != "packing":
            raise Conflict("need packing")
        order = self._repo.save(order.with_status("shipped"))
        self._notifier.order_shipped(order)
        return order
```

```python
def test_cannot_ship_cancelled():
    repo = InMemoryRepo([Order(id=1, status="cancelled")])
    svc = OrderService(repo, notifier=FakeNotifier())
    with pytest.raises(Conflict):
        svc.ship(1)
```

## Разбор примера

В первом фрагменте HTTP, SQL, правило и email слиплись. Юнит-тест правила тянет почту и БД. Во втором — тест без сети проверяет конфликт статусов. Notifier в проде шлёт письмо, в тесте — записывает вызов в список.

Зачем архитектура здесь буквально: быстрее проверка, безопаснее рефакторинг, проще добавить SMS-канал новой реализацией `Notifier`, не трогая правило `ship`.

## Типичные ошибки

- «Нам не нужна архитектура, мы стартап» — и через месяц боятся трогать статусы.
- «Нам нужна архитектура» → сразу 12 сервисов и сага на Kafka.
- Оптимизировать абстракции, которых нет в реальности домена.
- Игнорировать операционные боли (логи, миграции) в пользу только «красивых классов».

## Что запомнить

Архитектура снижает стоимость изменений и риск регрессий. Окупается на правилах домена, тестах, новых входах, смене хранения. Начинайте с границ в монолите. Измеряйте пользу болью, а не числом папок.
