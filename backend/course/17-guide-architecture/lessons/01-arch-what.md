# Что такое архитектура ПО

## Цель

Понять архитектуру как набор решений о границах, ответственности и связях частей системы — на примере маленького сервиса заказов, а не как набор модных слов. После урока вы сможете отличить «структуру кода» от «случайной свалки файлов» и назвать, какие решения у Orders API уже архитектурные.

## Что уже нужно понимать

Вы писали бэкенд на FastAPI, работали с БД и фронтом панели заказов. Архитектура начинается не когда «миллион пользователей», а когда появляется второй разработчик, второе правило домена или второй способ входа (HTTP + фон). Даже учебный монолит уже имеет архитектуру — явную или случайную.

## Объяснение

Архитектура ПО — это ответы на вопросы: какие части существуют, что каждая часть имеет право знать, как они обмениваются данными, где живут правила «заказ нельзя отгрузить без оплаты», что будет больно менять через полгода.

Это не диаграмма ради диаграммы и не список принципов без примера. Для сервиса заказов архитектурные решения выглядят так:

- один процесс FastAPI или несколько сервисов;
- SQL-таблица `orders` рядом с кодом или за HTTP другого сервиса;
- смена статуса в том же запросе, что и запись, или через событие в журнал;
- фронт ходит напрямую в БД (нет!) или только в API (да).

Хорошая архитектура уменьшает стоимость изменений в ожидаемых местах. Плохая делает любое изменение «тронь статус — упала отчётность». Предсказать все изменения нельзя; можно изолировать то, что меняется часто (правила статусов, форматы API) от того, что стабильно (факт «заказ существует»).

Архитектура проявляется в коде: импорты, папки, сигнатуры функций, схемы БД, контракты JSON. Если «слой» есть только на слайде, его нет.

## Термины

- **Граница** — линия, через которую нельзя тянуть внутренности соседа без контракта.
- **Ответственность** — за что модуль отвечает и за что нет.
- **Связанность** — насколько части зависят друг от друга.
- **Монолит** — одна доставляемая единица (часто один процесс), внутри могут быть модули.
- **Техдолг архитектурный** — решения, ускорившие вчера и замедляющие сегодня.

## Как это устроено

Возьмём Orders Desk backend:

1. HTTP-вход принимает JSON.
2. Прикладной сервис проверяет правила и оркестрирует шаги.
3. Репозиторий пишет/читает SQL.
4. Опционально публикация «OrderCreated» в журнал событий.

Уже четыре роли. Можно свалить всё в один файл `main.py` на 800 строк — система будет работать до первого серьёзного изменения. Можно разрезать по ролям с первого дня — чуть больше файлов, но ясный путь правки.

Архитектура также про эксплуатацию: один деплой или несколько, общие миграции, общие логи. Учебный курс ведёт к монолиту с внутренними границами — это сознательный выбор, не «отсталость».

## Пример

```python
# Плохо: всё в обработчике — архитектура «случайная»
@app.post("/orders")
def create_order(payload: dict, db: Session = Depends(get_db)):
    if not payload.get("customer"):
        raise HTTPException(400, "customer required")
    row = OrderRow(customer=payload["customer"], city=payload["city"], status="new")
    db.add(row)
    db.commit()
    # завтра сюда же влезут: скидки, склад, письмо, метрики...
    return {"id": row.id, "status": row.status}


# Явнее: вход тонкий, правило и запись разделены
@app.post("/orders")
def create_order(payload: OrderCreate, svc: OrderService = Depends()):
    order = svc.create(payload)
    return OrderOut.model_validate(order)
```

```text
Запрос → API (транспорт) → OrderService (правила) → OrderRepository (SQL)
                                    ↓
                              (позже) события
```

## Разбор примера

В первом варианте HTTP знает про поля таблицы и про правило валидации. Любой новый канал (CLI, consumer Kafka) скопирует логику или начнёт импортировать FastAPI-зависимости в странные места.

Во втором варианте API зависит от сервиса и DTO. Сервис не обязан знать, что снаружи HTTP. Репозиторий можно подменить на фейк в тесте. Это уже архитектура маленькой системы — без микросервисов.

Стрелочная схема показывает направление зависимостей: внешние слои знают про внутренние контракты, а не наоборот. Детали — в следующих уроках модуля.

## Типичные ошибки

- Считать архитектуру только выбором фреймворка.
- Рисовать слои и продолжать импортировать SQL в роуты.
- Копировать «enterprise» структуру на CRUD из трёх полей без нужды.
- Откладывать границы «до рефакторинга», пока файлы не слиплись.
- Путать архитектуру с инфраструктурой (Kubernetes ≠ модель домена).

## Что запомнить

Архитектура — решения о частях, границах и связях. У маленького Orders API она уже есть. Проявляется в коде и контрактах. Цель — удешевить ожидаемые изменения. Монолит с модулями — нормальная учебная и боевая точка старта.
