# Структуры данных

## Цель

Научиться выбирать способ организации данных: список, словарь (ассоциативный массив), множество, очередь, стек — исходя из операций, которые нужны алгоритму. После урока вы будете спрашивать не «какой тип красивее», а «что я буду делать чаще: искать по ключу, добавлять в конец, брать первый?».

## Что уже пройдено

Типы описывают природу значения; модули организуют код. Структуры данных организуют **наборы** значений. От выбора структуры зависит и ясность алгоритма, и стоимость операций.

## Объяснение с нуля

Структура данных — способ хранить связанные значения и правила доступа к ним. Одни и те же факты можно положить в разные структуры: список пар «имя-значение» или словарь. Разница проявится, когда вы начнёте искать, вставлять, удалять.

Базовые идеи:

- **Список / массив** — упорядоченная последовательность, доступ по индексу. Удобно хранить показания во времени, аргументы командной строки, набор точек. Поиск элемента без доп. индекса в среднем требует просмотра.
- **Словарь (map)** — ассоциация ключ → значение. Быстрый доступ по ключу: имя параметра, id устройства, код ошибки.
- **Множество** — коллекция уникальных элементов; удобны проверки «уже видели?» и операции объединения/пересечения (на уровне идеи).
- **Стек** — «последним пришёл — первым ушёл» (LIFO): откат, стек вызовов, разбор вложенности.
- **Очередь** — «первым пришёл — первым ушёл» (FIFO): задания на обработку, буфер событий.

Структура выбирается под **операции**. Если нужно часто доставать по имени — словарь. Если важен порядок и проход подряд — список. Если важен порядок обработки событий — очередь.

Вложенность нормальна: список словарей, словарь списков. Главное — не потерять смысл уровней. Документируйте контракт: «список сенсоров; у каждого сенсора поля id и value».

Изменяемые структуры нужно копировать осознанно. Две переменные, указывающие на один список, разделяют изменения — это уже встречалось в теме аргументов. Иногда нужна поверхностная копия, иногда глубокая.

Не храните в структуре хаос без схемы. «Универсальный словарь всего» быстро становится свалкой. Лучше явные поля записи (и переход к объектам в следующем уроке).

История и текущее состояние — часто разные структуры под разные вопросы к данным.

## Термины

- **Индекс** — позиция элемента в последовательности.
- **Ключ** — идентификатор для доступа в ассоциативной структуре.
- **Запись (record)** — набор именованных полей одного объекта предметной области.
- **LIFO / FIFO** — дисциплины стека и очереди.
- **Сложность операции** — насколько растёт работа при росте данных (интуитивно: быстро/медленно).
- **Инвариант структуры** — правило, которое структура поддерживает (уникальность ключей и т.п.).

## Внутреннее устройство

Массив в памяти часто лежит непрерывным блоком: индекс превращается в адрес арифметикой. Добавление в конец обычно дёшево амортизированно; вставка в середину дороже из-за сдвига.

Хеш-таблицы (частая реализация словарей) распределяют ключи по корзинам. В среднем доступ быстрый; нужны хороший хеш и запас места. Вам достаточно модели: словарь оптимизирован под доступ по ключу, не под «элемент номер 17» как основную операцию.

Связные списки, деревья, графы — следующие уровни. На введении хватит понимания, что «список» в языке может быть массивом под капотом, а «очередь» — обёрткой с двумя концами. Интерфейс важнее внутренностей, пока вы не упираетесь в производительность.

Выбор структуры влияет на алгоритмы сортировки, поиска, кэширования. Иногда данные дублируют в двух структурах (список для порядка + словарь для индекса) — плата памятью за скорость доступа. Делайте так только при явной нужде.

Границы индексов и отсутствие ключа — типичные runtime-ошибки при работе со структурами. Проверяйте предусловия доступа.

## Пример

```text
Задача: хранить последние команды и быстро знать статус устройства по id.

# история — список (важен порядок)
history ← []
history.append({"id": "m1", "cmd": 0.2})
history.append({"id": "m2", "cmd": 0.0})

# текущее состояние — словарь (важен доступ по id)
state ← {}
state["m1"] ← 0.2
state["m2"] ← 0.0

# очередь заданий
jobs ← queue()
jobs.push("calibrate")
jobs.push("run")
next ← jobs.pop()    # "calibrate"

# множество уже обработанных id
seen ← set()
ЕСЛИ "m1" не в seen:
  обработать
  seen.add("m1")

# Python-иллюстрация:
state = {"m1": 0.2, "m2": 0.0}
history = [("m1", 0.2), ("m2", 0.0)]
```

## Разбор

История и текущее состояние — разные вопросы к данным. Список отвечает «что было по порядку»; словарь — «какое значение у m1 сейчас». Одна структура плохо служит обеим ролям сразу без компромиссов.

Очередь гарантирует справедливость обработки заданий. Если взять стек, последнее задание вытеснило бы старые — иногда нужно (отмена), иногда нет (конвейер). Дисциплина — часть спецификации.

Множество `seen` делает проверку уникальности дешёвой и явной. Список + линейный поиск тоже сработает на малых данных, но смысл «множество» читается лучше и масштабируется иначе.

Когда проектируете буфер событий, сначала выпишите операции (добавить, взять старое, спросить «был ли fault»), потом выберите структуру — не наоборот.

## Ошибки

- Класть всё в один гигантский список и искать линейно без нужды.
- Использовать список пар вместо словаря там, где ключ естественен.
- Путать порядок очереди и стека.
- Менять список во время обхода и ловить пропуски.
- Хранить неоднородный хаос без схемы полей.

## Что запомнить

Структура данных выбирается под операции. Список — порядок и индекс; словарь — ключ; множество — уникальность; стек и очередь — дисциплины доступа. Вложенность требует ясного контракта. Разделение «история» и «текущее» часто улучшает модель. Внутренняя реализация объясняет стоимость, интерфейс — повседневную работу.

## Задание

Смоделируйте буфер событий датчика: нужно хранить до 100 последних событий по времени и уметь ответить, было ли событие типа `fault` за этот буфер. Предложите структуру(ы) и опишите операции добавления нового события при переполнении.
