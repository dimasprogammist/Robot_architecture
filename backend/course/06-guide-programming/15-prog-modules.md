# Модули

## Цель

Понять модуль как единицу организации кода: файл (или логический блок) с именами функций, констант и типов, который можно подключать в других местах. После урока вы сможете объяснить импорт как «взять готовые инструменты из другого пространства имён».

## Что уже пройдено

Функции дробят алгоритм на обязанности. Когда функций много, держать всё в одном полотне неудобно. Модуль группирует родственные объявления и скрывает внутренние детали за публичным интерфейсом.

## Объяснение с нуля

Модуль — именованная коробка с кодом. Обычно это файл: `math_utils`, `sensors`, `config`. Внутри — функции, константы, иногда классы. Снаружи другие части программы **импортируют** нужные имена.

Зачем модули:

1. **Навигация** — проще найти код по смыслу.
2. **Повторное использование** — один модуль подключают в нескольких программах.
3. **Изоляция** — меньше случайных конфликтов имён.
4. **Границы ответственности** — «работа с датами» отдельно от «отправки команд мотору».

Импорт бывает «весь модуль» и «отдельные имена». Первый стиль (`использовать math`) делает происхождение вызова явным: `math.sqrt`. Второй (`из math взять sqrt`) короче, но при избытке легко забыть, откуда имя. Командам полезно договориться о стиле.

Циклические зависимости (A импортирует B, B импортирует A) — признак плохого разреза. Часто помогает вынести общее в третий модуль или пересмотреть обязанности.

Модуль имеет своё пространство имён: `helper` внутри `sensors` не обязан быть тем же, что `helper` внутри `ui`. Полное имя учитывает модуль. Это напрямую связано с уроком про область видимости, только на уровне файлов.

Не всё в модуле обязано быть публичным. Внутренние вспомогательные функции можно считать деталями реализации. Меняйте их свободно, пока публичный контракт стабилен.

Хороший модуль отвечает на один вопрос предметной области. Модуль «и конфигурация, и сеть, и UI» — свалка под красивым именем файла.

## Термины

- **Модуль** — единица кода с собственным пространством имён.
- **Импорт** — подключение имён другого модуля.
- **Интерфейс модуля** — набор имён, которыми разрешено пользоваться снаружи.
- **Зависимость** — факт, что модуль A нуждается в B.
- **Циклическая зависимость** — взаимная нужда модулей друг в друге.
- **Инициализация модуля** — код, выполняемый при первом импорте.

## Внутреннее устройство

При первом импорте среда обычно загружает файл модуля, выполняет его верхнеуровневый код один раз и кэширует результат в таблице модулей. Повторный импорт берёт уже загруженное. Поэтому тяжёлую работу и сюрпризы на верхнем уровне файла устраивать опасно: импорт должен быть предсказуемым.

Пути поиска модулей задаются правилами языка и окружения: текущий проект, установленные пакеты, стандартная библиотека. Ошибка «модуль не найден» чаще про путь и окружение, чем про «пропавший алгоритм».

Компиляция и сборка в некоторых экосистемах связывают модули статически; в интерпретируемых — подгружают динамически. Для мышления достаточно: модуль — граница компиляции/загрузки и граница имён.

Тестировать модуль удобно изолированно: подменить зависимости-заглушки, проверить публичные функции. Если модуль тянет половину системы через скрытые глобалы, тесты становятся кошмаром — снова аргумент за чистые интерфейсы.

Диаграмма зависимостей (кто кого импортирует) — простой способ увидеть «ком» в архитектуре до того, как он затвердеет.

## Пример

```text
Модуль units.pseudo:
  ФУНКЦИЯ clamp(value, low, high):
    ...
  ФУНКЦИЯ deg_to_rad(deg):
    ВЕРНУТЬ deg * PI / 180
  PI ← 3.1415926535

Модуль motion.pseudo:
  импортировать units
  ФУНКЦИЯ safe_cmd(cmd):
    ВЕРНУТЬ units.clamp(cmd, -1.0, 1.0)

Главная программа:
  импортировать motion
  out ← motion.safe_cmd(1.7)   # → 1.0

# Python-иллюстрация идеи:
# файл units.py с clamp / deg_to_rad
# в другом файле: import units
# units.clamp(1.7, -1.0, 1.0)
```

## Разбор

`units` хранит математические мелочи без знания о моторах. `motion` знает про команды движения и переиспользует `clamp`. Главная программа не обязана импортировать `units` напрямую, если ей достаточно `safe_cmd` — меньше связанность.

Имя `units.clamp` показывает происхождение. Если в `motion` тоже появится своя `clamp` с другим смыслом, конфликта пространств не будет.

Верхний уровень `PI ← ...` в модуле выполняется при загрузке — здесь это константа, безопасно. Если бы при импорте сразу открывался порт устройства, любой тестовый импорт имел бы побочный эффект — плохой дизайн инициализации.

Стрелка зависимости идёт от `motion` к `units`, не наоборот. Так проще развивать математику отдельно от политики движения.

## Ошибки

- Сваливать весь проект в один файл «пока маленький».
- Делать модули-перекрёстки, которые знают обо всём.
- Писать тяжёлые побочные эффекты при импорте.
- Создавать циклические импорты и чинить их костылями порядка загрузки.
- Импортировать «всё подряд» и потерять след имён.

## Что запомнить

Модуль группирует код и имена. Импорт подключает зависимость. Публичный интерфейс важнее внутренностей. Первый импорт инициализирует модуль — держите это чистым. Циклические зависимости сигналят о неверных границах. Пространства имён модулей снижают конфликты.

## Задание

Разрежьте учебную программу «чтение конфигурации + расчёт скорости + печать отчёта» на три модуля. Для каждого перечислите публичные функции и кого он импортирует. Проверьте, нет ли цикла зависимостей.
