# Пакеты

## Цель

Понять пакет как способ группировать модули в библиотеку или часть проекта с общей зоной имён, версией и способом установки. После урока вы будете отличать «свой модуль в репозитории» от «внешняя зависимость» и понимать, зачем фиксировать версии.

## Что уже пройдено

Модуль — единица кода. Пакет — набор связанных модулей (часто каталог с правилами языка) плюс метаданные: имя, версия, зависимости. Экосистемы языков поставляют тысячи пакетов через реестры.

## Объяснение с нуля

Пакет решает организационную и дистрибутивную задачу. Организационно: `graphics.draw`, `graphics.color` — модули внутри пакета `graphics`. Дистрибутивно: вы публикуете или устанавливаете пакет целиком, чтобы не копировать файлы руками.

Стандартная библиотека — пакеты/модули, идущие с языком. Сторонние пакеты ставят отдельно. Писать всё с нуля редко разумно; слепо тянуть десятки зависимостей тоже опасно. Выбор — инженерное решение: зрелость пакета, лицензия, активность, размер, соответствие задаче.

Версии важны. Семантическое версионирование (упрощённо): мажор — ломающие изменения; минор — новая функциональность совместимо; патч — исправления. Фиксация версий в проекте помогает собрать завтра тот же мир, что сегодня. «Всегда бери последнюю» — путь к сюрпризам.

Конфликт зависимостей: пакету A нужна библиотека X версии 1, пакету B — версии 2. Менеджеры пакетов пытаются решить систему ограничений; иногда приходится менять набор библиотек. Это нормальная часть сопровождения, не личная неудача.

Пакет ≠ программа. Программа — то, что вы запускаете. Пакет — строительный материал. Иногда пакет содержит точку входа «как утилита», но концептуально это всё ещё поставляемый код с интерфейсом.

Внутренние пакеты компании и публичные open-source пакеты живут по одним правилам импорта, но по разным правилам доверия: внутренний код вы контролируете; внешний нужно оценивать.

Изоляция окружений («свой набор пакетов на проект») спасает от каши на машине разработчика. Это практика, которую стоит взять рано.

## Термины

- **Пакет** — распространяемый набор модулей с метаданными.
- **Зависимость** — другой пакет, без которого этот не работает.
- **Реестр пакетов** — каталог, откуда ставят библиотеки.
- **Версия** — метка состояния пакета во времени.
- **Менеджер пакетов** — инструмент установки и разрешения зависимостей.
- **Виртуальное окружение** (частая практика) — изолированный набор установленных пакетов для проекта.

## Внутреннее устройство

Установка кладёт файлы пакета в место, где язык их найдёт, и записывает метаданные. Импорт затем работает как с локальными модулями, только путь поиска включает каталог установленных библиотек.

Изоляция окружений предотвращает «у проекта А одна версия библиотеки, у B другая, а глобально всё перемешалось». Навык «окружение на проект» сберегает нервы ещё до глубокого изучения конкретного менеджера.

Сборка пакета упаковывает исходники (иногда компилированные артефакты), описывает зависимости и точку входа. Пользователю достаточно команды установки — если метаданные честные.

Безопасность: зависимость — это чужой код в вашем процессе. Минимизируйте набор, обновляйте при известных уязвимостях, читайте, что ставите в критичные системы. Для обучения достаточно принципа недоверия по умолчанию.

Манифест зависимостей (файл со списком пакетов и версий) — часть проекта наравне с исходниками. Без него «у меня работает» невоспроизводимо.

## Пример

```text
Структура идеи:

robot_kit/                 # пакет
  init-marker              # маркер пакета (концепция)
  motors.py                # модуль
  sensors.py               # модуль
  utils/
    mathx.py               # вложенный пакет/модуль

Использование в приложении:
  импортировать robot_kit.motors как motors
  motors.set_speed("left", 0.3)

Зависимости проекта (идея файла манифеста):
  robot_kit == 1.4.2
  yaml_lib  >= 6.0, < 7.0

Сценарий конфликта:
  app нуждает logging_ext 2.x
  robot_kit нуждает logging_ext 1.x
  → нужно обновить robot_kit или заменить logging_ext

# Python-иллюстрация идеи:
# pip install some-package
# import some_package
```

## Разбор

Пакет `robot_kit` прячет несколько модулей под общим префиксом. Приложению не важно, как устроены файлы внутри, пока стабилен импорт `robot_kit.motors`.

Манифест версий фиксирует воспроизводимость. Диапазон `>= 6, < 7` говорит: минорные обновления yaml_lib допустимы, мажорная семёрка — нет, пока не проверим совместимость.

Конфликт версий иллюстрирует, что «просто поставить всё» не всегда возможно. Решение — инженерия зависимостей, а не отключение проверок.

Отличие модуля от пакета здесь видно наглядно: `motors.py` — модуль; `robot_kit` — пакет, который его содержит и поставляет.

## Ошибки

- Копировать чужие исходники вместо осмысленной зависимости (или наоборот — тянуть пакет ради трёх строк).
- Не фиксировать версии и удивляться, что «вчера работало».
- Ставить всё глобально в одну кучу на машине.
- Считать любой популярный пакет безопасным без взгляда на контекст.
- Путать пакет как поставку с модулем как файлом: уровни разные, но связаны.

## Что запомнить

Пакет группирует модули для поставки и импорта. Версии и манифесты дают воспроизводимость. Менеджер пакетов решает граф зависимостей. Окружения изолируют проекты. Внешний код — ответственность, не магия. Стандартная библиотека и сторонние пакеты — разные источники доверия.

## Задание

Для учебного проекта перечислите три функции, которые разумно взять из готового пакета, и три, которые лучше написать самим. Для одной внешней зависимости укажите, какое ограничение версии вы бы задали и почему.
