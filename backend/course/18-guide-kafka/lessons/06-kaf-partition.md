## Цель

Понять partition как единицу параллелизма и упорядоченного лога внутри топика: как выбирается партиция, зачем ключ, какие пределы масштабирования из этого следуют.

## Что уже нужно понимать

- Topic — именованный поток.
- Запись имеет ключ и значение (ключ может быть пустым).
- Консьюмеры в группе делят работу; брокер хранит append-only лог.

## Объяснение

Топик в Kafka **разрезан на партиции**. Каждая партиция — это отдельный упорядоченный лог: запись номер 0, 1, 2, … (offset внутри партиции). Топик из шести партиций — это шесть независимых логов под одним именем.

Зачем резать? **Параллелизм**. Один лог последовательно читается одним консьюмером в группе на эту партицию. Чтобы обрабатывать поток в несколько рук, нужны несколько партиций. Грубое правило: максимум полезных активных консьюмеров в одной группе на топик ≈ число партиций.

Продюсер выбирает партицию так:

- если указан **ключ** — обычно `hash(key) % N` (упрощённо; в деталях есть sticky/murmur и т.д., идея та же);
- если ключа нет — распределение по политикам клиента (round-robin / sticky), без привязки сущности к одной партиции;
- иногда партицию задают явно (редко нужно в бизнес-коде).

Следствие хеша ключа: все сообщения с ключом `ord_9f2a` при фиксированном N попадают в одну и ту же партицию. Внутри неё они упорядочены по времени append. Сообщения разных ключей могут быть в разных партициях — **глобального порядка по всему топику нет**.

Это центральная ментальная модель Kafka: порядок гарантирован **внутри партиции**, а не «вообще в топике». Если вам нужен строгий порядок по заказу — кладите один и тот же ключ заказа. Если нужен глобальный порядок всех заказов магазина — одна партиция (и потолок параллелизма = 1), либо пересмотр требования.

Число партиций выбирают заранее с запасом. Увеличить можно, уменьшить практически нельзя без пересоздания. Увеличение N меняет `hash % N`: **тот же ключ может начать попадать в другую партицию**. Старые записи остаются где были; новые — уже по новой схеме. Локальный порядок «всех событий ключа за всю жизнь топика» при смене N ломается на границе. Поэтому партиции планируют осознанно, а не «добавим ночью в пятницу».

Репликация тоже идёт **по партициям**: у каждой свой лидер и свои follower’ы. Баланс лидеров по брокерам важен для равномерной нагрузки.

Перекос ключей (hot key) — практическая боль: один популярный `user_id` или один `tenant_id` на всю платформу собирает гигантскую партицию, пока другие пустуют. Тогда параллелизм на бумаге есть, а узкое место — одна горячая партиция. Лечится пересмотром ключа (иногда составной ключ), шардированием сущности, или принятием факта и вертикальным усилением обработки этой партиции.

Как оценить N на старте? Возьмите целевой throughput консьюмера на одно ядро/процесс, целевой пик топика и желаемый запас. Если один консьюмер тянет 500 msg/s, а пик 4000 — минимум порядка 8 партиций, плюс запас на рост. Не раздувайте до сотен «на всякий случай»: больше партиций — больше файлов, метаданных, дольше rebalance, выше нагрузка на контроллер/координацию. Баланс важнее круглой цифры.

Партиции также влияют на **операции восстановления**. Восстанавливать или перемещать лидеров приходится поштучно по партициям. Неравномерное размещение лидеров на одном брокере даёт «почему этот брокер горячий, хотя брокеров три». Периодически смотрят баланс лидеров.

Помните: консьюмер может читать несколько партиций, но **гарантия порядка не склеивает их**. Если обработчик пишет в одну таблицу статусов из разных партиций параллельно, гонки между сущностями возможны только если вы сами смешали ключи; между разными ключами это обычно нормально. Путаница начинается, когда бизнес думал, что «топик упорядочен целиком».

## Термины

- **Partition** — упорядоченный лог-часть топика.
- **Partition count (N)** — число партиций топика.
- **Partition key** — ключ, по которому выбирают партицию.
- **Leader partition** — лидер конкретной партиции на одном из брокеров.
- **Hot partition / hot key** — перекос нагрузки на одну партицию.
- **Ordering key** — ключ, выбранный ради порядка связанного потока.

## Как это устроено

Физически партиция хранится как сегменты файлов на диске брокера-лидера (и копии на репликах). Новая запись всегда **append** в конец активного сегмента. Консьюмер читает последовательно по offset — это дешёво.

Назначение партиций консьюмерам группы делает координатор: при трёх партициях и двумя консьюмерами один получит две, второй — одну (пример). При добавлении третьего консьюмера произойдёт rebalance — временная пауза обработки, о которой нужно помнить.

Продюсер не пишет «в топик вообще» без выбора партиции: даже при ключе клиент сначала вычисляет номер. Метаданные кластера говорят, на каком брокере лидер этой партиции.

## Пример

```python
def choose_partition(key: bytes | None, num_partitions: int) -> int:
    if key is None:
        # упрощённо: без ключа — нет стабильной привязки
        return sticky_or_round_robin(num_partitions)
    return murmur2(key) % num_partitions


def publish_order_events(producer, order_id: str, events: list[dict]) -> None:
    key = order_id.encode("utf-8")
    for event in events:
        producer.send(topic="orders.events", key=key, value=encode_json(event))
        # все events одного order_id -> одна partition -> порядок append сохраняется
```

Иллюстрация распределения:

```text
orders.events, N=4

key=ord_A -> partition 2
key=ord_B -> partition 0
key=ord_C -> partition 2   # может совпасть с A — это нормально
key=ord_D -> partition 1

В partition 2 лог:
offset 10: ord_A OrderCreated
offset 11: ord_C OrderCreated
offset 12: ord_A OrderPaid     # OrderPaid после Created для A — да
```

Между `ord_A` и `ord_C` порядок в партиции есть, но он не несёт бизнес-смысла «A раньше C в жизни магазина» — это просто порядок записи в этот лог.

## Разбор

Одним ключом `order_id` мы купили локальный порядок жизненного цикла заказа. Цена — все события этого заказа обрабатываются одним консьюмером группы (владельцем партиции). Если заказы распределены равномерно, четыре партиции дают до четырёх параллельных обработчиков. Если 80% событий — один оптовый клиент с одним id в ключе, получите hot key.

Совпадение `ord_A` и `ord_C` в одной партиции не значит, что они связаны; консьюмер должен смотреть ключ/тело, а не полагаться на «соседей по логу».

## Практическое применение

- Параллельная обработка потока заказов с порядком внутри заказа.
- Шардирование кликстрима по `session_id` / `user_id`.
- Оценка N от целевого throughput и желаемого числа консьюмеров.
- Планирование репликации и лидеров равномерно по брокерам.

## Типичные ошибки

- Ждать глобальный порядок по топику при N>1.
- Поставить N=1 «чтобы был порядок», потом упереться в CPU одного консьюмера.
- Увеличить партиции без миграционного плана по ключам.
- Ключ = новый UUID на каждое сообщение → порядок сущности уничтожен.
- Игнорировать hot keys и винить «Kafka тормозит».

## Что запомнить

- Партиция — единица порядка и параллелизма.
- Порядок: внутри партиции; между партициями — нет.
- Ключ стабильно привязывает сущность к партиции (пока N не меняли).
- Число консьюмеров в группе полезно до N.
- Менять N — операция с последствиями для маршрутизации ключей.
