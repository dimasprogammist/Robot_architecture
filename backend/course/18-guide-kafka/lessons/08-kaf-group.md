## Цель

Понять consumer group как способ масштабировать обработку одного топика и как способ независимо подписывать разные приложения на один и тот же лог.

## Что уже нужно понимать

- Топик разделён на партиции.
- Offset коммитится в контексте читателя.
- Одна партиция в один момент обрабатывается одним членом группы (для этой группы).

## Объяснение

**Consumer group** — набор консьюмер-процессов с одним и тем же `group.id`, которые **совместно** читают топик(и). Kafka распределяет партиции между членами группы так, чтобы каждая партиция досталась не более чем одному члену группы. Так достигается конкурирующая обработка: как «несколько воркеров на очередь», но единицей работы является партиция, а не отдельное сообщение из общего котла произвольным образом (внутри партиции порядок сохраняется у одного владельца).

Если группа одна, а инстансов три, при девяти партициях каждый обычно получит по три. Если инстансов десять при девяти партициях, один будет без партиций — онidle. Масштабирование «добавь ещё под» работает только пока есть свободные партиции.

Если **групп две** — `mail-service` и `analytics-service` — у каждой свой курсор offset. Сообщение, прочитанное почтой, не исчезает для аналитики. Это и есть естественный pub/sub fan-out в модели Kafka. Путать «два пода одного деплоя» и «два разных сервиса» — частая ошибка: первым нужен один group id, вторым — разные.

При изменении состава группы (деплой, падение пода, автоскейл) происходит **rebalance**: партиции переназначаются. Во время rebalance обработка может приостанавливаться; слишком частые rebalance (короткий session, нестабильная сеть, долгий poll) бьют по latency. Стабильность группы — часть дизайна: адекватный `max.poll.interval`, быстрая обработка или вынос тяжёлого в другой пул, аккуратные деплои (rolling без шторма join/leave).

Group id — тоже контракт. Случайно сменить `mail-service` на `mail-service-v2` без переноса offset = группа «с нуля» по политике старта: либо пропустит историю, либо переиграет всё доступное. Версионируйте group id осознанно (например, когда намеренно нужен replay с новой логикой и новым курсором).

Статическое членство (идея) и кооперативный rebalance уменьшают боль, но концепция та же: группа согласует, кто за какие партиции отвечает, и хранит committed offsets на группу.

Отдельно про **мультитопиковую подписку**: один консьюмер может подписаться на несколько топиков в одной группе. Assignment тогда делит все партиции всех подписок. Это удобно для одного сервиса, который применяет связанные потоки, но усложняет картину лага и нагрузки. Не склеивайте в одну группу несвязанные потоки «чтобы меньше деплоев» — операционно вы сами себе мешаете.

Деплой консьюмеров лучше делать постепенно: rolling update уменьшает шок rebalance по сравнению с одновременным убийством всех подов. Следите, чтобы время старта нового пода и прогрева не выталкивало остальных за session timeout. В Kubernetes liveness/readiness должны отражать реальную готовность читать, а не только «процесс жив».

Имя группы включайте в алерты и дашборды рядом с топиком: «лаг orders.events» без group id бесполезен, когда групп пять.

## Термины

- **group.id** — идентификатор группы.
- **Member** — процесс-консьюмер в группе.
- **Assignment** — какая партиция какому member досталась.
- **Rebalance** — пересчёт assignment при изменении членства/подписки.
- **Fan-out (через группы)** — независимые курсоры разных group id.
- **Competing consumers (внутри группы)** — разделённые партиции, без дублирования одной партиции двум членам.
- **Idle consumer** — член без назначенных партиций.

## Как это устроено

1. Консьюмер стартует с `group.id` и списком топиков.
2. Координатор группы фиксирует join.
3. Считается assignment (стратегия range/round-robin/cooperative — идея «алгоритм делит партиции»).
4. Каждый member читает только свои партиции и коммитит offset от имени группы.
5. Heartbeat поддерживает членство; пропуск → исключение → rebalance.
6. Новый сервис с другим group id проходит тот же цикл со своим хранилищем offset независимо.

Продюсеры о группах не знают и не должны знать. Они пишут в топик. Кто подписан — зона потребителей и платформы.

## Пример

```python
# Три инстанса одного сервиса — ОДИН group.id
def start_worker(instance_name: str) -> None:
    consumer = BrokerConsumer(
        group_id="warehouse-service",
        client_id=instance_name,
        topics=["orders.events"],
    )
    consumer.run(handler=handle_order_event)


# Другое приложение — ДРУГОЙ group.id, тот же топик
def start_mailer() -> None:
    consumer = BrokerConsumer(
        group_id="mail-service",
        topics=["orders.events"],
    )
    consumer.run(handler=handle_mail_event)
```

Карта назначений:

```text
topic orders.events partitions: 0 1 2 3 4 5

group warehouse-service:
  pod-a: 0,1
  pod-b: 2,3
  pod-c: 4,5

group mail-service:
  pod-m1: 0,1,2
  pod-m2: 3,4,5

Каждая запись обрабатывается один раз в warehouse-service
и один раз в mail-service (при нормальной работе групп).
```

## Разбор

`warehouse-service` масштабируется тремя подами по партициям — конкурирующее потребление. `mail-service` параллельно читает весь поток своим курсором — fan-out. Если у mail только один под на шесть партиций, он один читает все шесть (медленно, но корректно). Добавление второго mail-пода делит партиции пополам после rebalance.

`client_id=instance_name` помогает в метриках и логах отличать members, не меняя group id.

## Практическое применение

- Горизонтальный scale воркеров одного сервиса.
- Независимые подписки: поиск, аналитика, уведомления, антифрод.
- Выделенная группа для «перестройки проекции» с отдельным group id.
- Ограничение прав: разные группы — разные команды и алерты по лагу.

## Типичные ошибки

- Двум разным сервисам случайно поставить один group.id → они украдут партиции друг у друга, каждый увидит только часть потока.
- Назвать группу `test` в проде и переиспользовать в staging против одного кластера.
- Частые деплои всех реплик сразу → лавина rebalance.
- Ждать, что 20 реплик ускорят топик с 3 партициями.
- Сменить group id и удивиться полному replay или пропуску истории.

## Что запомнить

- Один group.id = совместное деление партиций + общий курсор.
- Разные group.id = независимые чтения одного топика.
- Потолок параллелизма группы ≈ число партиций.
- Rebalance — норма, но частый — проблема.
- group.id — часть контракта эксплуатации.
