## Цель

Понять роль консьюмера: как забирают сообщения, чем чтение лога отличается от «взял из очереди и удалил», зачем нужен commit смещения и почему обработка обязана переживать повторы.

## Что уже нужно понимать

- Продюсер публикует сообщения в брокер.
- Брокер хранит сообщения хотя бы некоторое время (политика retention / до ack — зависит от системы).
- Сеть и процессы падают; «сделал работу» и «сказал брокеру, что сделал» — два шага.

## Объяснение

Консьюмер — сторона, которая **читает** сообщения и выполняет побочный эффект или обновляет своё состояние: шлёт письмо, пишет в свою БД, дергает внешний API, считает метрику.

В классической очереди модель часто такая: получил сообщение в эксклюзивную «корзину», обработал, отправил ack — брокер больше никому его не отдаст. В Kafka модель другая: сообщения лежат в **логе** партиции. Консьюмер (точнее, группа консьюмеров) помнит **offset** — «до какого места я уже прочитал». Чтение не удаляет запись из лога для всех навсегда; другие группы могут читать тот же топик со своей позиции.

Отсюда важное следствие: консьюмер Kafka больше похож на «курсор по журналу», чем на «воркер, опустошающий ячейку». Это даёт возможность нескольким независимым приложениям питаться одним потоком событий. Цена — вы сами отвечаете за то, когда двигать курсор.

Когда двигать offset (commit)?

- Если закоммитить **до** обработки, а потом процесс умрёт — сообщение потеряется с точки зрения этого консьюмера (at-most-once поведение на практике).
- Если обработать и **потом** закоммитить, при падении между этими шагами сообщение придёт снова (at-least-once). Это самый частый рабочий режим.
- Exactly-once между системами — отдельная сложная тема; на уровне идей это «нет потерь и нет видимых дублей для эффекта», обычно через транзакции и/или идемпотентную обработку.

Поэтому здоровый консьюмер проектируют как **идемпотентный** или хотя бы безопасный к повтору: повторная обработка того же `order_id` не должна дважды списывать деньги. Техники: уникальный ключ в БД, таблица обработанных event_id, натуральные upsert.

Консьюмер должен уметь **отставать**. Если продюсер пишет быстрее, чем вы обрабатываете, лаг растёт. Это сигнал масштабировать потребителей (в рамках числа партиций), оптимизировать работу или ставить backpressure раньше по цепочке. Игнорировать лаг — значит жить с «событийной системой», которая фактически смотрит в прошлое на часы.

Ошибки обработки делят на временные и ядовитые. Временные (таймаут внешней API) — ретрай с паузой. Ядовитые (битый JSON, нарушенный инвариант) — бесконечный ретрай блокирует партицию для этого консьюмера. Нужны dead letter / карантин — отдельный урок.

Ещё одна обязанность консьюмера — **наблюдаемость**. Мало «сервис запущен». Нужны: лаг по партициям, скорость обработки, число ошибок, доля ретраев, длина dead letter. Без этого асинхронщина превращается в «вроде работает, а письма уходят через три часа и никто не заметил до жалоб».

Контракт консьюмера с продюсером обычно асимметричен: продюсер не знает вашу БД, а вы обязаны переживать эволюцию схемы. Практичные приёмы: игнорировать неизвестные поля, проверять `version`, явно логировать неизвестный `type` вместо падения всего процесса, если политика это допускает. Строгий режим «упал на всём чужом» уместен только когда топик узкий и под вашим контролем.

Не смешивайте в одном цикле «прочитал из брокера» и «держим HTTP-сервер того же процесса под пользовательским трафиком» без расчёта. Долгий poll и тяжёлый handle ухудшают latency API. Часто консьюмеры выносят в отдельные деплои — те же репозитории логики, другой entrypoint.

## Термины

- **Consumer** — клиент, читающий из брокера.
- **Poll / fetch** — запрос пачки записей.
- **Offset** — позиция в логе партиции.
- **Commit offset** — сохранить прогресс «обработано досюда».
- **Consumer group** — набор консьюмеров, совместно читающих топик с разделением партиций.
- **Lag** — насколько offset консьюмера отстаёт от конца лога.
- **Ack** (в очередях) — подтверждение обработки; в Kafka аналог по смыслу — commit, но механика иная.
- **Rebalance** — перераспределение партиций между членами группы при изменении состава.

## Как это устроено

Цикл типичного консьюмера:

1. Вступает в группу, получает назначения партиций.
2. Знает committed offset (или политику старта: с начала / с конца).
3. Делает poll — получает пакет записей.
4. Для каждой записи: десериализует, обрабатывает, при необходимости пишет в свою БД.
5. Коммитит новые offset’ы (автоматически по таймеру или вручную после пакета).
6. При падении/рестарте продолжает с последнего коммита — возможны повторы хвоста.

Вручную коммитить после пакета удобно, когда пачка должна быть либо обработана целиком с точки зрения вашей логики, либо повторена. Автокоммит проще, но легче получить сюрприз «коммитнули, обработать не успели».

Консьюмер не обязан обрабатывать вечно в одном процессе. Горизонтальное масштабирование внутри одной группы ограничено числом партиций: две партиции — два активных обработчика в группе на этот топик (лишние будут простаивать). Новая **группа** с другим group id читает тот же топик независимо — это fan-out приложений.

## Пример

```python
import json


class MailConsumer:
    def __init__(self, broker, mailer, processed_repo):
        self.broker = broker
        self.mailer = mailer
        self.processed = processed_repo

    def run_forever(self) -> None:
        self.broker.subscribe(
            topics=["orders.events"],
            group_id="mail-service",
        )
        while True:
            batch = self.broker.poll(timeout_ms=1000, max_records=100)
            if not batch:
                continue
            for record in batch:
                self.handle(record)
            # commit только после успешной обработки пакета
            self.broker.commit()

    def handle(self, record) -> None:
        event = json.loads(record.value.decode("utf-8"))
        if event.get("type") != "OrderCreated":
            return

        event_id = f"{record.topic}-{record.partition}-{record.offset}"
        # идемпотентность: повтор того же offset/события безопасен
        if self.processed.already_done(event_id):
            return

        self.mailer.send_order_confirmation(
            user_id=event["user_id"],
            order_id=event["order_id"],
        )
        self.processed.mark_done(event_id)
```

Сообщение на входе (упрощённо):

```text
topic=orders.events partition=2 offset=18491
key=ord_9f2a
value={"type":"OrderCreated","order_id":"ord_9f2a","user_id":"usr_17",...}
```

## Разбор

`group_id="mail-service"` означает: все инстансы почтового сервиса делят партиции между собой, но не мешают группе `warehouse-service`, у которой свой курсор. `event_id` из topic-partition-offset — стабильный идентификатор записи в логе; его удобно использовать как ключ идемпотентности, если у события нет своего uuid. Commit после цикла по batch снижает риск «отметили прочитанным то, что не обработали», ценой возможных повторов всего хвоста пакета при падении посередине — отсюда снова идемпотентность.

Пропуск событий других `type` — нормальная практика, когда в одном топике несколько видов фактов; альтернатива — отдельные топики на тип.

## Практическое применение

- Почтовые и push-уведомления по событиям домена.
- Построение read-модели: консьюмер пишет в Elasticsearch / свою Postgres.
- Воркеры тяжёлых задач, читающие команды из топика.
- Аудит и стриминг в аналитическое хранилище.

## Типичные ошибки

- Коммит до побочного эффекта → тихие потери при рестарте.
- Обработка без идемпотентности при at-least-once → дубли писем, двойные проводки.
- Один медленный вызов API в горячем цикле → лаг растёт, партиция «залипает».
- Ловить все исключения и continue без политики → ядовитые сообщения крутятся вечно или молча скипаются.
- Путать «два инстанса одного сервиса» (одна группа) и «два разных сервиса» (две группы).

## Что запомнить

- Консьюмер двигает курсор по логу; в Kafka чтение не равно удалению для всех.
- Commit offset — заявление о прогрессе, его момент определяет потери vs дубли.
- Идемпотентность — базовый навык консьюмера.
- Лаг — метрика здоровья, не «внутренности брокера».
- Масштаб внутри группы упирается в число партиций.
