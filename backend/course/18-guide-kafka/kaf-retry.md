## Цель

Научиться отличать временные ошибки от ядовитых сообщений, проектировать ретраи без блокировки партиции навечно и использовать dead letter как карантин с наблюдаемостью.

## Что уже нужно понимать

- Консьюмер обрабатывает записи последовательно в рамках партиции.
- At-least-once приводит к повторам при сбоях.
- Лаг растёт, если обработка стоит.

## Объяснение

Не каждая ошибка одинакова.

**Временная** (timeout зависимого API, 503, взаимная блокировка БД): имеет смысл повторить с паузой. Часто помогает экспоненциальный backoff и jitter, чтобы не устроить thundering herd.

**Ядовитая / permanent** (невалидный JSON, неизвестный тип при строгой схеме, бизнес-инвариант «отрицательный возраст»): повторять бесконечно бессмысленно. Сообщение будет падать снова, а записи **позади него в той же партиции** не обработаются, пока вы стоите на этой. Это «head-of-line blocking» — одна гнилая запись останавливает очередь партиции для вашей группы.

Поэтому нужен явный путь: после N попыток (или сразу для явно permanent ошибок) отправить сообщение в **dead letter** (отдельный топик/очередь/таблица карантина) с причиной, исходными координатами и телом, закоммитить исходный offset и идти дальше. Затем человек или спецпроцесс разбирает DLQ.

Ретраи бывают разных уровней:

1. **В процессе** — цикл try/sleep в handle. Просто, но держит poll и риск превысить max.poll.interval → rebalance.
2. **Отложенный топик** — записать в `topic.retry` с полем `attempt` и `execute_not_before`; отдельный консьюмер читает ретраи. Исходная партиция не блокируется долго.
3. **Снова в тот же топик** — опасно без маркеров: легко получить петли и нарушить порядок.

Для писем и платежей политики разные. Письмо можно отложить на минуты. Денежный эффект — часто лучше быстро упасть в DLQ/алерт, чем «тихо крутить» без наблюдаемости.

Dead letter — не помойка «чтобы не падал сервис». Это **очередь инцидентов**. Нужны метрики длины DLQ, алерты, runbook: кто смотрит, как реплеит исправленные сообщения, как правит продюсера при системной поломке схемы.

Идемпотентность и ретраи связаны: любой ретрай может привести к повторному эффекту. Сначала сделайте эффект безопасным к повтору, потом усиливайте ретраи.

Не путайте ретрай консьюмера с ретраем продюсера. Продюсер ретраит send до ack. Консьюмер ретраит бизнес-обработку уже доставленной записи. Оба могут плодить дубли на своём участке.

## Термины

- **Retry** — повторная попытка обработки.
- **Backoff** — пауза между попытками.
- **Jitter** — случайная добавка к паузе.
- **Poison message** — запись, стабильно ломающая обработку.
- **Dead letter (DLQ / DLT)** — карантин для безнадёжных/исчерпавших попытки.
- **Head-of-line blocking** — блокировка хвоста из‑за головы очереди.
- **Attempt count** — счётчик попыток в заголовке или обёртке.
- **Replay from DLQ** — возврат исправленного сообщения в основной поток.

## Как это устроено

Паттерн с лимитом попыток в процессе (осторожно с таймаутами группы):

1. Получили запись.
2. Пытаемся обработать до K раз с backoff.
3. Успех → commit.
4. Неуспех permanent или K исчерпан → publish в DLT с метаданными → commit исходной.

Паттерн retry-топика:

1. Основной консьюмер при временной ошибке пишет в `orders.events.retry` обёртку и коммитит основную.
2. Retry-консьюмер ждёт `execute_not_before`, пробует снова.
3. При исчерпании — в `orders.events.dlq`.

Метаданные в карантине обязательны: исходный topic/partition/offset, group, timestamp ошибки, exception, attempt. Без этого DLQ бесполезен для разбора.

## Пример

```python
import time
from datetime import datetime, timezone


class RetryingHandler:
    def __init__(self, broker, dlt_topic: str, max_attempts: int = 5):
        self.broker = broker
        self.dlt_topic = dlt_topic
        self.max_attempts = max_attempts

    def process(self, record) -> None:
        last_exc = None
        for attempt in range(1, self.max_attempts + 1):
            try:
                self.handle_business(record)
                return
            except TemporaryDependencyError as exc:
                last_exc = exc
                time.sleep(min(2 ** attempt, 30))
            except PermanentDataError as exc:
                self.to_dead_letter(record, exc, attempt)
                return
        self.to_dead_letter(record, last_exc, self.max_attempts)

    def to_dead_letter(self, record, exc: Exception, attempt: int) -> None:
        envelope = {
            "failed_at": datetime.now(timezone.utc).isoformat(),
            "attempt": attempt,
            "error": str(exc),
            "source": {
                "topic": record.topic,
                "partition": record.partition,
                "offset": record.offset,
            },
            "key": None if record.key is None else record.key.decode(),
            "value": record.value.decode("utf-8", errors="replace"),
        }
        self.broker.send(
            topic=self.dlt_topic,
            key=record.key,
            value=encode_json(envelope),
        )
```

Текст в DLT:

```text
{
  "failed_at": "2026-09-25T08:01:12+00:00",
  "attempt": 5,
  "error": "schema: missing field order_id",
  "source": {"topic": "orders.events", "partition": 2, "offset": 18491},
  "key": "ord_9f2a",
  "value": "{\"type\":\"OrderCreated\",\"total\":100}"
}
```

## Разбор

`PermanentDataError` сразу уходит в DLT — нет смысла жечь попытки. `TemporaryDependencyError` крутится с backoff, но ограничен `max_attempts`, после чего тоже карантин: бесконечный sleep в handle опасен для членства в группе. В DLT положили исходное тело и координаты — можно починить продюсера и решить, реплеит ли вручную.

Заметьте: после `to_dead_letter` вызывающий код должен закоммитить исходный offset, иначе яд останется в голове партиции.

## Практическое применение

- Интеграции с внешними API, которые иногда 503.
- Ввод данных от партнёров с грязной схемой — DLT + алерт на долю брака.
- Отложенные ретраи для rate-limited сервисов.
- Операционный процесс: ежедневный разбор DLT ответственным дежурным.

## Типичные ошибки

- Бесконечный ретрай на битых данных → лаг ↑, партиция стоит.
- DLT без алертов — карантин-могильник.
- Глотать exception и commit без DLT — тихая потеря.
- Ретраи без идемпотентности → дубли на каждом sleep.
- Класть в DLT только `str(exc)` без тела сообщения.

## Что запомнить

- Временное ретраим, ядовитое изолируем.
- Head-of-line blocking — цена «стоять на ошибке» в партиции.
- DLT — наблюдаемый карантин, не чёрная дыра.
- Лимит попыток обязателен.
- Commit исходного offset после отправки в DLT — чтобы хвост жил.
