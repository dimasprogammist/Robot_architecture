## Цель

Разобрать роль продюсера: что он делает при отправке, какие решения принимает (канал, ключ, подтверждения), и где заканчивается его ответственность.

## Что уже нужно понимать

- Зачем между сервисами ставят брокер (буфер, развязка во времени).
- Что сообщение — это данные плюс метаданные, а не «магический RPC».
- Базово: сеть может оборваться после того, как брокер уже принял запись, или до этого.

## Объяснение

Продюсер — сторона, которая **публикует** сообщения в брокер. В коде это обычно клиентская библиотека: открыли соединение, указали топик или очередь, сериализовали тело, отправили, дождались (или не дождались) подтверждения.

С точки зрения бизнеса продюсер отвечает на вопрос: «когда в системе случился факт, достойный сообщения?» Типичные моменты: после успешного commit в БД, после приёма вебхука, по таймеру batch-джоба. Плохой момент — «в середине сомнительной транзакции» без понимания, что увидит консьюмер.

Продюсер выбирает **куда** писать: имя топика/очереди. Это часть контракта. Переименование топика без миграции подписчиков ломает интеграцию так же, как смена URL API.

Дальше — **что** писать. Тело должно быть понятным консьюмеру: JSON, Avro, Protobuf — формат не важен сам по себе, важна стабильность схемы. Менять поле `orderId` на `order_id` без версии — частая причина ночных инцидентов. Хорошая привычка: явный `type`/`event_name` и версия схемы в заголовке или в теле.

В Kafka у записи часто есть **ключ**. Ключ не обязан быть уникальным навсегда; он влияет на то, в какую партицию попадёт сообщение (при стандартном партиционировании). Сообщения с одним ключом идут в одну партицию и там сохраняют порядок относительно друг друга. Если ключ не задать, маршрутизация обычно round-robin или sticky — порядок между связанными событиями не гарантирован.

Продюсер решает, **ждать ли подтверждения** брокера. «Послал и забыл» быстрее, но вы не знаете, дошло ли. «Ждать ack от лидера» или «ждать репликации» медленнее, но надёжнее при сбоях. Это компромисс latency vs durability на стороне записи.

Ещё обязанность продюсера — **не путать «отправил» с «обработали»**. Успешный publish значит: брокер принял запись по выбранной политике. Это не значит, что письмо ушло или склад обновился. Если пользователю нужна гарантия побочного эффекта, её даёт консьюмер и мониторинг лага, а не один HTTP 200 от API, который только опубликовал.

Продюсер также думает о **размере и частоте**. Тысячи крошечных сообщений в секунду — нормально для брокера, но дорого для наивного «flush на каждое». Батчинг на клиенте повышает пропускную способность. Гигантское сообщение на десятки мегабайт — обычно антипаттерн: лучше положить файл в object storage и в сообщении передать ссылку.

## Термины

- **Producer** — клиент, пишущий в брокер.
- **Publish / send** — операция отправки записи.
- **Key** — ключ записи; влияет на партиционирование и группировку порядка.
- **Value / payload** — тело сообщения.
- **Headers** — дополнительные метаданные (trace-id, версия схемы, тип события).
- **Ack / acknowledgment** — подтверждение брокера, что запись принята (с разной строгостью).
- **Serialization** — превращение объекта приложения в байты для сети и диска.
- **Idempotent producer** (идея) — режим, когда повторы отправки из‑за сетевых ретраев не плодят лишние дубликаты на уровне брокера (детали — в семантике доставки).

## Как это устроено

Типичный путь записи в лог-ориентированный брокер:

1. Приложение собирает объект события.
2. Клиент сериализует ключ и значение.
3. Клиент выбирает партицию: по хешу ключа или по явному указанию.
4. Запрос уходит на брокера-лидера этой партиции.
5. Лидер пишет в свой лог (append-only) и при необходимости ждёт реплики.
6. Клиенту возвращается успех с метаданными (топик, партиция, offset) или ошибка.
7. При временной ошибке клиент может ретраить; приложение должно понимать последствия повторов.

Append-only означает: новые записи добавляются в конец лога партиции, старые не «редактируются на месте». Исправление факта — новое сообщение (компенсация, обновление статуса), а не правка байтов посередине.

С точки зрения кода приложения продюсер часто живёт рядом с местом, где меняется состояние. Паттерн **transactional outbox**: в одной БД-транзакции пишем бизнес-строку и строку «событие на отправку»; отдельный процесс читает outbox и публикует в брокер. Так уменьшают рассинхрон «БД да / брокер нет».

## Пример

```python
import json
from dataclasses import asdict, dataclass


@dataclass
class OrderCreated:
    order_id: str
    user_id: str
    total_cents: int
    currency: str


class OrderProducer:
    def __init__(self, broker_client, topic: str = "orders.events"):
        self.broker = broker_client
        self.topic = topic

    def publish_order_created(self, event: OrderCreated) -> None:
        key = event.order_id
        value = {
            "type": "OrderCreated",
            "version": 1,
            **asdict(event),
        }
        headers = {
            "content-type": "application/json",
            "event_type": "OrderCreated",
        }
        # wait_for_ack=True — не считаем успехом «ушло в сокет»
        meta = self.broker.send(
            topic=self.topic,
            key=key.encode("utf-8"),
            value=json.dumps(value).encode("utf-8"),
            headers=headers,
            wait_for_ack=True,
        )
        # meta: partition, offset — полезно логировать для трассировки
        print(
            f"published order_id={event.order_id} "
            f"partition={meta.partition} offset={meta.offset}"
        )


def after_order_committed(order: dict, producer: OrderProducer) -> None:
    producer.publish_order_created(
        OrderCreated(
            order_id=order["id"],
            user_id=order["user_id"],
            total_cents=order["total_cents"],
            currency=order["currency"],
        )
    )
```

Текст сообщения (value), которое увидит консьюмер:

```text
{
  "type": "OrderCreated",
  "version": 1,
  "order_id": "ord_9f2a",
  "user_id": "usr_17",
  "total_cents": 4590,
  "currency": "RUB"
}
```

Ключ: `ord_9f2a` — все события этого заказа стремятся в одну партицию.

## Разбор

Ключ выбран как `order_id`, потому что дальше могут прийти `OrderPaid`, `OrderCancelled` того же заказа — их удобно читать по порядку в одной партиции. Поле `type` и `version` позволяют консьюмеру ветвиться и мягко эволюционировать схему. `wait_for_ack=True` отражает осознанный выбор: лучше задержать ответ API на миллисекунды, чем потерять событие при рестарте брокера в неудачный момент (в рамках выбранной политики ack).

Логирование partition/offset — мост к отладке: «событие ушло, консьюмер жалуется, что не видел» — можно проверить лаг и наличие записи.

## Практическое применение

- Публикация доменных событий после изменения агрегата.
- Отправка команд в worker-пул (`GenerateReport`, `ResizeImage`).
- Интеграция с внешней системой через «исходящий» топик, который читает адаптер.
- Аудит: каждое значимое действие — запись в топик для последующего разбора.

## Типичные ошибки

- Публиковать до commit в БД: консьюмер обработает событие про заказ, которого «нет».
- Менять схему без версии и без договорённости с потребителями.
- Класть в ключ случайный UUID на каждое сообщение связанного потока — порядок по сущности ломается.
- Глотать ошибки send и писать в лог «ну ладно»: тихая потеря событий.
- Считать продюсер местом для тяжёлой бизнес-логики «на всех подписчиков» — логика реакции живёт у консьюмеров.

## Что запомнить

- Продюсер пишет факт в брокер; обработка — зона консьюмера.
- Ключ влияет на партицию и локальный порядок.
- Подтверждение брокера и успех бизнес-обработки — разные вещи.
- Контракт: топик + схема + смысл ключа.
- Для согласованности с БД часто нужен outbox, а не «просто send рядом».

## Связь со следующим уроком

Следующий урок — **consumer**: как читают сообщения, где хранится прогресс чтения, почему обработка должна быть готовой к повторам.
