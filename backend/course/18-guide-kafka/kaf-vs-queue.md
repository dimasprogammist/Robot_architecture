## Цель

Сравнить модель Kafka (распределённый лог) с моделью классической очереди сообщений: где они совпадают как «буфер», где расходятся в потреблении, хранении и масштабировании, и как выбирать инструмент под задачу.

## Что уже нужно понимать

- Topic, partition, offset, consumer group.
- Семантики доставки и зачем идемпотентность.
- Когда Kafka избыточна, а когда сильна.

## Объяснение

На поверхности и Kafka, и «обычная очередь» (RabbitMQ, SQS, брокер с очередями/обменниками) решают одно: **перенести сообщение асинхронно** от продюсера к потребителю. Дальше модели расходятся.

**Классическая очередь** думает о сообщении как о задаче в ячейке. Воркер получает задачу (часто с эксклюзивной блокировкой/visibility timeout), обрабатывает, ack — сообщение уходит из очереди. Несколько воркеров конкурируют за задачи из одной очереди. Второй независимый подписчик «всего потока навсегда» обычно требует отдельной подписки/обменника (pub/sub), и это уже другая конфигурация, не «просто та же очередь».

**Kafka** думает о сообщении как о записи в **логе**. Запись остаётся доступной другим в пределах retention. Прогресс — курсор группы. Несколько групп = несколько независимых чтений. Параллелизм внутри группы = партиции, не «каждое сообщение любому воркеру произвольно» без учёта ключа/порядка партиции.

Отсюда практические следствия.

Хранение: очередь стремится быть пустой, когда воркеры справляются. Kafka нормально держит гигабайты лога осознанно — это журнал, не только inbox.

Повторное чтение: в очереди после ack сообщение обычно не взять снова (кроме специальных DLQ/редрайвов). В Kafka replay — штатная идея в окне retention.

Порядок: многие очереди дают порядок в пределах очереди/шарда, но конкурирующие консьюмеры легко перемешивают применение. Kafka явно говорит: порядок в партиции; ключ — ваш инструмент.

Маршрутизация: у очередей богатые exchange/binding, приоритеты, TTL на сообщение, delayed queues — часто удобнее «из коробки». В Kafka похожее делают топиками, заголовками и соглашениями.

Операции: очередь задач легче ментально для «фона приложения». Kafka — платформенный компонент с партициями, репликами, rebalance, схемами.

Не бывает «Kafka лучше очереди» вообще. Бывает «лучше для этого класса задач». Переписывать Celery-очередь отчётов на Kafka «чтобы было современно» — плохая мотивация. Строить шину доменных событий двадцати сервисов на одной FIFO-очереди без fan-out — тоже боль.

Гибрид в компаниях нормален: Kafka для event streams, SQS/Rabbit для job’ов конкретного сервиса, иногда outbox → любой транспорт.

Метрики тоже звучат похоже, но читаются иначе. **Длина очереди** в классике часто должна стремиться к малой величине в норме: воркеры успевают. **Размер лога** в Kafka может быть большим намеренно — это окно истории. Тревожный сигнал для Kafka скорее **лаг группы**, а не «в топике много гигабайт». Путать эти шкалы — путь к ложным инцидентам или пропущенным реальным.

Ещё отличие в **безопасном пропуске**. В очереди nack/requeue возвращает задачу. В Kafka «пропустить» ядовитое = решить, куда его деть (DLT) и сдвинуть offset. Без ритуала пропуска партиция встанет. Поэтому команды, пришедшие из мира очередей, должны явно добавить политику poison pill, а не ждать «очередь сама отложит в DLX как в Rabbit».

По стоимости обучения: очередь задач ближе к интуиции «фоновые джобы». Kafka требует ментальной модели лога — зато потом fan-out и replay становятся естественными. Инвестиция в обучение окупается на событийных платформах и не окупается на трёх cron-задачах.

## Термины

- **Queue** — модель «задача → воркер → ack → удалили».
- **Log / stream** — модель «запись в журнале → курсоры читателей».
- **Competing consumers** — воркеры делят задачи.
- **Pub/Sub** — публикация многим подписчикам.
- **Visibility timeout** — окно, пока сообщение спрятано у воркера в очередях вроде SQS.
- **Ack/Nack** — подтвердить/вернуть задачу в очередь.
- **Retention log** — хранение по времени/размеру в Kafka.
- **Work queue vs event bus** — два разных архитектурных роли.

## Как это устроено

Сравнение по шагам жизни сообщения:

1. **Запись:** обе системы принимают publish. Kafka ещё выбирает партицию по ключу.
2. **Хранение:** очередь — пока не ack (плюс политика); Kafka — пока retention/compaction.
3. **Доставка:** очередь — push/pull задачи воркеру; Kafka — fetch по offset.
4. **Параллелизм:** очередь — по сообщениям между воркерами; Kafka — по партициям между members группы.
5. **Второй сервис-читатель:** очередь — отдельная подписка/копия потока; Kafka — новый group.id на тот же топик.
6. **Ошибка:** очередь — nack/retry/DLQ; Kafka — ретрай в процессе / retry-топик / DLT + commit курсора.

Когда рисуете архитектуру, подпишите роль: «это work queue» или «это event log». Смешение ролей в одном топике/очереди без правил приводит к спорам команд.

## Пример

Один и тот же бизнес-факт, две реализации.

Очередь задач «только почта»:

```text
orders-api -> queue:send-mail -> mail-workers (N) -> ack
Поиск и склад об этом потоке не знают
```

```python
def on_order_created_queue(order: dict) -> None:
    queue.enqueue("send-mail", {"order_id": order["id"], "user_id": order["user_id"]})
```

Лог событий для многих:

```text
orders-api -> topic orders.events
               ├─ group mail-service
               ├─ group warehouse-service
               └─ group search-indexer
```

```python
def on_order_created_kafka(order: dict, producer) -> None:
    producer.send(
        topic="orders.events",
        key=order["id"].encode(),
        value=encode_json({"type": "OrderCreated", **order}),
    )
```

Если завтра понадобится антифрод, в Kafka добавляют группу. В модели одной mail-очереди придётся либо менять продюсера (вторая постановка задачи), либо вводить bus отдельно.

## Разбор

В queue-примере продюсер знает конкретного получателя смысла («send-mail»). В kafka-примере продюсер знает факт («OrderCreated»). Это разные контракты: команда vs событие. Kafka хорошо дружит с событием и fan-out; очередь — с командой и пулом воркеров. Можно слать команды и через Kafka (топик команд), но тогда вы сознательно используете лог как транспорт work queue — работает, просто оцените, не дороже ли managed queue.

Ключ в Kafka-примере снова про порядок заказа; в простой mail-очереди порядок писем обычно менее критичен, важнее throughput воркеров.

## Практическое применение

- Выбор транспорта на дизайн-ревью с явной таблицей сравнения.
- Разделение в инфраструктуре: кластер Kafka ≠ брокер задач CI.
- Миграция: сначала событие в лог, job’ы оставить в очереди.
- Объяснение новичкам, почему «лаг топика» и «длина очереди» — похожие, но не идентичные метрики.

## Типичные ошибки

- Считать Kafka «очередью с партициями» и ждать удаления после commit для всех.
- Строить event bus на классической очереди и копировать сообщения вручную каждому сервису.
- Искать в Kafka приоритеты как в Rabbit «из коробки» и разочаровываться.
- Дублировать одну и ту же задачу и событие без нужды, путая команды.
- Менять инструмент без смены контракта (событие vs команда) — боль останется.

## Что запомнить

- Очередь ≈ работа; Kafka ≈ журнал/поток (часто ещё и работа, но модель другая).
- Fan-out и replay — сильные стороны лога.
- Приоритеты, delay, простой job-пул — часто сильные стороны очереди.
- Commit offset ≠ ack удаления для всех читателей.
- Выбирайте по роли в архитектуре, не по хайпу.
