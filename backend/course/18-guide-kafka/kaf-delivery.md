## Цель

Разобрать три базовые семантики доставки — at-most-once, at-least-once, exactly-once — как инженерные компромиссы между потерями, дублями и сложностью, без магической веры в «галочку в конфиге».

## Что уже нужно понимать

- Продюсер получает ack от брокера с разной строгостью.
- Консьюмер коммитит offset отдельно от побочного эффекта.
- Сеть и процессы падают между любыми двумя шагами.

## Объяснение

Семантика доставки отвечает на вопрос: **сколько раз эффект от сообщения может произойти** при сбоях, и можете ли вы потерять сообщение.

**At-most-once** — не больше одного раза; допускается потеря. Пример пути: продюсер не ретраит при сомнении; или консьюмер коммитит offset до обработки и падает. Подходит для некритичных метрик, приблизительных счётчиков, телеметрии, где дырки терпимы.

**At-least-once** — хотя бы один раз; дубли возможны. Типичный путь: продюсер ретраит, пока не получит ack; консьюмер обрабатывает и только потом коммитит; при падении посередине — повтор. Это режим по умолчанию для большинства бизнес-интеграций. Цена — вы **обязаны** делать обработку идемпотентной или дедуплицировать.

**Exactly-once** — эффект ровно один раз с точки зрения заданных границ системы. Важно: «exactly-once» всегда **в рамках**: между какими компонентами, при каких сбоях, для какого эффекта. End-to-end между «HTTP пользователя» и «письмом у SMTP» без дыр почти никогда не бывает бесплатным. В экосистеме Kafka говорят об идемпотентном продюсере, транзакциях между топиками, read-process-write в рамках транзакционного API — но побочный эффект во внешней БД или платёжке всё равно требует идемпотентности на стороне эффекта.

Практическая формула для большинства команд:

1. Цельтесь в **at-least-once** на транспорте.
2. Делайте **идемпотентный консьюмер** (unique constraint, upsert, store event_id).
3. На продюсере избегайте тихого «send и забыть» для критичных фактов; используйте ack и ретраи осознанно.
4. «Exactly-once» включайте точечно, понимая границы, а не как религию.

Дубли рождаются не только у консьюмера. Продюсер отправил, брокер записал, ack потерялся на сети, продюсер послал снова — в логе две одинаковые бизнес-записи (если нет идемпотентного продюсера). Консьюмер без дедупа выполнит эффект дважды. Идемпотентный продюсер (идея) помогает на участке «один продюсер — один топик» снизить такие дубли записи; это не отменяет дедуп на консьюмере для всех случаев.

Ещё путаница: **успешная доставка в топик** ≠ **успешный бизнес-эффект**. Семантика транспорта про запись/чтение лога. Семантика приложения про деньги, письма, остатки. Склеивать их нужно явно.

Как говорить с бизнесом: не обещайте «Kafka гарантирует ровно один раз». Обещайте: «мы не теряем события при ретраях записи; обработка может повториться; деньги защищены уникальным ключом проводки». Это понятный и честный контракт.

На продюсере смотрите связку `acks`, `retries` и идемпотентности. Сильные ack без ретраев всё равно дают дырки при обрыве до ответа. Ретраи без дедупа/идемпотентности дают дубли. На консьюмере смотрите связку «эффект → commit». Большинство инцидентов «иногда два письма» и «иногда ноль писем» сидят именно в этих двух связках, а не в «мистике брокера».

Тестируйте семантику специально: убивайте под между эффектом и commit; обрывайте сеть после send; подавайте одно и то же event_id дважды. Если тесты только happy-path, прод удивит.

## Термины

- **At-most-once** — ≤1, возможны потери.
- **At-least-once** — ≥1, возможны дубли.
- **Exactly-once** — =1 в заявленных границах.
- **Idempotence** — повторный вызов не меняет результат.
- **Deduplication** — отбрасывание уже виденных id.
- **Producer retries** — повтор send при ошибках.
- **Transactional write** (идея) — атомарность набора записей в топики в рамках протокола брокера.
- **Effect boundary** — где именно вы считаете «ровно один раз» (лог / БД / внешний API).

## Как это устроено

Типичный at-least-once контур:

1. Продюсер send с ретраями до ack лидера/ISR.
2. Запись в логе есть (возможно, дубль при ретрае без идемпотентности).
3. Консьюмер читает, применяет эффект, коммитит offset.
4. Падение между 3а и 3б → повтор эффекта → спасает идемпотентность.

Типичный at-most-once контур:

1. Консьюмер коммитит заранее или игнорирует ошибки обработки.
2. Падение → сообщение считается обработанным → потеря эффекта.

Идея exactly-once read-process-write внутри Kafka:

1. Читаем входной топик.
2. Пишем результат во выходной топик транзакционно вместе с commit offset.
3. Внешний мир (почта) всё ещё separately — нужна идемпотентность ключа письма.

## Пример

```python
class AtLeastOnceWalletConsumer:
    def __init__(self, broker, db):
        self.broker = broker
        self.db = db

    def handle(self, record) -> None:
        event = decode(record.value)
        event_id = event["event_id"]  # UUID от продюсера

        with self.db.transaction():
            inserted = self.db.insert_processed(event_id)
            if not inserted:
                return  # уже применяли — дубль доставки
            self.db.apply_ledger_entry(
                account_id=event["account_id"],
                amount=event["amount"],
                event_id=event_id,
            )
        # commit offset ПОСЛЕ успешной транзакции БД
        self.broker.commit_record(record)


def publish_transfer(producer, event: dict) -> None:
    # event_id заранее — основа дедупа у всех потребителей
    producer.send(
        topic="wallet.events",
        key=event["account_id"].encode(),
        value=encode_json(event),
        acks="all",
        retries=10,
    )
```

Сообщение:

```text
{
  "event_id": "5c2e0c0a-2b1f-4d3a-9c1e-8f7a6b5d4c3b",
  "type": "Credit",
  "account_id": "acc_17",
  "amount": 1000
}
```

## Разбор

`insert_processed` с уникальным ключом по `event_id` превращает at-least-once транспорт в ровно-один эффект на уровне БД кошелька. Даже если в логе Kafka две физические записи с одним business `event_id` (или одна запись прочитана дважды), ledger не раздуется. `acks=all` и retries усиливают «не потерять на записи», принимая риск дублей записи.

Если бы commit offset стоял до транзакции БД, при падении после commit денег бы не начислили — это уже at-most-once по эффекту.

## Практическое применение

- Деньги, остатки, биллинг: at-least-once + строгая идемпотентность.
- Метрики UI: иногда at-most-once достаточно.
- Перекладка топик→топик: место, где транзакционный API Kafka даёт выигрыш.
- Письма: идемпотентный ключ на (template, order_id) во внешней системе или у себя.

## Типичные ошибки

- «Включили exactly-once» и убрали уникальные ключи в БД.
- Считать отсутствие дублей в логе доказательством отсутствия дублей эффекта за годы ретраев приложения.
- Молчаливые ретраи продюсера без event_id.
- Обещать заказчику exactly-once end-to-end без описания границ.
- Путать durability ack с семантикой эффекта.

## Что запомнить

- Три семантики — про потери и дубли при сбоях.
- Рабочий стандарт бизнеса: at-least-once + идемпотентность.
- Exactly-once всегда с границами; внешние эффекты отдельно.
- event_id / натуральный уникальный ключ — ваш друг.
- Момент commit offset определяет класс семантики консьюмера.

## Задание

Для сценария «списать деньги» и сценария «увеличить счётчик просмотров» выбери семантику и механизм защиты. Напиши последовательность шагов handle() с местом commit. Укажи один сбой, который твоя схема переживает, и один — который нет.
