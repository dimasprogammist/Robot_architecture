# Оболочка (shell): посредник между вами и ядром

## Цель

Понять, чем shell отличается от ядра и от программы терминала. После урока вы сможете объяснить цепочку: нажатие Enter → разбор строки → создание процесса → вывод на экран. Вы узнаете, почему `cd` нельзя заменить «обычной утилитой» в том же смысле, что `ls`.

## Исходные знания

Достаточно общего представления о процессе: у него есть память, открытые файлы и идентификатор. Полезно помнить, что ядро обслуживает системные вызовы (создание процесса, открытие файла, чтение и запись). Конкретный дистрибутив Linux знать не обязательно.

## Объяснение

Shell — обычная пользовательская программа. Она не является операционной системой и сама по себе не рисует окно. Её работа: принять текст команды, разобрать синтаксис (кавычки, переменные, перенаправления, конвейеры) и попросить ядро запустить нужную программу. Ядро планирует CPU, выделяет память и даёт доступ к устройствам. Если смешать роли, кажется, что «терминал запускает ls», хотя цепочка длиннее.

Исторически оболочка появилась как способ вызывать утилиты без перекомпиляции системы. В UNIX-традиции много маленьких программ, которые делают одну работу. Shell стал клеем: он связывает утилиты через потоки байтов и коды возврата. Bash, zsh, dash, PowerShell — разные реализации одной идеи. Синтаксис различается, роль посредника общая.

Когда вы вводите `ls -la /tmp`, оболочка делает несколько шагов. Сначала разбивает строку на токены с учётом кавычек. Затем раскрывает шаблоны вроде `*.txt`, если они есть. Подставляет переменные окружения. Решает: это встроенная команда (builtin) или внешняя программа. Для внешней ищет исполняемый файл по списку каталогов PATH. Через системные вызовы создаёт дочерний процесс и обычно ждёт его завершения. Вывод ребёнка попадает в тот же терминал, потому что дескрипторы ввода-вывода унаследованы.

Builtin-команды вроде `cd` и `export` в bash выполняются внутри процесса оболочки. Это принципиально: если бы `cd` был внешней программой, он менял бы каталог только у короткоживущего ребёнка, а ваша shell осталась бы на месте. Текущий каталог — свойство процесса shell, а не «свойство компьютера целиком».

Оболочка хранит состояние сеанса: переменные, функции, alias, историю, настройки дополнения по Tab. Это состояние живёт, пока жив процесс shell. Закрыли окно — процесс завершился, состояние пропало, если вы его не сохранили в файл профиля.

Внешняя команда без слэшей в имени ищется в PATH. Если в имени есть `/`, PATH не используется: путь считается явным. Так нельзя случайно запустить программу из текущей папки только по короткому имени, если точка не в PATH. Это и удобство, и элемент безопасности.

Неинтерактивный режим читает команды из файла скрипта или из аргумента `-c`. Тот же язык, но без приглашения. Скрипты — это просто текст для той же оболочки, а не отдельный «язык операционной системы».

## Термины

**Shell** — интерпретатор командной строки, который запускает программы и настраивает их ввод-вывод.

**Ядро (kernel)** — часть ОС, обрабатывающая системные вызовы, процессы, память и устройства.

**Builtin** — команда, реализованная внутри процесса shell, а не отдельным файлом.

**PATH** — список каталогов, в которых ищут внешние программы по короткому имени.

**Процесс** — экземпляр выполняющейся программы с ресурсами, выделенными ядром.

## Как это работает

Интерактивный цикл: вывести приглашение → прочитать строку → разобрать → выполнить → снова приглашение. Код возврата последней команды доступен через специальную переменную (в bash это `$?`).

Создание процесса на Linux опирается на пару идей fork/exec (фактически могут быть clone и execve): сначала появляется копия, затем образ заменяется нужной программой. До exec shell может подменить файловые дескрипторы — так работают перенаправления и pipe, а сама утилита об этом не думает.

Поиск по PATH идёт слева направо. Первое подходящее исполняемое имя побеждает. Поэтому порядок каталогов в PATH влияет на то, какая версия `python` или `node` запустится.

## Пример

```text
пользователь → эмулятор терминала → псевдотерминал (PTY)
                 ↓
              процесс bash (shell)
                 ↓  fork + exec
              процесс /bin/ls
                 ↓  write в stdout
              обратно в PTY → текст в окне
```

## Разбор

На схеме три разных актора. Эмулятор отвечает за клавиши и отрисовку. Shell отвечает за язык команд. Утилита делает свою работу (список файлов) и не знает про приглашение.

Если `ls` «завис», вы смотрите на процесс утилиты. Если не работает Tab — это поведение shell. Если не печатаются буквы — чаще кодировка терминала, а не поломка `ls`.

Разделение слоёв экономит время: всегда спрашивайте, это синтаксис shell, окружение процесса или сама программа.

## Ошибки

- Считать shell и ядро одним и тем же.
- Запускать скрипт через `sh`, ожидая bash-синтаксис: на многих системах `sh` — это dash.
- Класть `.` в начало PATH на общей машине.
- Путать «command not found» (нет в PATH) с «Permission denied» (файл есть, нет права execute).

## Что запомнить

- Shell — пользовательская программа-посредник; ядро исполняет процессы.
- Builtin меняет состояние самого shell; внешняя команда — отдельный процесс.
- PATH задаёт поиск по короткому имени.
- Разбор кавычек и шаблонов делает shell до запуска утилиты.

## Практика

Выполните `type cd` и `type ls` (bash/zsh) или в PowerShell `Get-Command cd`. Запишите, что встроено, а что внешне. Смените каталог через `cd` и снова посмотрите путь. Объясните себе, почему каталог изменился у shell, а не «у компьютера целиком».

Практический приём: перед отладкой «странной команды» выполните `type cmd` и `command -v cmd`. Если это alias или функция, поведение может отличаться от `/usr/bin/cmd`. В скриптах предпочитайте явные пути или отключённые alias.

Ещё один слой путаницы — разные bash на одной машине (login shell из `/bin/bash`, а CI вызывает `sh`). Проверяйте `echo $BASH_VERSION` и `ls -l $(command -v sh)`.

Когда пишете обёртку для робота или сервера, считайте shell частью контракта запуска: какая оболочка, какой `set -euo pipefail`, какой PATH. Иначе «у меня работает» непереносимо.

История команд (`history`) — ускоритель и риск утечки секретов. Не передавайте пароли аргументами команд: они остаются и в истории, и видны другим пользователям через список процессов.
