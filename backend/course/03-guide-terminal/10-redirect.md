# Перенаправление потоков в файлы

## Цель

Научиться направлять stdin, stdout и stderr в файлы и понимать, что shell делает с дескрипторами до запуска программы.

## Исходные знания

Три стандартных потока и конвейер. Понимание, что дескрипторы можно подменять.

## Объяснение

Перенаправление — просьба к shell: перед запуском команды связать поток с файлом или другим дескриптором. `>` направляет stdout в файл (создаёт или обрезает). `>>` дописывает. `<` подаёт файл на stdin. `2>` отдельно управляет stderr.

Важно: перенаправление делает shell, а не «магия команды». Программа после запуска просто пишет в fd 1; куда указывает fd 1, она обычно не знает.

Порядок и комбинированные формы имеют значение. `>file 2>&1` сначала направляет stdout в файл, затем ставит stderr туда же, куда сейчас смотрит stdout. Обратный порядок `2>&1 >file` ведёт себя иначе: stderr успевает привязаться к старому stdout (часто TTY), а потом stdout уходит в файл. Эту ловушку проходят почти все.

`&>file` в bash — краткая форма «оба потока в файл», но переносимость между оболочками разная. В скриптах иногда безопаснее писать явно `>file 2>&1`.

Перенаправление не отменяет код возврата. Команда может записать ошибку в файл stderr и всё равно вернуть ненуль. Или наоборот — успех с пустым файлом.

Осторожно с одним и тем же файлом как источником и приёмником в одной команде без буфера: `sort file > file` может уничтожить данные, потому что оболочка обрезает файл до запуска. Используйте временный файл или `sponge`-подобные подходы.

В конвейере перенаправления относятся к отдельным стадиям. Можно направить stderr только левой команды, оставив данные течь по pipe.

## Термины

**`>`** — перенаправление stdout с обрезанием файла.

**`>>`** — дозапись stdout в конец файла.

**`<`** — подача файла на stdin.

**`2>`** — перенаправление stderr.

**`2>&1`** — направить stderr туда же, куда сейчас указывает stdout.

## Как это работает

Shell открывает файл (open/creat), затем через dup2 связывает нужный дескриптор с полученным fd. Только после настройки дескрипторов выполняется программа. Поэтому сама утилита остаётся простой: она пишет в 1 и 2.

Права на файл проверяются в момент open. Нет права записи — перенаправление падает ещё до полезной работы команды, и вы увидите ошибку shell.

Номера больше 2 тоже существуют: программы могут открывать другие дескрипторы. В повседневной работе хватает 0/1/2, но синтаксис shell умеет и `3>`.

## Пример

```bash
echo hello > /tmp/out.txt
echo again >> /tmp/out.txt

cat < /tmp/out.txt

ls /tmp /нет  > /tmp/ls_out.txt 2> /tmp/ls_err.txt

ls /tmp /нет  > /tmp/both.txt 2>&1

# опасный шаблон (не повторять на важных данных):
# sort file > file
```

## Разбор

Первые две команды создают и дописывают файл через stdout.

`cat < file` показывает чтение stdin из файла — эквивалент по смыслу многим утилитам с именем файла аргументом, но механизм другой: данные идут через fd 0.

Раздельные `>` и `2>` дают два файла. Форма `>file 2>&1` собирает всё в один.

## Ошибки

- Путать порядок `>file 2>&1` и `2>&1 >file`.
- Затирать файл чтением и записью в него же одной командой.
- Думать, что `>` «глотает» и код возврата.
- Забывать про права на каталог для создания файла.

## Что запомнить

- Перенаправление настраивает дескрипторы shell до exec.
- `>` обрезает, `>>` дописывает, `2>` отдельно для ошибок.
- Порядок объединения потоков критичен.
- Не направляйте вывод команды в тот же файл, который она читает, без буфера.

## Практика

Запустите команду с успешным и ошибочным путями. Сохраните stdout и stderr раздельно, затем одним файлом через `2>&1`. Сравните содержимое.

Ротация логов вручную через `>>` без limit опасна. Для долгоживущих служб используйте journald или logrotate.

Here-doc `<<'EOF'` защищает от подстановки. `<<EOF` раскрывает переменные — выбирайте сознательно.

`/dev/null` — дыра для ненужного вывода. `2>/dev/null` маскирует ошибки; в скриптах делайте это только точечно.

Дескрипторы можно копировать: `exec 3>&1` сохраняет stdout, затем восстанавливает. Полезно в сложных обёртках, но документируйте.
