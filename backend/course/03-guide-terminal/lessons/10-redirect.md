# Перенаправление потоков в файлы

Pipe связывал два процесса. Здесь другой конец — **файл**. `>`, `>>`, `<`, `2>` — это не «опции команды». Shell **до** exec открывает файл и через `dup2` ставит его на дескриптор 0, 1 или 2. Программа потом честно пишет в fd 1 и не обязана знать, что это диск, а не TTY.

`>` создаёт или **обрезает**. `>>` дописывает. `<` кормит stdin. `2>` отдельно для ошибок. Права проверяются в момент open: нет записи в каталог — падает shell, утилита может даже не стартовать.

Порядок слияния ломает всех один раз. `>file 2>&1` сначала stdout в файл, потом stderr туда же, куда сейчас смотрит stdout — оба в файле. `2>&1 >file` сначала stderr к **старому** stdout (часто экран), потом stdout в файл — ошибки остаются на TTY. В bash `&>file` короче, в переносимых скриптах лучше явное `>file 2>&1`.

Перенаправление не глотает код возврата: ошибка в файле stderr и ненуль совместимы. В конвейере `>` относится к **своей** стадии: можно спрятать stderr слева, а данные гнать по `|`.

Опасно: `sort file > file`. Shell обрежет `file` **до** запуска `sort`, на вход придёт пустота. Временный файл, потом атомарный `mv`.

```bash
echo hello > /tmp/out.txt
echo again >> /tmp/out.txt
cat < /tmp/out.txt
ls /tmp /нет  > /tmp/ls_out.txt 2> /tmp/ls_err.txt
ls /tmp /нет  > /tmp/both.txt 2>&1
```

`2>/dev/null` уместен, когда шум известен и безвреден. Если скрипт «молчит и не работает», вы только что выкинули единственную подсказку.

Номера больше 2 существуют (`3>`), в быту хватает 0/1/2.
