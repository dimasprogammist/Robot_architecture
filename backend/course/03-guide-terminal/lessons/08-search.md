# Поиск: find и grep

В графическом интерфейсе «найти файл» и «найти слово в файле» часто одна кнопка. В командной строке это **две задачи** и два инструмента.

**Где лежит файл** — обход дерева: имя, тип, глубина, возраст. Команда `find` в момент запуска проходит каталоги. Это не служба в фоне.

**Что внутри** — построчный проход по содержимому. `grep` печатает строки, совпавшие с образцом.

```text
имя *.log в проекте     → find
слово error в одном логе → grep
все логи, где есть error → find … | xargs grep  (или grep -r)
```

Связка сильная: сначала сузить места, потом читать. Искать текст той же командой, что ищет имена — путать вопросы.

```bash
find /tmp -maxdepth 1 -type f
find . -name "*.log"
grep -n "error" /tmp/example.log
find . -name "*.log" | xargs grep -l "error"
```

`-maxdepth` спасает от сюрприза «весь диск». `-n` у grep даёт номера строк. `-l` — только имена файлов, не все совпадения.

Регулярные выражения — следующий уровень того же grep: не буква «error», а класс строк. Для повседневности хватает буквального текста. Бинарник grep часто предупреждает «binary file matches»; это не «нашли осмысленную строку».

Исключайте `.git`: иначе ищете по истории объектов, не по своему коду. Поиск «с корня `/` без фильтра» на учебной машине — способ забить вывод и диск кэшем.

Имя файла врёт: `log.txt` внутри JSON. Для отчёта «где ошибка в данных» смотрят содержимое, не расширение.

Конвейер как механизм — следующий урок; здесь достаточно: вывод одной команды становится аргументами или stdin другой.
