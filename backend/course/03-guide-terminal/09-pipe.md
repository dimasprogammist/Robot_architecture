# Конвейер (pipe) — связать вывод с вводом

## Цель

Понять механизм pipe: буфер в ядре, подключение дескрипторов и параллельная работа двух процессов. Научиться строить короткие цепочки фильтров без временных файлов.

## Исходные знания

stdin/stdout/stderr и идея фильтров. Умение запускать простые команды.

## Объяснение

Конвейер — способ соединить stdout одной программы со stdin другой без файла на диске. В shell это символ `|`. Слева производитель данных, справа потребитель. Ядро создаёт pipe — буфер с двумя концами: запись и чтение.

Обе стороны работают одновременно. Если потребитель медленный, буфер заполняется и писатель блокируется на write. Если писатель закончил и закрыл конец, читатель получает EOF. Это не «сначала вся команда слева, потом справа», а поток через буфер.

stderr по умолчанию не входит в pipe. Ошибки левой команды часто остаются на терминале, а данные текут дальше. Это удобно: диагностика видна, а следующий этап не засоряется.

Сила UNIX-модели: маленькие программы делают одну вещь. `grep` отбирает строки, `sort` упорядочивает, `uniq` сжимает повторы, `wc` считает. Конвейер собирает конвейерную обработку текста.

Не любой вывод годится для pipe. Таблицы с цветами и управляющими кодами плохо парсятся. Для автоматизации берите машиночитаемый режим или утилиты, которые изначально думают строками.

Длинные конвейеры сложно отлаживать. Иногда лучше сохранить промежуточный результат в файл или использовать `tee`, чтобы одновременно видеть поток и писать копию.

Код возврата конвейера в bash по умолчанию — код последней команды. Есть режим `pipefail`, чтобы ошибка любой стадии считалась ошибкой всего конвейера. Для скриптов это важно.

## Термины

**Pipe** — канал ядра с двумя концами для передачи байтов между процессами.

**Фильтр** — программа, читающая stdin и пишущая stdout.

**EOF** — конец потока; читатель узнаёт, что писать больше нечего.

**tee** — утилита, копирующая stdin одновременно в файл и в stdout.

**pipefail** — режим shell, учитывающий ошибки промежуточных стадий.

## Как это работает

Shell создаёт pipe, запускает левую команду с stdout на write-конец, правую — с stdin на read-конец. Обычно stderr обеих остаётся на TTY. Затем shell ждёт завершения (детали зависят от shell и job control).

Обратное давление (backpressure) естественное: заполненный буфер тормозит производителя. Так медленный потребитель не требует бесконечной памяти на стороне канала.

Несколько `|` подряд создают цепочку процессов. Каждый сегмент — отдельный процесс со своими дескрипторами.

## Пример

```bash
printf 'c\na\nb\na\n' | sort | uniq -c

ls /tmp /нет_такого 2>/dev/null | wc -l

printf 'one\ntwo\n' | tee /tmp/copy.txt | wc -l

set -o pipefail
false | true
echo $?
```

## Разбор

Первый конвейер сортирует строки и считает уникальные. Данные нигде не лежат на диске как обязательный шаг.

Во втором ошибки `ls` отброшены, в `wc` попадают только успешно перечисленные имена (если они были в stdout).

`tee` показывает поток и сохраняет копию — удобно при отладке.

`pipefail` делает ненулевой статус, если `false` упал в середине, даже когда справа `true`.

## Ошибки

- Парсить цветной интерактивный вывод в следующем этапе.
- Забывать, что stderr не в pipe по умолчанию.
- Игнорировать коды возврата промежуточных команд без `pipefail`.
- Строить конвейер из двадцати стадий без возможности посмотреть середину.

## Что запомнить

- Pipe — буфер ядра между stdout и stdin двух процессов.
- Процессы работают параллельно с обратно давлением буфера.
- stderr обычно остаётся на терминале.
- Для скриптов включайте учёт ошибок стадий.

## Практика

Постройте конвейер из трёх стадий над текстовым файлом: отбор строк, сортировка, подсчёт. Затем вставьте `tee` посередине и сравните промежуточный файл с финальным результатом.

Длинный конвейер отлаживайте разрезанием: сохраните промежуток через `tee /tmp/step1`. Убедитесь, что формат данных на границе стабилен.

`xargs` и `parallel` — следующие ступени после pipe, но у них свои правила кавычек и `-0` для нуль-разделённых имён.

Буферизация скрывает первые строки ошибки. `stdbuf -oL` иногда помогает в live-диагностике.

В PowerShell конвейер объектов другой: не ждите, что внешний `grep` получит те же объекты без преобразования в текст.
