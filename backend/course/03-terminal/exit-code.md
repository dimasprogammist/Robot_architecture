# Код возврата и успех команды

## Цель

Научиться читать и использовать код завершения процесса. Понять соглашение «ноль — успех» и как shell применяет коды в условиях и скриптах.

## Исходные знания

Запуск команд, конвейеры и переменные. Понимание, что процесс когда-то завершается.

## Объяснение

Когда процесс заканчивается, он возвращает ядру небольшой целочисленный статус. Оболочка делает его доступным (в bash — `$?`). По соглашению POSIX ноль означает успех, ненулевое значение — неуспех или класс ошибки. Это канал управления для скриптов: не только текст на экране, но и машинно-проверяемый итог.

Разные программы кодируют ошибки по-своему. `grep` часто возвращает 1, если совпадений нет, и 2 при настоящей ошибке. Для скрипта «нет совпадений» может быть нормой или аварией — решать вам, но код нужно интерпретировать по документации утилиты.

Shell использует коды в конструкциях `&&` и `||`. `cmd1 && cmd2` запускает вторую команду только если первая вернула ноль. `cmd1 || cmd2` — если первая неуспешна. Это короткий способ писать простые ветвления без полного `if`.

В условиях `if cmd; then` проверяется код возврата `cmd`, а не её текстовый вывод. Чтобы проверить строку, вызывают утилиты сравнения или встроенные тесты, которые сами возвращают код.

Сигналы меняют картину: процесс, убитый сигналом, часто даёт статус, отражающий сигнал (в bash типично 128+номер). Поэтому «ошибка 130» после Ctrl+C — ожидаемый след SIGINT, а не загадочная поломка программы.

В конвейере без `pipefail` статус обычно берётся от последней стадии. Промежуточная ошибка может потеряться. Для надёжных скриптов включают строгий режим.

Явный `exit N` в скрипте завершает shell с кодом N. Функции и подстановки вывода имеют свои нюансы статуса; отлаживайте простыми прогонами с `echo $?`.

## Термины

**Код возврата (exit status)** — целое 0–255 в типичных shell-практиках, итог процесса.

**Успех** — по соглашению статус 0.

**`&&` / `||`** — условный запуск следующей команды по статусу предыдущей.

**`set -e`** — режим выхода shell при ненулевом статусе простой команды (с оговорками).

**Сигнал** — асинхронное уведомление процессу; может завершить его со специальным статусом.

## Как это работает

Процесс вызывает `_exit`/`exit` с кодом или завершается от сигнала. Родитель через wait получает статус. Shell сохраняет его в `$?` до следующей команды переднего плана.

Скрипты в CI опираются на ненулевой код как на красный билд. Поэтому «проглотить» ошибку бездумным `cmd || true` можно, но только осознанно.

Проверяйте статус сразу: любая следующая команда, даже `echo`, перезапишет `$?`.

## Пример

```bash
true; echo $?
false; echo $?

ls /tmp >/dev/null && echo ok
ls /нет_такого >/dev/null 2>&1 || echo failed

grep -q '^root:' /etc/passwd
echo $?

# после прерывания sleep Ctrl+C часто бывает 130
```

## Разбор

`true` и `false` существуют почти только ради статусов 0 и 1.

`&&` и `||` показывают ветвление по коду без разбора текста.

`grep -q` молчит по выводу, но сообщает кодом, нашлось ли совпадение.

Статус после сигнала помогает отличить «пользователь прервал» от «программа упала сама».

## Ошибки

- Смотреть только текст ошибки и игнорировать код в автоматизации.
- Проверять `$?` слишком поздно, после лишнего `echo`.
- Считать любой ненуль одинаковым без чтения man.
- Отключать ошибки через `|| true` везде подряд.

## Что запомнить

- Ноль — успех; ненуль — сигнал проверить причину.
- Shell ветвится по коду, не по «красивости» вывода.
- Конвейеры требуют внимания к статусу стадий.
- Сигналы оставляют характерные коды.

## Задание

Напишите две команды с `&&` и `||`, где вторая печатает разный текст при успехе и неуспехе первой. Затем включите `set -o pipefail` и сравните статус `false | true` с режимом без pipefail.

## Дополнение: практика и нюансы

В bash функции возвращают статус через `return`, скрипты — через `exit`. Код больше 255 обрезается по модулю — не кодируйте длинные enum'ы в exit code.

`set -e` не всегда прерывает в условиях `if`/`while` — прочитайте правила bash. Для явной проверки пишите `cmd || exit 1`.

CI-системы красят сборку по статусу процесса. Сделайте статус честным: «предупреждение» не должно маскироваться нулём, если политика требует строгостью.

Документируйте ненулевые коды своей утилиты в `--help`, хотя бы основные классы.
