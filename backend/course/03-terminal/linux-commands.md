# Базовые команды Linux через shell и ядро

## Цель

Связать привычные утилиты (`ls`, `cat`, `cp`, `mv`, `rm`, `find`, `grep`, `ps`) с тем, что реально делает shell и ядро. Не выучить список флагов, а понять механизм каждого класса задач.

## Исходные знания

Shell, пути, argv, потоки, pipe, коды возврата. Готовность читать `man` или `--help`.

## Объяснение

Команды Linux — чаще отдельные программы в `/bin`, `/usr/bin` и соседних каталогах. Shell находит их по PATH и запускает. Сами они вызывают системные вызовы: читать каталог, читать файл, создать inode, послать сигнал.

`ls` просит ядро перечислить записи каталога и печатает имена. Метаданные (права, размер, время) берутся из inode через stat. Флаги меняют формат вывода, а не «магически ускоряют диск».

`cat` читает файлы и пишет на stdout. Для больших данных иногда лучше `less` как pager, но механизм тот же: read/write. `cp` копирует байты и метаданные по правилам опций; это не мгновенный «переезд» без работы, если только не используется другая ФС-оптимизация.

`mv` в пределах одной файловой системы часто делает rename — дёшево меняет имя в каталоге. Между разными устройствами — фактически copy+delete. Поэтому `mv` иногда внезапно долгий.

`rm` удаляет имя из каталога и уменьшает счётчик ссылок; блоки освобождаются, когда счётчик обнуляется и никто не держит файл открытым. Отсюда эффект «место не освободилось, пока жив процесс с открытым дескриптором».

`find` обходит дерево и для каждого пути проверяет предикаты. Это пространство пользовательских процессов, не отдельный демон. `grep` ищет образец в потоке байтов/строк. Вместе в pipe они покрывают поиск «где» и «что внутри».

`ps` и `top` читают информацию о процессах, которую ядро экспонирует (часто через `/proc`). Они не «создают» процессы — только показывают. Управление — через сигналы (`kill`), приоритеты и политики планировщика.

Каждая утилита имеет свою историю флагов (BSD vs GNU). На Linux обычно GNU coreutils. Не переносите слепо флаги с macOS без проверки.

## Термины

**coreutils** — набор базовых утилит GNU (ls, cp, mv, …).

**inode** — структура метаданных файла в файловой системе.

**rename** — системный вызов смены имени/места в пределах ФС.

**`/proc`** — виртуальная ФС с информацией о процессах и ядре.

**Pager** — программа постраничного просмотра (`less`).

## Как это работает

Минимальный цикл: shell → exec утилиты → системные вызовы → результат в stdout/stderr → статус. Понимание цикла позволяет предсказывать эффекты: почему `rm` открытого файла странный, почему `mv` на другой диск долгий, почему `grep` по бинарнику ругается.

Права проверяются ядром на каждом open/read/write/unlink. Утилита может только сообщить EACCES текстом на stderr и ненулевым кодом.

Для скриптов выбирайте предсказуемые флаги и стабильный вывод. Интерактивные удобства (`ls` с цветом) оставляйте человеку.

## Пример

```bash
ls -la /tmp | head
cp /etc/hosts /tmp/hosts.copy
mv /tmp/hosts.copy /tmp/hosts.moved
grep -n localhost /tmp/hosts.moved
find /tmp -maxdepth 1 -type f | head
ps -o pid,cmd --sort=pid | head
rm /tmp/hosts.moved
```

## Разбор

`ls` читает каталог; pipe в `head` ограничивает вывод без изменения самого `/tmp`.

`cp` создаёт новый файл с содержимым. `mv` в `/tmp` обычно делает rename.

`grep` фильтрует строки. `find` отбирает пути по типу. `ps` показывает процессы через интерфейс ядра.

`rm` убирает имя. Если бы файл держали открытым, блоки могли бы жить дольше.

## Ошибки

- Учить только флаги без модели «утилита = процесс + syscall».
- Делать `rm -rf` без проверки пути.
- Считать `mv` всегда мгновенным между дисками.
- Парсить `ps`/`ls` как стабильный API без специальных форматов.

## Что запомнить

- Базовые команды — программы, говорящие с ядром.
- `mv` дёшев внутри одной ФС и дорог между устройствами.
- Удаление имени ≠ мгновенная очистка блоков при открытых fd.
- `/proc` питает мониторинг процессов.

## Задание

Скопируйте небольшой файл в `/tmp`, найдите его через `find`, отфильтруйте строку через `grep`, затем удалите. На каждом шаге смотрите код возврата. Кратко опишите, какой системный смысл у каждого шага.

## Дополнение: практика и нюансы

`stat` показывает inode, права, времена — точнее догадок по `ls -l`.

`df` и `du` отвечают на разные вопросы о месте. Для «кто съел диск» начинайте с `du -x` на подозрительных точках монтирования.

`install -D` создаёт путь и копирует с режимом — удобно в обёртках установки.

`timeout` ограничивает время команды — полезно в healthcheck, чтобы не зависнуть навсегда.
