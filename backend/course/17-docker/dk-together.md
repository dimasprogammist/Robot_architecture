# Как контейнеры работают вместе

## Цель

Собрать целостную картину: образы как шаблоны, контейнеры как процессы в namespaces, тома для данных, bridge-сеть и DNS имён compose, путь запроса от браузера до строк в БД.

## Что уже нужно понимать

- Уроки модуля: образ, контейнер, Dockerfile, слои, тома, сети, env, compose, backend, frontend, БД.
- HTTP, TCP, клиент-сервер на уровне курсов сетей и backend.

## Объяснение

Учебный стек из трёх контейнеров — модель многих реальных приложений.

**web** — nginx со статикой. Процесс слушает `:80` в своём netns. Published `8080:80` даёт вход человеку.

**api** — приложение на `0.0.0.0:8000`. Может не публиковать порт, если снаружи ходят только через nginx. Для отладки часто публикуют.

**db** — Postgres с томом на data directory. Порт 5432 внутри сети; с хоста — по желанию.

Все три в одной user-defined сети compose. DNS:

- nginx резолвит `api` для `proxy_pass`;
- api резолвит `db` для драйвера БД;
- браузер резолвит только `localhost` (или домен сервера) — не имена compose.

Путь запроса «список пользователей»:

1. Браузер → `GET http://localhost:8080/api/users`.
2. Ядро хоста / Docker proxy → контейнер web:80.
3. Nginx проксирует на `http://api:8000/users`.
4. Api выполняет SQL по TCP на `db:5432`.
5. Postgres читает/пишет файлы на томе `pgdata`.
6. Ответ JSON идёт обратно по цепочке до браузера.

Если убрать том у db и сделать recreate — на шаге 5 данные «обнулятся», хотя образы тех же тегов. Если перепутать URL api на `localhost:5432` внутри контейнера api — на шаге 4 connection refused: localhost api ≠ db.

Изоляция namespaces:

- У каждого контейнера своё дерево процессов: падение воркера api не убивает postgres автоматически (но может оборвать соединения).
- Своя ФС из слоёв образа + writable + mounts.
- Свой netns: порт 8000 api не конфликтует с портом 8000 другого проекта в другой сети/контейнере, пока publish на хосте не столкнётся.

Образы остаются шаблонами: пересобрали api с новым кодом — подняли новый контейнер api, том db не трогали, web можно не пересобирать, если контракт API совместим.

Env связывает конфиг: пароль из `.env` попадает и в Postgres init (на пустом томе), и в `DATABASE_URL` api. Секрет один логически, два потребителя.

Слои и кэш ускоряют цикл: правка Python-файла не гоняет заново `pip install`, если Dockerfile написан правильно.

Типичный день:

1. `compose up -d`
2. Правки api с bind или rebuild
3. Миграции `compose run api ...`
4. Логи `compose logs -f`
5. `compose down` вечером — том хранит БД до следующего дня

Масштабирование мысли: тот же паттерн (сеть + DNS + том + env) лежит в основе更 сложных оркестраторов. Изучив compose-стек, вы узнаёте роли компонентов, а не только синтаксис YAML.

Границы ответственности:

| Компонент | Отвечает за |
|-----------|-------------|
| Образ | Код и зависимости |
| Контейнер | Запущенный процесс |
| Том | Долгоживущие данные |
| Сеть/DNS | Связность |
| Env | Конфиг стенда |
| Publish | Вход с хоста/мира |

Путаница любых двух колонок — источник большинства «Docker не работает».

## Термины

| Термин | Смысл |
|--------|--------|
| Stack | Набор связанных сервисов |
| Upstream | Куда проксирует nginx (api) |
| Data path | Путь данных на томе СУБД |
| Control plane | Compose/Engine, управляющие жизненным циклом |
| Data plane | Трафик запросов и ответы |

## Как это устроено

На хосте Docker Engine держит:

- объекты сетей и их bridge;
- тома на диске;
- контейнеры с привязкой к образам и mounts;
- правила publish портов.

Compose задаёт желаемое состояние «три сервиса up». Фактические процессы — PID на хосте (или в Linux-ВМ Desktop), каждый в своих namespaces. Union FS показывает процессу его корневой каталог. Запись БД уходит в mount тома, минуя эфемерный слой как место хранения истины.

Отладка стека целиком:

- web не открывается → publish / nginx / сборка статики;
- UI есть, API 502 → dns имя api, процесс api, upstream;
- API 500 на запросах к данным → DATABASE_URL, том, логи db, миграции;
- данные пропали → искали ли `-v`, был ли volume.

## Пример

```yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      timeout: 3s
      retries: 10

  api:
    build: ./backend
    environment:
      DATABASE_URL: postgresql://app:${POSTGRES_PASSWORD}@db:5432/app
    depends_on:
      db:
        condition: service_healthy

  web:
    build: ./frontend
    ports:
      - "8080:80"
    depends_on:
      - api

volumes:
  pgdata:
```

Сквозной smoke:

```bash
docker compose up -d --build
curl -s http://localhost:8080/api/health
docker compose exec db pg_isready -U app
docker compose down    # том остаётся
```

## Разбор

- Браузер касается только `web` через 8080.
- `api` без ports всё равно доступен nginx по имени.
- `db` хранит истину на `pgdata`; образ postgres только бинарники и init-логика.
- Healthcheck db снижает гонки старта.
- Один `.env` питает паролем и db, и URL api.

Сломайте мысленно каждый узел и сопоставьте симптом — это главный навык модуля.

## Практическое применение

- Шаблон любого учебного full-stack проекта.
- Демо заказчику на одном ноутбуке.
- База для перехода к staging с теми же ролями сервисов.
- Чеклист ревью Dockerfile/compose новичка в команде.

## Типичные ошибки

- Лечить симптомы переустановкой Docker вместо проверки URL, тома и портов.
- Мешать роли: класть данные в образ, секреты в git, DNS имена в фронтовый бандл.
- Публиковать всё наружу «чтобы заработало».
- Считать контейнер ВМ и настраивать его руками без фиксации в образе.
- Забыть, что три процесса = три точки отказа, логи смотреть у каждого.

## Что запомнить

- Образ — шаблон ФС; контейнер — процесс в namespaces.
- Том переживает контейнер; без тома БД теряет данные.
- Compose-сеть даёт DNS имён сервисов; браузер их не видит.
- Nginx связывает мир браузера с миром Docker DNS.
- Разделяйте код (образ), данные (том), конфиг (env), связность (сеть).

## Задание

Поднимите полный стек web+api+db. Нарисуйте (текстом) путь одного запроса по шагам с указанием портов и имён хостов на каждом hop. Проведите три эксперимента: (1) down без -v, (2) down -v, (3) неверный DATABASE_URL с localhost. Для каждого запишите наблюдаемый эффект. Кратко сформулируйте «правила стека» своими словами в 5–7 пунктах.
