# TCP — надёжный поток байтов

IP может потерять пакет, привезти дважды, переставить порядок. Браузеру и SSH нужна другая модель: упорядоченный поток байтов между двумя процессами, как труба. Эту трубу даёт **TCP**. Приложение пишет в сокет и читает из сокета; нарезку на сегменты, повторы и подтверждения делает стек ОС.

Сначала стороны **договариваются о соединении**. Классический ход:

```text
клиент                         сервер
 SYN      -------------------->
          <--------------------  SYN+ACK
 ACK      -------------------->
          … байты в обе стороны …
 FIN/ACK  закрытие (или RST — сброс)
```

Пока handshake не закончился, полезной нагрузки приложения ещё нет. Фильтры и «порт закрыт» часто рвут именно здесь: RST или таймаут. Это не HTTP 500: до приложения дело не дошло.

В сегменте — порты, номера последовательности и подтверждения (считают **байты**, не «пакеты»), флаги SYN/ACK/FIN/RST, окно («сколько ещё можно прислать, пока нет новых ack»), контрольная сумма, затем данные. Порты отличают процессы на одном IP. Четвёрка src IP, src port, dst IP, dst port — идентификатор соединения.

Потеряли сегмент — перешлют по таймеру или по «дырке» в ack. Окно и механизмы перегрузки притормозят, если сеть забита. Надёжность не абсолютна: если труба не собирается, верхний слой получает ошибку. TCP сам по себе не шифрует; TLS садится поверх.

```bash
ss -ltn
```

Список слушателей: кто на хосте ждёт входящие TCP. Попытка открыть закрытый порт — отказ API, часто из‑за RST.

Путаница: страница «500» значит, TCP до сервера доехал, ответило приложение. «Connection refused / timed out» — ещё транспорт или путь. Повторы в `ss` — потери на сети, не обязательно «медленный Python».

MTU-чёрная дыра: мелкий ping проходит, большой сегмент зависает. Handshake прошёл, а данные — нет. Таймаут приложения должен переживать RTT плюс handshake, иначе ложные обрывы.
