# Сокеты — API обмена

Порты и TCP уже есть. Программе нужен свой вход в стек ОС. **Сокет** — как раз эта ручка: файловый дескриптор, через который вызывают connect, send, recv, close. Ядро уже знает маршруты и сегменты; приложение знает «байт сюда / байт оттуда».

Для TCP сервер и клиент ходят разными лестницами.

```text
сервер:  socket → bind → listen → accept → recv/send → close соединения
клиент:  socket → connect → send/recv → close
```

`accept` отдаёт **новый** сокет на конкретного клиента. Слушающий остаётся ждать следующих. Смешать их — начать писать ответ «всем сразу» в listen-сокет.

UDP обычно без accept: `bind` и `recvfrom`/`sendto`. Нет трубы — есть датаграммы, как в прошлом уроке.

Домен адреса: IPv4, IPv6, Unix-сокет (путь в файловой системе, только эта машина). Тип: поток (`SOCK_STREAM`, TCP) или датаграмма (`SOCK_DGRAM`, UDP). Слушать только IPv4, когда клиент приходит с `::1`, — классическая «у меня не коннектится».

```python
import socket

s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.settimeout(2)
try:
    s.connect(("127.0.0.1", 22))
    print("connected", s.getpeername())
except OSError as e:
    print("connect failed:", e)
finally:
    s.close()
```

Если sshd нет, увидите отказ — это полезнее, чем вечный успех в учебнике.

`send` положил байты в буфер ядра. Это ещё не «пир прочитал». По TCP поток без границ сообщений: один `recv` может вернуть ползапроса или два склеенных. **Framing** (длина, разделитель, своя разметка) — обязанность прикладного протокола. UDP даёт границы датаграммы сам; TCP — нет.

Блокирующий сокет останавливает поток, пока сеть не ответит. Серверу с тысячей клиентов нужны неблокирующий режим и мультиплексирование — это следующий уровень, не этот урок. Обязательный `close`: иначе текут дескрипторы, а на TCP ещё и TIME_WAIT забивает порт при яростных тестах «открыл-закрыл тысячу раз».

HTTP-клиент прячет сокеты. Ошибка «connection refused» всё равно отсюда.
