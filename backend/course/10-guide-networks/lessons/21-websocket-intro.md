# WebSocket — вводный контраст с HTTP

HTTP силён в «спросил — ответил»: страница, CRUD, кэш. Для котировок, телеметрии робота, совместного курсора цикл «клиент всё время опрашивает» дорог и запаздывает. Long polling — тот же запрос-ответ, только задержанный.

**WebSocket** после короткого HTTP-рукопожатия становится двунаправленным каналом: обе стороны шлют кадры, когда есть что сказать. Обычно поверх TLS: `wss://`.

Handshake всё ещё выглядит как HTTP:

```http
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: ...
Sec-WebSocket-Version: 13
```

Сервер, если согласен:

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: ...
```

Дальше парсер HTTP сменяется кадрами: текст, бинарь, ping/pong, close. `curl -I` канал до конца не прощёлкает — нужен WS-клиент. Прокси и балансировщик обязаны понимать Upgrade и держать долгое соединение; обычный «короткий HTTP-таймаут» убьёт чат.

Это не замена REST. Список заказов и CDN по-прежнему HTTP. Канал — когда события идут сами. Поверх кадров всё равно свой прикладной протокол: JSON, авторизация, что делать при обрыве. Сеть порвётся — TCP умрёт — клиент должен **reconnect**, «один curl» этого не закрывает.

Масштаб сложнее stateless GET: соединение живёт на конкретном инстансе или его тащат через pub/sub. Липкая сессия на балансировщике — частый костыль.

Безопасность: `wss://`, проверка Origin, аутентификация до или сразу после upgrade, лимит размера кадра. Открытый `ws://` без проверок в публичной сети — приглашение.
