# Модель клиент–сервер

Сокет умеет и ждать, и стучаться. **Клиент–сервер** фиксирует роли: сервер предоставляет услугу и обычно **слушает**, клиент **инициирует**. Браузер — клиент HTTP. `sshd` — сервер. Ваше FastAPI-приложение — сервер для фронта и клиент для СУБД. В цепочке микросервисов одна программа бывает обеими ролями сразу — важно не путать, в каком разговоре.

Серверу нужна достижимость: имя или адрес, открытый порт, процесс в listen. Клиент может сидеть за NAT с плавающим адресом; стучаться «с интернета на телефон» без дырки или своего сервера посередине трудно. Поэтому входящие к домашнему клиенту — отдельная головная боль, а не «просто поменять роли».

```text
[Клиент] --запрос--> [Сервер] --ответ--> [Клиент]

для клиента один сервис, внутри уже двое:
[Клиент] --> [балансировщик] --> [S1]
                            \--> [S2]
```

Состояние. По-хорошему обработчик не помнит прошлый запрос в своей оперативке — тогда второй инстанс за балансировщиком обслужит повтор. Сессию кладут в БД или кэш. SSH и игра — наоборот, **stateful**: труба живёт минутами. Смешать «положил логин в память процесса» с тремя репликами — получите «на одном сервере залогинен, на другом нет».

Повторы. Сеть моргнула — клиент шлёт ещё раз. Для чтения это безопасно. Для «списать деньги» без ключа идемпотентности — два списания. Таймауты и ретраи проектируют **явно**, чаще на клиенте.

Peer-to-peer размывает роли, но и там часто есть сигнальный сервер. Для учётных систем клиент–сервер остаётся базой.

Безопасность асимметрична: сервер — большая мишень, клиент проверяет его (TLS). Клиента тоже надо узнать: пароль, токен, ключ. Канал без этого только прячет байты от зеваки в кафе, не от чужого логина.

Обрыв посередине оставляет хвосты: ползаписи в БД, полуоткрытый файл. Протокол и транзакция должны это переживать.

## Практика

### Задание 1. Цепочка ролей

Приложение → API → PostgreSQL. Кто чей клиент? Если API слушает только `127.0.0.1`, какой клиент ещё дойдёт, какой — нет?

### Задание 2. Память инстанса

Два инстанса за балансировщиком, сессия только в RAM первого. Что увидит клиент после второго запроса, если LB отправит его на второй инстанс?

### Задание 3. Повтор POST

Клиент не дождался ответа на «создать заказ» и повторил. При каких условиях заказ станет двумя? Что должно быть в контракте, чтобы не стало?

### Задание 4. NAT

Почему домашний ПК плохой «сервер для друга из интернета», даже если программа listen на 8080? Где теряется входящий SYN?

Дальше прикладной протокол, который вы видите каждый день: HTTP.
