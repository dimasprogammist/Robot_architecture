# ARP — IPv4-адрес в MAC

Чтобы отдать IP-пакет соседу по Ethernet, нужен кадр, а в кадре — **MAC**. Знать `192.168.1.1` недостаточно. **ARP** как раз спрашивает в локальном сегменте: «у кого этот IPv4?» и запоминает ответ. Для IPv6 та же работа у Neighbor Discovery, ARP туда не ходит.

Это не поиск сервера за океаном. MAC конечного сайта вы ARP-ом не узнаете: on-link только шлюз (или сосед в LAN). Внешнему IP сначала резолвят MAC шлюза — тем же ARP.

```text
кто хочет 192.168.1.1, кэш пуст
→ broadcast: who-has 192.168.1.1? tell 192.168.1.10
→ unicast reply: 192.168.1.1 is-at aa:bb:cc:dd:ee:ff
→ кадр с этим MAC, внутри IP-пакет
```

Сообщение ARP сидит на канале рядом с IPv4, другой EtherType. В запросе MAC цели часто нули — «ещё не знаю». Кэш (`ip neigh`) хранит REACHABLE, STALE, FAILED.

```bash
ip neigh
ping -c 1 192.168.1.1
ip neigh
```

После ping запись шлюза обычно появляется. FAILED — спрашивали, никто не ответил: кривой IP, хост молчит, изоляция клиента на Wi‑Fi, фильтр.

Коммутатор не «маршрутизирует ARP»: он таскает широковещательные кадры по VLAN. За роутером другой сегмент — другой ARP.

Устаревший кэш после замены коробки с тем же IP: кадры улетают на старый MAC. Иногда помогает подождать STALE, иногда сбросить neigh. В чужой LAN ARP можно подделать (spoofing): доверие к ответу — свойство локальной среды, не криптография.

Gratuitous ARP — объявление «это мой IP и MAC» без вопроса; так обновляют соседей после смены адреса.

## Практика

### Задание 1. Кэш

Снимите `ip neigh`, пинганите шлюз, снимите снова. Что изменилось? Если шлюз не в кэше и ping не идёт — это DNS?

### Задание 2. Не океан

Почему ARP-запрос с вашим MAC получателя = MAC `8.8.8.8` бессмыслен? Чей MAC вы должны узнать, чтобы пакет к `8.8.8.8` ушёл?

### Задание 3. FAILED

`ip neigh` показывает FAILED для адреса, который «точно в LAN». Три причины, не связанные с «интернет провайдера лёг».

### Задание 4. IPv6

Какой протокол играет роль ARP для `fe80::`? Почему команда `ip neigh` всё равно полезна на dual-stack хосте?
