# HTTP — запрос и ответ

Нужен общий способ: «дай ресурс по адресу, вот метаданные, вот тело». Браузер и API-клиент говорят на **HTTP**. Это протокол приложения поверх TCP (или TLS). Он не знает про Wi‑Fi и не шифрует сам.

Запрос — текст (в HTTP/1.1) из стартовой строки, заголовков, пустой строки и необязательного тела:

```http
GET /index.html HTTP/1.1
Host: example.com
Accept: text/html

```

Ответ так же: версия, **код статуса**, заголовки, тело:

```http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 13

Hello, world!
```

`Host` в 1.1 обязателен: на одном IP живут разные сайты. Тело отделяет пустая строка. `Content-Type` говорит, как читать байты: HTML, JSON, картинка.

Методы — не «разный синтаксис», а договорённость смысла. GET читает и не должен менять мир: его можно кэшировать и повторять. POST отправляет данные, повтор может создать вторую сущность. PUT/PATCH/DELETE — про обновление и удаление, если API так договорился. Врать методом («удаление через GET») ломает кэши и ботов.

Коды — машина читает число, человек — фразу.

- 2xx — получилось (201 часто «создано»).
- 3xx — смотри в другом месте.
- 4xx — запрос или доступ: 404 нет ресурса, 401/403 авторзация.
- 5xx — сервер или шлюз: 502/504 часто «за мной кто-то не ответил».

Страница с 500 уже приехала по TCP: сеть до приложения дошла. Timeout на connect — ещё не HTTP.

Ход: DNS → TCP (и TLS, если https) → запрос → ответ. HTTP/1.1 умеет несколько запросов на одном TCP (keep-alive). HTTP/2 мультиплексирует иначе — идея «запрос/ответ» та же.

```bash
curl -sI http://example.com
```

`-I` смотрит заголовки и статус, не всю страницу.

Прокси посередине тоже говорят HTTP. Сам протокол на публичной сети открытый: чувствительное — только в HTTPS.
