# REST как стиль API над HTTP

HTTP уже умеет методы, URL, коды. **REST** — стиль, как этим пользоваться: есть **ресурсы** с адресами, действие — глагол HTTP, тело — **представление** (часто JSON), итог — статус. Это не «JSON через POST на `/api`».

Ресурс — сущность мира: `/robots/42`, `/orders`. Не процедура `/doCreateRobot`. Существительное в пути, глагол в методе.

```http
POST /robots HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"name": "scout"}
```

```http
HTTP/1.1 201 Created
Location: /robots/42
Content-Type: application/json

{"id": 42, "name": "scout"}
```

Клиент знает URI новой сущности. Потом:

```http
GET /robots/42 HTTP/1.1
```

повтор безопасен. Если бы создание повесили на GET, кэш и префетч браузера плодили бы роботов.

GET/HEAD по задумке не меняют состояние. PUT и DELETE идемпотентны: второй раз — тот же мир. POST часто «создай» или «запусти» и при повторе может сделать два. Фактический контракт документируйте, идеал REST в проде дырявый.

Коды несут смысл для клиентов и кэшей. Всё отдавать `200` и `{ "error": true }` — спрятать аварию от HTTP-инструментов. 400 — кривой запрос, 404 — нет ресурса, 409 — конфликт, 429 — слишком часто, 5xx — у вас, не у клиента.

Красивые URL без семантики методов — не REST. HATEOAS (вести клиента ссылками в JSON) в полном виде редок; честно сказать «практический REST: ресурсы + JSON + коды» лучше, чем притворяться учебником Филдинга.

Версия в пути `/v1/` или в `Accept` — инженерия совместимости. GET с `ETag` / `Cache-Control` — сильная сторона HTTP, которую RPC «один метод всё» часто выбрасывает.

Посредники верят методам. Соврали, что GET безопасен — получите повтор от бота.
