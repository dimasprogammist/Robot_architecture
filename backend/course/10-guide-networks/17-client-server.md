# Модель клиент–сервер

## Цель

Закрепить роли клиента и сервера: кто слушает, кто инициирует, где хранится состояние и какие бывают альтернативы (peer-to-peer) на уровне идеи.

## Исходные знания

Сокеты, TCP/UDP, порты. Бытовой опыт браузера и API.

## Объяснение

В модели клиент–сервер одна сторона предоставляет услугу и обычно ждёт запросов (сервер), другая инициирует контакт (клиент). Браузер — клиент HTTP, sshd — сервер SSH, СУБД — сервер для приложений.

Сервер должен быть достижим: стабильный адрес/имя, открытый порт, процесс в listen. Клиент может быть эфемерным, за NAT, с меняющимся адресом. Поэтому входящие соединения к клиенту часто затруднены без доп. механизмов.

Состояние: stateless-сервер обрабатывает каждый запрос относительно независимо (удобно масштабировать). Stateful держит сессию (игра, SSH). На практике даже «статeless» API часто опирается на внешнее состояние (БД, кэш).

Масштабирование серверов: несколько инстансов за балансировщиком. Для клиента это всё ещё один логический сервис. Идемпотентность запросов становится важна при повторах.

Peer-to-peer размывает роли: узлы равнее. Но даже там часто есть трекеры/сигнальные серверы. Для большинства бизнес-систем клиент–сервер остаётся базой.

Безопасность асимметрична: сервер — большая поверхность атаки, клиент доверяет (или проверяет) сервер через TLS и сертификаты. Клиента тоже надо аутентифицировать.

Таймауты и ретраи — ответственность клиента чаще, чем сервера. Без политики повторов система хрупка к кратковременным сбоям сети.

## Термины

**Клиент** — инициатор запроса.

**Сервер** — сторона, предоставляющая услугу и слушающая.

**Балансировщик** — распределяет соединения/запросы по инстансам.

**Stateless** — обработка без серверной сессии на инстансе.

**Идемпотентность** — повтор запроса не меняет итог неожиданно.

## Как это работает

Сервер bind/listen. Клиент connect/request. Ответ возвращается по тому же соединению (TCP) или отдельной датаграммой (UDP). Логи пишут обе стороны; корреляционный id помогает склеить следы.

Обрыв посередине оставляет частичное состояние — проектируйте протоколы с этим в уме (повторы, версии, транзакции в БД).

## Пример

```text
[Клиент] --запрос--> [Сервер] --ответ--> [Клиент]

масштабирование:
[Клиент] --> [LB] --> [S1]
                 \--> [S2]
```

```bash
# клиентская проверка наличия сервера
ss -ltn | head
curl -I http://127.0.0.1:80 2>/dev/null | head || echo "нет локального HTTP"
```

## Разбор

Первая схема — канонические роли. Вторая показывает, что «сервер» для клиента может быть кластером.

curl — поведение клиента: инициировал, получил заголовки или ошибку соединения.

## Ошибки

- Делать сервер недоступным из-за bind на localhost в проде.
- Хранить критичное состояние только в памяти одного инстанса без плана.
- Ретраить неидемпотентные POST без защиты.
- Путать роль «кто клиент» в цепочке микросервисов (A клиент B, но сервер для C).

## Что запомнить

- Клиент инициирует, сервер слушает и обслуживает.
- Достижимость и порт — свойства серверной роли.
- Масштаб часто прячут за одним именем сервиса.
- Повторы и таймауты проектируют явно.

## Задание

Для трёх пар (браузер–сайт, приложение–БД, робот–облако) укажите клиента и сервера и кто за NAT скорее всего находится.

## Дополнение: практика и нюансы

Идемпотентные ключи на клиенте спасают при ретраях POST создания ресурсов.

Backpressure: если сервер медленный, клиентские очереди растут — нужен лимит и деградация.

Circuit breaker отключает вызовы к больному зависимому сервису — паттерн устойчивости.

Чётко разделяйте публичный API и admin API по портам/сетям.


Документируйте зависимость от внешнего NTP/DNS/прокси: без них «локальный» сервис тоже может деградировать.

Проверьте, что healthcheck бьёт тот же порт и путь, что и реальный трафик, а не заглушку.
