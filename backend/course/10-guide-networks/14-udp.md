# UDP — датаграммы без соединения

## Цель

Понять, когда нужен UDP, чем он отличается от TCP, какие поля у датаграммы и какие ошибки типичны.

## Исходные знания

IP и TCP на уровне идей. Порты.

## Объяснение

### Проблема

Иногда накладные расходы и семантика TCP мешают: нужен быстрый обмен короткими сообщениями, свой контроль над повторами, мультимедиа с потерей кадров, простой запрос-ответ (DNS).

### Зачем протокол

UDP даёт минимальный транспорт: порты + длина + контрольная сумма + данные. Нет handshake, нет гарантии доставки и порядка. Приложение само решает, что делать с потерями.

### Принцип

Отправитель шлёт датаграмму на IP:порт. Получатель, если слушает, читает сообщение целиком (или ошибку размера). Нет «трубы» со состоянием между ними на транспортном уровне (кроме локальных сокетов ОС).

### Структура сообщения своими словами

Заголовок UDP короткий: порт источника, порт назначения, длина UDP-сообщения, контрольная сумма. Дальше полезные данные. Вместе с IP это пакет в сети. Потеря пакета = потеря датаграммы.

### Ход обмена

Часто один запрос — один ответ (DNS). Иногда поток датаграмм в одну сторону (телеметрия). Иногда поверх UDP строят свои надёжные протоколы (QUIC и др. — уже другой уровень курса). ICMP «port unreachable» может сообщить, что никто не слушает — не всегда доходит.

### Ошибки

Молчаливые потери. Переупорядочивание. Обрезка при MTU/фрагментации. Файрвол, любящий только TCP. Предположение, что «раз send прошёл локально — значит дошло».

## Термины

**Датаграмма** — самодостаточное сообщение UDP.

**Connectionless** — без установления соединения на транспорте.

**Checksum** — проверка целостности заголовка/данных (с псевдозаголовком IP).

**Ненадёжность** — отсутствие гарантий доставки UDP.

**QUIC** — пример современного протокола поверх UDP (обзорно).

## Как это работает

Сокет `SOCK_DGRAM` отправляет и принимает сообщения. Сервер обычно bind на порт. Клиент может получить эфемерный порт автоматически. Масштабирование иное, чем у TCP: нет состояния соединения на транспорте, но приложение может держать своё.

Выбирайте UDP, когда понимаете модель потерь. Иначе TCP проще.

## Пример

```text
клиент UDP          сервер UDP :53
  DNS query  ----->
             <----- DNS response
(нет SYN/ACK)
```

```python
import socket
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.settimeout(1.0)
try:
    s.sendto(b'ping', ('127.0.0.1', 9))
    print(s.recvfrom(100))
except Exception as e:
    print('ожидаемо для закрытого порта/таймаута:', type(e).__name__)
```

## Разбор

DNS — канонический пример короткого UDP-обмена без handshake.

Python-фрагмент показывает sendto/recvfrom и реальность таймаутов. Успешный sendto не равен успешной доставке до приложения на другой стороне.

## Ошибки новичков

- Строить «свой TCP» плохо на UDP без необходимости.
- Использовать UDP и удивляться потерям в Wi‑Fi.
- Путать «нет соединения» с «нет шифрования» (это разные оси).
- Открывать UDP-порты без лимитов и валидации (отражение/амплификация).

## Что запомнить

- UDP минимален и ненадёжен по доставке.
- Заголовок короткий: порты, длина, checksum.
- Нет handshake.
- Приложение само отвечает за семантику надёжности.
