# REST как стиль API над HTTP

## Цель

Понять REST как архитектурный стиль: ресурсы, глаголы HTTP, представления, коды статуса и ограничения, а не «JSON через POST на один URL».

## Исходные знания

HTTP методы и коды. Клиент–сервер. JSON как популярное представление.

## Объяснение

REST (Representational State Transfer) описывает стиль взаимодействия с ресурсами через единообразный интерфейс. В вебе этим интерфейсом обычно служит HTTP: URL идентифицирует ресурс, метод — действие, тело — представление, статус — итог.

Ресурс — сущность предметной области (`/robots/42`, `/orders`). Не путайте с RPC «/doCreateRobot». REST подталкивает думать существительными и представлениями (JSON/XML), а не только процедурами.

Глаголы: GET читает и должен быть безопасным; PUT/DELETE идемпотентны по задумке; POST часто создаёт или запускает действие с менее строгой идемпотентностью. На практике API отклоняются от идеала — документируйте фактический контракт.

Статус-коды несут смысл: 201 создано, 204 нет тела, 400 кривой запрос, 404 нет ресурса, 409 конфликт, 429 слишком много запросов. Возвращать всё как 200 с полем error — антипаттерн для HTTP-клиентов и кэшей.

Гипермедиа (HATEOAS) в полной форме редка; часто делают «практический REST»: ресурсы + JSON + осмысленные коды. Важно честно назвать уровень строгости.

Версионирование: `/v1/` в пути, заголовки Accept или оба подхода. Совместимость важнее моды. Кэширование GET с ETag/Cache-Control — сильная сторона HTTP, которую RPC часто теряет.

REST не равен JSON и не равен «красивым URL». Можно нарушить дух REST, имея красивые пути. Смотрите на семантику методов, идемпотентность и использование статусов.

## Термины

**Ресурс** — объект/понятие, адресуемое URI.

**Представление** — конкретный формат содержимого ресурса.

**Безопасный метод** — не меняет состояние (идея GET/HEAD).

**Идемпотентность** — повтор даёт тот же эффект.

**HATEOAS** — управление состоянием через ссылки в представлениях.

## Как это работает

Клиент делает HTTP-вызов. Сервер маршрутизирует путь на обработчик ресурса, применяет метод, читает/пишет хранилище, возвращает представление и код. Посредники (кэш, прокси) опираются на семантику методов — поэтому её нельзя врать.

Ошибки валидации — 4xx с понятным телом проблемы. Ошибки инфраструктуры — 5xx. Повторы клиента безопасны для идемпотентных операций.

## Пример

```http
POST /robots HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"name": "scout"}

HTTP/1.1 201 Created
Location: /robots/42
Content-Type: application/json

{"id": 42, "name": "scout"}
```

```http
GET /robots/42 HTTP/1.1
Host: api.example.com

HTTP/1.1 200 OK
Content-Type: application/json

{"id": 42, "name": "scout"}
```

## Разбор

POST создаёт и возвращает 201 + Location — клиент знает URI нового ресурса.

GET читает представление. Повтор GET безопасен. Если бы создание сделали через GET, кэши и боты устроили бы хаос.

## Ошибки

- Один endpoint `/api` + параметр action.
- Всегда статус 200.
- GET с побочными эффектами.
- Ломать идемпотентность PUT без документации.

## Что запомнить

- REST — стиль ресурсов и представлений над HTTP.
- Методы и коды — часть контракта.
- JSON популярен, но не определение REST.
- Кэш и повторы опираются на честную семантику.

## Дополнение: практика и нюансы

Пагинация, фильтрация и сортировка — часть контракта коллекций. Делайте предсказуемо.

429 с Retry-After лучше молчаливого дропа. Клиенты должны уметь замедляться.

Проблемы валидации возвращайте машиночитаемым телом, не только HTML-страницей ошибки.

Контрактные тесты OpenAPI ловят расхождения раньше интеграционных сюрпризов.
