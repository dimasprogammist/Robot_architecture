# HTTPS — HTTP поверх защищённого канала

## Цель

Понять, чем HTTPS отличается от HTTP: зачем оборачивать запросы в TLS, как выглядит обмен для клиента и какие симптомы бывают при ошибках сертификата.

## Исходные знания

HTTP и TCP. Бытовое представление о «замочке» в браузере. Следующий урок углубит TLS.

## Объяснение

### Проблема

Обычный HTTP передаёт запросы и ответы открытым текстом на участке сети. Их можно читать и подменять на пути (общественный Wi‑Fi, плохой прокси).

### Зачем HTTPS

HTTPS — это HTTP поверх TLS (исторически SSL, ныне TLS). Канал шифруется, сервер обычно предъявляет сертификат, клиент проверяет цепочку доверия. Целостность и конфиденциальность данных на транспорте повышаются.

### Принцип

Клиент соединяется с портом 443 (типично), сначала выполняет TLS handshake, затем внутри защищённого канала шлёт обычные HTTP-сообщения. С точки зрения приложения API часто тот же: те же методы и заголовки, другой URL scheme `https://`.

### Связь с сертификатами

Сертификат связывает имя хоста с открытым ключом и подписан удостоверяющим центром (или корпоративным CA). Несоответствие имени, истечение срока, неизвестный CA — причины отказа клиента.

### Ход обмена (упрощённо)

1) TCP connect. 2) TLS handshake + проверка сертификата. 3) HTTP request/response как обычно, но в encrypted records. 4) Закрытие TLS/TCP.

### Ошибки

Certificate verify failed. Истёкший сертификат. Самоподписанный без доверия. Смешанный контент на страницах. Редирект http→https сломан. На сервере забыли слушать 443 или не настроили цепочку intermediate CA.

## Термины

**HTTPS** — HTTP over TLS.

**Сертификат** — документ о ключе и имени.

**CA** — Certificate Authority, удостоверяющий центр.

**Sovereign check / validation** — проверка цепочки доверия клиентом.

**HSTS** — политика принудительного HTTPS в браузерах.

## Как это работает

Библиотеки (OpenSSL, BoringSSL…) и ОС хранят набор доверенных корневых CA. Браузер/curl используют его при проверке. Корпоративные MITM-прокси ставят свой CA на устройства — иначе HTTPS ломается или «прозрачно» перехватывается.

HTTPS не заменяет аутентификацию пользователя сам по себе: он защищает канал и удостоверяет сервер (обычно). Логин — отдельные механизмы (сессии, токены).

## Пример

```bash
curl -sI https://example.com | head
# намеренная ошибка проверки (учебно):
curl -sI https://example.com --cacert /nonexistent 2>&1 | head || true
```

```text
http://  → TCP:80  → открытый HTTP
https:// → TCP:443 → TLS → HTTP внутри
```

## Разбор

Успешный `curl -sI https://` показывает, что handshake и HTTP-ответ прошли.

Схема сравнивает два URL scheme. Для разработчика смена scheme часто одна строка, для эксплуатации — сертификаты и порт.

## Ошибки новичков

- Отключать проверку сертификата «навсегда» в проде.
- Путать «сайт открылся» с корректной цепочкой на всех клиентах.
- Держать параллельно открытый HTTP с чувствительными cookie.
- Забыть промежуточные сертификаты на сервере.

## Что запомнить

- HTTPS = HTTP + TLS-канал.
- Сначала TLS, потом HTTP.
- Проверка имени и CA критична.
- Это защита канала, не полная модель безопасности приложения.

## Задание

Откройте любой HTTPS-сайт через `curl -v` и найдите в выводе упоминание TLS/certificate. Запишите, к какому имени выдан сертификат (если видно).

## Дополнение: практика и нюансы

HSTS заставляет браузер использовать HTTPS; ошибочная настройка «приклеивается» — тестируйте осторожно.

Смешанный контент: страница HTTPS тянет HTTP-ресурс — браузер блокирует.

На мобильных клиентах кастомный CA для отладки не должен попасть в прод-сборку.

Проверяйте цепочку с внешнего vantage point: локально может быть «свой» CA.
