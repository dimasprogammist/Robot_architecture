# API — контракт между программами

## Цель

Обобщить понятие API: границы, контракт, совместимость, документация и выбор стиля (REST, RPC, события) исходя из задачи, а не моды.

## Исходные знания

HTTP, REST, сокеты, клиент–сервер. Опыт вызова чужой библиотеки полезен как аналогия.

## Объяснение

API (Application Programming Interface) — формальная граница, через которую одна программа пользуется другой. Сетевой API — частный случай: контракт сериализованных сообщений по протоколу. Локальный API библиотеки — функции и типы. Идея одна: обещания и ограничения.

Контракт включает: адресацию и транспорт, формат данных, аутентификацию, ошибки, лимиты, семантику идемпотентности, гарантии порядка (если есть), политику версий. Без контракта интеграция держится на устных договорённостях и ломается на первом обновлении.

Совместимость: добавление опционального поля часто безопасно; удаление или смена смысла — нет. Версионирование и период deprecation защищают клиентов. Семантика «молча игнорируй неизвестные поля» помогает эволюции.

Документация и машиночитаемые схемы (OpenAPI и др.) ускоряют клиентов и проверки. Примеры запросов важны не меньше текста. Контрактные тесты ловят расхождения реализации и описания.

Стили: REST-ресурсы, RPC (gRPC/JSON-RPC), графовые запросы, асинхронные события/очереди. Выбирают по: нужна ли идемпотентность кэша HTTP, стриминг, строгие схемы, офлайн-буферы, fan-out. Роботу на телеметрии часто ближе поток событий; админке CRUD — HTTP-ресурсы.

Безопасность API: аутентификация, авторизация, rate limit, валидация входа, аудит. Сеть (TLS) — необходимый, но не достаточный слой.

Наблюдаемость: correlation id, структурированные логи, метрики кодов и задержек. Без них распределённая система непрозрачна.

## Термины

**Контракт API** — согласованные правила обмена.

**Обратная совместимость** — старые клиенты продолжают работать.

**Версионирование** — управление изменениями контракта.

**RPC** — стиль «вызов процедуры» по сети.

**Idempotency-Key** — ключ безопасных повторов операций.

## Как это работает

Поставщик публикует контракт и endpoint. Потребитель генерирует клиент или пишет вручную. На границе стоят шлюзы: TLS termination, auth, квота. Эволюция идёт через новые версии или аккуратные расширения.

Ошибка сети ≠ ошибка бизнес-логики. Клиент различает таймаут (повтор?) и 400 (чинить запрос). Это часть контракта поведения.

## Пример

```text
Контракт (фрагмент):
POST /v1/devices
Auth: Bearer token
Body: {"name": string, "type": "robot"|"gateway"}
201 → {"id": string}
400 → {"error": "validation", "fields": ...}
409 → имя занято
429 → слишком часто; Retry-After
```

```bash
# каркас вызова
curl -s -o /dev/null -w "%{http_code}\n" -X POST https://example.com/v1/devices \
  -H "Content-Type: application/json" -d '{"name":"n1","type":"robot"}' || true
```

## Разбор

Фрагмент контракта фиксирует не только путь, но и коды и формы ошибок — это и есть API.

curl демонстрирует клиентскую сторону: важны метод, заголовки, тело и интерпретация кода.

## Ошибки

- Менять смысл поля без новой версии.
- Документировать только happy path.
- Смешивать транспортные и доменные ошибки без различия.
- Выбирать gRPC/REST/очереди по моде, а не по требованиям.

## Что запомнить

- API — контракт границы между программами.
- Совместимость и версии — инженерия, не бюрократия.
- Стиль выбирают под задачу.
- TLS + auth + лимиты + наблюдаемость входят в зрелый API.

## Задание

Опишите мини-контракт API для «отправить команду роботу»: путь/канал, вход, успех, две ошибки, нужна ли идемпотентность. Обоснуйте выбор HTTP или иного стиля одним абзацем.

## Связь дальше

Модуль сетей завершён. Дальше в курсе обычно идут инструменты разработки (git) и языки — опираясь на умение читать трафик и контракты.

## Дополнение: практика и нюансы

SLA/SLO по latency и error-rate — часть продукта API, не «потом».

Версия в Accept или URL — выберите один стиль и придерживайтесь.

Идемпотентность записи документируйте явно: какие методы безопасны к повтору.

Deprecation header и changelog экономят доверие клиентов при эволюции.

Итог раздела: закрепляйте механизм на практике, а не только синтаксис команд.
