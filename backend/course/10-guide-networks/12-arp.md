# ARP — IPv4-адрес в MAC

## Цель

Понять проблему нахождения MAC соседа по IPv4, ход ARP-запроса/ответа, поля сообщения своими словами и типичные сбои кэша.

## Исходные знания

MAC, IPv4, подсеть on-link, шлюз как next hop.

## Объяснение

### Проблема

Чтобы отправить IP-пакет соседу в Ethernet, нужен кадр с MAC назначения. Знать только IP недостаточно: канальный уровень говорит на MAC.

### Зачем протокол

ARP (Address Resolution Protocol) сопоставляет IPv4 → MAC в пределах локального сегмента. Для IPv6 ту же роль играет Neighbor Discovery, не ARP.

### Принцип

Кто не знает MAC, широковещательно спрашивает: «у кого этот IP?». Владелец отвечает своим MAC. Результат кэшируется в таблице соседей на время.

### Структура сообщения своими словами

ARP-сообщение несёт: тип оборудования (Ethernet), тип протокола (IPv4), длины адресов, операция (request/reply), MAC и IP отправителя, MAC и IP цели. В запросе MAC цели часто нули — «неизвестно». Это не IP-пакет; ARP сидит рядом с IPv4 на канале (EtherType другой).

### Ход обмена

1) Хост хочет послать на 192.168.1.1, маска говорит on-link. 2) Нет записи в кэше → ARP request broadcast. 3) Шлюз/хост с этим IP шлёт ARP reply unicast. 4) Кэш обновлён → кадр с нужным MAC. Для внешнего IP сначала резолвят MAC шлюза тем же механизмом.

### Ошибки

Пустой/устаревший кэш после смены устройства. ARP spoofing в недоверенной LAN. Нет ответа — неверный IP, тихий хост, изоляция клиента на Wi‑Fi, firewall на уровне клиента. Proxy ARP усложняет картину на некоторых сетях.

## Термины

**ARP cache / neighbor table** — кэш соответствий IP↔MAC.

**Request / Reply** — запрос и ответ ARP.

**Gratuitous ARP** — объявление своего соответствия без просьбы.

**on-link** — цель в локальной подсети.

**ND** — аналог задачи для IPv6.

## Как это работает

Ядро автоматически шлёт ARP при необходимости. Утилита `ip neigh` показывает состояние: REACHABLE, STALE, FAILED. Очистка кэша иногда нужна после замены железа с тем же IP.

Коммутаторы не «маршрутизируют ARP», они переносят broadcast кадры в пределах VLAN. Межсетевой ARP «через роутер» не работает как поиск конечного MAC за океаном — только локально.

## Пример

```bash
ip neigh
ping -c 1 "$(ip route | awk '/default/ {print $3; exit}')" 2>/dev/null || true
ip neigh
```

```text
ARP request: who-has 192.168.1.1? tell 192.168.1.10
ARP reply:   192.168.1.1 is-at aa:bb:cc:dd:ee:ff
```

## Разбор

До ping кэш мог не знать шлюз; после — запись появляется.

Диалог who-has/is-at — вся суть протокола в двух строках. Поля MAC/IP отправителя и цели заполняются соответственно операции.

## Ошибки новичков

- Ждать ARP до сервера в другой стране.
- Путать ARP с DNS.
- Игнорировать FAILED в `ip neigh` при «нет сети».
- Считать MAC вечной константой устройства в кэше.

## Что запомнить

- ARP решает IPv4→MAC только локально.
- Request широковещательный, reply обычно адресный.
- Кэш обязателен для производительности.
- IPv6 использует ND, не ARP.

## Задание

Очистите одну запись соседа (осторожно на прод-хосте) или используйте учебную VM, сделайте ping и посмотрите, как запись появляется в `ip neigh`.

## Дополнение: практика и нюансы

`ip neigh flush` используйте точечно. Массовая очистка на роутере瞬时но поднимает broadcast-шторм запросов.

Статические neigh записи редки и хрупки; обычно лечат L2/VLAN, а не статикой ARP.

Wi‑Fi client isolation: ARP до соседа не проходит — это политика, не «сломанный IP».

Обнаружение duplicate address через gratuitous ARP — смотрите логи при конфликте DHCP.
