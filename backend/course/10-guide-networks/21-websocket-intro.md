# WebSocket — вводный контраст с HTTP

## Цель

Понять, зачем появился WebSocket и чем его модель двунаправленного канала отличается от классического HTTP request/response. Глубокий курс — отдельно; здесь только контраст.

## Исходные знания

HTTP и HTTPS/TLS. TCP как поток. Клиент–сервер.

## Объяснение

HTTP отлично качает документы и делает API-вызовы «спросил — ответил». Но для частых серверных событий (котировки, телеметрия, совместное редактирование) цикл «клиент постоянно спрашивает» расточителен и медлителен. Long polling — костыль на той же модели.

WebSocket начинается с HTTP-совместимого handshake: клиент просит Upgrade, сервер отвечает 101 Switching Protocols. Дальше соединение становится двунаправленным сообщением-ориентированным каналом поверх того же TCP (обычно через TLS как `wss://`). Обе стороны могут слать кадры, когда нужно.

Это не замена всему HTTP. Страницы, REST CRUD, кэш CDN — по-прежнему HTTP. WebSocket — когда нужен живой канал. Прокси и балансировщики должны уметь Upgrade и долгие соединения.

Сообщения WebSocket — кадры с опкодами (текст, бинарный, ping/pong, close). Прикладной протокол поверх (JSON-RPC, свой бинарный формат) всё равно нужно проектировать: идемпотентность, auth, реконнект.

Безопасность: используйте `wss://`, проверяйте происхождение (Origin) на сервере, аутентифицируйте до/после upgrade, ограничивайте размер кадров. Открытый WS без проверок — подарок атакующему.

Контраст коротко: HTTP — дискретные транзакции запрос/ответ; WebSocket — сессия с асинхронными сообщениями в обе стороны. Ошибки сети требуют явной логики reconnect, которой «один curl» не закрывает.

## Термины

**Upgrade** — переключение протокола из HTTP handshake.

**101 Switching Protocols** — успешный переход на WebSocket.

**`wss://`** — WebSocket поверх TLS.

**Кадр WS** — единица сообщения канала.

**Heartbeat (ping/pong)** — проверка живости канала.

## Как это работает

Клиент держит TCP/TLS, шлёт HTTP GET с заголовками Upgrade и Sec-WebSocket-Key. Сервер подтверждает Accept. Далее парсеры HTTP сменяются парсерами WS-кадров. Посредники, не понимающие Upgrade, рвут задумку.

Масштабирование stateful-каналов сложнее, чем stateless HTTP: липкие сессии или pub/sub на бэкенде.

## Пример

```text
клиент: GET /chat HTTP/1.1
        Host: example.com
        Upgrade: websocket
        Connection: Upgrade
        Sec-WebSocket-Key: ...
        Sec-WebSocket-Version: 13

сервер: HTTP/1.1 101 Switching Protocols
        Upgrade: websocket
        Connection: Upgrade
        Sec-WebSocket-Accept: ...

далее: двунаправленные кадры (текст/бинарные/ping)
```

```bash
# проверка, что обычный HTTP жив; WS нужен отдельный клиент
curl -sI https://example.com | head -n 5
```

## Разбор

Пример показывает только фазу Upgrade — дальше уже не классические request/response.

curl здесь напоминает: обычными HTTP-инструментами канал WS не «прощёлкать» до конца; нужен WS-клиент.

## Ошибки

- Заменять весь API на WebSocket без нужды.
- Забывать TLS (`ws://` на публичных сетях).
- Не проектировать reconnect и auth.
- Ломать прокси неподдерживаемым Upgrade.

## Что запомнить

- WebSocket — двунаправленный канал после HTTP Upgrade.
- Это контраст к модели «один запрос — один ответ».
- `wss` и проверки Origin/auth обязательны в проде.
- Глубокая практика WS — отдельная тема.

## Дополнение: практика и нюансы

LB idle timeout короче heartbeat WS — получите «тихие» обрывы. Согласуйте ping/pong и таймауты.

Горизонтальное масштабирование WS требует sticky или pub/sub бэкенда для fan-out.

Не смешивайте огромный бинарный поток и критичные control frames без своего протокола поверх.

Для редких событий подумайте SSE (Server-Sent Events) как более простую альтернативу в одну сторону.
