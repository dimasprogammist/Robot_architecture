# Порты — мультиплексирование на хосте

## Цель

Понять, зачем нужны порты TCP/UDP: как один IP обслуживает множество приложений и как выглядит сокет-адрес.

## Исходные знания

TCP и UDP. IP-адрес хоста.

## Объяснение

IP доставляет пакет на хост. На хосте может работать десятки сетевых программ. Порт — 16-битный номер, который указывает, какому сокету отдать данные транспорта. Пара (IP, порт, протокол) определяет конечную точку.

Сервер обычно слушает хорошо известный порт (HTTPS 443, SSH 22). Клиент получает эфемерный порт автоматически. Соединение TCP идентифицируется четвёркой: src IP, src port, dst IP, dst port.

Диапазоны: привилегированные порты ниже 1024 на UNIX часто требуют прав для bind. Это политика ОС, не свойство протокола интернета.

Список «официальных» номеров ведёт IANA, но на практике важнее, что реально слушает ваш процесс. Конфликт bind — порт занят другим сокетом.

Публикация сервиса «наружу» требует слушать на нужном интерфейсе (`0.0.0.0` vs `127.0.0.1`) и пропускать трафик фильтрами. Слушать на localhost недостаточно для удалённого доступа.

NAT переписывает порты: снаружи виден публичный IP и mapped port. Отладка «порт открыт» должна уточнять: с какой стороны смотрите.

## Термины

**Порт** — номер демультиплексирования TCP/UDP.

**Well-known ports** — распространённые номера сервисов.

**Эфемерный порт** — временный порт клиента.

**Bind** — привязка сокета к локальному адресу и порту.

**Четвёрка TCP** — идентификатор соединения.

## Как это работает

При входящем сегменте ядро ищет сокет по таблице. Нет слушателя — RST (TCP) или тишина/ICMP (UDP, зависит). Исходящие соединения ОС выбирает свободный локальный порт.

`ss -lntp` / `ss -lunp` показывают слушателей. Номер порта в URL `http://host:8080` явно задаёт нестандартный порт.

## Пример

```bash
ss -lntu | head
# схема адреса
# 203.0.113.5:443  — HTTPS на публичном хосте
# 127.0.0.1:5432   — PostgreSQL только локально
```

```text
один IP, много портов:
:22 sshd
:80 веб
:53 DNS
```

## Разбор

Список слушателей — правда о том, что доступно на хосте (до фильтра).

Разница `127.0.0.1` и `0.0.0.0` критична для безопасности и доступности.

## Ошибки

- Открывать сервис на `0.0.0.0` без файрвола.
- Путать порт контейнера и порт хоста.
- Считать, что «известный номер» сам по себе защищает.
- Диагностировать только порт, игнорируя интерфейс bind.

## Что запомнить

- Порт выбирает приложение на хосте.
- TCP-соединение задаётся четвёркой адресов/портов.
- localhost ≠ доступ из сети.
- NAT меняет видимые порты на границе.

## Задание

Снимите список слушающих портов. Для трёх номеров запишите процесс (если виден) и предположите, должен ли сервис быть доступен извне.

## Дополнение: практика и нюансы

Регистрация порта в systemd socket activation — отдельный паттерн: сокет создаёт systemd, сервис принимает.

Конфликт портов в docker: публикуйте только нужное на loopback или firewall.

Сканирование портов без разрешения может быть незаконным/против политики — работайте в своих лабах.

Документируйте таблицу портов сервиса в README рядом с compose/unit.


Проверьте цепочку сертификатов с промежуточными, не только листовой файл.

Убедитесь, что клиентский таймаут больше, чем худший RTT + handshake + обработка.

Разделите метрики ошибок транспорта и прикладных 4xx/5xx — это разные классы проблем.
