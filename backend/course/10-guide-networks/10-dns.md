# DNS — имена и адреса

## Цель

Понять проблему человекочитаемых имён, роль DNS, ход типичного запроса A/AAAA и где ломается резолвинг.

## Исходные знания

IP-адреса и порты на уровне идеи. Клиент-сервер бытовой опыт.

## Объяснение

### Проблема

Людям удобны имена вроде `example.com`, машинам для маршрутизации нужны адреса. Хранить таблицу «имя→IP» вручную на каждом хосте невозможно в масштабе интернета.

### Зачем протокол

DNS — распределённая система и протокол запросов, который по имени возвращает записи: адрес (A/AAAA), почтовый обменник (MX), сервисные указатели и др. Клиент получает адрес и уже строит TCP/UDP к нему.

### Принцип

Иерархия зон: корень → TLD → авторитетные серверы домена. Резолвер (на хосте или у провайдера) идёт по цепочке или использует кэш. TTL записи говорит, как долго кэшировать.

### Структура сообщения своими словами

Сообщение DNS содержит: идентификатор запроса, флаги (запрос/ответ, рекурсия), секции вопрос/ответ/authority/additional. В вопросе — имя и тип записи. В ответе — ресурсные записи с типом, классом, TTL и данными (например, четыре октета IPv4 для A).

Транспорт часто UDP/53; длинные ответы и зоны — TCP. Это детали, но полезны при отладке фильтрации.

### Ход обмена

1) Приложение просит ОС резолвить имя. 2) Stub-резолвер шлёт запрос на настроенный DNS (из DHCP или статически). 3) Рекурсивный сервер либо отвечает из кэша, либо обходит иерархию. 4) Ответ возвращается клиенту. 5) Клиент кэширует на время TTL.

### Ошибки

NXDOMAIN — имени нет. SERVFAIL — сбой сервера. Таймаут — сеть/фильтр/неверный резолвер. Устаревший кэш — «у меня один IP, у коллеги другой». Неправильный `/etc/hosts` перебивает DNS.

## Термины

**Резолвер** — компонент, выполняющий DNS-запросы.

**A / AAAA** — записи адресов IPv4/IPv6.

**TTL** — время жизни записи в кэше.

**Авторитативный сервер** — источник правды зоны.

**Stub resolver** — клиентская часть на хосте.

## Как это работает

Приложение обычно не говорит на «сыром» DNS: оно зовёт getaddrinfo. ОС использует configured nameserver. Ошибка DNS выглядит для пользователя как «нет интернета», хотя ping по IP ещё работает — разделяйте симптомы.

DNS не шифрует классический трафик по умолчанию; есть DoT/DoH как отдельные практики. Подделка ответов — риск без дополнительных защит (DNSSEC и т.п.).

## Пример

```bash
getent hosts example.com
# или
python -c "import socket; print(socket.getaddrinfo('example.com', 443)[:2])"
```

```text
вопрос: example.com A?
ответ:  example.com TTL A 93.184.216.34   # пример формы, адрес может отличаться
```

## Разбор

`getent`/`getaddrinfo` показывают результат через системный резолвер — то, чем реально пользуется софт.

Схема вопроса/ответа подчёркивает тип записи и TTL. Без правильного типа AAAA вы можете «не увидеть» IPv6.

## Ошибки новичков

- Чинить маршруты, когда не резолвится имя.
- Жёстко прописывать IP в приложении и забывать про смену.
- Игнорировать кэш после смены DNS у домена.
- Путать DNS-сервер с default gateway как сущности.

## Что запомнить

- DNS решает задачу имя→данные (часто адрес).
- Иерархия + кэш + TTL.
- Сообщение: вопрос и ресурсные записи.
- Отдельно проверяйте резолв и IP-связность.

## Задание

Разрешите имя известного сайта и сравните с доступом по полученному IP (если политика позволяет). Сломайте временно nameserver в тестовой среде и сравните симптомы.

## Дополнение: практика и нюансы

`dig +trace` показывает цепочку делегирования — учебный инструмент понимания иерархии.

Кэш на stub/рекурсоре объясняет «у меня обновилось, у него нет». Смотрите TTL.

Split-horizon DNS отдаёт разные ответы внутри/снаружи — источник сюрпризов для VPN.

Не используйте IP в сертификатах вместо имён без нужды; DNS и TLS связаны через имя.
