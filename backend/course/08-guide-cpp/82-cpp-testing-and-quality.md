# Качество и тестирование C++ проекта

## Цель

Работающая программа ещё не означает, что программа надёжная.

Она может:

* неправильно обрабатывать крайние случаи;
* падать при неправильном вводе;
* иметь гонки потоков;
* неправильно освобождать ресурсы;
* работать на одном компьютере и ломаться на другом.

Поэтому в реальной разработке важны не только написание кода, но и его проверка.

---

## Что такое тест

Тест — это автоматическая или ручная проверка ожидаемого поведения программы.

Например, есть функция:

```cpp
int add(int a, int b)
{
    return a + b;
}
```

Мы ожидаем:

```text
add(2, 3) == 5
```

Простейшая проверка:

```cpp
#include <cassert>

int main()
{
    assert(add(2, 3) == 5);
}
```

Если условие ложно, программа завершится с ошибкой.

---

## Проверка граничных случаев

Проверять только обычные значения недостаточно.

Для функции:

```cpp
double calculateError(
    double target,
    double actual
)
{
    return target - actual;
}
```

нужно проверить:

```text
target = 100
actual = 90

target = 0
actual = 0

target = -10
actual = 20
```

Особенно важны границы.

Например, если допустим диапазон:

```text
0 ... 100
```

проверяем:

```text
-1
0
1
99
100
101
```

## Тестирование класса

Допустим:

```cpp
class Device
{
public:
    void setValue(double value)
    {
        value_ = value;
    }

    double value() const
    {
        return value_;
    }

private:
    double value_ = 0.0;
};
```

Тест:

```cpp
#include <cassert>

int main()
{
    Device device;

    assert(device.value() == 0.0);

    device.setValue(42.5);

    assert(device.value() == 42.5);
}
```

Мы проверяем поведение класса, а не его внутреннюю реализацию.

---

## Unit test

Unit test — тест отдельной небольшой части программы.

Например:

```text
Device
```

можно тестировать отдельно от:

```text
Network
Database
GUI
```

Это важно.

Если тест требует подключения к реальному PLC, это уже не изолированный unit test.

## Fake объект

Предположим, монитор получает данные через:

```cpp
class ISensor
{
public:
    virtual ~ISensor() = default;

    virtual double read() = 0;
};
```

Для тестирования создадим:

```cpp
class FakeSensor : public ISensor
{
public:
    explicit FakeSensor(double value)
        : value_(value)
    {
    }

    double read() override
    {
        return value_;
    }

private:
    double value_;
};
```

Теперь можно проверить монитор без оборудования:

```cpp
FakeSensor sensor(42.0);

Monitor monitor(sensor);

monitor.update();
```

## Почему это важно для промышленной автоматизации

Представим программу, которая работает с:

```text
PLC
 ↓
датчики
 ↓
двигатели
 ↓
приводы
```

Запускать тесты непосредственно на работающей линии неудобно и иногда опасно.

Поэтому желательно иметь возможность заменить:

```text
Real PLC
```

на:

```text
Fake PLC
```

и проверить алгоритм программно.

## Инварианты

Инвариант — условие, которое должно оставаться истинным.

Например:

```text
температура >= 0
```

или:

```text
уровень >= 0 && уровень <= 100
```

Можно сделать проверку:

```cpp
bool isValidLevel(double level)
{
    return level >= 0.0 &&
           level <= 100.0;
}
```

Тесты:

```cpp
assert(isValidLevel(0.0));
assert(isValidLevel(50.0));
assert(isValidLevel(100.0));

assert(!isValidLevel(-1.0));
assert(!isValidLevel(101.0));
```

---

## Тесты ошибок

Нужно тестировать не только успешные сценарии.

Например:

```cpp
Config loadConfig(
    const std::string& path
);
```

Нужно проверить:

```text
файл существует
файл отсутствует
файл пустой
неправильный формат
отсутствует обязательный параметр
неверное значение
```

Хорошая программа должна предсказуемо обрабатывать такие ситуации.

---

## Тестирование потоков

Многопоточные программы сложнее.

Проблема может появляться редко:

```text
запуск 1 → работает
запуск 2 → работает
запуск 3 → ошибка
...
запуск 100 → ошибка
```

Поэтому особенно важно:

* защищать общие данные;
* минимизировать shared state;
* использовать RAII;
* проверять остановку потоков;
* не создавать data race;
* не допускать deadlock.

---

## Статический анализ

Помимо запуска тестов существуют инструменты, которые анализируют код.

Они могут находить:

* подозрительные конструкции;
* потенциальные ошибки;
* неиспользуемые переменные;
* проблемы типов;
* некоторые случаи неопределённого поведения.

Примеры инструментов:

```text
compiler warnings
clang-tidy
clang static analyzer
sanitizers
```

---

## Предупреждения компилятора

Не следует игнорировать предупреждения.

Например:

```bash
g++ -Wall -Wextra -Wpedantic main.cpp
```

Компилятор может обнаружить подозрительный код ещё до запуска программы.

Полезно относиться к предупреждениям как к сигналу:

```text
компилятор заметил потенциальную проблему
```

а не просто нажимать "build" до тех пор, пока программа не соберётся.

---

## Sanitizer

Современные компиляторы могут использовать sanitizers.

Например:

```bash
-fsanitize=address
```

AddressSanitizer способен обнаруживать некоторые ошибки работы с памятью.

Также существуют инструменты для обнаружения проблем многопоточности.

Например, в подходящей среде можно использовать:

```text
ThreadSanitizer
```

## Качество кода

Качественный код обычно имеет:

```text
понятные имена
маленькие функции
четкие ответственности
минимум скрытого состояния
предсказуемое управление ресурсами
обработку ошибок
тесты
```

Например:

```cpp
double x;
```

хуже объясняет назначение переменной, чем:

```cpp
double targetTemperature;
```

Имя должно помогать читать программу.

---

## Главное

Тестирование — не отдельная задача после программирования.

Хорошая архитектура изначально должна позволять проверять компоненты независимо.

Если класс невозможно протестировать без запуска всей системы, подключения к PLC и настройки сети, это может быть признаком слишком сильной связанности компонентов.

Чем проще тестировать отдельную часть программы, тем проще развивать весь проект.
