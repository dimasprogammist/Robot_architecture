# Основы тестирования C++ кода

## Цель

Отладчик помогает найти проблему, когда программа уже ведёт себя неправильно. Но полагаться только на ручную проверку нельзя: после каждого изменения кода старая ошибка может вернуться.

Тестирование позволяет автоматически проверять, соответствует ли программа ожидаемому поведению.

После урока вы должны понимать:

* зачем нужны автоматические тесты;
* что такое тестируемый код;
* из каких частей состоит простой тест;
* что такое ожидаемый результат;
* чем модульный тест отличается от ручной проверки;
* почему тесты особенно полезны после исправления ошибок;
* как проектировать функции, которые удобно тестировать;
* как тестирование связано с архитектурой C++ программы.

---

## Зачем нужны тесты

Представим функцию:

```cpp
int add(int a, int b) {
    return a + b;
}
```

Её легко проверить вручную:

```cpp
std::cout << add(2, 3) << '\n';
```

Мы увидим:

```text
5
```

Но в реальном проекте функций могут быть сотни.

После изменения одной функции другая часть программы может перестать работать.

Если каждый раз проверять всё вручную, процесс становится долгим и ненадёжным.

Тест позволяет записать ожидаемое поведение программы:

```text
add(2, 3) → 5
```

А затем проверять его автоматически.

---

## Что такое тест

Упрощённо тест состоит из трёх частей:

```text
подготовить данные
      ↓
выполнить код
      ↓
проверить результат
```

Например:

```cpp
int result = add(2, 3);

if (result != 5) {
    std::cout << "Test failed\n";
}
```

Если:

```cpp
result == 5
```

тест успешен.

Если:

```cpp
result != 5
```

тест сообщает об ошибке.

---

## Ожидаемый результат

Самая важная часть теста — понять, какой результат считается правильным.

Например:

```cpp
int multiply(int a, int b) {
    return a * b;
}
```

Можно проверить:

```text
multiply(2, 3) → 6
multiply(0, 10) → 0
multiply(-2, 3) → -6
```

Тесты должны проверять не случайные значения, а важные свойства функции.

---

## Ручная проверка

Допустим, у нас есть программа:

```cpp
double calculateSpeed(double distance, double time) {
    return distance / time;
}
```

Можно запустить программу и вручную проверить:

```text
distance = 100
time = 2
result = 50
```

Но завтра кто-то изменит формулу.

Ручную проверку придётся повторять.

Автоматический тест может выполнять её каждый раз:

```text
calculateSpeed(100, 2) == 50
```

---

## Модульный тест

**Модульный тест**, или unit test, проверяет небольшой самостоятельный фрагмент программы.

Чаще всего это:

* функция;
* класс;
* отдельный компонент.

Например:

```cpp
int clamp(int value, int min, int max);
```

Можно проверить его отдельно от всего приложения.

Это позволяет быстро понять, где возникла ошибка.

---

## Пример функции

Рассмотрим:

```cpp
int clamp(int value, int min, int max) {
    if (value < min) {
        return min;
    }

    if (value > max) {
        return max;
    }

    return value;
}
```

Ожидаем:

```text
clamp(5, 0, 10) → 5
clamp(-5, 0, 10) → 0
clamp(20, 0, 10) → 10
```

Это уже набор тестовых случаев.

---

## Простейший самодельный тест

Для изучения принципа можно вообще не использовать тестовый фреймворк:

```cpp
#include <iostream>

int clamp(int value, int min, int max) {
    if (value < min) {
        return min;
    }

    if (value > max) {
        return max;
    }

    return value;
}

int main() {
    int result = clamp(5, 0, 10);

    if (result == 5) {
        std::cout << "PASS\n";
    } else {
        std::cout << "FAIL\n";
    }
}
```

Это примитивный тест, но идея уже понятна.

---

## Несколько проверок

Можно сделать несколько:

```cpp
bool testClamp() {
    if (clamp(5, 0, 10) != 5) {
        return false;
    }

    if (clamp(-5, 0, 10) != 0) {
        return false;
    }

    if (clamp(20, 0, 10) != 10) {
        return false;
    }

    return true;
}
```

Затем:

```cpp
int main() {
    if (testClamp()) {
        std::cout << "All tests passed\n";
    } else {
        std::cout << "Test failed\n";
    }
}
```

Для настоящего проекта обычно используют специализированный тестовый фреймворк.

---

## Тестовый фреймворк

Тестовый фреймворк предоставляет готовые средства для:

* запуска тестов;
* проверки результатов;
* вывода ошибок;
* группировки тестов;
* автоматического отчёта.

В C++ существуют разные библиотеки для этого.

Например:

```text
GoogleTest
Catch2
doctest
```

Конкретный выбор зависит от проекта.

Главное сейчас — понять сам принцип тестирования.

---

## Assertion

В тестах часто используется понятие **assertion** — утверждение.

Например:

```text
ожидаем:
result == 10
```

Если условие истинно:

```text
PASS
```

Если ложно:

```text
FAIL
```

В тестовом фреймворке это обычно записывается специальной конструкцией.

Условно:

```cpp
EXPECT_EQ(result, 10);
```

Она проверяет равенство.

---

## Хороший тест

Хороший тест должен быть:

* понятным;
* воспроизводимым;
* независимым;
* быстрым;
* конкретным.

Например:

```text
testClampReturnsMinimumForSmallValue
```

сразу говорит, что именно проверяется.

---

## Тестирование граничных значений

Особенно важно проверять границы.

Для:

```cpp
clamp(value, 0, 100)
```

интересны:

```text
-1
0
1
99
100
101
```

Почему?

Потому что ошибки часто возникают именно на границах.

Например:

```cpp
if (value > max)
```

и:

```cpp
if (value >= max)
```

отличаются поведением при:

```text
value == max
```

---

## Нормальные и неправильные данные

Тесты должны проверять не только нормальный сценарий.

Например, функция:

```cpp
int parsePort(const std::string& text);
```

может получать:

```text
"8080"
"1"
"65535"
"0"
"65536"
"abc"
""
```

Это разные категории входных данных.

Хороший набор тестов проверяет каждую важную категорию.

---

## Тестирование ошибок

Если функция выбрасывает исключение:

```cpp
int parsePort(const std::string& text) {
    // ...
    throw std::invalid_argument("Invalid port");
}
```

тест должен проверять не только успешный результат, но и ошибочный сценарий.

То есть:

```text
правильный ввод → правильный результат
неправильный ввод → правильная ошибка
```

Это особенно важно для функций, которые работают с файлами, конфигурацией, сетью и внешними устройствами.

---

## Тестирование классов

Рассмотрим:

```cpp
class Motor {
public:
    explicit Motor(int speed)
        : speed_(speed) {
    }

    int speed() const {
        return speed_;
    }

private:
    int speed_;
};
```

Можно проверить:

```text
Motor(100).speed() == 100
```

Но лучше тестировать не внутреннее устройство класса, а его публичное поведение.

То есть тест должен отвечать на вопрос:

> Делает ли объект то, что обещает его интерфейс?

---

## Почему приватные поля обычно не тестируют

Предположим:

```cpp
class Motor {
private:
    int speed_;
};
```

Тест не должен пытаться напрямую получить:

```cpp
speed_
```

Если публичный интерфейс говорит:

```cpp
motor.speed()
```

тестирует именно его.

Так тест меньше зависит от внутренней реализации.

Если завтра:

```cpp
int speed_;
```

заменят на другой механизм хранения, тесты продолжат работать.

---

## Тестируемость

Не весь код одинаково удобно тестировать.

Например:

```cpp
int calculateSpeed(int sensorValue);
```

очень легко тестировать.

А функция:

```cpp
void runRobot() {
    connectToPlc();
    readSensor();
    moveMotor();
    updateDisplay();
}
```

сильно зависит от внешнего мира.

Она одновременно работает:

* с сетью;
* с оборудованием;
* с датчиками;
* с GUI.

Такой код сложнее тестировать автоматически.

---

## Разделение ответственности

Лучше разделять:

```text
получение данных
       ↓
обработка данных
       ↓
принятие решения
       ↓
управление устройством
```

Например:

```cpp
double calculateTarget(double sensorValue);
```

можно тестировать без реального датчика.

А отдельный компонент:

```cpp
SensorReader
```

может отвечать только за получение данных.

Так архитектура становится более тестируемой.

---

## Зависимости

Представим:

```cpp
class RobotController {
public:
    void start() {
        sensor_.read();
        motor_.start();
    }

private:
    Sensor sensor_;
    Motor motor_;
};
```

Тесту приходится работать с настоящими объектами.

Если вместо этого зависимости передаются извне, появляется больше возможностей для тестирования.

Например:

```cpp
class RobotController {
public:
    RobotController(Sensor& sensor, Motor& motor)
        : sensor_(sensor),
          motor_(motor) {
    }

private:
    Sensor& sensor_;
    Motor& motor_;
};
```

Это связано с темой архитектуры и зависимостей, которую мы будем развивать дальше.

---

## Регрессионный тест

Представим, что нашли ошибку:

```text
скорость 0 обрабатывается неправильно
```

После исправления добавляем тест:

```text
speed = 0
expected = ...
```

Теперь этот тест защищает от повторного появления ошибки.

Такой тест называется частью **регрессионного тестирования**.

Идея:

```text
нашли ошибку
    ↓
исправили
    ↓
добавили тест
    ↓
ошибка не должна вернуться
```

---

## Тесты и рефакторинг

Тесты особенно полезны при изменении архитектуры.

Допустим, функция работала:

```cpp
calculateSpeed(...)
```

Затем мы переписали её внутреннюю реализацию.

Если тесты продолжают проходить:

```text
старые тесты → PASS
```

это даёт дополнительную уверенность, что внешнее поведение сохранилось.

Тесты не доказывают абсолютную правильность программы, но существенно уменьшают количество незамеченных регрессий.

---

## Тестирование промышленного приложения

Представим:

```text
PLC
 ↓
OPC UA
 ↓
программа
 ↓
алгоритм
 ↓
команда
```

Нельзя каждую проверку выполнять на реальном оборудовании.

Лучше отдельно тестировать алгоритм:

```cpp
double calculateSetpoint(
    double actual,
    double target
);
```

На вход:

```text
actual = 95
target = 100
```

Ожидаемый результат известен.

Такую функцию можно проверять тысячами случаев без подключения к PLC.

---

## Тесты не заменяют интеграцию

Но модульный тест не проверит:

```text
работает ли настоящий PLC?
```

Для этого нужны интеграционные проверки.

Упрощённо можно представить уровни:

```text
Unit tests
    ↓
проверяют отдельные компоненты

Integration tests
    ↓
проверяют взаимодействие компонентов

System tests
    ↓
проверяют систему целиком
```

Каждый уровень отвечает на свои вопросы.

---

## Практический пример

Допустим, есть функция:

```cpp
double calculateError(
    double target,
    double actual
) {
    return target - actual;
}
```

Набор тестов:

```text
calculateError(100, 90) → 10
calculateError(100, 100) → 0
calculateError(90, 100) → -10
```

Можно добавить граничные случаи:

```text
calculateError(0, 0) → 0
calculateError(-10, -20) → 10
```

Для системы управления это уже полезный набор проверок.

---

## Что проверять в первую очередь

Особенно полезно тестировать:

* математические функции;
* преобразования данных;
* парсеры;
* работу с конфигурацией;
* алгоритмы;
* обработку ошибок;
* граничные значения;
* критические бизнес-правила.

Не обязательно сразу покрывать тестами каждую строку проекта.

Гораздо полезнее начать с логики, где ошибка дорого обходится.

---

## Главное

Тестирование превращает ожидаемое поведение программы в автоматически проверяемые условия.

Хороший процесс:

```text
написали код
    ↓
написали тест
    ↓
запустили
    ↓
получили PASS
```

При изменении:

```text
изменили код
    ↓
запустили тесты
    ↓
PASS → поведение сохранилось
FAIL → нужно исследовать изменение
```

Особенно ценны тесты для:

* алгоритмов;
* граничных условий;
* ошибок;
* преобразований данных;
* исправленных ранее багов.

Тестируемость напрямую связана с архитектурой программы. Чем сильнее код зависит от конкретного оборудования, сети, GUI и глобального состояния, тем сложнее его проверять автоматически.
