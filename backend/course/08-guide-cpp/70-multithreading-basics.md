# Основы многопоточности

## Цель

Создать поток в C++ относительно просто:

```cpp
std::thread thread(worker);
```

Сложность начинается тогда, когда потоков становится несколько и они начинают взаимодействовать.

Например:

```text
Поток датчиков → записывает данные
Поток обработки → читает данные
Поток интерфейса → показывает данные
```

Все они могут обращаться к одним и тем же объектам.

В этот момент появляются гонки данных, проблемы с порядком выполнения и взаимные блокировки.

После урока вы должны понимать:

* что такое многопоточность;
* что такое конкурентное выполнение;
* почему общий изменяемый объект опасен;
* что такое race condition;
* чем data race отличается от обычной логической ошибки;
* что такое mutex;
* зачем нужна синхронизация;
* почему большое количество потоков не всегда ускоряет программу.

---

## Многопоточность как модель программы

Однопоточная программа:

```text
A → B → C → D
```

Все действия выполняются последовательно.

Многопоточная программа:

```text
        ┌→ A → B ─┐
Start ──┤          ├→ Finish
        └→ C → D ─┘
```

Часть задач может выполняться независимо.

Например:

```text
Thread A → чтение датчика
Thread B → запись логов
```

Пока один поток ждёт устройство, другой может выполнять свою работу.

---

## Конкурентность и параллельность

Эти понятия часто используют как синонимы, но полезно различать их.

**Конкурентность** означает, что несколько задач находятся в состоянии выполнения и система организует их совместную работу.

**Параллельность** означает, что задачи действительно выполняются одновременно, например на разных ядрах.

Схематично:

```text
Одно ядро:

A A A B B A B B
```

Задачи чередуются.

Несколько ядер:

```text
Core 1: A A A A
Core 2: B B B B
```

Задачи могут выполняться одновременно.

---

## Почему многопоточность нужна

Представим программу мониторинга:

```text
проверка OPC UA
проверка TCP
запись журнала
обновление интерфейса
```

Если всё выполнять последовательно:

```text
OPC UA
↓
TCP
↓
лог
↓
GUI
↓
снова OPC UA
```

долгая операция может задержать остальные.

Разделение задач позволяет сделать архитектуру отзывчивее.

---

## Главная проблема — общие данные

Предположим:

```cpp
int value = 0;
```

Поток A:

```cpp
value++;
```

Поток B:

```cpp
value++;
```

Оба потока обращаются к одному объекту.

```text
Thread A ──┐
           ├── value
Thread B ──┘
```

Это уже требует внимания.

---

## Что происходит при `++`

Операция:

```cpp
value++;
```

логически означает:

```text
1. прочитать value
2. увеличить
3. записать результат
```

Представим:

```text
value = 10
```

Поток A:

```text
читает 10
```

Поток B:

```text
читает 10
```

Поток A:

```text
записывает 11
```

Поток B:

```text
записывает 11
```

Хотя увеличение произошло два раза, результат:

```text
11
```

а не:

```text
12
```

Это пример проблемы конкурентного доступа.

---

## Race condition

**Race condition** — ситуация, когда результат зависит от порядка выполнения конкурентных операций.

Например:

```text
Thread A
Thread B
```

могут завершить операции в разном порядке.

В результате программа иногда выдаёт:

```text
100
```

а иногда:

```text
99
```

или другой результат.

Такие ошибки особенно неприятны, потому что порядок выполнения потоков не всегда предсказуем.

---

## Data race

В C++ есть ещё более конкретное понятие — **data race**.

Упрощённо, data race возникает, когда несколько потоков одновременно обращаются к одной памяти, и хотя бы один из доступов изменяет данные, при этом отсутствует необходимая синхронизация.

Для C++ это уже не просто «результат может быть неожиданным».

Программа попадает в область неопределённого поведения.

Поэтому общие изменяемые данные нельзя просто использовать одновременно без защиты.

---

## Первый инструмент защиты — `std::mutex`

Для синхронизации используется:

```cpp
#include <mutex>
```

Создадим mutex:

```cpp
std::mutex mutex;
```

Перед изменением данных поток должен получить блокировку.

```cpp
mutex.lock();

++counter;

mutex.unlock();
```

Но ручной `unlock()` опасен.

Если между ними произойдёт исключение или другой выход из функции, mutex может остаться заблокированным.

Поэтому обычно используют RAII.

---

## `std::lock_guard`

Самый простой вариант:

```cpp
std::lock_guard<std::mutex> lock(mutex);

++counter;
```

Когда `lock` создаётся, mutex блокируется.

Когда `lock` уничтожается, mutex автоматически освобождается.

Это безопаснее ручного:

```cpp
lock();
unlock();
```

---

## Полный пример

```cpp
#include <iostream>
#include <mutex>
#include <thread>

int counter = 0;
std::mutex counterMutex;

void worker() {
    for (int i = 0; i < 1000; ++i) {
        std::lock_guard<std::mutex> lock(counterMutex);
        ++counter;
    }
}

int main() {
    std::thread a(worker);
    std::thread b(worker);

    a.join();
    b.join();

    std::cout << counter << '\n';
}
```

Теперь доступ к `counter` защищён mutex.

Ожидаемый результат:

```text
2000
```

---

## Критическая секция

Участок программы, в котором поток работает с общим ресурсом, часто называют **критической секцией**.

Например:

```cpp
{
    std::lock_guard<std::mutex> lock(mutex);

    // критическая секция
    ++counter;
}
```

Важно держать блокировку как можно меньше.

Не стоит делать внутри mutex долгие операции:

```cpp
std::lock_guard<std::mutex> lock(mutex);

connectToServer();
readHugeFile();
sleep();
processLargeDataset();
```

Если этого можно избежать, лучше вынести долгую работу за пределы критической секции.

---

## Почему mutex не ускоряет программу

Mutex не делает вычисления быстрее.

Он решает другую задачу:

```text
не допустить неправильный одновременный доступ
```

Цена — потоки могут ждать друг друга.

Например:

```text
Thread A → [mutex] → работа
Thread B → ждёт
```

После освобождения:

```text
Thread A → освобождает
Thread B → получает mutex
```

---

## Слишком крупная блокировка

Плохой вариант:

```cpp
std::lock_guard<std::mutex> lock(mutex);

readSensor();
processData();
writeLog();
sendNetworkPacket();
```

Весь этот код выполняется под одной блокировкой.

Другие потоки будут ждать.

Лучше ограничивать защищённую область:

```cpp
auto data = readSensor();

{
    std::lock_guard<std::mutex> lock(mutex);
    sharedData = data;
}

writeLog(data);
sendNetworkPacket(data);
```

Так mutex удерживается только во время изменения общего состояния.

---

## `std::unique_lock`

Иногда требуется более гибкое управление блокировкой.

Для этого есть:

```cpp
std::unique_lock<std::mutex>
```

Например:

```cpp
std::unique_lock<std::mutex> lock(mutex);
```

Он умеет:

* блокировать mutex;
* освобождать mutex;
* снова блокировать;
* работать с `condition_variable`.

На первых этапах `lock_guard` обычно проще.

---

## Атомарные переменные

Для некоторых простых операций mutex может быть избыточным.

C++ предоставляет:

```cpp
#include <atomic>
```

Например:

```cpp
std::atomic<int> counter = 0;
```

Теперь:

```cpp
++counter;
```

выполняется атомарно относительно других потоков.

Это полезно для простых счётчиков и флагов.

---

## Когда использовать `atomic`

Хороший пример:

```cpp
std::atomic<bool> running = true;
```

Один поток может проверять:

```cpp
while (running) {
    // работа
}
```

Другой:

```cpp
running = false;
```

Это позволяет безопасно передавать простой сигнал между потоками.

Но `std::atomic` не заменяет mutex для сложных структур данных.

---

## Общий объект

Представим:

```cpp
struct SensorData {
    double temperature;
    double pressure;
};
```

И есть:

```cpp
SensorData data;
```

Если один поток изменяет:

```cpp
data.temperature
```

а другой одновременно читает весь объект, может потребоваться синхронизация.

Например:

```cpp
std::mutex dataMutex;
```

Запись:

```cpp
{
    std::lock_guard<std::mutex> lock(dataMutex);

    data.temperature = 25.3;
    data.pressure = 101.2;
}
```

Чтение:

```cpp
SensorData copy;

{
    std::lock_guard<std::mutex> lock(dataMutex);

    copy = data;
}
```

После этого можно обрабатывать `copy` без удержания mutex.

---

## Почему копирование иногда полезно

Представим:

```text
shared data
    ↓
mutex
    ↓
local copy
    ↓
долгая обработка
```

Мы быстро захватываем mutex, копируем данные и отпускаем блокировку.

После этого сложная обработка происходит отдельно.

Это часто значительно упрощает архитектуру.

---

## Deadlock

Mutex решает одну проблему, но может создать другую.

Представим два mutex:

```cpp
std::mutex a;
std::mutex b;
```

Поток A:

```text
захватил A
ждёт B
```

Поток B:

```text
захватил B
ждёт A
```

Получаем:

```text
Thread A → A → ждёт B
Thread B → B → ждёт A
```

Никто не может продолжить.

Это называется **deadlock** — взаимная блокировка.

---

## Как уменьшить риск deadlock

Один из способов — соблюдать единый порядок захвата mutex.

Например:

```text
всегда сначала A
потом B
```

Никогда:

```text
Thread A: A → B
Thread B: B → A
```

Другой вариант — использовать механизмы стандартной библиотеки для одновременного безопасного захвата нескольких mutex.

Например:

```cpp
std::scoped_lock lock(a, b);
```

---

## Потоки и завершение программы

Поток должен иметь понятный жизненный цикл.

Например:

```text
START
  ↓
RUNNING
  ↓
STOP REQUESTED
  ↓
FINISHED
```

Один из распространённых вариантов:

```cpp
std::atomic<bool> running = true;
```

Рабочий поток:

```cpp
while (running) {
    // работа
}
```

Основной поток:

```cpp
running = false;
worker.join();
```

Это простой и понятный способ остановки фонового потока.

---

## Пример мониторинга

Представим:

```cpp
std::atomic<bool> running = true;
std::mutex dataMutex;

SensorData data;
```

Рабочий поток:

```cpp
void sensorWorker() {
    while (running) {
        SensorData newData = readSensor();

        {
            std::lock_guard<std::mutex> lock(dataMutex);
            data = newData;
        }

        std::this_thread::sleep_for(
            std::chrono::milliseconds(100)
        );
    }
}
```

Основной поток может безопасно получать копию:

```cpp
SensorData getData() {
    std::lock_guard<std::mutex> lock(dataMutex);
    return data;
}
```

Здесь:

```text
atomic → управление жизненным циклом
mutex  → защита данных
thread → выполнение фоновой работы
```

---

## Очередь вместо общего состояния

Иногда лучше не давать потокам постоянно менять общий объект.

Можно использовать очередь сообщений:

```text
Sensor Thread
     ↓
   Queue
     ↓
Processing Thread
```

Например:

```text
Sensor Thread
    ↓
Measurement
    ↓
Queue
    ↓
Logger
```

Такой подход уменьшает количество прямых зависимостей между потоками.

Для более сложных систем это часто становится основой архитектуры.

---

## Многопоточность и GUI

GUI-приложения часто имеют специальный главный поток.

Например:

```text
GUI Thread
    ↓
интерфейс

Worker Thread
    ↓
долгая операция
```

Не всегда можно напрямую изменять элементы GUI из рабочего потока.

Конкретные правила зависят от GUI-фреймворка.

Например, Qt обычно использует механизм сигналов и событий для передачи данных между потоками.

Поэтому архитектура должна учитывать требования конкретного фреймворка.

---

## Многопоточность и производительность

Не каждая задача выигрывает от многопоточности.

Если работа очень маленькая:

```cpp
int result = a + b;
```

создавать отдельный поток бессмысленно.

Накладные расходы могут быть больше самой работы.

Многопоточность особенно полезна, когда есть:

* независимые длительные операции;
* ожидание ввода-вывода;
* большие вычисления;
* работа с несколькими источниками данных.

---

## Ошибочная идея: «сделаем всё отдельными потоками»

Например:

```text
поток логирования
поток файла
поток каждого датчика
поток каждого таймера
поток каждого запроса
поток каждой кнопки
```

Это быстро превращает программу в сложную систему.

Лучше сначала определить:

```text
какие задачи действительно независимы?
какие данные общие?
где нужны очереди?
где достаточно одного потока?
```

---

## Главное

Многопоточность позволяет нескольким задачам выполняться конкурентно.

Но общие данные требуют синхронизации.

Основные инструменты:

```text
std::thread
std::mutex
std::lock_guard
std::unique_lock
std::scoped_lock
std::atomic
```

Запомните главный принцип:

> Чем меньше общих изменяемых данных между потоками, тем проще многопоточная программа.
