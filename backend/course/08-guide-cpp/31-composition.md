# Композиция вместо наследования

## Цель

До этого мы рассмотрели наследование и полиморфизм. Теперь разберём другой важный способ строить классы — **композицию**.

После урока вы должны понимать:

* что такое композиция;
* чем композиция отличается от наследования;
* что означает отношение «имеет» и «является»;
* почему композиция часто делает архитектуру гибче;
* как один объект может содержать другие объекты;
* когда наследование действительно уместно.

---

## Два способа строить сложные объекты

Представим робота. У него есть двигатель, датчики, аккумулятор и контроллер.

Можно попытаться построить такую модель через наследование:

```cpp
class Robot : public Motor
{
};
```

Но здесь возникает странная логика. Получается, что `Robot` **является** `Motor`. Это не соответствует реальному отношению между объектами.

Робот не является двигателем. Робот **имеет двигатель**.

Для такого отношения гораздо естественнее использовать композицию:

```cpp
class Robot
{
private:
    Motor motor;
};
```

Теперь модель соответствует предметной области: объект `Robot` содержит объект `Motor`.

---

## «Является» и «имеет»

Это один из самых полезных способов предварительно оценить, нужно ли наследование.

Наследование обычно описывает отношение:

> A является B.

Например:

```text
LaserSensor является Sensor.
Camera является Sensor.
MotorDriver является Device.
```

Композиция обычно описывает отношение:

> A имеет B.

Например:

```text
Robot имеет Motor.
Robot имеет Camera.
Robot имеет Battery.
Robot имеет Controller.
```

Можно представить это так:

```text
Наследование:

        Device
          ↑
          |
        Robot


Композиция:

        Robot
       /  |  \
      /   |   \
   Motor Camera Battery
```

Это не математическое правило, которое всегда даёт единственный правильный ответ. Но такая проверка помогает увидеть ошибочное наследование ещё до написания кода.

---

## Простой пример композиции

Создадим двигатель:

```cpp
#include <iostream>

class Motor
{
public:
    void start()
    {
        std::cout << "Motor started\n";
    }

    void stop()
    {
        std::cout << "Motor stopped\n";
    }
};
```

Теперь создадим робота, который содержит двигатель:

```cpp
class Robot
{
private:
    Motor motor;

public:
    void start()
    {
        motor.start();
    }

    void stop()
    {
        motor.stop();
    }
};
```

Использование:

```cpp
int main()
{
    Robot robot;

    robot.start();
    robot.stop();

    return 0;
}
```

Здесь `Robot` использует функциональность `Motor`, но не становится разновидностью `Motor`.

---

## Объект внутри объекта

Композиция основана на обычном размещении объектов как полей другого объекта.

Например:

```cpp
class Battery
{
public:
    int getVoltage() const
    {
        return 24;
    }
};

class Robot
{
private:
    Battery battery;

public:
    void showVoltage() const
    {
        std::cout << battery.getVoltage() << " V\n";
    }
};
```

Объект `Robot` содержит объект `Battery`.

Когда создаётся:

```cpp
Robot robot;
```

внутри этого объекта существует его поле:

```cpp
battery
```

Если `Battery` является обычным полем, то его жизненный цикл связан с жизненным циклом `Robot`.

---

## Несколько компонентов

Реальные классы часто собираются из нескольких других объектов.

```cpp
class Motor
{
public:
    void start()
    {
        std::cout << "Motor started\n";
    }
};

class Camera
{
public:
    void capture()
    {
        std::cout << "Image captured\n";
    }
};

class Battery
{
public:
    int voltage() const
    {
        return 24;
    }
};

class Robot
{
private:
    Motor motor;
    Camera camera;
    Battery battery;

public:
    void start()
    {
        motor.start();
    }

    void inspect()
    {
        camera.capture();
    }

    void showPower() const
    {
        std::cout << battery.voltage() << " V\n";
    }
};
```

Теперь `Robot` представляет более сложную систему, собранную из специализированных компонентов.

Это очень распространённая архитектурная идея: вместо одного огромного класса программа состоит из небольших объектов, каждый из которых отвечает за свою часть работы.

---

## Почему это удобно

Представим, что у нас есть робот:

```text
Robot
 ├── Motor
 ├── Camera
 ├── Battery
 └── Controller
```

Каждый компонент можно разрабатывать отдельно.

Например, `Motor` отвечает за двигатель:

```cpp
class Motor
{
public:
    void setSpeed(int speed);
};
```

`Camera` отвечает за изображение:

```cpp
class Camera
{
public:
    void capture();
};
```

`Battery` отвечает за состояние питания:

```cpp
class Battery
{
public:
    int getCharge() const;
};
```

А `Robot` объединяет эти возможности:

```cpp
class Robot
{
private:
    Motor motor;
    Camera camera;
    Battery battery;
};
```

Такой код проще разделять на части и изменять независимо.

---

## Композиция уменьшает связанность

Представим, что мы сделали очень глубокую иерархию:

```text
Device
  ↓
Machine
  ↓
Robot
  ↓
MobileRobot
  ↓
WarehouseRobot
```

Со временем базовые классы начинают влиять на большое количество производных классов. Изменение одного места может привести к необходимости проверять множество других классов.

При композиции структура может быть другой:

```text
Robot
 ├── Motor
 ├── Battery
 ├── Camera
 └── Navigation
```

Компоненты можно изменять независимо.

Например, заменить камеру на другую:

```text
Robot
 ├── Motor
 ├── Battery
 ├── NewCamera
 └── Navigation
```

При этом сам `Robot` может практически не измениться.

---

## Композиция и замена компонентов

Особенно полезна композиция, когда компонент можно заменить.

Например:

```cpp
class Camera
{
public:
    void capture()
    {
        std::cout << "Standard camera\n";
    }
};

class Robot
{
private:
    Camera camera;

public:
    void inspect()
    {
        camera.capture();
    }
};
```

Можно сделать другой тип камеры:

```cpp
class ThermalCamera
{
public:
    void capture()
    {
        std::cout << "Thermal image\n";
    }
};
```

Однако здесь возникает проблема: `Robot` напрямую зависит от конкретного класса `Camera`.

Для более гибкой архитектуры можно использовать интерфейс.

---

## Композиция с интерфейсом

Создадим общий интерфейс камеры:

```cpp
class ICamera
{
public:
    virtual ~ICamera() = default;

    virtual void capture() = 0;
};
```

Теперь создадим две реализации:

```cpp
class Camera : public ICamera
{
public:
    void capture() override
    {
        std::cout << "Standard camera\n";
    }
};
```

И:

```cpp
class ThermalCamera : public ICamera
{
public:
    void capture() override
    {
        std::cout << "Thermal camera\n";
    }
};
```

Робот может хранить ссылку или указатель на интерфейс:

```cpp
class Robot
{
private:
    ICamera& camera;

public:
    Robot(ICamera& camera)
        : camera(camera)
    {
    }

    void inspect()
    {
        camera.capture();
    }
};
```

Теперь выбор камеры можно сделать снаружи:

```cpp
int main()
{
    ThermalCamera camera;

    Robot robot(camera);

    robot.inspect();

    return 0;
}
```

В результате робот не обязан знать конкретный класс камеры. Ему достаточно знать, что объект умеет выполнять `capture()`.

---

## Композиция и внедрение зависимостей

В предыдущем примере камера передаётся роботу через конструктор:

```cpp
Robot robot(camera);
```

Это называется **внедрением зависимости**, или dependency injection.

Робот получает необходимый компонент извне вместо того, чтобы создавать его самостоятельно.

Например, такой вариант:

```cpp
class Robot
{
private:
    Camera camera;

public:
    Robot()
    {
    }
};
```

сильно связывает `Robot` с конкретной реализацией `Camera`.

А такой вариант:

```cpp
class Robot
{
private:
    ICamera& camera;

public:
    Robot(ICamera& camera)
        : camera(camera)
    {
    }
};
```

делает зависимость явной и позволяет подставить разные реализации.

---

## Композиция против наследования

Рассмотрим две модели.

### Наследование

```cpp
class Robot : public Device
{
};
```

Здесь `Robot` является `Device`.

### Композиция

```cpp
class Robot
{
private:
    Device device;
};
```

Здесь `Robot` имеет `Device`.

Это разные отношения.

Если объект действительно является специализированной разновидностью другого объекта, наследование может быть естественным:

```text
Sensor
  ↑
CameraSensor
```

Если объект состоит из компонентов, композиция обычно лучше отражает структуру:

```text
Robot
 ├── Sensor
 ├── Motor
 └── Battery
```

---

## Композиция не означает отсутствие наследования

Не нужно воспринимать это как правило «наследование плохо, композиция хорошо».

Оба подхода нужны.

Например, у нас действительно может существовать иерархия:

```text
Sensor
 ├── CameraSensor
 └── DistanceSensor
```

А внутри `Robot` могут находиться различные сенсоры:

```text
Robot
 ├── CameraSensor
 ├── DistanceSensor
 └── Motor
```

Получается комбинация:

```text
         Sensor
        /      \
 CameraSensor  DistanceSensor

             Robot
          /    |    \
         /     |     \
 CameraSensor  DistanceSensor  Motor
```

Это обычная ситуация в реальных программах.

---

## Композиция и повторное использование

Одна из главных причин использовать композицию — возможность повторно использовать готовые компоненты.

Например:

```cpp
class Logger
{
public:
    void log(const std::string& message)
    {
        std::cout << message << '\n';
    }
};
```

Теперь этот компонент можно использовать в нескольких классах:

```cpp
class Robot
{
private:
    Logger logger;
};
```

И:

```cpp
class Controller
{
private:
    Logger logger;
};
```

`Logger` не обязан быть базовым классом для этих объектов. Он просто предоставляет нужную возможность.

---

## Композиция позволяет собирать поведение

Представим систему:

```text
Robot
 ├── Navigation
 ├── MotorController
 ├── BatteryMonitor
 ├── Camera
 └── Logger
```

Каждый объект решает свою задачу.

`Robot` становится координатором:

```cpp
class Robot
{
private:
    Navigation navigation;
    MotorController motors;
    BatteryMonitor battery;
    Camera camera;
    Logger logger;
};
```

Такую архитектуру гораздо проще расширять, чем класс, содержащий тысячи строк и десятки несвязанных обязанностей.

---

## Когда стоит подумать о композиции

Композиция особенно полезна, когда:

* объект содержит несколько независимых компонентов;
* компонент может быть заменён;
* функциональность должна использоваться в разных классах;
* наследование создаёт искусственную иерархию;
* нужно уменьшить связанность между классами;
* объект должен получать зависимости извне.

Хороший вопрос перед использованием наследования:

> Действительно ли один объект является разновидностью другого?

Если ответ отрицательный, стоит рассмотреть композицию.

---

## Практический пример

Создадим простой контроллер двигателя:

```cpp
class MotorController
{
private:
    int speed = 0;

public:
    void setSpeed(int newSpeed)
    {
        speed = newSpeed;
    }

    int getSpeed() const
    {
        return speed;
    }
};
```

Теперь робот содержит контроллер:

```cpp
class Robot
{
private:
    MotorController motorController;

public:
    void move(int speed)
    {
        motorController.setSpeed(speed);

        std::cout << "Robot speed: "
                  << motorController.getSpeed()
                  << '\n';
    }
};
```

Использование:

```cpp
int main()
{
    Robot robot;

    robot.move(50);
    robot.move(100);

    return 0;
}
```

`Robot` не должен знать внутреннее устройство `MotorController`. Он использует его публичный интерфейс.

---

## Главное

Композиция позволяет строить сложные объекты из более простых.

Главное различие можно запомнить так:

```text
Наследование:
"A является B"

Композиция:
"A имеет B"
```

Наследование полезно для моделирования настоящей иерархии типов и полиморфизма. Композиция полезна для сборки объектов из компонентов и часто позволяет сделать архитектуру более гибкой.

В реальных системах оба подхода обычно используются вместе. Хороший объектно-ориентированный дизайн не заключается в полном отказе от наследования, а в выборе подходящего отношения между объектами.

## Что нужно запомнить

* Композиция означает построение объекта из других объектов.
* Она обычно описывает отношение «имеет».
* Наследование обычно описывает отношение «является».
* Компоненты можно переиспользовать в разных классах.
* Композиция помогает уменьшать связанность.
* Зависимости можно передавать через конструктор.
* Композиция и наследование не исключают друг друга.
* Перед использованием наследования полезно проверить, действительно ли между типами существует отношение «является».
