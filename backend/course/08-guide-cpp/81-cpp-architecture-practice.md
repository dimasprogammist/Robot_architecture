# Архитектура C++ приложения

## Цель

Финальный проект показал, как собрать несколько компонентов в одну программу. Теперь сделаем следующий шаг: научимся сознательно проектировать структуру приложения до написания большого количества кода.

В небольших программах можно написать всё в `main.cpp`.

Но по мере роста проекта такой подход становится неудобным:

```text
main.cpp
 ├── работа с файлами
 ├── сеть
 ├── устройства
 ├── логирование
 ├── настройки
 ├── бизнес-логика
 └── пользовательский интерфейс
```

В результате один файл превращается в огромный набор несвязанных обязанностей.

---

## Ответственность компонента

Хороший компонент должен иметь понятную задачу.

Например:

```text
Config
    отвечает за конфигурацию

Logger
    отвечает за журнал

Device
    отвечает за состояние устройства

DeviceManager
    отвечает за коллекцию устройств

Monitor
    отвечает за мониторинг
```

Если класс одновременно:

* читает JSON;
* открывает TCP-соединение;
* выводит меню;
* управляет потоками;

то его становится сложно изменять и тестировать.

---

## Разделение слоёв

Один из возможных вариантов:

```text
┌──────────────────────────┐
│       User Interface     │
├──────────────────────────┤
│       Application        │
├──────────────────────────┤
│       Domain             │
├──────────────────────────┤
│ Infrastructure           │
├──────────────────────────┤
│ Operating System / HW    │
└──────────────────────────┘
```

Например:

```text
UI
 ↓
MonitorService
 ↓
Device
 ↓
ModbusClient
 ↓
Network
 ↓
PLC
```

Каждый уровень знает только необходимую ему информацию.

## Интерфейс

Допустим, программа должна читать датчик.

Необязательно заставлять монитор знать, как именно подключён датчик.

Создадим интерфейс:

```cpp
class ISensor
{
public:
    virtual ~ISensor() = default;

    virtual double read() = 0;
};
```

Теперь можно создать реальный датчик:

```cpp
class TemperatureSensor : public ISensor
{
public:
    double read() override
    {
        return 42.5;
    }
};
```

И тестовый:

```cpp
class FakeSensor : public ISensor
{
public:
    double read() override
    {
        return 25.0;
    }
};
```

Монитор может работать с обоими.

---

## Почему это полезно

Без абстракции:

```text
Monitor
   ↓
TemperatureSensor
   ↓
Hardware
```

С абстракцией:

```text
             ┌── TemperatureSensor
             │
Monitor → ISensor
             │
             └── FakeSensor
```

Теперь монитор не зависит от конкретного устройства.

Это особенно полезно для тестирования.

---

## Зависимости

Если класс сам создаёт все свои зависимости:

```cpp
class Monitor
{
public:
    Monitor()
    {
        sensor_ = std::make_unique<TemperatureSensor>();
        logger_ = std::make_unique<FileLogger>();
    }
};
```

такой класс становится сильно связанным с конкретными реализациями.

Лучше передавать зависимости извне:

```cpp
class Monitor
{
public:
    Monitor(
        ISensor& sensor,
        ILogger& logger
    )
        : sensor_(sensor),
          logger_(logger)
    {
    }

private:
    ISensor& sensor_;
    ILogger& logger_;
};
```

Теперь можно передать разные реализации.

---

## Dependency Injection

Этот подход называется Dependency Injection — внедрение зависимостей.

Например:

```cpp
TemperatureSensor sensor;
FileLogger logger;

Monitor monitor(sensor, logger);
```

Для теста:

```cpp
FakeSensor sensor;
TestLogger logger;

Monitor monitor(sensor, logger);
```

Основной код монитора при этом не меняется.

## Практическая структура

Для проекта мониторинга можно использовать:

```text
include/
├── domain/
│   ├── Device.h
│   └── Measurement.h
│
├── application/
│   └── MonitorService.h
│
└── infrastructure/
    ├── FileLogger.h
    └── TcpClient.h

src/
├── domain/
├── application/
├── infrastructure/
└── main.cpp
```

Это не единственно правильная структура.

Архитектура должна соответствовать масштабу проекта.

---

## Главное правило

Не нужно создавать десять классов только потому, что это возможно.

Если программа состоит из 100 строк, сложная архитектура может только мешать.

Но если приложение содержит:

```text
20 000 строк
```

и в одном файле находятся:

```text
сеть
БД
логирование
GUI
устройства
настройки
потоки
```

архитектурное разделение становится необходимым.

---

## Практическое задание

Переделайте финальный проект:

```text
Device Monitor
```

так, чтобы:

1. устройство не знало о консоли;
2. монитор не знал о конкретном способе получения данных;
3. логгер можно было заменить;
4. конфигурацию можно было заменить;
5. тестовые устройства можно было использовать без реального оборудования.

Попробуйте добиться схемы:

```text
main
 ↓
application
 ↓
interfaces
 ↓
implementations
```

Это один из важных шагов от учебного C++ к разработке реальных систем.
