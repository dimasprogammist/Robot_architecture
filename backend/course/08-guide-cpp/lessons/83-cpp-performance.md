# Производительность C++ программ

## Цель

C++ часто выбирают там, где важна производительность:

* робототехника;
* обработка изображений;
* серверы;
* игровые движки;
* системы управления;
* промышленное оборудование;
* встроенные системы.

Но высокая производительность не появляется автоматически только из-за использования C++.

Важно понимать, где программа действительно тратит время и память.

---

## Не оптимизируйте вслепую

Предположим, программа выполняется:

```text
100 ms
```

и мы переписали небольшой участок, который занимает:

```text
1 ms
```

Даже если сделать этот участок в два раза быстрее:

```text
1 ms → 0.5 ms
```

общая программа почти не изменится:

```text
100 ms → 99.5 ms
```

Поэтому сначала нужно определить узкое место.

---

## Профилирование

Профилировщик показывает, где программа проводит время.

Условно:

```text
Function                 Time

readSensor()             5%
calculate()             10%
processData()           15%
databaseQuery()         60%
logging()               10%
```

В таком случае оптимизация `calculate()` почти не повлияет на общую скорость.

Основная проблема находится в:

```text
databaseQuery()
```

---

## Алгоритмы важнее мелких оптимизаций

Представим поиск элемента в `vector`:

```cpp
for (const auto& device : devices)
{
    if (device.id() == id)
    {
        return &device;
    }
}
```

Для `N` элементов в худшем случае нужно проверить:

```text
N
```

элементов.

Сложность:

```text
O(N)
```

Если элементов:

```text
10
```

это почти незаметно.

Если:

```text
10 000 000
```

разница становится существенной.

---

## Правильная структура данных

Если часто требуется поиск по ID, может подойти:

```cpp
std::unordered_map<int, Device>
```

Вместо:

```cpp
std::vector<Device>
```

Тогда операция поиска в среднем может быть близка к:

```text
O(1)
```

вместо:

```text
O(N)
```

Но это не означает, что `unordered_map` всегда быстрее.

Выбор структуры данных зависит от:

* размера данных;
* характера доступа;
* количества вставок;
* количества удалений;
* требований к порядку;
* использования памяти.

---

## Копирование объектов

Рассмотрим:

```cpp
void process(std::string text)
{
}
```

При вызове:

```cpp
std::string message = "hello";

process(message);
```

создаётся копия строки.

Если копировать не нужно:

```cpp
void process(const std::string& text)
{
}
```

теперь функция получает ссылку.

Но не нужно превращать каждую функцию в:

```cpp
const T&
```

без понимания владения и времени жизни объекта.

Иногда передача по значению является правильным вариантом.

---

## Move semantics

Если объект больше не нужен в исходном месте, можно передать его содержимое перемещением:

```cpp
std::string message = "large message";

std::string copy = std::move(message);
```

После перемещения состояние `message` остаётся корректным, но его содержимое не следует считать прежним.

Move semantics особенно полезен для объектов, владеющих ресурсами.

---

## Reserve

Рассмотрим:

```cpp
std::vector<int> values;

for (int i = 0; i < 1'000'000; ++i)
{
    values.push_back(i);
}
```

В процессе роста `vector` ему может потребоваться несколько раз перераспределять память.

Если размер примерно известен заранее:

```cpp
std::vector<int> values;

values.reserve(1'000'000);

for (int i = 0; i < 1'000'000; ++i)
{
    values.push_back(i);
}
```

может потребоваться меньше перераспределений.

Но `reserve` не является универсальной оптимизацией.

---

## Память и cache locality

Современный процессор работает не только с RAM.

Внутри процессора существуют быстрые уровни кэш-памяти:

```text
CPU
 ↓
L1 cache
 ↓
L2 cache
 ↓
L3 cache
 ↓
RAM
```

Поэтому последовательный доступ к данным часто оказывается эффективным.

Например:

```cpp
std::vector<int> values;

for (int value : values)
{
    process(value);
}
```

обычно имеет хорошую локальность доступа.

---

## Почему структура данных влияет на скорость

Два алгоритма могут выполнять одинаковое количество логических операций, но работать с памятью совершенно по-разному.

Например:

```text
vector
████████████████████

linked list
█     █     █     █
```

Элементы `vector` расположены последовательно.

У узлов связного списка элементы могут находиться в разных местах памяти.

Процессору проще эффективно обрабатывать последовательные данные.

Поэтому выбор структуры данных влияет не только на Big O, но и на реальное время выполнения.

---

## Лишние аллокации

Следует внимательно относиться к созданию большого количества временных объектов.

Например:

```cpp
for (int i = 0; i < 1'000'000; ++i)
{
    std::string text = createMessage(i);

    process(text);
}
```

Не всегда это проблема.

Но если профилировщик показывает, что программа тратит много времени на выделение памяти, можно исследовать:

* повторное использование буферов;
* `reserve`;
* перемещение;
* структуру данных;
* жизненный цикл объектов.

Оптимизация должна основываться на измерениях.

---

## Производительность потоков

Многопоточность не означает автоматически:

```text
2 потока = в 2 раза быстрее
```

Если два потока постоянно ждут один mutex:

```text
Thread 1 ──┐
           ↓
         mutex
           ↑
Thread 2 ──┘
```

часть параллелизма теряется.

Ещё хуже, если работа распределена между потоками так, что они постоянно передают данные друг другу.

Поэтому количество потоков должно соответствовать задаче.

---

## Производительность в системах управления

В промышленной системе может быть цикл:

```text
read inputs
     ↓
calculate
     ↓
control
     ↓
write outputs
     ↓
wait
```

Например:

```text
10 ms cycle
```

Тогда программа должна укладываться в заданные временные ограничения.

Но важно различать:

```text
среднее время
```

и:

```text
максимальное время выполнения
```

Для систем управления иногда критично именно второе.

---

## Не жертвуйте надёжностью ради скорости

Предположим, можно сделать код немного быстрее, используя сложную ручную оптимизацию.

Но если в результате появляются:

* гонки;
* ошибки памяти;
* undefined behavior;
* трудно поддерживаемый код;

это может быть плохим обменом.

В инженерном коде обычно важны одновременно:

```text
Корректность
Надёжность
Поддерживаемость
Производительность
```

Оптимизация не должна разрушать первые три пункта без серьёзной причины.

---

## Правильный порядок оптимизации

Хороший практический процесс:

```text
1. Сделать корректно
       ↓
2. Написать тесты
       ↓
3. Измерить производительность
       ↓
4. Найти узкое место
       ↓
5. Изменить код
       ↓
6. Снова измерить
       ↓
7. Проверить тесты
```

Не стоит начинать с:

```text
"Наверное, vector медленный"
```

или:

```text
"Нужно добавить больше потоков"
```

Сначала нужны данные.

## Практическое задание

Возьмите программу:

```text
Device Monitor
```

и добавьте измерение времени выполнения.

Например:

```cpp
#include <chrono>
#include <iostream>

auto start = std::chrono::steady_clock::now();

// операция

auto end = std::chrono::steady_clock::now();

auto duration =
    std::chrono::duration_cast<
        std::chrono::microseconds
    >(end - start);

std::cout
    << "Time: "
    << duration.count()
    << " us\n";
```

Измерьте:

* поиск устройства;
* обработку 1 000 значений;
* обработку 100 000 значений;
* запись большого количества данных.

Затем попробуйте изменить структуру данных и сравнить результаты.

---

## Главное

Производительность — это не набор магических оптимизаций.

Хороший C++ разработчик умеет ответить:

```text
Где программа тратит время?
Почему она там его тратит?
Как это измерить?
Что изменится после оптимизации?
Не сломалась ли корректность?
```

Сначала создаётся правильная программа.

Затем она измеряется.

И только после этого оптимизируются действительно важные места.
