# Ошибки времени выполнения

## Цель

До этого мы разбирались с ошибками компиляции: программа не запускается, потому что компилятор не смог превратить исходный код в исполняемую программу.

Но существует другой класс проблем: программа успешно компилируется и запускается, а затем во время работы делает что-то неправильное. Такие проблемы называют **ошибками времени выполнения**.

После урока вы должны понимать:

* чем ошибки компиляции отличаются от ошибок времени выполнения;
* почему программа может успешно собраться, но завершиться с ошибкой;
* что такое аварийное завершение программы;
* какие ошибки возникают при работе с памятью;
* почему выход за границы массива особенно опасен;
* чем ошибка программы отличается от обычной ошибки входных данных или внешнего ресурса;
* как искать причину ошибки времени выполнения.

---

## Три разных этапа возникновения ошибок

Упрощённо жизнь C++ программы можно представить так:

```text
Исходный код
    ↓
Компиляция
    ↓
Компоновка
    ↓
Запуск программы
    ↓
Выполнение
```

На каждом этапе могут возникнуть свои проблемы.

Например, если написать:

```cpp
int value = ;
```

компилятор не сможет разобрать программу.

Если исходный код компилируется, но программа использует функцию из библиотеки, которой нет при компоновке, может возникнуть ошибка линковки.

А если программа успешно собралась и запустилась, но затем попыталась обратиться к недопустимой области памяти, проблема возникает уже **во время выполнения**.

---

## Простейший пример

Рассмотрим программу:

```cpp
#include <iostream>

int main() {
    int a = 10;
    int b = 0;

    int result = a / b;

    std::cout << result << '\n';
}
```

Синтаксически программа корректна. Компилятор может её принять.

Но во время выполнения происходит деление целого числа на ноль. Результат не является допустимым для обычного целочисленного деления.

На конкретной системе программа может завершиться аварийно.

Главная мысль:

> Успешная компиляция не означает, что программа логически безопасна.

---

## Ошибки памяти

Один из самых опасных классов ошибок времени выполнения связан с памятью.

Например:

```cpp
#include <iostream>

int main() {
    int values[3] = {10, 20, 30};

    std::cout << values[10] << '\n';
}
```

Массив содержит только три элемента:

```text
values[0]
values[1]
values[2]
```

Но программа пытается получить:

```text
values[10]
```

Это выход за границы массива.

В C++ такой код может скомпилироваться. Проблема возникает при выполнении.

При этом программа не обязана сразу завершиться. Она может:

* упасть;
* вывести случайное значение;
* изменить чужие данные;
* продолжить работу и сломаться значительно позже.

Поэтому ошибки памяти особенно неприятны.

---

## Null pointer

Рассмотрим указатель:

```cpp
int* value = nullptr;
```

Он не указывает на объект `int`.

Если попытаться разыменовать его:

```cpp
std::cout << *value << '\n';
```

программа пытается обратиться к объекту, которого нет.

Это типичный пример ошибки работы с памятью.

Именно поэтому проверка указателей перед использованием иногда необходима:

```cpp
int* value = nullptr;

if (value != nullptr) {
    std::cout << *value << '\n';
}
```

В современном C++ ещё лучше проектировать программу так, чтобы владение объектами и возможность отсутствия объекта были выражены подходящими типами.

---

## Обращение к освобождённой памяти

Рассмотрим:

```cpp
int* value = new int(42);

delete value;

std::cout << *value << '\n';
```

После:

```cpp
delete value;
```

объект больше не существует.

Указатель `value` при этом всё ещё содержит старый адрес.

Он становится **висячим указателем**.

Использование такого указателя может привести к непредсказуемому поведению.

После ручного освобождения памяти указатель иногда обнуляют:

```cpp
delete value;
value = nullptr;
```

Но это не решает проблему владения в целом. Именно поэтому современный C++ старается использовать RAII и умные указатели.

---

## Выход за границы контейнера

Рассмотрим `std::vector`:

```cpp
#include <iostream>
#include <vector>

int main() {
    std::vector<int> values = {10, 20, 30};

    std::cout << values[100] << '\n';
}
```

Оператор `[]` не выполняет проверку границ.

Для учебных и диагностических целей можно использовать `at()`:

```cpp
std::cout << values.at(100) << '\n';
```

В этом случае `std::vector` обнаруживает недопустимый индекс и сообщает об ошибке через исключение.

Это важное отличие:

```cpp
values[index];
```

и:

```cpp
values.at(index);
```

не являются полностью эквивалентными операциями.

---

## Ошибка может быть не в коде

Не каждая проблема во время работы программы означает ошибку алгоритма.

Например, программа читает конфигурационный файл:

```cpp
#include <fstream>

int main() {
    std::ifstream file("config.txt");

    if (!file) {
        // Файл не удалось открыть.
    }
}
```

Файл может отсутствовать.

Это не обязательно ошибка C++ программы. Это может быть нормальная ситуация, которую программа должна корректно обработать.

То же самое относится к:

* отсутствию сетевого соединения;
* недоступному серверу;
* неправильному пути к файлу;
* неверному вводу пользователя;
* отключённому устройству;
* отсутствию разрешений;
* недоступному USB-устройству.

Хорошая программа должна отличать ожидаемые внешние проблемы от собственных ошибок.

---

## Аварийное завершение

Когда программа сталкивается с проблемой, которую она не может корректно обработать, она может завершиться аварийно.

Например:

```text
Segmentation fault
```

или на Windows может появиться сообщение о том, что приложение перестало работать.

Само сообщение обычно говорит только о месте или типе сбоя. Оно не всегда объясняет настоящую причину.

Например, ошибка может проявиться в строке:

```cpp
result = calculate(value);
```

но настоящая причина могла появиться значительно раньше.

---

## Ошибка и Undefined Behavior

Некоторые ошибки времени выполнения относятся к **Undefined Behavior**, или неопределённому поведению.

Например:

```cpp
int values[3] = {1, 2, 3};

std::cout << values[10] << '\n';
```

Это не означает:

> «Программа гарантированно завершится с ошибкой».

Это означает, что стандарт C++ не определяет, что программа должна делать в такой ситуации.

Компилятор не обязан сохранять какое-то конкретное поведение.

Подробно неопределённое поведение мы разберём в следующем уроке.

---

## Проверка входных данных

Многие проблемы можно предотвратить ещё до выполнения опасной операции.

Например:

```cpp
#include <iostream>

int main() {
    int index;

    std::cin >> index;

    if (index < 0 || index >= 5) {
        std::cout << "Invalid index\n";
        return 1;
    }

    std::cout << "Index is valid\n";
}
```

Здесь программа сначала проверяет данные, а затем использует их.

Такой принцип встречается повсюду:

```text
получить данные
    ↓
проверить
    ↓
использовать
```

а не:

```text
получить данные
    ↓
использовать
    ↓
разбираться с последствиями
```

---

## Ошибки в программах автоматизации

Представим программу управления роботом.

Она получает номер двигателя:

```cpp
int motor_index;
std::cin >> motor_index;
```

Затем использует его для обращения к массиву:

```cpp
Motor motors[6];

motors[motor_index].start();
```

Если пользователь передаст:

```text
100
```

программа попытается обратиться к элементу, которого нет.

Без проверки это потенциально опасная ошибка.

Правильнее:

```cpp
if (motor_index < 0 || motor_index >= 6) {
    std::cout << "Invalid motor number\n";
    return 1;
}

motors[motor_index].start();
```

В реальной системе проверки должны быть ещё строже, а критические операции управления оборудованием должны иметь дополнительные уровни защиты.

---

## Как искать ошибку времени выполнения

Если программа падает, полезно действовать последовательно.

### 1. Найдите момент сбоя

Определите:

```text
что произошло?
```

Например:

```text
Программа запускается.
Показывает список устройств.
После нажатия кнопки "Запуск" падает.
```

Это уже сильно сужает область поиска.

### 2. Проверьте последние данные

Например:

```text
device_id = 15
motor_count = 6
```

Если программа затем обращается к:

```cpp
motors[device_id]
```

проблема становится очевидной.

### 3. Используйте отладчик

Поставьте breakpoint перед подозрительной операцией.

Проверьте:

* значения переменных;
* указатели;
* размеры контейнеров;
* индексы;
* состояние объектов;
* стек вызовов.

### 4. Уменьшите пример

Если большая программа падает, попробуйте найти минимальный участок кода, который воспроизводит проблему.

Это часто гораздо эффективнее, чем просматривать весь проект.

---

## Логирование

Отладчик полезен во время разработки, но в работающей системе часто требуется журналирование.

Например:

```cpp
std::cout << "Connecting to controller...\n";
```

или:

```cpp
std::cout << "Motor index: " << motor_index << '\n';
```

Для реального приложения обычно используют полноценную систему логирования.

Важно не превращать программу в поток случайных сообщений. Хороший лог должен помогать восстановить последовательность событий.

---

## Практический пример

Допустим, есть простой контроллер устройств:

```cpp
#include <iostream>
#include <vector>

struct Device {
    std::string name;
    bool online;
};

int main() {
    std::vector<Device> devices = {
        {"Motor A", true},
        {"Motor B", false},
        {"Sensor A", true}
    };

    int index;

    std::cout << "Device number: ";
    std::cin >> index;

    if (index < 0 || index >= static_cast<int>(devices.size())) {
        std::cout << "Invalid device number\n";
        return 1;
    }

    const Device& device = devices[index];

    std::cout << device.name << '\n';

    if (!device.online) {
        std::cout << "Device is offline\n";
        return 1;
    }

    std::cout << "Device is ready\n";
}
```

Здесь программа отдельно проверяет две разные ситуации.

Первая:

```cpp
index < 0 || index >= devices.size()
```

означает неправильный индекс.

Вторая:

```cpp
!device.online
```

означает, что устройство существует, но сейчас недоступно.

Это разные проблемы и программа должна различать их.

---

## Главное

Ошибка времени выполнения возникает уже после того, как программа была успешно скомпилирована и запущена.

Она может быть связана с:

* неправильными входными данными;
* обращением к памяти;
* недопустимым индексом;
* указателями;
* отсутствующими файлами;
* сетевыми проблемами;
* состоянием внешних устройств;
* логической ошибкой программы.

Особенно опасны ошибки памяти и неопределённое поведение: программа может не упасть сразу, а продолжить работу с повреждённым состоянием.

Поэтому хороший C++ код не просто «работает на правильных данных». Он заранее проверяет границы, состояния и внешние ресурсы.

## Практика

### Задание 1

Создайте программу с массивом из пяти чисел.

Пользователь должен ввести индекс, после чего программа выводит элемент.

Сделайте проверку индекса.

### Задание 2

Создайте `std::vector<int>`.

Попросите пользователя ввести индекс и попробуйте реализовать два варианта:

```cpp
values[index]
```

и:

```cpp
values.at(index)
```

Сравните их поведение при неправильном индексе.

### Задание 3

Создайте структуру:

```cpp
struct Motor {
    std::string name;
    bool enabled;
};
```

Создайте несколько двигателей и программу, которая получает номер двигателя.

Проверьте:

* существует ли такой двигатель;
* разрешён ли его запуск.

### Задание 4

Создайте программу, которая читает имя конфигурационного файла.

Если файл не удалось открыть, программа должна вывести понятное сообщение и корректно завершиться.

### Задание 5

Найдите в небольшой программе место, где потенциально может произойти ошибка времени выполнения.

Добавьте проверки и объясните, какую именно проблему они предотвращают.
