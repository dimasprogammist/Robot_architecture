# Почему ручное управление памятью опасно

## Цель

Мы уже разобрали указатели, динамическую память, `new` и `delete`. Теперь важно понять не только то, как эти механизмы работают, но и почему их неправильное использование является одним из главных источников сложных ошибок в C++.

Проблемы с памятью часто не проявляются сразу. Программа может работать несколько минут или часов, а затем внезапно завершиться, повредить данные или начать вести себя непредсказуемо.

После урока вы должны понимать:

* что такое утечка памяти;
* что такое use-after-free;
* что такое double free;
* почему опасен висячий указатель;
* что такое переполнение буфера;
* почему владение памятью должно быть однозначным;
* как RAII помогает решать эти проблемы;
* почему современный C++ старается минимизировать ручное управление памятью.

---

## Почему ошибки памяти сложны

Обычная логическая ошибка часто выглядит очевидно:

```cpp
int result = 10 / 0;
```

Но ошибка управления памятью может быть гораздо менее предсказуемой.

Например:

```cpp
int* pointer = new int(10);

delete pointer;

std::cout << *pointer;
```

Иногда программа может сразу завершиться с ошибкой.

Иногда может вывести какое-то значение.

Иногда код может продолжить работать, а ошибка проявится значительно позже.

Такое поведение связано с неопределённым поведением программы.

---

## Утечка памяти

Утечка возникает, когда программа выделила память, но потеряла возможность её освободить.

Пример:

```cpp
void createData()
{
    int* data = new int[100];
}
```

После выхода из функции переменная:

```cpp
data
```

исчезает.

Но память, выделенная через:

```cpp
new int[100]
```

остаётся занятой.

Адрес потерян.

---

## Как возникает утечка

Рассмотрим:

```cpp
int* data = new int[100];

data = new int[200];
```

Что произошло?

Сначала была выделена память на 100 элементов.

Затем указателю присвоили адрес новой области.

Старый адрес был потерян:

```text
первая память
   ↑
старый адрес потерян

data
 ↓
вторая память
```

Освободить первую область теперь невозможно через этот указатель.

Получилась утечка.

---

## Утечки в долгоживущих программах

Для короткой программы одна небольшая утечка может остаться незаметной.

Но представим сервер:

```text
программа запущена
↓
обработка запроса
↓
выделение памяти
↓
утечка
↓
следующий запрос
↓
ещё одна утечка
↓
...
```

Если программа работает несколько дней, потребление памяти может постепенно увеличиваться.

Поэтому утечки особенно опасны в:

* серверах;
* промышленных приложениях;
* роботах;
* GUI-программах;
* системах мониторинга;
* фоновых службах.

---

## Use-after-free

Очень опасная ошибка — использование объекта после освобождения памяти.

Например:

```cpp
int* value = new int(100);

delete value;

std::cout << *value;
```

После:

```cpp
delete value;
```

объект больше не существует.

Разыменование:

```cpp
*value
```

обращается к уже освобождённой памяти.

Это называется use-after-free.

---

## Почему use-after-free опасен

Память после освобождения может быть повторно использована программой.

Например:

```text
объект A
↓
память освобождена
↓
эта же память выдана объекту B
```

Если старый указатель продолжит использоваться, он может фактически обращаться к данным другого объекта.

Получается очень сложная ошибка:

```text
старый указатель
      ↓
память уже используется другим объектом
```

Результат может зависеть от времени, порядка операций и состояния программы.

---

## Висячий указатель

Указатель после уничтожения объекта называют висячим указателем.

Пример:

```cpp
int* pointer = new int(10);

delete pointer;
```

После `delete`:

```text
pointer → старый адрес
```

но объекта там уже нет.

Можно уменьшить риск случайного повторного использования:

```cpp
delete pointer;
pointer = nullptr;
```

Теперь состояние указателя явно показывает:

```text
pointer → ничего
```

Но обнуление указателя не решает проблему, если существуют другие указатели на тот же объект.

---

## Двойное освобождение

Рассмотрим:

```cpp
int* pointer = new int(10);

delete pointer;
delete pointer;
```

Первая операция уничтожает объект.

Вторая пытается повторно освободить ту же память.

Это называется double free или двойное освобождение.

Такая ошибка может привести к:

* аварийному завершению;
* повреждению памяти;
* неопределённому поведению.

---

## Несколько владельцев

Особенно опасна ситуация, когда несколько частей программы считают себя владельцами одного объекта.

Например:

```cpp
int* first = new int(10);

int* second = first;
```

Теперь:

```text
first  ─┐
        ├──> один объект
second ─┘
```

Кто должен вызвать:

```cpp
delete
```

Если `first` удалит объект:

```cpp
delete first;
```

`second` станет висячим.

Если потом:

```cpp
delete second;
```

возникнет двойное освобождение.

Проблема здесь не в самом указателе. Проблема в том, что непонятно, кто владеет объектом.

---

## Владение

При работе с динамической памятью нужно уметь ответить на вопрос:

> Кто отвечает за время жизни этого объекта?

Например:

```text
Controller владеет Robot
```

означает, что `Controller` отвечает за создание и уничтожение `Robot`.

Если это правило не определено, разные части программы могут начать управлять одним ресурсом независимо друг от друга.

В больших проектах такая ситуация быстро становится сложной.

---

## Переполнение буфера

Ошибки памяти возникают не только из-за `delete`.

Опасна и запись за пределы массива:

```cpp
int values[3];

values[0] = 10;
values[1] = 20;
values[2] = 30;
values[3] = 40;
```

Последняя запись находится за пределами массива.

Программа записывает данные туда, где их быть не должно.

В зависимости от ситуации это может повредить другие данные программы.

---

## Чтение за пределами массива

Та же проблема возникает при чтении:

```cpp
int values[3] = {10, 20, 30};

std::cout << values[10];
```

Программа пытается прочитать данные за пределами массива.

Результат не определён.

Поэтому любые циклы, работающие с массивами, должны правильно контролировать границы.

---

## Указатели не проверяют границы

Рассмотрим:

```cpp
int values[3] = {10, 20, 30};

int* pointer = values;

std::cout << *(pointer + 10);
```

Компилятор не обязан автоматически остановить такую ошибку.

Указатель просто содержит адрес и тип.

Ответственность за корректность обращения лежит на программисте.

Именно поэтому низкоуровневые механизмы C++ требуют дисциплины.

---

## Исключения

Ручное управление памятью становится ещё сложнее при использовании исключений.

Например:

```cpp
void process()
{
    int* data = new int[100];

    riskyOperation();

    delete[] data;
}
```

Если:

```cpp
riskyOperation();
```

выбросит исключение, программа может не дойти до:

```cpp
delete[] data;
```

Память останется занятой.

Чтобы вручную обработать такую ситуацию, пришлось бы писать дополнительную логику:

```cpp
try
{
    riskyOperation();
}
catch (...)
{
    delete[] data;
    throw;
}
```

Но чем больше ресурсов, тем сложнее становится такая схема.

---

## RAII

Современный C++ предлагает принцип RAII:

**Resource Acquisition Is Initialization.**

Идея проста:

> время жизни ресурса связывается с временем жизни объекта, который этим ресурсом владеет.

Например:

```cpp
{
    std::vector<int> values(1000);

    // работа
}
```

Когда `values` выходит из области видимости, контейнер автоматически освобождает свою память.

Не нужно вручную писать:

```cpp
delete[];
```

---

## Почему RAII удобнее

С ручным управлением:

```cpp
int* data = new int[100];

doSomething();

delete[] data;
```

нужно помнить об освобождении.

С RAII:

```cpp
std::vector<int> data(100);
```

объект сам отвечает за свою память.

Даже если функция завершится через `return` или возникнет исключение, деструктор объекта будет вызван автоматически.

---

## Умные указатели

Для динамических объектов в современном C++ существуют умные указатели.

Например:

```cpp
std::unique_ptr<Robot> robot;
```

Или:

```cpp
auto robot = std::make_unique<Robot>();
```

Когда `unique_ptr` уничтожается, объект освобождается автоматически.

Для совместного владения существует:

```cpp
std::shared_ptr
```

а для наблюдения за объектом без увеличения счётчика владения:

```cpp
std::weak_ptr
```

Эти типы будут подробно изучаться позже.

---

## std::vector вместо new[]

Вместо:

```cpp
int* values = new int[size];

// ...

delete[] values;
```

обычно лучше:

```cpp
std::vector<int> values(size);
```

Теперь контейнер управляет памятью самостоятельно.

Можно использовать:

```cpp
values.push_back(10);
```

или:

```cpp
values[i]
```

и не заниматься ручным освобождением.

---

## std::string вместо char*

Для строк аналогично.

Старый подход:

```cpp
char* text = new char[100];
```

требует ручного управления памятью.

Современный:

```cpp
std::string text;
```

обычно намного безопаснее и удобнее.

Это хороший пример общего принципа современного C++:

> Используй высокоуровневый объект, который сам управляет ресурсом, если нет причины заниматься этим вручную.

---

## Когда ручное управление всё-таки встречается

Это не означает, что `new` и `delete` запрещены.

Они могут встречаться:

* в низкоуровневых библиотеках;
* при реализации собственных контейнеров;
* в системном программировании;
* в учебных примерах;
* при взаимодействии с C API;
* в специализированных системах с жёсткими требованиями к памяти.

Но даже там разработчик должен чётко понимать владение, время жизни и правила освобождения ресурсов.

---

## Практический пример

Сравним два подхода.

Ручное управление:

```cpp
void process()
{
    int* values = new int[1000];

    for (int i = 0; i < 1000; i++)
    {
        values[i] = i;
    }

    // нужно обязательно освободить память
    delete[] values;
}
```

Современный подход:

```cpp
#include <vector>

void process()
{
    std::vector<int> values(1000);

    for (int i = 0; i < 1000; i++)
    {
        values[i] = i;
    }
}
```

Во втором варианте память автоматически освобождается при уничтожении `values`.

---

## Почему C++ всё ещё позволяет делать опасные вещи

C++ создавался как язык, который должен был предоставлять разработчику очень высокий уровень контроля над машиной.

Поэтому программист может работать:

* с адресами;
* указателями;
* памятью;
* байтами;
* системными ресурсами.

Цена такой свободы — ответственность.

Современный C++ пытается сохранить низкоуровневый контроль, одновременно предоставляя безопасные абстракции поверх него.

---

## Главное

Основные опасности ручного управления памятью:

```text
memory leak
use-after-free
double free
dangling pointer
buffer overflow
неясное владение
ошибки при исключениях
```

Большую часть этих проблем можно существенно уменьшить, используя RAII:

```text
ресурс
   ↓
объект-владелец
   ↓
деструктор
   ↓
автоматическое освобождение
```

Поэтому современный C++ обычно предпочитает:

```cpp
std::vector
std::string
std::unique_ptr
std::shared_ptr
```

вместо прямого ручного управления через `new` и `delete`, когда это возможно.
