# Отладка программы

## Цель

Ошибки — обычная часть разработки. Важный навык программиста заключается не в том, чтобы никогда не ошибаться, а в том, чтобы быстро находить причину проблемы.

Для этого существует **отладка**, или debugging.

После урока вы должны понимать:

* что такое отладчик;
* зачем нужны точки останова;
* чем отличаются Step Over, Step Into и Step Out;
* как смотреть значения переменных;
* что такое стек вызовов;
* как исследовать указатели;
* чем отладчик отличается от логирования;
* как системно искать причину ошибки;
* как отлаживать C++ проект в IDE.

---

## Что такое отладчик

Отладчик — это инструмент, который позволяет остановить программу во время выполнения и исследовать её состояние.

Без отладчика программа обычно выполняется так:

```text
запуск
  ↓
код
  ↓
результат
```

С отладчиком можно сделать:

```text
запуск
  ↓
breakpoint
  ↓
пауза
  ↓
просмотр состояния
  ↓
следующая строка
  ↓
просмотр состояния
```

Это позволяет буквально пройти программу по шагам.

---

## Точка останова

**Breakpoint**, или точка останова, говорит отладчику:

> Когда выполнение дойдёт до этой строки, останови программу.

Например:

```cpp
int calculate(int a, int b) {
    int result = a + b;
    return result;
}
```

Можно поставить breakpoint на:

```cpp
int result = a + b;
```

Когда программа дойдёт до этой строки, выполнение остановится.

---

## Зачем нужны breakpoints

Представим:

```cpp
int motorIndex = getMotorIndex();
Motor& motor = motors[motorIndex];

motor.start();
```

Двигатель запускается неправильно.

Можно поставить breakpoint перед:

```cpp
motor.start();
```

и проверить:

```text
motorIndex
motors.size()
motor
```

Если:

```text
motorIndex = 20
motors.size() = 6
```

причина уже очевидна.

---

## Step Over

После остановки можно выполнить текущую строку и перейти к следующей.

Это называется:

```text
Step Over
```

или пошаговое выполнение без захода внутрь вызываемой функции.

Например:

```cpp
int value = readSensor();
process(value);
save(value);
```

Если остановиться на:

```cpp
int value = readSensor();
```

Step Over выполнит `readSensor()` целиком и остановится на следующей строке.

Это удобно, когда внутренняя реализация функции сейчас не интересует.

---

## Step Into

`Step Into` позволяет войти внутрь вызываемой функции.

Например:

```cpp
int value = readSensor();
```

Если выполнить Step Into, отладчик может перейти внутрь:

```cpp
int readSensor() {
    // ...
}
```

Это полезно, когда вы подозреваете проблему именно внутри функции.

---

## Step Out

Иногда вы уже находитесь внутри функции, но понимаете, что дальше её исследовать не нужно.

Тогда используется:

```text
Step Out
```

Он позволяет выполнить оставшуюся часть текущей функции и вернуться к вызывающему коду.

---

## Три основных шага

Получается:

```text
Step Over
```

— выполнить текущую операцию, не заходя внутрь вызова.

```text
Step Into
```

— войти внутрь вызываемой функции.

```text
Step Out
```

— выйти из текущей функции.

Эти три операции составляют основу пошаговой отладки.

---

## Просмотр переменных

Когда программа остановлена, можно посмотреть значения переменных.

Например:

```cpp
int speed = calculateSpeed(sensorValue);
```

Отладчик может показать:

```text
sensorValue = 73
speed = 120
```

Если результат неправильный, можно двигаться назад по цепочке вычислений:

```text
speed
  ↓
calculateSpeed()
  ↓
sensorValue
  ↓
датчик
```

---

## Watch

В отладчиках обычно есть область, где можно отслеживать выбранные выражения.

Например:

```cpp
motorIndex
```

или:

```cpp
devices.size()
```

или:

```cpp
*device
```

Это особенно полезно при сложной логике.

Можно наблюдать несколько значений и видеть, как они меняются на каждом шаге.

---

## Locals

Обычно отладчик показывает локальные переменные текущей функции.

Например:

```cpp
void process(int sensorId) {
    double value = readSensor(sensorId);
    bool valid = value >= 0;
}
```

При остановке можно увидеть:

```text
sensorId = 4
value = 25.7
valid = true
```

Это позволяет понять состояние программы без добавления десятков `std::cout`.

---

## Call Stack

**Call Stack**, или стек вызовов, показывает цепочку функций, которые привели программу к текущей строке.

Например:

```text
main()
  ↓
RobotController::start()
  ↓
MotorController::initialize()
  ↓
Sensor::read()
```

Если программа упала внутри:

```cpp
Sensor::read()
```

стек вызовов помогает понять, кто вызвал эту функцию.

Это особенно важно в больших проектах.

---

## Почему стек вызовов важнее одной строки

Допустим, ошибка возникла здесь:

```cpp
config.get("timeout");
```

Само по себе это мало что говорит.

Но стек может показать:

```text
main()
  ↓
Application::run()
  ↓
Robot::initialize()
  ↓
NetworkController::connect()
  ↓
Config::get()
```

Теперь понятно, в каком сценарии выполнялась операция.

Контекст часто важнее самой строки.

---

## Отладка указателей

Указатели требуют особого внимания.

Например:

```cpp
Device* device = getDevice();

device->start();
```

Если программа падает на:

```cpp
device->start();
```

нужно проверить:

```text
device
```

Если значение:

```text
nullptr
```

причина очевидна.

Но если указатель содержит какой-то адрес, это ещё не гарантирует, что объект действителен.

В таких случаях полезны санитайзеры и инструменты анализа памяти.

---

## Отладка контейнеров

Предположим:

```cpp
std::vector<Device> devices;
```

а затем:

```cpp
devices[index].start();
```

Перед выполнением нужно проверить:

```cpp
index
devices.size()
```

Например:

```text
index = 8
size = 4
```

Тогда проблема — выход за границы.

Очень полезная привычка:

> Перед подозрительной операцией проверить именно те значения, от которых зависит её корректность.

---

## Условный breakpoint

Иногда функция вызывается тысячи раз.

Ставить обычную точку останова неудобно.

Например:

```cpp
for (const auto& packet : packets) {
    process(packet);
}
```

Можно поставить условие:

```text
packet.id == 100
```

Тогда отладчик остановится только на интересующем пакете.

Условия зависят от конкретного отладчика, но идея одна:

```text
breakpoint
+
условие
=
остановка только в нужной ситуации
```

---

## Отладка по шагам

Представим:

```cpp
double calculateTemperature(double raw) {
    double voltage = raw * 0.01;
    double temperature = voltage * 100.0;

    return temperature;
}
```

Вызов:

```cpp
double temperature = calculateTemperature(rawValue);
```

Если результат неправильный, можно:

1. поставить breakpoint;
2. войти в функцию через Step Into;
3. проверить `raw`;
4. проверить `voltage`;
5. проверить `temperature`;
6. сравнить вычисления с ожидаемыми.

Так ошибка локализуется намного быстрее.

---

## Логирование и отладчик

Отладчик и логирование решают разные задачи.

Отладчик особенно полезен, когда вы можете воспроизвести проблему прямо сейчас.

Логирование полезно, когда проблема возникает:

* на другом компьютере;
* у пользователя;
* ночью;
* раз в несколько часов;
* в промышленной системе;
* при определённой последовательности событий.

Например:

```cpp
std::cout << "Connecting to controller...\n";
```

может показать последовательность событий даже тогда, когда отладчик недоступен.

---

## Что логировать

Хороший лог обычно содержит:

```text
время
уровень
компонент
событие
контекст
```

Например:

```text
10:42:15 ERROR Controller: connection timeout, address=192.168.1.20
```

Вместо бесполезного:

```text
ERROR
```

Контекст значительно ускоряет поиск проблемы.

---

## Debug и Release

C++ проекты часто имеют разные конфигурации сборки.

Например:

```text
Debug
Release
```

Debug обычно предназначен для удобства разработки и отладки.

Release ориентирован на конечное выполнение программы и обычно использует оптимизации.

Поведение программы может отличаться.

Если ошибка появляется только в Release, это повод особенно внимательно проверить:

* UB;
* ошибки памяти;
* время жизни объектов;
* многопоточность;
* зависимость от порядка выполнения;
* неинициализированные данные.

## Отладка CMake-проекта

Если проект собирается через CMake:

```text
project/
├── CMakeLists.txt
├── src/
│   ├── main.cpp
│   └── controller.cpp
└── include/
    └── controller.h
```

обычно сначала создают сборочную конфигурацию:

```text
cmake
  ↓
build
```

После этого IDE или отладчик запускает полученную программу.

Важно понимать разницу:

```text
CMake
```

описывает процесс сборки.

```text
компилятор
```

создаёт объектный код.

```text
отладчик
```

управляет выполнением уже собранной программы.

## Отладка в IDE

В современных IDE обычно есть кнопки:

```text
Run
Debug
Step Over
Step Into
Step Out
Continue
Stop
```

Название и расположение могут отличаться.

Для C++ часто используется отладчик на базе GDB, LLDB или системного отладчика платформы.

Но независимо от конкретного инструмента логика остаётся одинаковой:

```text
запустить
→
остановить
→
исследовать
→
выполнить шаг
→
проверить состояние
→
найти момент, когда состояние стало неправильным
```

## Как искать ошибку системно

Одна из самых плохих стратегий:

```text
поменять случайную строку
→
запустить
→
не помогло
→
поменять другую
```

Лучше действовать последовательно.

### Шаг 1. Воспроизведите проблему

Нужно понять:

```text
когда возникает ошибка?
```

### Шаг 2. Сузьте область

Определите:

```text
какая функция?
какой сценарий?
какие входные данные?
```

### Шаг 3. Поставьте breakpoint

Остановите программу непосредственно перед подозрительным местом.

### Шаг 4. Проверьте предположения

Не думайте:

> `index` наверняка равен 3.

Посмотрите значение.

### Шаг 5. Идите назад по данным

Если:

```cpp
result
```

неправильный, исследуйте:

```text
result
 ↓
вычисление
 ↓
аргументы
 ↓
источник данных
```

### Шаг 6. Исправьте причину

Не маскируйте симптом.

## Пример

Предположим:

```cpp
#include <iostream>
#include <vector>

struct Motor {
    int speed;

    void start() {
        std::cout << "Motor started at "
                  << speed
                  << '\n';
    }
};

int main() {
    std::vector<Motor> motors = {
        {100},
        {200},
        {300}
    };

    int index = 5;

    motors[index].start();
}
```

Программа использует:

```cpp
index = 5
```

при:

```cpp
motors.size() = 3
```

При отладке нужно остановиться перед:

```cpp
motors[index].start();
```

и посмотреть:

```text
index = 5
size = 3
```

Причина становится очевидной.

Исправление:

```cpp
if (index < 0 || index >= static_cast<int>(motors.size())) {
    std::cout << "Invalid motor index\n";
    return 1;
}

motors[index].start();
```

## Отладка сложных систем

В реальном приложении ошибка может возникать не в одной строке.

Например:

```text
PLC
 ↓
сетевой пакет
 ↓
драйвер
 ↓
парсер
 ↓
контроллер
 ↓
GUI
```

Если GUI показывает неправильное значение, не нужно сразу исправлять GUI.

Нужно проверить цепочку:

```text
какое значение пришло?
        ↓
правильно ли прочитано?
        ↓
правильно ли распарсено?
        ↓
правильно ли преобразовано?
        ↓
правильно ли передано в GUI?
```

Такой подход особенно важен в промышленной автоматизации и робототехнике.

---

## Отладка робота

Представим:

```cpp
robot.moveTo(x, y);
```

Робот перемещается не туда.

Потенциальная цепочка:

```text
датчик
 ↓
координаты
 ↓
преобразование системы координат
 ↓
планировщик
 ↓
команда двигателя
```

Отладка должна проверять данные на каждом уровне.

Например:

```text
sensor_x = 120
sensor_y = 80

world_x = 1.20
world_y = 0.80

target_x = 1.50
target_y = 0.90
```

Если значение стало неправильным на одном из этапов, дальше уже нет смысла искать проблему в двигателе.

---

## Breakpoint не всегда лучший инструмент

Если программа работает с несколькими потоками, сетевыми соединениями или реальным оборудованием, остановка процесса может изменить поведение системы.

В таких ситуациях полезнее:

* логирование;
* трассировка;
* счётчики;
* диагностические переменные;
* санитайзеры;
* тесты;
* воспроизводимый симулятор.

Для промышленной системы остановка реального процесса отладчиком вообще может быть опасной.

Отладка должна проводиться в безопасной среде или на тестовом оборудовании.

---

## Отладка и тестирование

Отладчик помогает понять:

> Почему программа сейчас делает это?

Тесты помогают проверить:

> Будет ли программа продолжать делать это правильно после изменений?

Например, если функция должна:

```cpp
calculateSpeed(100)
```

возвращать:

```text
50
```

можно написать тест.

После исправления тест подтверждает, что поведение сохраняется.

Поэтому хороший процесс выглядит так:

```text
ошибка
 ↓
воспроизведение
 ↓
отладка
 ↓
исправление
 ↓
тест
 ↓
проверка
```

---

## Главное

Отладка — это не случайное изменение кода до тех пор, пока программа снова не заработает.

Это систематическое исследование состояния программы.

Основные инструменты:

```text
breakpoint
```

останавливает выполнение.

```text
Step Over
```

выполняет текущую строку без входа внутрь функции.

```text
Step Into
```

переходит внутрь функции.

```text
Step Out
```

выходит из текущей функции.

```text
Watch / Locals
```

показывают значения данных.

```text
Call Stack
```

показывает цепочку вызовов.

Логирование и санитайзеры дополняют отладчик и особенно полезны для ошибок, которые сложно воспроизвести.

## Практика

### Задание 1

Создайте программу:

```cpp
int calculate(int a, int b) {
    int result = a * 10;
    result += b;
    return result;
}
```

Поставьте breakpoint и пройдите функцию по шагам.

Посмотрите значения `a`, `b` и `result`.

### Задание 2

Создайте программу с `std::vector`.

Специально передайте неправильный индекс.

С помощью отладчика найдите момент, когда значение индекса становится неправильным.

### Задание 3

Создайте три функции:

```cpp
main()
controller()
readSensor()
```

Передайте значение через все три функции.

Используйте Call Stack, чтобы увидеть цепочку вызовов.

### Задание 4

Создайте программу, где указатель может оказаться `nullptr`.

Поставьте breakpoint перед разыменованием и проверьте его значение.

Затем добавьте безопасную проверку.

### Задание 5

Создайте небольшую программу управления несколькими виртуальными двигателями.

Добавьте намеренную ошибку:

```text
неправильный индекс
```

С помощью debugger найдите проблему, исправьте её и добавьте проверку, которая не позволит ошибке возникнуть снова.
