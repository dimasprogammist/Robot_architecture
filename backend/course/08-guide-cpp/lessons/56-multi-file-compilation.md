# Компиляция нескольких файлов

## Цель

В предыдущих уроках мы научились разделять программу на заголовочные и исходные файлы. Теперь нужно разобраться, как такая программа превращается в готовое приложение.

Когда проект состоит из одного `main.cpp`, команда компиляции выглядит просто. Но настоящий проект может содержать десятки или сотни `.cpp` файлов, и важно понимать, что именно делает компилятор, что делает компоновщик и зачем вообще существует промежуточный этап с объектными файлами.

После урока вы должны понимать:

* как компилируется отдельный `.cpp`;
* что такое единица трансляции;
* что такое объектный файл;
* зачем нужен linker;
* чем компиляция отличается от линковки;
* как собрать проект из нескольких `.cpp` вручную;
* что означает ошибка `undefined reference` или аналогичная ошибка линковки;
* почему заголовочные файлы не компилируются отдельно в обычной модели C++ проекта.

---

## Один файл — простой случай

Возьмём программу:

```cpp
#include <iostream>

int main() {
    std::cout << "Hello\n";
}
```

Она находится в:

```text
main.cpp
```

Можно выполнить:

```text
g++ main.cpp -o app
```

После этого получим:

```text
app
```

Но внутри происходит не просто действие "превратить текст в exe".

Упрощённо процесс выглядит так:

```text
main.cpp
   ↓
препроцессор
   ↓
компилятор
   ↓
объектный код
   ↓
linker
   ↓
готовая программа
```

---

## Что происходит с несколькими файлами

Теперь проект состоит из:

```text
main.cpp
motor.cpp
sensor.cpp
```

Каждый `.cpp` обрабатывается отдельно:

```text
main.cpp
   ↓
main.o

motor.cpp
   ↓
motor.o

sensor.cpp
   ↓
sensor.o
```

Затем linker объединяет результаты:

```text
main.o
motor.o
sensor.o
   ↓
linker
   ↓
app
```

Это одна из фундаментальных идей C++.

---

## Что такое объектный файл

После компиляции `.cpp` получается промежуточный объектный файл.

На Linux обычно можно встретить:

```text
.o
```

На Windows при использовании некоторых инструментов:

```text
.obj
```

Например:

```text
motor.cpp
```

может превратиться в:

```text
motor.o
```

Этот файл содержит машинный код и служебную информацию, необходимую для дальнейшей сборки.

Он ещё не обязательно является самостоятельной программой.

---

## Почему нужен linker

Рассмотрим:

```cpp
// motor.h

#pragma once

class Motor {
public:
    void start();
};
```

В `main.cpp`:

```cpp
#include "motor.h"

int main() {
    Motor motor;
    motor.start();
}
```

Компилятор видит:

```cpp
void start();
```

и знает, что такой метод существует.

Но реализация находится в другом файле:

```cpp
// motor.cpp

#include "motor.h"

void Motor::start() {
}
```

Поэтому после отдельной компиляции нужно соединить эти части.

Этим занимается linker.

---

## Компиляция отдельно

Можно мысленно представить:

```text
main.cpp
```

как:

```text
"Мне нужен Motor::start()"
```

а:

```text
motor.cpp
```

как:

```text
"Я предоставляю Motor::start()"
```

Linker должен сопоставить эти две части.

---

## Компиляция без линковки

При использовании `g++` можно отдельно получить объектный файл:

```text
g++ -c motor.cpp
```

Появится:

```text
motor.o
```

Аналогично:

```text
g++ -c main.cpp
```

получим:

```text
main.o
```

Теперь у нас:

```text
main.o
motor.o
```

---

## Линковка

Теперь можно выполнить:

```text
g++ main.o motor.o -o app
```

Здесь `.o` файлы уже являются результатами компиляции.

Команда выполняет их компоновку.

Получаем:

```text
app
```

---

## Полная последовательность вручную

Для проекта:

```text
main.cpp
motor.cpp
```

можно выполнить:

```text
g++ -c main.cpp
g++ -c motor.cpp
g++ main.o motor.o -o robot
```

Получится:

```text
main.cpp
motor.cpp
main.o
motor.o
robot
```

В реальной разработке вручную делать это для каждого файла неудобно.

Именно поэтому существуют системы сборки.

---

## Система сборки

Для небольшого проекта можно использовать:

```text
g++
```

Для большого проекта появляются:

```text
Make
CMake
Ninja
MSBuild
```

Позже мы подробно познакомимся с CMake.

Система сборки должна определить:

```text
какие файлы нужно компилировать;
какие зависимости изменились;
какие библиотеки подключить;
как выполнить линковку;
куда положить результат.
```

---

## Заголовочные файлы не являются отдельными программами

Допустим:

```text
motor.h
motor.cpp
main.cpp
```

Обычно не нужно делать:

```text
g++ motor.h
```

Заголовок подключается через:

```cpp
#include "motor.h"
```

к соответствующим `.cpp`.

То есть основной объект компиляции — исходный `.cpp`.

---

## Единица трансляции

После обработки препроцессором каждый `.cpp` вместе со всеми подключёнными заголовками образует **единицу трансляции**.

Например:

```cpp
#include "motor.h"
#include <iostream>

int main() {
}
```

после обработки `#include` содержит код из подключённых заголовков.

Именно эту большую совокупность исходного текста компилятор анализирует как одну единицу трансляции.

---

## Почему это важно

Представим:

```text
main.cpp
motor.cpp
sensor.cpp
```

У каждого файла своя единица трансляции.

Условно:

```text
main.cpp + его includes
        ↓
translation unit 1

motor.cpp + его includes
        ↓
translation unit 2

sensor.cpp + его includes
        ↓
translation unit 3
```

Они компилируются независимо.

---

## Что будет, если забыть .cpp

Представим:

```text
main.cpp
motor.cpp
```

Мы запускаем:

```text
g++ main.cpp -o robot
```

Но забываем:

```text
motor.cpp
```

Компилятор может успешно обработать `main.cpp`, потому что в `motor.h` есть объявление.

Но на этапе линковки реализации `Motor::start()` не будет найдено.

Получится ошибка линковщика.

В GCC это часто выглядит примерно так:

```text
undefined reference to `Motor::start()`
```

Смысл ошибки:

> объявление есть, а определения среди переданных объектных файлов нет.

---

## Ошибка компиляции и ошибка линковки

Это разные вещи.

Например:

```cpp
Motor motor;
```

без подключения нужного заголовка может вызвать ошибку компиляции:

```text
Motor was not declared
```

Компилятор не знает, что такое `Motor`.

А если объявление есть, но реализация не была добавлена при линковке:

```text
undefined reference
```

Это уже ошибка linker.

Полезно различать эти ситуации.

---

## Несколько файлов и классов

Рассмотрим проект:

```text
robot/
├── main.cpp
├── motor.h
├── motor.cpp
├── sensor.h
└── sensor.cpp
```

### motor.h

```cpp
#pragma once

class Motor {
public:
    void start();
};
```

### motor.cpp

```cpp
#include "motor.h"
#include <iostream>

void Motor::start() {
    std::cout << "Motor started\n";
}
```

### sensor.h

```cpp
#pragma once

class Sensor {
public:
    double read() const;
};
```

### sensor.cpp

```cpp
#include "sensor.h"

double Sensor::read() const {
    return 24.5;
}
```

### main.cpp

```cpp
#include <iostream>

#include "motor.h"
#include "sensor.h"

int main() {
    Motor motor;
    Sensor sensor;

    motor.start();

    std::cout << sensor.read() << '\n';
}
```

---

## Сборка

Все исходники можно передать одной командой:

```text
g++ main.cpp motor.cpp sensor.cpp -o robot
```

Компилятор обработает каждый `.cpp`, а затем выполнит линковку.

Для небольшого проекта этого достаточно.

---

## Почему нельзя всё делать через include

Иногда начинающие программисты пытаются решить проблему так:

```cpp
#include "motor.cpp"
```

Это не является нормальным способом сборки проекта.

Получается, что содержимое `motor.cpp` физически вставляется в другую единицу трансляции.

Если затем `motor.cpp` ещё и отдельно передать linker'у, можно получить множественные определения.

Правильная модель:

```cpp
#include "motor.h"
```

и отдельно:

```text
g++ main.cpp motor.cpp
```

---

## Изменение одного файла

Одно из преимуществ разделения проекта — независимая компиляция.

Если изменился только:

```text
motor.cpp
```

нет необходимости концептуально пересобирать каждый `.cpp` с нуля.

Система сборки может перекомпилировать только изменившийся файл:

```text
motor.cpp
   ↓
motor.o
```

а затем снова выполнить линковку.

Это особенно важно в больших проектах.

---

## Почему заголовки влияют на сборку

Если изменить:

```text
motor.cpp
```

обычно нужно перекомпилировать только связанные исходные файлы и выполнить линковку.

Если изменить:

```text
motor.h
```

изменение может затронуть все `.cpp`, которые включают этот заголовок.

Поэтому чрезмерное количество зависимостей между заголовками может замедлять сборку больших проектов.

---

## Практический пример

Представим контроллер робота:

```text
robot/
├── main.cpp
├── motor.cpp
├── motor.h
├── sensor.cpp
├── sensor.h
├── controller.cpp
└── controller.h
```

Контроллер использует двигатель и датчик.

```cpp
// controller.h

#pragma once

class Controller {
public:
    void update();
};
```

```cpp
// controller.cpp

#include "controller.h"
#include "motor.h"
#include "sensor.h"

void Controller::update() {
    Motor motor;
    Sensor sensor;

    motor.start();

    double value = sensor.read();

    (void)value;
}
```

Главный файл:

```cpp
#include "controller.h"

int main() {
    Controller controller;

    controller.update();
}
```

Сборка:

```text
g++ main.cpp motor.cpp sensor.cpp controller.cpp -o robot
```

---

## Что будет дальше

В реальных проектах никто не хочет вручную писать:

```text
g++ main.cpp motor.cpp sensor.cpp controller.cpp ...
```

Когда файлов становится десятки, сотни или тысячи, сборкой должен управлять специальный инструмент.

Для этого мы будем использовать CMake.

Он позволит описать:

```text
какие исходники входят в проект;
какой стандарт C++ использовать;
какие библиотеки подключать;
какой исполняемый файл создавать.
```

## Главное

Процесс сборки C++ программы можно представить так:

```text
.cpp
 ↓
препроцессор
 ↓
единица трансляции
 ↓
компилятор
 ↓
.o / .obj
 ↓
linker
 ↓
исполняемый файл
```

Для нескольких файлов:

```text
main.cpp   → main.o
motor.cpp  → motor.o
sensor.cpp → sensor.o

main.o + motor.o + sensor.o
            ↓
          linker
            ↓
           app
```

Компилятор отвечает за перевод отдельных исходных файлов в объектный код.

Linker соединяет получившиеся части в единую программу.

Когда проект становится большим, ручная сборка перестаёт быть удобной — тогда на сцену выходит CMake.
