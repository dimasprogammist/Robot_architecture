# C++ и аппаратные устройства

## Цель

C++ часто используется в программах, которые взаимодействуют с реальным оборудованием.

Это могут быть:

```text
датчики
двигатели
ПЛК
контроллеры
камеры
USB-устройства
промышленные компьютеры
роботы
```

Но важно понимать: сам язык C++ не содержит универсальной команды «прочитать датчик».

Между программой и устройством существует несколько уровней.

После урока вы должны понимать:

* как программное обеспечение взаимодействует с аппаратурой;
* какую роль играют драйверы;
* что такое GPIO, UART, USB и CAN;
* почему промышленное оборудование часто работает через сетевые протоколы;
* что такое memory-mapped I/O на концептуальном уровне;
* почему стандартный C++ не предоставляет прямого универсального доступа к железу.

---

## Программа не разговаривает с железом напрямую

Упрощённая схема:

```text
C++ приложение
      ↓
библиотека / API
      ↓
драйвер
      ↓
операционная система
      ↓
аппаратное устройство
```

В embedded-системах схема может быть другой:

```text
C++ код
   ↓
HAL / регистры
   ↓
микроконтроллер
   ↓
периферия
```

Поэтому способ работы с устройством зависит от платформы.

---

## Драйвер

Драйвер — программный компонент, который позволяет операционной системе взаимодействовать с конкретным оборудованием.

Например:

```text
C++ приложение
      ↓
API
      ↓
драйвер USB
      ↓
USB устройство
```

Приложению не нужно знать все электрические детали USB-контроллера.

Драйвер скрывает большую часть низкоуровневой работы.

---

## Пример с USB

Допустим, подключён промышленный измерительный прибор по USB.

Приложение может использовать библиотеку производителя:

```cpp
device.connect();
device.readValue();
```

Но внутри:

```text
C++ библиотека
    ↓
USB API
    ↓
драйвер
    ↓
USB controller
    ↓
device
```

Поэтому `device.readValue()` может выглядеть просто, хотя под ним находится много системной работы.

---

## GPIO

GPIO — General Purpose Input/Output.

Это цифровые линии, которые можно использовать как:

```text
INPUT
OUTPUT
```

Например:

```text
GPIO input
    ↓
датчик

GPIO output
    ↓
светодиод / реле
```

В микроконтроллерах GPIO используется постоянно.

---

## Логические уровни

Цифровой вход обычно воспринимает состояния:

```text
0
1
```

Физически это соответствует определённым уровням напряжения.

Например:

```text
LOW
HIGH
```

Но конкретные напряжения зависят от аппаратной платформы.

Поэтому нельзя считать:

```text
HIGH = всегда 5 V
```

Для конкретного микроконтроллера нужно смотреть его документацию.

---

## UART

UART — простой последовательный интерфейс.

Упрощённо:

```text
Device A TX ───── RX Device B
Device A RX ───── TX Device B
GND ───────────── GND
```

Данные передаются последовательно.

Часто задаются параметры:

```text
baud rate
data bits
parity
stop bits
```

Например:

```text
115200 8N1
```

означает:

```text
115200 baud
8 data bits
No parity
1 stop bit
```

---

## USB

USB — универсальный интерфейс подключения устройств.

Он используется для:

```text
клавиатур
камер
накопителей
промышленных приборов
адаптеров
контроллеров
```

USB значительно сложнее простого UART.

Устройство и компьютер взаимодействуют по определённому протоколу USB.

Часто производитель предоставляет собственный SDK.

---

## CAN

CAN широко используется в:

```text
автомобилях
робототехнике
промышленности
контроллерах
```

В сети CAN несколько устройств могут обмениваться сообщениями.

У сообщения есть идентификатор и данные.

Упрощённо:

```text
ID      DATA
0x120   01 02 03 04
```

Разные устройства могут реагировать на определённые идентификаторы.

---

## Modbus

В промышленной автоматизации часто используется Modbus.

Он может работать поверх:

```text
RS-485
TCP
```

Например:

```text
C++ application
      ↓
Modbus TCP
      ↓
PLC
```

Программа отправляет запрос:

```text
прочитать регистры
```

а устройство отвечает данными.

---

## OPC UA

OPC UA используется для обмена промышленными данными.

Например:

```text
C++ application
      ↓
OPC UA Client
      ↓
OPC UA Server
      ↓
PLC / SCADA
```

C++ программа может получать:

```text
температуру
уровень
скорость
состояние оборудования
аварии
```

Для OPC UA обычно используется специализированная библиотека.

Сам стандартный C++ не содержит OPC UA клиента.

---

## Уровни абстракции

Хорошая архитектура может выглядеть так:

```text
Application
     ↓
Device Interface
     ↓
Protocol Driver
     ↓
OS / Network
     ↓
Hardware
```

Например:

```text
RobotController
     ↓
IMotorController
     ↓
CAN Driver
     ↓
CAN Interface
     ↓
Motor Controller
```

Такой подход позволяет менять конкретную реализацию.

---

## Интерфейс устройства

Можно определить:

```cpp
class TemperatureSensor {
public:
    virtual double readTemperature() = 0;
    virtual ~TemperatureSensor() = default;
};
```

Основная программа работает с интерфейсом:

```cpp
double temperature =
    sensor.readTemperature();
```

А конкретная реализация может быть:

```text
ModbusTemperatureSensor
UsbTemperatureSensor
MockTemperatureSensor
```

Это позволяет тестировать программу без реального устройства.

---

## Mock-устройство

Представим тест:

```cpp
class MockTemperatureSensor {
public:
    double readTemperature() {
        return 25.0;
    }
};
```

Теперь алгоритм можно протестировать без оборудования.

Это особенно важно для промышленного ПО и робототехники.

---

## Memory-mapped I/O

В некоторых системах аппаратные регистры отображаются в адресное пространство памяти.

Концептуально:

```text
адрес 0x40000000
        ↓
регистр устройства
```

Программа может читать или записывать значение по определённому адресу.

Например, условно:

```cpp
volatile std::uint32_t* registerAddress =
    reinterpret_cast<volatile std::uint32_t*>(0x40000000);
```

Но такой код нельзя запускать на обычном компьютере с произвольным адресом.

Конкретные адреса и правила определяются аппаратной платформой.

---

## Почему нужен `volatile`

В embedded-программировании можно встретить:

```cpp
volatile std::uint32_t registerValue;
```

`volatile` сообщает компилятору, что значение может изменяться неочевидным для обычного кода способом.

Например:

```text
аппаратное устройство
      ↓
регистр
      ↓
C++ программа
```

Но важно понимать:

> `volatile` не делает доступ к данным потокобезопасным и не является универсальным механизмом синхронизации.

Это особенно важное различие.

---

## Регистры устройств

Микроконтроллер может иметь регистры:

```text
GPIO
UART
SPI
I2C
Timer
ADC
```

Каждый регистр управляет определённой функцией.

Например:

```text
GPIO register
    ↓
настройка направления

GPIO output register
    ↓
установка HIGH / LOW
```

C++ код предоставляет удобный способ работать с этими регистрами.

---

## SPI

SPI — синхронный последовательный интерфейс.

Часто используется для:

```text
датчиков
дисплеев
Flash-памяти
ADC
DAC
```

Обычно присутствуют линии:

```text
SCLK
MOSI
MISO
CS
```

Несколько устройств могут использовать общую шину с отдельными сигналами выбора.

---

## I²C

I²C также используется для подключения периферии.

Основные линии:

```text
SDA
SCL
```

Несколько устройств могут находиться на одной шине.

Каждое устройство имеет адрес.

Например:

```text
Controller
    │
    ├── Sensor 0x48
    ├── Sensor 0x50
    └── Display 0x3C
```

---

## Реальный промышленный компьютер

В промышленной системе C++ приложение может вообще не работать с GPIO напрямую.

Например:

```text
C++ Monitor
    ↓
Ethernet
    ↓
Switch
    ↓
PLC
    ↓
Sensors
```

В таком случае приложение работает с:

```text
TCP
OPC UA
Modbus TCP
MQTT
```

а физическим управлением входами и выходами занимается PLC.

Это очень распространённая архитектура.

---

## Почему не стоит смешивать уровни

Плохая архитектура:

```text
GUI
 ↓
Modbus
 ↓
GPIO
 ↓
логика робота
 ↓
файлы
```

в одном огромном классе.

Лучше:

```text
GUI
 ↓
Application Logic
 ↓
Device Interface
 ↓
Protocol Layer
 ↓
Hardware
```

Каждый слой отвечает за свою задачу.

---

## Отладка аппаратного взаимодействия

Если программа не получает данные от устройства, проблема может находиться на любом уровне:

```text
C++ код
 ↓
библиотека
 ↓
протокол
 ↓
сетевой интерфейс
 ↓
драйвер
 ↓
кабель
 ↓
устройство
```

Поэтому диагностику лучше проводить последовательно.

Например:

```text
1. устройство включено?
2. интерфейс доступен?
3. IP / COM / CAN параметры правильные?
4. порт доступен?
5. протокол работает?
6. запрос корректный?
7. устройство отвечает?
8. данные правильно декодируются?
```

---

## Аппаратные ошибки

Оборудование может возвращать:

```text
timeout
CRC error
invalid command
device busy
connection lost
overvoltage
undervoltage
```

Программа должна отличать:

```text
валидное значение
```

от:

```text
ошибка связи
```

Нельзя превращать отсутствие данных в:

```cpp
temperature = 0;
```

если `0` является допустимой температурой.

Иначе ошибка связи будет выглядеть как настоящее измерение.

---

## Статусы данных

Хороший интерфейс может возвращать не только значение.

Например:

```cpp
struct Measurement {
    double value;
    bool valid;
};
```

Или:

```cpp
enum class Status {
    Good,
    Timeout,
    CommunicationError,
    InvalidData
};
```

Это намного надёжнее, чем передавать только число.

---

## C++ и промышленная автоматизация

C++ может находиться на уровне:

```text
SCADA integration
OPC UA
Modbus
TCP
robot controller
vision
data processing
```

При этом низкоуровневое управление может выполнять:

```text
PLC
microcontroller
motor controller
I/O module
```

Такое разделение часто делает систему более надёжной.

---

## Главное

C++ не является универсальным драйвером для железа.

Он является языком, на котором можно реализовать:

```text
драйверы
библиотеки
протоколы
контроллеры
серверы
клиенты
embedded firmware
```

Но конкретное взаимодействие определяется аппаратной платформой и программным стеком.

Запомните уровни:

```text
Application
    ↓
Library / API
    ↓
Protocol / Driver
    ↓
OS / HAL
    ↓
Hardware
```
