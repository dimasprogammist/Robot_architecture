# Работа с конфигурационным файлом

## Цель

Программа редко должна хранить все настройки прямо в исходном коде.

Например, адрес сервера:

```text
192.168.8.149
```

порт:

```text
4861
```

и интервал проверки:

```text
5 секунд
```

лучше вынести в конфигурацию.

После урока вы должны понимать:

* зачем нужны конфигурационные файлы;
* какие настройки стоит выносить из кода;
* как читать текстовые файлы в C++;
* как сохранять конфигурацию;
* чем отличается конфигурация от данных приложения;
* как использовать JSON в C++;
* как обрабатывать ошибки конфигурации;
* почему нельзя бездумно доверять содержимому конфигурационного файла.

---

## Зачем нужна конфигурация

Представим код:

```cpp
const std::string server = "192.168.8.149";
const int port = 4861;
const int interval = 5;
```

Чтобы изменить сервер, нужно:

```text
изменить код
↓
перекомпилировать
↓
заменить программу
```

Это неудобно.

Гораздо лучше:

```text
program.exe
config.json
```

Пользователь меняет:

```text
config.json
```

а программа читает настройки при запуске.

---

## Что обычно помещают в конфигурацию

Например:

```text
IP-адреса
порты
пути к файлам
таймауты
интервалы
имена устройств
уровни логирования
режим работы
```

Но не стоит помещать туда всё подряд.

Например, текущие измерения оборудования — это уже данные приложения, а не обязательно конфигурация.

---

## Простой текстовый формат

Самый простой вариант:

```text
server=192.168.8.149
port=4861
interval=5
```

C++ может прочитать файл построчно.

---

## Чтение файла

```cpp
#include <fstream>
#include <string>

std::ifstream file("config.txt");

if (!file) {
    // ошибка открытия
}
```

Читаем строки:

```cpp
std::string line;

while (std::getline(file, line)) {
    // обработать line
}
```

---

## Разбор строки

Допустим:

```text
port=4861
```

Можно найти:

```cpp
auto position = line.find('=');
```

Если разделитель найден:

```cpp
std::string key = line.substr(0, position);
std::string value = line.substr(position + 1);
```

Получим:

```text
key   = port
value = 4861
```

---

## Проблема самодельного формата

Поначалу это удобно.

Но затем появляются:

```text
массивы
вложенные объекты
булевы значения
числа
списки
```

Например:

```text
devices:
  - motor
  - camera
  - plc
```

Самодельный парсер быстро становится сложным.

Поэтому для сложных конфигураций используют стандартные форматы.

---

## JSON

JSON хорошо подходит для конфигураций.

Например:

```json
{
    "server": "192.168.8.149",
    "port": 4861,
    "interval": 5
}
```

Он читается человеком и имеет строгую структуру.

---

## Вложенные параметры

Можно описать устройство:

```json
{
    "server": {
        "host": "192.168.8.149",
        "port": 4861,
        "timeout": 3
    }
}
```

И список устройств:

```json
{
    "devices": [
        {
            "name": "Motor",
            "address": "192.168.8.10"
        },
        {
            "name": "PLC",
            "address": "192.168.8.20"
        }
    ]
}
```

---

## JSON и C++

Стандартный C++ не содержит полноценного JSON-парсера.

Поэтому обычно используется сторонняя библиотека.

Одна из популярных библиотек:

```text
nlohmann/json
```

С ней работа выглядит примерно так:

```cpp
#include <nlohmann/json.hpp>

using json = nlohmann::json;
```

---

## Чтение JSON

```cpp
std::ifstream file("config.json");

json config;
file >> config;
```

Теперь можно получить:

```cpp
std::string host =
    config["server"]["host"];

int port =
    config["server"]["port"];
```

---

## Проверка параметров

Нельзя предполагать, что файл всегда правильный.

Например, пользователь может написать:

```json
{
    "port": "hello"
}
```

вместо:

```json
{
    "port": 4861
}
```

Программа должна проверять конфигурацию.

---

## Значения по умолчанию

Иногда параметр может быть необязательным.

Например:

```text
timeout
```

может иметь значение:

```text
5
```

по умолчанию.

При отсутствии параметра:

```cpp
int timeout = config.value("timeout", 5);
```

Теперь программа использует:

```text
timeout = 5
```

если настройки нет.

---

## Валидация

Недостаточно проверить только наличие поля.

Например:

```json
{
    "port": -10
}
```

Поле существует, но значение неправильное.

Можно проверить:

```cpp
if (port <= 0 || port > 65535) {
    throw std::runtime_error("Invalid port");
}
```

---

## Конфигурация как структура

Хорошая практика — не таскать JSON по всей программе.

Можно преобразовать его в обычную структуру:

```cpp
struct ServerConfig {
    std::string host;
    int port;
    int timeout;
};
```

После чтения:

```cpp
ServerConfig config;
```

Теперь остальная программа работает с обычным C++ объектом.

---

## Почему это лучше

Вместо:

```cpp
config["server"]["host"]
```

по всему приложению:

```cpp
serverConfig.host
```

Код становится:

```text
типизированным
понятным
тестируемым
```

---

## Отдельный ConfigManager

Можно создать:

```cpp
class ConfigManager {
public:
    ServerConfig load(
        const std::string& path
    );

    void save(
        const std::string& path,
        const ServerConfig& config
    );
};
```

Теперь ответственность за файл находится в одном месте.

---

## Сохранение

Для JSON:

```cpp
json data;

data["server"]["host"] = config.host;
data["server"]["port"] = config.port;
data["server"]["timeout"] = config.timeout;

std::ofstream file("config.json");

file << data.dump(4);
```

`dump(4)` форматирует JSON с отступами.

---

## Не смешивайте конфигурацию и runtime state

Это важный принцип.

Конфигурация:

```text
IP сервера
порт
таймаут
имя устройства
```

Runtime state:

```text
подключено
текущее значение
ошибка
последний ответ
```

Не обязательно сохранять runtime state в тот же файл.

---

## Секреты

В конфигурации иногда находятся:

```text
пароли
токены
ключи
```

Это опасно.

Не стоит:

```text
commit
config.json
↓
GitHub
```

если внутри находятся реальные секреты.

Лучше использовать:

```text
environment variables
secret storage
protected configuration
```

в зависимости от архитектуры приложения.

---

## Путь к конфигурации

Нельзя всегда рассчитывать на:

```cpp
"config.json"
```

Потому что рабочая директория программы может быть разной.

Например:

```text
C:\Program Files\App
```

или:

```text
C:\Users\User\Desktop
```

Поэтому реальные приложения часто определяют путь к конфигурации явно.

---

## Конфигурация рядом с программой

Для простого учебного приложения:

```text
app/
├── app.exe
└── config.json
```

можно использовать относительный путь.

Для production-приложения нужно заранее определить правило:

```text
где находится конфигурация
кто может её менять
что происходит при отсутствии файла
```

---

## Обработка ошибок

Возможны ситуации:

```text
файл отсутствует
файл недоступен
JSON повреждён
параметр отсутствует
неправильный тип
неправильное значение
```

Программа должна сообщать понятную ошибку.

Например:

```text
Configuration error:
port must be between 1 and 65535
```

а не просто:

```text
Error
```

---

## Конфигурация и окружение

Некоторые настройки лучше передавать через environment variables.

Например:

```text
APP_SERVER=192.168.8.149
APP_PORT=4861
```

Это особенно удобно для серверных приложений и контейнеров.

Получается:

```text
code
+
environment
```

вместо:

```text
code
+
секреты внутри исходников
```

---

## Конфигурация устройства

Для нашего менеджера устройств можно сделать:

```json
{
    "devices": [
        {
            "id": 1,
            "name": "Motor",
            "type": "motor",
            "address": "192.168.8.20",
            "port": 502
        }
    ]
}
```

При запуске:

```text
config.json
   ↓
ConfigManager
   ↓
Device objects
   ↓
DeviceManager
```

---

## Архитектура

Теперь приложение может выглядеть так:

```text
main
 ↓
ConfigManager
 ↓
DeviceManager
 ↓
Devices
```

Конфигурация загружается один раз.

Дальше приложение работает с обычными C++ объектами.

---

## Главное

Конфигурационный файл нужен для настроек, которые должны изменяться независимо от исходного кода.

Хорошая схема:

```text
config file
     ↓
validation
     ↓
typed C++ structures
     ↓
application
```

Главное:

* проверять входные данные;
* задавать значения по умолчанию;
* отделять конфигурацию от runtime state;
* не хранить секреты без защиты;
* не распространять JSON-объект по всему приложению.
