# Undefined Behavior

## Цель

В C++ существует особый класс ошибок, который особенно важно понимать разработчику системного программного обеспечения: **Undefined Behavior**, или неопределённое поведение.

На первый взгляд кажется, что если программа написана неправильно, она просто должна выдать ошибку. Но в C++ это не всегда так.

После урока вы должны понимать:

* что означает Undefined Behavior;
* почему программа с UB может иногда работать;
* почему результат UB нельзя предсказывать;
* какие конструкции часто приводят к неопределённому поведению;
* почему оптимизация компилятора может неожиданно менять результат;
* чем UB отличается от обычной ошибки;
* как писать код, в котором неопределённое поведение невозможно или максимально ограничено.

---

## Что означает Undefined Behavior

Undefined Behavior сокращённо называют **UB**.

Это ситуация, в которой стандарт языка C++ не определяет, что должна делать программа.

Это важнее, чем просто:

> «Произошла ошибка».

Правильнее понимать так:

> Программа нарушила требования языка, поэтому стандарт больше не гарантирует её поведение.

После этого может произойти практически что угодно.

Например, программа может:

* вывести неправильное значение;
* завершиться с ошибкой;
* продолжить работу;
* работать только в Debug;
* работать только без оптимизации;
* работать на одном компьютере и ломаться на другом.

## Простой пример

```cpp
#include <iostream>

int main() {
    int values[3] = {10, 20, 30};

    std::cout << values[10] << '\n';
}
```

Массив имеет три элемента:

```text
0 → 10
1 → 20
2 → 30
```

Обращение к:

```cpp
values[10]
```

выходит за его границы.

Программа может напечатать какое-то число.

Но это число не является корректным результатом, на который можно рассчитывать.

Нельзя сказать:

> «На моём компьютере здесь обычно получается 1234, значит так и будет».

Это ошибка.

---

## Почему программа иногда продолжает работать

Это одна из самых опасных особенностей UB.

Например:

```cpp
int values[3] = {10, 20, 30};

std::cout << values[3] << '\n';
```

Может показаться, что `values[3]` просто читает «следующее число в памяти».

Но стандарт C++ не гарантирует такого поведения.

В памяти действительно могут находиться какие-то данные:

```text
values[0] → 10
values[1] → 20
values[2] → 30
следующая область → какое-то значение
```

Но программа не имеет права обращаться к этому значению как к четвёртому элементу массива.

Если программа случайно работает, это не делает код правильным.

---

## Неопределённое поведение и компилятор

Компилятор C++ не просто переводит каждую строку один в один.

Он анализирует программу и может оптимизировать её.

При этом компилятор имеет право исходить из того, что корректная программа не содержит UB.

Это может приводить к неожиданным результатам.

Рассмотрим условный пример:

```cpp
int divide(int value) {
    return value / 0;
}
```

Деление на ноль недопустимо.

Компилятор может обнаружить проблему уже во время компиляции, а в других ситуациях UB может проявляться намного менее очевидно.

Главная идея:

> Нельзя строить логику программы на поведении, которое стандарт C++ не гарантирует.

---

## Выход за границы массива

Один из самых известных случаев:

```cpp
int values[5] = {};

for (int i = 0; i <= 5; ++i) {
    values[i] = i;
}
```

Допустимые индексы:

```text
0
1
2
3
4
```

Но условие:

```cpp
i <= 5
```

позволяет `i == 5`.

Правильно:

```cpp
for (int i = 0; i < 5; ++i) {
    values[i] = i;
}
```

Или ещё лучше — не дублировать размер вручную:

```cpp
#include <array>

std::array<int, 5> values{};

for (std::size_t i = 0; i < values.size(); ++i) {
    values[i] = static_cast<int>(i);
}
```

## Использование неинициализированных данных

Рассмотрим:

```cpp
int value;

std::cout << value << '\n';
```

Переменная объявлена, но не получила корректное начальное значение.

Нельзя использовать её как будто там находится определённое число.

Лучше:

```cpp
int value = 0;
```

Или:

```cpp
int value{};
```

Форма:

```cpp
int value{};
```

особенно полезна в современном C++, потому что явно показывает намерение и выполняет инициализацию.

---

## Висячие указатели

Рассмотрим:

```cpp
int* value = new int(42);

delete value;

std::cout << *value << '\n';
```

После `delete` объект уничтожен.

Но указатель всё ещё содержит старый адрес.

Использование:

```cpp
*value
```

после освобождения памяти приводит к неопределённому поведению.

Более безопасная современная архитектура использует владение через RAII:

```cpp
#include <memory>

auto value = std::make_unique<int>(42);

std::cout << *value << '\n';
```

Когда `value` выходит из области видимости, объект освобождается автоматически.

---

## Возвращение ссылки на локальную переменную

Рассмотрим:

```cpp
int& getValue() {
    int value = 42;
    return value;
}
```

На первый взгляд функция возвращает ссылку на `value`.

Но `value` является локальной переменной.

После завершения функции её время жизни заканчивается.

Полученная ссылка будет указывать на объект, которого больше нет.

Так делать нельзя.

Правильнее вернуть значение:

```cpp
int getValue() {
    int value = 42;
    return value;
}
```

Или вернуть ссылку только на объект, который гарантированно продолжает существовать.

---

## Переполнение знакового целого

Рассмотрим:

```cpp
#include <limits>

int value = std::numeric_limits<int>::max();

++value;
```

Для знаковых целых переполнение за пределы представимого диапазона не является обычным «переходом на минимум».

В C++ это может привести к неопределённому поведению.

Поэтому нельзя рассчитывать на такое поведение:

```text
2147483647 + 1 → -2147483648
```

Это распространённое представление о машинных целых, но оно не является корректным основанием для программы со знаковым `int`.

Если алгоритму нужен контролируемый диапазон, его нужно проверять заранее или использовать подходящий тип и правила обработки переполнения.

## Data Race

Неопределённое поведение может возникать и в многопоточном коде.

Например, два потока одновременно изменяют одну обычную переменную без синхронизации:

```cpp
int counter = 0;
```

Один поток:

```cpp
++counter;
```

Другой поток:

```cpp
++counter;
```

Если доступы конфликтуют и отсутствует необходимая синхронизация, возникает гонка данных.

Для многопоточной программы нельзя считать обычную переменную автоматически безопасной только потому, что операция выглядит простой.

Позже мы подробно разберём многопоточность и синхронизацию.

---

## Почему Debug может работать

Это очень важная ситуация.

Допустим, программа содержит ошибку:

```cpp
int values[3] = {1, 2, 3};

std::cout << values[3] << '\n';
```

В одной сборке она может вывести какое-то значение.

После включения оптимизации:

```text
Debug → работает
Release → падает
```

Это не означает, что компилятор сломал программу.

Скорее всего, программа изначально содержала UB.

Изменение:

* оптимизации;
* расположения переменных;
* версии компилятора;
* архитектуры;
* библиотек;

может изменить проявление ошибки.

---

## Почему отладчик иногда «лечит» ошибку

Ещё интереснее ситуация:

```text
без debugger → падает
с debugger → работает
```

Это тоже может быть связано с неопределённым поведением.

Отладчик может изменить:

* расположение данных в памяти;
* время выполнения;
* порядок некоторых операций;
* содержимое памяти;
* распределение стека.

Поэтому:

> Если программа начинает работать только после установки breakpoint, это повод искать ошибку, а не считать breakpoint исправлением.

---

## Как уменьшить риск UB

Хороший современный C++ код старается ограничивать количество мест, где программист напрямую управляет опасными ресурсами.

Например:

Вместо:

```cpp
int* data = new int[100];
```

предпочтительно:

```cpp
std::vector<int> data(100);
```

Вместо:

```cpp
int* value = new int(42);
delete value;
```

предпочтительно:

```cpp
auto value = std::make_unique<int>(42);
```

Вместо:

```cpp
int values[10];

for (int i = 0; i <= 10; ++i) {
    values[i] = i;
}
```

лучше:

```cpp
std::array<int, 10> values{};

for (std::size_t i = 0; i < values.size(); ++i) {
    values[i] = static_cast<int>(i);
}
```

## Инструменты поиска UB

Для поиска проблем существуют специальные инструменты.

Одни из наиболее известных — **санитайзеры**.

Например, AddressSanitizer может помогать обнаруживать:

* выход за границы;
* use-after-free;
* некоторые ошибки работы с памятью.

UndefinedBehaviorSanitizer помогает находить различные формы неопределённого поведения.

Конкретная настройка зависит от компилятора и системы сборки, но идея одна:

```text
написали код
    ↓
собрали с диагностикой
    ↓
запустили тесты
    ↓
инструмент обнаружил опасное место
```

Это значительно эффективнее, чем ждать случайного падения программы.

## Практический пример

Представим систему датчиков:

```cpp
#include <iostream>
#include <vector>

int main() {
    std::vector<double> temperatures = {
        21.5,
        22.1,
        23.0
    };

    for (std::size_t i = 0; i <= temperatures.size(); ++i) {
        std::cout << temperatures[i] << '\n';
    }
}
```

Ошибка находится в условии:

```cpp
i <= temperatures.size()
```

Последнее допустимое значение:

```cpp
temperatures.size() - 1
```

Поэтому нужно:

```cpp
for (std::size_t i = 0; i < temperatures.size(); ++i) {
    std::cout << temperatures[i] << '\n';
}
```

В реальной системе такая ошибка может привести не просто к неправильному выводу, а к повреждению состояния программы.

## Хорошее правило

Если вы видите конструкцию и думаете:

> «На моей системе это работает».

Задайте другой вопрос:

> «Гарантирует ли стандарт C++ такое поведение?»

Если ответа нет, на это поведение нельзя опираться.

---

## Главное

Undefined Behavior — это не просто «неправильный результат».

Это состояние, при котором стандарт C++ перестаёт гарантировать поведение программы.

Типичные источники UB:

* выход за границы массива;
* использование освобождённой памяти;
* обращение через недействительный указатель;
* использование невалидных объектов;
* некоторые формы переполнения;
* гонки данных;
* другие нарушения требований языка.

Самая опасная особенность UB заключается в том, что программа может выглядеть полностью рабочей.

Она может работать месяцами, а затем перестать работать после:

* обновления компилятора;
* включения оптимизации;
* изменения архитектуры;
* добавления логирования;
* изменения порядка выполнения.

Поэтому исправлять нужно не проявление UB, а его причину.
