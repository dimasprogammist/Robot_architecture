# Библиотеки и зависимости

## Цель

Практически ни один серьёзный C++ проект не существует полностью самостоятельно. Программе могут понадобиться библиотеки для работы с сетью, JSON, базами данных, графикой, логированием, математикой или аппаратными интерфейсами.

В этом уроке разберём, что такое библиотека, чем статическая библиотека отличается от динамической, что такое зависимость и как CMake связывает проект с библиотеками.

После урока вы должны понимать:

* что такое библиотека;
* зачем нужны внешние зависимости;
* чем статическая библиотека отличается от динамической;
* что такое header-only библиотека;
* что такое include и linking;
* как библиотека подключается к CMake;
* почему зависимости должны быть частью конфигурации проекта;
* какие проблемы возникают при ручном подключении библиотек.

---

## Зачем нужны библиотеки

Представим, что нам нужно отправлять HTTP-запросы.

Можно написать HTTP-клиент самостоятельно.

Но для этого придётся реализовать:

```text
TCP
HTTP
заголовки
парсинг
обработку ошибок
таймауты
TLS
...
```

Вместо этого можно использовать готовую библиотеку.

То же самое относится к:

```text
JSON
SQL
WebSocket
графике
математике
сериализации
логированию
```

Библиотека позволяет использовать уже реализованный компонент.

---

## Что такое библиотека

Упрощённо библиотека — это набор готового кода, который можно использовать из другой программы.

Например:

```text
наша программа
      ↓
библиотека JSON
      ↓
разбор JSON
```

Или:

```text
наша программа
      ↓
сетевой library
      ↓
TCP/HTTP/WebSocket
```

---

## Библиотека и заголовочный файл — не одно и то же

Это важное различие.

Заголовочный файл:

```cpp
#include "motor.h"
```

сообщает компилятору интерфейс.

Но сам код реализации должен откуда-то появиться.

Например:

```text
motor.h
motor.cpp
```

можно собрать в библиотеку:

```text
libmotor.a
```

или в динамическую библиотеку:

```text
motor.dll
```

Заголовок и библиотека выполняют разные функции.

---

## Статическая библиотека

Статическая библиотека содержит объектный код, который при линковке включается в конечную программу.

Упрощённо:

```text
program
   +
librobot
   ↓
готовое приложение
```

На Unix-подобных системах часто используется:

```text
.a
```

На Windows:

```text
.lib
```

---

## Динамическая библиотека

Динамическая библиотека загружается отдельно от основного исполняемого файла.

На Windows часто используется:

```text
.dll
```

На Linux:

```text
.so
```

На macOS:

```text
.dylib
```

Упрощённая схема:

```text
program.exe
     ↓
  motor.dll
```

Программа использует библиотеку во время выполнения.

---

## Разница между static и dynamic

Статическая:

```text
код библиотеки
     ↓
встраивается при линковке
     ↓
program
```

Динамическая:

```text
program
  ↓
загружает библиотеку отдельно
  ↓
library.dll
```

У каждого подхода есть свои преимущества и недостатки.

Статическая библиотека часто упрощает распространение приложения, но увеличивает размер итогового файла.

Динамическая библиотека позволяет нескольким программам использовать один бинарный компонент, но появляется дополнительная зависимость при запуске.

---

## Header-only библиотеки

Некоторые библиотеки практически полностью реализованы в заголовочных файлах.

Например, библиотека может использовать:

```cpp
#include <some_library.hpp>
```

и не требовать отдельного `.cpp` или `.lib`.

Такие библиотеки называют **header-only**.

Они особенно часто встречаются среди шаблонных библиотек.

---

## Что такое зависимость

Если программа не может работать без внешнего компонента, этот компонент является зависимостью проекта.

Например:

```text
robot
  ↓
JSON library
```

или:

```text
robot
  ↓
database library
```

В проекте важно явно понимать:

```text
какая зависимость нужна;
какая версия поддерживается;
где она должна находиться;
как её подключать.
```

---

## Ручное подключение

Теоретически можно вручную указать:

```text
-Ipath/to/include
-Lpath/to/lib
-lsome_library
```

Например:

```text
g++ main.cpp \
    -I./third_party/include \
    -L./third_party/lib \
    -lsome_library
```

Но для большого проекта такой подход быстро становится неудобным.

---

## Что означает -I

Опция:

```text
-I
```

задаёт путь поиска заголовочных файлов.

Например:

```text
-I./third_party/include
```

После этого:

```cpp
#include <some_library.h>
```

может найти файл в:

```text
third_party/include/
```

---

## Что означает -L

Опция:

```text
-L
```

задаёт каталог поиска библиотек.

Например:

```text
-L./third_party/lib
```

---

## Что означает -l

Опция:

```text
-lsome_library
```

указывает, что нужно связать программу с библиотекой.

Точный поиск зависит от платформы и имени файла.

---

## CMake и библиотеки

CMake позволяет описывать зависимости непосредственно в конфигурации.

Например:

```cmake
add_library(robot_devices
    src/motor.cpp
    src/sensor.cpp
)

add_executable(robot
    src/main.cpp
)

target_link_libraries(robot
    PRIVATE
        robot_devices
)
```

Теперь `robot` зависит от `robot_devices`.

---

## Внутренняя библиотека проекта

Не обязательно библиотека должна быть внешней.

Можно создать её внутри собственного проекта:

```text
robot/
├── CMakeLists.txt
├── include/
├── src/
└── tests/
```

Например:

```cmake
add_library(robot_devices
    src/devices/motor.cpp
    src/devices/sensor.cpp
)
```

А затем:

```cmake
add_executable(robot
    src/main.cpp
)
```

и:

```cmake
target_link_libraries(robot
    PRIVATE
        robot_devices
)
```

---

## Include directories библиотеки

Можно сказать CMake, где находятся заголовки:

```cmake
target_include_directories(robot_devices
    PUBLIC
        include
)
```

Здесь используется:

```text
PUBLIC
```

Это означает, что include directory является частью интерфейса цели и может понадобиться потребителям библиотеки.

---

## PUBLIC, PRIVATE и INTERFACE

В CMake часто встречаются:

```text
PUBLIC
PRIVATE
INTERFACE
```

Упрощённо:

### PRIVATE

Нужно самой цели:

```cmake
target_include_directories(robot
    PRIVATE
        src/internal
)
```

### PUBLIC

Нужно самой цели и её пользователям:

```cmake
target_include_directories(robot_devices
    PUBLIC
        include
)
```

### INTERFACE

Самой цели не нужно, но это свойство передаётся потребителям.

Например:

```cmake
target_compile_features(robot_lib
    INTERFACE
        cxx_std_20
)
```

На первых этапах достаточно хорошо понимать разницу между `PRIVATE` и `PUBLIC`.

---

## Внешние библиотеки

Для внешних библиотек CMake может использовать разные подходы.

Например:

```text
find_package(...)
```

или:

```text
FetchContent
```

или специальные менеджеры зависимостей.

Какой способ выбрать, зависит от библиотеки и проекта.

---

## find_package

Если библиотека предоставляет CMake-конфигурацию, можно написать:

```cmake
find_package(SomeLibrary REQUIRED)
```

После этого:

```cmake
target_link_libraries(robot
    PRIVATE
        SomeLibrary::SomeLibrary
)
```

Это удобная модель, потому что библиотека сама предоставляет CMake-информацию о своих include directories, библиотеках и других настройках.

---

## FetchContent

CMake также умеет получать исходники зависимостей во время конфигурации проекта.

Например:

```cmake
include(FetchContent)

FetchContent_Declare(
    SomeLibrary
    GIT_REPOSITORY https://example.com/library.git
    GIT_TAG v1.0.0
)

FetchContent_MakeAvailable(SomeLibrary)
```

После этого библиотека становится частью CMake-проекта.

Конкретный способ использования зависит от самой библиотеки.

---

## Почему нельзя просто копировать код библиотеки

Можно положить исходники внешней библиотеки прямо в:

```text
third_party/
```

Но это создаёт проблемы:

```text
как обновлять;
какую версию использовать;
как отслеживать изменения;
как собирать;
как не смешивать свой код с чужим.
```

Иногда vendor-подход оправдан, особенно для встроенных систем.

Но в обычных проектах лучше иметь понятную систему управления зависимостями.

---

## Каталог third_party

Если проект действительно хранит сторонние исходники внутри репозитория, можно использовать:

```text
third_party/
```

Например:

```text
third_party/
└── library/
```

Важно чётко отделять:

```text
наш код
```

от:

```text
стороннего кода
```

---

## Зависимость — часть проекта

Если программа использует:

```text
JSON library
```

а на компьютере разработчика она установлена вручную, но в новом окружении проект не собирается, значит зависимость не описана нормально.

Хороший проект должен позволять другому разработчику понять:

```text
что установить;
какую версию использовать;
как выполнить сборку.
```

---

## Практический пример

Представим:

```text
robot/
├── CMakeLists.txt
├── include/
│   └── robot.h
├── src/
│   ├── main.cpp
│   └── robot.cpp
└── third_party/
```

Внутри проекта создадим библиотеку устройств:

```cmake
add_library(robot_core
    src/robot.cpp
)
```

Затем:

```cmake
target_include_directories(robot_core
    PUBLIC
        include
)
```

Исполняемый файл:

```cmake
add_executable(robot
    src/main.cpp
)
```

Связываем:

```cmake
target_link_libraries(robot
    PRIVATE
        robot_core
)
```

Получаем:

```text
robot
  ↓
robot_core
```

---

## Зачем разделять библиотеки

Представим большой проект:

```text
robot_core
robot_devices
robot_network
robot_diagnostics
```

Можно сделать:

```text
application
    ↓
robot_core
    ↓
robot_devices
```

и отдельно:

```text
robot_core
    ↓
robot_diagnostics
```

Так зависимости становятся явными.

---

## Библиотека и API

Если библиотека предоставляет:

```cpp
class Motor {
public:
    void start();
    void stop();
};
```

это её API.

Пользователь библиотеки работает с:

```cpp
Motor motor;
motor.start();
```

а внутренняя реализация может измениться.

Хороший API стараются делать небольшим и понятным.

---

## Пример архитектуры

Представим систему управления промышленным устройством:

```text
application
     ↓
control
     ↓
devices
     ↓
communication
```

Каждый слой может быть отдельной библиотекой или CMake target.

Например:

```text
app
robot_control
device_drivers
protocols
```

Это уже начинает напоминать архитектуру реального программного продукта.

---

## Проблема несовместимых версий

Допустим, проект ожидает:

```text
Library 2.x
```

а на компьютере установлена:

```text
Library 1.x
```

Программа может:

```text
не собраться;
собраться с ошибками;
не запуститься;
работать иначе.
```

Поэтому версия зависимости является частью воспроизводимой сборки проекта.

## Главное

Библиотека — это готовый код, который используется другим проектом.

Она может быть:

```text
статической
динамической
header-only
```

CMake позволяет описывать зависимости:

```cmake
add_library(...)
```

```cmake
target_link_libraries(...)
```

```cmake
target_include_directories(...)
```

Для внешних библиотек могут использоваться:

```cmake
find_package(...)
```

или:

```cmake
FetchContent
```

Главная идея:

> зависимость должна быть частью описания проекта, а не скрытым условием, которое существует только на компьютере одного разработчика.
