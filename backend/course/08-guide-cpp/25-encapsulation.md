# Инкапсуляция

## Цель

Мы уже научились создавать классы, скрывать их поля и предоставлять методы для работы с объектами. Теперь соберём эту идею в одно важное понятие — инкапсуляцию.

Инкапсуляция означает организацию объекта так, чтобы его внутреннее состояние и детали реализации были защищены от неконтролируемого внешнего доступа. Внешний код должен взаимодействовать с объектом через понятный интерфейс, а сам объект должен отвечать за сохранение собственных правил.

После урока вы должны понимать:

* что такое инкапсуляция;
* зачем скрывать внутреннее состояние;
* чем интерфейс отличается от реализации;
* как `private` помогает поддерживать корректность объекта;
* почему набор getter/setter для каждого поля не всегда является хорошей архитектурой;
* как проектировать простой интерфейс класса.

---

## Что такое инкапсуляция

Представим двигатель робота.

Внутри него существует множество деталей:

```text
контроллер
датчики
регистры
скорость
ток
температура
состояние
```

Пользователю объекта необязательно знать, как именно всё это устроено.

Ему может быть достаточно нескольких операций:

```text
start()
stop()
setSpeed()
getSpeed()
```

Это и есть идея инкапсуляции: внутреннее устройство скрыто, а наружу предоставляется управляемый интерфейс.

---

## Интерфейс и реализация

Удобно разделять два понятия.

**Интерфейс** отвечает на вопрос:

> Что объект умеет делать?

Например:

```cpp
start();
stop();
setSpeed(1000);
```

**Реализация** отвечает на вопрос:

> Как именно объект это делает?

Внутри `start()` может происходить очень много действий:

```cpp
void start()
{
    checkTemperature();
    checkErrorState();
    enablePower();
    configureController();
    setSpeedInternal(1000);
}
```

Внешнему коду не нужно знать эти детали.

---

## Проблема открытых данных

Рассмотрим плохой вариант:

```cpp
class Motor
{
public:
    double speed;
    bool enabled;
};
```

Теперь любой код может написать:

```cpp
motor.speed = -500;
motor.enabled = true;
```

Класс никак не контролирует состояние.

Можно получить ситуацию:

```text
speed = -500
enabled = true
```

которая физически или логически невозможна для конкретного устройства.

---

## Скрываем состояние

Используем `private`:

```cpp
class Motor
{
private:
    double speed = 0;
    bool enabled = false;
};
```

Теперь внешний код не может напрямую изменить поля.

Нужно предоставить методы:

```cpp
class Motor
{
private:
    double speed = 0;
    bool enabled = false;

public:
    void start()
    {
        enabled = true;
    }

    void stop()
    {
        enabled = false;
        speed = 0;
    }

    void setSpeed(double value)
    {
        if (value >= 0)
        {
            speed = value;
        }
    }
};
```

Теперь класс сам контролирует свои данные.

---

## Инкапсуляция защищает правила

Предположим, скорость должна находиться в диапазоне:

```text
0..3000
```

Тогда:

```cpp
void setSpeed(double value)
{
    if (value < 0)
    {
        value = 0;
    }

    if (value > 3000)
    {
        value = 3000;
    }

    speed = value;
}
```

Внешний код может передать любое число:

```cpp
motor.setSpeed(-100);
motor.setSpeed(100000);
```

но объект не позволит нарушить свои ограничения.

---

## Инкапсуляция не равна private

Важно понимать, что инкапсуляция — это не просто использование `private`.

`private` является инструментом языка, который помогает скрывать детали.

Сама инкапсуляция — более широкая идея организации объекта:

```text
внутреннее состояние
        ↓
правила объекта
        ↓
публичный интерфейс
        ↓
внешний код
```

Класс должен предоставлять такие операции, которые позволяют корректно использовать объект.

---

## Не обязательно создавать getter и setter для каждого поля

Начинающие программисты иногда делают так:

```cpp
class Robot
{
private:
    int battery;

public:
    int getBattery();
    void setBattery(int value);
};
```

Для каждого поля создаётся по два метода.

Но это не всегда хорошая идея.

Если `battery` — заряд батареи, возможно, логичнее предоставить операции:

```cpp
charge();
consumeEnergy();
getBattery();
```

Вместо:

```cpp
setBattery(37);
```

Почему?

Потому что объект должен контролировать смысл изменения состояния.

Например:

```cpp
void consumeEnergy(int amount)
{
    if (amount < 0)
    {
        return;
    }

    battery -= amount;

    if (battery < 0)
    {
        battery = 0;
    }
}
```

Теперь изменение заряда происходит через понятную операцию.

---

## Объект должен защищать свои инварианты

Инвариант — это условие, которое должно оставаться истинным для корректного объекта.

Например, для батареи:

```text
0 <= battery <= 100
```

Для скорости:

```text
0 <= speed <= 3000
```

Для координат это может быть другое ограничение.

Если внешний код может напрямую изменять поля, инварианты легко нарушить.

Если состояние закрыто, класс может поддерживать их самостоятельно.

---

## Пример с батареей

Рассмотрим полноценный класс:

```cpp
class Battery
{
private:
    int level = 100;

public:
    int getLevel() const
    {
        return level;
    }

    void consume(int amount)
    {
        if (amount <= 0)
        {
            return;
        }

        level -= amount;

        if (level < 0)
        {
            level = 0;
        }
    }

    void charge(int amount)
    {
        if (amount <= 0)
        {
            return;
        }

        level += amount;

        if (level > 100)
        {
            level = 100;
        }
    }
};
```

Теперь внешний код не может напрямую установить:

```cpp
level = -500;
```

Он должен использовать предусмотренные операции.

---

## Интерфейс можно менять меньше

Представим, что внутри класса батарея сначала хранится как число:

```cpp
int level;
```

Через несколько месяцев реализации может понадобиться более сложная модель:

```cpp
double voltage;
double capacity;
double consumed;
```

Если внешний код работал напрямую с `level`, изменение внутренней реализации потребует переписывать множество мест.

Если же внешний код использовал:

```cpp
getLevel()
charge()
consume()
```

внутреннее устройство можно изменить, сохранив тот же интерфейс.

Это одно из главных преимуществ инкапсуляции.

---

## Инкапсуляция и робототехника

В робототехнической программе объект двигателя может выглядеть так:

```cpp
class Motor
{
private:
    double targetSpeed = 0;
    bool enabled = false;

    void sendCommand()
    {
        // Отправка команды контроллеру
    }

public:
    void start()
    {
        enabled = true;
        sendCommand();
    }

    void stop()
    {
        enabled = false;
        targetSpeed = 0;
        sendCommand();
    }

    void setSpeed(double speed)
    {
        if (speed < 0)
        {
            speed = 0;
        }

        targetSpeed = speed;

        if (enabled)
        {
            sendCommand();
        }
    }
};
```

Метод `sendCommand()` является внутренней деталью реализации.

Пользователю класса не нужно напрямую вызывать его.

Он работает с понятными операциями:

```cpp
motor.start();
motor.setSpeed(1000);
motor.stop();
```

---

## private-методы

Инкапсуляция касается не только полей.

Внутренними можно сделать и методы:

```cpp
class Motor
{
private:
    void sendCommand()
    {
        // внутренняя логика
    }

public:
    void start()
    {
        sendCommand();
    }
};
```

`sendCommand()` является частью внутренней реализации.

Это помогает не превращать публичный интерфейс класса в огромный набор технических операций.

---

## Хороший публичный интерфейс

Публичный интерфейс желательно делать:

* небольшим;
* понятным;
* логичным;
* безопасным;
* независимым от внутренних деталей.

Например:

```cpp
motor.start();
motor.stop();
motor.setSpeed(1000);
```

обычно лучше, чем предоставлять десятки низкоуровневых методов:

```cpp
motor.setRegister(12, 0x04);
motor.writeByte(7);
motor.enableBit(3);
motor.sendPacket(...);
```

Низкоуровневые операции могут существовать внутри класса, но не обязательно должны быть доступны всему приложению.

---

## Инкапсуляция и изменение проекта

Представим большую программу:

```text
Робот
 ├── управление двигателями
 ├── датчики
 ├── батарея
 ├── связь
 └── навигация
```

Если все внутренние данные доступны напрямую, любой модуль может изменить что угодно.

Получается сильная связанность:

```text
модуль A → поля B
модуль B → поля C
модуль C → поля A
```

При изменении одного класса начинают ломаться другие части программы.

Инкапсуляция позволяет ограничить такие связи:

```text
модуль A → public API
модуль B → public API
модуль C → public API
```

Внутреннее устройство каждого объекта остаётся скрытым.

---

## Практический пример

Создадим класс контроллера робота:

```cpp
#include <iostream>

class RobotController
{
private:
    bool enabled = false;
    double speed = 0;

    bool isValidSpeed(double value) const
    {
        return value >= 0 && value <= 100;
    }

public:
    void start()
    {
        enabled = true;
    }

    void stop()
    {
        enabled = false;
        speed = 0;
    }

    void setSpeed(double value)
    {
        if (!isValidSpeed(value))
        {
            return;
        }

        speed = value;
    }

    void printState() const
    {
        std::cout
            << "enabled: " << enabled
            << ", speed: " << speed
            << '\n';
    }
};

int main()
{
    RobotController robot;

    robot.start();
    robot.setSpeed(50);

    robot.printState();

    robot.stop();

    robot.printState();

    return 0;
}
```

Метод `isValidSpeed()` скрыт, потому что это внутренняя проверка. Внешнему коду достаточно знать про `start()`, `stop()`, `setSpeed()` и `printState()`.

---

## Главное

Инкапсуляция позволяет отделить внутреннее устройство объекта от его внешнего интерфейса.

Хороший класс не просто хранит данные. Он определяет правила работы с ними и не позволяет внешнему коду произвольно нарушать состояние объекта.

`private` помогает скрывать детали, а `public` формирует интерфейс, через который объект используется остальной программой.

Главная идея:

```text
Скрываем детали.
Открываем необходимые операции.
Контролируем изменение состояния.
```
