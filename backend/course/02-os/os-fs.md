# Файловая система с точки зрения ОС

## Цель

Увидеть ФС как подсистему ядра: VFS, inode/dentry, page cache, монтирование, журналирование, связь дескрипторов процесса с объектами ядра. Понять, почему «файл» — универсальная абстракция Unix-подобных систем.

## Что уже нужно понимать

Файлы и каталоги с пользовательской стороны. Ядро и syscalls. Память процесса и page cache как идея кэша ОС.

## Объяснение

Пользователь видит пути. Ядро видит объекты: суперблок ФС, inode файла, dentries кэша имён, страницы данных в page cache, открытые file-структуры, связанные с дескрипторами процесса.

**VFS** позволяет вызывать один и тот же `read`, не зная, ext4 это, xfs или FUSE-обёртка. Драйвер конкретной ФС реализует операции inode/file.

Открытие файла: разбор пути, проверка прав на каждом каталоге, создание file-объекта, выдача номера дескриптора в таблице процесса. Дальнейшие `read`/`write` идут по дескриптору — быстрее и стабильнее, чем снова искать путь (путь мог бы измениться).

Page cache хранит содержимое недавно читаных/писаных страниц. Поэтому повторное чтение «мгновенное», а `write` может вернуться до физического коммита на диск. `fsync`/`fdatasync` просят вытолкнуть данные и/или метаданные.

Монтирование присоединяет дерево ФС к точке. Без mount блочное устройство — просто блоки. Сетевые ФС монтируются похоже, но с другими отказами (сеть пропала).

Специальные ФС: `proc`, `sysfs`, `tmpfs` — интерфейсы и RAM-хранилища в форме файлов. «Всё есть файл» — принцип, а не буквальный закон для Windows, но идея мощная.

## Термины

- **VFS** — Virtual File System.
- **Inode** — объект метаданных файла.
- **Dentry** — кэш компонента пути.
- **Page cache** — кэш страниц содержимого в RAM.
- **Mount** — монтирование.
- **Дескриптор** — индекс в таблице открытых файлов процесса.
- **Журнал ФС** — лог метаопераций для целостности.

## Как это устроено

Запись: user buffer → (часто) копирование в page cache → помечаются dirty pages → writeback флашером или fsync → блоковый слой → драйвер → устройство. Метаданные (размер, mtime) обновляются по правилам ФС.

Удаление открытого файла в Unix: имя исчезает из каталога, inode жив, пока есть открытые ссылки и nlink позволяет. Процесс продолжает читать/писать «удалённый» файл — частый сюрприз при ротации логов.

Блокировки файлов (flock, lockf) — совещательные или обязательные в зависимости от системы; не все приложения их соблюдают.

Квоты, ACL, расширенные атрибуты — расширения базовой модели владельца/группы/mode.

## Пример

Сервис пишет БД-файл. Сделали `write` транзакции и сообщили клиенту «ок» без `fsync`. Питание моргнуло — транзакции нет на диске. Правильные СУБД и аккуратные встроенные хранилища думают о барьерах записи явно.

Контейнер видит свою корневую ФС как overlay: слои образа + writable layer. С точки зрения процесса это обычное дерево; с точки зрения ОС — несколько mount и union.

## Типичные ошибки

- Полагать, что успешный `write` = данные на флэше.
- Ротировать логи без reopen дескрипторов.
- Заполнять корневой раздел — ломаются сервисы неочевидно.
- Копировать устройства (`/dev/sda`) как обычные файлы без понимания.
- Игнорировать разницу локальной ФС и NFS по семантике блокировок и задержек.

## Что запомнить

Для ОС файл — объекты ядра + кэш + ФС-драйвер под VFS. Дескриптор важнее повторного пути. Буферизация ускоряет и требует fsync для надёжности. Mount определяет, что вообще видно в дереве. СпецФС — часть интерфейса ядра.

## Задание

Откройте файл в редакторе, сохраните, затем найдите его путь и размер. Сформулируйте, какие действия ядра вероятно произошли (open, write, обновление inode, возможный writeback). Проверьте свободное место на разделе — привыкайте смотреть до кризиса.

## Практика и нюансы

Проверьте `df -h` / свойства диска до того, как логи заполнят корень. Заведите ротацию и лимиты заранее. Полный диск проявляется «странными» отказами служб, не всегда явной ошибкой вашей бизнес-логики.

Для важных данных робота опишите политику durability: достаточно ли write+rename, нужен ли fsync, нужен ли второй носитель.

Изучите, куда у вас смонтированы данные: корень, `/data`, сетевой шар. Разные mount — разные риски отказа и скорости.

Не копируйте сырые устройства диска без понимания; работайте с файлами и документированными утилитами бэкапа.

## Углубление (дополнение)

Опишите durability для каждого типа записи: лог (допустима потеря хвоста), конфиг (нужна атомарность), карта (нужны бэкапы). От этого зависят fsync и схема обновления.

Мониторьте inode и block free отдельно: иногда файлы мелкие и кончаются inode раньше гигабайт.

Overlay в контейнерах скрывает, где физически данные: изучите, что переживает recreate контейнера.
