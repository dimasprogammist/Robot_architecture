# Права доступа

## Цель

Научиться читать и применять модель прав Unix-подобных систем (и сопоставить с идеей ACL/Windows): владелец, группа, mode-биты, каталоги, исполняемые файлы, типичные ошибки «permission denied».

## Что уже нужно понимать

Файлы как объекты ОС. Процесс выполняется от имени пользователя. Ядро проверяет доступ при syscall.

## Объяснение

Каждый процесс имеет **идентичность**: UID, GID, дополнительные группы, иногда capabilities. Каждый файл имеет владельца, группу и набор битов (или ACL). При `open` ядро сопоставляет «кто просит» и «что разрешено».

Классическая триада: read, write, execute — для owner, group, others. Для файла `x` значит «можно исполнить». Для каталога `x` значит «можно пройти сквозь / искать имена» (traverse); `r` — читать список имён; `w` — создавать/удалять записи в каталоге (с нюансами sticky bit).

Бит `setuid`/`setgid` на исполняемых файлах меняет эффективные права при запуске — мощно и опасно. Sticky bit на `/tmp` ограничивает удаление чужих файлов.

ACL расширяют модель точечными правилами для пользователей/групп. SELinux/AppArmor добавляют мандатный контроль сверх дискреционных прав — на hardening-системах «файл 666» всё равно может быть недоступен политикой.

Windows использует ACL и SID иначе по синтаксису, но идея та же: субъект, объект, действия, ядро-арбитр.

Права — не только файлы: доступ к устройствам (`/dev/ttyUSB0` в группе `dialout`), к портам <1024, к модулям ядра. Capabilities дробят бывший всесильный root.

## Термины

- **UID / GID** — числовые id пользователя и группы.
- **Mode** — биты rwx и спецбиты.
- **Эффективный UID** — от чьего имени проверяются права сейчас.
- **ACL** — списки контроля доступа.
- **umask** — маска прав новых файлов.
- **Sticky / setuid / setgid** — специальные биты.
- **Capability** — дробная привилегия.

## Как это устроено

Проверка пути: для каждого каталога нужен execute, чтобы пройти дальше. Поэтому «закрыть дом» можно, убрав `x` у каталога, даже если внутри файл «открыт» по mode.

Создание файла: права = запрос приложения & ~umask, владелец = эффективный пользователь (с оговорками каталога setgid).

Смена прав: `chmod`, `chown` (часто только root), `setfacl`. Сетевые ФС могут игнорировать или эмулировать иначе.

В контейнерах UID внутри и снаружи могут расходиться (user namespace) — файл «мой» в контейнере выглядит иначе на хосте.

## Пример

Скрипт `run.sh` не запускается: нет бита `x`, хотя `r` есть. `bash run.sh` читает файл как данные — другой путь. Или: конфиг робота `600` принадлежит root, сервис от user `robot` не читает — permission denied в логе. Решение: группа, ACL, или запуск от правильного пользователя, а не `chmod 777`.

`chmod 777` «чтобы заработало» открывает запись всем — недопустимо на общих машинах и часто маскирует корневую проблему владельца сервиса.

## Типичные ошибки

- Ставить 777 на всё подряд.
- Путать права файла и права каталога.
- Запускать GUI/IDE от root «чтобы видело порт» и плодить root-owned файлы в проекте.
- Игнорировать группу для доступа к `/dev`.
- Думать, что скрытие имени файла = защита содержимого без прав.

## Что запомнить

Ядро сверяет идентичность процесса с правами объекта. Каталожный `x` критичен для путей. Специальные биты и ACL усиливают модель. `permission denied` — сигнал проверить пользователя сервиса, группы и mode, а не только «файл существует». Безопасность начинается с минимально необходимых прав.

## Задание

Для одного своего скрипта/бинарника и одного конфига выпишите текущие права (или предположите разумные). Предложите mode, достаточный для работы сервиса от отдельного пользователя без мировых прав на запись.

## Практика и нюансы

Для `/dev` вашего основного адаптера посмотрите владельца и группу (`ls -l`). Добавление пользователя в группу почти всегда лучше, чем chmod 666 на устройство.

Пройдитесь по домашним ключам SSH и секретам: mode должен быть строгим. Это права доступа в чистом виде.

В CI убедитесь, что артефакты не создаются от root в workspace разработчика. Иначе локальные правки «permission denied» после пайплайна.

Запомните: отсутствие `x` на каталоге ломает доступ к файлам внутри даже при «открытых» mode файла. Диагностика пути идёт слева направо.

## Углубление (дополнение)

Правило: новый сервис стартует без root; исключения документируются. Доступ к `/dev` — через группу и udev, не через 777.

Проверяйте ACL и MAC (SELinux) если «mode правильный, а доступ закрыт». Иначе будете чинить не тот слой.

Аудит: кто владеет `/var/lib/robot` после месяца экспериментов с sudo. Периодический `find` по чужим UID спасает.
