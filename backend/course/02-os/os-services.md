# Службы

## Цель

Понять службы (демоны, services) как способ автоматически и управляемо держать фоновые процессы: автозапуск, перезапуск, зависимости, логи, отличие от «скрипт в screen».

## Что уже нужно понимать

Процессы и пользователи. ОС поднимает init после ядра. Права и файлы конфигурации.

## Объяснение

**Служба** — долгоживущий процесс (или набор), который предоставляет функцию системе или приложению: сеть, база, ваш robot-stack, сбор логов. Ею управляет супервизор: в Linux чаще **systemd**, также бывают OpenRC, SysV scripts, на Windows — Service Control Manager.

Зачем не «просто запустить вручную»? Нужны: старт после boot, рестарт при падении, порядок («сначала сеть, потом VPN, потом агент»), изоляция (лимиты CPU/RAM), единые логи, единый статус `active/failed`.

Unit-файл systemd описывает `ExecStart`, пользователя, рабочую директорию, переменные, зависимости `After=`/`Requires=`, политику `Restart=`. Это декларативный контракт, а не легенда в README.

Демонизация по-старинке (fork дважды, setsid) сегодня часто не нужна: супервизор сам держит процесс на переднем плане в своей cgroup — проще журналировать.

Контейнеры и orchestrators (Compose, Kubernetes) — другой слой супервизии, но идея та же: желаемое состояние «сервис должен быть запущен».

## Термины

- **Daemon / service** — фоновая служба.
- **Init system** — первый user-space процесс и менеджер служб.
- **Unit** — описание службы/сокета/таймера в systemd.
- **Journal** — журнал systemd.
- **Restart policy** — когда перезапускать при выходе.
- **Socket activation** — старт по входящему соединению.
- **Cgroup** — группа учёта/лимитов процессов.

## Как это устроено

Boot → ядро → init/systemd → target (multi-user) → цепочка unit. `systemctl start foo` просит менеджер породить процесс по unit. stdout/stderr часто попадают в journald. `systemctl status` показывает PID, код выхода, последние логи.

Зависимости предотвращают гонки: приложение БД не стартует до сокета БД (идеальный случай). На практике проверяйте реальные гонки: «сеть up» ≠ «DNS уже работает».

Таймеры systemd заменяют часть cron. Сокеты позволяют не держать демон постоянно.

Windows services имеют свои типы запуска и учётные записи; идеология параллельна.

## Пример

Робот должен поднять `bringup.launch` после загрузки. Вручную забывают; через `@reboot` cron нет нормальных логов и рестартов. Unit с `Restart=on-failure`, `User=robot`, `EnvironmentFile=`, `After=network-online.target` даёт предсказуемость. Упал драйвер — политика рестарта; смотрите journal и лимит StartLimitBurst, чтобы не молотить цикл.

Плохой пример: служба с `Restart=always` и мгновенным падением из-за отсутствующего устройства — спам логов и износ. Нужен `RestartSec`, исправление причины, health-check.

## Типичные ошибки

- Держать прод на `tmux`/`screen` без супервизора.
- Забывать `WantedBy`/`enable` — после reboot тишина.
- Запускать службу от root без нужды.
- Игнорировать `StartLimit` и flapping.
- Путать «процесс жив» с «сервис готов принимать работу» — нужны probes.

## Что запомнить

Службы — управляемые долгоживущие процессы под супервизором ОС. Описывайте старт, пользователя, зависимости и рестарт явно. Логи и статус — через менеджер, не через легенды. Для роботов автозапуск стека — часть надёжности, не «удобство лени».

## Задание

Набросайте текст unit (или словесный аналог для вашей ОС) для одного своего скрипта: кто пользователь, какая команда старта, после чего стартовать, нужен ли рестарт. Не обязательно устанавливать — важна полнота описания.

## Практика и нюансы

Переведите один свой «ручной» долгоживущий процесс в черновик unit/service описания. Даже не устанавливая, вы обнаружите дыры: нет User, нет абсолютного пути, нет RestartSec.

Проверьте `systemctl status` / аналог после reboot-теста. Автозапуск, который не проверен холодным стартом, не существует.

Настройте просмотр логов службы одной командой и сохраните её в README эксплуатации. Без логов супервизор бесполезен.

Избегайте Restart=always без анализа причины падения: вы получите storm. Сначала root cause, потом агрессивный restart.

## Углубление (дополнение)

Cold boot тест обязателен для любого unit автозапуска. «У меня после login работало» не считается.

Логи службы читайте через journal с unit-фильтром; сохраните команду в runbook. RestartSec и StartLimitBurst настройте против flapping.

Healthcheck «процесс жив» недостаточен: нужен признак готовности принимать работу (сокет, файл ready, HTTP health).
