# Процессы и память процесса

## Цель

Увидеть процесс глазами ОС: структуры учёта, виртуальное адресное пространство, отображение на физические страницы, копирование при записи, утечки и лимиты. Связать «переменные программы» с механизмом ядра.

## Что уже нужно понимать

Что такое процесс и поток. RAM и виртуальная память на уровне идеи. Роль ядра в выделении ресурсов.

## Объяснение

Для ядра процесс — объект: PID, учётные данные, таблица файлов, сигнальная маска, приоритеты, mm_struct (память) и т.д. Программа думает переменными; ядро думает **страницами** и **VMA (virtual memory areas)**.

Виртуальное адресное пространство даёт каждому процессу иллюзию большого непрерывного диапазона адресов. Физические фреймы подкладываются по мере нужды. Два процесса могут иметь одинаковые виртуальные адреса, указывающие на разные физические страницы — изоляция.

При `fork` классически применяется copy-on-write: страницы помечаются разделяемыми до записи; при попытке изменить — копия. Это дёшево создаёт процессы. `exec` разбирает новый образ и перестраивает отображения.

Сегменты: код (часто RX), данные, heap (brk/mmap), стеки потоков, анонимные отображения, file-backed (библиотеки, mmap файлов). RSS — резидентные страницы; VSZ — виртуальный размер, часто больше и пугает новичков зря.

ОС может overcommit (выделить виртуально больше, чем есть физики) с разной политикой — отсюда внезапный OOM позже, не в момент malloc. На встраиваемых системах политики строже.

Разделяемая память и shm — осознанное нарушение «полной изоляции» для скорости IPC под контролем ОС.

## Термины

- **VMA** — область виртуальной памяти процесса.
- **Page table** — таблицы трансляции вирт→физ.
- **COW** — copy-on-write.
- **RSS / VSZ** — резидентный и виртуальный размеры.
- **Anonymous memory** — память не на файле (куча, стек).
- **File-backed** — страницы, связанные с файлом.
- **OOM** — out of memory, политика при исчерпании.

## Как это устроено

Обращение к ещё не выделенной странице кучи → page fault → ядро выделяет нулевой фрейм → продолжение. Обращение к файлу mmap → fault → чтение блока с носителя в страничный кэш → отображение.

Защита: попытка писать в RX-страницу кода → fault → SIGSEGV. NX-бит не даёт исполнять стек по умолчанию (с оговорками и эксплойт-митигациями).

Лимиты: `ulimit -v`, cgroup memory max в контейнерах. Робот в Docker с лимитом 512 МБ будет убит при утечке — это защита хоста.

Инструменты: `/proc/PID/maps`, `pmap`, `smem`, профилировщики кучи. Они читают взгляд ОС на память процесса.

## Пример

Сервис на Python держит кэш словарей. VSZ большой из-за аллолятора и отображений; RSS растёт с кэшем. После очистки кэша RSS может не вернуться к ОС сразу из-за поведения аллолятора — «утечка» или удерживаемый пул? Смотрят тренды и профилировщик, не одну цифру VSZ.

`fork` большого процесса без немедленного exec временно рискует давлением COW при записи. Паттерн prefork серверов учитывает это.

## Типичные ошибки

- Паниковать из-за большого VSZ.
- Путать утечку с ростом кэша ОС (page cache — не RSS вашего процесса).
- Игнорировать cgroup-лимиты в контейнере.
- Считать, что `free()` всегда мгновенно отдаёт страницы ОС.
- Делить сложные структуры между процессами без IPC, ожидая «общую кучу».

## Что запомнить

Процесс для ОС — учёт + виртуальная память из областей и страниц. Изоляция через таблицы страниц. COW ускоряет fork. RSS важнее VSZ для «сколько физики съели». Лимиты и OOM — реальные механизмы, не теория.

## Задание

Для одного своего процесса посмотрите потребление памяти в диспетчере или `ps`. Если доступен `/proc/PID/maps` или аналог, найдите упоминание стека или библиотеки. Запишите разницу между «память процесса» и «файлы на диске».

## Практика и нюансы

Снимите RSS ключевых процессов стека до и после типичной нагрузки (карта, камера). Заведите порог алерта. Память — ресурс с потолком; лучше узнать о росте по графику, чем по OOM mid-demo.

В контейнере намеренно поставьте низкий memory limit на тестовом сервисе с утечкой и посмотрите, кто убивает процесс. Это лучший учебный стенд по cgroup.

Не оптимизируйте VSZ. Смотрите RSS, тренды, профили кучи. Для Python дополнительно учитывайте фрагментацию аллокаторов и кэши.

Документируйте ожидаемый бюджет памяти на изделие так же, как бюджет CPU и диска.

## Углубление (дополнение)

Введите алерт на рост RSS за сутки при постоянной нагрузке. Утечки ловят трендом, не абсолютом.

В контейнере тестируйте memory.max до продакшена. Лучше увидеть OOM на стенде, чем в демо.

Не делайте огромный fork без exec тяжёлого процесса зря — COW может ударить в момент записи. Prefork-паттерны учитывают это.
