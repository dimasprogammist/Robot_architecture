# Как приложения разговаривают с ОС

## Цель

Свести воедино модель общения приложения с операционной системой: язык → стандартная библиотека → системные вызовы → ядро; понятия API и ABI; что видит разработчик на Python/C/Go и что происходит «под капотом».

## Что уже нужно понимать

Весь модуль OS и база computer: процессы, файлы, права, запуск, сигналы, службы. Граница user/kernel.

## Объяснение

Приложение почти никогда не «прыгает в ядро» вручную из высокоуровневого кода. Цепочка типична:

1. Ваш код вызывает функцию языка или библиотеки (`open`, `socket`, `Thread.start`, `subprocess.run`).
2. Runtime/стандартная библиотека готовит аргументы и выполняет syscall (или вызывает libc).
3. **libc** (glibc, musl) или аналог — главный посредник для C-экосистемы.
4. Инструкция syscall/svc/sysenter переключает режим в ядро.
5. Ядро выполняет работу и возвращает код результата / errno.

**API** — программный контракт для человека и компилятора: имена функций, семантика. **ABI** — двоичный контракт: размеры структур, calling convention, номера syscall, формат объектных файлов. Можно сохранить API и сломать ABI (нужна пересборка). Дистрибутивы берегут ABI ядра и glibc внимательно.

Языки отличаются толщиной runtime: C тонкий; Python тяжёлый (интерпретатор, GC); Go сам делает syscalls и планирует горутины; JVM — ещё слой. Но все упираются в услуги ядра для I/O, процессов, памяти.

Помимо raw syscall есть интерфейсы «файлами»: `/proc`, `/sys`, netlink, ioctl на устройствах. Это тоже разговор с ОС, только через VFS и спецканалы.

Совместимость: контейнер с musl vs хост с glibc; Windows Subsystem; эмуляция. Понимание слоя спасает от мистики «на этой машине не линкуется».

## Термины

- **API** — Application Programming Interface.
- **ABI** — Application Binary Interface.
- **libc** — стандартная библиотека C как мост к ядру.
- **errno** — код ошибки после неудачного вызова.
- **Runtime** — среда исполнения языка.
- **ioctl / fcntl** — расширенное управление fd/устройствами.
- **POSIX** — семейство стандартов переносимых API.

## Как это устроено

Пример чтения файла на C: `fread` буферизует в user space → при необходимости `read` syscall → ядро копирует из page cache. На Python `f.read()` → слой файлового объекта → CPython → read. На Go `os.ReadFile` → syscall обёртки.

Сетевой сервер: `socket/bind/listen/accept/epoll_wait` — явный разговор. Фреймворки прячут это, но при отладке таймаутов вы снова спускаетесь к этим вызовам.

Права и изоляция проверяются в ядре при syscall, не в «честности» библиотеки. Вредоносная программа может делать syscall напрямую, минуя libc — политика безопасности должна учитывать это (seccomp, sandbox).

Версионирование: новые syscalls появляются с ядром; старый userland на новом ядре обычно ок; новый userland на очень старом ядре — нет. Отсюда минимальные версии в документации дистрибутивов и контейнерных образов.

## Пример

`subprocess.run(["ls"])` в Python: интерпретатор делает fork/exec (или posix_spawn), передаёт env, ждёт код выхода — всё через ОС. Пайп stdout — pipe fd, наследуемые дескрипторы, read в родителе.

Другой пример: запись лога в файл и отправка метрики по UDP — два класса syscall (fs и net). Если диск заполнен, write вернёт ошибку; сеть может терять UDP без ошибки приложения — семантика канала разная, хотя «разговор с ОС» с обеих сторон есть.

## Типичные ошибки

- Думать, что высокоуровневый язык «обходится без ОС».
- Путать ошибку библиотеки с отказом ядра без чтения errno/cause.
- Смешивать ABI разных libc в одном процессе неосторожно.
- Игнорировать буферизацию stdio при отладке.
- Считать ioctl «магией» вместо документированного контракта драйвера.

## Что запомнить

Приложения говорят с ОС через библиотеки и syscalls. API удобен людям; ABI обязан совпадать у двоичников. Ядро остаётся арбитром ресурсов и прав. Разные языки — разная толщина обёртки, одна модель услуг. Отладка сложных сбоев часто требует спуска на уровень вызовов ОС.

## Задание

Выберите три операции в своём коде (файл, сеть или процесс, время/случайность). Для каждой назовите вероятный класс услуги ОС. Если можете — найдите в документации языка, какая нижнеуровневая функция/модуль это оборачивает.

## Практика и нюансы

Возьмите один вызов высокого уровня (`Path.read_text`, `requests.get`, `subprocess.run`) и спуститесь на один слой документации ниже. Назовите, какие услуги ядра задействованы. Упражнение снижает страх перед «магией фреймворка».

При странных отказах смотрите errno/cause, а не только текст исключения фреймворка. Часто там EACCES, ENOENT, ETIMEDOUT — точный класс.

Сверяйте libc и архитектуру при переносе бинарников между образами. «На Ubuntu собрал — на Alpine не бежит» — классика ABI.

Seccomp и drop capabilities — следующий уровень защиты сервисов робота, когда базовые права уже настроены. Не начинайте с них, но знайте, что разговор с ОС можно сужать.

## Углубление (дополнение)

Для трёх ключевых операций кода выпишите цепочку до syscall-класса. Это упражнение снимает страх фреймворков и ускоряет чтение strace.

Ловите errno/cause в обёртках: ETIMEDOUT vs ECONNREFUSED лечатся по-разному.

ABI: не копируйте `.so` между дистрибутивами без проверки. Собирайте в том же userland, где бежите, или используйте переносимые артефакты (wheels, static, контейнер).


## Закрепление

Три операции кода → класс syscall в документации модуля.

Читайте errno/cause, не только текст фреймворка.

Сборка в том же ABI, где исполнение.

Seccomp/caps — после базовых прав, не вместо них.

Три операции кода → класс syscall в документации модуля.
