# Ввод и вывод

Когда программа получает температуру с датчика, читает файл или принимает сетевой пакет, для неё всё это выглядит довольно просто:

```python
temperature = read_sensor()
```

Но за этой строкой может скрываться целая цепочка. Данные проходят через контроллер устройства, драйвер, ядро операционной системы, буферы и только потом становятся доступны программе.

```text
датчик
  ↓
контроллер
  ↓
драйвер
  ↓
ядро
  ↓
буфер
  ↓
программа
```

Эта цепочка называется **вводом-выводом**, или I/O (Input/Output). В этом уроке разберём, как данные перемещаются между программой и устройствами, зачем нужны драйверы, буферы, прерывания и DMA и почему задержки I/O особенно важны для робототехники.

## Что такое I/O

I/O — это обмен данными между вычислительной системой и внешними по отношению к конкретной операции источниками или приёмниками данных.

**Input** — данные поступают в компьютер:

```text
клавиатура
камера
датчик
USB-устройство
сетевая карта
UART
диск
```

**Output** — компьютер передаёт данные наружу:

```text
экран
динамик
мотор
UART
сетевая карта
диск
```

При этом понятия «ввод» и «вывод» определяются относительно системы. Например, сетевой пакет, пришедший с Ethernet-интерфейса, является вводом для компьютера, даже если для другой системы этот же пакет был исходящим.

I/O — это не только физические устройства. Для программы источником или приёмником данных могут быть файл, сокет, последовательный порт, устройство хранения или другой объект операционной системы:

```python
data = file.read(1024)
```

```python
data = socket.recv(1024)
```

```python
data = serial.read(100)
```

С точки зрения программы во всех случаях происходит получение данных, хотя внутри ОС эти операции устроены по-разному.

## Как программа получает данные

Программа обычно не управляет устройством непосредственно. Она обращается к операционной системе через предоставленный ей интерфейс.

Упрощённая модель выглядит так:

```text
+-----------------------------+
|          ПРОГРАММА          |
|          user space         |
+-------------+---------------+
              | системный вызов
              ↓
+-----------------------------+
|             ЯДРО            |
|                             |
| файловая система            |
| сетевой стек                |
| драйверы                    |
+-------------+---------------+
              ↓
+-----------------------------+
|          КОНТРОЛЛЕР         |
|      USB / SATA / UART      |
|          / NIC              |
+-------------+---------------+
              ↓
+-----------------------------+
|          УСТРОЙСТВО         |
|    SSD / камера / датчик    |
+-----------------------------+
```

Это упрощённая схема: конкретный путь зависит от устройства и архитектуры ОС. Например, сетевой пакет проходит через сетевой стек, а чтение файла — через файловую систему и подсистему хранения.

Главная идея в другом: **программа работает с абстракцией, а ядро и драйверы скрывают от неё значительную часть аппаратных деталей**.

Программе не нужно знать, в какие регистры USB-контроллера записывать значение, где именно на SSD находится блок файла или как сетевая карта физически принимает пакет.

## Драйвер связывает ОС и устройство

**Драйвер** — программный компонент, который обеспечивает взаимодействие операционной системы с определённым устройством или классом устройств.

Упрощённо:

```text
программа
    ↓
ядро
    ↓
драйвер
    ↓
контроллер
    ↓
устройство
```

Приложение камеры, например, не обязано самостоятельно управлять USB-контроллером. Оно использует интерфейс, который предоставляет ОС, а драйвер переводит операции более высокого уровня в конкретные действия с оборудованием.

Поэтому драйвер является важной частью границы между программным и аппаратным миром. Ошибка обычного приложения чаще всего приводит к завершению этого приложения, а ошибка привилегированного драйвера в некоторых системах может повлиять на работу всей ОС.

## Буферы: почему данные не всегда идут напрямую

Одно из главных понятий I/O — **буфер**.

Буфер — это область памяти, в которой данные временно хранятся перед передачей дальше. Он нужен потому, что источник и получатель редко работают с одинаковой скоростью.

Например, камера может выдавать кадры с одной скоростью, а программа обрабатывать их с другой:

```text
камера
  ↓
буфер
  ↓
программа
```

Без промежуточного хранения любое кратковременное расхождение скоростей было бы гораздо сложнее обрабатывать.

Буферы встречаются на нескольких уровнях:

```text
устройство
    ↓
буфер контроллера
    ↓
буфер ядра
    ↓
буфер библиотеки
    ↓
буфер программы
```

Поэтому даже простая команда:

```python
print("Alarm!")
```

не обязательно означает, что текст уже физически оказался на конечном устройстве вывода. Между программой и устройством могут находиться дополнительные буферы.

Это важно и при диагностике. Например:

```python
print("Ошибка датчика", flush=True)
```

заставляет соответствующий пользовательский буфер передать данные дальше по цепочке. Но `flush()` не означает, что данные мгновенно записаны на физический носитель или уже получены удалённой системой.

## Почему программа иногда ждёт

Устройства обычно значительно медленнее CPU. Если процессор будет постоянно проверять состояние устройства:

```python
while not sensor_ready():
    pass
```

он тратит вычислительное время на активное ожидание.

Это называется **busy-waiting**.

```text
CPU
 |
 +-- проверка
 +-- проверка
 +-- проверка
 +-- проверка
 |
 +-- данные появились
```

Busy-wait может быть оправдан в некоторых низкоуровневых задачах, особенно когда ожидание очень короткое и предсказуемое. Но для обычного I/O такой подход часто неэффективен.

Гораздо чаще используется ожидание, при котором поток перестаёт занимать процессор.

## Блокирующий и неблокирующий I/O

При **блокирующем I/O** операция может приостановить текущий поток до появления результата.

Например:

```python
data = socket.recv(1024)
```

Если данных пока нет, поток может перейти в состояние ожидания:

```text
поток
  ↓
recv()
  ↓
данных нет
  ↓
ожидание
  ↓
данные появились
  ↓
продолжение работы
```

Важно: блокируется не обязательно весь процессор или весь процесс. Блокируется конкретный поток, а планировщик ОС может в это время выполнять другие потоки.

```text
Процесс
+------------------------+
| Поток 1 -> ждёт сеть   |
| Поток 2 -> считает     |
| Поток 3 -> пишет лог   |
+------------------------+
```

При **неблокирующем I/O** операция не обязана ждать появления данных. Она может сразу сообщить программе, что данных пока нет.

```text
программа
    ↓
проверка
    |
    +-- данные есть -> читать
    |
    +-- данных нет -> продолжить работу
```

Неблокирующая модель особенно полезна, когда один поток обслуживает много источников данных. В Unix-подобных системах для этого применяются, например, `select`, `poll`, `epoll`, а в Windows есть другие механизмы, включая IOCP.

Конкретные API различаются, но принцип одинаковый: **программа сообщает ОС, какие каналы её интересуют, а ОС уведомляет её, когда с ними можно работать**.

## Прерывания

Не всегда система сама должна постоянно спрашивать устройство о его состоянии. Устройство может сообщить о событии самостоятельно.

Для этого используются **аппаратные прерывания**.

Например, сетевая карта получила пакет:

```text
сетевая карта
      | "данные готовы"
      ↓
     CPU
      ↓
обработчик ядра
```

CPU временно переключается на обработку события, после чего продолжает выполнение прерванного кода.

Без такого механизма процессору пришлось бы постоянно опрашивать устройство:

```text
CPU -> данные есть?
CPU -> данные есть?
CPU -> данные есть?
CPU -> данные есть?
```

Прерывания особенно полезны для событий, которые происходят нерегулярно.

Однако прерывания тоже требуют ресурсов. Если устройство генерирует огромное количество событий, CPU может потратить значительную часть времени только на их обработку. Поэтому высокоскоростные устройства используют дополнительные механизмы, в том числе DMA.

## DMA: передача данных без копирования каждого байта CPU

**DMA (Direct Memory Access)** позволяет контроллеру устройства передавать данные непосредственно между устройством и оперативной памятью, не заставляя CPU вручную переносить каждый байт.

Упрощённо без DMA:

```text
устройство
    ↓
   CPU
    ↓
   RAM
```

При использовании DMA:

```text
             CPU
              | настроить передачу
              ↓
        DMA / контроллер
              ↓
             RAM
              ^
          устройство
```

CPU задаёт параметры операции, после чего аппаратный механизм выполняет сам перенос.

DMA **не означает, что CPU вообще не участвует**. CPU по-прежнему запускает или настраивает операцию и обрабатывает результат. Главное преимущество в том, что ему не нужно вручную переносить каждый байт большого блока данных.

Это особенно важно для сетевых карт, дисков, камер и других устройств, которые передают большие объёмы информации.

Например, сетевой пакет может проходить примерно так:

```text
1. пакет приходит на сетевую карту
2. контроллер записывает данные в RAM через DMA
3. система получает уведомление
4. драйвер и сетевой стек обрабатывают данные
5. данные становятся доступны сокету
6. программа читает их
```

CPU всё равно выполняет существенную работу, но перенос самого большого блока данных между устройством и RAM выполняется эффективнее.

## Полный путь данных

Теперь можно собрать несколько механизмов в одну картину.

Представим камеру:

```text
камера
  ↓
контроллер
  ↓
DMA
  ↓
RAM
  ↓
драйвер
  ↓
ядро
  ↓
буфер
  ↓
программа
```

Конкретная реализация может отличаться, но роли хорошо видны:

* устройство создаёт или принимает данные;
* контроллер обеспечивает аппаратный обмен;
* DMA помогает переносить большие блоки;
* драйвер связывает устройство с ОС;
* ядро управляет этим обменом;
* буферы временно хранят данные;
* программа использует результат.

Для UART путь может выглядеть проще:

```text
датчик
  ↓
UART
  ↓
контроллер
  ↓
драйвер
  ↓
буфер ОС
  ↓
read()
  ↓
программа
```

Если датчик передал:

```text
T=24.7
```

программа получает набор байтов, а уже её код разбирает протокол и превращает данные в значение `24.7`.

Это важное разделение ответственности: **ОС доставляет данные, но смысл этих данных обычно определяет приложение**.

## I/O в робототехнике

Для робота ввод-вывод особенно важен, потому что одновременно работают десятки источников и потребителей данных:

```text
камера
лидар
IMU
энкодеры
UART
CAN
Ethernet
мотор-контроллеры
```

У каждого канала свои требования к частоте, объёму данных и времени реакции.

Например:

```text
+----------+----------+----------------+
| Источник | Частота  | Размер данных  |
+----------+----------+----------------+
| IMU      | 1 кГц    | небольшой      |
| Энкодер  | 500 Гц   | небольшой      |
| Лидар    | 10 Гц    | большой        |
| Камера   | 30 Гц    | очень большой  |
+----------+----------+----------------+
```

Но одной частоты недостаточно. Важны также **latency**, **throughput**, джиттер, размер буфера и допустимость потери данных.

**Latency** — задержка от момента появления события до момента, когда программа получила или обработала результат.

**Throughput** — объём данных, который система способна передавать или обрабатывать за единицу времени.

Например, канал с пропускной способностью `100 MB/s` не обязательно обеспечивает минимальную задержку каждого отдельного сообщения. Между источником и программой могут находиться очереди, буферы, планировщик, драйвер и другие уровни.

Поэтому высокая скорость передачи и низкая задержка — разные характеристики.

## Очереди и переполнение

Представим датчик, который выдаёт 100 сообщений в секунду, а программа успевает обрабатывать только 80:

```text
получено:   100 сообщений/с
обработано:  80 сообщений/с
```

Разница в 20 сообщений в секунду постепенно накопится в очереди.

Если очередь неограниченная, она в конце концов займёт всю доступную память. Поэтому реальная система должна иметь определённую политику переполнения:

```text
block       -> остановить производителя
drop oldest -> удалить самые старые данные
drop newest -> удалить новые данные
throttle    -> уменьшить скорость поступления
```

Выбор зависит от задачи.

Для камеры старый кадр часто уже не представляет интереса: если система обрабатывает изображение с задержкой, может быть полезнее пропустить старые кадры и взять самый свежий.

Для другого протокола потеря одного сообщения может быть недопустима.

В робототехнике важно также контролировать **свежесть данных**. Наличие последнего значения ещё не означает, что оно актуально:

```text
скорость = 2.0 м/с
timestamp = 12:00:00.100

датчик отключился

текущее время = 12:00:01.500
```

Программа всё ещё может иметь значение `2.0`, но оно уже устарело. Поэтому полезно хранить не только само значение, но и время получения, а иногда ещё флаг `↓alid` или состояние источника.

## I/O и контур управления

Представим управляющий цикл робота:

```text
датчики
   ↓
расчёт
   ↓
команды моторам
   ↓
следующий цикл
```

Если внутри этого цикла выполнять потенциально медленную операцию:

```python
sa↓e_log_to_disk()
```

то управление начнёт зависеть от скорости файловой системы и накопителя:

```text
датчики
   ↓
расчёт
   ↓
запись на диск
   ↓
задержка
   ↓
моторы
```

Часто лучше отделить критический контур от медленного I/O:

```text
                 +------------------+
                 |    управление    |
датчики -------->| расчёт -> моторы |
                 +--------+---------+
                          ↓
                       очередь
                          ↓
                 +------------------+
                 |   логирование    |
                 |    диск/сеть     |
                 +------------------+
```

Теперь задержка записи файла не обязана напрямую останавливать управляющий цикл.

Это не универсальное правило: архитектура зависит от требований конкретной системы. Но общий принцип важен — **критические по времени операции не следует бездумно связывать с потенциально медленным I/O**.

## Ошибки ввода-вывода

I/O может завершиться не только успехом.

Возможны:

```text
обрыв кабеля
устройство отключено
таймаут
ошибка CRC
буфер переполнен
ошибка драйвера
повреждённый пакет
```

При этом разные ситуации имеют разный смысл.

Например:

```text
данных пока нет
```

не то же самое, что:

```text
устройство отключилось
```

Для неблокирующего сокета отсутствие данных может быть совершенно нормальной ситуацией. Для датчика потеря связи может означать необходимость перейти в безопасное состояние.

Поэтому приложение должно понимать не только значение данных, но и состояние источника.

## Блокирующий или неблокирующий I/O?

Универсального победителя нет.

Блокирующий I/O часто хорошо подходит, когда поток может спокойно ждать и ожидание не мешает остальной программе. Например, отдельный поток может блокироваться на чтении одного устройства.

Неблокирующий или событийный подход полезен, когда один поток должен обслуживать большое количество каналов или нельзя надолго останавливать выполнение.

Поэтому выбор модели I/O должен определяться архитектурой программы:

```text
простая задача
    |
    ↓
блокирующий I/O
```

или:

```text
много каналов
    |
    ↓
событийная / неблокирующая модель
```

Главное — понимать, **что именно блокируется, на какое время и какие задачи от этого зависят**.

## Практика

### Задание 1. Проследите путь данных

Выберите один источник:

```text
файл
сокет
UART
USB-датчик
камера
```

Нарисуйте реальный путь данных от источника до вашей программы. Не нужно искусственно добавлять каждый уровень из общей схемы — определите, какие компоненты действительно участвуют.

### Задание 2. Найдите буферы

Для выбранного канала определите:

1. где находятся буферы;
2. кто записывает в них данные;
3. кто их читает;
4. что происходит при переполнении;
5. можно ли терять старые данные.

### Задание 3. Посчитайте поток

Пусть датчик отправляет 100 сообщений в секунду по 100 байт:

```text
100 * 100 = 10000 байт/с
```

Это примерно 10 КБ/с.

Теперь оцените, какой запас буфера понадобится, если программа может не обрабатывать данные, например, 200 мс.

### Задание 4. Найдите опасный I/O

В своём проекте найдите операции:

```text
чтение файла
запись файла
сетевой запрос
чтение датчика
отправка команды
```

Для каждой подумайте:

* может ли она блокироваться;
* сколько она может занимать;
* что произойдёт при задержке;
* можно ли вынести её из основного потока.

## Типичные ошибки

**«I/O — это только файлы».**

Нет. I/O включает файлы, сеть, USB, UART, камеры, диски и множество других каналов обмена данными.

**«DMA полностью освобождает CPU».**

Нет. CPU всё равно настраивает передачу и обрабатывает результат. DMA прежде всего избавляет его от ручного переноса каждого байта.

**«Прерывание означает, что CPU ничего не делает».**

Нет. Прерывание сообщает процессору о событии, после чего система выполняет необходимую обработку.

**«Если `write()` завершился успешно, удалённая система уже получила данные».**

Не обязательно. Между программой и конечным получателем могут находиться пользовательские и системные буферы, TCP-стек, драйвер, сетевой контроллер и сама сеть.

**«Нужно всегда использовать неблокирующий I/O».**

Нет. Блокирующий вариант часто проще и вполне подходит, если ожидание происходит в правильном потоке.

**«Очередь должна быть бесконечной».**

Нет. Если производитель стабильно быстрее потребителя, бесконечная очередь в итоге заполнит память. Нужна явная политика переполнения.

**«Последнее значение датчика можно использовать сколько угодно».**

Нет. Для систем управления важна не только величина, но и её свежесть.

## Что нужно запомнить

I/O связывает вычислительную систему с внешним миром. Программа обычно работает не с аппаратным устройством напрямую, а через интерфейсы ОС, ядро и драйверы.

Упрощённая цепочка ввода:

```text
УСТРОЙСТВО
     |
     ↓
КОНТРОЛЛЕР
     |
     ↓
ДРАЙВЕР
     |
     ↓
ЯДРО
     |
     ↓
БУФЕР
     |
     ↓
ПРОГРАММА
```

Для вывода направление меняется.

Главные идеи:

1. I/O — это обмен данными между программой и внешними источниками или приёмниками.
2. Драйвер связывает ОС с конкретным устройством.
3. Буферы компенсируют разницу скоростей между производителем и потребителем данных.
4. Блокирующий I/O может приостановить текущий поток до появления результата.
5. Неблокирующий I/O позволяет продолжить выполнение, если данных пока нет.
6. Прерывания позволяют устройствам сообщать системе о событиях.
7. DMA позволяет эффективнее передавать большие блоки данных между устройством и RAM без ручного копирования каждого байта CPU.
8. У I/O важны не только throughput, но и latency, джиттер, размер буфера и политика обработки переполнения.
9. В робототехнике нужно учитывать актуальность данных и не связывать критический контур управления с медленным I/O без необходимости.

Главная инженерная мысль:

> **I/O — это не просто вызов `read()` или `write()`. Это целая цепочка передачи данных между устройством, памятью, ядром и программой. От архитектуры этой цепочки зависят задержки, пропускная способность, устойчивость системы и её поведение при ошибках.**

## Связь со следующим уроком

Мы уже разобрали основные элементы компьютера: CPU выполняет инструкции, память хранит данные, процессы и потоки обеспечивают выполнение программ, ядро управляет ресурсами, а I/O связывает систему с внешним миром.

Теперь эти элементы можно собрать в одну аппаратную картину.

Следующий урок — **устройство современного компьютера**: процессорные ядра, кэш, RAM, шины, контроллеры, накопители и периферия как части одной системы.
