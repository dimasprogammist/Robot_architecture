# Пользовательское пространство и ядро

Мы уже знаем, зачем операционной системе нужен доступ к CPU, памяти, дискам и устройствам. Но теперь возникает более глубокий вопрос: **почему обычная программа не получает такой же доступ, как само ядро ОС?**

Если дать любому приложению полный контроль над компьютером, ошибка в одной программе может повредить память другой программы, данные ядра или состояние устройств. Вредоносная программа получила бы ещё больше возможностей.

Поэтому современный процессор вместе с ОС разделяет выполнение кода по уровням привилегий.

Упрощённая модель выглядит так:

```text
┌-----------------------------┐
|         USER SPACE          |
| Python / C++ / браузер      |
| сервер / редактор           |
└--------------┬--------------┘
               | контролируемый переход
               ↓
┌-----------------------------┐
|        KERNEL SPACE         |
| ядро ОС / драйверы          |
└--------------┬--------------┘
               ↓
┌-----------------------------┐
|           ЖЕЛЕЗО            |
| CPU / RAM / SSD / USB / NIC |
└-----------------------------┘
```

Это не означает, что user space и kernel space — две разные физические области памяти или два отдельных компьютера. Это прежде всего **разные уровни привилегий и доступа**, которые реализуются процессором и ОС.

## User space

**User space** — среда, в которой обычно выполняется код приложений.

Например:

```text
браузер
Python-программа
C++-программа
терминал
сервер
графический редактор
```

Каждый процесс имеет собственное виртуальное адресное пространство. Упрощённо его можно представить так:

```text
   процесс A            процесс B
┌-------------┐      ┌-------------┐
| код         |      | код         |
| данные      |      | данные      |
| heap        |      | heap        |
| stack       |      | stack       |
└-------------┘      └-------------┘
```

Процесс A не может просто взять указатель и прочитать произвольную память процесса B. Аппаратный механизм виртуальной памяти и настройки ОС ограничивают доступ к страницам памяти.

Это одна из причин, почему ошибка в обычной программе обычно приводит к падению только этой программы.

## Kernel space

**Kernel space** — среда, в которой выполняется привилегированный код операционной системы.

Там находятся ядро и различные системные подсистемы, например:

```text
планировщик
управление памятью
файловые системы
сетевой стек
драйверы
управление устройствами
```

Упрощённо:

```text
USER SPACE
    |
    ├-- процесс A
    ├-- процесс B
    └-- процесс C
             ↓
       KERNEL SPACE
       ┌-----┼-----┐
       ↓     ↓     ↓
     память  сеть  устройства
```

Важно не воспринимать эту схему буквально. Конкретная организация памяти зависит от архитектуры CPU и ОС. В некоторых системах ядро и пользовательские адресные пространства организованы по-разному.

Главная идея остаётся неизменной:

> **обычный код не должен иметь тех же привилегий, что и ядро.**

## Зачем нужны привилегии процессора

Процессор сам участвует в защите системы.

У разных архитектур есть свои механизмы. Например, x86 предоставляет несколько уровней привилегий, традиционно называемых rings. В обычной модели операционной системы нам достаточно различать:

```text
user mode
    ↓
kernel mode
```

В user mode процессор ограничивает выполнение определённых привилегированных операций.

В kernel mode работает код, которому ОС разрешила выполнять такие операции.

Например, пользовательский процесс не должен самостоятельно:

```text
изменять таблицы страниц;
управлять критическими регистрами CPU;
получать произвольный доступ к физической памяти;
перенастраивать системные устройства;
отключать механизмы защиты.
```

Если бы обычный процесс мог делать всё это напрямую, изоляция программ практически потеряла бы смысл.

## Как программа обращается к ядру

Допустим, приложение хочет открыть файл:

```text
config.yaml
```

Оно не должно самостоятельно искать физические блоки SSD.

Вместо этого оно обращается к ОС через системный интерфейс:

```text
программа
    | "открой файл"
    ↓
системный вызов
    ↓
ядро
    ├-- проверяет аргументы
    ├-- проверяет права
    ├-- работает с файловой системой
    └-- обращается к драйверу
    ↓
результат
    ↓
программа
```

Такой механизм называется **системным вызовом (system call, syscall)**.

Системный вызов — это контролируемый способ попросить ядро выполнить операцию, для которой пользовательскому коду недостаточно собственных привилегий.

## Что происходит при syscall

Рассмотрим концептуально операцию чтения:

```text
read(...)
```

В упрощённом виде последовательность выглядит так:

```text
1. Программа подготавливает аргументы
                ↓
2. Выполняется специальный механизм входа в ядро
                ↓
3. CPU передаёт управление ядру
                ↓
4. Ядро определяет нужную системную операцию
                ↓
5. Проверяются аргументы и права
                ↓
6. Выполняется необходимая работа
                ↓
7. Результат возвращается программе
```

На реальном компьютере между этими этапами есть дополнительные детали: регистры, таблицы, обработчики, переключение контекста и другие механизмы.

Например, на x86-64 Linux для системных вызовов используется инструкция `syscall`. Но обычному программисту не нужно вручную писать эту инструкцию — операционная система и библиотеки предоставляют более удобный интерфейс.

Главное понять не конкретную инструкцию, а принцип:

```text
USER MODE
    | syscall
    ↓
KERNEL MODE
    | return
    ↓
USER MODE
```

Программа не «становится ядром». Она лишь временно передаёт управление привилегированному коду ОС.

## Почему ядро проверяет аргументы

Представим вызов:

```c
read(fd, buffer, size);
```

Программа передаёт ядру:

```text
fd
buffer
size
```

Ядро не может слепо доверять этим значениям. Программа может быть ошибочной, повреждённой или вредоносной.

Поэтому ядро проверяет, например:

```text
корректен ли дескриптор;
разрешена ли операция;
допустим ли размер;
доступен ли указанный буфер;
не нарушает ли операция границы доступа.
```

Именно поэтому системный вызов — не просто «прыжок в код ядра». Это переход через защищённую границу, после которого ядро должно безопасно обработать запрос.

## Ошибка приложения и изоляция памяти

Рассмотрим простой пример на C:

```c
int *p = NULL;
*p = 1;
```

Программа пытается записать данные по недопустимому адресу.

Процессор обнаруживает нарушение доступа:

```text
программа
    ↓
недопустимый доступ к памяти
    ↓
CPU
    ↓
обработчик ядра
    ↓
ошибка процесса
```

В Unix-подобной системе такой процесс обычно получает `SIGSEG↓`.

Важно, что это не означает падение всей ОС:

```text
процесс A
   ✕
процесс B
   ✓
процесс C
   ✓
ядро
   ✓
```

Именно изоляция процессов делает такую модель возможной.

Если браузер ошибся с указателем, это не должно автоматически позволять ему записать данные в память ядра или другого процесса.

## Page fault — не всегда ошибка

Здесь важно не перепутать понятия.

**Page fault** — событие, возникающее при обращении к виртуальной странице, которое требует специальной обработки.

Это не обязательно означает, что программа написана неправильно.

Например, процесс может обратиться к странице, которая ещё не была подготовлена соответствующим образом. Ядро может обработать ситуацию, после чего выполнение продолжится:

```text
процесс
  ↓
доступ к странице
  ↓
page fault
  ↓
ядро
  ├-- обработало ситуацию
  ↓
процесс продолжает работу
```

В других случаях обращение действительно недопустимо:

```text
процесс
  ↓
недопустимый адрес
  ↓
page fault
  ↓
ядро
  ↓
процесс получает ошибку
```

Поэтому само наличие page fault ещё не говорит о сбое программы.

## Не только syscall приводит к ядру

Системный вызов — лишь один из механизмов, по которым выполнение может перейти к обработчику ядра.

Есть три важных класса событий.

### Системный вызов

Программа сама просит ОС выполнить операцию:

```text
программа
    ↓
syscall
    ↓
ядро
```

### Исключение

CPU обнаруживает событие, связанное с выполнением инструкции.

Например:

```text
деление на ноль
недопустимый доступ к памяти
некоторые другие ошибки или специальные условия
```

Упрощённо:

```text
программа
    ↓
CPU обнаружил событие
    ↓
обработчик
    ↓
ядро
```

### Аппаратное прерывание

Внешнее устройство сообщает процессору о событии.

Например:

```text
сетевая карта получила данные
          ↓
      прерывание
          ↓
          CPU
          ↓
         ядро
```

Эти механизмы связаны с передачей управления привилегированному коду, но их причины и семантика различаются.

## Системный вызов, исключение и прерывание — не одно и то же

Полезно держать различие в голове:

| Механизм    | Причина                                                              |
| ----------- | -------------------------------------------------------------------- |
| System call | программа запрашивает услугу ОС                                      |
| Exception   | событие связано с выполнением инструкции CPU                         |
| Interrupt   | внешнее устройство или другой аппаратный источник сообщает о событии |

На практике детали зависят от архитектуры и ОС, поэтому таблица — это именно учебная модель, а не описание всех возможных механизмов.

## Почему ошибка драйвера опаснее

Теперь становится понятна важная практическая разница.

Обычная программа обычно работает в user space:

```text
user space
    ↓
ошибка
    ↓
процесс завершён
```

А многие драйверы работают с привилегиями ядра:

```text
kernel space
    ↓
ошибка драйвера
    ↓
может быть повреждено ядро
    ↓
может пострадать вся система
```

Поэтому ошибка в приложении и ошибка в kernel-mode компоненте имеют совершенно разный потенциальный масштаб.

Это одна из причин, почему разработка драйверов требует особенно строгого контроля памяти, синхронизации и взаимодействия с аппаратурой.

## Что происходит при работе с устройством

Рассмотрим робота с USB-камерой.

Приложение хочет получить изображение:

```text
приложение
    ↓
библиотека камеры
    ↓
системный интерфейс
    ↓
ядро
    ↓
USB-драйвер
    ↓
USB-контроллер
    ↓
камера
```

Приложение не получает произвольный доступ к регистрам USB-контроллера.

Оно использует интерфейс, предоставленный ОС, а драйвер и ядро выполняют низкоуровневую работу.

С файлом принцип похож:

```text
Python
  ↓
open()
  ↓
библиотека
  ↓
syscall
  ↓
ядро
  ↓
файловая система
  ↓
драйвер
  ↓
SSD
```

Высокоуровневая команда приложения превращается в цепочку низкоуровневых действий, но сама программа не обязана знать физические детали устройства.

## Почему root — это не kernel

В Linux пользователь `root` обладает очень широкими административными правами.

Но:

```text
root ≠ kernel
```

`root` — это пользователь, которому ОС разрешает выполнять множество административных операций.

Обычный код root-процесса всё равно выполняется в user mode:

```text
root-процесс
     ↓
USER MODE
     ↓
syscall
     ↓
KERNEL MODE
```

Конечно, root может иметь права на загрузку модулей, изменение системных настроек и управление устройствами. Но это всё ещё не означает, что его обычный код автоматически выполняется с привилегиями ядра.

Это важное различие между **правами пользователя в ОС** и **режимом исполнения CPU**.

## Kernel panic и падение приложения

Если обычный процесс совершил недопустимую операцию, система может просто завершить его:

```text
┌-----------------------------┐
|     Ошибка приложения       |
|                             |
|     падает один процесс     |
|     ОС продолжает работу    |
└-----------------------------┘
```

Если же критическая ошибка произошла внутри ядра и система не может безопасно продолжить работу, последствия могут быть намного серьёзнее.

В Linux это может привести к:

```text
kernel panic
```

В Windows критическая ошибка ядра обычно приводит к остановке системы с `Bug Check`, часто известной пользователям как `BSOD`.

Поэтому:

```text
segmentation fault
```

и:

```text
kernel panic
```

— совершенно разные классы проблем.

## Как устроена граница в разных ОС

Конкретная организация ядра может различаться.

В **монолитном ядре** значительная часть системных подсистем работает в kernel space. Linux относится к этой модели, хотя его реальная архитектура намного сложнее простой схемы.

```text
USER SPACE
    ↓
KERNEL SPACE
 ┌---┼---┬---┐
FS сеть память драйверы
```

В **микроядерной архитектуре** стараются оставить в ядре минимальный набор механизмов, а некоторые службы и драйверы могут работать как отдельные процессы в user space:

```text
USER SPACE
 ┌---------┬---------┬---------┐
 | драйвер |   FS    | сервис  |
 └----┬----┴----┬----┴----┬----┘
      └---------┼---------┘
                ↓
             микроядро
                ↓
             железо
```

Это уже вопрос архитектуры конкретной ОС. Для нас важнее другое: **привилегированный код стараются отделять от обычных приложений, чтобы уменьшить последствия ошибок и ограничить доступ к критическим ресурсам.**

## Инженерный смысл user space и kernel space

Знание этой границы полезно не только для теории.

Представим сообщение:

> «Программа упала».

Для диагностики этого недостаточно.

Если проблема находится в user space, нужно искать:

```text
ошибки программы
неправильные указатели
исключения
race condition
проблемы библиотек
```

Если проблема связана с kernel space, дополнительно рассматривают:

```text
драйверы
модули ядра
аппаратные устройства
системные журналы
ошибки взаимодействия с оборудованием
```

То есть граница привилегий помогает понять, **где искать причину проблемы и насколько широко она потенциально может повлиять на систему**.

## Что нужно запомнить

Главная идея урока:

```text
┌-----------------------------┐
|         USER SPACE          |
|                             |
| приложения / процессы       |
| Python / C++ / браузер      |
└--------------┬--------------┘
               | syscall
               | exception
               | interrupt
               ↓
┌-----------------------------┐
|        KERNEL SPACE         |
|                             |
| ядро / драйверы             |
└--------------┬--------------┘
               ↓
┌-----------------------------┐
|           ЖЕЛЕЗО            |
└-----------------------------┘
```

Нужно помнить:

* обычные приложения выполняются с ограниченными привилегиями;
* ядро выполняется с более высокими привилегиями;
* процессор участвует в обеспечении этой границы;
* системный вызов позволяет программе контролируемо обратиться к ядру;
* исключение и аппаратное прерывание — другие механизмы передачи управления обработчику ядра;
* page fault не обязательно означает ошибку;
* ошибка user-space процесса обычно ограничивается этим процессом;
* ошибка привилегированного кода может затронуть всю систему;
* `root` — это пользователь с большими правами, а не «режим ядра».

Главная инженерная модель:

> **User space выполняет приложения с ограниченными правами. Kernel space содержит привилегированный код ОС. Контролируемая граница между ними позволяет приложениям пользоваться ресурсами компьютера, не получая полного контроля над системой.**
