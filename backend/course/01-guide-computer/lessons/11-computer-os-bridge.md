# Зачем между программой и железом стоит ОС

Мы уже разобрали, что программа после запуска становится процессом, процесс содержит потоки, а потоки получают время на CPU. Но возникает важный вопрос: **кто управляет всем остальным компьютером?**

Представим обычный ПК. На нём одновременно работают браузер, терминал, сервер, музыкальный проигрыватель и десятки фоновых служб. Все они хотят использовать один CPU, одну RAM, один SSD, сетевую карту, USB-устройства и другие ресурсы.

Если дать каждой программе полный доступ к железу, одна программа легко сможет испортить работу другой. Она может записать данные в чужую память, занять процессор бесконечным циклом или неправильно настроить устройство.

Поэтому между приложениями и аппаратным обеспечением существует специальный слой — **операционная система (ОС)**.

```text
┌-----------------------------┐
|        Приложения           |
| браузер / Python / сервер   |
└--------------┬--------------┘
               ↓
┌-----------------------------┐
|      Операционная система   |
| процессы / память / файлы   |
| сеть / устройства / доступ  |
└--------------┬--------------┘
               ↓
┌-----------------------------┐
|           Железо            |
| CPU / RAM / SSD / USB / NIC |
└-----------------------------┘
```

ОС не просто «передаёт команды железу». Она распределяет ресурсы, изолирует программы друг от друга и предоставляет удобные абстракции, благодаря которым приложению не приходится знать все физические детали компьютера.

## ОС как управляющий ресурсами

Главная задача ОС хорошо видна на примере CPU. На компьютере может существовать гораздо больше потоков, чем физических ядер:

```text
поток A -┐
поток B -┼--► планировщик ОС ---► CPU
поток C -┤
поток D -┘
```

ОС решает, какой поток получит процессорное время, когда его нужно остановить и передать CPU другому потоку. Благодаря этому браузер, терминал и сервер могут работать одновременно, хотя физические вычислительные ресурсы ограничены.

Похожая ситуация с памятью. Несколько процессов одновременно используют RAM, но программа обычно не работает с произвольными физическими адресами. Каждый процесс получает собственное **виртуальное адресное пространство**, а ОС вместе с аппаратным механизмом управления памятью связывает виртуальные адреса с физической памятью.

```text
          физическая RAM
       ┌--------┼--------┐
       ↓        ↓        ↓
   процесс A  процесс B  процесс C
   своё       своё       своё
   пространство адресов
```

Это позволяет процессам быть изолированными. Ошибка в одном процессе не должна автоматически означать запись в память другого процесса.

ОС также управляет хранением данных. Приложение работает с понятиями:

```text
файл
папка
путь
```

а не с физическими секторами SSD.

То же самое относится к сети и устройствам: программа использует предоставленные ОС интерфейсы, а конкретные детали оборудования скрыты ниже.

## ОС создаёт абстракции

Это одна из самых важных идей всего урока.

Допустим, программа хочет сохранить настройки:

```text
config.yaml
```

Ей не нужно знать:

```text
какой SSD установлен;
какой контроллер используется;
какие физические блоки свободны;
какие команды понимает накопитель;
как работает его кэш.
```

Программа работает с более простой моделью:

```text
открыть файл
прочитать файл
записать файл
закрыть файл
```

А дальше цепочка может выглядеть так:

```text
Программа
    ↓
файловый API
    ↓
ядро ОС
    ↓
файловая система
    ↓
драйвер
    ↓
контроллер
    ↓
SSD
```

Каждый уровень скрывает часть сложности следующего.

Именно поэтому одна и та же программа может работать с разными накопителями, сетевыми картами или USB-устройствами, не реализуя отдельно всю низкоуровневую работу для каждого конкретного устройства.

Без такой абстракции приложениям пришлось бы самостоятельно разбираться с контроллерами, протоколами, адресами, ошибками и распределением ресурсов. Если таких программ десятки, система быстро стала бы практически неуправляемой.

## Ядро и драйверы

Центральная часть ОС называется **ядром (kernel)**. Оно отвечает за наиболее привилегированные и системные операции:

```text
процессы
память
планирование
файловые системы
сеть
устройства
безопасность
```

При этом ядро — не вся операционная система. Графическая оболочка, системные службы и многие утилиты могут работать как обычные процессы.

Устройствами ядро часто управляет через **драйверы**.

Драйвер — программный компонент, который знает, как работать с конкретным устройством или классом устройств.

Например:

```text
сетевое приложение
       ↓
сетевой стек ОС
       ↓
сетевой драйвер
       ↓
сетевой адаптер
```

Или:

```text
программа
    ↓
ОС
    ↓
USB-драйвер
    ↓
USB-контроллер
    ↓
устройство
```

Приложение поэтому обычно не обращается непосредственно к регистрам сетевой карты или контроллера SSD. Оно использует интерфейс ОС, а уже ядро и драйвер выполняют необходимую низкоуровневую работу.

## Системные вызовы

Но как обычная программа вообще просит ядро выполнить операцию?

Для этого существуют **системные вызовы (system calls)**.

Программа может попросить ОС:

```text
открыть файл
создать процесс
выделить память
получить время
отправить данные через сокет
создать сетевое соединение
```

Упрощённо это выглядит так:

```text
пользовательская программа
          | системный вызов
          ↓
        ядро ОС
          ↓
     нужная операция
```

Системный вызов является контролируемой границей между пользовательским кодом и привилегированными возможностями ядра.

При этом не нужно считать, что каждая функция языка превращается в один системный вызов.

Например:

```python
print("Hello")
```

может пройти через несколько библиотечных уровней и буферизацию. А некоторые операции вообще выполняются полностью в пользовательском пространстве.

Поэтому неверны обе модели:

```text
одна функция Python = один syscall
```

и:

```text
один syscall = одно непосредственное обращение к железу
```

Между приложением и физическим устройством часто находится несколько уровней абстракции.

## Почему программы не получают полный доступ к железу

Современный процессор поддерживает механизмы привилегий. В упрощённом виде систему можно представить так:

```text
┌-----------------------------┐
|     пользовательский код    |
| Python / C++ / браузер      |
└--------------┬--------------┘
               | syscall
               ↓
┌-----------------------------┐
|            ядро             |
| память / процессы / драйверы|
└--------------┬--------------┘
               ↓
┌-----------------------------┐
|           железо            |
└-----------------------------┘
```

Обычный процесс не должен иметь возможности произвольно изменить физическую память, перенастроить контроллер или вмешаться в работу другого процесса.

Иначе одна ошибка в приложении могла бы повредить всю систему.

Поэтому ОС предоставляет контролируемый интерфейс: приложение просит выполнить операцию, ядро проверяет контекст и выполняет её с необходимыми привилегиями.

Конкретная реализация этой границы зависит от архитектуры процессора и ОС. Подробно режимы привилегий, user mode, kernel mode и механизм системных вызовов мы разберём в следующем уроке.

## Пример: что происходит при чтении файла

Рассмотрим простой Python-код:

```python
with open("config.txt") as f:
    data = f.read()
```

На уровне Python всё выглядит очень просто. Но внутри системы происходит гораздо больше:

```text
Python
  ↓
библиотека
  ↓
системный интерфейс
  ↓
ядро
  ↓
файловая система
  ↓
драйвер
  ↓
контроллер
  ↓
SSD
```

Данные проходят обратный путь:

```text
SSD
  ↓
контроллер
  ↓
драйвер
  ↓
ядро
  ↓
процесс
  ↓
Python
```

При этом Python-коду не нужно знать, в каких физических блоках SSD лежит файл.

То же самое происходит с сетью. Сервер может использовать:

```text
socket
TCP / UDP
bind()
listen()
accept()
```

и не знать, какие регистры необходимо изменить в конкретном сетевом контроллере.

```text
Приложение
    ↓
socket API
    ↓
сетевой стек ОС
    ↓
драйвер
    ↓
сетевой адаптер
```

Абстракция позволяет приложению работать с сетью как с понятным программным интерфейсом, а не как с набором электрических сигналов и регистров.

## ОС и многозадачность

Представим компьютер, на котором одновременно работают:

```text
браузер
терминал
музыкальный проигрыватель
сервер
антивирус
```

Они конкурируют за одни и те же ресурсы:

```text
CPU
RAM
диск
сеть
устройства
```

ОС становится арбитром:

```text
программа A -┐
программа B -┼--► ОС ---► общие ресурсы
программа C -┤
программа D -┘
```

Она решает, кто получает процессорное время, какую память видит процесс, какие файлы можно открыть и какие устройства доступны.

Это не означает, что ОС может исправить любую ошибку программы. Если приложение содержит бесконечный цикл, утечку памяти, deadlock или отправляет неправильную команду мотору, сама ОС не знает, что алгоритм приложения ошибочен.

ОС управляет **ресурсами компьютера**, но не заменяет правильную архитектуру программы.

## Где заканчивается ОС и начинается приложение

Полезно разделять две разные задачи.

Приложение отвечает за свою предметную логику:

```text
получить показание датчика
вычислить положение
рассчитать команду
управлять алгоритмом
```

ОС отвечает за общие ресурсы:

```text
дать процессору время
предоставить память
открыть файл
передать данные через сеть
дать доступ к устройству
```

Например, если программа робота хочет отправить данные по Ethernet, приложение решает **что** отправить, а ОС предоставляет механизм, через который эти данные попадут в сетевой стек и далее на адаптер.

Это разделение позволяет одному компьютеру одновременно выполнять множество разных приложений.

## Обычный компьютер и bare metal

ОС нужна не любой вычислительной системе.

Рассмотрим простой микроконтроллер:

```text
один микроконтроллер
        ↓
     прошивка
        |
        ├-- датчики
        ├-- таймеры
        └-- моторы
```

Программа может непосредственно обращаться к регистрам периферии:

```text
прошивка
   ↓
регистры микроконтроллера
   ↓
периферия
```

Такой подход называется **bare metal** — система работает без полноценной операционной системы.

Например, простая прошивка может выглядеть так:

```c
int main(void)
{
    init_hardware();

    while (1)
    {
        read_sensor();
        control_motor();
    }
}
```

Здесь разработчик сам отвечает за значительную часть системной работы: настройку периферии, таймеров, обработку событий, управление памятью и планирование логики.

Для небольшого микроконтроллера это может быть вполне разумно. Там нет десятков независимых приложений, которым нужно безопасно делить один компьютер.

На более мощном компьютере ситуация другая:

```text
Linux
  |
  ├-- процессы
  ├-- память
  ├-- файловая система
  ├-- сеть
  ├-- драйверы
  └-- устройства
```

Приложение робота в такой системе уже взаимодействует с железом через ОС.

## ОС и робототехника

В робототехнике часто встречаются обе модели.

Микроконтроллер может отвечать за быстрый контур управления:

```text
датчик
  ↓
микроконтроллер
  ↓
контроллер мотора
  ↓
мотор
```

А Linux-компьютер может выполнять более сложные задачи:

```text
камера
  ↓
Linux-компьютер
  ├-- обработка изображения
  ├-- планирование
  ├-- логирование
  └-- сетевое взаимодействие
```

Получается распределённая архитектура:

```text
┌-------------------┐
|    Linux / SBC    |
| интерфейс         |
| планирование      |
| обработка данных  |
└---------┬---------┘
          ↓
┌-------------------┐
|   микроконтроллер |
| быстрый контур    |
| датчики / моторы  |
└-------------------┘
```

Это не означает, что Linux обязательно плох для realtime. Важен конкретный уровень требований. Если системе требуется строгое ограничение времени реакции, используют подходящую архитектуру, realtime-механизмы или выносят критический контур на специализированный контроллер.

Главное правило здесь простое: **сначала измеряют требования и задержки, а затем выбирают архитектуру**.

## ОС как слой абстракции

Теперь можно собрать всё в одну модель:

```text
┌-----------------------------┐
|        приложения           |
| Python / C++ / браузер      |
└--------------┬--------------┘
               ↓
┌-----------------------------┐
|      системные API          |
| файлы / сеть / процессы     |
└--------------┬--------------┘
               ↓
┌-----------------------------┐
|       ядро + драйверы       |
| память / CPU / устройства   |
└--------------┬--------------┘
               ↓
┌-----------------------------┐
|           железо            |
| CPU / RAM / SSD / USB / NIC |
└-----------------------------┘
```

ОС превращает физические ресурсы в удобные программные абстракции:

```text
физическая память → виртуальная память
SSD               → файлы
сетевая карта     → socket
процессор         → планирование потоков
устройство        → интерфейс драйвера
```

Именно поэтому программисту не приходится каждый раз писать собственный код управления конкретным контроллером SSD или сетевой картой.

На Linux можно использовать `strace`:

```bash

```

или, например, запустить через него Python-программу.

Вы увидите обращения программы к файлам, процессам, памяти, сокетам и другим системным ресурсам.

Цель упражнения не в том, чтобы выучить список системных вызовов. Нужно увидеть сам принцип:

```text
пользовательская программа
          ↓
    интерфейс ОС
          ↓
         ядро
          ↓
       ресурсы
```

## Что нужно запомнить

ОС нужна прежде всего потому, что **много программ должны безопасно и удобно пользоваться ограниченным набором аппаратных ресурсов**.

Она:

* управляет процессами и потоками;
* распределяет CPU;
* управляет виртуальной и физической памятью;
* предоставляет файловую систему;
* предоставляет сетевые интерфейсы;
* управляет устройствами через драйверы;
* контролирует доступ;
* изолирует процессы;
* предоставляет системные вызовы.

Главная модель урока:

```text
много программ
      ↓
    ОС
      ↓
общие ресурсы компьютера
```

А главный смысл абстракции:

> **Программа работает не непосредственно с физическим устройством, а с удобным интерфейсом, который скрывает большую часть деталей этого устройства.**

ОС при этом не является обязательной частью любой системы. В bare-metal устройстве часть её функций берёт на себя сама прошивка.

## Связь со следующим уроком

Мы несколько раз встретили границу:

```text
пользовательская программа
          ↓
      системный вызов
          ↓
         ядро
```

Теперь нужно понять, **как процессор технически защищает эту границу**.

Следующий урок — **пользовательское пространство и ядро**. Мы разберём режимы привилегий, изоляцию памяти, user mode, kernel mode и то, как системный вызов переводит выполнение программы из одного режима в другой.
