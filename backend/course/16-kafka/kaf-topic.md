## Цель

Разобраться, что такое topic в Kafka: зачем именованный поток, как проектировать границы топиков, чем топик отличается от очереди «одна задача — один воркер».

## Что уже нужно понимать

- Брокер хранит сообщения и отдаёт их консьюмерам.
- Продюсеры пишут, консьюмеры читают по курсору.
- В Kafka хранение — лог (append-only), а не обязательно «удалил после ack».

## Объяснение

**Topic** — именованный поток записей в Kafka. Имя вроде `orders.events` или `payments.commands` — часть публичного контракта платформы. Продюсеры договариваются писать сюда, консьюмеры — подписываться.

Топик — это не просто ярлык. Под капотом топик делится на **партиции** (следующий урок). Но с точки зрения продукта и команд вы сначала думаете топиками: «какой поток фактов или команд мы выделяем?»

Два распространённых стиля содержимого:

1. **События (events)** — факт уже произошёл: `OrderCreated`, `PaymentCaptured`. Прошедшее время в имени типа. Подписчики реагируют, не отменяя факт сам по себе.
2. **Команды (commands)** — просьба что-то сделать: `SendEmail`, `ReserveStock`. Обычно ожидается ровно один исполнитель по смыслу (хотя технически группы устроены одинаково).

Смешивать в одном топике и огромный кликстрим UI, и редкие платёжные события можно технически, но операционно плохо: разные SLA, разные права доступа, разный retention, разный профиль нагрузки. Лучше резать по домену и по характеру потока.

Имя топика стоит делать стабильным и говорящим. Антипаттерны: `test`, `data`, `topic1`, `new_orders_final_v3`. Лучше иерархия: `{domain}.{entity}.{kind}` или принятый в компании стандарт. Переименование топика — миграция: либо двойная запись, либо перекладка, либо новый топик + перевод потребителей.

Топик задаёт **политику хранения**: сколько дней держать данные, компактировать ли лог по ключу (идея compacted topic — последнее значение по ключу важно дольше, чем полный журнал всех изменений). Для событийного журнала домена часто нужен срок «несколько дней/недель», для changelog состояния — compaction.

Важное отличие от «очереди задач» в голове новичка: один и тот же топик могут читать **несколько consumer group** независимо. Почтовый сервис и аналитика не выхватывают сообщения друг у друга. В классической конкурирующей очереди два воркера одной очереди делят задачи; второй независимый «подписчик всего потока» — уже другая абстракция (pub/sub), которую Kafka даёт естественно через группы.

Сколько топиков заводить? Слишком мало — толстый шланг без изоляции. Слишком много — ад операций и прав. Практичный якорь: топик = поток с одним владельцем-продюсером (командой), понятным смыслом и своими требованиями к retention/ACL. Не обязательно топик на каждый тип события; часто типы живут внутри одного доменного потока и различаются полем `type`.

## Термины

- **Topic** — именованный поток записей.
- **Record / message** — запись в топике (ключ, значение, заголовки, timestamp).
- **Partition** — упорядоченный сегмент топика (деталь следующего урока).
- **Retention** — сколько хранить данные топика.
- **Compacted topic** — политика, при которой для ключа важнее последнее значение.
- **Fan-out** — несколько независимых групп читают один топик.
- **Schema** — договорённость о формате value (и ключа).

## Как это устроено

1. Админ или сервисный аккаунт создаёт топик с параметрами (партиции, репликация, retention).
2. Метаданные топика известны кластеру; клиенты получают их через metadata API.
3. Продюсеры пишут в `topic` + выбирают партицию.
4. Консьюмеры подписываются на список топиков (или pattern).
5. Данные физически лежат в логах партиций на брокерах, логически адресуются именем топика.

С точки зрения приложения «создать топик» — как «создать таблицу»: это схема интеграции. В некоторых окружениях топики создают автоматически при первой записи — удобно в dev, опасно в prod без контроля партиций и ACL.

Контракт топика включает не только имя, но и семантику: какие ключи, какие типы событий, гарантии порядка (на уровне ключа/партиции), ожидаемая частота, кто имеет право писать. Документируйте это рядом с кодом продюсера — иначе консьюмеры гадают.

## Пример

```python
TOPIC_ORDERS = "orders.events"
TOPIC_MAIL_COMMANDS = "notifications.mail.commands"


def publish_domain_event(producer, event_type: str, order_id: str, body: dict) -> None:
    producer.send(
        topic=TOPIC_ORDERS,
        key=order_id.encode(),
        value=encode_json({"type": event_type, **body}),
    )


def enqueue_email(producer, to: str, template: str, vars_: dict) -> None:
    producer.send(
        topic=TOPIC_MAIL_COMMANDS,
        key=to.encode(),  # письма одному адресату упорядочены локально
        value=encode_json({
            "type": "SendEmail",
            "to": to,
            "template": template,
            "vars": vars_,
        }),
    )
```

Пример «контракта» топика текстом:

```text
topic: orders.events
owner: team-orders
producers: order-service
consumers: mail-service, warehouse-service, search-indexer
key: order_id (string)
value: JSON, поле type обязателен
events: OrderCreated, OrderPaid, OrderCancelled
retention: 7 days
partitions: 6
```

## Разбор

Два топика разделены по смыслу: доменные факты заказа vs команды на почту. Почту можно переиздать без дублирования бизнес-события заказа. Индексатор поиска подписан на `orders.events` и не обязан знать про шаблоны писем. Ключ в событиях — `order_id`, в командах почты — адрес: разная ось порядка.

Поле `type` внутри одного топика позволяет эволюционировать набор событий без взрыва числа топиков, пока они одной доменной области и одного владельца.

## Практическое применение

- Доменные event streams на bounded context.
- Топик команд для пула воркеров.
- Changelog топик для синхронизации кэша (идея compaction).
- Изоляция PII: отдельный топик с жёстким ACL и коротким retention.

## Типичные ошибки

- Один топик «на всё приложение» с несвязанными схемами.
- Топик на каждый микро-тип события без необходимости → операционный шум.
- Нет владельца топика — схема ломается молча.
- Разный смысл ключа у разных продюсеров одного топика.
- Вечный retention «на всякий случай» без расчёта диска.

## Что запомнить

- Topic — именованный контрактный поток, не «папка».
- Несколько групп читают один топик независимо.
- Режьте топики по домену, SLA и доступу, не по случайным удобствам.
- Имя + схема + ключ + retention = минимальный паспорт топика.
- Типы событий могут жить внутри топика через поле type.

## Задание

Спроектируй 2–3 топика для интернет-магазина (заказ, оплата, уведомления). Для каждого укажи владельца, ключ, retention и двух потребителей. Объясни, почему ты не слил всё в один топик `shop`.

## Связь со следующим уроком

Внутри топика живут **partition** — именно они дают параллелизм и локальный порядок. Разберём, как сообщения раскладываются по партициям и чем это ограничивает масштабирование консьюмеров.
