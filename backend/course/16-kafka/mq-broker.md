## Цель

Понять, что такое брокер сообщений как инфраструктурный компонент: какие обязанности он берёт на себя, чем кластер отличается от одного процесса, и где проходит граница между брокером и приложением.

## Что уже нужно понимать

- Есть продюсеры и консьюмеры.
- Сообщения нужны как буфер и канал между частями системы.
- Данные на диске и репликация — способ переживать падение одного узла.

## Объяснение

**Брокер** — сервер (или набор серверов), который принимает сообщения от продюсеров, хранит их по правилам системы и отдаёт консьюмерам. Приложение не шлёт байты «напрямую другому приложению» в обход; оно говорит с брокером по клиентскому протоколу.

Брокер решает инфраструктурные задачи, которые плохо дублировать в каждом сервисе:

- принять поток записи под нагрузкой;
- сохранить данные так, чтобы после рестарта они не исчезли (в рамках конфигурации);
- маршрутизировать чтение многим клиентам;
- контролировать доступ, квоты, лимиты размера;
- давать метрики: размер очереди/лога, лаг, скорость in/out.

В простых очередях брокер может жить одним узлом — для разработки это нормально, для продакшена часто нужен кластер. В Kafka **кластер** — несколько брокеров, которые вместе обслуживают топики. Данные партиций распределены по брокерам; у каждой партиции есть **лидер**, обслуживающий запись/чтение (в классической модели), и **реплики**, которые копируют лог лидера.

Зачем реплики? Если лидер умер, одна из реплик может стать новым лидером (при достаточной синхронизации). Продюсеры и консьюмеры переподключаются к новому лидеру. Без репликации падение диска = потеря несохранённого и даже сохранённого локально хвоста.

Брокер **не** должен становиться местом бизнес-правил «если сумма > 1000, откажи заказ». Его зона — транспорт и хранение потока. Бизнес остаётся в сервисах. Исключение — лёгкие инфраструктурные политики: TTL, compact (в Kafka), лимиты, ACL.

Важно отличать брокер от базы данных. БД оптимизирована под запросы, обновления строк, транзакции предметной области. Брокер (особенно лог) оптимизирован под **последовательную запись** и чтение потока многими клиентами. Хранить «весь интернет» в Kafka как в primary database — распространённая ошибка мышления. Retention конечен (по времени/размеру), если вы сами не построили вокруг этого data platform с явной политикой.

Ещё роль брокера — **точка контракта среды**. Dev, staging, prod — разные кластеры или хотя бы разные префиксы топиков. Путаница «писали в прод из отладочного скрипта» лечится ACL и дисциплиной имён, не надеждой.

## Термины

- **Broker** — узел, принимающий и отдающий сообщения.
- **Cluster** — согласованный набор брокеров.
- **Replica** — копия лога партиции на другом брокере.
- **Leader** — реплика, обслуживающая клиентские операции для партиции.
- **Follower** — реплика, догоняющая лидера.
- **Durability** — устойчивость данных к сбоям в рамках настроек (acks, min ISR и т.п. — идеи).
- **Retention** — политика, сколько хранить записи в логе.
- **Controller / coordinator** (идея) — компонент, который следит за членством, лидерами, балансом (реализации менялись между версиями; суть — есть управляющий контур).

## Как это устроено

Упрощённо для лог-брокера:

1. Администратор создаёт топик с N партициями и фактором репликации R.
2. Кластер размещает лидеров и follower’ов по брокерам.
3. Продюсер узнаёт через метаданные, кто лидер нужной партиции, и пишет туда.
4. Лидер append’ит запись в локальный лог на диск (последовательная запись — важна для скорости).
5. Followers копируют новые записи.
6. В зависимости от настроек продюсер ждёт, пока запись считается «закоммиченной» в кластере.
7. Консьюмер читает у лидера (типично) свою порцию лога по offset.

Append-only лог на диске хорошо ложится на железо: меньше случайных seek’ов при записи потока. Старые сегменты удаляются или компактируются по политике — это не «таблица, где UPDATE».

Брокер также участвует в **жизненном цикле групп консьюмеров**: кто какой партиции член, когда делать rebalance. Это уже координация клиентов, но живёт в инфраструктуре брокера/координатора.

С точки зрения эксплуатации брокер — такой же критичный сервис, как БД: диск, сеть, JVM/процесс, мониторинг under-replicated partitions, дискового пространства, request latency. «Поставили и забыли» заканчивается записью в никуда, когда диск 100%.

## Пример

Административное описание топика (концептуально):

```text
topic: orders.events
partitions: 6
replication.factor: 3
retention.ms: 604800000   # 7 дней
```

Продюсер не выбирает брокера вручную каждый раз — клиент получает metadata:

```python
def publish(broker_client, topic: str, key: bytes, value: bytes) -> None:
    # клиент внутри:
    # 1) partition = hash(key) % num_partitions
    # 2) leader = metadata.leader_for(topic, partition)
    # 3) send to leader broker
    meta = broker_client.send(topic=topic, key=key, value=value)
    assert meta.topic == topic
    # meta.partition, meta.offset — позиция в логе лидера
```

Картина отказа:

```text
Broker A — leader partition 0,1
Broker B — leader partition 2,3; follower 0,1
Broker C — leader partition 4,5; follower 2,3

A падает -> лидеры 0,1 переезжают на B или C (если реплики в синхроне)
Продюсеры обновляют metadata и продолжают писать
```

## Разбор

Шесть партиций позволяют до шести активных консьюмеров в одной группе параллельно есть топик. Фактор репликации 3 означает: каждая партиция на трёх брокерах — переживается падение одного (и часто двух — зависит от настроек и состояния ISR). Retention 7 дней — спустя неделю старые offset’ы могут стать недоступны; консьюмер с огромным лагом рискует попасть в ситуацию «данные уже вычищены».

Брокер здесь — посредник с памятью-логом, а не «умный маршрутизатор бизнес-правил». Клиентская библиотека скрывает поиск лидера, но не снимает с вас ответственность за мониторинг кластера.

## Практическое применение

- Общий кластер для доменных событий компании (с квотами и ACL по командам).
- Отдельный кластер для высоконагруженного кликстрима, чтобы не мешать транзакционным топикам.
- Локальный брокер в docker для разработки интеграционных тестов.
- Зеркалирование топиков между ЦОДами (идея geo-replication) для DR — уже продвинутый уровень.

## Типичные ошибки

- Один брокер в проде «на время» без реплик — и диск умирает в пятницу вечером.
- Путать брокер с БД и строить к нему произвольные запросы «дай все заказы user=5 за год» без материализации в хранилище.
- Не мониторить диск и under-replicated — молчальная деградация durability.
- Давать всем сервисам права write на все топики.
- Менять число партиций «на лету» без понимания, что ключи перераспределятся и локальный порядок по ключу может нарушиться между старыми и новыми сообщениями.

## Что запомнить

- Брокер хранит и раздаёт поток; бизнес-логика — в сервисах.
- Кластер + реплики — способ пережить отказ узла.
- Лидер партиции — точка записи/чтения в классической модели.
- Retention ограничивает, как долго консьюмер может отставать.
- Эксплуатация брокера — часть надёжности системы, не «чужая магия».
