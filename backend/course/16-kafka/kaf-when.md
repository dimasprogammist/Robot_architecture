## Цель

Научиться выбирать Kafka (или брокер вообще) по свойствам задачи: нагрузка, число подписчиков, требования к хранению лога, команда эксплуатации — и узнавать случаи, где достаточно проще.

## Что уже нужно понимать

- Модель лога, партиций, групп, at-least-once.
- Цена порядка, ретраев, эксплуатации кластера.
- Разница между буфером задач и шиной событий.

## Объяснение

Kafka сильна там, где есть **поток событий**, который нужно:

- писать с высокой пропускной способностью;
- хранить некоторое время как журнал;
- читать независимо нескольким приложениям;
- масштабировать чтение партициями;
- иногда переигрывать (replay) историю в пределах retention.

Типичные «да»: кликстрим и продуктовая аналитика, обмен доменными событиями между многими сервисами, пайплайны в озеро данных, буфер перед поисковой индексацией, changelog для синхронизации кэшей.

Kafka **не** нужна автоматически, если:

- два сервиса редко вызывают друг друга и хватает синхронного HTTP с таймаутом и ретраем;
- нужна классическая очередь задач «взял один воркер — удалил» без fan-out и без длинного лога — проще RabbitMQ/SQS/Redis queue и т.п.;
- команда из двух человек без опыта эксплуатации, а нагрузка — десятки сообщений в минуту;
- вы хотите «базу для сложных запросов» — это не замена SQL/OLAP;
- пользователю нужен результат в том же запросе (оплата с мгновенным подтверждением всех побочных систем) — асинхронный журнал не отменяет синхронный критический путь.

Критерии решения удобно разложить по осям.

**Fan-out.** Один поток, ≥2 независимых потребителя с разными скоростями и деплоями → лог+группы хорошо ложатся. Один потребитель-воркер → очередь задач часто проще.

**Объём и пики.** Высокий TPS и пики → брокер-лог окупается. Крошечный поток → операционная цена Kafka может превысить пользу.

**Replay.** Нужно пересобирать проекции из истории → Kafka (или event store) уместна. Разовая задача «посчитай ночью» → batch/cron.

**Порядок и ключи.** Есть сущности с порядком операций → партиции+ключи. Нет — любая очередь справится.

**Операции.** Есть платформенная команда/managed Kafka → риск ниже. Нет никого, кто смотрит under-replicated и диск → сначала упростить архитектуру.

Частая ловушка: «мы перешли на микросервисы, значит нужна Kafka». Микросервисы могут общаться синхронно. Kafka — за требование к потоку данных, не за модный ярлык оргструктуры.

Другая ловушка: внедрить Kafka только как «очередь писем», никогда не используя независимое чтение несколькими группами и retention. Вы платите сложностью лог-системы за сценарий, где хватило бы managed queue.

Иногда нужен **брокер, но не обязательно Kafka**: если важны приоритеты очередей, сложный роутинг, RPC-over-messaging, delayed messages из коробки — классические очереди могут быть удобнее. Kafka умеет многое через дополнительные топики и соглашения, но «умеет» ≠ «удобно из коробки».

## Термины

- **Event stream** — непрерывный поток фактов.
- **Task queue** — пул работ с конкурирующими воркерами.
- **Managed service** — Kafka/очередь как облачный сервис.
- **Operational overhead** — стоимость поддержки кластера.
- **Replayability** — возможность перечитать историю.
- **Critical sync path** — шаги, без которых нельзя ответить пользователю.

## Как это устроено

Прагматичный чеклист перед внедрением:

1. Сколько независимых потребителей у одного факта сейчас и через год?
2. Какой пиковый TPS и средний?
3. Нужен ли replay / окно хранения > нескольких часов?
4. Есть ли требование порядка по ключу?
5. Кто будет дежурить по кластеру и схемам?
6. Что будет, если задержка обработки 1–5 минут — терпимо ли бизнесу?
7. Можно ли начать с проще (очередь/outbox+worker) и вырасти позже?

Если на 1–4 ответы «слабо/нет», а на 5 — «никто», Kafka, скорее всего, рано. Если 1–4 ярко «да», а бизнес терпит асинхронность — сильный кандидат.

Архитектурно часто начинают с **outbox в БД + один воркер**, затем выносят транспорт в брокер, когда появляется второй потребитель или растёт нагрузка. Это нормальная эволюция, не «слабость».

## Пример

Сценарий A — Kafka уместна:

```text
OrderService публикует OrderCreated
→ Mail, Warehouse, Search, AntiFraud, BillingAnalytics
Пик 5k событий/сек в распродажу
Нужен replay индекса поиска за вчерашний день
```

Сценарий B — Kafka избыточна:

```text
Админ-панель раз в час генерирует PDF
Один worker в том же приложении
Достаточно таблицы jobs + cron или Celery/RQ
```

Сценарий C — брокер да, но проще очередь:

```text
Нужно разослать 100k push с приоритетом «срочно/обычно»
Один потребительский сервис
Delayed retry через 15 минут из коробки важнее лога на 7 дней
```

Псевдокод решения в голове команды:

```python
def choose_transport(reqs: dict) -> str:
    if reqs["sync_user_response_needs_all_side_effects"]:
        return "синхронный вызов / сага с осторожностью — не заменяй Kafka"
    if reqs["independent_consumers"] >= 2 and reqs["need_replay"]:
        return "Kafka или аналог лог-брокера"
    if reqs["independent_consumers"] == 1 and reqs["tps"] < 50:
        return "таблица jobs или лёгкая очередь"
    if reqs["need_priority_and_delay"] and not reqs["need_multi_group_log"]:
        return "классическая очередь"
    return "обсудить с платформой: managed Kafka vs queue"
```

## Разбор

В A fan-out и replay прямо бьют в сильные стороны лога. В B операционная цена не окупается. В C важны фичи очереди задач; Kafka можно притянуть, но вы будете изобретать приоритеты поверх топиков.

Функция `choose_transport` не догма, а каркас разговора на дизайн-ревью: она заставляет назвать потребителей, TPS и replay вслух.

## Практическое применение

- Дизайн-ревью нового сервиса уведомлений.
- Выбор между «ещё один топик» и «метод в том же процессе».
- Оценка, пора ли выносить jobs из БД в брокер.
- Аргументация бизнесу: задержка vs устойчивость пиков.

## Типичные ошибки

- Kafka «для галочки» в резюме архитектуры.
- Использовать Kafka как RPC (запрос-ответ через топики) без нужды.
- Игнорировать стоимость схемы, ACL, мониторинга.
- Обещать пользователю мгновенность всех асинхронных эффектов.
- Выбирать Kafka, потому что «очереди устарели» — они не устарели для task-сценариев.

## Что запомнить

- Kafka — про поток, fan-out, масштаб, журнал; не про любую асинхронность.
- Малый поток и один воркер → проще инструменты.
- Операции и команда — часть решения.
- Асинхронность терпит задержку; критический путь может остаться синхронным.
- Эволюция «jobs → очередь → Kafka» нормальна.

## Задание

Возьми три интеграции из своей работы или учебного проекта. Для каждой заполни: число потребителей, TPS, нужен ли replay, допустимая задержка. Вынеси вердикт: sync / jobs-таблица / очередь / Kafka. Одним предложением обоснуй.
