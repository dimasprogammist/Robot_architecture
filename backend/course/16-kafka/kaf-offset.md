## Цель

Понять offset как адрес записи в логе партиции и как курсор прогресса консьюмера; научиться осознанно выбирать момент commit и читать метрику лага.

## Что уже нужно понимать

- Партиция — упорядоченный append-only лог.
- Консьюмер читает последовательно и может переживать рестарты.
- At-least-once часто возникает из пары «обработал / закоммитил».

## Объяснение

**Offset** — монотонно растущий номер записи внутри партиции. Первая запись может иметь offset 0, следующая 1, и так далее. Offset **не глобален для топика**: partition 0 offset 100 и partition 1 offset 100 — разные записи. Полный адрес записи: `(topic, partition, offset)`.

Для продюсера успешная запись возвращает назначенный offset — полезно для логов и саппорта («вот координаты события»). Для консьюмера offset — это **где я нахожусь**.

Kafka (через механизм consumer group) хранит **committed offsets** — последнее зафиксированное положение группы по каждой партиции. После рестарта консьюмер продолжает с committed+1 (идея). Если коммитов ещё не было, действует политика старта: с earliest (с начала доступного лога) или latest (только новые) — выбор критичен при первом запуске.

**Lag** по партиции = (конец лога) − (текущая позиция консьюмера). Большой лаг = обработка отстаёт. Лаг 0 не всегда «всё хорошо» (можно коммитить не обрабатывая — плохая идея), но растущий лаг почти всегда сигнал.

Когда коммитить:

1. **После успешной обработки** — стандарт для бизнес-эффектов. Падение до commit → повтор. Нужна идемпотентность.
2. **До обработки** — почти никогда для денег и писем; это путь к потерям.
3. **Раз в N записей / раз в T мс** — компромисс производительности; при падении повторится незакоммиченный хвост.

Синхронный commit каждой записи проще рассуждать, но медленнее. Batch commit быстрее, но увеличивает окно дублей. Инженерный выбор, а не догма.

Offset не «удаляет» сообщение из топика для других групп. Ваш commit двигает только курсор вашей group id. Данные живут по retention. Если лаг больше retention, консьюмер может обнаружить, что нужный offset уже вычищен — это инцидент данных/процессов, не «маленький варнинг».

Иногда делают **ручной seek**: перемотать группу на прошлый offset и переиграть события (replay). Это мощный инструмент восстановления read-моделей и одновременно способ устроить шторм дублей, если эффекты не идемпотентны. Replay — осознанная операция с окном и мониторингом.

Committed offset хранится **на группу**, не на процесс. Убили под — другой под группы (после rebalance) продолжит с того же commit. Поэтому «я закоммитил у себя в памяти» недостаточно: без commit в механизме группы рестарт вернёт вас назад (или в политику старта). Обратная ошибка — хранить свой прогресс только во внешней БД и никогда не коммитить в Kafka: тогда встроенный lag-мониторинг врёт, а штатные инструменты сброса ведут себя сюрпризно. Обычно коммитят в Kafka и при необходимости дублируют курсор в своей БД для аудита.

Автокоммит в клиентах выглядит удобно, но скрывает момент. Если автокоммит сработал на записях, которые вы ещё не успели надежно применить, получите дырку. Если вы полагаетесь на автокоммит «после успешного цикла» — прочитайте поведение конкретной библиотеки: интервал, что именно коммитится, как связаны poll и commit. Для денежных потоков чаще безопаснее явный commit в коде после своей транзакции.

Не сравнивайте offset разных партиций между собой как «кто впереди»: у каждой партиции свой счётчик. Сравнивают lag и скорость, а не «у нас offset 10 миллионов — мы крутые».

## Термины

- **Offset** — индекс записи в партиции.
- **Committed offset** — сохранённый прогресс группы.
- **Current position** — где консьюмер читает сейчас (может быть впереди commit при автокоммите/батчах — зависит от клиента).
- **Lag** — отставание от конца лога.
- **Seek / reset** — принудительная перемотка курсора.
- **Replay** — повторное чтение прошлого участка лога.
- **High watermark / end offset** (идея) — край доступных/закоммиченных в кластере записей для чтения.

## Как это устроено

1. Продюсер append’ит → запись получает offset.
2. Консьюмер fetch’ит записи, начиная с позиции.
3. Приложение обрабатывает.
4. Клиент пишет commit offset в специальное хранилище группы (внутренний механизм Kafka).
5. При rebalance/рестарте новый владелец партиции читает committed offset и продолжает.

Важно не путать offset записи и «номер попытки обработки». Повтор одной и той же записи — тот же offset; ваш код может видеть её дважды в жизни процесса, если commit не случился.

Для отладки связки «продюсер → консьюмер» логируют тройку topic-partition-offset на обеих сторонах и correlation id в headers. Тогда из саппорт-тикета можно найти запись в логе и понять, дошла ли она до обработки.

## Пример

```python
def process_partition_batch(records, db, consumer) -> None:
    for r in records:
        event = decode(r.value)
        # адрес записи — стабильный id для идемпотентности
        cursor = {
            "topic": r.topic,
            "partition": r.partition,
            "offset": r.offset,
        }
        if db.seen(cursor):
            continue
        db.apply_event(event)
        db.mark_seen(cursor)

    # коммит верхней позиции пакета после успешного apply всех
    consumer.commit()


def lag_seconds_rough(end_offset: int, committed: int, rate_per_sec: float) -> float:
    if rate_per_sec <= 0:
        return float("inf") if end_offset > committed else 0.0
    return (end_offset - committed) / rate_per_sec
```

Пример координат в логе приложения:

```text
processed type=OrderPaid order_id=ord_9f2a
topic=orders.events partition=2 offset=18491
group=warehouse-service lag=37
```

## Разбор

`mark_seen` по `(topic, partition, offset)` защищает от повторного `apply_event`, если commit не прошёл и пачка пришла снова. Commit после цикла — позиция группы двигается только когда БД приняла эффекты (в идеале mark_seen и apply в одной транзакции БД — ещё крепче).

Лаг 37 при высокой скорости может быть секундами; при низкой — минутами. Смотреть абсолютный лаг в сообщениях полезно вместе со скоростью обработки, иначе «лаг 10_000» пугает без контекста.

## Практическое применение

- Мониторинг лага как SLO консьюмера.
- Идемпотентность по координатам записи или по business event id.
- Контролируемый replay при пересборке проекции.
- Расследование «событие потерялось»: проверка end offset vs committed.

## Типичные ошибки

- Думать, что offset уникален во всём кластере.
- Автокоммит включён, а обработка долгая и падает — потери или хаос (зависит от момента автокоммита).
- Reset на earliest на проде без понимания объёма → шторм.
- Хранить «свой offset» только в памяти процесса без commit — после рестарта сюрприз.
- Сравнивать лаги разных групп как одну метрику без разделения.

## Что запомнить

- Адрес записи: topic + partition + offset.
- Commit — прогресс группы, не удаление из топика.
- Момент commit определяет потери vs дубли.
- Lag — ключевой индикатор здоровья консьюмера.
- Replay мощный и опасный без идемпотентности.
