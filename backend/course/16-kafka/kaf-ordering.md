## Цель

Ясно зафиксировать гарантии порядка в Kafka: внутри партиции — да, глобально по топику — нет; научиться выбирать ключ и архитектуру под реальные требования порядка.

## Что уже нужно понимать

- Партиция — упорядоченный лог.
- Ключ влияет на выбор партиции.
- Консьюмер группы читает партицию последовательно (один владелец).

## Объяснение

Бизнес часто говорит: «события должны идти по порядку». Инженер обязан уточнить: **по порядку чего?** Всех заказов магазина? Событий одного заказа? Операций одного счёта? От ответа зависит, хватит ли ключа и партиций или требование нереалистично при нужном параллелизме.

Kafka гарантирует: записи **в одной партиции** имеют чёткий порядок offset. Консьюмер, читая эту партицию, видит их в том же порядке (пока сам не параллелит обработку внутри себя неосторожно — об этом ниже).

Kafka **не** гарантирует: единый порядок между партициями. `OrderCreated` заказа A в partition 0 может «по времени стены» произойти раньше, чем `OrderCreated` заказа B в partition 1, но консьюмеры разных партиций обработают их как угодно относительно друг друга. Даже один консьюмер с двумя партициями чередует poll’ы — межпартиционного total order нет.

Поэтому паттерн такой: выберите **ordering key** = идентификатор сущности, для которой порядок критичен. Все события этой сущности — с этим ключом — одна партиция — один порядок. Сущности разные — можно параллелить.

Опасное место на стороне консьюмера: взяли сообщения из партиции по порядку, но отправили обработку в пул потоков без сохранения порядка по ключу. Тогда брокер честно отдал 1,2,3, а вы применили 1,3,2. Если нужен порядок — либо обрабатывайте строго последовательно в партиции, либо шардируйте воркеры по ключу внутри процесса (одинаковый ключ — одна очередь потока).

Продюсер тоже может нарушить ожидания: ретраи, несколько продюсеров без согласования, публикация из разных сервисов «примерно об одном» с разными ключами. Два сервиса пишут события заказа — договоритесь о ключе и о том, кто источник истины.

Смена числа партиций ломает привязку ключа к номеру партиции для **новых** сообщений. Старый хвост и новый хвост одного ключа могут оказаться в разных партициях — порядок «на всей истории» не склеить без доп. логики. Планируйте N заранее.

Есть случаи, когда порядок на уровне брокера не обязателен: достаточно идемпотентных upsert («последнее по version победило»). Тогда в событии носят `version` или `updated_at`, а консьюмер отбрасывает устаревшее. Это часто проще, чем бороться за тотальный порядок.

## Термины

- **Per-partition ordering** — порядок внутри партиции.
- **Total order** — единый порядок всего потока (обычно требует N=1 или внешнюю сериализацию).
- **Ordering key** — ключ для сохранения порядка сущности.
- **Causal order** — «B после A, потому что B следствие A»; обеспечивается тем же ключом/каналом.
- **Out-of-order** — приход/применение не в ожидаемом порядке.
- **Version vector / monotonic version** (идея) — поле для разрешения гонок без жёсткого порядка доставки.

## Как это устроено

Цепочка сохранения порядка для сущности `S`:

1. Все продюсеры ставят `key = id(S)`.
2. При неизменном N хеш направляет записи в партицию P.
3. Лидер P сериализует append: сначала A, потом B получают offset i, i+1.
4. Консьюмер-владелец P читает i затем i+1.
5. Если обработка последовательна, эффекты применятся в том же порядке.

Нарушения:

- другой ключ на событие B;
- увеличение N;
- параллельная обработка без учёта ключа;
- чтение двумя группами — у каждой свой мир, но это не ломает порядок внутри группы, просто независимые проекции.

## Пример

Нужен порядок по заказу:

```python
def publish(producer, order_id: str, event_type: str, payload: dict) -> None:
    producer.send(
        topic="orders.events",
        key=order_id.encode(),
        value=encode_json({"type": event_type, "order_id": order_id, **payload}),
    )


publish(p, "ord_1", "OrderCreated", {"total": 10})
publish(p, "ord_1", "OrderPaid", {"payment_id": "pay_9"})
publish(p, "ord_2", "OrderCreated", {"total": 5})
```

Внутри партиции для `ord_1` всегда Created перед Paid. Относительно `ord_2` гарантий «чей Created первый в мире» нет.

Плохой консьюмер, ломающий порядок:

```python
from concurrent.futures import ThreadPoolExecutor

pool = ThreadPoolExecutor(max_workers=8)

def on_batch(records):
    # ОПАСНО при требованиях порядка: Paid может обогнать Created того же ключа
    for r in records:
        pool.submit(handle, r)
```

Лучше для порядка по ключу внутри процесса:

```python
# упрощённо: очередь на каждый hash(key) % workers
def on_batch(records, sharded_queues):
    for r in records:
        q = sharded_queues[hash(r.key) % len(sharded_queues)]
        q.put(r)  # один поток читает q последовательно
```

## Разбор

Первый фрагмент демонстрирует правильный ключ. Второй — классическую ошибку «масштабировали потоками и потеряли порядок». Третий возвращает порядок внутри шарда ключа ценой сложности. Часто проще оставить обработку партиции однопоточной и масштабировать числом партиций/процессов.

Для статусов с версией:

```text
{ "order_id": "ord_1", "status": "PAID", "version": 5 }
```

если уже применили version=6, то version=5 игнорируется — даже при out-of-order доставке после replay.

## Практическое применение

- Лента операций по счёту / кошельку.
- Workflow заказа: created → paid → shipped.
- Сессии пользователя в аналитике (порядок событий сессии).
- Отказ от глобального порядка в пользу версий при высоком TPS.

## Типичные ошибки

- Требовать total order при сотнях тысяч msg/s без готовности к N=1.
- Разные ключи на связанные события («created без ключа, paid с order_id»).
- Параллелить handle без шардирования по ключу.
- Путать порядок в брокере с порядком в UI после нескольких проекций.
- После увеличения партиций обещать «как раньше по ключу на всей истории».

## Что запомнить

- Порядок Kafka — per partition.
- Ключ сущности = ваш инструмент порядка.
- Консьюмер может сам сломать порядок параллелизмом.
- Версионирование состояния — альтернатива жёсткому порядку.
- Total order и высокий параллелизм редко дружат.

## Задание

Сформулируй требование порядка для «баланс кошелька» и для «счётчик просмотров витрины». Для каждого выбери: ключ, число партиций «много/мало», нужна ли version-проверка на консьюмере. Объясни разницу.

## Связь со следующим уроком

Порядок — не единственная гарантия. Дальше — **семантика доставки**: at-most-once, at-least-once, exactly-once на уровне идей и практических компромиссов.
