# Переменные окружения и PATH

Мы уже знаем, что службы запускаются супервизором, а не человеком вручную из терминала. Но откуда программа вообще узнаёт, где искать нужные ей настройки и как найти команды, которые она вызывает? Для этого у каждого процесса есть **окружение**.

## Что такое переменные окружения

**Переменные окружения** — это небольшой набор пар «имя — значение», который ядро хранит для каждого процесса и передаёт по наследству его дочерним процессам при их создании. Программы читают эти значения через обычные средства своего языка программирования. Это удобный, гибкий способ передать программе настройки: пути к нужным файлам, режим работы, адрес сервера, к которому подключаться, и многое другое.

Важно не считать переменные окружения надёжным местом для секретов вроде паролей: их довольно легко увидеть со стороны, если знать, где посмотреть, и они могут случайно попасть в дочерние процессы там, где это не задумывалось. Для действительно чувствительных данных лучше подходят отдельные файлы с ограниченными правами доступа.

## PATH — особая переменная

Среди переменных окружения есть одна особенно важная — **PATH**. Это список каталогов, в которых оболочка ищет программу, когда вы вызываете её по короткому имени, а не по полному пути. Если вы набираете `python`, оболочка проходит по каталогам из PATH по порядку и запускает первую же найденную программу с этим именем — и порядок здесь имеет значение: если в разных каталогах из PATH оказалось по одноимённой программе, победит та, что нашлась раньше.

## Почему «у меня работает, а в службе — нет»

Интерактивная сессия в терминале обычно получает довольно богатое окружение: оболочка при запуске сама подгружает и дополняет его. А вот служба, запущенная супервизором, по умолчанию получает куда более скромный, урезанный набор переменных. Отсюда берётся классическая ситуация: команда прекрасно работает, если её ввести руками в терминале, но та же самая команда в службе выдаёт «команда не найдена» — потому что у службы попросту другой, более скромный PATH, и она ищет программу не там, где её только что нашли руками.

```text
   Интерактивный терминал
          ↓
   Богатое окружение (настройки профиля, активированное виртуальное окружение)

   Служба, запущенная супервизором
          ↓
   Урезанное окружение по умолчанию
```

## Пример

Разработчик активировал в терминале виртуальное окружение Python, и PATH стал начинаться с каталога этого окружения — поэтому команда `python` находит нужную версию со всеми установленными пакетами. Но служба, запущенная тем же именем `python`, никакого виртуального окружения не активировала и находит совсем другую, системную версию интерпретатора без нужных пакетов. Решение — указать для запуска службы не короткое имя, а полный путь именно к нужному интерпретатору, не полагаясь на то, что PATH службы совпадает с PATH в терминале разработчика.

## Типичные ошибки

Самая частая ошибка — полагаться в автоматически запускаемой службе на тот же PATH, что и в собственном интерактивном терминале. Вторая — хранить пароли и ключи в переменных окружения на общем компьютере без должного контроля доступа. Третья — не документировать, какие переменные окружения программе вообще нужны для работы, из-за чего настройка на новом компьютере превращается в угадывание.

## Что нужно запомнить

Окружение — часть контекста, который процесс получает при запуске и передаёт по наследству своим дочерним процессам. PATH определяет, где искать программы по короткому имени. У служб окружение обычно куда более скромное, чем у интерактивного терминала, поэтому для надёжного автозапуска лучше указывать полные пути, а не полагаться на совпадение PATH.

## Практика

Выведите значение PATH в своём терминале (например, командой `echo $PATH` в Linux/macOS). Найдите, каким именно полным путём на самом деле запускается ваш интерпретатор или компилятор, и запишите, как вы бы явно указали этот путь при настройке автозапуска — так, чтобы не зависеть от того, что PATH совпадёт с вашим личным терминалом.

## Связь со следующим уроком

Помимо переменных окружения, у операционной системы есть ещё один способ что-то сообщить работающему процессу — на этот раз асинхронно, в любой момент. Это **сигналы**.
