# Как это запускают и меняют

## Цель

Связать разработку с эксплуатацией: Git → сборка → Linux-сервер → Docker Compose → логи и выкат изменений приложения заказов. После урока вы поймёте, почему «у меня локально работает» недостаточно для продакшена.

## Что уже нужно понимать

Карта приложения. Базовый Git, Linux shell, Docker Compose, где живут данные.

## Объяснение

### Полный цикл изменения

1. Разработчик меняет код в ветке Git.
2. Review / CI (тесты, линтер).
3. Merge в main.
4. На сервере: `git pull` или выкат нового образа.
5. `docker compose up -d` с новыми образами.
6. Миграции БД.
7. Проверка healthcheck и логов.
8. Наблюдение метрик/ошибок.

Код без этого контура — лабораторная работа. Приложение — когда контур есть.

### Git: как меняют систему

- ветка на задачу: `feature/order-status`;
- маленькие коммиты с понятным why;
- PR: что изменилось в API контракте?
- теги релизов: `v1.4.0` ↔ образ `shop-api:1.4.0`;
- секреты (пароль Postgres, JWT secret) **не** коммитят — только `.env.example`.

Откат кода: `git revert` / предыдущий тег образа. Откат данных — отдельная история (бэкапы).

### Linux-сервер

Типичный VPS:

- SSH под ключом;
- пользователь без лишнего root в повседневности;
- Docker Engine + Compose plugin;
- файрвол: открыты 80/443, не открыт порт Postgres наружу;
- каталог `/opt/shop` с `docker-compose.yml` и `.env`.

Процессы приложения вы не запускаете «голым» `python` в tmux надолго — только для отладки. В бою — systemd или Docker restart policies.

### Docker Compose как единица стенда

```yaml
services:
  api:
    image: registry.example/shop-api:${TAG}
    env_file: .env
    depends_on: [db]
  worker:
    image: registry.example/shop-api:${TAG}
    command: python -m app.workers.billing
  db:
    image: postgres:16
    volumes: [pgdata:/var/lib/postgresql/data]
  broker:
    image: redpanda:...
```

Один файл описывает связку. Выкат: поменяли `TAG`, `compose pull && compose up -d`.

### Миграции

Новый код может ждать новую колонку. Порядок безопасного выката:

1. миграция *расширяющая* (добавить колонку nullable) → выкат API;
2. потом заполнение / NOT NULL;
3. избегать «ломающих» миграций без окна.

Миграции гоняют осознанно (`alembic upgrade`), не молча при каждом старте без блокировок — зависит от дисциплины команды.

### Логи — глаза эксплуатации

Куда смотреть:

```bash
docker compose logs -f api worker
```

В проде часто: stdout контейнера → сборщик (Loki/ELK) → поиск по `request_id` / `order_id`.

Без структурированных логов фон и HTTP не связать. Пишите JSON или ключ=значение: `order_id=90421 event=order_placed`.

### Healthcheck и готовность

Compose/оркестратор должен знать, когда api готов принимать трафик:

- `/health` — процесс жив;
- `/ready` — есть соединение с БД.

Иначе балансировщик отправит запросы в ещё стартующий контейнер → ложные 500 после выката.

### Конфигурация среды

| Переменная | Зачем |
|------------|-------|
| `DATABASE_URL` | связь с Postgres |
| `KAFKA_BOOTSTRAP` | брокер |
| `JWT_SECRET` | подпись токенов |
| `CORS_ORIGINS` | фронт |

Различайте `dev` / `stage` / `prod`. Один и тот же образ, разные env — норма.

### Как расследуют инцидент

1. Симптом UI: «заказ не оплачивается».
2. Логи api: POST 201 был?
3. Логи worker: событие съели? ошибка провайдера?
4. БД: статус в таблице?
5. Брокер: лаг консьюмера?
6. Недавний деплой в Git? откат образа?

Ops — продолжение архитектуры, не отдельная магия.

### Типичные ошибки поставки

- деплой руками без фиксации версии образа;
- Postgres порт 5432 в интернет;
- один `.env` на всех с продом в чате;
- выкат ломающей миграции вместе с кодом без плана;
- отсутствие логов worker;
- «починил на сервере файлом», забыл в Git — следующий деплой откатил фикс.

### Минимальный чеклист перед боем

- [ ] образы версионированы;
- [ ] тома БД на месте, бэкап протестирован хотя бы раз;
- [ ] секреты не в Git;
- [ ] HTTPS на входе;
- [ ] логи доступны;
- [ ] rollback: предыдущий `TAG` известен;
- [ ] миграции описаны в PR.

### Связь с курсом целиком

Вы учили Linux, Git, Docker, HTTP, FastAPI, SQL, фронт, очереди по отдельности. Ops — момент, где они **одновременно** нужны: без Git нет воспроизводимого изменения, без Linux некуда поставить Compose, без логов не связать HTTP и Kafka.

## Коротко

Систему меняют через Git и версионированные образы, запускают на Linux через Docker Compose, состояние БД держат на томах, поведение смотрят в логах api/worker. Выкат — это код + миграции + проверка готовности, а не «скопировать файлы на сервер».

## Проверьте себя

2. Зачем отдельный сервис `worker` с тем же образом, что `api`?
3. Как логи помогают связать 201 и «оплата не прошла»?
4. Что опаснее для данных: рестарт контейнера db или удаление volume?
