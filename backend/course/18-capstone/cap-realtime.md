# Живое обновление через WebSocket

## Цель

Понять, как статус заказа доезжает до UI без ручного обновления страницы: от изменения в БД/воркере до сообщения в сокете и setState в React. После урока вы сможете спроектировать простой канал «заказ обновился».

## Что уже нужно понимать

Путь HTTP-запроса. Отличие request/response от длительного соединения. Базовый JS.

## Объяснение

### Зачем WebSocket в приложении заказов

HTTP отлично создаёт заказ. Но статус потом меняют:

- оператор вручную;
- воркер биллинга;
- склад после резерва;
- таймаут отмены.

Если UI только делает GET раз в 30 секунд — оператор видит устаревшее. WebSocket даёт **push**: сервер сам сообщает клиентам.

### Модель соединения

1. После логина React открывает `ws://.../ws/orders` (или `wss` в проде).
2. Сервер держит сокет в памяти процесса (или через Redis pub/sub между репликами API).
3. Когда статус заказа меняется, API (или слой realtime) шлёт JSON-фрейм.
4. React обновляет список/карточку.

Соединение живёт минутами и часами, пока вкладка открыта.

### Фрагмент клиента

```ts
useEffect(() => {
  const ws = new WebSocket(`${wsBase}/ws/orders?token=${token}`);
  ws.onmessage = (ev) => {
    const msg = JSON.parse(ev.data);
    if (msg.type === "order_updated") {
      patchOrderInState(msg.order);
    }
  };
  ws.onclose = () => {
    // план: reconnect с backoff
  };
  return () => ws.close();
}, [token]);
```

Важно: токен в query — компромисс; часто предпочитают первое сообщение auth после connect.

### Фрагмент сервера (идея)

```python
@app.websocket("/ws/orders")
async def orders_ws(ws: WebSocket):
    await ws.accept()
    user = await auth_from_ws(ws)
    await hub.subscribe(user.id, ws)
    try:
        while True:
            await ws.receive_text()  # ping/pong или клиентские команды
    finally:
        await hub.unsubscribe(user.id, ws)
```

При обновлении заказа:

```python
async def notify_order_updated(order: Order):
    await hub.broadcast(
        user_id=order.owner_id,
        payload={"type": "order_updated", "order": OrderOut.model_validate(order).model_dump()},
    )
```

Кто вызывает `notify_order_updated`?

- service после успешного PATCH статуса;
- worker через «внутренний» вызов API или через Redis pub/sub, если воркер в другом процессе.

### Связка с HTTP и воркерами

Типичный полный цикл:

1. `POST /orders` → заказ `new` → HTTP ответ.
2. Событие в Kafka → billing worker → статус `paid` в БД.
3. Worker публикует в Redis канал `order_updated` **или** дергает внутренний endpoint.
4. Процесс API, держащий сокеты, получает сигнал → `ws.send_json(...)`.
5. React патчит строку таблицы.

Без шага 3–4 UI узнает о `paid` только после F5 или polling.

### Масштабирование: память процесса недостаточна

Один процесс FastAPI знает свои сокеты. Два реплики API за балансировщиком: заказ обновили на реплике A, сокет клиента на реплике B — нужен **брокер сигналов** (Redis Pub/Sub). Иначе realtime «иногда работает».

Для учебного Compose с одним `api` хватает in-memory hub. Для продакшена — сразу заложите pub/sub.

### Что слать по сокету

Минимально:

```json
{"type": "order_updated", "order": {"id": 90421, "status": "paid"}}
```

Или ещё короче: `{ "type": "...", "order_id": 90421 }` и клиент делает GET. Полный снимок удобнее для UI, но следите за размером и PII.

Не шлите секреты, полные платёжные реквизиты, чужие заказы. Фильтруйте по правам пользователя на сервере.

### Ошибки и переподключение

Сеть ноутбука моргнула — сокет умер. Клиент обязан:

- reconnect с exponential backoff;
- после reconnect сделать HTTP snapshot (`GET /orders`), чтобы не пропустить сообщения;
- не полагаться, что WebSocket — единственный источник истины.

Сервер — источник истины в PostgreSQL; сокет — ускоритель уведомлений.

### Когда WebSocket не нужен

- редкие обновления, достаточно кнопки «Обновить»;
- простой CRUD без совместной работы операторов;
- SSR-страница, которую читают раз в день.

Не тащите сокет «потому что модно», если polling раз в 10 с закрывает боль.

### Типичные ошибки

- держать бизнес-логику только в ws-сообщениях без записи в БД;
- забывать auth на сокете — утечка чужих заказов;
- broadcast всем подряд без фильтра `user_id`/`tenant`;
- отсутствие heartbeat → прокси режет «тихие» соединения;
- смешивать бинарные протоколы без нужды, когда JSON достаточен.

### Практика отладки

1. DevTools → Network → WS → Frames: видно ли сообщение после смены статуса?
2. Лог API: subscribe/unsubscribe.
3. Два браузера под одним пользователем: оба должны обновиться.
4. Убить worker: HTTP создаёт заказ, но `paid` не приходит — проблема фона, не сокета.
5. Убить pub/sub: при двух репликах симптом «иногда».

## Коротко

WebSocket доставляет в React факт «заказ изменился», пока HTTP создаёт и читает ресурсы. Источник истины — БД; сокет — push-канал. Воркеры и несколько реплик API требуют сигнала через Redis/шину, иначе живые обновления ломаются.
