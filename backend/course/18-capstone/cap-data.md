# Где живут данные

## Цель

Разложить данные приложения заказов по носителям: RAM процесса, диск, PostgreSQL, кэш, тома Docker — и понять, что пропадает при рестарте, а что нет. После урока вы перестанете путать «состояние UI» с «заказом в БД».

## Что уже нужно понимать

Карта приложения. Процессы Linux. Базовый Docker Compose.

## Объяснение

### Пять мест, которые путают новички

1. **RAM браузера** — React state;
2. **RAM процесса API** — кэш в памяти, список WebSocket, объекты сессий;
3. **Кэш (Redis)** — быстрые копии, сессии, pub/sub;
4. **PostgreSQL** — источник истины домена;
5. **Диск / том Docker** — файлы БД, логи, загруженные вложения.

У каждого — своя судьба при refresh, рестарте контейнера и падении сервера.

### RAM браузера

`useState`, данные списка заказов в памяти вкладки. Закрыли вкладку — нет. F5 — заново качаем с API (если нет устойчивого клиента в IndexedDB — обычно нет в учебном приложении).

Это **кэш представления**, не истина. Сервер мог уже сменить статус, пока UI рисовал старое — отсюда нужен refetch/WS.

### RAM процесса FastAPI

Примеры:

- in-memory hub сокетов;
- `lru_cache` на справочнике;
- глобальный dict «idempotency».

Рестарт контейнера `api` — всё исчезло. Поэтому сокеты переподключаются, кэш прогревается заново. Не храните заказы только в dict Python.

### Redis (если есть)

Живёт в своём процессе. Данные по умолчанию в RAM Redis; при конфигурации — снимки на диск.

Типичное использование в заказов:

- сессия / blacklist JWT;
- rate limit;
- кэш `GET /products/{id}`;
- pub/sub для WebSocket между репликами.

Потеря Redis болезненна для сессий и кэша, но **заказы должны пережить** это, если они в PostgreSQL. Не кладите единственную копию заказа в Redis.

### PostgreSQL — источник истины

Таблицы `orders`, `order_items`, `users`… Хранятся в файлах данных СУБД на диске. Commit = устойчивость (с оговорками fsync/настроек).

Рестарт API заказы не убивает. Рестарт Postgres — краткий даунтайм, данные на томе остаются. Удаление тома без бэкапа — катастрофа.

```text
INSERT → WAL → data files на томе
SELECT ← buffer cache RAM postgres ← диск
```

Буферный кэш Postgres — тоже RAM, но обслуживается СУБД; вы его не путаете с `useState`.

### Диск хоста и тома Docker

В Compose:

```yaml
services:
  db:
    image: postgres:16
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
```

Том `pgdata` переживает пересоздание контейнера. Без тома данные жили в writable-слое контейнера и исчезли бы вместе с ним.

Другие дисковые данные:

- логи (`./logs` или journald);
- загруженные файлы (`uploads:/app/uploads`);
- сертификаты (обычно read-only mount).

### Kafka и «данные в полёте»

Сообщения в топиках — тоже данные, часто на диске брокера. Это **журнал фактов/команд**, не замена таблице заказов. Consumer должен сделать эффект идемпотентно; источник статуса заказа после обработки — снова PostgreSQL (или отдельное read-модель хранилище).

### Сравнительная таблица

| Место | Пример | Переживёт F5 | Переживёт restart api | Переживёт restart db container с томом | Переживёт удаление тома |
|-------|--------|--------------|------------------------|----------------------------------------|-------------------------|
| React state | список на экране | нет* | да (на сервере) | да | да |
| API RAM | ws hub | — | нет | — | — |
| Redis | session | зависит | да | да (если том Redis) | нет |
| PostgreSQL | orders | да | да | да | нет |
| Kafka log | order_placed | да | да | да | нет |

\*если не persist во frontend storage

### Типичные баги «потерялись данные»

1. Хранили заказ только в state React — «пропал после обновления».
2. Записали в API dict — «пропало после деплоя».
3. Postgres без volume — «после compose down / up база пустая».
4. Кэш Redis отдали как истину и забыли invalidate — «старая цена навечно».
5. Файл upload в контейнере без тома — «картинка исчезла».

### Как выбирать, куда писать

- Нужно помнить завтра и для всех клиентов → **PostgreSQL**.
- Нужно ускорить повторное чтение → **кэш** с TTL поверх БД.
- Нужно только для текущего экрана → **React state**.
- Нужно связать реплики realtime → **Redis pub/sub**.
- Нужно асинхронно развязать работу → **Kafka**, эффект фиксировать в БД.

### Бэкапы — часть «где живут»

Том Docker на одном диске ноутбука — не бэкап. Реальная устойчивость: dump PostgreSQL, снапшоты тома, offsite. Для учебного стенда достаточно понимать риск; для боя — политика бэкапа обязательна.

### Практика самопроверки стенда

1. Создайте заказ.
2. Restart только `api` — заказ на месте?
3. Restart `db` — заказ на месте?
4. `docker volume rm ...` (осторожно!) — понимаете, что уничтожили?
5. Обновите страницу — заказ подтянулся по HTTP?

Если шаг 2 или 3 «нет» — вы храните не там.

## Коротко

Истина заказов — PostgreSQL на томе диска. React и RAM API — временные. Redis/Kafka ускоряют и развязывают, но не заменяют БД. Тома Docker отделяют жизнь данных от жизни контейнера; удаление тома = потеря данных.
