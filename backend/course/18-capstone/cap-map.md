# Карта всего приложения

## Цель

Собрать в одну картину всё, что вы изучали по частям: от клика в React до PostgreSQL, Kafka и Docker на Linux-сервере. После урока вы сможете провести пальцем по пути данных учебного приложения заказов и назвать роль каждого слоя.

## Что уже нужно понимать

HTTP и JSON, FastAPI, слои service/repository, SQL, основы фронта на React, идея WebSocket, очереди, Git, Linux, Docker Compose — хотя бы на уровне отдельных модулей курса.

## Объяснение

### Один продукт — много технологий

Учебное приложение (панель/магазин заказов) — не «набор уроков», а **одна система**, где каждая технология закрывает свою роль. Карта сверху вниз:

```text
[ Браузер: React + HTML/CSS/JS ]
        |  HTTP JSON          |  WebSocket
        v                     v
[ FastAPI: роуты, auth, валидация ]
        |
        v
[ Service: правила заказа ]
        |
        v
[ Repository: SQL ]
        |
        v
[ PostgreSQL на диске (том Docker) ]
        
[ Workers ] <--> [ Kafka ] <--> события заказа
[ Логи / Linux / Compose / Git ] — как это живёт и меняется
```

Ниже — что делает каждый блок и зачем он рядом с остальными.

### Frontend (React)

Задача: показать UI, держать локальное состояние экрана, отправлять действия пользователя на сервер.

- **HTML** — структура страницы заказа.
- **CSS** — внешний вид, не бизнес-правила.
- **JS/TS + React** — компоненты, хуки состояния, эффекты загрузки.
- Браузер **не** пишет в PostgreSQL и **не** знает про Kafka.

Фронт говорит только протоколами наружу: `fetch`/`axios` для HTTP и `WebSocket` для живых обновлений статуса.

### HTTP

Контракт запрос-ответ:

- метод и путь: `POST /api/orders`;
- заголовки: `Authorization`, `Content-Type: application/json`;
- тело JSON;
- статус и JSON ответа.

HTTP подходит для команд пользователя («создай заказ») и чтения («список заказов»). Для «статус изменился сам» чаще дополняют WebSocket или polling.

### WebSocket

Долгое соединение: сервер **пушит** события в браузер без нового HTTP на каждое изменение.

Пример: оператор видит, что заказ `90421` стал `paid`, потому что воркер биллинга закончил работу и API разослал сообщение подписчикам сокета.

WebSocket не заменяет HTTP для создания ресурсов — он дополняет его для realtime.

### FastAPI

Входная рамка бэкенда:

- маршрутизация;
- парсинг и валидация (Pydantic);
- зависимости (сессия БД, текущий пользователь);
- перевод доменных ошибок в HTTP-коды.

FastAPI — **край системы**, не место для SQL и не место для длинных циклов бизнес-логики.

### Service

Слой правил: «можно ли оформить заказ», «какой статус допустим», «как посчитать сумму».

Сервис оркестрирует репозитории и иногда ставит задачи в очередь. Он не знает про React и почти не знает про HTTP-статусы (кроме маппинга ошибок на границе).

### Repository

Единственное место, где живут SQL/ORM-запросы к таблицам заказов. Меняете PostgreSQL-диалект — правите репозиторий, а не кнопки React.

### SQL / PostgreSQL

Источник истины для заказов, пользователей, платежей (в учебном монолите — одна БД). Данные на диске переживают рестарт процесса API. Транзакции защищают инварианты.

### Kafka (и воркеры)

Когда HTTP не должен ждать тяжёлую работу:

- письмо клиенту;
- пересчёт аналитики;
- реакция склада на `order_placed`.

API публикует сообщение → **worker** (отдельный процесс) читает → делает работу → пишет результат в БД / шлёт уведомление. Фронт может узнать через WebSocket или следующим GET.

### Docker

Упаковка процессов: `api`, `worker`, `postgres`, `kafka` (или redpanda), иногда `frontend` nginx. Один `docker compose up` поднимает связку на машине разработчика и похожую — на сервере.

Тома Docker держат данные PostgreSQL на диске хоста, чтобы `compose down` не уничтожал БД без нужды.

### Linux

Сервер, где крутятся контейнеры или systemd-сервисы: процессы, права, логи в journald/файлах, SSH, файрвол, env-файлы. Без базового Linux вы не поймёте, «куда пропал» упавший воркер.

### Git

Как команда меняет систему безопасно: ветки, review, история, откат. Код фронта, бэкенда и Compose-файлы — в репозитории; секреты — нет.

### Как части связаны на одном сценарии

«Оператор создаёт заказ»:

1. React собирает форму → HTTP POST;
2. FastAPI валидирует → service;
3. repository INSERT в PostgreSQL;
4. service кладёт событие в Kafka (или outbox);
5. ответ JSON → React рисует карточку;
6. worker обрабатывает событие → обновляет статус в БД;
7. API пушит WebSocket → React обновляет бейдж статуса.

Один пользовательский смысл — цепочка технологий. Выпадение любого звена ломает разный симптом (UI пустой, 500, заказ есть, а письмо нет, статус не живой).

### Границы ответственности (шпаргалка)

| Слой | Имеет право | Не должен |
|------|-------------|-----------|
| React | UI, локальный state | SQL, секреты БД |
| HTTP/WS | транспорт | бизнес-инварианты |
| FastAPI | протокол, auth | сырой SQL по всему коду |
| Service | правила | детали CSS |
| Repository | SQL | решать «можно ли отменить» |
| PostgreSQL | хранить факты | знать про React |
| Kafka/worker | фон | быть единственным UI-каналом |
| Docker/Linux/Git | поставка и среда | заменять дизайн домена |

### Зачем карта нужна вам

Без карты каждое багфикс-приключение начинается с угадывания. С картой вы спрашиваете: «симптом на каком слое?» — и идёте туда. Это и есть навык собирать курс в одно приложение.

### Два направления чтения карты

**Сверху вниз (запрос пользователя):** UI → транспорт → API → правила → данные → (опционально) очередь.

**Снизу вверх (инцидент данных):** строка в PostgreSQL → кто её менял (api или worker) → какое событие/запрос → что увидел фронт.

Оба навыка нужны: продукт думает сверху, продакшен-отладка часто снизу.

### Что сознательно вынесено «за край» карты

CDN, service mesh, multi-region — не обязательны, чтобы понять учебное приложение. Сначала стабильно пройдите путь заказа на одном Compose. Усложнение инфраструктуры без ясной боли только размазывает карту.

### Мини-словарь связей

- React **использует** HTTP/WS, **не** SQL.
- FastAPI **вызывает** service, **не** наоборот.
- Service **вызывает** repository и producer.
- Worker **читает** Kafka, **пишет** БД, **сигналит** realtime.
- Git **версионирует** код и манифесты Compose; Linux **исполняет** контейнеры.

Если стрелка нарушена (например React → SQL) — это уже баг архитектуры, не «удобство».

## Коротко

Приложение заказов — связка React ↔ HTTP/WebSocket ↔ FastAPI ↔ service ↔ repository ↔ PostgreSQL, плюс Kafka/workers для фона и Docker/Linux/Git для запуска и изменений. Каждая технология закрывает одну роль; путь заказа проходит через несколько слоёв подряд.
