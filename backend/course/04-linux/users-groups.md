# Пользователи и группы

## Цель

Понять модель идентичности в Linux: UID, GID, пользовательские записи, группы и зачем нужны сервисные учётки без login.

## Исходные знания

FHS на уровне «где /etc и /home». Понятие процесса.

## Объяснение

Каждый процесс выполняется от имени числового идентификатора пользователя (UID) и группы (GID). Имена вроде `alice` — удобная оболочка над числами в системных базах. Ядро в проверках прав смотрит на числа.

Файлы `/etc/passwd` и `/etc/group` (плюс shadow-хранилище паролей) описывают локальных пользователей. Современные системы могут брать учётки из LDAP/SSSD, но идея та же: сопоставить имя и идентификаторы.

Обычный пользователь работает с ограниченными правами. `root` имеет UID 0 и обходит большинство проверок. Администрирование через `sudo` даёт временное повышение с аудитом, безопаснее постоянного login как root.

Группы позволяют разделять доступ между людьми и службами без выдачи прав «всем». Пользователь имеет основную группу и дополнительные. Файлы несут владельца-пользователя и владельца-группу.

Сервисные пользователи (`www-data`, `nobody`, пользователи systemd) нужны, чтобы демон не бежал от root. Компрометация службы тогда ограничена правами этой учётки.

Домашний каталог, shell login и срок пароля — свойства учётки. Для роботов и серверов часто создают пользователя приложения с `/usr/sbin/nologin`, чтобы нельзя было зайти интерактивно, но процессы жили от его UID.

Команды `id`, `whoami`, `getent` помогают увидеть, кем вы являетесь в конкретной сессии, включая дополнительные группы — важно для доступа к `/dev/ttyUSB*` или docker-сокету.

## Термины

**UID / GID** — числовые идентификаторы пользователя и группы.

**root** — суперпользователь с UID 0.

**sudo** — механизм делегирования административных команд.

**Сервисный пользователь** — учётка для демонов без интерактивного входа.

**passwd/group** — классические базы локальных учёток.

## Как это работает

При login система аутентифицирует пользователя, запускает сессию с его UID/GID и окружением. Дочерние процессы наследуют идентификаторы, пока не сделают легальный переход (setuid-программы, sudo, capabilities).

Проверка доступа к файлу сравнивает UID/GID процесса с владельцем файла и битами режима. Группы процесса расширяют «группу» в этой проверке.

Смена пользователя в юните systemd (`User=`) задаёт идентичность службы на старте без интерактивного login.

## Пример

```bash
whoami
id
getent passwd "$USER"
getent group "$(id -gn)"
ls -l /etc/passwd
```

## Разбор

`whoami` и `id` показывают имя и числовые id, включая группы.

`getent` читает учётки через системный слой (важно, если есть сетевые базы).

`/etc/passwd` обычно читается всеми, хэши паролей живут в shadow с жёсткими правами.

## Ошибки

- Работать постоянно под root «для удобства».
- Выдавать приложению UID 0 вместо сервисного пользователя.
- Забывать дополнительные группы при доступе к устройствам.
- Править passwd вручную без понимания shadow и блокировок.

## Что запомнить

- Ядро оперирует UID/GID, имена — удобство.
- Группы — способ разделить доступ.
- Сервисные учётки ограничивают ущерб.
- sudo лучше постоянного root-login.

## Задание

Выведите `id` для своего пользователя. Найдите через `getent` свою запись и основную группу. Проверьте, есть ли у вас дополнительные группы, и для чего они могут быть нужны.

## Дополнение: практика и нюансы

`useradd`/`adduser` различаются по дистрибутивам. Читайте man конкретной системы.

UID в NFS/кластерах должны совпадать между хостами, иначе права «плывут».

Не используйте одного человека-UID для всех служб. Разделение — базовая гигиена.

Проверка: `sudo -u serviceuser -H env` показывает окружение от имени службы.


Проверьте согласованность настроек после перезагрузки: разовые правки ip/sysctl часто исчезают без конфига.

Сверьте документацию сервиса с фактическим unit/командой запуска: расхождения — частый источник сюрпризов.

Зафиксируйте ожидаемый код возврата успешного сценария в runbook рядом с командой проверки.
