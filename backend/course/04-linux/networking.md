# Сеть на хосте Linux

## Цель

Увидеть сеть глазами Linux-хоста: интерфейсы, адреса, маршруты, DNS-настройки и базовые команды диагностики без глубокого курса протоколов.

## Исходные знания

Службы и процессы. Общее представление, что у машины есть IP-адрес и шлюз (детали будут в модуле сетей).

## Объяснение

На Linux сетевая карта (или виртуальный интерфейс) представлена объектом интерфейса: `eth0`, `ens33`, `wlan0`, `lo`. У интерфейса бывают адреса, состояние UP/DOWN и счётчики пакетов. Loopback `lo` всегда для связи с собой.

Адреса и маршруты хранит ядро. Утилиты `ip` (из iproute2) — современный способ смотреть и менять это. Устаревшие `ifconfig`/`route` ещё встречаются, но учиться лучше на `ip`.

Маршрут по умолчанию указывает, куда слать пакеты «в остальной мир». Без него доступна только прямо подключённая сеть. DNS на хосте — настройка резолвера (`/etc/resolv.conf` или systemd-resolved): превращение имён в адреса.

Firewall (nftables/iptables/firewalld) фильтрует пакеты. Служба может слушать порт, но пакеты не дойдут, если фильтр закрыт. Диагностика всегда разделяет: «процесс слушает?» и «пакет доходит?».

Проверки: есть ли адрес, есть ли маршрут, отвечает ли сосед (ping — если разрешён), резолвится ли имя, открыт ли TCP-порт. Каждая проверка отвечает на свой вопрос; одна «не работает сеть» бесполезна.

В облаках и контейнерах интерфейсы виртуальные, но команды те же. NAT и оверлеи добавляют слои — сначала убедитесь в базовой таблице маршрутов namespace.

## Термины

**Интерфейс** — логическое сетевое устройство в ядре.

**Маршрут** — правило, куда отправлять пакеты для префикса.

**Резолвер** — клиентская настройка DNS на хосте.

**iproute2** — набор утилит (`ip`, `ss`) для сети Linux.

**`ss`** — утилита просмотра сокетов (замена части netstat).

## Как это работает

Приложение вызывает сокеты; ядро выбирает маршрут и интерфейс исходя из таблицы. Драйвер отправляет кадры. Входящие пакеты поднимаются по стеку к сокету, если порт и протокол совпали и фильтры пустили.

`ss -lntp` показывает слушающие TCP-сокеты и процессы. Это ответ на «занят ли порт». `ip route` отвечает на «куда уйдёт пакет».

Службы NetworkManager, systemd-networkd или облачные агенты могут управлять конфигом. Ручные `ip addr add` часто живут до перезагрузки, если не закреплены в конфиге.

## Пример

```bash
ip link
ip addr
ip route
ss -lntp 2>/dev/null | head
getent hosts localhost
ping -c 1 127.0.0.1
```

## Разбор

`ip link` — состояние интерфейсов. `ip addr` — адреса. `ip route` — маршруты, включая default.

`ss` показывает слушателей. `getent hosts` проверяет резолв через системные механизмы.

ping на loopback проверяет стек без внешней сети.

## Ошибки

- Лечить DNS, когда нет маршрута по умолчанию.
- Путать «порт слушает на 127.0.0.1» с доступностью извне.
- Править сеть только вручную и удивляться после reboot.
- Игнорировать firewall после открытия приложения.

## Что запомнить

- Интерфейс, адрес, маршрут, DNS — разные слои проверки.
- `ip` и `ss` — базовый инструментарий.
- Слушающий сокет ≠ открытый путь через фильтр.
- Постоянство настроек даёт конфиг, не разовый `ip`.

## Дополнение: практика и нюансы

`ip -s link` показывает ошибки/drops на интерфейсе — полезно при плохом кабеле/Offload.

`ss -s` — сводка сокетов. Рост TIME_WAIT при тестах — нормален, но экстремумы смотрите.

DNS: `resolvectl status` на systemd-системах. Неправильный DNS маскируется под «нет сети».

В облаке security group — ещё один фильтр до вашего nftables. Проверяйте оба.


Посмотрите, на каком интерфейсе слушает сервис: localhost не равен доступности из LAN.

Проверьте права на каталог целиком по пути, а не только на конечный файл.

Сверьте группы пользователя после usermod: новая группа часто требует перелогина.
