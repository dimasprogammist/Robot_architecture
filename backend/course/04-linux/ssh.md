# SSH — удалённый доступ

## Цель

Понять, как SSH даёт удалённый shell и туннели: ключи, аутентификация, агент, конфиг клиента и базовые меры безопасности сервера.

## Исходные знания

Терминал, пользователи Linux, сеть на уровне «есть IP и порт». Служба sshd.

## Объяснение

SSH (Secure Shell) — протокол удалённого доступа с шифрованием и проверкой сервера. Клиент соединяется с sshd на порту 22 (или другом), проверяет ключ хоста, аутентифицирует пользователя и получает сессию shell или выполняет одну команду.

Аутентификация по паролю проста и опасна на открытом интернете (подбор). Предпочтительны ключи: у клиента приватный ключ, на сервере — строка в `authorized_keys`. Приватный ключ не передаётся; доказывается владение.

При первом подключении клиент спрашивает fingerprint хоста и сохраняет его в `known_hosts`. Если fingerprint внезапно изменился, это может быть подмена сервера или легитимная переустановка — проверяйте out-of-band.

`~/.ssh/config` задаёт алиасы хостов, пользователя, ключ и порты. Это экономит ошибки и делает команды короче. Права на `.ssh` и ключи должны быть узкими, иначе клиент откажется работать.

Агент (`ssh-agent`) держит расшифрованные ключи в памяти сессии, чтобы не вводить passphrase каждый раз. На общих машинах агент нужно понимать осторожно.

SSH умеет туннели и проброс портов, копирование (`scp`/`sftp`), проброс агента. Для начала освойте вход, ключи и безопасный `authorized_keys`. Не отключайте проверку хоста «навсегда» ради удобства.

На сервере: отключить root-login по паролю, запретить пустые пароли, ограничить пользователей, иногда сменить порт и поставить fail2ban/аналог — по политике. Обновления sshd обязательны.

## Термины

**sshd** — серверный демон SSH.

**Ключевая пара** — приватный и публичный ключ пользователя.

**authorized_keys** — список публичных ключей, которым разрешён вход.

**known_hosts** — база известных ключей серверов у клиента.

**Fingerprint** — короткий отпечаток ключа для сверки.

## Как это работает

После TCP-соединения стороны согласуют криптографию и обмениваются материалом ключей сессии. Сервер доказывает владение host key. Клиент аутентифицирует пользователя. Далее открывается канал сессии: PTY для интерактива или exec одной команды.

Каждый последующий канал (туннель) идёт внутри того же защищённого соединения. Обрыв TCP рвёт сессию; reconnect-утилиты существуют, но базово SSH сессионен.

## Пример

```bash
# генерация ключа (пример алгоритма; на практике следуйте актуальной политике)
ssh-keygen -t ed25519 -f /tmp/demo_id_ed25519 -N ""

# типичный вход (не запускает реальный хост в этом примере)
# ssh -i ~/.ssh/id_ed25519 user@server.example

ls -la ~/.ssh 2>/dev/null || echo "no ~/.ssh yet"
man ssh 2>/dev/null | head -n 5 || true
```

## Разбор

`ssh-keygen` создаёт пару файлов: приватный и `.pub`. На сервер копируют только публичный.

Проверка прав `~/.ssh` — часть рабочей гигиены. Документация `man ssh` описывает опции клиента.

В реальной работе добавляют публичный ключ в `authorized_keys` целевого пользователя.

## Ошибки

- Светить приватный ключ в чат/репозиторий.
- Игнорировать предупреждение о смене host key.
- Оставлять парольный root-login на публичном IP.
- Права 777 на `.ssh`.

## Что запомнить

- SSH шифрует сессию и проверяет хост.
- Ключи предпочтительнее паролей на серверах.
- known_hosts защищает от грубой подмены.
- Конфиг клиента и права файлов — часть безопасности.

## Задание

Создайте ключевую пару в тестовом пути. Посмотрите содержимое `.pub`. Опишите, какой файл можно копировать на сервер, а какой нельзя. Если есть свой сервер — добавьте ключ и войдите без пароля.

## Дополнение: практика и нюансы

`ssh -v` показывает этапы auth — первый инструмент при отказе входа. Не путайте отказ ключа с отказом сети.

Опция `IdentitiesOnly=yes` мешает клиенту перебирать лишние ключи и упираться в MaxAuthTries.

На сервере `AllowUsers`/`DenyUsers` сужают вход. Fail2ban/аналог — по угрозной модели.

Копирование ключа: `ssh-copy-id` удобно, но проверяйте содержимое authorized_keys вручную на критичных хостах.


Сверьте документацию сервиса с фактическим unit/командой запуска: расхождения — частый источник сюрпризов.

Зафиксируйте ожидаемый код возврата успешного сценария в runbook рядом с командой проверки.
