# Сервер через терминал — повседневная работа

## Цель

Сложить рабочий цикл администратора: войти по SSH, проверить здоровье хоста, службы, логи, диск и сеть, внести аккуратное изменение и зафиксировать результат.

## Исходные знания

Все предыдущие темы модуля Linux: процессы, systemd, пакеты, логи, SSH, права.

## Объяснение

Сервер без монитора управляется удалённо. Ваша задача — не «знать все команды», а иметь устойчивый маршрут осмотра. Сначала доступ и идентичность: кто я, на каком хосте, какое время. Затем ресурсы: CPU, память, диск. Затем службы приложения. Затем логи вокруг времени инцидента. Затем сеть, если симптомы внешние.

Изменения делайте маленькими и обратимыми. Перед правкой конфига — копия. После правки — reload/restart и проверка статуса. Если есть healthcheck — дерните его. Не держите интерактивный редактор как единственный источник правды: конфиг должен лежать в файле и в учёте (git/ansible).

Диск заполняется логами и данными. `df` и `du` отвечают на разные вопросы: файловая система vs деревья каталогов. inode тоже могут закончиться при массе мелких файлов.

Обновления безопасности планируйте. Слепой `upgrade` на проде без окна — риск. Читайте, что будет обновлено, особенно ядро и systemd.

Документируйте уникальности хоста: зачем этот костыль в `/etc`, какой таймер критичен. Будущий вы скажет спасибо.

Для роботов и edge-устройств цикл тот же, но добавляются устройства `/dev`, udev и иногда офлайн-обновления. Принцип осмотра не меняется.

Автоматизация повторяющегося осмотра — скрипты и мониторинг. Сначала научитесь руками, потом автоматизируйте.

## Термины

**Healthcheck** — проверка, что сервис реально отвечает.

**Incident window** — временной интервал, в котором ищут логи.

**Rollback** — откат изменения.

**Capacity** — запас CPU/RAM/диска.

**Runbook** — короткая инструкция «что проверить».

## Как это работает

Практически вы строите гипотезы и опровергаете их командами, каждая из которых закрывает один слой: процесс жив? порт слушает? диск пишет? DNS резолвит? сертификат не истёк? systemd не в restart loop?

Сигналы мониторинга (алерты) направляют осмотр, но не заменяют чтение логов. Алерт «5xx выросли» — начало, не диагноз.

Бэкапы проверяют восстановлением, не наличием файла. Хотя бы раз пройдите restore на копии.

## Пример

```bash
set -e
hostname; date; uptime
df -h
free -h 2>/dev/null || true
systemctl --failed 2>/dev/null || true
journalctl -p err -n 30 --no-pager
ip route | head
ss -lntp | head
```

## Разбор

Блок собирает быстрый паспорт: кто/когда/нагрузка, диск, память, упавшие юниты, ошибки журнала, маршрут и слушатели.

Это не полная диагностика, а стартовый runbook. Дальше углубляются в конкретную службу приложения.

Порядок важен: нет смысла копать тонкий баг приложения на хосте без места на диске.

## Ошибки

- Менять три вещи сразу без проверки.
- Рестартовать «на всякий случай» всё подряд.
- Игнорировать failed units.
- Не оставлять следов, что меняли.

## Что запомнить

- Есть стандартный маршрут осмотра хоста.
- Изменения маленькие, с откатом и проверкой.
- Диск, служба, лог, сеть — разные вопросы.
- Автоматизация следует за ручным пониманием.

## Задание

Составьте свой одностраничный runbook из 8–12 команд для «сервер странно себя ведёт». Прогоните его на учебной машине и сохраните вывод в файл с датой.

## Дополнение: практика и нюансы

Держите файл runbook рядом с инвентарём хоста. После инцидента обновляйте runbook тем, чего не хватило.

Изменения через ansible/cloud-init воспроизводимее ручных правок. Ручное — допустимо в hot-fix с последующей фиксацией.

Перед reboot: есть ли автозапуск служб, есть ли консольный доступ, если сеть не поднимется.

Снимайте `systemctl status` и хвост journal в файл с timestamp до «починки наугад».


Убедитесь, что firewall и security group оба пропускают нужный порт — одного слоя мало в облаке.
