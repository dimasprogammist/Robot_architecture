# Слоистая архитектура

## Цель

Разложить сервис заказов на слои: транспорт, сценарии, домен, инфраструктура — и понять, что каждый слой делает в запросе `POST /orders/{id}/ship`. После урока вы проведёте один запрос через все слои по именам функций.

## Что уже нужно понимать

Направление зависимостей. Слои — классический способ упорядочить монолит. Это модель, а не культ: слой должен быть тонким смыслом, а не папкой-отпиской.

## Объяснение

Типичные слои для Orders API:

1. **Интерфейсный / транспортный** — FastAPI роуты, WebSocket, CLI. Понимает HTTP и DTO.
2. **Прикладной (application)** — сценарии use-case: `create_order`, `ship_order`. Оркестрирует домен и порты.
3. **Доменный** — сущности, инварианты, политики статусов. Без SQL и HTTP.
4. **Инфраструктурный** — SQLAlchemy, SMTP, Kafka producer, файловая система.

Запрос идёт сверху вниз по управлению, зависимости — внутрь. Инфраструктура реализует порты, объявленные для application/domain.

Антипаттерн «слоистая лапша»: каждый слой — тупой прокси без правила (`api` вызывает `service` вызывает `manager` вызывает `crud` вызывает `repo`), а правило всё равно в SQL. Слой оправдан, только если несёт свою работу.

Транзакции обычно живут на прикладном уровне или в unit of work инфраструктуры: один сценарий — одна бизнес-транзакция.

## Термины

- **Use-case / сценарий** — прикладная операция.
- **Порт и адаптер** — интерфейс и реализация на краю (идея hexagonal).
- **Антикоррупционный слой** — перевод чужой модели в свою (когда появится внешняя система).

## Как это устроено

Сценарий `ship`:

1. Роут парсит `order_id`, вызывает application.
2. Application открывает транзакцию, грузит заказ через репозиторий.
3. Домен меняет статус с проверкой.
4. Репозиторий сохраняет.
5. Порт notifier вызывается (или пишется outbox в той же транзакции).
6. Роут сериализует DTO ответа.

Ошибка домена → application пробрасывает → транспорт мапит в HTTP. Слой не глотает чужое молча.

## Пример

```python
# domain
@dataclass
class Order:
    id: int
    status: str
    def ship(self) -> None:
        if self.status != "packing":
            raise Conflict("need packing")
        self.status = "shipped"

# application
class ShipOrder:
    def __init__(self, repo, notifier, uow):
        self._repo, self._notifier, self._uow = repo, notifier, uow

    def __call__(self, order_id: int) -> Order:
        with self._uow:
            order = self._repo.get(order_id)
            order.ship()
            self._repo.save(order)
            self._notifier.order_shipped(order)
            return order

# transport
@router.post("/{order_id}/ship", response_model=OrderOut)
def ship_endpoint(order_id: int, use_case: ShipOrder = Depends(get_ship_order)):
    try:
        order = use_case(order_id)
    except Conflict as e:
        raise HTTPException(409, str(e)) from e
    return OrderOut.model_validate(order)
```

## Разбор примера

Доменная `ship` ничего не знает о БД: её можно вызвать в тесте на чистом объекте. Application связывает шаги и границы транзакции. Transport — тонкий. Инфраструктурные `repo` и `notifier` сюда не попали, но именно они реализуют детали за кадром.

Имя `ShipOrder` как use-case подчеркивает сценарий, а не «бог OrderService на 40 методов» — хотя один сервис-класс с методами тоже допустим, пока не расползётся.

## Типичные ошибки

- Анемичный домен: всё в service, объекты — мешки полей.
- Толстый транспорт: SQL в роуте.
- Слой ради слоя без правила.
- Транзакция на каждый мелкий вызов репозитория без сценария.

## Что запомнить

Слои режут Orders API по ролям в обработке запроса. Зависимости внутрь. Сценарий оркестрирует. Домен держит правила. Инфраструктура — детали. Не плодите прокси без смысла.
