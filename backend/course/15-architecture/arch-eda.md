# Событийная архитектура

## Цель

Понять событийную модель на примере магазина: заказ публикует `order_placed`, склад и биллинг реагируют асинхронно. После урока вы сможете объяснить разницу между «запрос ждал всех» и «запрос опубликовал факт», плюс когда события не нужны.

## Что уже нужно понимать

Монолит, модули, микросервисы. Очереди/брокеры на уровне идеи (Kafka). Идемпотентность и повторная доставка сообщений.

## Объяснение

### Событие — факт о прошлом

Событие — запись о том, что **уже произошло** в домене, а не команда «сделай».

Примеры для магазина:

- `order_placed` — заказ принят и сохранён;
- `payment_captured` — деньги списаны;
- `stock_reserved` — остаток зарезервирован;
- `order_cancelled` — заказ отменён.

Имя в прошедшем времени. Payload несёт данные, нужные подписчикам, без утечки всей БД.

```json
{
  "event_id": "01HZX...",
  "type": "order_placed",
  "occurred_at": "2026-09-25T10:15:00Z",
  "payload": {
    "order_id": 90421,
    "user_id": 55,
    "total": "1990.00",
    "currency": "RUB",
    "items": [{"product_id": 12, "qty": 2, "price": "995.00"}]
  }
}
```

### Поток в интернет-магазине

Синхронный путь (упрощённо):

1. Клиент `POST /api/orders`.
2. `orders` сохраняет заказ в БД (монолит или orders-service).
3. `orders` публикует `order_placed` в Kafka (или другую шину).
4. HTTP отвечает `{ "order_id": 90421, "status": "accepted" }` — **не ждал** склад и биллинг до конца.
5. Consumer биллинга читает событие → создаёт платёж.
6. Consumer склада читает событие → резервирует остаток.
7. При успехе/ошибке они публикуют свои события; orders может обновить статус или UI узнаёт по WebSocket/polling.

Так HTTP не держит соединение, пока банк думает 3 секунды.

### Кто публикует, кто подписан

| Компонент | Роль |
|-----------|------|
| Orders (модуль/сервис) | источник `order_placed` |
| Billing worker | подписчик → charge / refund |
| Stock worker | подписчик → reserve / release |
| Notification worker | подписчик → email/push |
| Analytics | подписчик → витрина метрик |

Издатель не вызывает подписчиков напрямую. Он не знает полный список — это снижает связность.

### Монолит тоже может быть событийным

События ≠ обязательные микросервисы. В модульном монолите:

- тот же процесс пишет в outbox-таблицу;
- воркер того же Compose читает outbox и кладёт в Kafka;
- или даже in-process шина для начала.

Событийность — про **стиль интеграции**, не только про число репозиториев.

### Outbox — чтобы не потерять событие

Опасный порядок:

1. commit заказа;
2. publish в Kafka;
3. если publish упал — заказ есть, события нет.

Надёжный паттерн transactional outbox:

```python
with db.begin():
    order = insert_order(...)
    insert_outbox(db, type="order_placed", payload=...)
# отдельный publisher читает outbox и шлёт в брокер
```

Заказ и запись о событии атомарны в одной БД. Доставка в брокер — eventual, но не теряется молча.

### Идемпотентность подписчиков

Брокер может доставить `order_placed` дважды. Billing обязан:

```python
def on_order_placed(event):
    if payments_repo.exists_by_event_id(event.event_id):
        return  # уже обработали
    payments_repo.create(..., event_id=event.event_id)
```

Без идемпотентности получите двойное списание — худший баг магазина.

### Согласованность: eventual

После ответа HTTP склад может ещё не зарезервировать товар. UI показывает «обрабатывается». Это нормально для событийной модели, если бизнес согласен.

Если бизнес требует «либо всё, либо ничего» в момент клика — либо синхронная транзакция монолита, либо сага с чётким UX ожидания.

### Когда событийная архитектура помогает магазину

- долгие побочные эффекты (письма, антифрод, аналитика);
- несколько независимых реакций на один факт;
- сглаживание пиков (очередь буферизует);
- ослабление связности между модулями/сервисами;
- аудит: журнал фактов можно хранить и переигрывать (осторожно с неидемпотентными эффектами).

### Когда НЕ дробить и не усложнять событиями

Не вводите Kafka и десяток топиков, если:

1. один модуль синхронно делает всё нужное за 50 мс в одной транзакции;
2. нет второго подписчика — событие ради события;
3. команда не умеет дебажить «потерялось в очереди»;
4. нужна строгая атомарность checkout без готового outbox/саги;
5. объём заказов крошечный, а операционная цена брокера высокая.

Часто достаточно: монолит + фоновая очередь задач (Redis/RQ) для писем, без полной EDA.

### Сравнение с синхронным вызовом

| | Синхронный HTTP | Событие |
|--|-----------------|---------|
| Связность | вызывающий знает адресата | знает тип события |
| Ответ клиенту | ждёт цепочку | может ответить рано |
| Отказ downstream | сразу виден вызывающему | нужна политика ретраев/DLQ |
| Отладка | стек вызовов | трейсы + лог событий |

### Типичные ошибки

- события-команды: `ChargePayment` под видом события — путаница ответственности;
- огромный payload «весь агрегат» или наоборот пустой `order_id` без данных и гонки чтений;
- отсутствие `event_id` и идемпотентности;
- бесконечные ретраи без dead letter queue;
- циклические события `A→B→A` без стоп-условия;
- использование шины как RPC (запрос-ответ через топики без нужды).

### Практика на истории заказа

Разложите checkout:

1. какой факт фиксирует orders синхронно?
2. кто должен узнать и зачем?
3. что увидит пользователь, пока подписчики работают?
4. что делать при двойной доставке?
5. что делать, если stock не смог резервировать — какое компенсирующее событие?

Если на эти вопросы нет ответов — рано включать «событийную архитектуру» в прод.

## Коротко

В событийной модели магазина `order_placed` — факт: склад и биллинг реагируют сами, HTTP заказа не обязан ждать всю цепочку. Нужны outbox, идемпотентность и eventual consistency. Не усложняйте событиями и микросервисами то, что закрывается одной транзакцией модульного монолита.
