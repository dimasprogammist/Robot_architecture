# Разделение ответственности

## Цель

Научиться замечать и устранять смешение ответственностей в коде заказов: когда один модуль и валидирует HTTP, и считает скидку, и шлёт письмо, и строит SQL. После урока вы проведёте аудит короткого фрагмента и разрежете его по ролям.

## Что уже нужно понимать

Слои API, сервис, домен, репозиторий. Separation of Concerns (SoC) — принцип: каждый кусок кода решает одну задачу на своём уровне абстракции. Это не «один класс = один метод», а «одна причина меняться» в духе соседнего SOLID, но здесь фокус на ролях в сценарии.

## Объяснение

Смешение выглядит так: роут `create_order` на 80 строк — парсинг, скидка, запись, email, метрика Prometheus, логирование в файл. Меняется шаблон письма — рискуете сломать создание заказа. Меняется формула скидки — трогаете HTTP.

Разделение: роут принимает DTO; сервис оркестрирует; pricing — отдельный порт; notifier — порт; метрики — декоратор/middleware или вызов порта telemetry. Правка письма не открывает файл роутера.

SoC нарушают и «удобные» shared-утилиты: `save_order_and_notify_and_log` — снова слияние. Имя функции, в котором три «and», — запах.

Фронтенд-параллель: кнопка не должна знать SQL. Бэкенд-параллель: репозиторий не должен знать, что такое «красивый subject письма».

## Термины

- **Concern** — аспект ответственности (транспорт, правило, хранение, уведомление).
- **Смешение** — несколько concern в одной единице изменения.
- **Причина изменения** — зачем файл открыли в git diff.

## Как это устроено

Проверка SoC вопросами к модулю:

1. Зачем этот файл обычно меняют?
2. Сколько разных «зачем» получилось?
3. Можно ли вынести второе/третье без копипасты правила?

Для `OrderService.cancel`: причины изменения — новые ветки сценария отмены, новые порты после отмены. Если в том же методе правите SQL join отчёта — concern отчёта смешан.

Middleware FastAPI — хороший SoC для auth/logging: не повторять в каждом роуте.

## Пример

```python
# Смешение
@app.post("/orders")
def create(payload: dict, db: Session = Depends(get_db)):
    if len(payload.get("customer", "")) < 1:
        return JSONResponse({"e": "bad"}, status_code=400)
    price = 1000
    if payload.get("city") == "Казань":
        price *= 0.95
    row = OrderRow(customer=payload["customer"], city=payload["city"], status="new", price=price)
    db.add(row)
    db.commit()
    requests.post("https://mailer/send", json={"to": payload["customer"], "text": "created"})
    metrics.inc("orders_created")
    return {"id": row.id, "price": price}


# Разделение (эскиз)
@router.post("/orders", status_code=201)
def create(payload: OrderCreate, svc: OrderService = Depends(get_svc)):
    order = svc.create(payload.customer, payload.city)
    return to_out(order)

# service.create: Order.create → pricing.quote → repo.add → notifier.created → metrics через порт
```

## Разбор примера

В смешанном варианте одна функция знает JSONResponse, формулу Казани, ORM, HTTP mailer, метрики. Тест «скидка в Казани» требует сеть и БД.

В разделённом роут меняется только при смене контракта HTTP. Формула цены — в `pricing`. Письмо — в notifier. Метрики можно повесить на порт или на декоратор сценария. Diff в git становится локальным.

## Типичные ошибки

- Считать SoC = «много маленьких файлов» без ясных ролей.
- Выносить всё в микросервисы вместо модулей — SoC ≠ сеть.
- Прятать смешение за фасадом `OrderFacade.do_everything`.

## Что запомнить

Разделение ответственности локализует изменения. Ищите несколько причин править один кусок. Режьте по ролям сценария заказа. Имена с тремя «и» — запах. SoC работает внутри монолита.

## Ещё один разрез: отчёт и оплата

Тот же заказ. Бухгалтерии нужен CSV раз в сутки, кассе — ответ за миллисекунды, складу — событие «оплачено». Если всё это пишет `OrderService.pay`, у функции три причины меняться: формат CSV, протокол кассы, контракт склада.

Разделение здесь такое. `pay` меняет состояние заказа и вызывает порт `PaymentGateway`. Выгрузка CSV — отдельная функция, которая читает уже сохранённые заказы. Уведомление склада — подписчик на факт «статус стал paid», а не строка внутри `pay`. Тогда смена колонок CSV не трогает кассу.

Проверка, что разрез настоящий: можете ли вы протестировать оплату без файла и без склада? Если нет, ответственность всё ещё смешана, просто разложена по вызовам внутри одной функции.

## Связь со следующим уроком

Свяжем SoC с **связанностью и зацеплением**: когда связи между модулями вредят изменениям.
