# Монолит

## Цель

Понять монолит как один деплойный юнит: один процесс приложения и одна основная база, на примере интернет-магазина заказов. После урока вы сможете объяснить, почему монолит — не «плохая архитектура», а осознанный выбор с предсказуемой ценой изменений.

## Что уже нужно понимать

Вы уже делили код на слои, сервисы и репозитории. Монолит — про границы *развёртывания*, а не про «всё в одном файле». Внутри монолита может быть чистая структура; снаружи — один артефакт, который стартует целиком.

## Объяснение

### Что такое монолит на практике

Монолит — система, которую вы запускаете как **один процесс** (или небольшой набор процессов одного приложения) и которая обычно опирается на **одну базу данных** как на источник истины для домена.

Для интернет-магазина заказов это выглядит так:

- один FastAPI-процесс обслуживает каталог, корзину, оформление заказа, оплату и статусы;
- одна PostgreSQL: таблицы `products`, `cart_items`, `orders`, `payments`, `stock`;
- один деплой: обновили код — выкатили один контейнер/сервис;
- транзакция «создать заказ + списать остаток + зарезервировать оплату» может жить в одной БД-транзакции.

Это не значит, что код хаотичный. Это значит: **границы модулей не совпадают с границами процессов**.

### Реальный сценарий: оформить заказ

Пользователь нажимает «Оформить» во фронте. Запрос `POST /api/orders` попадает в один процесс:

1. роут принимает JSON корзины;
2. сервис проверяет цены и остатки в тех же таблицах;
3. репозиторий пишет `orders` и уменьшает `stock.qty`;
4. биллинг в том же процессе создаёт запись `payments` со статусом `pending` или сразу `paid` (если имитация);
5. ответ JSON с `order_id` уходит клиенту.

Всё это — один процесс, одна БД, одна транзакция (или короткий набор запросов без распределённого консенсуса).

Пример скелета:

```python
@router.post("/orders")
def create_order(body: CreateOrderIn, db: Session = Depends(get_db)):
    with db.begin():
        order = order_service.place(db, body.user_id, body.items)
        billing_service.charge(db, order.id, order.total)
        stock_service.reserve(db, body.items)
    return {"order_id": order.id, "status": order.status}
```

В монолите `order_service`, `billing_service` и `stock_service` — это **пакеты одного приложения**, а не отдельные сети и деплои.

### Сильные стороны монолита

**Простота рассуждений.** Нет сетевых таймаутов между «заказом» и «складом». Нет частичных отказов вида «заказ создан, а оплата сервис недоступен». Ошибка — исключение в одном процессе.

**Транзакции.** ACID в одной PostgreSQL закрывает инварианты: нельзя оставить заказ без резерва остатка, если вы пишете оба изменения в одной транзакции.

**Операционка.** Один образ Docker, один healthcheck, один набор логов, один CI pipeline. Для команды из 2–5 человек это часто выигрыш в скорости, а не проигрыш.

**Рефакторинг границ.** Перенести функцию из `orders` в `billing` — это перемещение кода и тестов, а не миграция данных между сервисами и согласование контрактов HTTP.

### Слабые стороны монолита

**Общий риск выката.** Баг в каталоге может уронить процесс, который обслуживает и оплату. Изоляция сбоев слабее, чем у отдельных процессов.

**Масштабирование целиком.** Если узкое место — тяжёлые отчёты по каталогу, вы масштабируете весь процесс, включая биллинг, хотя нагрузка там другая.

**Рост связанности.** Без дисциплины модулей монолит превращается в «большой ком»: сервисы тянут чужие таблицы, циклические импорты, скрытые зависимости.

**Командная конкуренция.** Много людей в одном репозитории и одном деплое увеличивают конфликты merge и страх «сломать прод одним релизом».

### Монолит ≠ плохой код

Частая ошибка: путать монолит с антипаттерном «god object». Монолит может быть:

- слоистым (api → service → repository);
- модульным внутри (см. следующий урок);
- с очередями и воркерами *внутри* того же деплоя (фон через Celery/arq, но всё ещё один продукт).

Монолит — про **единицу поставки**, не про запрет на чистую структуру.

### Когда монолит — правильный выбор

- один продукт, одна команда или малая команда;
- домен ещё нестабилен: часто меняются границы «что такое заказ»;
- нужна сильная консистентность между частями (заказ + остаток + платёж);
- нет доказанной необходимости независимого масштабирования частей;
- операционная зрелость ниже, чем желание «как в Netflix».

Интернет-магазин на старте почти всегда выигрывает от монолита: быстрее проверить бизнес-модель, проще отладить путь заказа, меньше инфраструктуры.

### Когда НЕ дробить систему

Не дробите, если:

1. **Нет независимых команд** с разными релизными циклами. Микросервисы без организационной нужды дают только сетевую сложность.
2. **Инварианты пересекают границы.** «Заказ нельзя создать без резерва» в распределённой системе требует саг, идемпотентности, компенсации — дороже, чем транзакция в одной БД.
3. **Объём и нагрузка не требуют.** 100 заказов в день не оправдывают оркестратор, service mesh и 12 репозиториев.
4. **Нет наблюдаемости.** Без трейсов, метрик и культуры on-call отдельные сервисы становятся «распределённым монолитом боли».
5. **Границы домена неясны.** Если вы не уверены, где заканчивается catalog и начинается orders, разрезание по процессам зацементирует ошибку.

Правило: сначала **чёткие модули в одном процессе**, потом — вынос процесса, если появилась измеримая причина (нагрузка, команда, изоляция сбоя, отдельный жизненный цикл данных).

### Как выглядит структура репозитория монолита магазина

```text
app/
  api/          # HTTP-роуты
  services/     # правила заказа, оплаты, склада
  repositories/ # SQL
  models/       # ORM / схемы таблиц
  workers/      # фоновые задачи того же продукта
```

Один `docker-compose`: `api`, `postgres`, иногда `redis`. Фронт ходит только в API. Это уже полноценная архитектура.

### Типичные ошибки

- Считать монолит временным мусором и не вводить границы модулей «потому что потом микросервисы».
- Тянуть бизнес-логику в роуты: монолит быстро становится нечитаемым.
- Делать «микросервисы» как отдельные Flask-приложения с общей БД — это худшее из обоих миров: сеть есть, транзакций нет.
- Масштабировать вертикально бесконечно, игнорируя горячие запросы, вместо профилирования внутри монолита.

### Практика мышления

Возьмите путь «оформить заказ» и запишите:

- сколько процессов участвует? (в монолите — один);
- сколько БД? (одна);
- где проходит транзакция?
- что сломается, если упадёт процесс?

Если ответы простые и этого достаточно бизнесу — монолит работает.

### Монолит и фон: это не противоречие

Монолит может включать воркеры того же продукта: письмо уходит из очереди Redis, PDF чека строится ночью, но **доменные таблицы** всё ещё общие, деплой — один релизный контур. Фон не превращает систему в микросервисы, пока у вас нет независимых границ поставки и отдельных БД на сервис.

Отличие критично: «один репозиторий + Compose с api и worker» — нормальный монолит. «Двенадцать репозиториев с общей БД» — нет.

### Эволюция без героизма

Практичный путь для магазина:

1. монолит со слоями;
2. модульные пакеты catalog/orders/billing;
3. события/очередь для писем и отчётов;
4. вынос процесса только при доказанной боли.

Прыжок сразу на шаг 4 без 2–3 почти всегда дороже, чем кажется на диаграмме.

### Чеклист «монолит здоров»

- [ ] Роуты тонкие, правила в service
- [ ] SQL сосредоточен в repository
- [ ] Нет скрытых глобальных синглтонов с доменным состоянием
- [ ] Миграции БД версионируются
- [ ] Есть тесты на checkout-инварианты
- [ ] Логи содержат `order_id`

Если чеклист красный — чините монолит, не маскируйте микросервисами.

### Монолит глазами команды

Два разработчика в одном репозитории — норма. Двадцать без модульных CODEOWNERS и без CI — уже социальная проблема, которую микросервисы лишь маскируют стоимостью сети. Организационный закон Конвея действует в обе стороны: структура команд формирует архитектуру; насильно разрезанная архитектура без команд-владельцев гниёт.

## Коротко

Монолит интернет-магазина — один процесс и одна БД: заказ, склад и биллинг живут вместе и могут делить транзакцию. Это ускоряет разработку и упрощает консистентность. Дробить систему стоит только при явной нужде в независимых деплоях, нагрузке или командах — иначе вы купите цену сети без выгоды.
