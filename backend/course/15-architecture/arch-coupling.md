# Связанность и зацепление

## Цель

Различать вредную связанность модулей заказов и полезное зацепление внутри модуля. После урока вы оцените пару компонентов: «слишком связаны» или «нормально сцеплены внутри».

## Что уже нужно понимать

SoC и граф зависимостей. В литературе: coupling (связанность между модулями) и cohesion (зацепление внутри). Нам нужны практические признаки в коде Orders API, не формулы из учебника 70-х.

## Объяснение

**Высокое зацепление внутри** — хорошо: всё в `orders/domain.py` про жизненный цикл заказа. Методы и данные про одно.

**Высокая связанность между** — плохо, когда `orders.service` не может жить без внутренних функций `mailer.templates.render_order_html` и ещё лезет в `warehouse.tables`. Правка склада ломает отмену заказа.

Виды связанности (упрощённо):

- по данным (общий Mutable global);
- по контролю (A напрямую дергает внутренности B);
- по внешнему формату (оба хардкодят один JSON без явного контракта);
- по времени (A должен вызваться строго до B в одном потоке без явной оркестрации).

Ослабление: интерфейсы/порты, события, явные DTO на границе, не шарить ORM-модели между фичами.

Связанность нулевая невозможна: система должна работать вместе. Цель — связанность через стабильные контракты, а не через кишки.

## Термины

- **Coupling** — сила зависимости между модулями.
- **Cohesion** — насколько части модуля про одну задачу.
- **Контрактная связанность** — зависимость от явного интерфейса (приемлемо).
- **Общая область** — shared DB table без владельца (опасно).

## Как это устроено

Пример роста: заказы и уведомления. Плотная связь: сервис импортирует SMTP-клиент. Слабее: порт `Notifier`. Ещё слабее для пишущей стороны: запись события `OrderCancelled` в outbox; mailer читает отдельно. Цена — задержка и сложность; выгода — mailer падает без отката отмены, если так задумано.

Общая БД двух «сервисов» без границ — скрытая сильная связанность: вы думаете, что независимы, но схема связывает крепче REST.

Внутри монолита измеряйте связанность импортами и «сколько модулей надо открыть для одной правки».

## Пример

```python
# Сильная связанность: заказы знают кишки склада
class OrderService:
    def ship(self, order_id: int) -> None:
        order = self._repo.get(order_id)
        order.ship()
        self._repo.save(order)
        # лезем во внутренний SQL склада
        self._db.execute("UPDATE warehouse_bins SET busy=0 WHERE order_id=:id", {"id": order_id})


# Слабее: явный порт
class WarehousePort(Protocol):
    def release_bin(self, order_id: int) -> None: ...

class OrderService:
    def __init__(self, repo, warehouse: WarehousePort):
        self._repo = repo
        self._warehouse = warehouse

    def ship(self, order_id: int) -> None:
        order = self._repo.get(order_id)
        order.ship()
        self._repo.save(order)
        self._warehouse.release_bin(order_id)
```

## Разбор примера

В первом случае `OrderService` хрупко зависит от схемы `warehouse_bins`. Переименование колонки ломает отгрузку. Во втором — зависимость от операции `release_bin`. Склад может сменить таблицы; контракт метода живёт дольше.

Зацепление `OrderService` остаётся высоким: всё про сценарии заказа. Связанность со складом стала контрактной.

## Типичные ошибки

- Путать «мало импортов» с хорошим дизайном (один god-файл без импортов тоже плох — низкое зацепление по смыслу разрезания).
- Shared database между командами без владельца таблицы.
- События ради событий, когда хватило бы вызова порта в процессе.

## Что запомнить

Высокое зацепление внутри модуля — плюс. Высокая связанность через кишки — минус. Связывайте контрактами. Общая БД без правил — ловушка. Оценивайте число мест правки на одну фичу.
