# Доменный слой

## Цель

Вынести правила жизненного цикла заказа в доменный слой так, чтобы их можно было тестировать без HTTP и SQL. После урока вы опишете переходы статусов и инварианты на сущности `Order` (или доменных службах).

## Что уже нужно понимать

Слои и сервис-оркестратор. Домен — сердце смысла: «что есть заказ в нашей системе» и «какие изменения допустимы». Не путать с «все классы с большой буквы».

## Объяснение

У заказа есть жизненный цикл: `new → packing → shipped`, ветка `cancelled` из `new`/`packing`, но не из `shipped`. Это инварианты. Если они размазаны по роутам и SQL CHECK вперемешку без единого места, новое правило «нельзя cancel после печати этикетки» придётся искать по всему репо.

Доменный слой выражает эти правила языком проекта: методы `start_packing`, `ship`, `cancel`, объекты-значения (деньги, адрес), политики. Без импорта FastAPI и Session.

Когда логика не принадлежит одной сущности (резерв склада + заказ), появляется доменная служба или прикладной сценарий, который координирует несколько частей — но правило «склад» не обязано знать HTTP.

Анемичная модель: у `Order` только поля, все `if` в сервисе. Работает, пока ветвлений мало. При росте статусов методы на сущности читаются лучше. Не нужно насиловать «всё в методы» для тупых CRUD-полей.

## Термины

- **Инвариант** — условие, всегда истинное после операции.
- **Агрегат** — кластер объектов с корнем (заказ + позиции).
- **Value object** — объект без собственного идентификатора (Money, Address).
- **Доменное событие** — факт «OrderShipped» внутри модели (ещё не Kafka).

## Как это устроено

Сервис загружает агрегат, вызывает доменную операцию, сохраняет. Домен может вернуть список доменных событий; прикладной слой опубликует их в outbox/Kafka. Так правило «после ship» отделено от транспорта брокера.

Тесты домена — самые быстрые и ценные для регрессий статусов. Пишите их раньше, чем e2e на весь Docker Compose.

## Пример

```python
from dataclasses import dataclass, field

ALLOWED = {
    "new": {"packing", "cancelled"},
    "packing": {"shipped", "cancelled"},
    "shipped": set(),
    "cancelled": set(),
}

@dataclass
class Order:
    id: int
    customer: str
    city: str
    status: str
    events: list[str] = field(default_factory=list)

    def _transit(self, new_status: str) -> None:
        if new_status not in ALLOWED[self.status]:
            raise Conflict(f"{self.status} → {new_status} forbidden")
        self.status = new_status

    def start_packing(self) -> None:
        self._transit("packing")
        self.events.append("OrderPackingStarted")

    def ship(self) -> None:
        self._transit("shipped")
        self.events.append("OrderShipped")

    def cancel(self, reason: str) -> None:
        if not reason.strip():
            raise ValueError("reason required")
        self._transit("cancelled")
        self.events.append("OrderCancelled")
```

```python
def test_ship_requires_packing():
    order = Order(1, "A", "B", "new")
    try:
        order.ship()
        assert False, "should fail"
    except Conflict:
        pass
```

## Разбор примера

Таблица `ALLOWED` делает политику переходов явной: её можно показать продукту. Методы добавляют события — задел на интеграцию без знания Kafka внутри домена.

Тест не поднимает БД: чистое правило. Сервис после `ship` заберёт `events` и опубликует, затем очистит — или репозиторий сохранит outbox.

`reason` для cancel проверяется в домене: пустая причина бессмысленна бизнес-языком, не только «строка в JSON».

## Типичные ошибки

- Инварианты только в UI.
- Домен импортирует ORM и начинает «ленивые» запросы внутри метода сущности.
- Путать доменные события с сообщением в брокере один-в-один без адаптера.
- Overengineering value objects на каждом булевом флаге.

## Что запомнить

Домен держит смысл заказа и инварианты. Тестируется быстро. Сервис оркестрирует, домен решает допустимость. События домена — факты для интеграций. Таблица переходов лучше размазанных if.
